## 这本书解决什么问题

市面上的 AI 学习资料常见两种毛病：

1. **散**：PDF、笔记、题库各说各话，学完不知道知识点之间什么关系，更不知道面试会问到哪一层。
2. **飘**：上来就讲 Agent、讲 RAG，读者连一个能跑的后端接口都没写过，代码抄下来也不知为什么。

本教材的做法是：**先把资料拆成最小知识点，再按「地基 → 工具 → 原理 → 框架 → 系统 → 求职」
重新排列**，并让**同一个项目贯穿全书**（见 [`STYLE.md`](STYLE.md) 第五节），
最后把题库按知识点打散嵌回各章。

## 素材审计结论（重要）

审计按**汉字量**而非页数计量，结果修正了多处初判：

- **第 1 篇素材尚可**（0.61）、**第 5 篇偏薄且分布极偏**（0.47）——后者的素材有一多半
  集中在「检索增强」一章（`5.4` 单独 1.44，计划值上调后），而向量库与综合项目两章只有 0.05 / 0.28。
  所以「整篇够用」不能当作「每章都能整理改写」。
- **第 2、3、4 篇都不足**（0.36 / 0.22 / 0.14）。名义上「几份素材」不等于几份都能用：
  三份 AI 工具手册、两本 LangChain 素材都已**按实际用到的节**逐份实测权重
  （实测定下来 LangChain 三章是 230 / 330 / 1,567 汉字，对应权重 0.101 / 0.145 / 0.688）；
  LangChain + LangGraph 两本合计仅 **4,680 个汉字**且无规范代码块——页数看着不少，
  实际撑不起 5 章。
- **题库篇驱动**：题量充足但质量分层，**1038 道 AI Agent 题是通用套话且存在专题漂移**，
  只能当考点索引；后端题库实为 **Java 体系**（JVM/Spring 占比高，网络仅出现 0 次）。
- **意外收获**：Python 手册的打分只看编号章节会漏掉 **55% 的内容**——
  3.0 万字的「进阶块」藏在无编号标题里，覆盖异常、日志、装饰器、OOP 进阶、
  网络编程（TCP/IP 五层协议）与并发编程，直接把第 1 篇的 1.7、1.8 从"缺素材"变成"充裕"。

## 体系缺口（现有规划少了哪块）

结论是：现有规划**不是章节不够细，而是体系少了一整块**——
从「能做出 demo」到「能交付一个有 SLO 的产品」之间的工程化与交付环节。

| 优先级 | 缺口 | 现状 |
| --- | --- | --- |

| **P0** | 部署与交付（容器化、CI/CD、运维） | 学完只会在本地跑 `uvicorn` |
| **P0** | AI 系统设计面试 | 题库只覆盖知识点，不覆盖方案设计 |
| P1 | 评测流水线、可观测性、安全落地、成本工程、前端流式交互、数据合规 | 只有理论或完全没有 |
| P2 | 本地推理、微调、多模态与语音、多租户计费、GraphRAG | 差异化加分项 |

## 脚本用法

原始资料已完整归档且未做任何修改，素材库与审计报告都可随时重新生成：

```bash
cd 学生就业AI开发教材

# 1. 抽取文本素材（raw/ → sources/）
python tools/extract_sources.py --report   # 只统计文本密度，不写文件
python tools/extract_sources.py            # 重建 sources/ 与 sources/README.md

# 2. 审计素材覆盖度（生成逐章报表）
python tools/audit_coverage.py             # 控制台报表
python tools/audit_coverage.py --pool      # 素材池明细，核对分段
python tools/audit_coverage.py --out COVERAGE.md   # 刷新 COVERAGE.md

# 3. 校验官方文档链接
python tools/check_refs.py                 # 校验全部（并发 HEAD，报告失效与跳转）
python tools/check_refs.py --only-broken   # 只看失效与跳转
python tools/check_refs.py --offline       # 只解析链接清单，不发请求

# 4. 校验正文一致性（每章写完必跑，零错误才算定稿）
python tools/lint_book.py                  # 校验全部章节（含 GLOSSARY 术语日志逐章对账）
python tools/lint_book.py --only 1.1       # 只校验指定章
python tools/lint_book.py --self-test      # 夹具自检（字数口径 / 接线 / 计划行 / 实测编号 / 术语日志）

# 5. 改稿前查引用：给出术语 / 数字 / 结论，列出全书哪些章用了它
python tools/trace_refs.py "上下文工程"                # 术语：逐行列出命中位置
python tools/trace_refs.py "26,091" --from 2.2         # 数字：26,091 / 26091 / 全角都算同一个
python tools/trace_refs.py "真正的成本从写代码转移到了验证" --fuzzy   # 结论被改写的地方
python tools/trace_refs.py "RAG" --scope book --quiet  # 只列章，直接当回改清单
python tools/trace_refs.py --self-test                 # 合成反例自检（会响 / 不乱响）

# 6. 把校验接成提交前钩子（只需装一次；之后漏跑不了）
python tools/install_hooks.py              # 安装（设置本仓库 core.hooksPath）
python tools/install_hooks.py --status     # 看当前是否启用
python tools/install_hooks.py --self-test  # 用一个临时违规章节验证钩子真能拦下
python tools/install_hooks.py --uninstall  # 卸载
```

## 防丢失机制（为什么这部长文不会越写越偏）

三十万字跳 68 章，靠「记得」必然漂移。本仓库把记忆**外置成文件**，并把校验**接成强制流程**：

| 层次 | 做法 | 防的失效 |
| --- | --- | --- |
| 单一事实来源 | [`GLOSSARY.md`](GLOSSARY.md) 术语唯一写法 | 术语漂移 |
| 单一事实来源 | [`REFERENCES.md`](REFERENCES.md) 技术结论出处 | 事实过时 / 臆造链接 |
| 单一事实来源 | [`LEDGER.md`](LEDGER.md) 知识点→章节落点 | **关键信息静静漏掉** |
| 机械校验 | `tools/lint_book.py` 12 项检查 | 体例 / 引用 / 篇幅 / 跨章重复 / 标题空行 |
| 数字对账 | `tools/audit_coverage.py --check` | 文档里的汇总数字与实测漂移——含**篇级小计**与 **README 的总数/规划总量/全书结构表**（曾出现 PLAN 写 1.24 而实测已是 1.25，以及文首写「第 2 篇 92,607 字」而实测已是 117,020） |
| 篇幅表自对账 | `tools/audit_coverage.py --check`（逐节校准表） | **LEDGER 里那张「事前估 / 实测」逐节表自己加不起来**——它既要校准后面几章的估算，又会在定稿后停下不动：加这道当天就查出四章四错（4.5 少 95、5.2 把同一行抄了两遍、5.3 少 1,276、5.4 少 768） |
| 行数格对账 | `tools/check_runnable.py`（第六道） | 正文章节里那些「文件 ＋ 行数」的表格**两个门都不管**（既不是代码块，也不是汇总数字）——文件改多了、章节里的数不动，谁也不会报错。接上当天在四章查出 **14 格已漂**（4.2 ×4、4.3 ×6、5.6 ×2、5.7 ×1、5.8 ×1，最久的差 85 行）。树那一侧的同一条由 `scripts/recap.py` 的第四条对账管着，两处各带反向守与一条「改一行就红」的夹具 |
| 条数格对账 | `tools/check_runnable.py`（第七道）＋ `zhizhou-v5/scripts/recap.py`（第五条） | 正文与树里文档中那些「N 条夹具」「N 条用例」（正文四棵树合计 **62 处**——认了中文数字与「个」之后从 38 涨上来，多出的那一批此前一格都没被核过）是同一类「两个门中间的数」：数字写错了既不动代码块也不动汇总。**两个数都跑出来**、两侧用同一把尺子：夹具数跑一次那个脚本的 `--self-test`，用例数导入那个测试模块、数 `dir()` 里的 `test_`（拿不到才退回数文件，两把尺子不一样时另报一行）。接上当天在架构文档里咬到两处；而书侧这道自己的肚子里也掏出两处同族错：十八条夹具因为 `cases += ...` 写在循环之后而一条都没跑过（分母却算它们通过了），且那个分母本身是手写算式（少算七处） |
| 用例引用对账 | `tools/check_runnable.py`（第九道） | 围栏里那句 `python -m pytest tests/x.py -q # 7 passed` 与 `# 全树 89 条` 也是**手抄的第二份数字**——而它们比表格里的更难被发现，因为它们长得像「说明文字」。树从 89 长到 150 条之后，正文里还留着 89、122 与四处 `N passed`。现在：单文件主语与该测试文件实跑条数比、`全树 N 条` 与整棵树比，数可以写在命令的下一行，但主语只在同一个围栏内继承。同一轮里条数格也认了**中文数字与「个」**（表里写着「七个用例」而这种写法此前一格都没被核过，当天报出四处漂），边界是**中文的「一」是量词不是条数**（「里有一条用例」在 5.4 出现两次） |
| 输出块对账 | `tools/check_runnable.py`（第八道） | 正文里**贴在围栏里的「真实输出」**靠人跑一遍核对（`STYLE` 8.8 第 2 条）——改一个数字、改一个词都不会让任何别的门响，而那些数看起来永远像真的（5.9 那句「夹具 23 条」就是在脚本长到 27 条之后还写着 23）。现在只要那段输出前面标了命令（` ```text $ python scripts/x.py --offline `），第八道就**重跑那条命令**、逐行比引用的行还在不在，**顺序**也算（同一棵树同一条命令只跑一次，与离线入口那道共用）。接上当天标了 **28 个块**，其中每个块的引用行都只被一条命令解释得了 |
| 术语日志对账 | `tools/lint_book.py`（术语日志） | `GLOSSARY.md` 的「三、维护记录」是术语表的**第二份手写账**：有词条的章漏了一行、或一行被「少一个换行」粘成 4 格，不会让任何数字变难看。加这道当天就查出四处缺行（1.12 / 2.1 / 2.6 / 5.6，其中 1.12 那条回头查明是首现章记错）与三处粘行（3.6 / 5.2 / 5.8，含当轮自己造的一处） |
| 交付清单对账 | `tools/audit_coverage.py --check`（PROJECT 字数） | `PROJECT.md` 的「正文 N 有效字」与正文漂了——它和 PLAN 是两份独立手写的数字，加这道当天报出六处（最久的已错三天） |
| 改稿前查引用 | `tools/trace_refs.py` | 改了术语/数字/结论却漏改别处（正文是硬换行的，`grep` 看不见接缝） |
| 逐章审阅 | [`STYLE.md`](STYLE.md) 8.8 四项 | 台账反向回查 / 声称输出必须实跑 / 结论回到官方文档 / 偏差归因 |
| 篇幅口径 | 有效字数 = 汉字 + 15 × 有效代码行（**围栏行不计入**） | 「代码密集」被误判成偷工减料，或反过来放宽容差遮盖真问题 |
| 口径自检 | `tools/lint_book.py --self-test` | 算法静默退化：曾把围栏行也算作内容，全书虚增 20,130 字而输出看着正常 |
| 门槛自检 | `tools/audit_coverage.py --self-test` | 对账靠「解析文档里的句子」，句式一变就落空成摆设；夹具从**当前真实文档**派生错误，书在长也不用改 |
| 强制流程 | `.githooks/pre-commit`（git 钩子） | 漏跑校验就提交不了 |
| 最后一道门 | `.github/workflows/book-checks.yml` | 绕过钩子也会在 CI 被拦住 |

每章走五步闭环（规范见 [`STYLE.md`](STYLE.md) 第八节）：

```
落事前估（动笔之前；写进 tools/audit_coverage.py 的该章注释 ＋ PLAN 的「写作前校正」行）
→ 通读该章素材 → 知识点逐条进 LEDGER（标 ⬜） → 写正文
→ 回填状态（✅ / 🔀 / ⏭）与逐节表的「事前估」列 → 跑 lint 到零错误 → 一章一提交
```

紧急情况可绕过本机钩子（`SKIP_BOOK_CHECKS=1 git commit ...` 或 `--no-verify`），
但 CI 会用同一套脚本再跑一遍——**绕过只是推迟，不是豁免**。

依赖：`pdftotext`（poppler）、Python 3.10+。

抽取参数说明：PDF 必须用 `pdftotext -enc UTF-8 -raw`——默认编码会**静默丢掉全部中文**，
而 `-layout` 会把 LangChain 那类 PDF 的行号与正文打乱。
