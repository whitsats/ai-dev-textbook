# 6.2 多厂商接入：Messages、Responses 与 OpenAI 兼容层

## 本章导读

6.1 选好了模型，这一章解决「怎么把它接进来」。三家的 API 不是三个名字，是**三种形状**：同一个输出上限在三家叫三个名字（而且其中一家**必填**）；系统提示在一家是顶层字段、在另一家也是顶层字段但叫别的名字、在第三家是消息数组里的第一条；工具参数在一家递给你一个**对象**、在另外两家递给你一个 **JSON 字符串**。这一章先立一个**规范形状**，再让三个适配器各自翻译，然后用六组读数证明「翻得对」这件事是可以被机器核的——而不是靠人看一遍。

这一章在书里有个前身：4.1 量过手写版的模型出口 `app/llm/client.py` 是 **468 行**，框架版把它压成一次 `init_chat_model`（**78 行**）。本章回头把那个 468 行里属于「方言」的那一部分**单独做一遍**，并把它从一段代码变成**一张逐格能核的表**。与 6.1 一样，它**不调模型**：读数全部来自这张表与三段夹具流。

## 6.2.1 三家不是三个名字，是三种形状

一线开发者对多厂商接入最常见的心算是「换个 `base_url`、换个 key」。这个心算在**同一家的两种端点之间**大致成立，跨厂商就不成立了——因为三家对同一件事的处置**不止名字不同，形状也不同**：

- **系统提示**：一家把它放在顶层字段 `system` 里（而且是**字符串**）；另一家也放顶层，但字段叫 `instructions`；第三家把它当成对话数组里的第一条 `role="system"` 消息；
- **工具结果**：一家把它塞进一条 user 消息的内容块里；另一家把它做成**与消息平级的 item**；第三家发一条独立的 `role="tool"` 消息；
- **输出上限**：一家叫 `max_tokens` 而且**必填**；另一家叫 `max_output_tokens`；第三家叫 `max_completion_tokens`——名字最长的那一个反而最宽松（选填）。

「兼容层」这个词因此要说得准确一点：它**不是**「一套通用形状」，而是**一家的形状 ＋ 一个能翻译的端点**。它兼容的是那一家的客户端与请求体，不是「所有厂商的并集」。本章的第三列就叫 `chat`（Chat Completions 兼容层），它是本章唯一一个「兼容」字样的方言——而它在能力矩阵里恰好是限制最多的那一列（见 6.2.8）。

> 💡 **提示**：本章的每个读数都来自 `zhizhou-v6/scripts/wire_reader.py --offline`。它**不调模型、不要密钥、不要网络**：它把同一个规范请求翻成三家的载荷、把三家的答复翻回来、再把三段夹具流解析成同一段答复。所以它能在提交门里一直跑——与 6.1 同一条纪律：**读数要么能复算，要么别写进正文**。

## 6.2.2 规范形状：一个请求、一个答复

先把「一次调用」写成一个不依赖任何一家的形状，再让适配器各自翻译：

```python
# app/wire.py —— 字段顺序与「翻译表」一致，方便逐行对读
@dataclass(frozen=True)
class Request:
    """一次调用。字段顺序与「翻译表」一致，方便逐行对读。"""

    model: str
    system: str
    messages: tuple[Message, ...]
    tools: tuple[Tool, ...] = ()
    max_output_tokens: int | None = None
    temperature: float | None = None
    stream: bool = False
    dialect: str = "messages"
```

这一个类里有三处是**刻意**的，每一处都对应一种会被重复犯的错：

1. **`system` 是它自己的字段**。规范形状里**没有 `system` 这个角色**——`Message.role` 只有 `user` / `assistant`。理由不是洁癖：三家里有两家把系统提示放在顶层，第三家放在数组里；留在数组里的话，每个适配器都要再判断一次「这条是不是系统消息」，而那三次判断迟早会不一致；
2. **`max_output_tokens` 是可选的**。这是「规范形状取三家**最宽**的那一个」这条判据的落点：如果取最窄（必填），另外两家会被无谓地要求一个数；取最宽之后，**必填的那一家在翻译时报错**（见 6.2.4 的代码节选）——报错的位置从「调用方」挪到了「翻译那一行」，而后者只有一个地方要改；
3. **规范档 `stop` 不是任何一家的取值**。它取的是 `end_turn` / `max_output` / `tool_call` / `stop_sequence` / `refusal` 这五个**中立名**，翻译表负责映射（见 6.2.6）。

一个请求能不能被翻译，是可以在**发出去之前**问出来的：

```python
# app/wire.py —— 把「翻过去才发现」的错提前
    if not req.system.strip():
        bad.append("系统提示是空的——三家里有一家把它当必填的顶层字段")
    if not req.messages:
        bad.append("一条消息都没有")
```

`validate()` 在真请求上返回空列表，在四类坏请求上各说一句话（缺系统提示、结果指向一次不存在的调用、工具 schema 不是对象、方言名写错）。它与 6.1 的 `violations()` 是同一个形状：**空列表才是正常**。

## 6.2.3 翻译表：8 个字段，没有一栏同名

把「三家不一样」从一句印象变成能逐格核的东西，只需要一张表：规范字段 × 三种方言的**落点**。

| 规范字段 | `messages` | `responses` | `chat`（兼容层） |
| --- | --- | --- | --- |
| 系统提示 | `system`（顶层字段） | `instructions`（顶层字段） | `messages[0]`（`role=system`） |
| 对话历史 | 数组，角色只有 `user`/`assistant` | `input` 的 item 列表 | 数组，角色有四个 |
| 工具的 schema | 一个字段 `input_schema` 装它 | 与 `name` 同级（扁平） | 嵌一层 `function` |
| 工具参数 | `input`，**对象** | `arguments`，**JSON 字符串** | `function.arguments`，**JSON 字符串** |
| 工具结果 | 消息里的一个块 | 与消息平级的 item | 一条独立消息 |
| 输出上限 | `max_tokens`（**必填**） | `max_output_tokens` | `max_completion_tokens` |
| 「为什么停」 | 一个字段 `stop_reason` | `status` ＋ `incomplete_details.reason` | 一个字段 `finish_reason` |
| 口径 / 版本 | `anthropic-version` 请求头 | 请求体里的 `store`（默认 true） | 没有 |

这张表在树里就是 `FIELD_MAP`，而它的**行数与列数是被读出来的**，不是描述出来的：

```text $ python scripts/wire_reader.py --offline
名字层：8/8 个字段**三家各说各的（没有一栏同名）**；形状只有一种的字段 0 个
形状层：3 种形状的字段 4 个（messages、tools[].schema、tool_result、口径/版本）
形状层：2 种形状的字段 4 个（system、tool_call.arguments、max_output_tokens、stop）
```

三条读法：

1. **名字层是 8/8**——八栏里**没有一栏是同名的**。这条数不是「差不多」，它是「一共八栏，八栏都要单独处理」；
2. **形状层分三堆**（3 种形状 4 个、2 种形状 4 个、1 种形状 **0** 个）。所以「换厂商要改多少」有一个可算的上界：**四格要改三处**（历史、工具 schema、工具结果、口径），另外四格只改一处（顶层那两格、参数那一格、上限那一格）；
3. **真正省事的是形状只差一档的那四格**（`system`、工具参数、输出上限、停止原因）：它们的改动是**一行**（换个键名、加一次 `json.loads`、换个字段），而那 4 个「三种形状」的格要动的是**结构**。这条分堆是本章唯一一条能直接指导改代码的结论。

表里的第一列与最后一列也不是装饰：`WIRE_AS_OF = "2026-09-17"` 与 **6 页官方文档**（`SOURCES`）都进了树——与 6.1 的价格表同一条规矩：**没有出处的格子不进表**。

## 6.2.4 同一个请求翻成三种载荷

给三个适配器**同一个请求**（一段系统提示 ＋ 3 条消息，其中包含一次完整的工具往返 ＋ 2 个工具），数一数三份载荷：

```text $ python scripts/wire_reader.py --offline
Messages（Anthropic）        路径 /v1/messages         key 路径  27 个  JSON   806 字节
Responses（OpenAI）          路径 /v1/responses        key 路径  27 个  JSON   812 字节
Chat Completions（兼容层）      路径 /v1/chat/completions key 路径  28 个  JSON   862 字节
三份载荷都有的 key 路径：1 个（model）
```

三条读法：

1. **三份载荷的 key 路径是 27 / 27 / 28**——同一件事，三种写法的**叶子数**几乎一样。「三家不一样」不是「三家复杂度不一样」；
2. **字节数是 806 / 812 / 862**：兼容层那份最大，多出来的 56 字节几乎全部来自 `function` 那一层（工具 schema 与函数名都嵌进去了）；
3. **三份载荷共有的 key 路径只有 1 个：`model`**。这一条最值钱：它把「换个厂商不是换个 `base_url`」从一句经验变成一个数——**两份载荷之间只有模型名是同一个位置上的同一个名字**。

正因为共有面这么小，翻译要发生在**边界**（适配器里），而不是在业务代码里。4.1 那个 468 行的手写 client 里，真正属于「方言」的是这个边界；本章把它做成三个类，每个类只有四个动作：`to_wire`（请求 → 载荷）、`from_wire`（答复 → 规范答复）、`from_stream`（SSE → 规范答复）、`headers`（认证与口径头）。

## 6.2.5 工具参数：一家给对象、两家给字符串

先把三份**真载荷**里的那一次工具调用取出来看：

```text $ python scripts/wire_reader.py --offline
Messages（Anthropic）        content[].input                              object  {"q": "北京 天气"}
Responses（OpenAI）          input[].arguments                            string  "{\"q\": \"北京 天气\"}"
Chat Completions（兼容层）      messages[].tool_calls[].function.arguments   string  "{\"q\": \"北京 天气\"}"
三份形状解出来的规范对象是否逐个相同：是　{"q": "北京 天气"}
坏 JSON（chat）：chat：参数不是合法 JSON（Expecting property name enclosed in double quotes）；原文前 60 字符：'{"q": "北京", '
坏 JSON（responses）：responses：参数不是合法 JSON（Expecting property name enclosed in double quotes）；原文前 60 字符：'{"q": "北京", '
```

一个对象、两个字符串——而那个字符串**是模型生成的**，所以它可能不是合法 JSON：

```python
# app/dialects.py —— 那两家的 JSON 字符串在这里解开
    try:
        got = json.loads(raw or "{}")
    except json.JSONDecodeError as exc:
        raise WireError(f"{where}：参数不是合法 JSON（{exc.msg}）；"
                        f"原文前 60 字符：{raw[:60]!r}") from exc
    if not isinstance(got, dict):
        raise WireError(f"{where}：参数解出来是 {type(got).__name__}，不是一个对象")
    return got
```

**坏 JSON 必须报错**，不许静默退回 `{}`：一个空字典会在下游被读成「模型这次没传参数」，而线上真正的现象是「模型的参数被截断了」——**两者长得像，修法完全不同**。上面那个 `where` 参数就是为报错服务的：它会带上这是**流里**的第几次调用、还是**非流式答复里**的哪一个 item（真报错的样子在本章末尾的演示里）。

第三条读法是为什么：**这两家为什么用字符串？** 因为流式。参数在线上是**一片一片来的**（Messages 叫 `input_json_delta`、兼容层叫 `function.arguments` 的分片），到齐了才是一个对象。所以「统一成对象」这件事只能做在**收齐之后**，而这正好是适配器的位置。

## 6.2.6 「为什么停」的 15 格：空与撞车

「模型为什么停下来」在业务代码里通常只有一处用处：判断**要不要接着跑一次工具**。而这件事在三种方言里各有各的答案：

| 规范档 | `messages` | `responses` | `chat` |
| --- | --- | --- | --- |
| `end_turn` | `end_turn` | `completed` | `stop` |
| `max_output` | `max_tokens` | `incomplete` ＋ `max_output_tokens` | `length` |
| `tool_call` | `tool_use` | `completed`（**撞车**） | `tool_calls` |
| `stop_sequence` | `stop_sequence` | **空** | `stop`（**撞车**） |
| `refusal` | `refusal` | **空** | `content_filter` |

```text $ python scripts/wire_reader.py --offline
Messages（Anthropic）        能原样表达的 5/5 档　空 0 格　与别的档撞车 0 格
Responses（OpenAI）          能原样表达的 2/5 档　空 2 格　与别的档撞车 1 格
Chat Completions（兼容层）      能原样表达的 4/5 档　空 0 格　与别的档撞车 1 格
表自身：15 格逐格核过（正程与回程对得上），不符 0 处
```

四条读法：

1. **五档里只有一种方言能原样表达全部五档**（`messages` 5/5）。另两家分别缺两档与一档——所以「拿停止原因做判断」这件事**必须先被翻译成规范档**，再进业务逻辑；
2. **`responses` 只有 2/5**：两格是**空**（`stop_sequence` 与 `refusal`——后者的拒答在这一家是一个**内容块**而不是停止原因），一格是**撞车**；
3. **空与撞车不是一回事，而撞车更危险**：空格是 `None`，谁读都会在第一步被拦下（`_back()` 会报「这一档说不出来」）；撞车**有值、但值是别人的**——读的人以为读到了。最重的一格是 `tool_call`：`responses` 用 `completed` 同时表示「答完了」和「请你调工具」；
4. 因此有一条可照用的判据：**「要不要接着跑工具」不能只读停止原因**。`responses` 上要去看 `output` 里有没有那个 `function_call` item——三段夹具流里三家都带着一次工具调用，而停止原因两家说「要调工具」、一家说「答完了」（见 6.2.7 的读数）。这正是「一个字段被拆成两个」时最容易丢的那一半。

这张表在树里是**两张表**：正程（`STOP_MAP`，规范档 → 各家取值）与回程（`STOP_BACK`，各家取值 → 规范档）。它们必须逐格对得上，而这条一致性由 `table_violations()` 守——**正程表自己看不出来**：把 `length` 的回程改读成「正常结束」，两张表各自都写得很整齐，只有合起来才看得出断了一根线（`tests/test_wire.py` 里就有这一条反例）。

## 6.2.7 流式：同一段答复的三种帧形

流式最容易被误读的一点是「帧数」：三家的帧数差一倍，而它们表达的是**同一段答复**。

```text $ python scripts/wire_reader.py --offline
Messages（Anthropic）        帧 12 个　带 event: 名 12 行　ping 1 个　以 [DONE] 收尾 否
Responses（OpenAI）          帧  9 个　带 event: 名  0 行　ping 0 个　以 [DONE] 收尾 否
Chat Completions（兼容层）      帧  7 个　带 event: 名  0 行　ping 0 个　以 [DONE] 收尾 是
停下来的原因：messages=tool_call／responses=end_turn／chat=tool_call　（2 种说法，而三段流都带着一次工具调用）
```

| 方言 | 帧 | 类型写在哪 | 记账帧 | 结尾 |
| --- | ---: | --- | --- | --- |
| `messages` | 12 | `event:` 行（名） ＋ `data:` 里的 `type` | `ping` | 一个 `message_stop` 事件 |
| `responses` | 9 | 只在 `data:` 里的 `type` | — | 一个 `response.completed` 事件 |
| `chat` | 7 | **没有类型**，靠 `choices[].delta` 的形状认 | 空 delta 的那一帧 | `data: [DONE]`（**不是 JSON**） |

四条读法：

1. **帧数不是速度**。同一段答复是 12 / 9 / 7 帧，而信息量完全一样——所以「帧数多」既不能说明更细，也不能说明更慢。要比的是**首字时长**（5.7 登记过这个词），不是帧数；
2. **三家有三种「帧的类型」写法**：一家在 `event:` 行上给名字，一家在 `data:` 里给 `type`，第三家**连类型都没有**（它靠「这一帧里有没有 `delta.tool_calls`」认）。所以三家的解析器不是同一个循环换三个键名，而是三套分支；
3. **两家有「不算内容」的记账帧**：一家会夹 `ping`，另一家最后会发一个空 delta 的帧。解析器要显式跳过它们——**跳过的方式也在报错话术里**，不然「收到不认识的事件」会被当成协议变动；
4. **`data: [DONE]` 不是 JSON**。这是个很小的坑，但它长在**每一段流的最后一行**上：把它丢给 `json.loads` 会抛在正常路径的末尾，看起来像服务端出错。上面那个「帧数」就是按 `data:` 行数的——**拿 `event:` 行去数，这一家会少一帧**（它把 `ping` 也包成一对 `event`/`data`），三家就不可比了。

验收线只有一条，而它是可以断言的：**三段帧形解出来的必须是同一个规范答复**（同一段文本、同一组工具参数、同样一次调用）。

## 6.2.8 谁能走哪条路：8 个模型 × 3 种方言

最后一组读数把 6.1 的登记表与本章的三种方言对起来——**这是两张表第一次互相问问题**：

```text $ python scripts/wire_reader.py --offline
24 个格子（8 模型 × 3 方言）里，调得到工具的 11 格，调不到 13 格；其中兼容层上 3 个模型可以，但都要先关掉推理
调不到的那 13 格里有 8 格属于同一件事：**另一家的四个模型不在兼容层的图纸上**
```

| 模型 | 厂商 | 能接的方言 | 能调到工具的方言 | 前提 |
| --- | --- | --- | --- | --- |
| `claude-fable-5-1`／`claude-opus-5`／`claude-sonnet-5`／`claude-haiku-4-5` | Anthropic | `messages` | `messages` | — |
| `gpt-6-astra` | OpenAI | `responses` | `responses` | **工具调用只走 Responses** |
| `gpt-5.6-sol`／`gpt-5.6-terra`／`gpt-5.6-luna` | OpenAI | `responses`、`chat` | `responses`、`chat` | 走兼容层时要**关掉推理** |

三条读法：

1. **24 格里 11 格能调到工具、13 格不能**。这张矩阵的形状说明一件事：能力不是模型的属性，是**模型 × 协议**的属性；
2. **13 格里有 8 格是同一件事**——另一家的四个模型不在兼容层的图纸上（兼容层是一家的形状）。所以「都走兼容层，省得写两套」这条路上，**一半的模型是上不去的**；
3. **余下的限制都是「有前提的可用」**：最大的那一个模型在兼容层上**做不了工具调用**（这一家的示例里那个位置已经换成了小一号的模型），另外三个可以，但前提是关掉推理。这类前提**不会在你第一次调用时报错**——它会在「推理开着、同时又挂了工具」的组合上才出现。所以它必须**被登记**，而不是被记住。

这张矩阵与 6.1 的登记表**共用同一份模型清单**（`tool_dialects()` 直接读 `registry.MODELS`）：那里加一个模型，这里会跟着多一行；那里改一家厂商，这里的两列会一起变。**一张表、两处用**——这也是本章唯一一处依赖 6.1 的地方。

### 接口契约

- `wire.Request` / `wire.Response`：中立的请求与答复；`Response` 里带着 `dialect` 与 `events`（流式读过多少帧）
- `wire.FIELD_MAP` / `wire.SHAPE_MAP`：翻译表的**名字层**与**形状层**，两层的行数由读数逐个数出来
- `wire.table_violations()`：**这张表唯一会响的一条路**（正程与回程逐格对），空列表才是正常
- `wire.validate(req)`：四类坏请求各说一句话，返回空列表才是正常
- `dialects.ADAPTERS`：`{"messages" / "responses" / "chat"}` → 适配器；每个适配器四个动作
- `dialects.load_arguments(raw, where)`：**唯一**解那两家 JSON 字符串的地方（坏 JSON 报错，不许静默成 `{}`）
- `dialects.tool_dialects(model)` / `tool_constraint(model, dialect)`：从 6.1 的登记表算出来的能力矩阵（**空白也是答复**：没有前提就写空）
- 离线入口：`python scripts/wire_reader.py --offline`

### 不能破坏什么

- **不发请求**：这一层只有字典进、字典出——「离线当门」能成立的前提，也是 6.3 能把重试接在**外面**的原因；
- **不引框架**：第 6 篇沿用「手写」这一档（4.1 已经量过框架把它压成多少行）；
- **不改前三棵树**：v3／v4／v5 照旧可装可跑；
- **不把没量过的形状写成量过的**：三段流是夹具，`WIRE_AS_OF` 与 6 页出处都进表；`responses` 那一格「撞车」**必须留在表里**，不许为了让读数好看而改成一个独占的取值。

## 常见坑

1. **把 `max_tokens` 当通用名**。同一件事在三家叫三个名字，而且其中一家必填、两家选填（6.2.3）。
2. **把系统提示塞进消息数组**。规范形状里没有 `system` 角色——有一家把它放在**顶层字符串**字段里。
3. **以为「兼容层」是通用层**。它是一家的形状 ＋ 一个能翻译的端点；另一家的四个模型根本不在它的图纸上（6.2.8）。
4. **把工具参数当对象直接读**。两家递的是 JSON 字符串，而那是**模型生成的**（6.2.5）。
5. **坏 JSON 静默成 `{}`**。那会伪造一次「模型没传参数」的调用，而真现象是参数被截断。
6. **拿停止原因判断「要不要接着跑工具」**。`responses` 用 `completed` 同时表示「答完了」和「请你调工具」（6.2.6）。
7. **把「空」与「撞车」当一种缺失**。空会被 `None` 拦下，撞车什么都不报——后者才是真危险的那种。
8. **只写正程表**。回程（取值 → 规范档）也得有一份，而且两份要逐格对得上（`table_violations()`）。
9. **拿 `event:` 行去数帧**。有一家会把 `ping` 也包成一对 `event`/`data`，帧数就不可比了（6.2.7）。
10. **把 `data: [DONE]` 丢给 JSON 解析**。它不是 JSON，而它长在**每一段流的最后一行**上。
11. **把帧数当速度**。同一段答复可以是 12 帧或 7 帧，信息量一样；要比的是首字时长（5.7）。
12. **以为换厂商只改 `base_url`**。两份载荷之间**只有模型名是同一个位置上的同一个名字**（6.2.4）。
13. **在业务代码里到处 `if vendor == ...`**。翻译要在边界做一次；第四家进来时，边界只有一处要改。
14. **把没验过的形状写成验过的**。本章没有对着任何一家的线上端点跑过——这一条要写进「已知不足」，而不是靠「文档上是这么写的」蒙过去。

## 面试视角

本章对应的是「你怎么接多家模型」这一类工程题。五个高频问法：

1. **「多厂商接入要注意什么？」**——别答「换个 base_url」。答三样形状差异：系统提示的落点、工具参数的形态、停止原因的映射；再报一个数：**同一件事在三家是 27 / 27 / 28 个 key 路径，而共有的只有一个**（`model`）。
2. **「怎么保证各家行为一致？」**——答规范形状 ＋ 适配器 ＋ 一条可断言的验收线：**三段帧形解出来的必须是同一个规范答复**；再补一句「停止原因要翻成规范档，不能直接进业务判断」。
3. **「兼容层是不是万能？」**——答不是：它是一家的形状；本章的矩阵里 24 格里 13 格调不到工具，其中 8 格是另一家的四个模型，另外的限制是「关掉推理才有工具调用」。
4. **「流式怎么处理多家？」**——答三种帧形与三个坑：命名事件 / `data` 里的类型 / 连类型都没有；`ping` 与空 delta 要跳过；`[DONE]` 不是 JSON。
5. **「工具调用的参数会不会坏？」**——答会：两家给的是**模型生成的 JSON 字符串**，所以边界上要做一次解析，而且**坏 JSON 必须报错**——静默成空字典会伪造一次「没传参数」的调用。

## 本章小结

- 三家不是三个名字，是**三种形状**：八栏里**没有一栏同名**；形状层的分堆是 4 / 4 / 0。
- 值得记住的一格：**工具参数在一家是对象、在两家是 JSON 字符串**，而那是模型生成的，所以边界上要解析、坏了要报错。
- 同一个请求翻成三份载荷是 **27 / 27 / 28** 个 key 路径、**806 / 812 / 862** 字节，而**共有的 key 路径只有 1 个**。
- 「为什么停」是 5 档 × 3 方言 = **15 格**：只有一种方言能原样表达全部五档；另两家分别 2/5 与 4/5。
- 两种缺失不一样：**空**会被拦下，**撞车**什么都不报；最重的一格是「要调工具」在 `responses` 上读成「答完了」。
- 同一段答复在三种帧形下是 **12 / 9 / 7 帧**；只有一家发 `event:` 名与 `ping`，只有一家以 `[DONE]` 收尾（**它不是 JSON**）。
- 8 个模型 × 3 种方言 = 24 格里，能调到工具的是 **11 格**——**能力是「模型 × 协议」的属性，不是模型的属性**。
- 这一层只有字典进、字典出：**不发请求**，所以重试与降级（6.3）能接在适配器外面。

### 这一章在整条流水线里改的是哪一格

6.1 改的是「这份应用跑在什么价钱上」，本章改的是**它跑在什么形状上**。它给后面两章各留了一个接口：6.3 拿 `ADAPTERS` 去接重试、限流与降级（那三件事都要在适配器**外面**做，因为它们是「怎么发」而不是「发什么」），6.4 拿 `Response.usage` 去做成本看板（三家的用量字段名字也不同，而它们都在这一段被翻成同一个字典）。**这一章一次模型都没调**——先有账、再有形状，最后才轮到接线。

## 练习

- **基础**：给 `FIELD_MAP` 加一栏（比如「推理/思考的开关」在三家的落点），跑 `wire_reader.py --offline`，看「名字层」与「形状层」两个数怎么变。
- **进阶**：在 `STOP_MAP` 里加一档规范停止原因（比如 `content_filter`），然后让它通过 `table_violations()`。如果它在某一家**说不出来**，就照 `stop_sequence` 的做法**登记成空**，并写一条反例测试证明「原因被抹掉时会红」。
- **进阶**：给三个适配器各写一个**非流式**的往返夹具（用你自己项目里的一次真实答复形状），跑一遍 `from_wire`，确认三份解出来的是同一个规范答复。
- **挑战**：给 `dialects.py` 加第四个适配器（比如某家自建的 vLLM 端点），并在 `validate()` 里补一条它特有的前提；然后回答：**这次改动动了几个文件、几处表**？
- **挑战**：把三段夹具流换成**真流**。你只需要一个能返回 SSE 的端点（本机 vLLM 或任何一家），然后把真实帧逐行贴进夹具——**注意别改任何断言**：如果真实帧让某条断言红了，那条断言才是这一章最值钱的东西。
