# 7.2 可观测性：链路追踪、指标与成本看板

## 本章导读

7.1 把「它变差了没有」变成了一条离线流水线——一批题、几条指标、一道门。而离线判据有一个天生的盲区：**它只说这一个版本在那一批题上如何，说不出刚才那一次请求里谁慢、谁贵、谁错了。**「用户说刚才很慢」这句话落不进评测集：那条请求没有编号、没有现场、也没有留下任何一个能复算的数。7.2 补的就是这一层——**链路追踪**（一次请求是一棵树）、**指标与成本看板**（把树上的账汇总成一张表）、**告警**（什么时候该叫人）。它接在 3.9 的追踪之上，也接在 6.3 的网关与 6.4 的四栏账之下。

**这一章的第一句话是一条纪律**：**埋点不是加日志，是把「这条请求里发生过什么」写成一个有名字、有属性、有父子关系的结构**。它贵在「有名字」这一件事上：官方的语义约定把属性名（`gen_ai.*`）定成一套公共词表，而看板、评估器、过滤器全都**按名字取数**——所以名字漂了，它们会静默失配：报表不会报错，它只会变成空的。本章与 7.1 一样**不调模型、不联网**：那条 trace 与那 200 条现场记录都是**造出来的**，所以它能量埋点、语义约定、采样与看板自己的性质，量不了真实延迟。

## 7.2.1 三件套：把「刚才那一次」留下来

先看这三件套各自回答哪一句话，以及它们**共用**什么：

| 件 | 它回答的那一句 | 它的形状 | 没有它的时候 |
| --- | --- | --- | --- |
| 追踪 | **刚才那一次，时间花在哪一层** | 一棵树（span） | 只能看单点的日志，跨服务的因果全靠猜 |
| 看板 | 这一周**钱和延迟**长成什么样 | 一张按维度分组的表 | 账单月底才知道，而那时已经晚了 |
| 告警 | **什么时候该叫人** | 一条带窗口的判据 | 出事靠用户投诉发现 |

三件套共用**一根线**：`trace_id`。官方（Langfuse）的数据模型把它讲得最干净：**观测（observation）是应用里的每一步**——模型调用、工具调用、检索步骤，它们**按 `trace_id` 归成一个 trace**，而 `user_id`／`session_id`／`tags`／`metadata` 这些**trace 级的属性会复制到每一行观测上**（这样按维度过滤与聚合不用连表）。同一条线也把 7.1 的跑记录串了回来：跑记录里写下 `trace_id`，就回答了「这一条题是哪一次跑答的」。

**trace 的粒度是「一次自足的请求」**，官方给了三个典型：一次对话轮（用户发一句、应用检索、调模型、回一句）、一次 agent 运行（收到任务、推理、调工具、出结果）、一次管线执行（进来一份文档、切分、嵌入、入库）。如果这些动作连着发生（多轮对话、多个 agent 汇成一份报告），那属于**会话（session）**：**一轮一条 trace、一段会话一个 session**——理由是「你事先不知道一段会话什么时候结束」，而按轮切让每一条 trace 都小而好读。

官方那条命名建议值得单独记下来：**名字是一个接口**。评估器按名字挑观测、看板按名字过滤与聚合、保存的视图按名字取数——所以**名字一改，那些东西会静默失配**（不是报错，是变成空的）。两条推论：

- **动态值不进名字**：`process-order-8945` 这种写法让每一次执行都是一个新名字，于是再也分不成组、聚不了合（这与 OpenTelemetry 对 span 名的低基数要求是同一条）；**运行相关的值放属性**（官方的原话就是「放 metadata」）；
- **不拿模型名当名字**：换一个模型，所有按名字取数的看板与评估器一起失效——模型本来就已经是一个属性（`gen_ai.request.model`）。

> 💡 **提示**：本章的每个读数都来自 `zhizhou-v7/scripts/trace_reader.py --offline`。它不调模型、不要密钥、不联网——**那条 trace 与那 200 条现场记录都是造出来的**。所以它验证的是埋点、语义约定、采样与看板自己的性质，**不构成一次真实的可观测性压测**：这一条写在「不能破坏什么」里，不写成结论。

## 7.2.2 一条 trace 的形状：树、自耗时与缺口

一条 trace 不是「一列 span」，是**一棵树**。主键只有四个：名字、类型（`chain` / `retriever` / `llm` / `tool` / `gateway`）、父子关系、时间区间。树形带来的第一个好处是**能把时间往下拆**：

```text $ python scripts/trace_reader.py --offline
=== 一、一条 trace 的形状：8 根 span、5 个直接子 span ===
· invoke_agent 知舟                chain        1240ms  自     120ms
  · check-injection                tool           20ms  自      20ms
  · retrieve-context               retriever     200ms  自     200ms
  · chat gpt-5.6-terra             gateway       640ms  自      20ms
    · attempt 1                      llm           260ms  自     260ms
    · attempt 2                      llm           360ms  自     360ms
  · execute_tool get_table_schema  tool          120ms  自     120ms
  · chat gpt-5.6-luna              llm           140ms  自     140ms
根的总时长            1240ms
直接子 span 覆盖过    1120ms（并集：重叠只算一次）
缺口                120ms  ← 不在任何 span 里的那一段
自身的断言            0 条违规（干净）
```

先把两个数说清：

- **自耗时**（`self_ms`）＝ 自己的时长 − 所有子 span 之和。它回答「**时间花在这一层，还是它调的那一层**」——网关那一根 640ms 里，两次尝试占了 260 ＋ 360，所以它自己只等了 **20ms**；「网关慢」这句判断到这里才有落点；
- **缺口**（`gap_ms`）＝ 根的总时长 − 子 span **覆盖过的并集**。上面那条是 **120ms**：这 120ms **不在任何 span 里**。它不是 bug——它是**没被埋点的那一段代码**（排队、序列化、框架自己的开销），而它在只有加法、没有并集的报表上是隐身的。

这两个数在串行树上相等，在**并行**树上分叉：

```text $ python scripts/trace_reader.py --offline
串行那一条：自耗时 120ms ＝ 缺口 120ms（子 span 不重叠时两个数相等）
并行那一条：自耗时 0ms ／ 缺口 300ms——自耗时说「根自己没花时间」，缺口说「有 300ms 不在任何 span 里」；两个数都对，问的不是同一个问题
```

并行那一条：两路各跑 300ms 且完全重叠，根一共等了 600ms。**自耗时说「根自己没花时间」（0ms，因为加法把两路算了 600ms，正好等于根），而缺口说「有 300ms 不在任何 span 里」。** 两个数都对，因为它们问的不是同一个问题——**加法回答「下面花了多少」，并集回答「根等了多久、其中多少没人认领」**。看到「自耗时是 0」就去优化根，是这一族里最常见的误判。

树的第二个好处是**形状本身就能报错**：`violations()` 不判断业务，只判断这棵树能不能信。它守的是这几件：

| 违规 | 为什么它必须报 |
| --- | --- |
| `span_id` 重复 | 两根 span 变成一根：聚合时后者覆盖前者，而报表上看不出少了什么 |
| 父 span 不在这一条 trace 里（**挂空**） | 它看起来与「链路真的断在那一处」一模一样，见 7.2.6 |
| 一根 trace 里有**两个根** | 一次请求被拆成了两截，而「总时长」从此没有定义 |
| 子 span 的区间超出父 | 时间相加会得到比根还长的「总耗时」 |
| 子 span 比父还长 | 自耗时会被截到 0——**截可以，但要报出来**，不然它会伪装成「这一层不花时间」 |

还有一条不是「违规」而是**故障**的：**空 trace**。一条 span 都没有时，所有求和都是 0、所有检查都不响——它与「一切正常」在报表上长得一样（7.1 的 `empty` 那一档是同一件事，pytest 用退出码 `5` 说的也是它）。所以 `violations()` 对空 trace 直接返回一句话，而不是空列表。

> 💡 **提示**：官方这两条建议都是「结构」建议，而且都有代价：**工具调用要挂在编排它的那一步下面**（作为与生成平级的孩子），否则它会以「挂在根上」的形式丢掉上下文；**不要让一根 generation 包住整个循环**——那样看板上只会看到「一次调用、一个总价」，而**看不到每一步的决策、也看不出哪个工具把上下文撑爆了**（这正是 6.4 里「贵是怎么来的」那个问题的现场版）。

## 7.2.3 属性与语义约定：缺了要报出来

树只说了「谁调了谁」，**账与筛选全靠属性**。官方把属性分成三档：

| 档 | 例子 | 缺了会怎样 |
| --- | --- | --- |
| Required | `gen_ai.operation.name`、`gen_ai.provider.name` | 看板分不成组：这一行会掉进「没有这一栏」 |
| Conditionally Required | `error.type`（**出错的那一趟**必须带）、`gen_ai.prompt.name`（用了命名模板时） | 出错的那一类事后查不出来 |
| Recommended | `gen_ai.usage.input_tokens` / `output_tokens`、缓存读／写那两栏（「适用时才有」） | **这一格的账算不出来**——而它看起来像「花了 0 元」（7.2.7） |

把这张表落成代码，就是一棵树上的**缺口清单**：

```text $ python scripts/trace_reader.py --offline
=== 二、属性与语义约定：8 根 span，必填属性 22 处、缺 3 处 ===
  s-guard  tool      check-injection                  缺 gen_ai.tool.name
  s-retr   retriever retrieve-context                 缺 db.collection.name
  s-sum    llm       chat gpt-5.6-luna                缺 gen_ai.usage.output_tokens
条件必填的例子：出错的那一趟必须带 error.type（`s-att1` 带了，所以它不算缺口）
按类型算：llm 5 项、gateway 3 项、retriever 2 项、tool 1 项、chain 0 项
```

三处缺口都在「Recommended」那一档上（少了 `gen_ai.tool.name`、`db.collection.name`、`gen_ai.usage.output_tokens`）——**而这一条 trace 的结构是干净的（0 条违规）**。这就是本章要立的那条区分：**结构干净 ≠ 属性齐了**。两条断言守的是两件事：

- `violations()` 守**树能不能信**（重复、挂空、两个根、越界、空树）；
- `missing()` 守**账能不能算、报表能不能看**（按类型列出该带而没带的属性）。

三处细节值得单独说：

1. **条件必填是「条件成立时才要求」**。上面那条 trace 里 `s-att1` 是失败的第一次尝试，它带了 `error.type: 429`，所以不算缺口；反过来，如果一根 span 打了 `error` 却**没有** `error.type`，那才是缺口——「出错了」与「错在哪一类」是两个信息，后者才是能聚合的那一个；
2. **「没报」与「报了 0」是两件事**。缓存那两栏官方写的是「适用时才有」，所以本层的口径是：没报时按「全未命中」算（否则未命中输入那一栏没有定义），**但要把这件事记下来**——否则看板上「这一格没报缓存」与「这一格真的没有缓存」会合成一个数；
3. **属性名会变**。`gen_ai.provider.name` 今天叫这个，而它的旧写法是 `gen_ai.system`；3.9 已经指出这套约定的状态还是 **Development**。所以「名字是接口」这句话在这里是**双向**的：看板按名字取数，改名就要连看板一起改；而**约定自己也会改**，所以口径里要写清「本树认哪一届名字」。本层把口径写成一张能执行的表（`trace.REQUIRED`），于是改名这件事变成一次**会当场报错的改动**，而不是一次静默的失配。

关于内容类属性（`gen_ai.input.messages` 那一族）：官方把「把提示与答复原文写进 span」写成**要显式打开的**（默认不记），理由是它们可能含敏感数据；3.9 也记过这一条。本章的口径与它一致：**内容不进属性**——本层的 trace 只留结构、计数与模型名。

## 7.2.4 关联：一条 trace_id 串起三层账

`trace_id` 的价值在于**把三层账串成一件事**：6.3 的 `attempts`（这一次逻辑调用重试了几次）、6.4 的四栏账（这次调用花了多少）、7.1 的跑记录（这一条题是哪一次跑答的）。串起来之后，一个很容易踩的坑就露出来了——**重试要付钱，但只能付一次**：

```text $ python scripts/trace_reader.py --offline
=== 三、关联：一条 trace_id 串起三层账 ===
这一条 trace_id        tr-0000
  ↳ 6.3 的 attempts      2 次（网关那一层记的：s-att1、s-att2）
  ↳ 7.1 的跑记录          同一个 trace_id 也写在跑记录里（本树里编的：题 q07 ／ run 42）
按 attempts 层记账      $0.0275  算得出 2 格、算不出 1 格
按 logical 层记账       $0.0275  算得出 1 格、算不出 0 格
两层都记（一个 sum）    $0.0550  ← 重试那一段算了两遍，贵 100.0%
失败的那一次（s-att1）  $0.0080，占这一次逻辑调用的 29.1%——它没产出任何东西，但账单上有它
```

三种记法，两种结果：

| 层 | 记法 | 它回答 | 这一条的账 |
| --- | --- | --- | --- |
| `attempts` | **每一次物理尝试**各一根 span，各自带 usage | 失败那几次花了多少 | $0.0275 |
| `logical` | **一次逻辑调用**一根 span，usage 是几次之和 | 这一次调用一共花了多少 | $0.0275 |
| 两层都加 | 任何一张「把所有 span 加起来」的看板 | —— | **$0.0550（贵 100.0%）** |

两层都记**不是错**（审计与排障各自需要一层），错的是**账单认了两层**。所以本层把 `layers` 写成**必填参数**：`trace_cost(trace, layers=("attempts",))` —— 一个默认值会让这件事悄悄发生，而参数会让它在每一次调用里被看见。这与 6.4 那四栏「四栏之和必须等于总价」是同一条纪律的两次执行：**口径要么写在参数里，要么它就不是口径**。

顺带看第二件容易被忽略的事：**失败的那一次照样有账**——`s-att1` 花了 $0.0080，占这一次逻辑调用的 **29.1%**，而它一个字都没产出。这正是 6.4 那条读数（失败率 20% 会让一笔账平均贵 24.80%）在 trace 上的形态：**「没产出」不等于「没花钱」**，而一个只看成功响应的看板会把这一栏整个漏掉。

官方的口径也支持「一根逻辑 span」：GenAI span 那一节写得明确——**如果请求被自动重试，对应的那根 span 覆盖的是「含全部重试」的逻辑时长**。这条约定顺带解决了一个歧义：那一根 span 的**时长**是逻辑时长（含等待与退避），而**重试几次**是属性（本层写作 `zhizhou.attempts`）。时长里含重试、次数写在属性里，两者不重不漏。

## 7.2.5 指标与分位：报分位要连算法一起报

看板的另一栏是延迟与吞吐。这里最容易出的一种错是**报了一个数却没说它是谁**：

```text $ python scripts/trace_reader.py --offline
=== 四、指标与分位：200 条 trace 的根时长 ===
均值                497.1ms
p50                 442.5ms
p95（nearest_rank） 556.8ms   两种算法在全量上给出同一个数（差 -0.0ms）
p99（nearest_rank） 2980.0ms　最大 3200.0ms——200 条上 p99 就是「第 199 个」
只拿前 20 条算 p95    547.5ms（全量 556.8ms）——样本越少，分位越是「最近几次的运气」
10 条一窗的 p95      nearest_rank 1500.0ms（＝这一窗的最大值：ceil(0.95×10)−1 = 9）
                    linear 1071.4ms（在第二大与最大之间插了一刀）　两种算法差 428.6ms
                    前者是这一窗真发生过的值，后者是一个**没人经历过的值**
```

四件事：

1. **均值掩盖长尾**。均值 497.1ms 只比 p50 高 12%（442.5ms），而 p99 是 2980.0ms——**那 6 条慢的被摊进了 200 条里**，用均值看它们是看不见的。所以延迟一定要报分位，而且要报**哪一个**分位：p95 与 p99 在这一批上差 5.4 倍；
2. **分位要说算法**。同一批数，`nearest_rank` 报的是**实际发生过的某一个值**（第 `ceil(q·n)` 个），`linear` 在相邻两个值之间插值——**可能报出一个没人经历过的值**。全量 200 条上两者恰好给出同一个数，而一窗 10 条上差 **428.6ms**（1500.0 对 1071.4）：一个说「这一窗最慢的那一次是 1.5 秒」，另一个说「1.07 秒」——**后者从未发生过**。所以「报分位」这件事的最小完整写法是：**分位数 ＋ 算法 ＋ 样本量**；
3. **分位要有样本量撑着**。只拿前 20 条算 p95 是 547.5ms、全量是 556.8ms——**样本越少，分位越是「最近几次的运气」**。而更极端的情形：10 条一窗时 p95 **就是这一窗的最大值**（`ceil(0.95×10) − 1 = 9`，正好是第 10 个）。换句话说，**窗口大小决定了这条指标看起来是什么**——「p95 突然涨了」这句话在 10 条一窗的看板上，等价于「这一窗有一条慢的」；
4. **官方那两条指标是直方图**。`gen_ai.client.operation.duration` 与 `gen_ai.client.token.usage`（后者按 `gen_ai.token.type` 分输入与输出）都是 **histogram**——直方图的分位数是**桶边界之间的估计值**，与「把全部样本排序算出来的 p95」不是同一个数。所以看板上那个 p95 要么标明「直方图估计」，要么就把原始样本留着重算——**两个都不做，读出来的差就不是系统的差**。

> 💡 **提示**：分位与 7.1 的分辨率是同一件事的两头：那里说「n 条上看得见的最小差异是 1/n」，这里说「n 条上的 p95 站在哪」。两者都用**样本量**当分母，所以两个数要一起看——一个说「这一批够不够判」，一个说「这个数可不可信」。

## 7.2.6 采样：抽多少、抽谁

生产上不可能把每一条 trace 都留下来：采样的三个数（抽多少、抽谁、谁来决定）决定了看板看到的是**哪一半世界**。

```text $ python scripts/trace_reader.py --offline
=== 五、采样：200 条里抽 10% ===
头部采样（按 trace_id 掷骰子）  留 20 条，其中出错的那一类 0/6 条
尾部采样（出错与慢的一律留）    留 27 条，其中出错的那一类 6/6 条
多留的代价                      7 条（13.5% 对 10.0%）——换来的是「要看的那几条一条不少」
逐 span 各自掷骰子（0.5）       一条 trace 剩 4 根、丢了 4 根；违规 1 条：
  s-att2（attempt 2）的父 span s-gw 不在这一条 trace 里——挂空；逐 span 抽样留下的断口就长这样
同一根 trace_id 连掷三次         都一样——三处服务必须掷出同一个决定，否则一条 trace 会被抽成半条
```

**① 头部采样在「知道结果之前」就定了。** 10% 的头部采样在这 200 条里留了 20 条，其中**出错的那 6 条一条都没留下**（0/6）。这不是运气差：**它在结果出来之前掷骰子**，而出错恰恰是稀有事件（6/200 ＝ 3%），10% 的抽取期望值只有 0.6 条。所以「线上错误率」这种指标在头部采样下会漂得非常厉害——**看板不报错，它只是看不到**。

**② 尾部采样等结果出来再决定**，代价是两样：**内存**（整条 trace 要先缓存住）与**时间**（「慢」这个条件只有结束时才判得出来，而一条卡住不返回的请求，正是最该留下的那一种）。换来的是那 6 条一条不少（6/6），总留存从 10.0% 涨到 **13.5%**——多留 7 条。**这不是「更贵」，这是「多花 3.5 个百分点买回出错的全部样本」**，而它值得写在成本口径里（6.4 的那张表会给这笔钱一个数）。

**③ 头部采样必须是确定性的。** 同一个 `trace_id` 在网关、检索、生成三处必须得到**同一个**决定：如果每处各自随机，一条 trace 会被抽掉一半——而**半条 trace 看起来与「链路真的断在那里」一模一样**（下一条正是这件事的人为版本）。所以本层的 `head_keep()` 用的是**确定性哈希**，而不是随机数生成器。

**④ 最省事也最像坏掉的写法：每一根 span 各自掷骰子。** 0.5 的逐 span 抽样把这条 trace 抽成 4 根、丢掉 4 根，并且留下一条**挂空**（`s-att2` 的父 `s-gw` 不在这一条 trace 里）。它与真正的链路断裂在报表上无法区分——两种情形的报表都是一棵树里挂着没有父的节点。**所以「trace 级」不是一种优化，是一种正确性要求**：抽样要么整条留、要么整条不留，中间没有一格。

## 7.2.7 成本看板：算不出来不是 0

6.4 把一笔账拆成四栏（未命中输入／缓存写／缓存读／输出），而四栏在 trace 上的名字就是官方那四个属性：`gen_ai.usage.input_tokens`、`gen_ai.usage.output_tokens`、`gen_ai.usage.cache_read.input_tokens`、`gen_ai.usage.cache_write.input_tokens`。挂上去之后，看板长这样：

```text $ python scripts/trace_reader.py --offline
=== 六、成本看板与告警 ===
按模型分组（认 attempts 层，四栏的列名用属性名）：
  key              uncached     write      read       out     total grid unknown
  gpt-5.6-luna       0.0000    0.0000    0.0000    0.0000    0.0000    0       1
  gpt-5.6-terra      0.0160    0.0005    0.0002    0.0108    0.0275    2       0
覆盖率（算得出的格 / 有 usage 的格）  2/3 = 0.6667——「luna 那一行 0.0000 元」与「luna 没被调用」是两件事
全量 200 条：总额 $0.3519　覆盖率 1.0000　模型 2 个
按路由分组：
  /ask      190 条  $0.2390（格 190、未知 0）
  /export    10 条  $0.1128（格  10、未知 0）
```

这张表里最该看的是**两行之间的那个对比**，以及最后那一列：

- `gpt-5.6-luna` 那一行的四个数都是 **0.0000**，而它的 `unknown` 是 **1**——**「这一行花了 0 元」与「这一行只有一次调用、而它的账算不出来」是两件事**，它们在这一行里长得一样。覆盖率那一栏（算得出的格 ÷ 有 usage 的格 ＝ **2/3 = 0.6667**）就是为这一行准备的：**看板必须把钱与覆盖率一起报**，否则「便宜了」这个结论永远没人会质疑；
- 反过来，`gpt-5.6-terra` 那一行的四栏加起来正好是它的总额（$0.0275）——四栏之和等于总价这条口径（6.4）在这一层依然成立，它保证的是「拆开的那四栏没有漏项」。

三种「算不出来」，三种都必须进 `unknown` 而不是 `0`：

| 情形 | 为什么不能记 0 | 本层怎么处理 |
| --- | --- | --- |
| 缺 usage 两项中的任一项 | 「这一格没测」与「这一格是 0 元」在报表上一样 | `usage_of()` 返回 `None`，格数进 `unknown` |
| 模型名不在价表里 | 6.4 的三件套里「模型名」是第一件：名字对不上就算不出来 | `span_cost()` 返回 `None`（不是「按默认价算」） |
| 缓存两栏自相矛盾（读 ＋ 写 > 输入） | 两家的口径不同（`input_tokens` 含不含缓存读），矛盾时不能选一个 | 同样返回 `None`，并记一条说明 |

**口径要先声明**是这一节的最后一条：本层按「`input_tokens` **含**缓存读与写」处理，所以未命中输入 ＝ 输入 − 缓存读 − 缓存写，并对上面第三种情形**报错**。反过来做（静默取绝对值、或者把缓存读当额外加成）也能算出一个数，而那个数依然自洽——这就是它危险的地方。

最后是分组维度：这张板子按 `gen_ai.request.model` 分组，同一份数据换成 `key_of=BY_ROUTE` 就变成按路由分组（`/ask` 190 条 $0.2390、`/export` 10 条 $0.1128）。**每一行都要带「几条 trace」**：一份不带条数的看板看不出「数据变少了」——那与「省了钱」长得一模一样（7.1 那条「数据集少了两条会伪装成退步」是同一族）。官方在 best practices 里还给了两个可用的维度：`user_id`（谁在花钱、谁的质量差）与 `environment`（别让测试流量污染生产看板）。

## 7.2.8 告警：阈值、窗口与告警疲劳

看板报数，告警叫人。叫人的那条判据有三个旋钮：**阈值**、**窗口**（连续几个窗口才报）与**方向**。阈值不是拍的——它接 7.1 那一条：**基线 ＋ 抖动带**。

```text $ python scripts/trace_reader.py --offline
告警：20 个窗口（每窗 10 条的 p95）
  基线（健康窗口的 p95）558.7ms ＋ 抖动带 42.1ms → 阈值 600.7ms
  各窗口               1500 542 522 558 517 548 539 1600 549 557 535 1520 545 3050 3200 2980 559 521 553 550
  连续 1 个窗口越线才报   4 次告警（窗口 1、8、12、14–16）
  连续 2 个窗口越线才报   1 次告警（窗口 15–16）
  连续 3 个窗口越线才报   1 次告警（窗口 16）
阈值一次也不假报的那条路是「不报警」——所以判据里要写清「拿哪一段当基线」与「连续几个窗口」
```

三个规则读同一串窗口，读出来的东西完全不同：

| 规则 | 告警次数 | 它报了什么 | 代价 |
| --- | ---: | --- | --- |
| 连续 1 个窗口越线 | **4** | 窗口 1、8、12 那三次**孤立的单点** ＋ 事故那一次 | 3 次假报：前三次的窗口值都只越线一格 |
| 连续 2 个窗口越线 | **1** | 只剩事故（窗口 15–16 起） | 报得**晚 1 个窗口** |
| 连续 3 个窗口越线 | **1** | 只剩事故（窗口 16 起） | 报得**晚 2 个窗口** |

规律很清楚：**`for`（连续窗口数）买到的是「假报变少」，付出的是「真报变晚」**。两条都写进口径，别只写一半。另外两件必须写清的事：

- **基线取哪一段**。上面用的是「健康窗口的 p95 ＋ 抖动带」（558.7 ＋ 42.1 → 阈值 600.7ms）。如果换成「全部窗口的均值」，那 3 条 3 秒级的事故会把阈值抬到 800ms 以上——**用出事的自己被污染的基线去判出事**，这是生产上最常见的一种自伤。健康窗口怎么界定要写在规则里，而且**它本身也要能被复核**；
- **状态语义**。连续越线只算**一次**事件（进入告警态就报一次，条件消失才清空），不连着报三次。这不是实现细节：一个每窗口都发一条的规则会把「一次事故」变成三条通知，而**通知的条数本身就是告警疲劳的来源**。本层的 `alert_events()` 返回的是 `(起, 止)` 两个窗口号——**「这一次告警持续了几个窗口」也该进通知**，因为一个 15 分钟的抖动与一次 3 小时的故障，处理方式完全不同。

> 💡 **提示**：阈值一次也不假报的那条路是「不报警」——所以判据里**必须**同时写清「拿哪一段当基线」与「连续几个窗口」，否则每一次调参都是在两个错之间挪：先是假报太多、所有人学会绕过它（7.1 那条「容差取 0 的门跑十次红个五六次，然后所有人学会绕过它」是同一件事），然后是把窗口调到 5 个，于是真事故要靠用户先发现。

## 7.2.9 知舟接线

### 加了什么

第五棵树 `zhizhou-v7/` 的第二段增量：**可观测的两块**。它与 7.1 是同一个问题的两半：7.1 的三块（`suite` / `metrics` / `gate`）量的是**离线判据**（这一批题上好不好），7.2 的两块（`trace` / `board`）量的是**在线现场**（刚才那一次里谁慢、谁贵、谁错了）。两者之间**没有 import 关系**，这不是巧合：**离线判据在没有流量的日子也要能跑，而看板在没有评测集的项目里也得能用**；把它们连起来的只有一样东西——`trace_id`（7.2.4）。它也接在 6.4 的四栏账**上面**：四栏换成官方的四个 `gen_ai.usage.*` 属性名之后，就长在 span 上了。

| 文件 | 行数 | 职责 |
| --- | ---: | --- |
| `app/trace.py` | 408 | span 与 trace：树、自耗时与缺口、违规、语义约定缺口、样本、两档采样、分位 |
| `app/board.py` | 246 | 价表与四栏账、覆盖率、两层记账（`layers`）、按维度分组、告警事件 |
| `scripts/trace_reader.py` | 385 | 六组读数 ＋ **50 条夹具**（`--offline` / `--self-test`） |
| `tests/test_trace.py` | 148 | 十五组断言：形状、自耗时与缺口、违规、语义约定、采样与分位；**15 条用例** |
| `tests/test_board.py` | 139 | 十三组断言：四栏账、覆盖率、两层记账、失败那一次的账、告警窗口；**13 条用例** |
| `app/__init__.py` | 84 | 与四棵旧树的边界 ＋ **7.1／7.2 两块之间的边界** |

### 接口契约

- `trace.Span(span_id, trace_id, name, kind, start_ms, end_ms, parent_id, attrs)`：类型与时间在构造时校验（类型必须在 `KINDS` 里、结束不得早于开始）
- `trace.Span.missing()`：这一根缺了哪些**该带而没带**的属性（Required ＋ 条件成立的 Conditionally Required）
- `trace.Trace(trace_id, spans)`：`.roots()` / `.children()` / `.orphans()` / `.root()` / `.self_ms(span)` / `.covered_ms()` / `.gap_ms()` / `.violations()` / `.missing_attrs()` / `.tree_lines()`
- `trace.head_keep(trace_id, rate)` / `trace.tail_keep(trace, rate, slow_ms)` / `trace.sample_spans(trace, rate)`：确定性头部采样 ／ 尾部采样 ／ **逐 span 抽样（反面教材，用来钉住断口）**
- `trace.percentile(values, q, method="nearest_rank")` / `trace.p95_gap(values)`：分位与两种算法的差
- `trace.sample_trace()` / `trace.fanout_trace()` / `trace.workload(n)` / `trace.window_p95(traces)`：**造出来的**样本（与 7.1 的 `sample_suite()` 同一个约定：样本住在模块里，所以测试能直接断言它）
- `board.Model(name, input_price, output_price, cache_read, cache_write)` 与 `board.violations()`：价表与它自己的断言（写价 ＝ 输入 × 1.25）
- `board.usage_of(span)` / `board.usage_notes(span)`：四栏，以及这一格的「没法核」
- `board.trace_cost(trace, layers=...)` / `board.board(traces, layers=..., key_of=...)`：**`layers` 必填**；返回值里带「算得出几格、算不出几格」
- `board.alert_events(series, threshold, window=..., direction=...)`：告警事件（`(起, 止)` 窗口号）
- 离线入口：`python scripts/trace_reader.py --offline`

```text $ python scripts/trace_reader.py --self-test
  ✓ 方向不合法要报错

```

**实跑**：以上两条命令与全部用例都是实跑——`tests/test_trace.py` 的 15 条用例与 `tests/test_board.py` 的 13 条用例（合计 28 条）。**口径**：本树的读数**不调模型、不要密钥、不联网**——那条 trace 与那 200 条现场记录都是**造出来的**（`trace.sample_trace()` 与 `trace.workload()`），所以它验证的是埋点、语义约定、采样与看板自己的性质，**不构成一次真实的可观测性压测**，也量不了真实延迟。本章引到的官方口径有三处：Langfuse 的数据模型（观测按 `trace_id` 归组、trace 级属性复制到每一行、后台批量导出与短进程必须 `flush()`）与最佳实践（一条 trace 的粒度、嵌套、命名是接口、算成本要模型名与 usage、标签在创建时定死而事后判定用 score），以及 OpenTelemetry 的 GenAI 语义约定（span 名格式、三档属性、**重试时一根 span 覆盖含全部重试的逻辑操作**、内容类属性默认不记）与那篇 GenAI 观测的官方博客（`invoke_agent` 树形、两条 `gen_ai.client.*` 直方图指标）。其余全是本章自己的算术，能手算复核。

### 不能破坏什么

- **不许把「算不出来」写成 0**：`usage_of()` 返回 `None`、覆盖率与钱一起报。想改这条，先把覆盖率那一栏补上；
- **不许让看板只认一层账单**：`layers` 是必填参数，而两层都加会让账单翻倍（7.2.4）；
- **不许把「整条 trace」抽成「每根 span」**：挂空与真断链在报表上一样，这条有夹具守着；
- **头部采样必须是确定性的**：同一个 `trace_id` 在三处服务必须得到同一个决定；
- **不许把内容写进属性**：内容类属性是显式打开的（官方默认不记），本树连打开的口子都不留——这属于 7.5 的边界；
- **离线入口不许读 `.env`、不许联网**：这是「离线当门、真机报数」（3.10 起）在本篇的形态；
- **不改前四棵树**：v3／v4／v5／v6 照旧可装可跑，7.1 的三块也不动。

## 常见坑

1. **把「加日志」当成埋点**。埋点要产出的是一个有名字、有属性、有父子关系的结构；一堆散落的日志行拼不出「这次请求花在哪一层」（7.2.2）。
2. **名字里塞动态值**。`generate-response-retry-2` 这种名字让每一次执行都是一个新名字，于是再也分不成组——运行相关的值放属性（7.2.1）。
3. **拿模型名当观测名**。换一个模型，所有按名字取数的看板与评估器一起静默失配（7.2.1）。
4. **让一根 generation 包住整个循环**。看板上只剩「一次调用、一个总价」，看不出每一步的决策与哪个工具把上下文撑爆了（7.2.2）。
5. **工具调用挂在根上**。它丢掉了「是谁调了它」，而排障时第一个要问的就是这个（7.2.2）。
6. **把「自耗时是 0」当成「这一层不花时间」**。并行时它与缺口会分叉：**并集**才是根等了多久（7.2.2）。
7. **把「没埋点的那一段」当不存在**。缺口 120ms 不在任何 span 里，它不是 bug，它是**还没埋点**——不报这个数，它就永远是隐形的（7.2.2）。
8. **空 trace 判通过**。0 条 span 时所有求和都是 0、所有检查都不响，而它与「一切正常」长得一样（7.2.2）。
9. **以为「树没报错」就等于「埋点合格」**。结构与属性是两条断言：这条 trace 结构 0 违规而属性缺 3 处（7.2.3）。
10. **把「没报」当「报了 0」**。缓存两栏官方写的是「适用时才有」——没报要标出来，否则两种世界合成一个数（7.2.3、7.2.7）。
11. **一次逻辑调用记成两根顶层 span**。看板按名字聚合会把一次算成两次（7.2.4）。
12. **两层都记账**。按 span 加与按逻辑调用加，加起来就是重试那一段算两遍：$0.0275 变 $0.0550（7.2.4）。
13. **只看成功的调用**。失败的那一次花了 $0.0080，占这一次逻辑调用的 29.1%——它不产出内容，但账单上有它（7.2.4）。
14. **报分位不报算法**。同一窗 10 条数上两种算法差 428.6ms，而其中一个值是**没人经历过的**（7.2.5）。
15. **拿 10 条一窗的 p95 当系统的 p95**。10 条时 p95 就是这一窗的最大值，「p95 涨了」等价于「这一窗有一条慢的」（7.2.5）。
16. **以为头部采样对错误率和延迟是「无偏」的**。它在结果之前决定，而出错是稀有事件：10% 的头部采样把 6 条出错的**全丢了**（7.2.6）。
17. **每根 span 各自抽样**。留下的树里有挂空的子 span，与真正的链路断裂无法区分（7.2.6）。
18. **看板只报钱不报覆盖率**。缺 usage 的那一格会变成 0 元，于是「便宜了」也变成真的（7.2.7）。
19. **用被污染的基线判异常**。拿包含事故的窗口算基线，阈值会被事故抬上去（7.2.8）。
20. **连续越线每窗口都报一次**。一次事故变成三条通知，而通知条数正是告警疲劳的来源（7.2.8）。

## 面试视角

1. **「一条 trace 该有多长？」**——答粒度：**一次自足的请求**（一轮对话、一次 agent 运行、一次管线执行）；多轮与多 agent 汇成一份报告用 session 串起来，**一轮一条 trace、一段会话一个 session**。理由是「你事先不知道一段会话什么时候结束」，而按轮切让每条 trace 小而好读。
2. **「服务变慢了，你怎么定位？」**——答「把时间往下拆」：先看根的总时长与**缺口**（有多少时间不在任何 span 里），再沿树找**自耗时**最大的那一层；然后分三件事问——是模型慢、工具慢、还是重试在等退避（`gen_ai.request.model` ＋ `attempts`）。读数里那条 1,240ms 的请求：网关自耗时只有 20ms，而两次尝试 620ms，缺口 120ms。
3. **「你们的看板准吗？」**——这是能看出有没有真做过的一问。答三件事：**覆盖率**（多少格的账算得出来，读数里是 2/3）、**认哪一层**（物理尝试还是逻辑调用，两层都加会翻倍）、**分位口径**（算法 ＋ 窗口大小 ＋ 是不是直方图估计）。
4. **「采样会不会让监控失真？」**——答会，而且要分开说：头部采样便宜但**抽掉的是稀有事件**（10% 抽走 6 条出错的全部），尾部采样留住它们但要多花内存、多留 3.5 个百分点；无论哪种，**抽样必须是 trace 级且确定性的**，否则报表里会出现挂空的「断链」。
5. **「告警怎么调才不疲劳？」**——答：阈值取「基线 ＋ 抖动带」而基线要取健康段；`for`（连续窗口数）买到假报变少、付出真报变晚（读数里从 4 次告警变 1 次，代价是晚 2 个窗口）；连续越线只报一次事件，并把「持续了几个窗口」写进通知。

## 本章小结

- 可观测性三件套——**追踪**（刚才那一次花在哪一层）、**看板**（这一周钱与延迟长成什么样）、**告警**（什么时候该叫人）——共用一根线：`trace_id`；trace 的粒度是**一次自足的请求**（7.2.1）。
- **名字是接口**：看板、评估器、过滤器都按名字取数，所以动态值不进名字（放属性）、不拿模型名当名字（7.2.1）。
- 一条 trace 是**一棵树**：`自耗时` 回答「时间花在这一层还是下一层」，`缺口` 回答「有多少时间不在任何 span 里」；串行时两者相等，**并行时分叉**（0ms 对 300ms）（7.2.2）。
- **结构干净 ≠ 属性齐了**：`violations()`（重复、挂空、两个根、越界、空树）与 `missing()`（Required、条件必填）是两条断言；条件必填的典型是 `error.type`（7.2.3）。
- **重试要付钱，但只能付一次**：一次逻辑调用一根 span（官方的约定：它覆盖含全部重试的时长），重试次数写成属性；两层都记会让账单翻倍（$0.0275 → $0.0550），失败那一次占 29.1%（7.2.4）。
- **报分位要连算法一起报**：同一窗 10 条上 `nearest_rank` 1500.0ms（真发生过）对 `linear` 1071.4ms（没人经历过）；10 条一窗时 p95 就是最大值；官方的两条 `gen_ai.client.*` 指标是直方图，分位是估计值（7.2.5）。
- **采样决定看板看到哪一半世界**：10% 的头部采样把 6 条出错的**全丢了**（0/6），尾部采样留住它们（6/6）而多留 3.5 个百分点；逐 span 抽样会留下挂空（7.2.6）。
- **算不出来不是 0**：缺 usage、模型名不在价表、缓存两栏自相矛盾，三种都进 `unknown`；看板必须把钱与**覆盖率**一起报（读数里是 2/3）（7.2.7）。
- **告警的阈值是基线 ＋ 抖动带**，`for` 买到假报变少、付出真报变晚（4 次 → 1 次，晚 2 个窗口），连续越线只报一次事件（7.2.8）。
