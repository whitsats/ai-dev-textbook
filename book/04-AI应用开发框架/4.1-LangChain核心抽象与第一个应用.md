# 4.1 LangChain 核心抽象与第一个应用

## 本章导读

第 3 篇的模型出口是手写的：`zhizhou-v3/app/llm/client.py`，468 行（非空 396 行）——两套方言的传输、
有界超时、重试与退避、工具调用解析、受约束解码、`finish_reason == "length"` 的识别。
那 396 行每一条都有理由，也每一条都能被替换：**「把一次 HTTP 请求变成一个可靠的对象」这件事，
框架已经做了很多年**，而且做得比一个人几周写出来的更细。

这一篇换工具，不换目标。第 4 篇要用 LangChain 与 LangGraph 把第 3 篇做过的事**再写一遍**：
同一个知舟、同一套工具契约、同一批验收标准。真正的产出不是「会用框架」，而是一张
**对照表**——框架替你做了什么、把什么藏起来了、藏起来的那部分什么时候会回来找你。

本章只走第一步，但这一步要立住三根桩：一个**有界的模型出口**、一场**用消息对象撑起来的多轮问答**、
一本**能对上的账**。三根桩都落在可运行树的新目录 `zhizhou-v4/` 里，与 `zhizhou-v3/` 并列，
读同一份 `.env`。

## 学习目标

读完本章，你应该能够：

1. 说清 LangChain v1 的命名空间划分——`langchain.agents` / `messages` / `tools` / `chat_models` /
   `embeddings` 各装什么，`langchain-classic` 里放的是什么；
2. 用 `init_chat_model` 建出一个**有界可用**的模型对象，并解释为什么接本地兼容端点时必须显式给
   `model_provider`；
3. 分清「框架层给了什么值」与「你没给时下游会兜底成什么」，并把两个数都量出来；
4. 用消息对象而不是字典维护多轮历史，并说清 `trim_messages(max_tokens=...)` 里的 `max_tokens`
   **数的到底是什么**；
5. 从消息里取用量，并在取不到时如实报「读不到」，而不是编一个 0；
6. 用框架自带的测试替身写离线验收，并说清为什么离线读数是**装配证据**而不是成本数据。

## 4.1.1 换工具之前：先看清要换掉什么

先把两份实现摆在一起。左边是 `zhizhou-v3`（手写），右边是 `zhizhou-v4`（框架版）本章这一批：

| 能力 | 手写版（第 3 篇） | 框架版（本章） |
| --- | --- | --- |
| 模型出口 | `app/llm/client.py` 468 行：方言枚举、双传输、重试退避、工具解析 | `app/llm.py` **78 行**：一次 `init_chat_model` |
| 配置与脱敏 | 手写 `Config` ＋ `redacted()` | 仍是手写（**框架不认识你的日志**） |
| 消息与历史 | 自定义 `Message` 数据类、手拼 OpenAI 格式 | `HumanMessage` / `AIMessage` / `SystemMessage` 是**类型** |
| 裁剪 | 手写装配策略四种（full / clean / note / compress） | `trim_messages` 一个函数 |
| 用量 | 自己从响应里抄 `usage` | 消息上的 `usage_metadata` |
| 测试替身 | 自写假客户端 | 框架自带 `GenericFakeChatModel` |

先记下这张表的形状，它后面会反复出现：**框架收走的是「通用管道」，留下的是「你的口径」。**
配置脱敏、成本算成什么、失败怎么分档——这些它不知道，也不该知道。

再看数字。`zhizhou-v4/` 本章这一批五个文件共 **445 行**（`config.py` 42、`llm.py` 78、
`history.py` 108、`scripts/first_app.py` 98、`tests/test_first_app.py` 119），
而它顶掉的手写出口一个文件就是 468 行。**这不是「框架让代码变短」的意思**——
它顶掉的只是「与模型服务商打交道」这一层；循环、工具、记忆、护栏、观测一样都得自己写，
只不过下一次它们是长在框架的接口上，而不是长在自己的接口上。

## 4.1.2 v1 的命名空间：先知道东西在哪

LangChain v1 做了一件对学习者最友好、也最容易踩空的事：**把命名空间收窄了**。
旧版本里 `from langchain import ...`、`langchain.chains`、`langchain.retrievers` 满天飞；
v1 只留下做 Agent 需要的那几块，其余整体搬去 `langchain-classic`。官方文档给的表是这样：

| 命名空间 | 装什么 | 说明 |
| --- | --- | --- |
| `langchain.agents` | `create_agent`、`AgentState` | Agent 构建入口（替代 `langgraph.prebuilt.create_react_agent`） |
| `langchain.messages` | 消息类型、内容块、`trim_messages` | **从 langchain-core 重导出** |
| `langchain.tools` | `@tool`、`BaseTool`、注入辅助 | 从 langchain-core 重导出 |
| `langchain.chat_models` | `init_chat_model`、`BaseChatModel` | 统一的模型初始化 |
| `langchain.embeddings` | `Embeddings`、`init_embeddings` | 嵌入模型 |

搬去 `langchain-classic` 的是：旧的链式实现（`LLMChain` 那一族）、检索器
（`MultiQueryRetriever` 与原来 `langchain.retrievers` 的全部）、索引 API、`hub` 模块、
以及 `langchain-community` 的导出。

这张表在写代码之前必须先看，因为本章要用到的三个导入分别落在三格里：

```python
from langchain.chat_models import init_chat_model      # 模型出口
from langchain.messages import AIMessage, HumanMessage, SystemMessage, trim_messages   # 消息与裁剪
```

而如果照着手上那份教程写成 `from langchain_community.chat_models import ChatTongyi`，
在 v1 上是**装不出来的那一类错**：包还在，但位置与写法都换了。
一句话记住这一节：**v1 的迁移成本主要在导入与命名，不在概念。**

## 4.1.3 第一个模型出口：一次调用

框架版里「接模型」这件事被压成了一个函数。整个 `app/llm.py` 的长度是 78 行，其中真正干活的是这一段：

```python
# app/llm.py —— 唯一入口：每次模型调用都从这里拿对象（节选）
from langchain.chat_models import init_chat_model

from app.config import Config

# 与 v3 对齐的边界（v3 的 `client.py`：连接 5s、读 30s、重试 2 次）。
DEFAULT_TIMEOUT = 30.0
DEFAULT_MAX_RETRIES = 2


def build_model(cfg: Config | None = None, *, timeout: float = DEFAULT_TIMEOUT,
                max_retries: int = DEFAULT_MAX_RETRIES, temperature: float | None = None,
                **overrides):
    """唯一入口。**每一次模型调用都从这里拿对象**，别处不得直接构造 ChatOpenAI。

    `overrides` 是留给后面几章的（工具绑定、结构化输出、流式），
    但它有一个纪律：**只能加参数，不能改这里的默认值**。
    """
    cfg = cfg or Config.from_env()
    return init_chat_model(
        cfg.model,
        model_provider="openai",          # 本地服务商是 OpenAI 兼容端点，所以走这一支
        base_url=cfg.base_url,
        api_key=cfg.api_key,
        temperature=cfg.temperature if temperature is None else temperature,
        timeout=timeout,                  # 显式给出，不用 SDK 的 600 秒
        max_retries=max_retries,
        **overrides,
    )
```

配置那一半仍是自己写的，而且**这一半必须自己写**：

```python
# app/config.py —— 配置与脱敏：框架不认识你的日志（节选）
@dataclass(frozen=True)
class Config:
    api_key: str
    base_url: str
    model: str
    temperature: float = 0.0

    @classmethod
    def from_env(cls, getenv=os.environ.get) -> "Config":
        """缺密钥要**在装配时**就报错，而不是等到第一次调用（v3 同一条纪律）。"""
        key = getenv("LLM_API_KEY", "")
        if not key:
            raise RuntimeError("缺少 LLM_API_KEY——v4 与 v3 读同一套变量，见 .env.example")
        return cls(
            api_key=key,
            base_url=getenv("LLM_BASE_URL", "https://api.openai.com/v1"),
            model=getenv("LLM_MODEL", "gpt-4o-mini"),
            temperature=float(getenv("LLM_TEMPERATURE", "0") or 0),
        )

    def redacted(self) -> dict:
        """唯一能进日志的形态：密钥只留尾四位，其余抹掉。"""
        return {"base_url": self.base_url, "model": self.model,
                "temperature": self.temperature,
                "api_key": f"***{self.api_key[-4:]}" if self.api_key else "(未设置)"}
```

两个设计决定值得说明。

**一、变量名一个不改。** `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL` 沿用 v3 的名字，
两个版本共用一份 `.env`。第三篇与第四篇要比的是「同一件事用框架做会变成什么样」，
如果连配置方式都换了，比出来的差异里就混进了无关变量。

**二、`timeout` 与 `max_retries` 是显式参数，不是默认。** 它们不是「顺手加的保险」，
而是本章第二个要点，下一节专门讲。

## 4.1.4 框架按名字猜提供方

`init_chat_model` 最方便的地方是不用告诉它提供方：给个模型名就行。这条便利有一个边界，
而边界正好落在本书用的服务商身上——实测三条：

```console
>>> init_chat_model("gpt-4o-mini", api_key="test")
ChatOpenAI(model_name='gpt-4o-mini')                       # 从名字认出了 openai

>>> init_chat_model("agnes-2.5-flash", api_key="test")
ValueError: Unable to infer model provider for model='agnes-2.5-flash'.
            Please specify 'model_provider' directly.      # 名字里没有它能认的线索

>>> init_chat_model("agnes-2.5-flash", model_provider="openai",
...                 base_url="https://api.agnes-ai.cn/v1", api_key="test")
ChatOpenAI()                                               # 显式指定就通了
```

所以 `build_model` 里的 `model_provider="openai"` 不是冗余代码，它是**必需的一句**：
本地兼容端点提供的是 OpenAI 协议，但模型名不在框架的认识里。
这类错有个共同特征：**它在装配时抛、不在调用时抛**——比「跑到一半 401」好得多，
但前提是你把「显式指定提供方」当成纪律，而不是等它抛出来再补。

**接口契约一句话**：`model_provider` 描述的是**协议方言**，`base_url` 描述的是**地址**，
`model` 描述的是**名字**。三者不能互相代替。

## 4.1.5 有默认值不等于有边界

`init_chat_model` 返回的对象「能用」，但「能用」不等于「有界」。不传 `timeout` 时，
框架这一层确实没给值，**而真正的超时由下游 SDK 兜底**。实测（`openai` 2.36.0）：

```console
>>> from openai import _constants as sdk
>>> sdk.DEFAULT_TIMEOUT
Timeout(connect=5.0, read=600, write=600, pool=600)        # 读超时 600 秒
>>> sdk.DEFAULT_MAX_RETRIES
2
```

也就是说，一次卡住的请求可以占住十分钟，而重试两次就是半小时级别。
本书的 v3 手写出口给的是 `读 30 秒 / 重试 2 次`——**同一个程序的框架版必须显式改回来**，
否则「换了个框架」会静默地把延迟预算放大二十倍。

这件事之所以值得写成一节，是因为它有个**很难自己发现的诊断陷阱**。第一版诊断函数读的是
内部 HTTP 客户端的 `.timeout`，两种情况下读到的都是 `None`：

```text
第一版（错）：
  build_model(cfg)          -> http_client.timeout = None
  ChatOpenAI(...)           # 不传 timeout  -> http_client.timeout = None
  # 结论：两种都没设超时 —— 而它们的真实行为差二十倍
```

错在**框架把超时按请求传下去**（在 `create(..., timeout=...)` 的调用点上），
而不是在构造客户端时传。只看客户端对象，就会得出「没设超时」这个既对又没用的结论。
所以现在的诊断读三层，并把「没给值时兜底成多少」也算出来：

```python
# app/llm.py —— 把「框架写了什么、没写什么、没写时兜底成什么」读出来（节选）
    from openai import _constants as sdk          # noqa: PLC0415 —— 只有诊断这里需要它

    floor = sdk.DEFAULT_TIMEOUT
    timeout = getattr(model, "request_timeout", None)
    retries = getattr(model, "max_retries", None)
    return {
        "类型": type(model).__name__,
        "model": getattr(model, "model_name", ""),
        "框架层 request_timeout": timeout,
        "框架层 max_retries": retries,
        "未设时下游兜底的 read 超时（秒）": getattr(floor, "read", None),
        "未设时下游兜底的重试次数": sdk.DEFAULT_MAX_RETRIES,
        "实际生效的 read 超时（秒）": getattr(floor, "read", None) if timeout is None else timeout,
        "实际生效的重试次数": sdk.DEFAULT_MAX_RETRIES if retries is None else retries,
    }
```

真机跑出来的两个形态并列如下（同一个服务商、同一个模型）：

| | 本树（显式给值） | 只写 `init_chat_model(...)` |
| --- | --- | --- |
| `框架层 request_timeout` | `30.0` | `None` |
| `框架层 max_retries` | `2` | `None` |
| 未设时兜底的 read 超时 | `600`（兜底值，未生效） | `600` |
| **实际生效的 read 超时** | **30.0 秒** | **600 秒** |
| **实际生效的重试次数** | **2** | **2**（还是下游那个 2） |

最后一行要单独看一眼：**重试次数看起来「一样」，来源却不同**——
本树是显式 2，另一种是根本没设、由 SDK 兜底成 2。今天它们相等，明天 SDK 改默认值就分岔了。
这正是「有默认值不等于有边界」的完整含义：**框架的默认值不是你的决定，只是此刻的巧合。**

顺带一条纪律：读 `openai._constants` 这种私有常量，只在**诊断函数**里可以接受，
而且必须注明它是「此刻这个版本的事实，不是稳定契约」。所以它出现在 `describe_defaults()`
里，不出现在 `build_model()` 里——**依赖私有常量的代码不许进主路径**。

## 4.1.6 消息是对象：历史与裁剪

手写版把历史存成三个键的字典列表，送出去之前手拼一次 OpenAI 格式。框架版里，
消息是**类型**，历史是一个对象列表，而裁剪是现成函数：

```python
# app/history.py —— 系统消息单独存，因为它永远不该被裁掉（节选）
class ChatHistory:
    """一次会话的消息列表。系统提示单独存，因为它**永远不该被裁掉**。"""

    def __init__(self, *, system: str = "", max_messages: int = 12) -> None:
        self.system = system
        self.max_messages = max_messages
        self._messages: list = []
        self.usage = Usage()
        self.trimmed_calls = 0

    def add_user(self, text: str) -> None:
        self._messages.append(HumanMessage(text))

    def add_ai(self, message) -> str:
        """收下模型的回复：抄账、入库、返回正文。"""
        if not isinstance(message, AIMessage):
            raise TypeError(f"只收 AIMessage，收到 {type(message).__name__}")
        self.usage.add(message)
        self._messages.append(message)
        return message.text
```

裁剪那一段值得逐行看，因为它中间藏着一个**参数名与实现不符**的坑：

```python
# app/history.py —— 裁剪：max_tokens 数的到底是什么，取决于 token_counter（节选）
    def _kept(self) -> list:
        """裁剪后留下的历史（**不含**系统消息）。**纯函数式**：不改任何计数器。

        `dropped` 与 `to_messages` 都走它——否则一个「读状态」的属性会顺手加计数，
        而打印顺序一变，读数就不一样了。
        """
        return trim_messages(
            self._messages,
            max_tokens=self.max_messages,
            token_counter=len,          # 数的是**条数**，见模块文档
            strategy="last",            # 留最近的那些
            include_system=False,       # 系统消息不在这个列表里，由本类单独拼
            allow_partial=False,        # 不许把一条消息切成两半
        )

    def to_messages(self) -> list:
        """送给模型的完整入参：系统消息 ＋ 裁剪后的历史。"""
        kept = self._kept()
        if len(kept) < len(self._messages):
            self.trimmed_calls += 1
        prefix = [SystemMessage(self.system)] if self.system else []
        return prefix + kept
```

参数写着 `max_tokens`，**而它数的是消息条数**——因为我们传了 `token_counter=len`。
这不是框架的错，是它的设计：`token_counter` 决定计数单位，写 `len` 就是条数，
换成某个模型的计数字符串就是词元。它带来的第一个后果是**离线可测**（不需要分词器），
第二个后果是**必须在代码里写清**——否则下一个人会以为 `max_messages=4` 的意思是「四个词元」。

这也解释了 `_kept()` 为什么写成纯函数：`dropped` 与 `to_messages()` 都调用它，
如果它在里面顺手 `self.trimmed_calls += 1`，那么「打印一次读数」就会改变读数。
**一个读状态的属性不该有副作用**——这条在手写版与框架版里同样成立。

离线跑起来，能直接看见「系统消息没被裁掉」与「留下的是最近的那些」：

```console
$ python scripts/first_app.py --offline        # 历史上限 4 条，跑 4 轮
  用户：刷新令牌的滑动过期有什么代价？
  发出的消息 2 条：['System', 'Human']

  用户：那黑名单方案呢？
  发出的消息 4 条：['System', 'Human', 'AI', 'Human']

  用户：两种能一起用吗？
  发出的消息 5 条：['System', 'AI', 'Human', 'AI', 'Human']      # 八条历史被裁到四条

  用户：我更该先上哪一种？
  发出的消息 5 条：['System', 'AI', 'Human', 'AI', 'Human']

  账：调用 0 次｜输入 0 / 输出 0（共 0，输入占比 0.0%）
       ↑ 剧本模型不产生 `usage_metadata`——**离线读数不能当成本数据**（同一个坑在 3.10 的一键验收里也踩过）
  裁剪：累计 2 次发生裁剪，当前丢弃 4 条
```

第三轮起，发出的消息形状变成 `['System', 'AI', 'Human', 'AI', 'Human']`：
**八条历史里最早的四条被丢掉，系统消息始终在第一位。**

## 4.1.7 账在消息里

成本那一节在第 3.9 已经立好口径：输入与输出是两笔钱，且输入往往是大头。
框架版把这两个数放在消息对象上，取用是本模块里最短的一段：

```python
# app/history.py —— 记的是账，不是「调用次数」（节选）
@dataclass
class Usage:
    """这一轮会话的账：**输入与输出分开**（v3 的实测：输入占比可达 96%）。"""

    calls: int = 0
    input_tokens: int = 0
    output_tokens: int = 0
    per_call: list[tuple[int, int]] = field(default_factory=list)

    @property
    def total(self) -> int:
        return self.input_tokens + self.output_tokens

    @property
    def input_share(self) -> float:
        return round(self.input_tokens / self.total, 4) if self.total else 0.0

    def add(self, message) -> bool:
        """从一条 AI 消息里把用量抄下来。读不到就返回 False——**不编一个数**。"""
        meta = getattr(message, "usage_metadata", None) or {}
        if not meta:
            return False
        self.calls += 1
        self.input_tokens += int(meta.get("input_tokens", 0) or 0)
        self.output_tokens += int(meta.get("output_tokens", 0) or 0)
        self.per_call.append((int(meta.get("input_tokens", 0) or 0),
                              int(meta.get("output_tokens", 0) or 0)))
        return True
```

`add()` 返回 `bool` 而不是 `None`，是为了让「读不到」这件事**有地方可去**：
离线剧本模型不产生用量元数据，脚本必须据此明说「这不是成本数据」（上一节输出里那一行），
而不是打出一本 0 元的账让人以为不要钱。

真机那一轮读到的账（agnes-2.5-flash，4 轮问答）：

| 轮次 | 发出去的消息 | 输入词元 | 输出词元 |
| --- | --- | ---: | ---: |
| 1 | System ＋ Human | 71 | 32 |
| 2 | ＋ AI ＋ Human | 117 | 34 |
| 3 | ＋ AI ＋ Human（历史已满，裁掉最早两条） | **153** | 26 |
| 4 | 同上形状 | 148 | 30 |
| **合计** | 调用 4 次 | **489** | **122** |

输入占比 80.0%（489 / 611），逐次是 `71 → 117 → 153 → 148`。三个可读的形状：

1. **输入单调上涨、输出基本不变**——钱花在「每一轮把历史重发一遍」上，与第 3.9 节真机
   96.6% 的输入占比是同一个现象，只是会话更短、比例更低；
2. **第四轮输入回落（153 → 148）**——因为第三轮之后裁剪开始生效。
   这个回落是**可观测的**：账与裁剪读数是同一本；
3. **输出 122 词元、四轮**——平均一轮 30 个输出词元，与「回答控制在两句话内」这句系统提示对得上。
   **提示里写的约束，最后会以数字的形式出现在账上。**

## 4.1.8 知舟接线

### 加了什么

本章新建了与 `zhizhou-v3/` 并列的第二棵可运行树 `zhizhou-v4/`（框架版），它顶替的是 v3 的
**模型出口与消息层**这两块，其余零件仍由第 3 篇的手写版承担：

| 文件 | 行数 | 顶替 v3 的哪一块 |
| --- | ---: | --- |
| `app/config.py` | 42 | `app/llm/client.py` 的 `Config` 与 `redacted()` |
| `app/llm.py` | 78 | 同一文件的传输、超时、重试（工具解析留给 4.3） |
| `app/history.py` | 108 | `app/agent/memory.py` 的消息与裁剪部分 |
| `scripts/first_app.py` | 98 | 一条可跑的最小演示（离线 ＋ 真机） |
| `tests/test_first_app.py` | 119 | 本章六条断言的离线验收 |

两棵树**读同一份 `.env`**，因此「同一份配置下两个版本各是什么行为」这件事可以被直接对照。

### 接口契约

| 契约 | 内容 |
| --- | --- |
| 模型对象只有一个出口 | `app/llm.py::build_model()`；别处不得直接构造 `ChatOpenAI`，后面几章只能通过 `overrides` 加参数 |
| 有界性不许回退 | `timeout` 与 `max_retries` 是显式参数；任何新章节都不得把 `build_model` 的默认值改回 `None` |
| 提供方必须显式 | 本地兼容端点走 `model_provider="openai"`；不靠模型名推断 |
| 密钥不进日志 | 只有 `Config.redacted()` 的形态能进日志与打印（尾四位） |
| 历史形状 | 系统消息单独存、永远不参与裁剪；裁剪只作用于对话列表，且**纯函数式**（读状态不改状态） |
| 用量口径 | 输入与输出分开记；读不到时返回 `False`，由调用方如实说明 |

### 怎么验

```bash
cd zhizhou-v4
python scripts/first_app.py --offline      # 不需要密钥：剧本模型；**这一路是门**
set -a && . ../zhizhou-v3/.env && set +a   # 真机那一路：读同一份配置
python scripts/first_app.py                # 报读数，不当门（真机读数不进基线）
python ../tools/check_runnable.py          # 正文里的每段节选都要能在树里逐行找到
```

四道判据：

1. **离线那一句** `✔ 离线自检通过` 必须出现，且账里写着「离线读数不能当成本数据」；
2. **裁剪**：上限 4 条、跑 4 轮时，`当前丢弃 4 条`，且发出的消息第一条永远是 `System`；
3. **有界性**：`describe_defaults` 报「实际生效的 read 超时 30.0 秒 / 重试 2 次」，
   而**不传** `timeout` 的对照对象报 600 秒；
4. **一致性**：本章每个带路径标注的代码块，其每一行都要能在 `zhizhou-v4/` 里按顺序找到。

### 不能破坏什么

- **不许给 v3 加框架依赖**：第 3 篇的整条主线是「手写」，`zhizhou-v3/` 里出现 LangChain 导入
  即视为违反（见 [`PROJECT.md`](PROJECT.md) 第一节）；
- **不许改 v3 的 `.env` 变量名**：本章的对照条件就是「同一份配置、两个实现」，改名会让对照失效；
- **不许把 `describe_defaults` 移进主路径**：它依赖下游 SDK 的私有常量，只做诊断；
- **不许把离线读数当成本**：`--offline` 的账永远是 `调用 0 次`，
  任何用它算「每任务成本」的写法都是错的；
- **不许把提供方推断当成可用特性**：模型名换成本地服务商时它会直接抛装配错误。

## 常见坑

- **照抄旧教程的导入**：`langchain_community` 与 `langchain.chains` 那一路在 v1 上要么报错、
  要么把整套旧抽象又拉回来。先看命名空间表，再写第一行导入。
- **不传 `timeout` 就上线**：`init_chat_model` 不带这个参数时，读超时由下游 SDK 兜底成 600 秒。
  「能跑通」不能证明「有边界」。
- **读错超时的位置**：框架把超时**按请求**传，不在构造客户端时传。只看 `http_client.timeout`
  会得出「两种都没设」的错误结论。
- **把 `max_tokens` 当词元**：`trim_messages` 数什么由 `token_counter` 决定，
  传 `len` 就是条数。写代码时把这句注在参数旁边，否则下一个人一定会误读。
- **让「读状态」的函数改状态**：计数放在 `to_messages()` 而不是 `_kept()`；
  否则打印顺序一变，读数就变了。
- **把离线当绿就收工**：离线剧本不产生用量元数据，账永远是 0。
  它是**装配证据**，不是成本数据。
- **拿私有常量当契约**：`openai._constants.DEFAULT_TIMEOUT` 是此刻的事实，
  不是 API。它可以出现在诊断里，不可以出现在主路径里。

## 面试视角

「用过 LangChain 吗」这句话真正的考点，通常落在下面四层上：

1. **第一层：知不知道它在哪。** 答「`init_chat_model` 在 `langchain.chat_models`，
   消息与 `trim_messages` 在 `langchain.messages`（从 core 重导出），
   旧的链与检索器搬去了 `langchain-classic`」——这是入门线。
2. **第二层：知不知道它替你做了什么。** 具体到文件：手写的 396 行传输与重试被一个函数顶掉；
   **而配置脱敏与成本口径它不管**。能说出「它收走通用管道、留下你的口径」，
   比背 API 名单更有说明力。
3. **第三层：知不知道它没告诉你什么。** 一个真实答案：「`init_chat_model` 不写 `timeout` 时，
   框架层是 `None`，实际生效的是下游 SDK 的 600 秒；我们是显式改成 30 秒并写进测试的。」
   这一层是**能拉开差距的那一层**，因为它来自「去查默认值」而不是「照着文档抄」。
4. **第四层：知不知道它的抽象会漏。** `max_tokens` 数条数、超时按请求传而非按客户端构造传——
   举出一个自己踩过的漏抽象，比说「框架很好用」可靠得多。

一个常被追问的收尾问题：「那你为什么还要手写一遍？」回答要落在**对照**上：
手写一遍才知道哪些是框架给的、哪些是自己一直在做的；
而「哪些是自己一直在做的」在换框架时最容易丢——成本口径、脱敏、失败分档都属于这一类。

## 本章小结

1. LangChain v1 **收窄了命名空间**：`langchain.agents` / `messages` / `tools` / `chat_models` /
   `embeddings` 五格；旧的链、检索器、索引 API、`hub` 搬去 `langchain-classic`。
2. `init_chat_model` 会**按模型名推断提供方**；本地兼容端点的模型名不在它的认识里，
   必须显式给 `model_provider="openai"`。这类错在装配时抛，不在调用时抛。
3. **有默认值不等于有边界**：不传 `timeout` 时框架层是 `None`，
   实际生效的是下游 SDK 的 600 秒读超时与 2 次重试；本书显式统一成 30 秒 / 2 次。
   重试次数「看起来一样」的两个对象，来源不同。
4. 诊断要读**三层**：框架层参数、下游兜底常量、实际生效值。
   只看内部客户端的 `.timeout` 会得出错误结论（超时是**按请求**传的）。
5. 消息是**类型**，历史是对象列表；系统消息单独存、永不参与裁剪；
   裁剪函数是**纯函数式**的——读状态的函数不许改状态。
6. `trim_messages(max_tokens=...)` 数什么**由 `token_counter` 决定**：传 `len` 就是条数。
   参数名不是契约，实现才是。
7. 用量在 `usage_metadata` 里，输入与输出分开记；**读不到时返回 `False` 并如实说明**，
   不编一个 0。
8. 真机四轮读数：输入 `71 → 117 → 153 → 148`、输出 122，输入占比 80.0%；
   **第四轮的回落就是裁剪生效的时刻**——账与裁剪读数是同一本。
9. 离线剧本证明的是**装配正确**，它不产生用量元数据，因此**离线读数不能当成本数据**。
10. 两棵树并存的纪律：第 3 篇不出现框架依赖，第 4 篇不依赖第 3 篇的内部实现，
    只共用同一份 `.env` 与同一套工具契约。

## 练习

- **基础**：给 `zhizhou-v4/tests/test_first_app.py` 加两条断言——一条证明
  「不传 `timeout` 时实际生效值是大值、传了就变成本树的值」，一条证明
  「历史上限设为 1 时，发出的消息是 `['System', 'Human']`（只留最新一条用户消息）」。
  要求：两条都**不需要密钥**，且跑法写进 `zhizhou-v4/README.md`。
- **进阶**：把 `ChatHistory` 的裁剪从「按条数」改成「按字符数」
  （`token_counter=lambda msgs: sum(len(m.text) for m in msgs)`），
  重跑离线脚本，回答一个问题：**同样上限下，系统消息会不会被裁掉？
  为什么第一版要专门把它摘出去？** 再把两种口径的 `dropped` 读数并列成一张表。
- **挑战**：给 `describe_defaults` 加一项「配置了却没有生效的参数」——
  做法是把传进 `init_chat_model` 的关键字与对象的实际属性对一遍，
  找出「写了但没落到对象上」的那些。要求：1）至少能抓住一个真实案例
  （提示：`temperature` 在部分提供方上会被忽略）；2）写一条测试证明它
  **在参数确实生效时不报警**（反向守比正例更重要）。
