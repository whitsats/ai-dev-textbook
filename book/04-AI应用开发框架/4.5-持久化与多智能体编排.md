# 4.5 持久化、多智能体编排与实战

## 本章导读

4.4 的结尾停在「检查点」上：`publish_node` 里那句 `interrupt()` 让整张图停住等人点头。
那一章有一条被反复引用的读数——**不挂检查点时中断照样发生，而恢复才抛 `RuntimeError`**。
那一章还留了一个练习：写一个能在**新进程**里把中断续上的脚本，并说明
「为什么 `InMemorySaver` 做不到」。这一章就是那道练习的答案，而且不止于此：

- 先给一个**跨进程的检查点后端**（`SqliteCheckpointer`，200 多行，标准库 `sqlite3`），
  用它把「停在哪一步」变成一个新进程读得回来的事实；
- 再用它把 4.4 那张**工序链**换成一个**团队**：一个调度者 ＋ 三个专业角色，
  于是「谁上场、交接几次、谁来叫停」第一次成为可读的数；
- 最后把两棵树（v3 手写版 / v4 框架版）里关于「记忆」的两套东西对齐——
  **检查点不等于记忆**，这是本篇给 3.6 三张表的交代。

五组读数，前四组是机制、第五组是团队：

| 组 | 问题 | 量到的数 |
| --- | --- | --- |
| ① 快照 | 检查点存的是什么 | 6 份快照 ＝ 5 个超级步 ＋ 1 份输入；`source` 三档 |
| ② 后端 | 换个进程还读得到吗 | 内存后端读不到（0 份），SQLite 后端读得到（6 份） |
| ③ 时间旅行 | 能回到旧的那一步吗 | 同一个步骤出现 2 份快照；缺 `as_node` 直接抛 |
| ④ 交接 | 没有上限会怎样 | `GraphRecursionError`，默认上限 **10007** |
| ⑤ 团队 | 调度者怎么派人 | 离线 3 次交接收口；真机 **6 次**才收口，还绕了 5 次圈 |

读完这一章，你应该能回答一个具体问题：**一个「跑了很久、中途还等过人」的 Agent 服务，
重启之后凭什么接着跑？** 答得出来，才敢把它放到生产里。

## 4.5.1 检查点不是日志：一步一份

先说最容易搞混的一件事：**检查点不是「把每一步记下来」，而是「把某个时刻的整份状态存下来」。**
一份 `Checkpoint` 里有四组字段：

| 字段 | 是什么 | 谁在读它 |
| --- | --- | --- |
| `id` | 时间序 ID（单调递增） | 排序、恢复的游标 |
| `channel_values` | 那一刻**所有**通道的值 | 恢复时直接放回状态 |
| `channel_versions` | 每个通道的版本号 | 判断「这一步哪些通道变了」 |
| `versions_seen` | 每个节点看过哪些版本 | 判断「下一步该跑谁」 |

最后一行是这个设计的全部意义：**图之所以知道「接下来去哪个节点」，靠的不是一个计数器，
而是「每个节点看过哪些通道版本」**。所以恢复不需要重放，它只需要一份快照。

`CheckpointTuple` 把这份快照与它的上下文打包在一起：配置、快照、元数据、父配置、待写入。
本树把它们读成一张表（`app/checkpoint.py` 的 `history()`）：

```python
# app/checkpoint.py —— 把一条线程的快照读成一张表（节选）
    out = []
    for snap in app.get_state_history(config):
        values = snap.values or {}
        out.append({
            "checkpoint_id": snap.config["configurable"]["checkpoint_id"],
            "step": snap.metadata.get("step"),
            "source": snap.metadata.get("source"),
            "next": tuple(snap.next),
            "log_len": len(values.get("log", [])),
            "parent": (snap.parent_config or {}).get("configurable", {}).get("checkpoint_id"),
        })
```

拿 4.4 那张流水线跑一遍（`python scripts/persistence_multiagent.py --offline` 的第 ① 组）：

```text $ python scripts/persistence_multiagent.py --offline
一次 invoke 的返回值键：['__interrupt__', 'draft', 'summary']
步骤    来源      下一步                   账目条数
4     loop    ('publish',)          4
3     loop    ('review',)           3
2     loop    ('draft',)            2
1     loop    ('review',)           1
0     loop    ('draft', 'summary')  0
-1    input   ('__start__',)        0
快照 6 份 = 超级步 5 步 ＋ 1 份输入（step=-1）
返回值里**看不到** `log` 与 `rounds`：它们是内部账，但快照里全都在
```

四件事值得逐个说明：

1. **`step = -1` 那一份是输入**，`source = "input"`。它同样是一份完整快照，
   所以「变量还没开始跑的时候状态是什么样」也是查得到的——排查「参数没传对」
   时，这一份比日志有用得多。
2. **`source` 只有三档**：`input` / `loop` / `update`（还有一档 `fork` 留给复制线程）。
   看见 `update` 就说明有人从外部改过状态——这正是第 3 节要用的那一档。
3. **`parent` 把快照串成一条链**，一直串到 `"input"` 那一份。所以「从哪来」是可查的，
   不需要另建一张历史表。
4. **接口挡得住的地方，快照全都在**：`invoke` 的返回值只有三个键
   （4.4 的 `PipelineOutput` 定的），而 `log` 与 `rounds` 这类内部账在快照里一行不少。
   换句话说：**检查点天然是「可观测性的底料」**（3.9 那条追踪线在这里有了免费的锚点——
   每个超级步一份快照，`log_len` 就是当时的进度）。

## 4.5.2 后端与跨进程：内存后端为什么续不上

4.4 用的 `InMemorySaver` 有一句听上去很安全的名字，但它的「内存」是**进程的内存**。
把这件事变成读数只需要一个子进程（脚本的第 ② 组，子程序写在常量里、用 `subprocess` 跑）：

```text $ python scripts/persistence_multiagent.py --offline
InMemorySaver        同进程：有    另一个进程：无（快照 0 份）
SqliteCheckpointer   同进程：有    另一个进程：有（快照 6 份）
```

两行读数，一条结论：**换后端不是换介质**。`InMemorySaver` 换成 SQLite 之后，
「同一个 `thread_id`」在两个进程里读到的才是同一条线程。
顺带一个容易骗到自己的地方：`SqliteCheckpointer(":memory:")` 也跨不过进程——
**路径才是契约**，`:memory:` 只是把内存数据库换个说法。

那为什么值得**手写**一个（而不是装官方的 `langgraph-checkpoint-sqlite`）？三条理由，
每一条都在本节正文里：

1. `BaseCheckpointSaver` 一共就五个方法要实现，而**每个方法的签名都是被图调用出来的**；
   手写一遍才知道 `parent_id` 从哪来、`new_versions` 是谁在用。
2. 本书的验收要能在**不装新依赖**的机器上跑（`requirements.txt` 只有四个包），
   而 `sqlite3` 是标准库。
3. 官方的 sqlite / postgres 包已经要考虑并发、迁移、加密、异步驱动——那些是第 7、8 篇的话题。

### 存储：两张表，三个键

```python
# app/checkpoint.py —— 这套存储的全部结构（节选）
CREATE TABLE IF NOT EXISTS checkpoint (
    thread_id     TEXT NOT NULL,
    checkpoint_ns TEXT NOT NULL DEFAULT '',
    checkpoint_id TEXT NOT NULL,
    parent_id     TEXT,
    ck_type       TEXT,
    ck_value      BLOB,
    md_type       TEXT,
    md_value      BLOB,
    PRIMARY KEY (thread_id, checkpoint_ns, checkpoint_id)
);
```

主键那三个键就是契约，缺一个都会串线：`thread_id` 是一条会话线程
（等价于 3.6 的 `agent_session.id`）、`checkpoint_ns` 是命名空间
（每个子图各占一份，同一线程互不覆盖）、`checkpoint_id` 是恢复的游标。
`parent_id` 就是上表里那条链——它由 `put()` 顺手记下（`conf.get("checkpoint_id")`），
不需要调用方传。

### 五个方法里最容易写错的三处

这是本节的正文：三处都是本机跑出来的，而且**报错都不指向真因**。

**第一处：序列化器返回的是二元组，不是一段字节。** 第一版把
`self.serde.dumps_typed(checkpoint)` 直接绑进一个 `BLOB` 列，报的是
`sqlite3.InterfaceError: Error binding parameter 4 - probably unsupported type`——
看上去像「数据太大」或者「类型不对」，其实是**少解了一层元组**：
`dumps_typed` 返回 `(类型名, 字节)`，所以要存两列（`ck_type` / `ck_value`），
读回来再拼成元组交给 `loads_typed`。

**第二处：空写入会让 `commit` 抛「没有事务」。** 图有时会调 `put_writes` 而这一次没有写入，
`executemany([])` 什么也不做（因而**没有开启事务**），紧接着的 `commit()`
报 `sqlite3.OperationalError: cannot commit - no transaction is active`。
修法是先判空。这一条本身没什么了不起，但它说明了一个更普遍的事实：
**存储适配层的错误大多发生在「这一次什么都没做」的时候**，而不是数据最多的时候。

**第三处：同一个连接被两个线程用，会报「not an error」。** 这一处最值得记。
pregel 会在后台线程里落检查点，而 SQLite 的连接一旦跨线程并发使用，
报出来的是 `sqlite3.OperationalError: not an error`——**一个长得完全不像并发问题的错**。
而且它**偶发**：第一次运行完全正常，第二次才炸。
第一次跑通不等于写对了，这一条在教材里必须变成「必然」，所以本模块加了一把
`threading.RLock`，并在注释里写清它为什么在：

```python
# app/checkpoint.py —— 那把锁与它的理由（节选）
        # `check_same_thread=False`：图可能在别的线程里跑（`asyncio.to_thread` 那几条路径）。
        # **但允许跨线程访问不等于并发是安全的**——pregel 会在后台线程里落检查点，
        # 而同一个 sqlite3 连接被两个线程同时用，会报出
        # `sqlite3.OperationalError: not an error`（一个长得不像并发问题的错）。
        # 本模块第一版没有这把锁，报错发生在第二次运行时，第一次完全正常——
        # 这类「偶发」在教材里必须变成「必然」，所以加锁并且注释清楚它为什么在。
        self.conn = sqlite3.connect(path, check_same_thread=False)
        self._lock = threading.RLock()
        with self._lock:
            self.conn.executescript(SCHEMA)
            self.conn.commit()
```

生成器的锁还有一处分寸：`list()` 是**生成器**，锁若抱着不放，
调用方一边遍历它、一边再调 `get_tuple` 就会自己把自己锁住
（`RLock` 也救不了——那是同一线程的两次进入）。所以本实现**先把行读完再离开锁**，
再在锁外面 yield。这一条在官方那份 sqlite 实现里同样存在，只是它用了连接池。

### 官方后端对照

| 后端 | 在哪 | 跨进程 | 本课用它做什么 |
| --- | --- | --- | --- |
| `InMemorySaver` | `langgraph-checkpoint`（随 langgraph 装） | ✗ | 4.4 的中断演示、本章的测试 |
| `SqliteSaver` / `AsyncSqliteSaver` | 需另装 `langgraph-checkpoint-sqlite` | ✓ | 官方的最小持久化方案 |
| `PostgresSaver` | 需另装 `langgraph-checkpoint-postgres` | ✓ | 多实例部署（第 7、8 篇） |
| 本树的 `SqliteCheckpointer` | `app/checkpoint.py`，标准库 | ✓ | 让接口可见的那一份 |

选后端这件事有一句可照用的判据：**「这条线程会不会换进程」决定要不要持久化；
「会不会换机器」决定要不要上数据库服务**。只在一台机器上跑，SQLite 就够；
一旦要多实例共享线程（例如灰度发布时两个副本接同一批用户），
内存与文件都不行——那时检查点就是一个**共享状态**，得放进数据库。

## 4.5.3 时间旅行：回到旧快照，再往前走

有了历史，第二件事就是「回到某一步」。三个 API 分工很清楚：

- `app.get_state_history(cfg)`：列出这条线程的全部快照（最新在前）；
- `app.update_state(旧配置, {...})`：在**某一份快照上**改一笔，造一份新快照；
- `app.invoke(None, 旧配置)`：从那一步**接着往下跑**（`None` 表示「不换输入」）。

跑一遍（第 ③ 组）：

```text
第 1 步的快照：1f1b0da4… next=('review',)
不给归属 → InvalidUpdateError: Ambiguous update, specify as_node
补上 `as_node='draft'` 之后：这一笔记在 `draft` 头上
分支后各步骤的快照份数： {-1: 1, 0: 1, 1: 1, 2: 2, 3: 1, 4: 1}
步骤 [2] 各有 2 份快照——**同一个步骤两条路**，旧的那条不会被覆盖
从第 1 步再走一遍：草稿＝【草稿 2】发布说明：知舟是一个把写稿流程拆成工…（长度 331）
```

第一行与第二行是本组最值钱的两条：

**① 「回到某一步」的全部秘密就是配置。** 配置里多一个 `checkpoint_id`，
同一张图、同一个 `thread_id`，起点就换到那一步。**没有单独的「回滚 API」**——
这正是前面那句「快照是游标」的实际含义。

**② 分支点上改状态必须给 `as_node`。** 报错是
`InvalidUpdateError: Ambiguous update, specify as_node`。
为什么会有歧义：第 2 步是两个节点（`draft` 与 `summary`）在同一个超级步里写的，
所以那一笔人工修改「算谁写的」不确定，而 `versions_seen` 需要这个答案才能决定下一步跑谁。
**框架不猜**——这一点值得记住：它宁可报错，也不替你定一个可能错的归属。

第三行是「分支」：`update_state` 造的是 `source="update"` 的新快照，
它**挂在同一个步骤号上**，与原来那条并存。所以「改坏了退回去」不是靠备份，
而是靠**两条路都在库里**。`invoke(None, 旧配置)` 再跑一遍，
`draft` 又从第 1 步重新长了一次（长度 331，与第一次的最终稿一样——因为剧本模型是确定性的）。

`at_checkpoint()` 这个三行函数因此值得单独存在（`app/checkpoint.py`）：

```python
# app/checkpoint.py —— 「回到某一步」的配置，三个键一次给全（节选）
    return {"configurable": {"thread_id": thread_id, "checkpoint_ns": checkpoint_ns,
                             "checkpoint_id": checkpoint_id}}
```

理由是**两个后端对「配置缺键」的容忍度不一样**：少给 `checkpoint_ns` 时，
内存后端用下标读、直接 `KeyError: 'checkpoint_ns'`（栈顶指向 `perform_superstep`，
看不出是配置的问题）；而本模块的 SQLite 后端用 `.get(..., "")` 兜住了、照常工作。
同一个 bug 在 A 后端静默、在 B 后端报错，归因很容易找错地方——
统一从一个函数造配置，这类差异就没有机会出现。

## 4.5.4 检查点不等于记忆：与 3.6 三张表的对账

这一节回答一篇作业：**框架里的检查点，能不能替掉 3.6 那三张表？** 答案是不能，
而要看清为什么不能，最好的办法是把两边的概念一一对上：

| 3.6 的东西 | 框架里的对应物 | 作用域 | 谁在查它 |
| --- | --- | --- | --- |
| `agent_session.id` | `thread_id`（检查点的第一主键） | 一条会话线程 | 恢复、时间旅行 |
| `agent_message`（role / content / tokens） | 检查点的 `channel_values`（消息通道） | 同上，随快照滚动 | 装配一次请求的上下文 |
| `agent_memory`（跨会话的偏好与事实） | **没有对应物**——框架里要另用 `store` | **按用户**，跨线程 | 召回偏好、个性化 |

第三行是关键。检查点是**按线程分仓**的：`app.get_state(new_thread("nope"))`
在本机读到的是一份空状态（脚本里那一行 `未写过的线程` 就是这个读数）——
**同一个用户换一条新线程，检查点里什么都读不到**。而 3.6 的长期记忆要的正好相反：
它必须跨会话活着。所以两边的边界是：

- **检查点回答「这条线程走到哪一步」**——它是流程的账，包含「中断停在哪」、「哪一步是谁写的」；
- **记忆回答「这个用户是谁」**——它是人的账，包含偏好、称呼、已发布过什么。

两个直接的工程后果：

1. **删用户要两边都删。** 检查点的 `channel_values` 里存着完整的消息正文，
   只删 3.6 的消息表而留着检查点，等于「删了但没删干净」。本模块因此实现了
   `delete_thread()`：它一次删掉这条线程的全部快照与待写入——
   第 3.8 节承诺的「能按用户彻底清空」，到这里才算落到位。
2. **长期记忆不能塞进检查点。** 一个常见的省事做法是把偏好写进状态里跟着快照滚动，
   代价是：换一条线程就丢、每条线程各存一份副本、
   而且它会随每一次时间旅行被「恢复」成当时那个旧值。**检查点是不可变的账，
   记忆是可变的事实**——把两件事放进一个容器，两边都会坏。

## 4.5.5 Supervisor：一个调度者与三个角色

4.4 那张图是**一条工序链**：摘要 → 起草 → 自评 → 发布。这一节换一种拓扑：
**一个调度者 ＋ 三个专业角色**，角色干完都回到调度者，由它决定下一步派谁。
这就是常说的 Supervisor 模式——3.7 用手写编排器做过同一件事，这里是它的框架形态。

调度者的决策是**一次模型调用**还是**一个纯函数**，两条路都能跑。本树两条都写了，
接口完全一样（`decide(state) -> (角色, 理由)`），所以**换调度者不用改图**：

```python
# app/supervisor.py —— 结构化输出：调度者只有四个出口（节选）
class Route(BaseModel):
    next: Literal["researcher", "writer", "reviewer", "done"] = Field(
        description="下一步交给谁；全部完成时给 done")
    reason: str = Field(default="", description="一句话说明为什么这么派")
```

`Literal` 让服务端**只能**从这四个值里挑一个——但那不等于它一定挑对。
4.2 量过这件事：结构化输出保证形状，不保证语义。这一章的读数是它的续集（见第 7 节）。

规则版调度者长这样（同文件的 `decide_by_rules()`），它只有一件事值得注意——
**三个通道全部用 `.get(..., "")` 读**：

```python
# app/supervisor.py —— 规则版调度者（节选）
    handoffs = state.get("handoffs", 0)
    if handoffs >= state.get("max_handoffs", 0):
        return ("done", f"限额用尽（已交接 {handoffs} 次）")
    if not state.get("brief"):
        return ("researcher", "缺要点")
    if not state.get("draft"):
        return ("writer", "缺草稿")
    if not state.get("verdict"):
        return ("reviewer", "缺审校结论")
```

为什么不是「防御性编程的洁癖」：本图挂了输入 schema（调用方只该给 `task` 与 `max_handoffs`），
于是 `initial_team_state()` 里写好的 `brief=""` 这些初值**在入口就被过滤掉了**——
第一次读它们时通道里什么都没有。第一版直接下标，第一次运行就 `KeyError: 'brief'`。
这是 4.4 那条 `max_rounds` 事故的**同族**：输入 schema 是一道白名单，
而白名单会把你顺手给的初值一起挡掉。区别只在这次栈顶指向那个调度者节点、
上次指向条件边的路由函数——**两次报的位置都不是真因**。

装配上，团队图比工序链多一条边：**每个角色的出口都回到调度者**，于是图成环。

```python
# app/supervisor.py —— 团队的形状（节选）
    builder.add_edge(START, "supervisor")
    builder.add_conditional_edges("supervisor", route_after_supervisor,
                                  {name: name for name in SPECIALISTS} | {"done": END})
    for name in SPECIALISTS:            # 每个角色干完都回到调度者：这就是「团队」的形状
        builder.add_edge(name, "supervisor")
```

离线跑一遍（第 ⑤ 组）：

```text $ python scripts/persistence_multiagent.py --offline
输出 schema 的键：['answer', 'hops']
上场顺序（也在返回值里）：
   researcher -> brief（14 字）
   writer -> draft（27 字）
   reviewer -> verdict（8 字）
调度记录（**只在检查点里**）：
   supervisor -> researcher（缺要点）
   supervisor -> writer（缺草稿）
   supervisor -> reviewer（缺审校结论）
   supervisor -> done（审校通过）
调度了 4 次：{'researcher': 1, 'writer': 1, 'reviewer': 1, 'done': 1}
交接次数：3 ｜ 最后一条：supervisor -> done（审校通过）
```

三条读数各有一句结论：

- **输出 schema 只留两个键**（`answer` / `hops`），调度记录只在检查点里。
  这不是巧合，而是本树刻意的分界：**「谁决定了什么」是内部账**（要能查、但不该是接口）。
  想读它就得挂检查点——顺带量到一件事：**不挂检查点，`get_state` 直接抛
  `ValueError: No checkpointer set`**，也就是「连自己的账都读不回来」。
- **上场顺序与交接账对齐**：三个角色各一次、调度四次，最后一次是 `done`。
  原因是「两个出口留下不同痕迹」那一条（4.4）在这里变成了**四条**：
  `缺要点` / `缺草稿` / `缺审校结论` / `审校通过`—— 一眼能看出流程是在哪一步收的口。
- **`max_handoffs` 住在状态里，不订在构造参数上**。`build_team()` 没有这个参数：
  上限是「这一次运行」的输入，不是「这张图」的属性。订错地方，同一张图就跑不了
  两种预算的对照——而第 6 节那两条读数正是同一张图跑两种预算。

### 与 v3 手写编排器的对照

| 维度 | v3（3.7 手写） | v4（本章） |
| --- | --- | --- |
| 交接契约 | 函数返回值的元组（谁交给谁、交了什么） | 状态里的 `next` 键 ＋ 条件边的映射表 |
| 预算 | 编排器里的一个整数，按份切 | 状态里的 `max_handoffs`，由归约器累加 |
| 终止 | 编排器里的终止判定（3.3 的五类） | 调度者自己返回 `done`（同一件事的另一处写法） |
| 谁能看见流程 | 读那一段代码 | `route_log` ＋ 检查点 |
| 加一个角色 | 改编排器的分支 | 加一个节点 ＋ 一行映射 |

**这张表里没有「谁更好」。** 手写版的优势是链路短、任何一步都能下断点；
框架版的优势是「流程是可查的数据」。判据是同一个问题：
**这套编排将来要不要被观察、被改、被回放？** 要，就值得把它变成图。

## 4.5.6 交接的两种载体与那条必须写进流程的限额

### 先量「没有限额会怎样」

两个节点互相委派、谁也不说「我干完了」，第 ④ 组把这件事跑成了读数：

```text $ python scripts/persistence_multiagent.py --offline
无上限 → GraphRecursionError：Recursion limit of 10007 reached without hitting a stop conditio
         两个节点共跑了 10007 次（默认上限是一个大得不像话的数）
recursion_limit=12 → 同样撞，共跑了 12 次：**上限管的是图，不管业务**
```

两条结论：

1. **默认上限是 10007 个超级步**——对一次「谁交给谁」的委派来说，
   这个数等于没有上限。它是个安全网，不是限额。
2. **把 `recursion_limit` 调小只改变撞墙的位置**，不改变结果：它治的是「图跑太久」，
   治不了「这个流程本来就没有出口」。

所以限额要**写进流程**。把上限放进状态之后，同一张图跑两种预算：

```text $ python scripts/persistence_multiagent.py --offline
不给检查点 → get_state 抛 ValueError: No checkpointer set
有上限（2 次）→ **正常返回**：上场 2 次，末条决定：supervisor -> done（限额用尽（已交接 2 次））
```

差别就在这两行之间：**没有限额时「停下来」是一个异常，有限额时它是一个结果**——
而结果是带账的（`限额用尽（已交接 2 次）`），可以被指标统计、可以被测试断言。
这与 3.3 的五类终止条件、3.9 的「运行中断不该记成模型失败」是同一条纪律的两个侧面。

### 再量两种载体

调度者说完「下一步谁上场」，把它交给框架有两种写法：

| 载体 | 写法 | 装配代价 | 目标名写错会怎样 |
| --- | --- | --- | --- |
| 状态键 ＋ 条件边 | 返回 `{"next": ...}`，图上有 `add_conditional_edges` | 多一行映射表 | **运行期** `KeyError`（路由值漏在映射表外） |
| `Command(goto=...)` | 节点直接返回跳转目标 | 少一行，图上看不出分支 | **静默**：只写一句日志，然后当作没写 |

第二种写法的隐患是这一节要记的东西。本机实测：`Command(goto="不存在的节点")`
既不在编译期报错、也不在运行期抛异常，只在日志里留一句
`wrote to unknown channel branch:to:nope, ignoring it`，然后**图正常结束**。
所以一条纪律：**用 `Command(goto=...)` 时，目标名必须来自一个常量元组**
（本树的 `SPECIALISTS`），而不是拼出来的字符串——否则「跳错人」和「跳到了」长得一模一样。

这与 4.4 的孤立节点（官方说 compile 会查、实测不拦）、4.3 的 `when` 谓词静默失效
是**同一族**：框架在「结构上说得通但语义上错了」的地方，大多选择沉默。
三次都出现在同一个位置上——**跨节点的那条线**。

## 4.5.7 真机：模型调度者把自己绕进去了

把规则调度者换成模型调度者（`model_supervisor()`：一次结构化输出调用，理由截断到 40 字），
同一张图、同一个任务，真机跑一遍（本机 `agnes-2.5-flash`）：

```text
上场顺序（也在返回值里）：
   researcher -> brief（55 字）
   researcher -> brief（95 字）
   researcher -> brief（95 字）
   researcher -> brief（95 字）
   researcher -> brief（95 字）
   writer -> draft（95 字）
调度记录（**只在检查点里**）：
   supervisor -> researcher（草稿和审校均为空，需要先由 researcher 收集新版本信息才能动笔。）
   supervisor -> researcher（当前草稿为空，需先由 researcher 补充新版本的具體變更內容（新增功能、）
   supervisor -> researcher（发布说明需要具体版本变更内容，先由检索者补充功能、修复和优化信息后再进入写作阶段）
   supervisor -> researcher（发布说明需要基于具体变更内容，当前缺少新版本的功能更新、问题修复和性能优化信息，）
   supervisor -> researcher（发布说明依赖具体变更内容，需检索者先明确版本号和更新细节才能继续推进写作。）
   supervisor -> writer（检索者已请求具体变更内容，但当前任务状态显示草稿为空、信息待补充，需由write）
   supervisor -> done（检索者需要用户补充版本变更细节才能继续，已无法单方面推进，应终止当前阶段并等待用）
调度了 7 次：{'researcher': 5, 'writer': 1, 'done': 1}
交接次数：6 ｜ 最后一条：supervisor -> done（检索者需要用户补充版本变更细节才能继续，…）
```

这是一次**失败得很漂亮**的运行。**但它只是一次运行**——同一条命令再跑一遍，绕圈的角色就换了：

```text
上场顺序（也在返回值里）：
   writer -> draft（12 字）
   reviewer -> verdict（2 字）
   writer -> draft（12 字）
   writer -> draft（26 字）
   writer -> draft（78 字）
   writer -> draft（195 字）
调度了 7 次：{'writer': 5, 'reviewer': 1, 'done': 1}
交接次数：6 ｜ 最后一条：supervisor -> done（模型想派 writer，但限额已用尽）
```

两遍并排看，就能分出**哪三件事是不变量、哪三件是这一遍的偶然**：

| 量 | 第一遍 | 第二遍 | 是不是不变量 |
| --- | --- | --- | --- |
| 调度记录条数 | 7 | 7 | ✅ |
| 交接次数（＝限额） | 6 | 6 | ✅ |
| 末条决定 | `supervisor -> done` | `supervisor -> done` | ✅ |
| 被反复派的角色 | `researcher` ×5 | `writer` ×5 | ❌ 换了 |
| 重复派送是否等价 | 五次同一段 95 字 | 12 → 12 → 26 → 78 → 195 字 | ❌ 不保证 |
| 末条由谁按下 | 模型自己选了 `done` | 模型还想派 `writer`，被兜底按住 | ❌ 换了 |

所以下面三条结论只认前三行那三件事，**不认角色名、也不认那 95 字**——
凡是随运行变的数，这一节一律不拿来当论据：

**① 模型调度者看的是「够不够」，不是「空不空」。** 规则调度者一看到 `brief` 有值就往下走；
模型看到的是「要点只有一句话，够写发布说明吗」——不够，于是它**又派了同一个角色**，
一连五次。**重复派同一个人 ＝ 每次都花一次模型调用、而流程没有推进**（第一遍的五次
连输出都一样，第二遍的五次至少长度在变，但同样没有一次让它收口）。

**② 限额的作用不是每一遍都显形，但只有它保证最坏情况一定收口。** 两遍都恰好用尽六次交接，
末条都是 `done`——**但按下它的不是同一只手**。第一遍是模型自己选的 `done`
（理由：「已无法单方面推进，应终止当前阶段」）；第二遍模型还想再派一次 `writer`，
是 `supervisor._decide` 里那句兜底（「模型想派 X，但限额已用尽」）把它按住的。
第一遍那一次看着「模型挺懂节制」，实际上**它只是碰巧走到了这一步**：同一个任务、同一句提示，
换一遍运行就在同一个位置上不肯罢手。所以那一道「框架外的兜底」不是多余的保险——
它才是让最坏情况一定结束的那一行（3.3 的五类终止条件、4.4 的 `recursion_limit` 同一条纪律）。

**③ 真机读数只报数，不做归因。** 两遍都是「6 次交接里 5 次绕圈」，看上去像「流程设计有缺陷」，
但换个任务（比如给 `researcher` 的提示加上「可以接收追问」）它可能一次就过；
而**绕圈的是谁，两遍就不一样**。**同一条路径跑两遍的差可能大于两条路径之差**
（4.3 那条教训在这里再次适用）：真机读数用来发现问题，不用来下判决。
要在真机上做对照实验，就得固定种子、跑多次、报分位——那是第 7 篇的内容。

顺带一条工程上的结论：**调度者越聪明，硬限额越不能少**。
规则调度者不会绕圈（它只认得「通道空不空」），但它也判断不了「要点够不够」；
模型调度者判断得好，却会在「不够」上反复加码。
两者都不是缺陷——**缺陷是没有那条上限**。

## 4.5.8 知舟接线

### 加了什么

这一节给知舟加的是**「能跨进程续跑」＋「能分工」**两件事，都属于 v4（框架版）的第五段增量：

- `zhizhou-v4/app/checkpoint.py`（新文件，约 260 行）：一个跨进程的检查点后端
  （`BaseCheckpointSaver` 的最小实现）＋ `at_checkpoint()` ＋ `history()`；
- `zhizhou-v4/app/supervisor.py`（新文件，约 240 行）：Supervisor ＋ 三个角色 ＋
  两种交接载体（条件边 / `Command(goto=...)`）；
- `zhizhou-v4/scripts/persistence_multiagent.py`（五组读数）＋
  `zhizhou-v4/tests/test_persistence.py`（18 条离线用例）。

至此第 4 篇收口：v4 与 v3 用同一份 `.env` 做同一件事，
**v3 是手写版、v4 是框架版**，两棵树都在树里、都能跑、都被同一道门守着。

| 4.4 的状态 | 4.5 的状态 |
| --- | --- |
| 检查点是 `InMemorySaver`（进程内） | 本树自带的 `SqliteCheckpointer`（跨进程） |
| 只有一条工序链 | 另有「调度者 ＋ 三角色」的团队图 |
| 中断只能同进程续跑 | 换个进程照样能读回快照、从旧步骤重跑 |
| 没有长期记忆的位置 | 与 3.6 三张表划定边界：检查点不是记忆 |
| 交接是「下一步是谁」（隐式） | 交接有账（`hops` / `route_log`）**且有上限** |

### 接口契约

| 契约 | 形态 | 说明 |
| --- | --- | --- |
| 后端 | `SqliteCheckpointer(path, *, serde=None)` | 传给 `compile(checkpointer=...)`；`close()` 关连接 |
| 五个方法 | `get_tuple` / `list` / `put` / `put_writes` / `delete_thread` | 另带 `a*` 异步包装（`asyncio.to_thread`） |
| 回到某一步 | `at_checkpoint(thread_id, checkpoint_id, checkpoint_ns="")` | 三个键一次给全，避免后端差异 |
| 快照表 | `history(app, config) -> list[dict]` | 六个字段：id / step / source / next / log_len / parent |
| 团队装配 | `build_team(model=None, *, checkpointer=None, real=False, decide=None)` | **没有 `max_handoffs` 参数**：它是状态的输入 |
| 团队输入 | `initial_team_state(task, *, max_handoffs=6)` | 与 `TeamInput` 两个键对齐 |
| 团队输出 | `{"answer", "hops"}` | `route_log` 是内部账，只在检查点里 |
| 调度者接口 | `decide(state) -> (角色, 理由)` | 规则版 `decide_by_rules` ／ 模型版 `model_supervisor(model)` |

### 怎么验

```bash
# 1）五组机制读数（不需要密钥，提交门跑这个）
cd zhizhou-v4 && python scripts/persistence_multiagent.py --offline

# 2）18 条离线用例（不依赖 pytest）
cd zhizhou-v4 && python tests/test_persistence.py

# 3）真机：模型调度者 ＋ 模型角色，只报读数
cd zhizhou-v4 && python scripts/persistence_multiagent.py --real
```

第 ① 组与第 ② 组的结果写在本章第 1、2 节，第 ③–⑤ 组在第 3–7 节——
**每一条都是先跑后贴的**，包括那条 `GraphRecursionError` 的 10007
和真机那次「5 次绕圈」。本节是**实跑**：
SQLite 后端、跨进程读回、时间旅行、交接限额与团队编排都在本机复现过；
真机那一路用同一份 `.env` 打通了 3.6 的三张表所依赖的持久化路径的那一半
（长期记忆仍由 v3 的表负责——**本树不重造它**）。

### 不能破坏什么

- **不许把 `:memory:` 当默认路径。** 那等于把「持久化」换成「看起来像持久化」；
  本节的第 ② 组读数就是照它写的。
- **不许在 `put_writes` 之前少判空。** 空写入会让 `commit` 抛
  「no transaction is active」——那是一次偶发、且与数据无关的失败。
- **不许把锁去掉后再测并发**。这一条不是保守：SQLite 的连接跨线程使用会报
  「not an error」，而它**第一次跑不出来**。
- **不许把 `max_handoffs` 搬回构造参数。** 它是「这一次运行」的输入；
  搬回去之后，第 6 节那条「同一张图两种预算」的对照就写不出来了。
- **不许删 `initial_team_state` 里的累加键初值，也不要依赖它们。**
  输入 schema 会把它们过滤掉——所以节点读通道一律走 `.get`，这条是硬约定。
- **不许把长期记忆写进检查点。** 换一条线程就丢，而且会随时间旅行被恢复成旧值；
  3.6 的三张表仍然是唯一的那份记忆。
- **不许让真机读数进提交门。** 第 5 节那 5 次绕圈说明它不稳定；
  门只跑 `--offline`（`tools/check_runnable.py` 的 `offline_cmds` 里是这一条）。

## 常见坑

- **把检查点当日志**：它是一步一份的**整份状态**，不是一次一步的增量记录。
- **以为「换了后端」就是「换了介质」**：`InMemorySaver` 换成 `SqliteCheckpointer(":memory:")`
  仍然跨不过进程——路径才是契约。
- **以为 `channel_values` 只存一份摘要**：它存的是完整正文，所以删用户时必须一起删。
- **把序列化器的返回值当字节**：`dumps_typed` 返回 `(类型, 字节)` 二元组，
  少解一层报的是 `InterfaceError: ...probably unsupported type`。
- **不给存储加锁就跨线程用**：报 `sqlite3.OperationalError: not an error`，且第一次往往正常。
- **在生成器里抱锁不放**：调用方一边遍历、一边再调别的方法就会自己锁住自己。
- **`list()` 按行号排序**：要按 `checkpoint_id` 倒序——并发写入时行号不是时间序。
- **配置里少 `checkpoint_ns`**：内存后端直接 `KeyError`，SQLite 后端却不报——
  同一个 bug 在两个后端表现不同，归因极易找错。
- **在分支点上不给 `as_node`**：`Ambiguous update`——框架不猜这笔算谁写的。
- **以为 `update_state` 会覆盖旧路**：它是**新增一条分支**，两条都在库里。
- **以为「跑完的线程再 resume」是重放**：它返回旧状态（4.4 那条在这里同样成立）。
- **把输入 schema 当建议**：它会把 `initial_*` 函数里给的初值一起过滤掉，
  于是第一次读通道就 `KeyError`——节点读通道一律用 `.get`。
- **用 `recursion_limit` 当交接限额**：它数超级步、默认 10007，治的是图跑太久，
  治不了「流程本身没有出口」。
- **用 `Command(goto=...)` 又拼字符串目标名**：写错不报错，只留一句日志然后当作没写。
- **以为模型调度者会数预算**：它不认识你的限额，兜底那一行必须自己写。
- **用一次真机运行给流程下结论**：同一路径跑两遍的差可能大于两条路径之差。

## 面试视角

「你怎么让 Agent 服务重启之后接着跑」这个问题，答案的层次也分四层：

1. **第一层：说出检查点是什么。** 「一次超级步一份快照，存整份通道状态 ＋ 版本号，
   配置是线程 ID ＋ 命名空间 ＋ 快照 ID 的三元组；恢复靠的是快照，不是重放。」
   再补一句「`InMemorySaver` 活在进程里，跨进程要用 SQLite 或 Postgres」——
   这两句能立刻把「用过」和「配过」分开。
2. **第二层：说出后端怎么选。** 「本机单实例 SQLite 够；多实例共享线程就必须是数据库，
   因为那时检查点是一个共享状态。」再举一个具体的：灰度发布时两个副本接同一批用户。
3. **第三层：说出记忆与检查点的边界。** 「检查点按线程分仓，回答『这条线程走到哪一步』；
   跨会话的偏好是另一份东西，按用户存，框架里对应 `store` 或者自己的表。
   两者的删除策略也连在一起：检查点里有正文，删用户要两边都删。」
   这一层最容易讲出彩，因为它证明你想过数据治理，而不只是把 API 串起来。
4. **第四层：说出多智能体的那条线。** 「Supervisor 模式是一个调度者 ＋ 若干角色，
   角色干完回到调度者；交接可以用状态键 ＋ 条件边，也可以 `Command(goto=...)`。
   **关键是交接必须有写进流程的上限**——`recursion_limit` 不是限额，
   它默认一万次，而且撞上去是一个异常而不是一个结果。」
   最后补一条自己的读数：「我在模型调度者上跑过两次，两次都在『要点不够』上连派了五次同一个角色；
   其中一遍是限额把它按停的，另一遍是它自己罢手的——而**绕的是哪个角色两遍还不一样**。
   所以限额不是每遍都显形，但只有它能保证最坏情况结束。」

一个常见的追问是「多智能体到底比单智能体强在哪」。诚实的回答落在**成本与可观测性**上：
分工带来的不是「更聪明」，而是**每一步的输入变小**（每个角色只带自己需要的那部分）
与**失败可定位**（`route_log` 直接告诉你谁在哪一步没干活）。
如果这两点都不需要，单智能体少一层交接、少一处能出错的地方。

## 本章小结

1. **检查点是一步一份的整份状态**：`id` / `channel_values` / `channel_versions` /
   `versions_seen`，其中 `versions_seen` 就是「下一步跑谁」的依据——所以恢复不用重放。
2. **配置就是游标**：`thread_id` ＋ `checkpoint_ns` ＋ `checkpoint_id`；
   「回到某一步」与「接着最新一步」用的是同一个方法。
3. **快照数可以对账**：本树那条流水线一次运行 6 份 ＝ 5 个超级步 ＋ 1 份输入；
   `source` 只有 `input` / `loop` / `update`（＋ `fork`）四档。
4. **内部账在快照里，不在返回值里**：输出 schema 只放 `summary` / `draft` / `approved`，
   而 `log` 与 `rounds` 全在检查点——这是免费的观测锚点。
5. **换后端不是换介质**：`InMemorySaver` 与 `SqliteCheckpointer(":memory:")`
   都跨不过进程；跨进程要的是一条**路径**。
6. **手写后端只要五个方法**，而三处最容易错的地方是：序列化器返回的是二元组、
   空写入会让 `commit` 抛错、同一连接跨线程会报「not an error」（且第一次往往正常）。
7. **时间旅行靠的是「不动原来的路」**：`update_state` 造分支、`invoke(None, 旧配置)` 从旧步骤续跑；
   旧的那条不会被覆盖。
8. **分支点改状态必须给 `as_node`**：`Ambiguous update`——框架不替一个可能有歧义的动作定归属。
9. **检查点不是记忆**：它按线程分仓；跨会话的偏好必须另存（3.6 的三张表）。
   两者的删除策略连在一起：**删用户要两边都删**。
10. **Supervisor 是一个调度者 ＋ 若干角色**，角色干完回到调度者；
    调度者的接口是 `decide(state) -> (角色, 理由)`，**换调度者不用改图**。
11. **上限住在状态里**：它是「这一次运行」的输入，不是「这张图」的构造参数；
    订错地方，两种预算的对照就没法做。
12. **没有写进流程的限额，唯一能停住图的是一个异常**：`GraphRecursionError`，
    默认上限 **10007** 个超级步；有限额时「被截断」是一条账（`限额用尽`）。
13. **两种交接载体各自藏一种错**：状态键＋条件边漏了映射表会运行期 `KeyError`；
    `Command(goto=...)` 目标名写错**静默**——所以目标名要来自常量元组。
14. **模型调度者会绕圈**：真机上它连派了五次同一个角色，六次交接用尽才收口——
    **调度者越聪明，硬限额越不能少**。但**别拿一遍真机当结论**：
    第二次跑时绕的是另一个角色、末条是模型自己想派而**被兜底按住**的，
    而第一遍是它自己选停的。两遍共有的只有「七条记录／六次交接／末条 `done`」三件事。

## 练习

- **基础**：给 `SqliteCheckpointer` 加一个 `stats()`，返回这条线程的快照数、
  最早与最新快照的时间戳、以及库里两行合计的字节数。要求：
  1）写两条测试（一条空线程、一条跑完流水线的线程）；2）回答一个问题——
  同一张图跑 10 次之后，**库里的字节数是怎么长的**？用读数回答，不要凭感觉。
- **进阶**：把团队从「调度者 ＋ 三个角色」改成**子图**：让每个角色是一张独立的图
  （带自己的状态 schema），再当节点挂进主图。要求：
  1）主图与子图之间**只共享一个键**；2）写一条测试证明「子图的私有通道在主图里读不到」；
  3）回答——**改成子图之后，交接账要记在哪一层？** 说清你的选择与代价。
- **挑战**：把限额换成**预算**：不再数「交接了几次」，而是给这条线程一个词元额度，
  每步从检查点里读已用量、写回新增量，用尽时正常收口。
  要求：1）额度用尽与交接用尽**在账上必须能分开**；2）写一条测试证明
  「换个进程接着跑，额度不会被重置」（提示：已用量住在哪）；
  3）回答——如果两个进程**同时**跑同一条线程、同时扣额度，会先坏在哪里？
