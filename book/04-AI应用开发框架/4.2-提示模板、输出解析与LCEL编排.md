# 4.2 提示模板、输出解析与 LCEL 编排

## 本章导读

4.1 解决了「怎么拿到一个模型对象」。这一章解决它之前与之后的两个问题：
**送进去的那段话是怎么拼出来的**（提示），以及**回来的那段话怎么变成能用的数据**（解析）。

这两件事在第 3 篇里都是手写的。v3 的提示是一份 Markdown 文件（`app/llm/prompts/article_summary.md`），
读进来是一整个 `str`，变量名只活在写代码那个人的脑子里；v3 的解析是
`schemas.py::validate()`，把服务端返回的 JSON 用 Pydantic 校一遍，出错时把
`ValidationError` 翻成人话。

框架版把这两头换成了**对象**：提示是 `ChatPromptTemplate`（它自己知道需要哪几个变量），
解析是 `with_structured_output`（返回的就是校验过的对象）。而把它们缝在一起的是 `|`——
于是整条「提示 → 模型 → 解析」变成一个能被 `describe()` 读出形状、能被 `.batch()` 一次跑一批的**链**。

本章的四条主线各配一张读数表：模板的必填与选填、少样本的形态、四种解析做法里**哪一种会失败**、
以及并行的账。最后一条会打破一个常见期待——**并行省的是墙钟，不是钱**。

## 学习目标

读完本章，你应该能够：

1. 说清 `ChatPromptTemplate` 的必填变量与选填变量分别是什么，以及**哪一个默认是选填的**；
2. 用 `MessagesPlaceholder` 承载历史，并解释为什么把历史拼进字符串会丢掉一个可查的事实；
3. 写出少样本提示，并说清「示例是消息」与「示例是一段散文」在模型侧的区别；
4. 分辨四种拿到结构化输出的做法（纯文本＋解析器 / `JsonOutputParser` / `with_structured_output` /
   `include_raw=True`），并说出各自的失败模式；
5. 读懂一条 LCEL 链的输入、输出与步数，并用 `.batch()` 与 `RunnableParallel` 组合出更宽的链；
6. 说清「链不替你做哪四件事」，并为其中两条给出可执行的补救（回调记账、`include_raw` 进指标）。

## 前置知识

- 第 4.1 节的消息与裁剪：本章的提示模板产出的正是那一节的消息列表；
- 第 3.2 节的提示契约（`app/llm/schemas.py`）：本章的 `ArticleSummary` 与它**是同一份契约**；
- 第 3.9 节的失败分档与观测：4.2.5 的 `include_raw` 是它在线上的落点；
- 第 3.1 节的上下文预算：4.2.3 的裁剪不是优化，是预算。

## 4.2.1 提示从文件变成对象

先看两份提示。v3 的是一份纯文本文件：

```text
你是知舟博客的编辑助手。把用户给出的文章正文压成三句话以内的摘要。

要求：
1. 摘要只陈述正文里写过的事实，不要补充正文之外的背景，不要给建议。
2. tags 只能从清单里选，最多三个：后端、前端、数据库、AI、运维。
3. 按正文实际内容选标签；正文只讲一件事时，给一个标签也是正确结果，不要凑数。
4. 输出使用简体中文。
```

v4 的提示是一个 `ChatPromptTemplate`：

```python
# app/prompts.py —— 摘要链的提示：系统消息（规则）＋ 用户消息（数据）（节选）
SUMMARY_PROMPT = ChatPromptTemplate.from_messages([
    ("system", SUMMARY_SYSTEM),
    ("human", "正文：\n{article}"),
])
```

两者看着差不多，差别在**提示多了一个可以被问的接口**。同一个提示，`format_messages()` 能列出它渲
染出来的消息（一条系统消息 ＋ 一条用户消息），`input_variables` 能列出它需要哪些变量。
再往前一步：v3 的第 2 条规则（「最多三个」）只对模型有效，**对自己无效**——
回来之后 `validate()` 用的是 schema 里的 `max_length=3`，两者是两处手写。

v4 把这条规则收进契约里，一物三用：

```python
# app/schemas.py —— 一份契约，三个身份：schema / 给模型的说明 / 回来后的校验（节选）
class ArticleSummary(BaseModel):
    """摘要与标签：把一篇文章压成两句话与不超过三个标签。

    两个字段都带 `description`，因为**模型看到的就是它们**：
    v3 把「最多三个」写在提示文件的第 2 条规则里，v4 写在 `Field` 里——
    而 `Field` 的这一份是**同时**给模型的（进 schema）和给自己的（回来校验）。
    """

    summary: str = Field(max_length=120, description="三句话以内的摘要，只陈述正文写过的事实。")
    tags: list[Tag] = Field(max_length=3, description="从清单里选，按正文实际内容选，不要凑数。")
```

**这一节真正省掉的是「同一件事写两遍」**——不是省掉提示，也不是省掉校验。

## 4.2.2 模板知道什么：一个必填，一个选填

三个提示各问一遍「你需要什么」，读数如下：

```console
$ python scripts/prompt_chain.py --offline
① 模板知道什么
  摘要：必填 ['article']｜选填 []
  多轮：必填 ['question']｜选填 ['history']
  少样本：必填 ['request']｜选填 []
  少样本的变量里没有 input/output——**示例是数据，进模板时就固定了**。
  缺必填变量 → KeyError 'article'（**渲染时就抛**，不用等模型答非所问）
  缺选填变量 → 不报错，历史位置安静地空着，渲染出 2 条：['System', 'Human']
```

三行读数各有一条结论。

**第一，缺必填变量在渲染时就抛，而且抛的是 `KeyError`。**
这比「模型答非所问」好得多：错在调用方，不在模型。多轮提示的那一行代码是这样的：

```python
# app/prompts.py —— 历史占的是一个位置，装的是**一个消息列表**（节选）
CHAT_PROMPT = ChatPromptTemplate.from_messages([
    ("system", "你是知舟的技术助手。回答控制在两句话内，不要客套。"),
    ("placeholder", "{history}"),
    ("human", "{question}"),
])
```

**第二，`MessagesPlaceholder` 装进来的是一个位置，不是一个字符串。** 区别在读数里：
传 `history=[HumanMessage(...), AIMessage(...)]` 时渲染出 4 条消息；v3 那种把历史拼进字符串的写法，
渲染出的永远是 2 条——**「历史里有几条」这件事在模板层面不可知**。

**第三，也是这一节最该记住的：历史是选填的。** 上面那一行的 `history` 落在
`optional_variables` 里，不在 `input_variables` 里——所以**忘了传不会报错**，
只会安静地把上下文丢掉。这是框架里最典型的「默认行为帮了你、也埋了你」：

| 变量类别 | 缺了会怎样 | 谁落在这一类 |
| --- | --- | --- |
| 必填（`input_variables`） | 渲染时抛 `KeyError` | `article`、`question`、`request` |
| 选填（`optional_variables`） | **静默变成空** | **`history`** |

所以 v3 与 v4 给这条都留了一个可查的读数：v3 在装配账里报「历史 0 条」，
v4 在 4.1 的 `ChatHistory` 里报「丢弃 N 条」。**模板不会替你把这件事说出来，你得自己数。**

## 4.2.3 少样本：示例是消息，不是散文

那份教程 §4.3 教的写法是把示例拼进一段文本里：

```text
("human", "示例：\n情绪: 开心\n表达: 我今天非常开心！\n\n情绪: 难过\n表达: 我感到有些难过...")
```

框架版的写法是把示例做成**成对的消息**：

```python
# app/prompts.py —— 每一例是一对消息，不是一段散文（节选）
_EXAMPLES = [
    {"input": "给文章 12 打标签", "output": '{"tool": "get_tags", "args": {"article_id": 12}}'},
    {"input": "文章 7 的第一段是什么", "output": '{"tool": "read_article", "args": {"article_id": 7}}'},
]
_EXAMPLE_PROMPT = ChatPromptTemplate.from_messages([
    ("human", "{input}"),
    ("ai", "{output}"),
])
_FEW_SHOT = FewShotChatMessagePromptTemplate(example_prompt=_EXAMPLE_PROMPT, examples=_EXAMPLES)

# 起草草稿的提示：少样本 ＋ 真实任务。素材 §4.3 想教的正是这件事，只是写成了字符串。
# `_FEW_SHOT` 本身就是一个消息模板，所以它**整体**占列表里的一个位置。
DRAFT_PROMPT = ChatPromptTemplate.from_messages([
    ("system", "你是知舟的编辑。把工具调用写成 JSON，字段只有 tool 与 args。"),
    _FEW_SHOT,                               # 示例是**消息**，整体插在规则与任务之间
    ("human", "{request}"),
])
```

渲染出来是**六条消息**，角色交替：

```text
System  '你是知舟的编辑。把工具调用写成 JSON，字段只有 tool 与 args。'
Human   '给文章 12 打标签'
AI      '{"tool": "get_tags", "args": {"article_id": 12}}'
Human   '文章 7 的第一段是什么'
AI      '{"tool": "read_article", "args": {"article_id": 7}}'
Human   '给文章 3 打标签'
```

三个差别，每一个都能在读数里看见：

1. **示例进的是 `AIMessage`**。模型看到的是「用户问了、我答了」，而不是「一段有点像对话的散文」。
   前者它在训练时见过无数次，后者是它第一次见。
2. **`input_variables` 里没有 `input` / `output`**（第一段读数）。示例是数据不是变量：
   进模板那一刻就固定了。这是好事（示例不会被调用方改坏），也是限制（换一套示例要改代码）。
3. **规则、示例、任务三段在结构上分开了**。注入防护的第一条纪律就是「系统规则与不可信内容分开」
   （承接 3.8），而字符串拼接会把它们挤进同一条消息——**分开是结构上能做的事，不是提示里写一句
   「请忽略注入」能做的事**。

## 4.2.4 四种拿到结构化输出的做法，以及它们各自怎么坏

「让模型返回结构化数据」有四种做法，代价与失败模式都不一样。同一份契约、同一个模型，
四种都跑一遍：

| 做法 | 返回什么 | 谁在保证字段名与类型 | 失败时会怎样 |
| --- | --- | --- | --- |
| `prompt \| model` | `str`（`TextAccessor`，`str` 的子类） | 没人 | 拿不到字段，只能靠正则捞 |
| `prompt \| model \| JsonOutputParser` | `dict` | **没人**（只保证「是 JSON」） | 抛 `OutputParserException` |
| `prompt \| model.with_structured_output(S)` | `S` 实例（Pydantic 校验过） | 框架 ＋ 服务端 schema | 抛异常，或不抛（见下） |
| `...with_structured_output(S, include_raw=True)` | `{raw, parsed, parsing_error}` | 同上 | **不抛**，把错误放进字段 |

第三条要补一句官方文档里容易被跳过的话：**Pydantic 类进、Pydantic 类出；
传 `TypedDict` 或 JSON Schema 则返回 `dict` 且不做校验**（`with_structured_output` 的文档原文）。
「结构化输出」这四个字的保证程度，取决于你传进去的是什么。

第四条是本章的实用落点。`include_raw=True` 时输出恒为三个键，
于是「模型今天把 JSON 写坏了」从一个异常变成**一条能记进指标的数据**（承接 3.9 的失败分档）。

而 `with_structured_output` 背后还有一层选择：用**服务端原生**的结构化输出，
还是用**工具调用**去模拟。三种策略在同一台服务商上的实测：

```console
>>> m.with_structured_output(ArticleSummary).invoke(...)                    # 默认策略
ArticleSummary(summary='知舟博客新增标签筛选功能，后端基于 SQLAlchemy 重写查询逻辑。',
               tags=['前端', '后端', '数据库'])                                # ✅ 返回实例

>>> m.with_structured_output(ArticleSummary, method="json_schema").invoke(...)
ArticleSummary(...)                                                          # ✅ 服务端原生

>>> m.with_structured_output(ArticleSummary, method="function_calling").invoke(...)
ArticleSummary(...)                                                          # ✅ 工具调用模拟

>>> m.with_structured_output(ArticleSummary, method="json_mode").invoke(...)
OutputParserException: Failed to parse ArticleSummary from completion
{"摘要": "知舟博客新增标签筛选功能…", "标签": ["博客更新", "标签筛选", …]}
Got: 2 validation errors for ArticleSummary
```

**最后一条是这一节最值钱的读数**：`json_mode` 只向服务端要「合法 JSON」，
**不要「你要的那几个字段名」**。于是模型给出了一份完全合法、也完全用不了的 JSON——
键名换成了中文，标签从一个换成四个。前三种做法在**同一句提示、同一个模型**上全部通过，
差别不在提示写得好不好，而在**要不要把 schema 交给服务端**。

## 4.2.5 两种失败，两种处置

把上面那张表的最后两行分开看：

```console
$ python scripts/prompt_chain.py --offline
④ 解析失败怎么办
  JsonOutputParser 好输入 → dict {'tool': 'get_tags', 'args': {'article_id': 12}}
  JsonOutputParser 坏输入 → OutputParserException（**异常**，进不了指标）
```

一个异常意味着两件事：**这一条运行的结论丢了**（调用方要知道的是「模型没按格式答」，
而它拿到的是一个堆栈），以及**它进不了失败分布**（3.9 的六档里没有「解析失败」这一档，
因为它根本没走到记账那一步）。

`include_raw=True` 把同一件事变成三个字段：

```python
# app/chains.py —— 解析失败要能进指标，落点就在这里（节选）
def tool_call_chain(model, *, include_raw: bool = False) -> Runnable:
    """工具调用 ＋ 可选保留原文：这是「解析失败要能进指标」的落点。

    官方文档里最容易被跳过的一页：`with_structured_output(..., include_raw=True)` 时，
    输出恒为 `{'raw': BaseMessage, 'parsed': ... | None, 'parsing_error': BaseException | None}`。
    于是「模型今天把 JSON 写坏了」从一个异常变成一条**可以记进指标的数据**（承接 3.9 的失败分档）。
    """
    return DRAFT_PROMPT | model.with_structured_output(ToolAction, include_raw=include_raw)
```

`describe()` 能读出这个差别，不用去读文档：

| 链 | 输出字段 |
| --- | --- |
| `draft_chain` | `{root}` |
| `tool_call_chain(..., include_raw=True)` | `{parsed, parsing_error, raw, root}` |

**判据**：凡是「模型可能不按格式答」且这件事要进账的地方，用 `include_raw=True`；
凡是「格式错了就该立刻停下」的地方（比如离线夹具），用会抛的那种。
两种都对，**错的是不分场合地只用一种**。

## 4.2.6 LCEL：链是对象，所以它有形状

`|` 组合出来的东西是 `Runnable`，于是它的输入输出**是带类型的**。`describe()` 把它读出来：

```python
# app/chains.py —— 输入要什么、输出是什么、中间几步（节选）
    graph = chain.get_graph()
    return {
        "输入": _schema_name(chain.input_schema),
        "输出": _schema_name(chain.output_schema),
        "步数": len(graph.nodes),
        "节点": sorted(graph.nodes),
    }
```

七条链的形状：

```console
② 链的形状（读出来的，不是试出来的）
  用的是一个**不联网**的模型对象：建链只拼结构，不发请求。
  纯文本摘要     输入 {article}            输出 {root}                          5 步
  结构化摘要     输入 {article}            输出 {summary, tags}                5 步
  裁剪＋摘要     输入 {root}               输出 {root}                          6 步
  工具 JSON      输入 {request}            输出 {root}                          5 步
  JSON＋原文     输入 {request}            输出 {parsed, parsing_error, raw, root} 5 步
  并行两条       输入 {article, request}   输出 {draft, summary}                8 步
  带上入参       输入 {article}            输出 {article, result}               6 步
  节点名长这样：1c069d240de5…——**随机 id，不是可读的步骤名**。
```

四件能从这张表里直接读出来的事：

1. **输入由链的第一环决定。** `summary_chain` 要 `{article}`，`clipped_chain` 要一个裸字符串——
   因为它的第一环是 `CLIP`。把同一把提示挪到裁剪后面，接口就变了。
   `describe()` 会告诉你，别靠记。
2. **`{root}` 就是「一个裸字符串」。** 输出 schema 会对没有字段名的东西包一层单字段模型，
   `StrOutputParser` 的输出就落在这一格里。
3. **`include_raw=True` 多出的正是那三个字段**（上一节）。
4. **节点是随机 id。** 所以 `get_graph()` 能回答「有几个节点」，
   **不能回答「是哪一步坏了」**——那要靠 3.9 的追踪层给每一步起名。

「链是对象」还带来两个不需要额外代码的能力：

```console
>>> draft_chain(model).batch([{"request": "a"}, {"request": "b"}])
[{'tool': 'get_tags', 'args': {'article_id': 12}}, {'tool': 'get_tags', 'args': {'article_id': 12}}]
```

`.batch()` 与 `.invoke()` 用的是同一条链——**不需要为「一次跑一批」写第二份代码**，
它们是同一个接口族。这是 `|` 与「自己写一个 `summarize()` 函数」最实际的区别。

而组合更宽的链也不需要新概念：

```python
# app/chains.py —— 两条链各自独立，再组合成一条更宽的（节选）
def parallel_chain(model) -> Runnable:
    """两条独立验收过的链并行跑：`RunnableParallel` 的值是两条链，入参是同一份。

    它证明的是「链是对象」的后半句：两条链可以**各自独立存在**，再组合成一条更宽的链，
    而组合本身不要求它们知道对方存在。代价是一片论文级的账——一次并行就是两次调用，
    见 4.2.6 的读数。
    """
    return RunnableParallel(summary=structured_chain(model), draft=draft_chain(model))
```

### 并行的账：省的是墙钟，不是钱

真机跑一遍，四条链各自的读数如下（agnes-2.5-flash）：

| 链 | 返回类型 | 输入词元 | 输出词元 | 合计 |
| --- | --- | ---: | ---: | ---: |
| 纯文本摘要 | `TextAccessor`（`str` 子类） | 221 | 66 | 287 |
| 结构化摘要 | `ArticleSummary`（107 字，`tags=['后端']`） | 221 | 84 | 305 |
| 工具 JSON ＋ 原文 | `parsed=ToolAction(...)`，`parsing_error=None` | 144 | 21 | 165 |
| 并行两条 | 一条链，两个键 | **365** | 105 | **470** |

**读第三行与第四行：365 ＝ 221 ＋ 144。** 并行那一条的输入词元**正好等于**两条链分别跑的总和——
因为并行只是把两次调用**同时**发出去，钱一分没省。它是延迟优化，不是成本优化。

第二行与第一行的差也值得看：输入一样（221），输出多了 18 个词元（84 vs 66）——
多出来的正是 schema 那一段。**结构化输出的代价是输出端的词元，不是输入端的。**

真机那一轮还顺手抓到一条：模型返回的工具名是 `tag_article`，
而示例里教的是 `get_tags`——**校验通过了**，因为 `tool: str` 上没有枚举约束。
这是本章最后一条结论的实证：**schema 保证字段名与类型，保证不了语义**。

## 4.2.7 这条链不替你做什么

四条都写在实现里，逐条对得上读数：

| 不替你做的事 | 读数（上面哪一处） | 补救在哪 |
| --- | --- | --- |
| 不限流、不把重试做成有界 | 4.1 的 `describe_defaults`：不传 `timeout` 时实际生效 600 秒 | 模型出口（4.1 的 `build_model`） |
| 不记账 | `StrOutputParser` 的输出是 `str`，用量已经在输入里丢掉 | **回调**（下面的 `TokenTally`） |
| 不告诉你是哪一步坏了 | 节点名是随机 id，异常类型只分得出「模型」与「解析」 | 3.9 的追踪层 |
| 不保证字段的语义 | `tag_article` 通过了 `tool: str` 的校验 | 契约里加约束（`Literal` / 枚举） |

第二条值得给出可执行的写法，因为它最容易被当成「框架的锅」：

```python
# scripts/prompt_chain.py —— 链不记账，但回调能（节选）
class TokenTally(BaseCallbackHandler):
    """把「链跑了多少次、花了多少词元」记在外面。

    这是本节的一个结论的可执行版本：**链不替你记账**——`StrOutputParser` 的输出是一个
    `str`，用量信息在它的输入里，已经被丢掉了。但回调能看见每一次调用，
    所以账可以记在链的**外面**（承接 3.9 的追踪层：观测是旁路）。
    """

    def __init__(self) -> None:
        self.calls = 0
        self.input_tokens = 0
        self.output_tokens = 0
```

调用时挂在配置上：`chain.invoke(payload, config={"callbacks": [tally]})`。
于是上面那张真机表里的每一个数，都是这么量出来的——
**链没给你账，但也没挡着你记账**，这两句话要一起说。

## 4.2.8 知舟接线

### 加了什么

4.2 往 `zhizhou-v4/` 里加了三个模块与两份测试，它们顶掉的是 v3 的提示那一份 Markdown 与手写校验：

| 文件 | 行数 | 顶替 v3 的哪一块 |
| --- | ---: | --- |
| `app/prompts.py` | 88 | `app/llm/prompts/article_summary.md` ＋ 手拼的 `render()` |
| `app/schemas.py` | 56 | `app/llm/schemas.py` 的 `json_schema_strict()` 与 `validate()` |
| `app/chains.py` | 147 | `app/services/` 里那些「拼提示 → 调模型 → 解析」的手写函数 |
| `scripts/prompt_chain.py` | 221 | 无对应（v3 用 `demo.py` 的一条路径代替） |
| `tests/test_prompt_chain.py` | 170 | 无对应（v3 的同类测试散在 `tests/test_wiring.py`） |

**契约没变的地方要说清楚**：`ArticleSummary` 的字段名、`Tag` 清单、四条提示规则，
与 v3 逐条一致。换框架不换契约，否则第 4 篇的对照就失去了基准。

### 接口契约

| 契约 | 内容 |
| --- | --- |
| 一份契约只写一遍 | 字段名、类型、上限、给模型的说明都写在 `app/schemas.py` 的 `BaseModel` 里；不在提示里再抄一遍 |
| 规则与数据分开 | 系统消息只放规则，用户消息只放数据；历史走 `MessagesPlaceholder`，不拼字符串 |
| 必填变量要显式 | 模板的 `input_variables` 是调用方的契约；**选填的那一个（`history`）必须由调用方负责传** |
| 失败要能进账 | 凡是「模型可能不按格式答」且要进指标的链，用 `include_raw=True` |
| 账在链外 | 记账靠回调（`TokenTally`），不靠链的返回值；链的输出不带用量 |
| 模型出口不许绕过 | 所有链的模型参数都从 `app/llm.py::build_model()` 来（4.1 的硬约定） |

### 怎么验

```bash
cd zhizhou-v4
python scripts/prompt_chain.py --offline   # 不需要密钥：模板、形状、裁剪、解析；**这一路是门**
set -a && . ../zhizhou-v3/.env && set +a
python scripts/prompt_chain.py             # 真机：四条链的词元读数，不当门
python ../tools/check_runnable.py          # 正文里每段节选都要能在树里逐行找到
```

四条判据：

1. **离线那一句** `✔ 离线自检通过` 必须出现，且第①段打出
   `多轮：必填 ['question']｜选填 ['history']`；
2. **缺必填变量要抛**：`缺必填变量 → KeyError 'article'`；
3. **解析失败要分得开**：坏输入报 `OutputParserException`，而 `include_raw=True` 那一支
   在输出 schema 里给出 `{parsed, parsing_error, raw, root}`；
4. **一致性**：本章带路径标注的每一个代码块，都要能在 `zhizhou-v4/` 里逐行对齐（由 `check_runnable.py` 守）。

### 不能破坏什么

- **不许把 `ArticleSummary` 的字段改名**：v3 的 `validate()` 与本章的链共用它，
  改名会让第 4 篇的对照失去基准（契约见 [`PROJECT.md`](PROJECT.md)）；
- **不许把 `history` 改成必填**：`MessagesPlaceholder` 的选填是**框架行为**，
  改成必填需要自己包一层；如果做了，必须在 4.6 的清单里登记，否则所有旧调用会一起报错；
- **不许在 `app/prompts.py` 里出现模型对象**：提示只描述输入，不拥有模型（否则离线测不了模板）；
- **不许把 `include_raw` 的返回值直接当数据用**：它是三个字段的**诊断包**，
  业务代码必须显式判 `parsing_error`；
- **不许用 `json_mode` 拿固定字段**：4.2.4 的读数就是它的失败方式（键名不受约束）。

## 常见坑

- **必填与选填分不清**：`input_variables` 缺了会抛，`optional_variables` 缺了会静默丢内容。
  **历史恰好是选填的**，所以最该数的一个数没人替你数。
- **用字符串拼历史**：`「历史：…」` 这种写法在看板上与「一条用户消息」长得一样，
  但在模型侧不是一回事（前者是数据里的文本，后者是对话结构）。
- **少样本示例写成一段散文**：模型见到的不是「一问一答」，而是一段看起来像对话的说明文字。
- **以为 `json_mode` 保证字段名**：它只保证「合法 JSON」。实测同一句提示下它返回了中文键名，
  而 `json_schema` / `function_calling` / 默认策略全部通过。
- **拿 `with_structured_output` 的输出当「一定对」**：它保证字段名与类型，
  **不保证语义**（实测：模型返回了一个示例里没有的工具名，校验照样通过）。
- **在链上找用量**：`StrOutputParser` 的输出是 `str`。用量要靠回调，
  或者用 `include_raw=True` 把原始消息留下来。
- **以为并行省钱**：实测并行那一条的输入词元正好等于两次串行之和（365 ＝ 221 ＋ 144）。
  并行买的是墙钟。
- **拿 `get_graph().nodes` 当步骤名**：它们是随机 id。要可读的步骤名，得自己做命名（3.9 的追踪层）。

## 面试视角

「你用过 LangChain 的提示模板吗」这句话背后的考点，通常分四层：

1. **第一层：知道它是个对象。** 答「它自己知道需要哪些变量，缺必填会在渲染时抛 `KeyError`；
   历史走 `MessagesPlaceholder`，而且它在 `optional_variables` 里——**不传不报错**」。
   最后一小句是这一层里唯一能拉开差距的。
2. **第二层：知道结构化输出有几种做法。** 能说出「纯文本＋解析器 / `JsonOutputParser` /
   `with_structured_output` / `include_raw=True` 四种，失败模式各不相同」，
   并且能解释 `json_mode` 为什么不可靠（**它只要合法 JSON，不要字段名**）。
3. **第三层：知道链的边界。** 「链是对象，所以有 `input_schema` / `output_schema` 可读、
   有 `.batch()` 可用；但**它不记账、不命名步骤、不替你限流**。」
   面试官往往会追问「那你怎么记账」——答回调，并把 `input/output` 分开（承接 3.9 的 96.6% 输入占比）。
4. **第四层：知道校验不等于语义。** 举出自己踩过的例子（「模型换了个工具名，schema 照样放行」），
   并说明你会怎么补（`Literal` / 枚举 / 白名单校验，
   以及 3.8 那条「结构性控制不依赖概率」）。

一个常被追问的收尾：「那你还手写 v3 那一版干什么？」回答落在**对照**上：
手写一遍才知道 `validate()` 与 `json_schema_strict()` 是自己写的，
而 `Field(max_length=120)` 同时喂了两头——**知道省掉的是什么，才知道它什么时候不够用。**

## 本章小结

1. **提示是对象，不是字符串**：`ChatPromptTemplate` 能报出需要哪些变量，也能被独立于模型测试。
2. **必填与选填要分清**：`input_variables` 缺了在渲染时抛 `KeyError`；
   `optional_variables` 缺了**静默变空**——而 `history` 正好落在选填那一类。
3. **`MessagesPlaceholder` 装的是消息列表**，不是一段拼接文本；「历史里有几条」因此可查。
4. **少样本示例是成对的消息**，不是一段散文；示例是数据，所以它不出现在 `input_variables` 里。
5. **一份契约只写一遍**：`BaseModel` 同时是 schema、给模型的说明、回来后的校验器；
   v3 这三件事是三处手写。
6. **结构化输出有四种做法**，保证程度递减：`with_structured_output`（Pydantic 类，校验过）→
   `include_raw=True`（三个字段，不抛）→ `JsonOutputParser`（只保证是 JSON）→ 裸文本。
7. **`json_mode` 不保证字段名**：同一句提示下它返回了中文键名与四个标签，
   而 `json_schema` / `function_calling` / 默认策略全部通过。
8. **解析失败有两种处置**：会抛（离线夹具、立刻停下）与三字段（进指标、可统计）。
   错的是不分场合只用一种。
9. **链是对象**：`describe()` 读得出输入、输出与步数；`.batch()` 不需要第二份代码；
   `RunnableParallel` 把两条独立验收过的链组合成更宽的一条。
10. **并行省的是墙钟，不是钱**：实测输入词元 365 ＝ 221 ＋ 144。
    结构化输出多花的是**输出端**（84 vs 66），输入端一样。
11. **链不替你做四件事**：不限流、不记账、不命名步骤、不保证语义。四条各有一个补救。
12. **校验不等于语义**：模型返回了示例里没有的工具名，`tool: str` 照样放行。

## 练习

- **基础**：给 `app/prompts.py` 加一把「起草草稿」的提示，要求：
  1）规则走系统消息；2）带两条少样本示例；3）必填变量只有一个 `request`；
  4）写一条测试证明它的 `input_variables == ["request"]`、渲染出 6 条消息、角色序列正确。
- **进阶**：把 `tool_call_chain` 的 `ToolAction.tool` 从 `str` 收成
  `Literal["get_tags", "read_article", "create_draft", "publish_article"]`，
  重跑真机那一轮并回答两个问题：**约束收紧之后，模型还会不会给出 `tag_article`？
  如果它改成了返回一个不存在的工具名，你现在看到的是一次解析失败，还是一次校验失败？**
  两种失败在 3.9 的失败分布里该归到哪一档？
- **挑战**：给本章的链加一个**成本护栏**（不改链本身的结构）：
  用回调在每一次 `on_llm_end` 之后累计输入词元，超过阈值时抛一个自定义异常，
  让这条链**立刻停下**而不是跑完。要求：1）阈值来自配置；2）异常里带上
  「本次调用链的哪一步、已用多少」这两条信息（提示：用 `on_chain_start` 拿到步骤名，
  这正是 4.2.6 说的「框架不命名，你得自己命名」）；3）写一条测试证明它
  **在阈值内不误停**——反向守比正例重要（承接 3.10）。
