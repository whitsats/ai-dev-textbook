# 4.4 LangGraph：StateGraph 与状态编排

## 本章导读

4.3 的结尾留了一个问题：`create_agent` 一行装配就把循环、工具节点、路由、消息归并全做完了——
**那张图是谁装的？** 这一章自己装一张，并且装的是知舟真正的那条流水线：
正文进来，先出摘要，再起草，草稿不够好就再来一轮，够了就停在「发布」上等人点头。

这就是状态编排（state orchestration）：**一次请求要走几步、每步看什么、下一步去哪，
是显式写出来的，而不是藏在函数调用栈里**。v3 里它是 `orchestrator.py` 的一个 `while`
加上 `loop.py` 里的终止条件；v4 里它是四个零件：

| 零件 | 是什么 | 这一章要量的数 |
| --- | --- | --- |
| 状态 | 一份 schema ＋ 每个键各自的归约器 | 覆盖与累加各在什么时候发生 |
| 节点 | 干活的函数，只返回**要改的字段** | 返回一个没声明过的键会怎样 |
| 边 | 普通边与条件边（循环就是条件边指回自己） | 三种边各会怎么错 |
| 编译 | 结构检查 ＋ 挂上检查点 | 上限数的是哪一步、中断需要什么 |

四组读数各有出处，也都可复现：

1. **归约器**：同一个键，写 `Annotated[..., operator.add]` 与不写的差别，
   以及**没写进 schema 的键会被静默丢掉**（不报错、不警告）；
2. **上限**：`recursion_limit` 数的是超级步——线性 3 节点图的最小值是 **4**，
   循环 3 轮的最小值也是 **4**，4.3 量到的「一次模型往返 2 步」由此有了下落；
3. **并行**：同一个超级步里两个节点写同一个没有归约器的键会抛
   `InvalidUpdateError`——「要不要归约器」不是风格问题；
4. **中断**：图停在检查点上等人。不挂检查点时**中断照样发生，而恢复会抛**
   ——这是本章最贵的一次实测。

读完这一章，你应该能回答一个具体问题：**`create_agent` 帮你省掉的那几十行，
每一行原本在做什么？** 答得出来，才算「会用框架」而不是「只会框架」。

## 学习目标

- 能写出一份带归约器的状态 schema，并说清哪些键该累加、哪些该覆盖；
- 能解释「节点只返回要改的字段」在归约器这一层的真实含义；
- 能写出普通边、条件边与循环，并说清路由映射表的键是谁；
- 能把 `recursion_limit` 的数值折算成超级步，并按节点数算出一个安全值；
- 能在并行分支上判断「这里需不需要归约器」，并说清不需要时的合并顺序；
- 能用输入/输出 schema 把内部账目挡在接口之外，并知道流的哪一处挡不住；
- 能用 `interrupt` 把整张图停在检查点上，并说清恢复时节点会重跑哪一部分；
- 能说清本树的流水线为什么两层都要审批（工具层 4.3 ＋ 图层 4.4）。

## 4.4.1 状态：一份 schema，每个键各写各的归约器

先说结论：**状态不是「一个共享变量」，而是一组通道，每个通道自带一个合并函数。**
官方文档把这个函数叫 reducer，本书记作**归约器**——它是二元的，
左参数是通道里已有的值，右参数是节点这一步返回的更新：

```python
new_value = reducer(left=current_state[key], right=node_update[key])
```

不写归约器时用的是默认的那一个，而默认的行为是**丢掉左参数、只留右参数**——
也就是「覆盖」。要让某个键累加，就在类型上挂一个函数：

```python
# scripts/state_graph.py —— 三种合并，一个一个量（节选）
class MergeState(TypedDict):
    overwritten: str                       # 无 reducer → 覆盖
    accumulated: Annotated[list[str], operator.add]   # 有 reducer → 累加
    # `undeclared` 故意**不**声明在这里：4.4.2 要量它回来之后还在不在


def one(s):        # noqa: ANN001
    return {"overwritten": "A", "accumulated": ["A"], "undeclared": "A"}
```

跑一遍（`python scripts/state_graph.py --offline` 的第 ① 组）：

```
覆盖键 overwritten     ：'-' → 'A' → 'B'
累加键 accumulated     ：['start'] → ['start', 'A', 'B']
未声明键 undeclared    ：节点返回了两次，回来之后**没有这个键**
累加键不给初值         ：{'overwritten': 'A', 'accumulated': ['A']}
```

第一行是「最后一次为准」，第二行是「每一份都留」，第四行是一处容易被写进注释当契约的
**推断**：累加键不给初值时不会报错，框架会照着类型提示推一个空表。能跑，但那是它猜的。
**契约要自己写**——本树的 `initial_state()` 就把三个累加键的初值显式写出来：

```python
# app/graph.py —— 一次运行的输入（节选）
def initial_state(article: str, title: str, *, max_rounds: int = MAX_ROUNDS) -> dict:
    return {"article": article, "title": title, "summary": "", "draft": "",
            "approved": False, "revisions": [], "log": [], "rounds": 0,
            "max_rounds": max_rounds}
```

本树的状态里有两个归约器，一共六个键。为什么要分这两类，看第 4.4.4 节那个循环就明白：

```python
# app/graph.py —— 图的内部 schema（节选）
class PipelineState(TypedDict):
    article: str
    title: str
    summary: str
    draft: str
    approved: bool
    revisions: Annotated[list[str], operator.add]
    log: Annotated[list[str], operator.add]
    rounds: Annotated[int, operator.add]
    max_rounds: int
```

`draft` 是覆盖的：读者要的是最新那一稿。`revisions` 是累加的：**每一稿都要留着**,
否则「它改了三次还是没变好」这句话没有任何证据。`log` 与 `rounds` 同理。
`rounds` 用累加还有一个实际理由：节点返回 `{"rounds": 1}` 是「我这一步跑了一次」,
而返回 `{"rounds": state["rounds"] + 1}` 是「我替你要了一个总数」——
前者在并行与重放时都对，后者两种情况下都会算错。

对照 v3：`memory.py` 里 `Message` 是一个 `dataclass`，装配时由函数决定「留下哪几条」；
图里的状态把这件事换成了「每条消息进来就按归约器合并」。**同一个效果，两种责任划分**——
前者是「装配时挑」，后者是「写入时合」。第二种的好处是**并行的分支也能安全地写入同一个键**,
这正是第 4.4.5 节的伏笔。

## 4.4.2 节点返回什么、不返回什么

节点是一个函数，收当前状态，返回一个字典。它**只需要返回要改的键**——
这句话在 4.2 里是「链的输入由第一环决定」，在这里是「更新的范围由返回值决定」。
上表的 `overwritten` 从 `'-'` 走到 `'B'`，`accumulated` 却把三份都留下了：
同一个节点，两种键，两种结果，差别只在 schema 上有没有挂归约器。

不返回的键不会被动，**但返回一个 schema 里没有的键会被静默丢掉**：

```
未声明键 undeclared    ：节点返回了两次，回来之后**没有这个键**（False）
```

这一行里的 `（False）` 是脚本打印的 `'undeclared' in out`。它值得单独讲，
因为「丢掉的键」与「值恰好为空」在返回值里长得一模一样：
`out.get("undeclared")` 是 `None`，`"undeclared" in out` 是 `False`——
而**两者都不会有任何报错**。v3 里这个错会被 `dataclass` 的类型检查挡住一半
（多一个字段会进 `__init__` 报错），框架里的 `TypedDict` 只是类型提示，运行时不查。

本树结结实实踩了这个坑一次，而且**报错指向了别的地方**。第一版把 `max_rounds` 写进
`initial_state()`，却没写进输入 schema：

```python
# app/graph.py —— 输入 schema（节选）
class PipelineInput(TypedDict):
    article: str
    title: str
    max_rounds: int
```

报出来的是 `KeyError: 'max_rounds'`，而栈顶是**条件边的路由函数**：

```
File ".../app/graph.py", line 124, in route_after_review
    if state["rounds"] >= state["max_rounds"]:
KeyError: 'max_rounds'
```

一个「我明明传了」却报在别处的错。它的完整机制是 4.4.7 的输入过滤，
这里先记住两条工程经验：

1. **键在「输入进来的那一刻」就被过滤了**，不是在节点里丢的——
   所以「初值写了就一定有」这句话不成立；
2. **路由函数拿到的状态就是运行时状态**，它不会替你补默认值。
   要么把键写进 schema，要么用 `state.get("max_rounds", MAX_ROUNDS)` 显式兜底。

还有一件更隐蔽的事：返回**整份** state 不会报错，但会让归约器白写。
如果节点返回 `{"accumulated": state["accumulated"] + ["A"]}`，
在只有自己写这个键的时候看起来是对的；一旦并行分支也这么写，
两份「左值 ＋ 新增」会各自基于同一份旧左值，最后被合并成一份——**另一半静默消失**。
所以节点里那条纪律写成一句话是：**节点只描述自己做了什么，不描述总数。**

## 4.4.3 边：普通边、条件边与路由映射表

边只有两种写法，但它们有三种错法，而且三种错的**报错时机**各不相同——
这就是这一节的全部价值：

```python
# app/graph.py —— 装配（节选）
    builder.add_edge(START, "draft")
    builder.add_edge("draft", "review")
    builder.add_conditional_edges("review", route_after_review,
                                  {"draft": "draft", "publish": "publish"})
    builder.add_edge("publish", END)
```

`add_edge` 是「必定走」，`add_conditional_edges(源节点, 决策函数, 映射表)` 是「由函数说了算」。
这里最容易记错的一点是：**映射表的键是决策函数的返回值，不是节点名**。
本树的决策函数返回 `"draft"` 或 `"publish"` 两个字符串，映射表把它们翻成同名的节点——
因为名字恰好一样，所以看上去像没写映射表。把映射表换成 `{"again": "draft", "done": "publish"}`
效果完全相同。

三种错法的实测（第 ③ 组读数）：

```
路由返回映射表里没有的名字 → KeyError 'two'（compile 不报、无警告，而且是运行到那一步才报）
映射表目标名写错 → ValueError：At 'a' node, 'condition' branch found unknown target 'typo_node'
悬空节点 → compile 通过、运行不报错（x=1，孤立那个一次都没跑）
```

三种时机一条条说：

- **路由值漏在映射表外**：编译期不查，运行到那一步才 `KeyError`——
  键是路由函数的返回值。它的危险在于**只有当某个分支被走到时才炸**，
  于是「我测过」的那些输入路径全都通，出事的是那条没测的；
- **映射表里的目标名写错**：这是唯一一种编译期就拦下的——
  `ValueError: ... found unknown target 'typo_node'`。
  官方对 `compile` 的定位正是「做几个基本检查」，这一条属于它会查的「边的两端都要存在」；
- **孤立节点**：官方同一段描述里提到「没有孤立节点」这类检查，本机 1.2.2 上实测**没有拦**——
  编译通过、运行不报错，那个节点一次都不跑。但**它在图上**：
  `get_graph().nodes` 里能看到它。这与 3.10 那张接线状态表是同一条教训：
  **「图上写了它」与「它会跑」是两件事**，模型可用的工具清单、服务端点里挂的中件、
  图里的节点，三处都会有人把前者当后者。

还有一条**顺序**纪律，它不在报错里，只在读数里。本树的路由函数先判质量、再判预算：

```python
# app/graph.py —— 条件边的决策函数（节选）
def route_after_review(state: PipelineState) -> Literal["draft", "publish"]:
    if len(state["draft"]) >= DRAFT_TARGET_CHARS:
        return "publish"
    if state["rounds"] >= state["max_rounds"]:
        return "publish"
    return "draft"
```

两个出口的顺序反过来的话（先判预算），结果是「轮数用尽就发布」——
**一份没通过自评的草稿会被当成通过的稿子发出去**，而这不会抛任何异常。
v3 的 `loop.py` 里也有同一类判断（终止条件写在工具执行之前），
到了图里它是两条 `if` 的先后——**顺序即语义**，测试是唯一能钉住它的东西。

## 4.4.4 循环与上限：把一个上限折算成超级步

循环不需要新语法：**条件边指回自己就是循环**。本树的循环是
`review → draft → review`，终止条件写在路由函数里。

问题在于「跑多少轮算太多」。4.3 量过一次：`create_agent` 的 `recursion_limit`
数的是 super-step，一次模型往返占 2 步。这一次把它拆到最小例子，逐档试出最小值：

```
线性 3 节点图，逐档试出最小值：
  recursion_limit=2 → GraphRecursionError
  recursion_limit=3 → GraphRecursionError
  recursion_limit=4 → 通过（x=3）
循环图 3 轮（同一个节点跑 3 次）：limit=3 → GraphRecursionError｜limit=4 → 通过（n=3）
```

两个最小例子给出同一条折算规则：

> **每一个节点跑一次算一个超级步，再留一步收尾。**
> 线性 3 节点 → 4；同一个节点跑 3 轮 → 也是 4。

「一步收尾」这一步是哪一步，官方文档给的机制可以解释：图执行开始时所有节点都是
`inactive`，收到消息才 `active`；**所有节点都 `inactive` 且没有消息在途时**图才终止。
因此最后一次路由、以及「确认没有新消息」这件事本身要占一步。工程上不必细究，
照上面的公式算一个值即可：

```python
# 一次运行最多几步，按最坏想法数，再乘 2 留余量
limit = 2 * (节点数 + 循环轮数上限) + 2
```

本树的流水线是 4 个节点、最多 2 轮，按公式是 14；脚本里显式给的正是这个量级的数。
**别省掉这一行**：默认值是 9999（4.3 实测），它在纯计算图里等于「没有上限」——
而一个卡在循环里的 Agent，每一轮都在花钱。

循环还有一条比上限更要紧的纪律：**它必须有收敛方向**。本树的每一轮都多摘一段正文，
所以第 2 轮一定比第 1 轮长（171 字 → 331 字），自评才会在有限的轮数内通过。
第 7 组读数里那个「短正文」的例子正好是反面：正文只有 4 字时两轮都不够，
于是它走的是**预算出口**，`log` 里四条记录一条 `pass` 都没有：

```
短正文（4 字）
  log 逐条：draft#1 14 字 → review revise (14 字) → draft#2 14 字 → review revise (14 字)
  rounds=2（= max_rounds）→ 走的是**预算出口**，不是质量出口
```

两条出口都留着、并且**给它们不同的痕迹**，是编排层最实用的一条经验：
出事时要能回答「它是做完了，还是被上限截断了」。v3 的 `loop.py` 用
「终止原因」这一个字段回答同一件事；图里的答案是 `log` 的最后一条。

## 4.4.5 并行：两个节点写同一个键就是错的

把两条边都从同一个节点出发，就得到并行分支。本树的摘要与起草就是并联的
（两条边都从 `START` 出发）：

```python
# app/graph.py —— 并联的摘要与起草（节选）
    if with_summary:
        # 摘要与起草**互不依赖**，所以并联：两条边都从 START 出发。
        # 但 `summary` 与 `draft` 写的是不同的键，因此这里不需要 reducer（4.4.5 的反面）。
        builder.add_edge(START, "summary")
        builder.add_edge("summary", END)
```

两条分支写**不同**的键，所以这里什么都不用额外做。而它们一旦写同一个键，就是硬错误：

```
两节点 fan-out 写同一个**无 reducer** 键 → InvalidUpdateError
  At key 'plain': Can receive only one value per step. Use an Annotated key to handle multiple values.
```

这句话值得整句记住：**「这一步只能收到一个值」**。它的来源是超级步的语义——
同一个超级步里并行跑的节点，各自的更新在超级步结束时一起合并；
合并无归约器的键时框架无法替你在「谁赢」上做决定，于是抛错而不是挑一个。
**换句话说是：并行不是优化选项，它是会改变正确性要求的**。

那给累加键并行写呢？能合，但要小心顺序：

```
只写累加键（第二个节点不碰 plain）：{'plain': 'a', 'joined': ['a', 'b']}——顺序按节点名的字典序，不按边的书写顺序
```

本机 1.2.2 上合并顺序是**节点名的字典序**（`a`、`b`）。这不是文档承诺的顺序，
而是一个实现细节——所以本书给的纪律是：**累加键的合并结果不该被用来推断「谁先跑」**。
要顺序，就把顺序写进图（串行边），而不是写进列表下标。

分支汇合（fan-in）也要说清：两条分支各写自己的键、再一起进同一个节点时，
那个汇合节点会在**下一个超级步**收到两份更新的合并结果：

```
FANIN: {'x': 111}
```

`x` 是累加键（初值 0），两支各写 1 与 10，汇合节点写 100，一次运行拿到 111。
对照 v3：3.7 的编排器用「指纹去重」保证同一篇正文不被两个下游各处理一遍，
图里的对应物是**归约器**——去重逻辑搬进了 `operator.add` 之外的自定义函数里
（本树没用上，因为知舟的摘要与起草本来就吃不同的输入）。

## 4.4.6 流：一次运行吐几帧

运行结果有两种拿法：`invoke` 一次拿全量，`stream` 一帧一帧拿。帧数是可以数出来的，
3 节点线性图跑一遍：

```
stream_mode=values   →  4 帧
stream_mode=updates  →  3 帧
stream_mode=debug    →  6 帧
```

三个数的关系如下：

- `values` 每个超级步一帧**全量快照**，而且**包含初始那一帧**，所以是 3 ＋ 1；
- `updates` 只吐「这一步改了什么」，所以是 3，但它**不含未变的键**——
  想拿全量就得自己累积；
- `debug` 每个节点两帧（任务 ＋ 结果），所以是 6。

工程上的取舍：**给前端的进度条用 `updates`，给日志与回放用 `values`**。
3.9 的追踪层在这一步之上：一个超级步是「图走了一步」，一个`span` 是「一次外部调用」——
两者不是一对一。本树那次真实运行里，摘要子图是一个节点（1 个超级步），
但它内部有一次模型调用（1 个 span）；反过来，4.3 的 Agent 一次模型往返占 2 个超级步，
那个往返里只有 1 次模型调用。**帧数与指标必须分开数**，否则
「今天比昨天多花了 30% 的词元」这句话会被帧数掩盖。

## 4.4.7 输入/输出 schema 与私有通道：什么进来、什么出去

`StateGraph` 的第一个参数是**内部** schema，它还能额外收两个参数：
`input_schema`（允许进来的键）与 `output_schema`（`invoke` 返回的键）。

```python
# app/graph.py —— 装配（节选）
    builder = StateGraph(PipelineState, input_schema=PipelineInput,
                         output_schema=PipelineOutput)
```

三个实测读数：

```
invoke 回来             ：{'shown': '正文!'}
  不在输入 schema 里的初值进不来；不在输出 schema 里的键出不去
stream_mode='values' 的第一帧：{'seed': '正文'}
stream_mode='values' 的最后一帧键：['private_note', 'seed', 'shown']
```

两条过滤规则先记清楚：

1. **输入是一道白名单**。不在 `input_schema` 里的初值，在进图之前就被丢掉了——
   这是 4.4.2 那个 `KeyError` 的完整解释。
2. **输出是一道过滤器，不是补全器**。没被任何节点写过的键**没有这个键**，
   不是 `None` 也不是 `False`。本树那条流水线的第一次 `invoke` 回来只有
   `['__interrupt__', 'draft', 'summary']`——`approved` 不在里面。
   取它会 `KeyError`。**想让它总是有值，就得有一个节点在某个时刻写过它。**

第二条引出本树的一个真实设计选择：`summary`、`draft`、`approved` 三个键构成**接口**,
`log`、`revisions`、`rounds` 三个键构成**内部账**。这条边界不是洁癖，
它对应两个具体好处：

- 调用方只依赖接口，内部账改字段不影响它（3.10 的验收测试正是这么写的）；
- 内部账可以随实现变化（比如把 `revisions` 换成带时间戳的列表），接口不动。

但官方文档有一句必须记住的警告，**私有通道只对 `invoke` 隐身，不对流隐身**：

> 私有通道不会被流式输出隐去。`stream_mode="values"` 默认吐**全部**状态通道，
> 包括私有通道，因为 values 流默认用全量通道而不是输出 schema。

第 ⑥ 组的最后一帧正是这句话：`['private_note', 'seed', 'shown']`——三个键全在。
要真的只吐一部分，得显式给 `output_keys`。也就是说：
**「接口」是给 `invoke` 的定义，不是给所有出口的定义。**
这和第 3 章的一条老结论是同一族的：**默认行为要读出来，不能推**。

## 4.4.8 中断：让整张图停在检查点上等人

4.3 的审批发生在**工具层**（一次工具调用等人点头）。这一章的审批发生在**图层**:
不是「这个动作要不要做」，而是「这条流程要不要往下走」。两种都留着，理由在最后一节。

图层中断只需要一个函数调用：

```python
# app/graph.py —— 发布节点（节选）
def publish_node(state: PipelineState) -> dict:
    answer = interrupt({"ask": "发布这份草稿吗？", "title": state["title"],
                        "chars": len(state["draft"])})
    approved = answer is True
    return {"approved": approved,
            "log": [f"publish {'approved' if approved else 'rejected'}"]}
```

但**它需要两个前提**，少一个都会静默失效：

- 一个检查点（`checkpointer`）：把「停在哪一步」写下来；
- 一个线程 ID：下次从哪条线程接上。

第 7 组把这件事量成了两半，**两半都要记住**：

```
第一次 invoke：键 ['__interrupt__', 'draft', 'summary']｜中断负载 {'ask': ..., 'chars': 331}
恢复后：approved=True｜log 尾条=publish approved
把 checkpointer 去掉：中断照样发生（True）
  恢复 → RuntimeError: Cannot use Command(resume=...) without checkpointer
```

「不挂检查点时中断照样发生」这一半是最容易被误读的：它**不报错**，
`__interrupt__` 也照样出现在返回值里，看上去一切正常——只是你**再也接不回去**了。
换一个线程 ID 也一样：它是新线程、空状态，跑到中断处会**重新算一遍**。
所以「中断能停」和「中断能续」是两件事，验收要分别测（本树两条测试都在）。

第二件事更隐蔽：**恢复时节点从头重跑**。官方文档明写：

> 恢复后，节点会从它被中断的位置重新开始执行，因此 `interrupt` 之前的任何代码都会再跑一遍。

这意味着「在 `interrupt` 之前记一次审计」会在恢复时记两次。本树的 `publish_node`
在中断之前只有一个赋值，正是为了让这条规则没有代价——**这也是一个可以照搬的写法**：
把副作用放在中断之后，或者把它变成幂等的（3.5 的幂等键就是为这种情况准备的）。

第三件事是恢复的输入形态。整个恢复协议只有一个入口：

```python
# app/graph.py —— 恢复的游标（节选）
def new_thread(thread_id: str = "zhizhou-1") -> dict:
    return {"configurable": {"thread_id": thread_id}}
```

`invoke(Command(resume=True), cfg)` 里的那个 `True` 会成为 `interrupt()` 的返回值。
官方文档还有一句容易忽略的限定：**`Command(resume=...)` 是唯一一种可以传给
`invoke` 的 `Command`**，其余的（`update`、`goto`）是给节点返回用的——
拿 `Command(update=...)` 当输入不算恢复，是多开一次运行。

最后一条读数，它决定了「恢复」这个词的边界：

```
跑完之后再 resume → log 不变（它返回旧状态，**不重放**）
```

也就是说线程跑完之后再调用不报错、不重跑、也不返回新东西——**它是空转**。
把「重放」当恢复来用，会得到一份「看起来成功」的假读数。

## 4.4.9 知舟接线

### 加了什么

`zhizhou-v4/app/graph.py`（新文件，约 230 行）＋ `scripts/state_graph.py`（七组读数）
＋ `tests/test_state_graph.py`（20 条离线用例）。这一刻起，知舟的**主流程**
在框架版里是一张图，而不是一串链：

| 4.2 的状态 | 4.4 的状态 |
| --- | --- |
| 摘要是一条链（`SUMMARY_PROMPT \| model`） | 摘要是 `summary_subgraph(model)`，当节点挂进主图 |
| 起草是 `draft_chain` | 起草是 `draft_node`（规则式，见下） |
| 没有「一轮不够就再来一轮」 | `review → draft` 条件边构成循环，上限 2 轮 |
| 没有审批 | `publish_node` 里一次 `interrupt`，等人点头 |
| 返回值就是链的输出 | `invoke` 只回 `summary` / `draft` / `approved` 三个键 |

一处刻意的简化要说明：`draft_node` 是**规则式**的（按轮数多摘一段正文），
没有调模型。原因是这一章验的是**编排**——循环跑几轮、上限怎么折算、中断怎么恢复——
把模型混进来会让每一组读数都带上下不确定性，而 4.3 已经用真机证明过「同一路径跑两遍
的差可能更大」。**先让流程确定性可见，再把模型装进去**，这条顺序在 3.10 也用了一次。

### 接口契约

| 契约 | 形态 | 说明 |
| --- | --- | --- |
| 装配 | `build_pipeline(model, *, checkpointer=None, with_summary=True)` | 返回编译后的图；不给检查点也能跑，但不能恢复 |
| 输入 | `initial_state(article, title, max_rounds=2)` | 与 `PipelineInput` 三个键对齐，多写的会被丢掉 |
| 线程 | `new_thread(thread_id="zhizhou-1")` | 换成别的 ID 就是另一条线程、另一份状态 |
| 输出 | `{"summary", "draft", "approved"}` | 三个键由 `PipelineOutput` 定；**没写过就没有这个键** |
| 中断负载 | `{"ask", "title", "chars"}` | 给前端弹确认框用，字段名由本树定 |
| 恢复 | `invoke(Command(resume=<值>), cfg)` | 值是 `True` 才算同意（`answer is True`） |

### 怎么验

```bash
# 1）七组机制读数 ＋ 流水线两路（不需要密钥，提交门跑这个）
cd zhizhou-v4 && python scripts/state_graph.py --offline

# 2）20 条离线用例（不依赖 pytest）
cd zhizhou-v4 && python tests/test_state_graph.py

# 3）真机：同一张图换成真实服务商，报读数
cd zhizhou-v4 && python scripts/state_graph.py --real
```

第 ③ 条在写这一章时跑过一次（本机 `agnes-2.5-flash`）：

```
第一次 invoke：键 ['__interrupt__', 'draft', 'summary']｜中断 True
内部账：rounds=2｜summary 30 字｜草稿 331 字
log：draft#1 171 字 → review revise (171 字) → draft#2 331 字 → review pass (331 字)
拒发后：approved=False｜log 尾条=publish rejected
```

**离线那一路与真机那一路走的是同一条路径**，差的是摘要那句话由谁写（30 字，
是真模型按 `SUMMARY_SYSTEM` 写的）。这也是把模型放在子图里的好处：
要换策略，换的是那一张子图，主流程一行不动。

### 不能破坏什么

- **不许把 `max_rounds` 从输入 schema 里拿掉**。它是本章那个
  「报错指向别处」的现场；要加默认值就加在 schema 的键上，别指望节点兜底。
- **不许在 `interrupt` 之前加副作用**（写日志、扣配额、发通知）。恢复时整段重跑。
- **不许依赖并行分支的合并顺序**。字典序是实现细节，不是契约。
- **不许把 `approved` 当布尔用**。没写过它就是没有这个键；
  要判真假请用 `.get("approved")`，并在契约里写清「没写过 ＝ 没批」。
- **不许把两条出口合成一条**（质量与预算合并成一个 `return "publish"`）。
  合并之后，「被上限截断」这件事在读数里就消失了。
- **不许把 4.3 的工具层审批换成图层审批**。两者管的不是一件事，见下。

## 常见坑

- **把「状态」当成一个共享变量**：它是一组通道，每个通道各有一个归约器。
- **以为不写归约器就是「保留旧值」**：默认行为是覆盖（丢左参数）。
- **以为累加键必须给初值**：不给不会报错，框架按类型提示推一个空值——
  但那是推断，不是契约。
- **节点返回整份 state**：不报错，但并行时会让归约器的另一半静默消失。
- **以为返回一个没声明的键会报错**：静默丢弃，且与「值恰好为空」无法区分。
- **把 `input_schema` 当成「建议」**：不在里面的初值进不来。
- **以为输出 schema 会补默认值**：没写过的键不在返回值里，取它会 `KeyError`。
- **以为私有通道对流也隐身**：`stream_mode="values"` 默认吐全部通道。
- **把路由映射表的键当成节点名**：键是路由函数的返回值；写错目标名编译期就报 `ValueError`，
  漏一个返回值要运行到那一步才 `KeyError`。
- **以为 `compile` 会拦孤立节点**：1.2.2 实测不拦，它只是永远不跑。
- **把 `recursion_limit` 当「轮数上限」**：它数超级步，按「节点数 ＋ 轮数」折算再留余量；
  默认 9999。
- **循环没有收敛方向**：只在「预算用尽」时退出，等于每一轮都在花钱还拿不到更好的稿。
- **并行两个节点写同一个无归约器的键**：`InvalidUpdateError`，这是硬错误不是警告。
- **以为中断需要检查点才能发生**：不挂检查点也照样停，只是**再也续不上**——
  而恢复时才抛 `RuntimeError`，不是中断时。
- **在 `interrupt` 之前写副作用**：恢复会重跑整段节点。
- **把跑完的线程再 resume 当成重放**：它返回旧状态，什么都不做。

## 面试视角

「你用过 LangGraph 吗」这个问题，通常也分四层：

1. **第一层：知道图的三件事。** 「状态是 schema ＋ 每键一个归约器，
   节点只返回要改的字段，边分普通边与条件边；循环是条件边指回自己」。
   再补一句「`compile` 是必须的一步：它做结构检查并挂上检查点」——
   这两句能立刻把「看过文档」与「跑过」分开。
2. **第二层：知道上限数什么。** 「`recursion_limit` 数的是超级步，
   按『每个节点一次 ＋ 一步收尾』折算；默认 9999，约等于没有上限」。
   再举 4.3 的折算：「`create_agent` 的图是模型与工具两个节点来回，所以一次往返 2 步」——
   这句话的杀伤力在于它把两个抽象（框架的 Agent 与底层的图）接成了一条算式。
3. **第三层：知道什么时候非用归约器不可。** 「并行分支写同一个键必须挂归约器，
   否则 `InvalidUpdateError`；合并顺序是节点名字典序，但它是实现细节，
   要顺序就写进边而不是靠合并」。再加上「节点只描述自己做了什么」这一句。
4. **第四层：知道中断的两半。** 「中断需要检查点与线程 ID；不挂检查点也会停下来，
   但恢复会抛；恢复时节点从头重跑，所以副作用要放在中断之后或者做成幂等的」。
   最后补一条边界：「跑完之后再 resume 是空转，不是重放」。

一个常见的追问是「那你为什么不直接用 `create_agent`？」回答落在**两层审批**上：
4.3 的审批管的是**一次工具调用**（要不要执行这个动作），4.4 的审批管的是**一条流程**
（这份稿子要不要进入下一个状态）。前者是调用层的护栏，后者是业务状态机的闸门——
把两者合并，要么让工具层知道流程语义（耦合），要么让流程层看不见单次动作的细节（失控）。
**能说清这两层的分工，比能写出一张图更能说明你真的用过。**

## 本章小结

1. **状态是一组通道，每个通道自带归约器**：不写就是覆盖（丢左参数），
   写 `Annotated[..., operator.add]` 才是累加。
2. **节点只描述自己做了什么**：返回 `{"rounds": 1}` 让归约器去加，
   返回 `state["rounds"] + 1` 在并行与重放时都会算错。
3. **没写进 schema 的键会被静默丢掉**：不报错、不警告，
   且与「值恰好为空」在返回值里长得一样。
4. **输入 schema 是一道白名单**：初值也在被过滤之列——本树的 `max_rounds`
   就是这么丢的，报错还指向条件边的路由函数。
5. **输出 schema 只过滤、不补全**：没写过的键没有这个键，取它会 `KeyError`。
6. **三种边错法，三种时机**：路由值漏在映射表外 → 运行期 `KeyError`；
   目标名写错 → 编译期 `ValueError`；孤立节点 → 一路静默，只是永不执行。
7. **上限按超级步折算**：线性 3 节点图最小 4，循环 3 轮最小 4——
   每个节点一次，再留一步收尾；默认 9999。
8. **循环必须有收敛方向**，并且**两条出口要留下不同的痕迹**：
   本树的 `log` 最后一条区分「质量通过」与「预算用尽」。
9. **并行写同一个无归约器的键是硬错误**（`InvalidUpdateError`）；
   挂归约器后合并顺序按节点名字典序，但**不要依赖它**。
10. **帧数可以数**：3 节点图 `values` 4 帧、`updates` 3 帧、`debug` 6 帧；
    帧数与追踪层的`span` 不是一对一。
11. **私有通道只对 `invoke` 隐身，不对流隐身**：`stream_mode="values"` 默认吐全部通道，
    要收窄得显式给 `output_keys`。
12. **中断需要检查点 ＋ 线程 ID**：少了检查点也照样停，但恢复会抛
    `RuntimeError`；恢复时节点从头重跑，副作用要放在中断之后。
13. **完成后再 resume 是空转**，不是重放——把两者混起来会得到假的成功读数。
14. **两层审批不是重复**：工具层管「这次调用做不做」，图层管「这条流程走不走」。

## 练习

- **基础**：给 `PipelineState` 加一个 `tag_suggestions` 键，要求：
  1）它是累加键；2）在摘要子图里顺带产出（用 4.2 的 `ArticleSummary` 取 `tags`）；
  3）在**输出 schema 里不出现**。然后写两条测试：
  一条证明它在内部账里有值，另一条证明 `invoke` 的返回值里没有这个键——
  并且第三条测试证明 `stream_mode="values"` 的最后一帧**能看到它**。
  （提示：第三条是文档明写的警告，不是 bug。）
- **进阶**：把「自评」从规则式换成**子图**：新增一张 `review_subgraph`，
  它先按长度算一个分，再（可选用模型）判断「是否写到了正文之外的事实」，
  最后返回 `{"score", "verdict"}`。要求：
  1）主图的路由函数改成读 `verdict`；2）离线两种剧本（够好 / 不够好）各跑一条测试；
  3）回答——**把自评放进子图之后，「上限折算」的公式要不要改？**用读数回答，
  不要凭感觉（提示：数一下主图上有几个节点）。
- **挑战**：给这张流水线加一条**断点续跑的验收**：写一个脚本，
  在中断处把 `app.get_state(cfg)` 与 `get_state_history(cfg)` 的全部快照转成 JSON 存盘，
  然后新开一个进程读回来继续（用 `InMemorySaver` 做不到这一点——请说明它为什么做不到，
  并给出一个能跨进程的最小替代方案）。要求：报告两件事——
  1）跨进程恢复后 `log` 会不会重复；2）如果 `publish_node` 在 `interrupt` 之前
  多了一句「扣一次发布配额」，你的验收会怎么发现这件事。
