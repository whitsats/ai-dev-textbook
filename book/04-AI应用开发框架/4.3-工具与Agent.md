# 4.3 工具与 Agent：让模型动手干活

## 本章导读

3.3 到 3.5 那三章，我们把「代理循环」一个字一个字写了出来：决策 → 执行 → 回填 → 再问，
终止条件、预算、卡死检测、工具错误、幂等键，一样一样拼上去。写完那一版的读者往往会问一句：
**这些能不能不自己写？**

这一章就是回答这句话。分两步：

1. **工具**：把 v3 手写的六个工具改成 `@tool`。三个要交代的东西（名字、描述、参数 schema）里，
   名字与 schema 由类型提示生成，描述由 docstring 生成。
2. **循环**：用 `create_agent` 替掉那个 `while True`，然后**把两条路径摆在同一个任务上跑**，
   看差在哪、没差在哪。

一个预告：**框架替代的是编排，不是判断。** 这一章最有价值的部分不是「一行装完循环」，
而是三件「一行装不完」的事：

- 框架接得住**参数形状错**，接不住**业务失败**（越权、状态不对）——实测里前者变成一条可读消息，
  后者直接抛穿整轮；
- 框架的默认终止条件**不是预算**：`recursion_limit` 默认 **9999**，而它数的是 super-step，
  折合约 5,000 次模型调用；
- 四条护栏（异常、幂等、审批、审计）在两条路径上**必须一字不差**，只是住的地方不同。

## 学习目标

读完本章，你应当能够：

1. 用 `@tool` 定义一个工具，并说出名字、描述、参数 schema **各自**来自哪一处；
2. 判断一个约束（类型、范围、枚举、必填）能不能靠类型提示表达，不能的话怎么补；
3. 说出框架默认行为里**三条**与直觉相反的：工具异常抛穿、`"42"` 被静默转成 `42`、
   `recursion_limit` 默认 9999；
4. 解释 `recursion_limit` 数的是 super-step 而不是模型调用，并算出「一次往返占几步」；
5. 把 v3 的四条护栏规则搬到中间件上，并说清哪一条**不能**只靠框架；
6. 用离线剧本模型证明两条路径读数一致，并解释为什么真机读数**不能**用来比较路径；
7. 说出审批的两种做法的代价差别，以及 `when` 谓词在小版本边界上的实际行为。

## 4.3.1 工具就是三样东西

一个工具交给模型的信息只有三样：**它叫什么、它是干什么的、它要什么参数**。
v3 里这三样是三个手写字段：

```python
# zhizhou-v3 的形状（不在 v4 树里，此处为对照）
Tool("read_article",
     "按 id 读一篇知舟文章的正文；正文超过 2,000 字会被截断并注明原文长度。适用于已经知道 id、"
     "要看内容细节的场景；只知道主题时先用 search_article 拿 id。",
     {"type": "object",
      "properties": {"article_id": {"type": "integer", "minimum": 1,
                                    "description": "文章 id，正整数"}},
      "required": ["article_id"]},
     READONLY, read_article, guard=lambda article_id: _own(article_id, user_id))
```

v4 里它是一段 Python：

```python
# app/tools.py —— 名字取自函数名，描述取自 docstring，schema 取自类型提示（节选）
    @tool(parse_docstring=True)
    def read_article(article_id: Annotated[int, Field(ge=1)]) -> dict:
        """按 id 读一篇知舟文章的正文。

        正文超过 2,000 字符会被截断并注明原文长度。适用于已经知道 id、要看内容细节的场景；
        只知道主题时先用 search_article 拿 id。

        Args:
            article_id: 文章 id，正整数
        """
        _own(article_id, user_id)
        return _fit({"article_id": article_id, "title": "JWT 刷新令牌怎么做",
                     "body": BODY_OF.get(article_id, "正文")})
```

差别不只是「少写了一行」。手写的那一份里，**三样东西是三个可以互相不一致的地方**：
描述里说「超过 2,000 字截断」，实现里的上限可能是 1,800；schema 说 `minimum: 1`，
函数里可能忘了判 0。v4 这一份把「参数长什么样」与「函数收什么」绑在了一起——
类型提示是函数签名的一部分，**改了签名就是改了 schema**，没有第二处可改。

另外两处细节值得一提：

- **`parse_docstring=True` 是必须写的**（下一节给读数）。不写的话，`Args:` 那一段会整段
  混进「描述」，而参数自己**拿不到** `description`。
- **`-> dict` 也是契约**。工具返回 `dict` 时框架把它序列化成 JSON 交给模型（实测用的是
  `json.dumps(..., ensure_ascii=False)`）；返回 `str` 就是原样文本。v3 这一步是手写的
  `ToolResult.payload()`，两种写法都要**量「模型看到的那一段」有多长**——见 4.3.3。

## 4.3.2 描述与 schema 从哪两处来

### 同一段 docstring，两种读法

`@tool` 默认 `parse_docstring=False`。这个默认值有一处不显眼的后果：

| 写法 | 工具描述（送给模型的那一段） | `article_id` 的 `description` |
| --- | --- | --- |
| 默认（`parse_docstring=False`） | 「按 id 读…正文。\n\nArgs:\n article_id: 文章 id，正整数」 | **没有** |
| `parse_docstring=True` | 「按 id 读…正文。」 | 「文章 id，正整数」 |

也就是说：**默认写法把参数说明当成散文塞进描述，而不是放进字段**。模型看到的是
一段带缩进的文本，而不是一份带注释的 schema。这不是「错」，但它意味着
你在 docstring 里认真写的 `Args:` 有相当一部分没有落在它该在的位置上。

还有一条**静默**的坑：`Args:` 里漏写某个参数**不会报错**。
实测写一个三参数函数、只在 `Args:` 里写了其中一个，`@tool(parse_docstring=True)` 构造成功，
缺的那个参数只是没有 `description`——而 `error_on_invalid_docstring` 的默认值是 `True`。
**它的校验管的是「格式坏」，不管「漏了一条」。**

### 与手写的 schema 逐条对照

六份定义都生成出来后，逐项量一遍（同一把尺子：`json.dumps(..., ensure_ascii=False)`）：

| 项 | v3 手写 | v4 生成 |
| --- | --- | --- |
| 六份定义合计 | 1,766 字符 | **2,603 字符** |
| 参数说明在哪 | `properties.<参数>.description` | 同左（**前提是写了 `parse_docstring=True`**） |
| 范围约束 | `"minimum": 1` 手写 | `Annotated[int, Field(ge=1)]` |
| 枚举约束 | `"enum": [...]` 手写 | `Literal["by_tag", "recent", "count"]` |
| `additionalProperties: false` | **有**（受约束解码靠它） | **默认不生成** |
| 每份定义里多出的字段 | 无 | `title`（Pydantic 每个字段自动加一个） |

多出来的 837 字符里，**`title` 占 280 字符**——它是白送的开销，但它不是小数：
这份定义**每次请求都要重发一遍**，它进不了任何对话缓存（3.1 的上下文预算就是按这个口径算的）。
2,603 字符对一次 4 万词元的调用不算什么，但工具集长到三十个时，这一项就是六千字符的固定成本。

`additionalProperties: false` 那一行值得单独说：v3 手写它是因为**要配合服务端的受约束解码**
（3.2 的做法）。框架默认不生成它——也就是说，换到 v4 之后，
「模型只能给出 schema 里有的字段」这条保证**没有跟着过来**。要它，得自己开服务商侧的
strict 开关，或者继续用 4.2 学过的结构化输出。**换框架时要专门问一句「哪些保证是框架给的、
哪些是上一版自己给的」**，这一行就是一个例子。

### 体积上限也归工具自己

实测：一个工具返回 `dict`，序列化后 4,047 字符，**框架原样放进上下文，一个字都不裁**。
所以 v3 放在注册表 `payload()` 里的那个上限，在 v4 里落到工具身上：

```python
# app/tools.py —— 按序列化后的长度限体积：超了就把最长的字符串字段裁到刚好放下（节选）
def _fit(payload: dict, limit: int = MAX_PAYLOAD_CHARS) -> dict:
    text = json.dumps(payload, ensure_ascii=False)
    if len(text) <= limit:
        return payload
    key = max((k for k, v in payload.items() if isinstance(v, str)),
              key=lambda k: len(payload[k]), default=None)
    if key is None:
        return payload
    original = payload[key]
    note = f"……（已截断，原文 {len(original)} 字）"
    overhead = len(text) - len(original)          # 字段名、引号、其它字段、转义都已算进去
    keep = max(0, limit - overhead - len(note))
    return {**payload, key: original[:keep] + note, "截断": True}
```

两个设计取舍：

- **裁完再序列化一次核对**。上限量的是「模型看到的那一段」，所以裁的对象是**序列化后的字符串**，
  不是字段本身的长度（字段名、引号、`\n` 的转义都算在预算里）。实测：3,104 字符的一篇正文
  进 `_fit` 出 1,976 字符，而上限写的是 2,000——剩下那 24 字符正是 `……（已截断，原文 N 字）`。
- **返回里多一个 `截断` 字段**。于是「这次到底裁没裁」是可读的，不必靠事后去猜
  （与 4.2 的 `clipped`、4.1 的 `describe_defaults` 是同一种做法：**把隐式状态变成字段**）。

## 4.3.3 类型提示拦得住什么、拦不住什么

这是本章第一张实测表。同一个错误参数，两条路径各自的处置：

| 调用 | v3（手写校验） | v4（框架 ＋ 类型提示） |
| --- | --- | --- |
| `read_article(43)`（别人的文章） | 拦下：`文章 43 不属于你，无权读写。` | **抛穿整轮**（`ToolException`） |
| `read_article("42")`（字符串） | 拦下：`类型错：article_id 应为 integer，实为 str` | **静默转成 42，工具真的执行了** |
| `read_article()`（缺必填） | 拦下：`缺必填：article_id 未提供` | 框架拦住，`status=error`，`Field required` |
| 未知工具 `no_such_tool` | 拦下：`未知工具` | 框架拦住，并**列出可选工具** |
| `articles(mode="latest")` | 拦下：`枚举越界` | 框架拦住：`Input should be 'by_tag', 'recent' or 'count'` |
| `read_article(0)` | 拦下：`范围越界：0 小于下限 1` | 框架拦住（靠 `Field(ge=1)`） |

表里最该看的是第二行与第一行。

**第二行是「宽进」。** v3 的手写校验是严格的：`"42"` 不是 `integer`，判类型错。
框架走的是 Pydantic 的宽松模式，`"42"` 被**静默转成** `42`，工具照常执行。
这对模型是好事（少一次失败重试），对你是坏事：**不能靠类型来挡参数**。
如果你的工具里有一个「必须是刚读到的 id」的参数，宽松模式会让一个字符串悄悄变成合法输入。

**第一行是本章最该记住的一条默认行为：框架不接工具内部的异常。**
langgraph 的默认处理器是这么写的（`langgraph/prebuilt/tool_node.py`，1.2.2）：

```text
def _default_handle_tool_errors(e):
    if isinstance(e, ToolInvocationError):   # 参数形状错、工具名不存在
        return e.message
    raise e                                  # 其它一律往上抛
```

于是规律只有一条：

> **框架接得住「调用得不对」，接不住「调用对了但做不成」。**

前半句覆盖缺参、类型、枚举、未知工具——它们都是**调用形状**问题；
后半句覆盖越权、状态不对、下游失败——它们都是**业务**问题。
`ToolException` 属于后半句：它是框架认识的异常类型，但**默认不替你接**。
一份照抄 v3 逻辑的工具集搬过来，第一次越权就是整轮崩掉。

这正好解释了 3.5 那个决定的份量：**授权钩子写在工具里（`_own`），校验先于执行**。
v3 的注册表把「参数校验」与「授权」分成两道闸，第二道闸在 v4 里没有任何框架替你装。

## 4.3.4 create_agent：一个函数装下整个循环

装配一行：

```python
# app/agent.py —— 框架版：一行装配。循环、工具节点、路由、消息归并全在图里（节选）
def create_zhizhou(model: BaseChatModel, tools: list[BaseTool], *,
                   middleware: list[Any] | None = None,
                   checkpointer: Any = None,
                   system_prompt: str = AGENT_SYSTEM,
                   name: str = "zhizhou-v4"):
    return create_agent(model, tools=tools, system_prompt=system_prompt,
                        middleware=list(middleware or []), checkpointer=checkpointer,
                        name=name)
```

它装出来的是一张图，读出来是这样（`describe_agent`）：

```text
节点：['__end__', '__start__', 'model', 'tools']
边：__start__→model ｜ model→__end__（条件）｜ model→tools（条件）｜ tools→model（条件）
```

四条边就是 3.3 那个循环的骨架：「先问模型；有工具调用就去工具节点；工具节点回模型；
没有工具调用就结束」。**`while True` 变成了两条条件边**。

### 默认的终止条件不是预算

v3 的循环有三条上限（模型调用数 8、词元 8,000、墙钟 120 秒），撞上任何一条都**先收口**。
框架侧对应的旋钮叫 `recursion_limit`，它有三个要记住的点：

1. **它数的是 super-step，不是模型调用。** 实测（一个永不收敛的剧本）：

   | `recursion_limit` | 实际发生的模型调用 | 结果 |
   | ---: | ---: | --- |
   | 6 | 3 | `GraphRecursionError` |
   | 8 | 4 | 同左 |
   | 10 | 5 | 同左 |

   一次「模型 ＋ 工具」的往返占 2 步，所以**模型调用数 ≈ `recursion_limit` ÷ 2**。
   把它当「步数」读，会高估一倍。

2. **默认值是 9999**（langgraph 1.2.2）。按上一条折算，那是约 5,000 次模型调用——
   这不叫预算，这叫没有预算。本书在 `app/agent.py` 里显式写了 `DEFAULT_RECURSION_LIMIT = 8`，
   与 v3 的 `max_steps=8` 对齐。

3. **它不是一个参数**。`create_agent` 不收这个值，它是**调用时**的配置：

```python
# app/agent.py —— 一条运行配置。上限必须写在这（节选）
def agent_config(*, thread_id: str | None = None,
                 recursion_limit: int = DEFAULT_RECURSION_LIMIT) -> dict:
    config: dict[str, Any] = {"recursion_limit": recursion_limit}
    if thread_id is not None:
        config["configurable"] = {"thread_id": thread_id}
    return config
```

这条「装配时设不了、调用时才能设」的性质很关键：**它意味着上限不属于应用，属于调用方**。
一个只装配一次、到处复用的 agent 对象，可以在每个入口用不同的上限——
比 v3 把上限写进 `chat(max_steps=...)` 的签名更灵活，但也更容易漏（漏了就是 9999）。

### 读数是数出来的

```python
# app/agent.py —— 用 stream_mode="values" 而不是 invoke：每一步的快照都要（节选）
    try:
        for snapshot in agent.stream({"messages": [{"role": "user", "content": task}]},
                                    config=cfg, stream_mode="values"):
            frames.append(snapshot)
    except Exception as exc:                     # GraphRecursionError 也会走到这里
        stats.crashed = f"{type(exc).__name__}: {str(exc)[:60]}"
        stats.stop = f"异常中断（{type(exc).__name__}）"
    stats.super_steps = max(0, len(frames) - 1)   # 第一帧是入口状态，不算一步
```

为什么不用 `invoke`：**「框架走了几步」这件事只有流能看见**，`invoke` 只给你最后一帧。
而步数、模型调用数、工具调用数、词元，四列读数分别来自：帧数、状态里的 `AIMessage` 条数、
`ToolMessage` 条数、`usage_metadata` 之和。**一个都不手填**（承接 3.9 的纪律）。

## 4.3.5 框架不替你做的那四件事

v3 的四条护栏规则原来挤在 `bind_tools` 那个闭包里（那是 3.5 的装配点）。
搬到 v4 之后它们住进一个中间件，因为它们遵守的是同一个契约：

> 一次工具调用 = 判断（谁、能不能、做没做过）→ 执行 → 记账

```python
# app/middleware.py —— 四条规则装成一个中间件；approve 没给时默认拒绝（节选）
    @wrap_tool_call
    def guard(request, handler):       # noqa: ANN001 —— 框架给的签名
        call = request.tool_call
        name, args, call_id = call["name"], call.get("args") or {}, call["id"]
        started = time.perf_counter()

        def emit(**kw: Any) -> None:
            if audit is not None:
                audit.append({"tool": name, "run_id": run_id,
                              "ms": round((time.perf_counter() - started) * 1000, 1), **kw})

        if name in require_approval and not (approve and approve(name, args)):
            text = f"[等待人工确认] {name} 未获批准，本轮不执行。请向用户说明并停下。"
            emit(ok=False, error_type="未获人工确认", arguments=json.dumps(args, ensure_ascii=False))
            # `name` 要自己填：框架自己的工具节点会填，替它合成的消息不填的话
            # 下游按 `message.name` 分组的统计会把这两类失败归成一个空名字。
            return ToolMessage(content=text, tool_call_id=call_id, status="error", name=name)
```

四条规则与 v3 的对应关系：

| 规则 | v3 的位置 | v4 的位置 | 实测行为 |
| --- | --- | --- | --- |
| 异常收成可读文本 | 循环里的 `except` | `wrap_tool_call` | 越权 → `status=error`，并归到「越权」档 |
| 幂等键 | `bind_tools` 闭包 | `wrap_tool_call` | 同一运行重发同一笔写 → 命中 1 次，服务端不重复写 |
| 人工确认 | `approve` 回调 | `wrap_tool_call`（或框架中断） | 不批 → 不执行，且**留痕** |
| 审计与耗时 | 追踪回呼 | `wrap_tool_call` | 被拒的调用也进审计（它不是「没发生的事」） |

三处细节，都是从实测里长出来的：

- **替框架合成的消息要自己填 `name`。** 框架自己的工具节点会填，我们拦下调用时替它合成的
  `ToolMessage` 不填的话，下游按 `message.name` 分组会把「被拦的发布」和别的失败归成一个空名字。
- **幂等键里必须有 `run_id`。** 实测：同一次运行里连写两遍 → 命中 1 次；
  同一个 `run_id` 再跑一轮 → 累计 2 次（键没变）；换一个 `run_id` → 0 次。
  重放不会被静默吞掉，也不会重复写。
- **默认拒绝**。`approve` 没给时，`require_approval` 里的动作一律不执行——
  这与 v3 的 `approve=lambda name, args: False` 默认值一致（3.8 的档位表里，
  「没配」等于哪一档必须有明确答案，答案是「关」）。

还有一件**框架有、我们没用**的东西：`ToolRetryMiddleware`。实测（一个前两次必失败的夹具）
`max_retries=3` 时工具体被调用 3 次后成功，失败与退避都不用写。
但要记住 3.5 的结论：**写操作不能盲目重试**，重试要配幂等键才有意义——
所以本章的工具层给了幂等键，重试中间件才是安全的。两件事要一起上。

## 4.3.6 两条路径摆在一起

### 离线：逐项相同

同一个剧本（看标签 → 读一篇 → 写草稿 → 给结论）跑两条路径：

| 路径 | 终止原因 | 模型调用 | super-step | 工具调用 | 词元 |
| --- | --- | ---: | ---: | ---: | ---: |
| 手写循环 | 模型给出最终答案 | 4 | 7 | 3 | 1,460 |
| `create_agent` | 模型给出最终答案 | 4 | 7 | 3 | 1,460 |

**逐项相同。** 工具序列也一样（`get_tags、read_article、create_draft`）。
差的是：手写版那段 `while True` 在本树 60 行，框架版那一段是 `create_agent(...)` 一行
——而循环本身变成了图里的四条边。

这里有一个**必须对齐的细节**：手写版的 super-step 是自己数的
（一次模型调用 ＋ 一个有工具调用的往返再加一个工具节点），框架版是流出来的帧数。
两把尺子必须是同一把，否则会凭空造出一个「手写 8 步 vs 框架 7 步」的假差异
——本章第一版正是这么写的，读出来的差不是框架的差，是我数法的差。

### 真机：读数不能用来比较路径

同一个任务（把 42 号文章的草稿改成「刷新令牌用版本号方案」），**每条路径跑两遍**：

| 轮次 | 模型调用 | 工具调用 | 工具序列 | 词元 |
| --- | ---: | ---: | --- | ---: |
| 手写 #1 | 2 | 1 | `create_draft` | 2,758 |
| 手写 #2 | 3 | 2 | `read_article → create_draft` | 9,326 |
| 框架 #1 | 3 | 2 | `read_article → create_draft` | 8,448 |
| 框架 #2 | 3 | 2 | `read_article → create_draft` | 8,152 |

**同一条路径跑两遍的差（2,758 与 9,326），比两条路径之间的差还大。**
手写 #1 直接改了草稿，手写 #2 先读了一遍再改——两次都「对」，只是模型这一轮的选择不同。

所以这一节的结论要写得比看上去紧：

> **真机读数里有模型自己的随机性，它只能报量级，不能用来比较路径。**
> 能下结论的地方是离线——剧本固定，两边逐项相同。

这与 3.9 那条教训是同一族：**把「基础设施与采样带来的波动」当成「实现之间的差异」，
会读出完全相反的结论。** 上一章是「连接断开被当成模型失败」，这一章是
「模型这轮多读了一篇被当成框架的开销」。凡是拿两次真机运行做比较的结论，
都要先做一次「同一条路径跑两遍」的对照实验。

## 4.3.7 审批：两种做法的代价

3.8 定了规矩：发布不可逆，所以它不在「模型说做就做」的范围内。v4 里这件事有两种实现。

### 做法一：回调（v3 的形状）

`approve(name, args) -> bool`，一个进程内的函数。实测两条路径行为一致：

| 路径 | `approve=False` | `approve=True` |
| --- | --- | --- |
| 手写循环 | `create_draft:成功、publish_article:被拦` | `create_draft:成功、publish_article:成功` |
| `create_agent` ＋ 中间件 | 同左 | 同左 |

它的代价很直白：**问题与回答必须在同一个进程里**。服务重启、请求断开、人过了十分钟才批，
这次调用就没人回答了。好处同样直白：一个函数，不用检查点、不用恢复协议。

### 做法二：框架中断（跨进程等人）

`HumanInTheLoopMiddleware` 把中断变成一个**可以持久化的状态**：

```python
# scripts/agent_tools.py —— 中断发生在执行之前，工具体一次都没执行（节选）
    first = agent.invoke({"messages": [{"role": "user", "content": "改完就发布"}]},
                         config=config, version="v2")
    asked = first.interrupts[0].value["action_requests"][0] if first.interrupts else None
```

实测（剧本：写草稿 → 发布 → 收尾）：

- 第一次 `invoke` **中断**，被问的动作是 `publish_article`，已产出 4 条消息，
  而**工具体一次都没有执行**——中断发生在执行之前；
- 批准后：6 条消息，末条是模型的「已发布。」；
- 拒绝后：模型收到的是**人的原话**（`用户说先别发`）作为一条工具消息。

代价是三样：**要检查点**（`InMemorySaver` 起步，生产要换持久化的）、
**要 `thread_id`**（否则没法恢复）、**要一条 `Command(resume=...)` 恢复协议**。
换来的是：人可以十分钟后回来批，进程可以重启，审批记录留在状态里。

### 一个版本边界上的静默失效

官方文档里 `interrupt_on` 支持一个 `when` 谓词，用来做**条件审批**
（例如「只拦写库的 SQL 查询」），并注明**需要 `langchain>=1.3.3`**。本机是 1.3.2，实测：

| `when` 的返回值 | 是否中断 |
| --- | --- |
| `True` | **否** |
| `False` | **否** |

**参数被接受了，但不生效**——不报错、不警告、不抛异常。这比直接报错危险得多：
报了错你会去查版本，不报错你会以为策略生效了，直到某天发现所有调用都没被拦。
可操作的结论有两条：**看到「需要某版本以上」的文档，先去查自己的版本**；
以及**在小版本边界上的新参数，要用一次「它到底生效了吗」的反例去验**——
本章的测试就是这么写的（按版本分支断言，升级之后同一条测试会自己转到另一支）。

想做条件审批又不想升级，就把它放进 `wrap_tool_call`：读 `request.tool_call["args"]`，
自己判条件，不满足就返回一条「等待人工确认」的工具消息——**这条路与框架版本无关**。

## 4.3.8 知舟接线

### 加了什么

4.3 往 `zhizhou-v4/` 里加了五个模块与两份脚本，顶掉的是 v3 的工具层与循环：

| 文件 | 行数 | 顶替 v3 的哪一块 |
| --- | ---: | --- |
| `app/tools.py` | 245 | `app/agent/tools/zhizhou.py`（183 行）＋ `registry.py` 里的 JSON Schema 校验与体积上限 |
| `app/middleware.py` | 120 | `app/agent/loop.py::bind_tools`（幂等键、审批、错误分档、追踪回呼） |
| `app/agent.py` | 271 | `app/agent/loop.py::run_agent`（循环与预算） |
| `app/scripted.py` | 71 | 无对应（v3 用 `scripted()` 策略函数代替） |
| `scripts/agent_tools.py` | 301 | 无对应（v3 的 `demo.py` 没有这一组对照） |
| `tests/test_agent_tools.py` | 369 | 无对应（v3 的工具测试在 `tests/test_wiring.py` 里） |

**注册表没有被完全替代，这是本章最该说清楚的一句。** v3 的 `registry.py` 干了四件事：
参数校验、授权钩子、体积上限、审计与幂等。在 v4 里：

- 参数校验 → **类型提示 ＋ 框架**（但**变宽了**，`"42"` 会被转成 `42`）；
- 授权钩子 → **仍在自己手里**（`_own`，写在工具里）；
- 体积上限 → 工具自己（`_fit`）；
- 审计与幂等 → 中间件。

也就是说 `registry.py` 那一份确实可以删掉了，但**删掉的是它的壳，不是它守的规矩**。

### 接口契约

| 契约 | 内容 |
| --- | --- |
| 六个工具的名字与参数名不许改 | `search_article` / `read_article` / `articles` / `get_tags` / `create_draft` / `publish_article`，与 v3 逐条一致；第 4 篇的对照靠它 |
| 系统提示两份是一个文本 | `app/prompts.py::AGENT_SYSTEM` 与 v3 的 `app/agent/prompts/agent.md` 逐字相同 |
| 模型出口不许绕过 | 所有工具与 agent 的模型都从 `app/llm.py::build_model()` 来（4.1 的硬约定） |
| 授权写在工具里 | `_own(article_id, user_id)` 在**每次读写之前**执行，不靠类型、不靠中间件 |
| 上限必须显式 | `recursion_limit` 由 `agent_config()` 给出，默认 8；**不许依赖框架的 9999** |
| 审批默认拒绝 | `approve` 没给或返回 `False` → 不执行，且负例也进审计 |
| 剧本模型每轮换 `tool_call_id` | 复用同一个 id 会让框架报一个不指向真因的 `KeyError: 'model'` |

### 怎么验

```bash
cd zhizhou-v4
python scripts/agent_tools.py --offline   # 不需要密钥：五段读数；**这一路是门**
set -a && . ../zhizhou-v3/.env && set +a
python scripts/agent_tools.py --real      # 真机：两条路径各跑两遍，报量级
python ../tools/check_runnable.py         # 正文里每段节选都要能在树里逐行找到
```

四条判据：

1. **离线那一句** `✔ 离线自检通过` 必须出现，且第①段打出
   `合计 2603 字符`（对照 v3 的 1,766）；
2. **第②段的六行**：越权那一行必须是「抛穿整轮」，
   类型那一行必须是「工具真的执行了」——**两条都是框架的默认行为，不是我们的选择**；
3. **第③段两条路径的四列必须相同**（模型调用 4 / super-step 7 / 工具 3 / 词元 1460）；
4. **一致性**：本章带路径标注的每一个代码块，都要能在 `zhizhou-v4/` 里逐行对齐
   （由 `check_runnable.py` 守）。

### 不能破坏什么

- **不许把 `_own` 挪进中间件**。授权需要业务语义（谁是作者），中间件只有参数。
  3.5 的结论在这里照旧成立：**schema 管得了类型，管不了「这是谁的文章」**。
- **不许把上限交给框架默认值**。`recursion_limit` 9999 与 v3 的 `max_steps=8`
  差了三个数量级，漏掉这个参数就是把预算换成「没有预算」。
- **不许在工具里 `try/except` 吞掉异常后返回空串**。可读的失败必须是**文本**，
  空串会让模型以为拿到了结论（3.5 的 `payload()` 有一条：「绝不截断成空」）。
- **不许给写操作开无幂等的重试**。要开 `ToolRetryMiddleware`，先把幂等键装上。
- **不许把两份系统提示改得不一样**。改了以后第 4 篇所有对照都不成立。

## 常见坑

- **不写 `parse_docstring=True`**：`Args:` 整段混进描述，参数自己拿不到 `description`。
- **以为 `Args:` 漏写会报错**：`error_on_invalid_docstring=True` 管的是格式，
  漏一条参数它不吭声。
- **以为类型能挡参数**：`"42"` 会被静默转成 `42`。要挡就在函数里挡。
- **以为 `ToolException` 会被框架接住**：默认不接，整轮抛穿。
  要接就 `wrap_tool_call`，或者用 `ToolRetryMiddleware` 配 `on_failure`。
- **把 `recursion_limit` 当步数**：它数 super-step，一次往返 2 步。
- **忘了设 `recursion_limit`**：默认 9999，约 5,000 次模型调用。
- **给限额中间件配了一个更紧的 `recursion_limit`**：实测 `run_limit=3` 时，
  `recursion_limit=8` 会让整轮**撞图递归上限、空手回来**（`answer` 是空的），
  提到 20 才拿到那句「Model call limits exceeded: run limit (3/3)」。
  两个闸门都装了，但**没有对过账**。
- **剧本模型复用同一个 `tool_call_id`**：框架按 id 去重，第二次工具调用没有对应的
  工具消息，报出来的是 `KeyError: 'model'`——一个完全不指向真因的错。
- **拿真机两次运行比较两条路径**：同一条路径跑两遍的差可能比路径之间的差还大。
- **以为工具结果是框架帮忙裁过的**：实测 4,047 字符原样进上下文，一个字都不裁。

## 面试视角

「你用过 LangChain 的 Agent 吗」背后的考点，通常也分四层：

1. **第一层：知道 `create_agent` 装的是图。** 答「节点是模型与工具，
   边是两条条件边；循环是编译出来的，不是我写的」，
   并且能说出默认 `recursion_limit` 是 **9999** 且**数的是 super-step**
   （这两句一说，面试官就知道你真跑过）。
2. **第二层：知道框架接什么、不接什么。** 「参数形状错框架兜住——缺参、类型、枚举、
   未知工具都会变成 `status=error` 的工具消息；而工具内部的异常**默认抛穿**，
   越权这种业务失败必须自己拦」。再补一句「`ToolException` 是框架认识的类型，
   但默认不替你接」——这是本章最容易被追问的一条。
3. **第三层：知道护栏住在哪一层。** 能把 v3 的四条规则（异常、幂等、审批、审计）
   一条条对到中间件上，并说明**为什么授权不能搬**（要业务语义）。
   还会主动提「幂等键要带 `run_id`，否则重放被静默吞掉」。
4. **第四层：知道怎么测。** 「离线用剧本模型证明两条路径读数逐项相同；
   真机只报量级，因为同一条路径跑两遍的差可能更大」。
   再加上一条版本纪律：「看到『需要某版本以上』先去查自己的版本——
   1.3.2 上的 `when` 谓词**不报错，只是不生效**」。

一个常被追问的收尾：「那你为什么不就用框架？」回答落在**知道自己省掉了什么**上：
手写一遍才知道 `registry.py` 里那四件事分别是什么，于是搬到框架上时，
知道哪三件可以交出去、哪一件必须自己留着。**这是「会用框架」与「只会框架」的分界。**

## 本章小结

1. **工具的三样东西来自三处**：名字来自函数名，schema 来自类型提示，描述来自 docstring
   （要写 `parse_docstring=True`，否则 `Args:` 会整段混进描述）。
2. **生成的定义比手写的长**：六份 2,603 字符 vs 1,766，其中 `title` 占 280 字符；
   而且 `additionalProperties: false` **没跟过来**——换框架时要问「哪些保证是自己给的」。
3. **体积上限仍归工具自己**：框架不裁（实测 4,047 字符原样进上下文）。
4. **框架接得住「调用得不对」，接不住「调用对了但做不成」**：缺参、枚举、未知工具都被兜住；
   越权抛穿整轮，`"42"` 被静默转成 `42`。
5. **循环变成四条边**：`__start__→model`、`model→tools`、`tools→model`、`model→__end__`。
6. **`recursion_limit` 数 super-step，默认 9999**（约 5,000 次模型调用）；
   本书显式写 8，与 v3 的 `max_steps` 对齐。
7. **四条护栏搬到中间件**：异常、幂等、审批、审计；**授权留在工具里**（要业务语义）。
8. **两个上限要对账**：`ModelCallLimitMiddleware(run_limit=3)` 配 `recursion_limit=8`
   会撞图递归上限空手回来，配 20 才拿到那句限额说明。
9. **离线能下结论，真机只能报量级**：离线两条路径逐项相同（4 / 7 / 3 / 1,460）；
   真机上同一条路径跑两遍的差（2,758 与 9,326）比路径之间的差大。
10. **审批有两种做法**：进程内回调（一个函数，不能跨进程）与框架中断
    （要检查点与恢复协议，但人能十分钟后回来批）；中断发生在执行之前，工具体一次都没跑。
11. **版本边界上最危险的不是报错，是不报错**：1.3.2 上 `when` 谓词静默失效。
12. **`ToolRetryMiddleware` 能用，但要先有幂等键**：写操作不能盲目重试。
