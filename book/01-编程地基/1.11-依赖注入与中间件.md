## 1.11.1 依赖注入解决的是什么问题

先在路由函数里写一段「能跑但会痛」的代码。

```python
# ❌ 资源在路由内部自己创建
@app.get("/users/me")
def read_user_me():
    db = create_session()              # 每次请求自己建连接
    token = "从请求头里取……"            # 手工解析，写死在函数里
    if token != "valid_token":
        db.close()
        raise HTTPException(status_code=401, detail="无效 Token")
    user = db.query("SELECT * FROM users WHERE id = 1")
    db.close()                          # 忘了关就是连接泄漏
    return user
```

这段代码有四个问题，而且都不是「写得丑」层面的：

1. **资源与业务缠在一起**：想给另一个路由复用「取当前用户」的逻辑，只能复制粘贴。
2. **无法替换**：测试时这个路由会去连真实数据库，跑一轮测试污染一次数据。
3. **清理不可靠**：任何一条提前 `return` 或 `raise` 都会绕过 `db.close()`。
4. **参数来源写死**：`token` 从哪来、怎么校验，和业务逻辑挤在同一个函数体里。

**依赖注入（Dependency Injection, DI）** 的做法是反过来：路由**声明**它需要什么，
由框架负责**创建、组装、注入**。

```python
# ✅ 依赖声明在参数上，创建与清理交给 FastAPI
def get_db():
    db = create_session()
    try:
        yield db
    finally:
        db.close()

def get_current_user(token: str = Header(...), db=Depends(get_db)):
    if token != "valid_token":
        raise HTTPException(status_code=401, detail="无效 Token")
    return {"id": 1, "name": "alice"}

@app.get("/users/me")
def read_user_me(user=Depends(get_current_user)):
    return user                      # 路由只剩业务
```

对比一目了然：清理逻辑**只写一次**，且写在 `try/finally` 里；
校验逻辑**只写一次**，需要它的路由声明一句就行。

### 这不是 FastAPI 发明的

依赖注入是**控制反转（Inversion of Control, IoC）** 的一种落地方式：
对象的创建权从「使用者」反转给「容器」。Java 的 Spring、.NET 的内置容器都是同一思路。

差别在于**重量级**。Spring 需要注解 + 容器 + 配置文件，因为 Java 的依赖图通常很复杂；
FastAPI 把「容器」压缩成了一个函数调用 `Depends(f)`，依赖图就是函数的调用图。
这是 Python 的便利：函数本身就是一等对象，能直接当参数传。

| 做法 | 资源创建位置 | 替换（测试） | 清理保证 | 依赖关系可见性 |
| --- | --- | --- | --- | --- |
| 模块级单例（`db = Session()`） | 导入时一次 | 需改全局变量 | 无 | 隐藏，看代码才知道 |
| 路由内部自己建 | 每次请求 | 需改路由代码 | 靠自觉 | 隐藏 |
| 依赖注入 | 框架按声明创建 | `dependency_overrides` | `try/finally` | **写在签名里** |

### 三个收益，按重要性排序

1. **可测试**——这是最被低估的一条。测试时用 `app.dependency_overrides` 把真依赖换成替身，
   路由代码一行不动（见第 1.11.8 节）。
2. **可清理**——`yield` + `finally` 把「借了要还」变成框架保证，而不是程序员自觉。
3. **可组合**——依赖可以依赖别的依赖，形成一棵树；越靠近业务的需求（「当前用户」）
   越靠上，越通用的资源（「数据库会话」）越靠下。

> 💡 **提示**：判断一段逻辑该不该做成依赖，问一句「它是不是『某几个路由需要的东西』」。
> 需要就做成依赖；**每个**路由都需要、且不关心路由上下文，那才考虑中间件（第 1.11.12 节）。

## 1.11.2 `Depends`：声明依赖与执行流程

### 三步原理

路由通过参数和 `Depends` 声明它需要什么，剩下的由 FastAPI 完成：

1. **看声明**：这个参数声明了 `Depends(get_db)`；
2. **执行依赖函数**：调用 `get_db()`（如果它自己也有依赖，先递归解析）；
3. **注入返回值**：把依赖函数的返回值（或 `yield` 出来的值）塞进这个参数。

```python
from fastapi import FastAPI, Depends

app = FastAPI()

def get_query_param():
    return "default_value"

@app.get("/items")
def read_items(q: str = Depends(get_query_param)):
    return {"q": q}
```

```text
$ curl "http://127.0.0.1:8000/items"
{"q":"default_value"}
```

依赖函数可以返回任何东西：字符串、字典、Pydantic 模型、数据库会话对象。

### 最常见的第一个错误：传了函数调用

```python
# ❌ 传的是调用结果
@app.get("/items")
def read_items(q=Depends(get_query_param())):   # 注意末尾的 ()
    ...
```

```text
TypeError: 'str' object is not callable
```

`Depends` 需要的是**可调用对象**，它自己在合适的时机调用。
多写一对括号，函数在**导入时**就被执行了一次，`Depends` 拿到的是那个返回值。
这类错误在启动时就会抛出，不算难查；真正难查的是「参数漏写 `Depends`」（见「常见坑」）。

### 路由参数与依赖参数各自解析

依赖函数的参数**独立解析**，和路由函数是同一套规则：依赖参数名对应查询参数，
就意味着它在 URL 上取值（第 1.11.4 节）。这带来一个容易误解的点：

```python
def get_pagination(skip: int = 0, limit: int = 10):
    return {"skip": skip, "limit": limit}

@app.get("/items")
def list_items(params: dict = Depends(get_pagination)):
    return {"params": params}
```

```text
$ curl "http://127.0.0.1:8000/items"
{"params":{"skip":0,"limit":10}}
$ curl "http://127.0.0.1:8000/items?skip=5"
{"params":{"skip":5,"limit":10}}
```

路由函数签名里**看不到** `skip` 和 `limit`，但文档页里它们照常出现——
因为参数来自依赖函数签名。这是依赖注入的一个「副作用」：
**接口的输入面由整棵依赖树决定**，不是只看路由签名。

## 1.11.3 带 `yield` 的依赖：资源清理

需要「借了要还」的资源（数据库会话、文件句柄、锁、临时目录）时，依赖函数写成生成器：
在 `yield` 之前是**初始化**，`yield` 之后是**收尾**。

```python
def get_db():
    print("连接数据库……")          # ① 初始化
    db = "DB_Connection_Object"
    try:
        yield db                    # ② 把 db 交给路由，此处暂停
        print("提交事务……")          # ④ 路由正常返回后执行
    finally:
        print("关闭数据库连接……")    # ⑤ 无论如何都执行

@app.get("/users")
def get_users(db: str = Depends(get_db)):
    print("路由主逻辑")             # ③
    return {"users": ["Alice", "Bob"]}
```

```text
$ curl "http://127.0.0.1:8000/users"
{"users":["Alice","Bob"]}
```

```text
# 服务端输出
连接数据库……
路由主逻辑
提交事务……
关闭数据库连接……
```

### 异常路径：素材这里说错了

讲义写道：「即使路由函数抛出异常，`finally` 块也会保证执行——**清理顺序与正常情况完全一致**」。
前半句对，后半句会把人带进坑里。实测（FastAPI 0.136 / Starlette 1.6）：

```python
log = []

def dep_no_try():
    yield "x"
    log.append("yield 之后：提交")        # 没有 try 保护

def dep_with_try():
    try:
        yield "x"
        log.append("提交")
    except Exception:
        log.append("回滚")
    finally:
        log.append("关闭")

@app.get("/a")
def a(d=Depends(dep_no_try)):
    raise RuntimeError("boom")

@app.get("/b")
def b(d=Depends(dep_with_try)):
    raise RuntimeError("boom")
```

```text
# 两个请求都返回 500，服务端日志分别为
/a  →  []
/b  →  ['回滚', '关闭']
```

结论很关键：

- 路由抛异常时，异常会被**抛回生成器的 `yield` 处**；
- 所以 `yield` **之后**的「提交事务」**根本不会执行**——不是顺序变了，是没执行；
- 只有 `try` / `except` / `finally` 写全，才能既回滚又关闭。

> ⚠️ **素材纠错（照抄会丢事务）**：讲义把 `yield` 之后直接写「提交事务」当作正常收尾，
> 并声称异常下 Cleanup 顺序一致。**异常下提交语句不会执行，也没有回滚**——
> 数据库会话被关闭，但事务悬空。生产代码必须写成
> `try: yield db` / `except Exception: await session.rollback(); raise` / `finally: await session.close()`。
> 第 1.12 节会把这段写成可直接用的 `get_db`。

### `yield` 依赖只能 `yield` 一次

生成器依赖的设计就是「一次 setUp、一次 tearDown」。这两种写法都不行：

```python
# ❌ 想「提前返回」：return 会让生成器结束，清理走的是 StopIteration 路径
def get_db():
    db = create_session()
    if not healthy():
        return None              # yield 都没执行过，Depends 拿到 None
    try:
        yield db
    finally:
        db.close()

# ✅ 初始化失败就抛异常，让 FastAPI 直接返回错误
def get_db():
    db = create_session()
    if not healthy():
        db.close()
        raise HTTPException(status_code=503, detail="数据库暂时不可用")
    try:
        yield db
    finally:
        db.close()
```

> 🔥 **常见坑**：在 `yield` 依赖里 `raise HTTPException` 清理不了已借资源。
> 「初始化失败」这段代码发生在 `yield` 之前，`finally` 还没建立，
> 所以必须**手动关闭再抛**，如上面第二段。

## 1.11.4 带参数的依赖与链式依赖

### 参数来自请求

依赖函数的参数按 1.9 的同一套规则从请求里取，于是「带约束的公共参数」可以一次定义、多处复用：

```python
from typing import Annotated
from fastapi import Query

def get_pagination(
    skip: Annotated[int, Query(ge=0, description="跳过的条数")] = 0,
    limit: Annotated[int, Query(ge=1, le=100, description="每页条数")] = 10,
):
    return {"skip": skip, "limit": limit}
```

约束、描述、默认值都写在依赖里，**文档里每个用到它的路由都会自动带上**。

### 链式依赖

依赖可以依赖别的依赖，形成一棵树。解析顺序是**自底向上**：

```python
def get_db():
    return "DB_Connection"

def verify_token(token: str = "valid_token"):
    if token != "valid_token":
        raise HTTPException(status_code=401, detail="无效 Token")
    return {"user_id": 1}

def get_current_user(
    token: dict = Depends(verify_token),
    db: str = Depends(get_db),
):
    return {"user": token, "db": db}

@app.get("/profile")
def get_profile(user: dict = Depends(get_current_user)):
    return user
```

解析过程（与素材一致，已实跑核对）：

```text
/profile  →  需要 get_current_user
             ├── 需要 verify_token → 执行 → {'user_id': 1}
             └── 需要 get_db        → 执行 → 'DB_Connection'
          →  get_current_user 拿到两者，返回合并结果
          →  注入路由参数 user
```

> ⚠️ **注意**：**兄弟依赖之间没有约定的执行顺序**。上面 `verify_token` 与 `get_db`
> 谁先谁后属于实现细节，不要写出依赖这个顺序的代码——需要顺序就把它变成父子关系。

### 依赖能用上路由的路径参数

依赖函数里声明**同名**的路径参数，就能拿到它：

```python
@app.get("/posts/{post_id}/comments")
def list_comments(post_id: int, page: int = Depends(get_page)):
    ...                     # get_page 里声明 post_id: int 也能取到同一个值
```

这让「按资源 ID 做权限校验」变得自然：

```python
def owned_post(post_id: int, user=Depends(get_current_user), db=Depends(get_db)):
    post = db.get_post(post_id)
    if post.author_id != user["id"]:
        raise HTTPException(status_code=403, detail="无权访问该文章")
    return post

@app.get("/posts/{post_id}")
def read_post(post: dict = Depends(owned_post)):
    return post
```

路由函数里没有一行权限代码，但它被**强制**执行了——因为 `post` 只能从 `owned_post` 来。

## 1.11.5 类依赖与 `Annotated`

### 类作为依赖项

依赖不必是函数，**类**也行。`Depends()` 不传参数时，FastAPI 用这个类本身当依赖并自动实例化，
`__init__` 的参数就是依赖的参数：

```python
class PaginationParams:
    def __init__(self, skip: int = 0, limit: int = 10):
        self.skip = skip
        self.limit = limit

@app.get("/items")
def list_items(p: PaginationParams = Depends()):
    return {"skip": p.skip, "limit": p.limit}
```

类依赖的好处是**把一组相关参数打包成一个有名字的对象**，并在 `__init__` 里做一次加工
（比如把 `limit` 夹到上限、算出 `offset`）。参数校验照样能用注解声明：

```python
from typing import Annotated
from fastapi import Header

class UserQuery:
    def __init__(self, x_token: Annotated[str, Header()]):
        self.token = x_token

@app.get("/query")
def user_query(q: UserQuery = Depends()):
    return {"token": q.token}
```

### `Annotated` 写法

`str = Depends(get_db)` 与 `Annotated[str, Depends(get_db)]` 等价，但后者把
**类型**和**依赖来源**分开写，IDE 与类型检查器看得更清楚：

```python
from typing import Annotated

PaginationDep = Annotated[dict, Depends(get_pagination)]

@app.get("/items")
def list_items(params: PaginationDep):
    return {"params": params}
```

真正的收益在 `PaginationDep` 这一行：它是一个**带依赖的类型别名**，
十来个路由共用一个 `PaginationDep`，改约束时只改一处。

| 写法 | 类型信息 | 依赖信息 | 复用 | 适用 |
| --- | --- | --- | --- | --- |
| `q: str = Depends(f)` | 参数上 | 参数上 | 只复用 `f` | 一次性依赖 |
| `Annotated[str, Depends(f)]` | 参数上 | 参数上 | 只复用 `f` | 官方推荐，类型检查更友好 |
| `X = Annotated[T, Depends(f)]` 别名 | 别名里 | 别名里 | 复用整套 | 仓库里多个路由共用 |
| 类 + `Depends()` | `__init__` 里 | `__init__` 里 | 复用整套 | 参数要加工、要打包 |

> 💡 **提示**：1.9 里 `Query`、`Path`、`Header` 用的是同一套 `Annotated` 机制。
> 记住一句话就够：**`Annotated` 是「类型 + 元信息」的容器，`Depends` 只是元信息的一种**。

## 1.11.6 依赖的执行顺序与生命周期

### setup 自上而下，teardown 自下而上

素材给了一份十行的执行顺序示例，内容是对的。用它说明「栈式清理」：

```python
def get_db():
    print("1. [DB] Setup")
    try:
        yield "DB_Session"
        print("9. [DB] yield 之后：提交事务")
    finally:
        print("10. [DB] Teardown: 关闭连接")

def get_cache():
    print("2. [Cache] Setup")
    try:
        yield "Cache_Connection"
        print("7. [Cache] yield 之后：写回缓存")
    finally:
        print("8. [Cache] Teardown: 断开缓存")

def get_current_user(db=Depends(get_db), cache=Depends(get_cache)):
    print("3. [User] Setup")
    try:
        yield f"User_Data ({db}, {cache})"
        print("5. [User] yield 之后：更新活跃时间")
    finally:
        print("6. [User] Teardown: 清理用户资源")

@app.get("/profile")
def user_profile(user=Depends(get_current_user)):
    print("4. [Route] 路由主逻辑")
    return {"profile": user}
```

```text
# 服务端输出（已实跑核对，与素材给的顺序一致）
1. [DB] Setup
2. [Cache] Setup
3. [User] Setup
4. [Route] 路由主逻辑
5. [User] yield 之后：更新活跃时间
6. [User] Teardown: 清理用户资源
7. [Cache] yield 之后：写回缓存
8. [Cache] Teardown: 断开缓存
9. [DB] yield 之后：提交事务
10. [DB] Teardown: 关闭连接
```

规律一句话：**最后拿到的资源，最先归还**（后进先出，LIFO）。
这不是设计者的偏好，而是必然——`get_current_user` 的清理代码在拿到 `db` 和 `cache` 之后才可能运行，
所以它的 `yield` 必须比两者都晚进入、比两者都早退出。

> 💡 **提示**：这个「栈」解释了为什么依赖清理的顺序**看起来像倒放**。
> 排错时如果发现「日志里连接先关、会话后关」，先检查是不是把两个依赖的父子关系写反了。

### 依赖、中间件、后台任务的完整次序

这一条官方文档讲了两句，素材没提，但线上排错非常依赖它：

- 「如果有带 `yield` 的依赖，退出代码会在中间件之后运行。」
- 「如果有后台任务，它们会在所有中间件之后运行。」

实跑（连跑三次结果一致）确认了完整次序：

```python
# 一次请求里同时有：中间件、yield 依赖、后台任务
@app.get("/")
def root(d=Depends(dep), bg: BackgroundTasks = None):
    bg.add_task(job)
    return {"ok": True}
```

```text
中间件：请求前
依赖 setup
路由
中间件：响应后
后台任务
依赖 yield 之后（提交）
依赖 finally（关闭）
```

两处值得记住：

1. **中间件的「响应后」早于依赖的清理**。想在响应头里写「本次耗时」可以，
   但**不能**指望在这里读到依赖的收尾结果（那时数据库还没提交）。
2. **后台任务早于依赖清理**。后台任务里如果用了同一条数据库连接，它跑的时候连接还活着；
   但如果它自己去获取新连接，就要注意连接池上限。

## 1.11.7 全局依赖与批量认证

`dependencies=[Depends(...)]` 可以把依赖挂到**一批**路由上，有三种挂载点：

```python
from fastapi import FastAPI, APIRouter, Depends
from fastapi.security import HTTPBearer

security = HTTPBearer()

def verify_api_key(cred=Depends(security)):
    if cred.credentials != "my-secret-key":
        raise HTTPException(status_code=403, detail="无效的 API Key")

# ① 整个应用
app = FastAPI(dependencies=[Depends(verify_api_key)])

# ② 一组路由（1.9 的 APIRouter）
admin = APIRouter(prefix="/admin", dependencies=[Depends(verify_api_key)])

# ③ 单个路由
@app.get("/items", dependencies=[Depends(verify_api_key)])
def read_items():
    return ["item1", "item2"]
```

### 三种挂载点的取舍

| 挂载点 | 生效范围 | 典型用途 |
| --- | --- | --- |
| `FastAPI(dependencies=[...])` | 全部路由，**包括文档页** | 全局审计、内部系统的整体鉴权 |
| `APIRouter(dependencies=[...])` | 该路由器下的所有路由 | 管理端整体需要管理员身份 |
| 路由的 `dependencies=[...]` | 单个路由 | 少量例外 |

> ⚠️ **注意**：全局依赖**不作用于文档路由**（这一点与不少教程的说法相反）。
> 实测（FastAPI 0.136）：挂上「必须带 API Key」的全局依赖后，
> `/items` 返回 403，而 `/docs`、`/redoc`、`/openapi.json` 依旧 200。
> 原因是文档路由不是用装饰器注册的路径操作，不在全局依赖的覆盖范围内。
> 所以**不要指望用全局依赖顺带把文档一并发保护起来**：
> 真要让文档也要凭证，用中间件卡（中间件包住整个 ASGI 应用，实测有效），
> 或干脆在生产环境关掉文档（见 1.9.1）。

### 多个依赖的顺序

同一个路由上写多个依赖时，**按声明顺序依次执行**，前面失败后面不执行。
这正是 RBAC（基于角色的访问控制）需要的语义：

```python
def verify_login(token: str = "valid_token"):
    if token != "valid_token":
        raise HTTPException(status_code=401, detail="未登录")
    return {"user_id": 1}

def verify_admin(token: str = "admin_token"):
    if token != "admin_token":
        raise HTTPException(status_code=403, detail="非管理员")
    return {"role": "admin"}

@app.get("/admin/panel")
def admin_panel(admin=Depends(verify_admin), user=Depends(verify_login)):
    return {"admin": admin, "user": user}
```

```text
# 未登录用户访问：401（不是 403）
$ curl -H "token: wrong" "http://127.0.0.1:8000/admin/panel"
{"detail":"未登录"}
```

顺序为什么重要？**401 与 403 的语义不同**：401 是「你没证明你是谁」，
403 是「知道你是谁，但你没权限」。如果先查管理员权限，匿名用户会收到 403——
这等于告诉攻击者「这个接口存在且需要管理员」，属于信息泄露。

> 🎯 **面试**：被问「401 和 403 怎么选」时，别只答状态码定义。
> 加上一句「处理顺序上应先认证再鉴权，否则匿名请求会拿到 403，泄露接口存在性」，
> 分数立刻不同。

### 批量和单点混用

路由自己声明的依赖与全局依赖**都会执行**，且全局的在前。所以可以：

```python
app = FastAPI(dependencies=[Depends(verify_token)])   # 所有路由都要登录

@app.delete("/posts/{post_id}", dependencies=[Depends(require_owner)])
def delete_post(post_id: int, user=Depends(get_current_user)):
    ...        # 先全局登录校验，再本路由的归属校验
```

**全局依赖拿不到路由的返回值**——它没有参数接收处（除非它自己声明同名路径参数，
或者通过 `request.state` 传递，见下一节）。需要「上一步的结果」时，用父子依赖，不要用全局依赖。

## 1.11.8 依赖缓存、状态共享与测试替换

### 依赖缓存：同一请求内只算一次

在**同一次请求**中，若多处引用**同一个、参数完全相同**的依赖，FastAPI 只执行它一次，
并把结果复用：

```python
calls = []

def heavy():
    calls.append(1)
    return {"n": len(calls)}

@app.get("/c")
def c(a=Depends(heavy), b=Depends(heavy)):
    return {"同一对象": a is b, "依赖执行次数": len(calls)}
```

```text
$ curl "http://127.0.0.1:8000/c"
{"同一对象":true,"依赖执行次数":1}
```

这条特性在依赖树里更重要：`get_current_user` 与 `get_db` 被多个上层依赖同时需要时，
数据库会话**只会创建一次**，不会一次请求开出三条连接。

关掉缓存（确实需要每次重新执行）用 `use_cache=False`：

```python
@app.get("/x")
def x(t1=Depends(now, use_cache=False), t2=Depends(now, use_cache=False)):
    ...        # t1 与 t2 是两个不同时刻
```

> ⚠️ **注意**：缓存的**作用域是单次请求**，请求结束即失效。
> 它和 `functools.lru_cache` 不是一回事，别拿它当「全进程缓存」用。

```python
import functools

@functools.lru_cache(maxsize=1)      # 进程级：所有请求共用一份
def load_config():
    ...

def cached_dep():                    # 请求级：每个请求算一次
    return load_config()
```

| | `Depends` 缓存 | `lru_cache` |
| --- | --- | --- |
| 生效范围 | 单次请求 | 整个进程 |
| 键 | 依赖函数 + 参数 | 函数参数 |
| 适合 | 会话、当前用户 | 配置、词表等只读数据 |
| 风险 | 无（随请求销毁） | 数据改了不刷新 |

### 状态共享：`app.state` 与 `request.state`

两个地方都能挂状态，区别在**生命周期**：

- `request.state`：**单次请求**内共享（请求结束即销毁）；
- `app.state`：**整个应用**共享（进程级，常用于存放连接池、配置、限流器）。

素材给了一个「用 `app.state` 做自增请求 ID」的例子，写法是：

```python
# ❌ 素材写法：在 Starlette 1.6 上不成立
def get_request_id(request: Request):
    if "request_id" not in request.app.state.__dict__:
        request.app.state.request_id = 0
    request.app.state.request_id += 1
    return request.app.state.request_id
```

```text
$ curl .../ ; curl .../ ; curl .../
{"request_id":1} {"request_id":1} {"request_id":1}     # 每次都被重置
```

原因是 Starlette 的 `State` 把值存在内部的 `_state` 字典里，
`state.__dict__` 里只有 `_state` 这一个键——所以那句 `not in` **永远成立**，
每次请求都把计数重置成 0。实测：

```text
state.__dict__ 内容: ['_state']   |  _state: {'request_id': 1}
```

```python
# ✅ 修正写法
def get_request_id(request: Request):
    if not hasattr(request.app.state, "request_id"):
        request.app.state.request_id = 0
    request.app.state.request_id += 1
    return request.app.state.request_id
```

```text
{"request_id":1} {"request_id":2} {"request_id":3}
```

> ⚠️ **素材纠错（照抄会静默失效）**：判定 `State` 上有没有某个属性要点用 `hasattr()`，
> 不能用 `state.__dict__`。后者在 Starlette 1.6 恒为真，代码**不报错、也不生效**——
> 计数器永远返回 1。这类「静默失效」比抛异常难查得多：接口一直有响应，只是数字不对。

### 测试替换：`dependency_overrides`

这是 1.11.1 里说的「可测试」的落地方式。测试时把真依赖换成替身，**路由代码一行不改**：

```python
def real():
    return "真依赖"

def fake():
    return "测试替身"

app = FastAPI()

@app.get("/")
def r(d=Depends(real)):
    return {"d": d}
```

```python
def test_it():
    client = TestClient(app)
    assert client.get("/").json() == {"d": "真依赖"}      # 覆盖前

    app.dependency_overrides[real] = fake
    assert client.get("/").json() == {"d": "测试替身"}    # 覆盖后

    app.dependency_overrides.clear()                     # ⚠️ 用完必须清
```

替换是**按依赖函数对象**匹配的，所以**同一个依赖函数**在整棵依赖树里的所有引用会一起被替换——
包括那些作为别人子依赖引用的地方。这正是「一个 fake 顶掉整条链路」的原因，
也是它比手工 monkeypatch 干净的地方。

> 🔥 **常见坑**：忘了 `dependency_overrides.clear()`。
> 覆盖是挂在 `app` 上的全局状态，测试之间会互相污染，
> 表现为「单独跑通过、整包跑失败」这种最费时间的 bug。
> 修法：放到 `pytest` 的 fixture 里，`yield` 之后清理。

## 1.11.9 中间件：洋葱模型与执行顺序

依赖是「某些路由需要的东西」，**中间件（Middleware）** 是「每个请求/响应都要走一遍的东西」：
它在请求到达任何路由**之前**执行，在响应返回给客户端**之前**再执行一次。

```python
import time
from fastapi import FastAPI, Request

app = FastAPI()

@app.middleware("http")
async def add_process_time(request: Request, call_next):
    start = time.perf_counter()          # ← 请求前
    response = await call_next(request)  # ← 交给下一层（可能是别的中间件，最后是路由）
    elapsed = time.perf_counter() - start
    response.headers["X-Process-Time"] = f"{elapsed:.4f}s"
    return response                      # ← 响应后
```

三个要点：

- `call_next` 是「继续往下走」的开关。**不调用它，请求永远到不了路由**。
- `call_next` **之前的代码**在请求阶段执行，**之后的代码**在响应阶段执行。
- 中间件必须是 `async def`（`BaseHTTPMiddleware` 会替你处理，见下节）。

### 洋葱模型

多个中间件是层层包裹的，像洋葱。以两个中间件 A、B 为例：

```python
@app.middleware("http")
async def mw_a(request: Request, call_next):
    print("A 请求前")
    resp = await call_next(request)
    print("A 响应后")
    return resp

@app.middleware("http")
async def mw_b(request: Request, call_next):
    print("B 请求前")
    resp = await call_next(request)
    print("B 响应后")
    return resp

@app.get("/")
async def root():
    print("路由")
    return {"ok": True}
```

```text
# 实跑输出
B 请求前 → A 请求前 → 路由 → A 响应后 → B 响应后
```

### 素材的顺序说明是反的

讲义写「先注册的中间件在外层」「响应返回顺序与注册顺序相反」，并给出
`A 请求前 → B 请求前 → 路由 → B 响应后 → A 响应后` 作为上面这段代码的结果。**实测不是这样。**

官方文档的原话是：

> When you add multiple middlewares using either `@app.middleware()` decorator or
> `app.add_middleware()` method, each new middleware wraps the application, forming a stack.
> **The last middleware added is the outermost, and the first is the innermost.**
> On the request path, the outermost middleware runs first. On the response path, it runs last.

即：**最后添加的在最外层，最先添加的在最内层**。请求路径上外层先跑，响应路径上外层最后跑。
源码也印证了这一点：`add_middleware` 用 `user_middleware.insert(0, ...)` 入栈
（后添加的排在最前），而构建中间件栈时用 `reversed(middleware)` 逐层包裹
（排在最前的最后被包裹，因而成为最外层）。

> ⚠️ **素材纠错（按素材的说明配置会得到相反的嵌套）**：讲义给出「建议顺序（从外到内）：
> TrustedHost → CORS → HTTPSRedirect → 自定义 → GZip」，并按「先注册在外层」叙述。
> 在 FastAPI 0.136 / Starlette 1.6 上，要让 `TrustedHostMiddleware` 处在最外层，
> 必须**最后**注册它。第 1.11.12 节给出了按实测重写的注册顺序。

### 顺序为什么重要

中间件是**唯一能决定「别的中间件能不能看到这个请求」**的位置。三个具体后果：

1. **认证放在最外层**：未认证的请求应在进入其他中间件（尤其是写日志、算耗时）之前就被拒掉，
   否则攻击流量会灌满日志。
2. **CORS 必须能覆盖错误响应**：跨域请求被自己的认证中间件拒掉时，
   浏览器需要 `Access-Control-Allow-Origin` 才能把错误读出来给前端；
   CORS 若在内层，这个头就丢了，前端只能看到一个没有信息的网络错误。
3. **压缩必须在最外层的内侧、但在响应已定型之后**：压缩改的是响应体字节，
   它必须排在所有「会改响应体」的中间件之后（即更内层），否则压缩过的字节会被再改一次。

## 1.11.10 三种定义方式与常用内置中间件

### 三种定义方式的取舍

| 方式 | 代码量 | 能否带参数 | 性能 | 适用 |
| --- | --- | --- | --- | --- |
| `@app.middleware("http")` 装饰器 | 最少 | 不能 | 中 | 一次性、无配置的逻辑（计时、简单日志） |
| 继承 `BaseHTTPMiddleware` | 中 | **能** | 中 | 大多数场景；需要按环境传配置时 |
| 纯 ASGI 类 | 多 | 能 | **最高** | 需要直接操作 `scope`、对性能敏感 |

**方式二：`BaseHTTPMiddleware`（最常用）**

```python
from starlette.middleware.base import BaseHTTPMiddleware
from fastapi import FastAPI, Request

class AuthMiddleware(BaseHTTPMiddleware):
    def __init__(self, app, header_value: str = "default"):
        super().__init__(app)          # ⚠️ 必须先调父类构造函数
        self.header_value = header_value

    async def dispatch(self, request: Request, call_next):
        print(f"收到请求: {request.method} {request.url.path}")
        response = await call_next(request)
        response.headers["X-Custom-Auth"] = self.header_value
        return response

app = FastAPI()
app.add_middleware(AuthMiddleware, header_value="MyAuth")   # 注册时传参
```

`super().__init__(app)` 不能省。漏了它，中间件会在启动时报
`AttributeError` 或直接不生效——这是继承 `BaseHTTPMiddleware` 最常见的错误。

**方式三：纯 ASGI**

ASGI 中间件就是一个 `async def __call__(scope, receive, send)`。
它不构造 `Request` / `Response` 对象，直接操作原始三元组，所以最快、也最难写：

```python
import typing
from starlette.types import ASGIApp, Receive, Scope, Send
from starlette.requests import HTTPConnection
from starlette.responses import PlainTextResponse

class IPWhiteListMiddleware:
    def __init__(self, app: ASGIApp, allow_ips: typing.Sequence[str] = ()) -> None:
        self.app = app
        self.allow_ips = allow_ips

    async def __call__(self, scope: Scope, receive: Receive, send: Send) -> None:
        conn = HTTPConnection(scope=scope)
        client_ip = conn.client.host if conn.client else ""
        if self.allow_ips and client_ip not in self.allow_ips:
            response = PlainTextResponse("IP 不在白名单内", status_code=403)
            await response(scope, receive, send)     # 自己把响应发出去
            return
        await self.app(scope, receive, send)         # 放行
```

> ⚠️ **注意**：`scope` 只有在 **HTTP 请求**时才含 `"http"` 类型；
> 同一段代码也会收到 `lifespan` 与 `websocket` 事件。
> 纯 ASGI 中间件里如果直接访问 `scope["headers"]` 之类的键而不判断 `scope["type"]`，
> 启动阶段就会崩。这也是 `BaseHTTPMiddleware` 存在的理由——它把这些判断做掉了。

> 🔥 **常见坑（`BaseHTTPMiddleware` 的已知限制）**：它会为每个请求额外包一层
> 「请求任务 + 响应流」，在某些版本上会导致：后台任务在响应**完成后**才被调用、
> 以及在依赖里 `raise` 的异常被视为「响应已开始」而无法变成 500。
> 官方文档在 Starlette 的 `BaseHTTPMiddleware` 一节里列出了这些限制。
> 遇到行为诡异（异常被吞、流式响应中断）时，第一反应应该是换纯 ASGI 写法试试。

### 四个内置中间件

**① `CORSMiddleware`——跨域**

跨域的原理与判定表在 1.8.10 已经讲过，这里只讲**怎么配**：

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:3000"],   # 允许的来源
    allow_credentials=True,                    # 允许携带 Cookie
    allow_methods=["GET", "POST", "PUT", "DELETE"],
    allow_headers=["Authorization", "Content-Type"],
    max_age=600,                               # 预检结果缓存 600 秒
)
```

浏览器对「复杂请求」（`PUT` / `DELETE` / 带自定义头）会先发一个 `OPTIONS` 预检请求。
**这个请求由中间件自动应答，你不需要写 `OPTIONS` 路由**：

```text
$ curl -X OPTIONS "http://127.0.0.1:8000/api" \
    -H "Origin: http://localhost:3000" \
    -H "Access-Control-Request-Method: GET" \
    -H "Access-Control-Request-Headers: Authorization"
200
access-control-allow-origin: http://localhost:3000
access-control-allow-credentials: true
access-control-allow-methods: GET, POST
access-control-max-age: 600
```

`max_age=600` 就是那个「预检结果缓存 600 秒」——省掉的是浏览器的重复预检，不是服务端的工作。

**关于 `allow_origins=["*"]` + `allow_credentials=True`**：讲义说这是「❌ 错误，
必须指定具体域名」。实测（Starlette 1.6）**它不报错，而是回显请求来源**：

```text
# allow_origins=["*"] 且 allow_credentials=True，请求头 Origin: http://evil.com
200
access-control-allow-origin: http://evil.com      ← 回显了任意来源
access-control-allow-credentials: true
```

> ⚠️ **素材纠错（这是安全问题，不是配置问题）**：讲义把它描述成「写法不对」，
> 仿佛会报错提醒你。实际上中间件为了兼容 `credentials`，会**把任意来源原样写回
> `Access-Control-Allow-Origin`** 并放行凭证——等于对**任何网站**开放了带 Cookie 的跨域访问。
> 代码不会报错，接口照常工作，问题只在浏览器端别人能否拿到你的用户数据。
> 所以：只要用了 `allow_credentials=True`，`allow_origins` **必须**是显式域名列表。

生产环境按环境变量切换来源：

```python
import os

env = os.getenv("ENV", "development")
if env == "production":
    origins = ["https://zhizhou.example"]          # 显式列出，且不带路径
else:
    origins = ["http://localhost:3000", "http://localhost:8080"]

app.add_middleware(CORSMiddleware, allow_origins=origins, allow_credentials=True,
                   allow_methods=["GET", "POST", "PUT", "DELETE"],
                   allow_headers=["Authorization", "Content-Type"])
```

**② `GZipMiddleware`——响应体压缩**

```python
from fastapi.middleware.gzip import GZipMiddleware

app.add_middleware(GZipMiddleware, minimum_size=1000)
```

它只在**三个条件同时满足**时压缩：客户端发了 `Accept-Encoding: gzip`、
响应体大于 `minimum_size`、内容是文本类型（JSON/HTML/XML；图片视频本身已压缩，不处理）。
实跑验证阈值确实生效：

```text
$ curl -H "Accept-Encoding: gzip" .../small      # 响应 10 字节
Content-Encoding: 无
$ curl -H "Accept-Encoding: gzip" .../big        # 响应约 5.6 KB
Content-Encoding: gzip
```

`minimum_size` 的建议值要看响应体分布：

| 场景 | 建议值 | 原因 |
| --- | --- | --- |
| API 接口 | 1000–2000 | 小响应压缩反而更费 CPU |
| 网站 / 博客（HTML 大） | 500–1000 | 页面收益明显 |
| 实时小数据 | 关掉或 5000+ | 频繁小包不值得 |

> 🔥 **常见坑**：**应用层与 CDN 层同时压缩是纯浪费 CPU**。
> 只在一层启用即可。要「禁用应用层压缩」就**不要注册这个中间件**，
> 而不是把 `minimum_size` 调到 100000——后者会让超大响应仍被压缩，逻辑更绕。

`brotli` 装上后 Starlette 会自动优先用它（压缩率比 gzip 高约 15%–25%）：

```bash
pip install brotli
```

**③ `HTTPSRedirectMiddleware`——强制 HTTPS**

```python
from fastapi.middleware.httpsredirect import HTTPSRedirectMiddleware

app.add_middleware(HTTPSRedirectMiddleware)
```

```text
$ curl -I "http://127.0.0.1:8000/"
307 Temporary Redirect
location: https://127.0.0.1:8000/
```

**307 而不是 301**：307/308 会保留原请求方法，`POST` 不会退化成 `GET`。
如果这里用了 301，客户端发 `POST` 会被重定向成 `GET`，请求体丢失，这类 bug 极难定位。

> ⚠️ **注意**：这个中间件**只处理 HTTP 协议**，不会把 `ws://` 重定向成 `wss://`。
> WebSocket 的安全传输需要客户端直接连 `wss://`，或在 Nginx 层做一次升级重定向。

部署建议：**只在一层做重定向**。Nginx 与应用层同时配，会得到
`HTTP → HTTPS → HTTP → HTTPS` 的无限循环：

```nginx
# Nginx 层（推荐）
server {
    listen 80;
    server_name zhizhou.example;
    return 301 https://$server_name$request_uri;
}
server {
    listen 443 ssl;
    ssl_certificate     /path/cert.pem;
    ssl_certificate_key /path/key.pem;
    location / { proxy_pass http://127.0.0.1:8000; }
}
```

物理机 / Nginx 已存在 → 放 Nginx 层；容器内、没有前置代理 → 放应用层。

**④ `TrustedHostMiddleware`——主机头校验**

```python
from fastapi.middleware.trustedhost import TrustedHostMiddleware

app.add_middleware(
    TrustedHostMiddleware,
    allowed_hosts=["zhizhou.example", "*.zhizhou.example", "localhost"],
)
```

```text
$ curl -I -H "Host: zhizhou.example" http://127.0.0.1:8000/
200 OK
$ curl -I -H "Host: evil.com" http://127.0.0.1:8000/
400 Bad Request
Invalid host header
```

它拦的是**主机头攻击**：攻击者伪造 `Host` 头，利用「服务端用 `Host` 头拼绝对 URL」的习惯，
把发到用户邮箱的重置密码链接指向自己的域名；或用它污染 CDN/WAF 的缓存。

通配符规则：`*.zhizhou.example` 匹配 `api.zhizhou.example` 与 `a.b.zhizhou.example`。
`["*"]` 等于不设防，生产环境**不要用**。

> ⚠️ **素材纠错（响应体不是 JSON）**：讲义给出的拦截响应是
> `{"detail": "Invalid host header"}`。实测返回的是**纯文本** `Invalid host header`，
> 不是 JSON。前端若按 `response.json()` 解析这个 400，会再抛一个解析错误，
> 把真正的报错盖掉。判断状态码即可，不要依赖这里的响应体结构。

> 💡 **提示**：反向代理下，这个中间件默认只校验**原始 `Host` 头**
> （即 Nginx 发给 FastAPI 的那个，通常是 `127.0.0.1`）。
> 想校验客户端真实域名（`X-Forwarded-Host`），要 `FastAPI(proxy_headers=True)`
> 并另写校验逻辑——但更简单的做法是把它交给 Nginx 的 `server_name`。

## 1.11.11 自定义中间件实战

### 请求耗时统计

```python
import time
from starlette.middleware.base import BaseHTTPMiddleware

class TimeMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        start = time.perf_counter()
        response = await call_next(request)
        response.headers["X-Process-Time"] = f"{time.perf_counter() - start:.4f}s"
        return response
```

```text
$ curl -I "http://127.0.0.1:8000/"
X-Process-Time: 0.0523s
```

用 `time.perf_counter()` 而不是 `time.time()`：前者是**单调时钟**，
不受系统时间调整（NTP 校时、夏令时）影响，测间隔更准。

### 请求超时控制

```python
import asyncio
from fastapi.responses import JSONResponse

@app.middleware("http")
async def timeout_middleware(request: Request, call_next):
    try:
        task = asyncio.create_task(call_next(request))
        return await asyncio.wait_for(task, timeout=5.0)
    except asyncio.TimeoutError:
        return JSONResponse(status_code=504, content={"detail": "请求超时"})
```

讲义强调「必须显式 `create_task`，确保异步超时生效」。实测在
FastAPI 0.136 / Starlette 1.6 上，**两种写法都能正确返回 504**：

```text
超时中间件（create_task 版）: /slow → 504, /fast → 200
超时中间件（直接 await 版） : /slow → 504, /fast → 200
```

在旧版本 Starlette 上直接 `wait_for(call_next(request))` 曾出现「取消不掉」的问题，
`create_task` 版本就是当年的规避写法；现在它只是**更显式**，不是必需。

> ⚠️ **注意**：中间件的超时**只能保住「不让客户端干等」**，
> 它无法真正杀掉已经在执行的同步代码。如果 `/slow` 里是
> `def`（同步）路由，它跑在线程池里，超时后线程仍在跑完——见第 1.7 节的
> 「同步与异步路由的分工」。真正的超时保护要有另外的手段（进程隔离、上游限流）。

### 安全响应头

```python
class SecurityHeadersMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request, call_next):
        response = await call_next(request)
        response.headers["X-Content-Type-Options"] = "nosniff"
        response.headers["X-Frame-Options"] = "DENY"
        return response
```

`nosniff` 阻止浏览器把「声明为 JSON 的响应」按 HTML 解析（防内容嗅探型 XSS），
`DENY` 禁止本站被嵌进 iframe（防点击劫持）。这类「给所有响应加同一批头」的需求，
中间件是唯一合适的位置。

### 请求限流

限流常用 `slowapi`（基于 `limits`）：

```bash
pip install slowapi
```

```python
from slowapi import Limiter
from slowapi.util import get_remote_address
from slowapi.middleware import SlowAPIMiddleware
from slowapi.errors import RateLimitExceeded

limiter = Limiter(key_func=get_remote_address)     # 按客户端 IP 限流
app.state.limiter = limiter                        # slowapi 要求挂到 app.state
app.add_middleware(SlowAPIMiddleware)

@app.post("/login")
@limiter.limit("5/minute")                         # 登录接口从严：防撞库
async def login(request: Request):
    return {"message": "login"}

@app.get("/public/data")
@limiter.limit("100/minute")                       # 公开数据放宽
async def public_data(request: Request):
    return {"data": "public"}
```

> ⚠️ **注意**：本段代码**未在本机实跑**（环境未安装 `slowapi`），只保证与官方文档一致。
> 另外被装饰的路由**必须有 `request: Request` 参数**，否则 `slowapi` 拿不到请求对象。

超过限制时返回 `429 Too Many Requests`，并带 `Retry-After` 头告诉客户端多久后重试。
把 `429` 统一改造成本项目自己的响应格式，用异常处理器（见 1.14）：

```python
@app.exception_handler(RateLimitExceeded)
async def rate_limit_handler(request: Request, exc: RateLimitExceeded):
    retry_after = exc.retry_after or 60
    return JSONResponse(
        status_code=429,
        content={"error": "请求过于频繁", "retry_after": retry_after},
        headers={"Retry-After": str(retry_after)},   # HTTP 规范要求是字符串
    )
```

> ⚠️ **注意（多实例）**：默认的限流计数存在**进程内存**里。
> 部署 3 个副本后，每个副本各算各的，实际放行量变成 3 倍。
> 多实例必须用共享存储：

```bash
pip install redis
```

```python
import redis
from slowapi import Limiter
from slowapi.storage.redis_storage import RedisStorage

redis_client = redis.Redis(host="localhost", port=6379, db=0,
                           decode_responses=True, socket_timeout=5)
limiter = Limiter(key_func=get_remote_address, storage=RedisStorage(redis_client))
```

**限流键的选择**：按 IP 会被 NAT 后的整栋楼共用一个额度；
按用户更公平，但**必须先用解析后的用户 ID，而不是原始 Token**——
把 Token 当键，等于把它写进 Redis 的键名里（泄露风险），
且 Token 一刷新额度就重置，限流形同虚设。解析失败时降级为按 IP。

## 1.11.12 中间件 vs 依赖注入：选型与注册顺序

### 选型对比

| 维度 | 中间件 | 依赖注入 |
| --- | --- | --- |
| 生效范围 | 默认全局（可按路径部分生效） | 精准指定单个/多个路由 |
| 执行时机 | 请求进入与响应返回（在路由之外） | 路由执行之前 |
| 拿到路由信息 | 只有 `request`，拿不到路径参数与路由函数 | 能声明路径参数、用 `Depends` 组合 |
| 错误处理 | 需手动捕获并构造响应 | 直接 `raise HTTPException`，框架自动格式化 |
| 能否改响应体 | 能（压缩、替换内容） | 不能（只提供数据） |
| 适合 | 跨域、压缩、限流、请求 ID、耗时 | 认证、权限、参数打包、资源管理 |

一句话判据：

> **不关心「这是哪个路由」，且要对响应做手脚** → 中间件；
> **关心路由上下文、错误要"正常"抛出** → 依赖注入。

这条判据来自一个真实差异：在中间件里 `raise HTTPException` **不会**被 FastAPI 的异常处理器
接住（那时请求还在框架外层），必须自己 `except` 并构造响应；而依赖里 `raise` 会得到标准的
`{"detail": ...}` 响应。认证、权限这类「失败就是 401/403」的逻辑用依赖写更省事，也更准确。

### 注册顺序（按实测重写）

前提：**后注册的在外层**，请求路径上外层先执行。

```python
from fastapi.middleware.trustedhost import TrustedHostMiddleware
from fastapi.middleware.cors import CORSMiddleware
from fastapi.middleware.httpsredirect import HTTPSRedirectMiddleware
from fastapi.middleware.gzip import GZipMiddleware

app = FastAPI()

# 从内到外的注册顺序（最内层先写）
app.add_middleware(GZipMiddleware, minimum_size=1000)        # 最内层：最后改响应体
app.add_middleware(RequestIDMiddleware)                      # 请求 ID：日志要用
app.add_middleware(HTTPSRedirectMiddleware)                  # 不安全的请求尽早跳走
app.add_middleware(CORSMiddleware, allow_origins=ORIGINS,    # 让错误响应也带上 CORS 头
                   allow_credentials=True, allow_methods=["*"], allow_headers=["*"])
app.add_middleware(TrustedHostMiddleware, allowed_hosts=HOSTS)   # 最外层：最早挡掉伪造 Host
```

对应的请求路径顺序就是：

```text
TrustedHost → CORS → HTTPSRedirect → 请求 ID → GZip → 路由
```

即：**先用 `TrustedHost` 把伪造 Host 挡在门外，再给响应加 CORS 头，最后才做内部处理**。

> ⚠️ **注意**：讲义给的是「从外到内：TrustedHost → CORS → HTTPSRedirect → 自定义 → GZip」。
> 那个**从外到内**的名单本身是对的，错的是「怎么注册才能得到它」——
> 由于最后注册的在外层，**实际代码里要把这个名单倒过来写**，就是上面那段。

### 三条实践建议

1. **CORS 要能覆盖错误响应**，所以它得在「会拒绝请求的中间件」之外层
   （例子里的顺序：CORS 在 HTTPSRedirect 与请求 ID 之外）。
2. **谨慎使用全局依赖**：它作用到所有路由（含文档页），且没有「按路由豁免」的开关。
   需要豁免时用 `APIRouter` 分组，而不是在依赖内部判断路径字符串。
3. **敏感操作放依赖注入**：中间件对所有请求可见、拿不到路由上下文，
   「这个用户能不能改这篇文章」这类判断只有在依赖里才能写清楚。

## 1.11.13 综合示例：知舟的请求上下文与限流

把本章的机制组装成一个能跑的骨架：**请求 ID**（中间件）+ **限流**（中间件）+
**当前用户与资源**（依赖）+ **全局鉴权**（全局依赖）。

```python
# app/middleware.py
import time
import uuid
from collections import defaultdict, deque
from starlette.middleware.base import BaseHTTPMiddleware
from fastapi import Request
from fastapi.responses import JSONResponse

class RequestContextMiddleware(BaseHTTPMiddleware):
    """给每个请求分配 request_id，写进 state 与响应头，并记录耗时。"""

    async def dispatch(self, request: Request, call_next):
        request_id = request.headers.get("X-Request-ID") or uuid.uuid4().hex[:12]
        request.state.request_id = request_id
        start = time.perf_counter()

        response = await call_next(request)

        response.headers["X-Request-ID"] = request_id
        response.headers["X-Process-Time"] = f"{time.perf_counter() - start:.4f}s"
        return response

class RateLimitMiddleware(BaseHTTPMiddleware):
    """滑动窗口限流：同一客户端在 window 秒内最多 limit 次（仅演示，单进程）。"""

    def __init__(self, app, limit: int = 60, window: float = 60.0):
        super().__init__(app)
        self.limit = limit
        self.window = window
        self.hits: dict[str, deque[float]] = defaultdict(deque)

    async def dispatch(self, request: Request, call_next):
        if request.url.path.startswith("/admin"):
            return await call_next(request)          # 管理端不在此限流

        client = request.client.host if request.client else "unknown"
        now = time.monotonic()
        bucket = self.hits[client]
        while bucket and now - bucket[0] > self.window:
            bucket.popleft()                          # 丢掉窗口外的记录

        if len(bucket) >= self.limit:
            retry_after = int(self.window - (now - bucket[0])) + 1
            return JSONResponse(
                status_code=429,
                content={"detail": "请求过于频繁", "request_id": request.state.request_id},
                headers={"Retry-After": str(retry_after)},
            )

        bucket.append(now)
        return await call_next(request)
```

```python
# app/deps.py
from fastapi import Depends, Header, HTTPException

def get_db():
    """借出的会话，无论成败都要关。"""
    session = {"id": "session-1"}
    try:
        yield session
        session["committed"] = True          # 只有正常路径会走到这里
    except Exception:
        session["rolled_back"] = True        # 异常时确实回滚了
        raise
    finally:
        session["closed"] = True

def get_current_user(x_token: str = Header(..., alias="X-Token"), db=Depends(get_db)):
    if not x_token.startswith("token-"):
        raise HTTPException(status_code=401, detail="无效的认证令牌")
    return {"id": int(x_token.removeprefix("token-")), "db": db}

def require_admin(user=Depends(get_current_user)):
    if user["id"] != 1:
        raise HTTPException(status_code=403, detail="需要管理员权限")
    return user
```

```python
# app/main.py
from fastapi import FastAPI, Depends, Request
from app.middleware import RequestContextMiddleware, RateLimitMiddleware
from app.deps import get_current_user, require_admin

app = FastAPI(title="知舟博客 API")

app.add_middleware(RateLimitMiddleware, limit=5, window=60.0)   # 内层
app.add_middleware(RequestContextMiddleware)                     # 外层：先有 request_id

def audit(request: Request):
    """全局依赖：每个请求都记一条带 request_id 的审计日志。"""
    request.state.audited = True

@app.get("/posts")
def list_posts(request: Request, user=Depends(get_current_user)):
    return {"request_id": request.state.request_id, "user": user["id"], "posts": []}

@app.get("/admin/stats", dependencies=[Depends(audit)])
def admin_stats(user=Depends(require_admin)):
    return {"users": 12, "posts": 340}
```

跑起来之后依次验证四件事：

```python
from fastapi.testclient import TestClient
from app.main import app

client = TestClient(app)

r = client.get("/posts", headers={"X-Token": "token-1", "X-Request-ID": "abc123"})
assert r.status_code == 200
assert r.headers["X-Request-ID"] == "abc123"          # 客户端传的 ID 被沿用
assert r.json()["request_id"] == "abc123"             # 路由能读到同一个 ID

# 没带令牌 → 401（依赖里 raise，框架自动格式化）
assert client.get("/posts").status_code == 422        # X-Token 是必填头

# 普通用户访问管理端 → 403（不是 401：身份有效，权限不够）
r = client.get("/admin/stats", headers={"X-Token": "token-2"})
assert r.status_code == 403 and r.json()["detail"] == "需要管理员权限"

# 管理员 → 200
assert client.get("/admin/stats", headers={"X-Token": "token-1"}).status_code == 200
```

```text
# 实测输出
/posts 带 X-Token 与 X-Request-ID   → 200，响应头回显 X-Request-ID: abc123
/posts 不带 X-Token                 → 422（必填请求头缺失，发生在进入路由之前）
/admin/stats token-2                → 403 {"detail":"需要管理员权限"}
/admin/stats token-1                → 200
```

四个设计点值得记住：

1. **请求 ID 从请求头取、取不到才生成**。这样跨服务链路能串起来（上游服务传下来的 ID 被沿用，而不是各生成一个）。
2. **限流要在请求 ID 之后**吗？反了——上面注册顺序让 `RequestContextMiddleware` 在外层，
   所以 429 响应**也带着 `X-Request-ID`**。被限流的请求同样需要可追踪。
3. **权限分层用「认证依赖 → 鉴权依赖」**，得到 401 与 403 的正确区分。
4. **`get_db` 用 `except` 真回滚**，而不是像素材那样把提交写在 `yield` 之后就不管了。

## 常见坑

- **`Depends` 漏写或加括号**（同一处错误的两面）。现象：参数一直是默认值，传了没生效；或启动即报 `TypeError: 'str' object is not callable`。原因：前者漏写 `Depends`（`params: dict = get_pagination` 被当成默认值是个函数对象的普通参数），后者多写了括号 `Depends(f())` 以致函数在**导入时**就被调用。修法：一律写 `Depends(f)`——传函数本身。`Dict` 类型参数尤其容易漏，因为不写 `Depends` 时它会被当成请求体。
- **路由抛异常导致事务既没提交也没回滚**。现象：接口正常返回错误码，但数据库里没数据（或事务悬空）。原因：「提交事务」写在 `yield` 之后，而异常被抛回 `yield` 处，那里之后的代码**不执行**（第 1.11.3 节实测）。修法：`try: yield db` / `except: rollback; raise` / `finally: close`。
- **中间件里 `raise HTTPException` 变成 500**。现象：本该 401 的请求返回 `Internal Server Error`。原因：中间件在异常处理器之外，框架接不住它的异常（实测确认）。修法：中间件内 `try/except` 后自己返回 `JSONResponse`；或把认证逻辑改成依赖。
- **`allow_origins=["*"]` 配上 `allow_credentials=True`**。现象：前端一切正常，但任何网站都能带 Cookie 读你的接口。原因：中间件会**回显任意来源**而不报错（第 1.11.10 节实测），是静默的越权放行。修法：只要开了 `allow_credentials`，`allow_origins` 必须是显式域名列表。
- **中间件顺序按「先注册在外层」写**。现象：加了两个中间件后认证失效，未登录请求也进了业务逻辑。原因：实际是**后注册的在外层**，认证被包到了最里面。修法：记住「后注册在外」；先想清楚「谁该最先见到请求」，再倒序注册。
- **测试串味 / `app.state` 计数永远从 1 开始**。现象：测试单独跑通过、整包跑失败；或自增请求号每次都重置。原因：前者忘了 `dependency_overrides.clear()`，后者用 `state.__dict__` 判断属性存在性（Starlette 1.6 下恒为真）。修法：覆盖放进 fixture 的 `yield` 之后清理；属性判断用 `hasattr()`。

## 面试视角

> 🎯 **面试**：依赖注入与中间件是「跑过 demo」和「写过项目」的分界线——前者只会背 `Depends` 的用法，
> 后者能讲出清理时机、执行顺序与选型依据。`sources/06-求职冲刺/` 的后端题库把
> 「依赖注入」「中间件」「认证与鉴权」列为 FastAPI 岗位的必问题，落到本章的是下面六问，
> 其中第 2、3 两问区分度最高。

1. **「依赖注入是什么？FastAPI 怎么实现的？」**
   考察点：对机制的理解而非 API 记忆。答题要点：控制反转（IoC）的一种落地；`Depends` 声明依赖，框架递归解析依赖树后把返回值注入参数；与 Spring 的区别在于容器极轻（一个函数调用）。追问通常落在 **`yield` 依赖的清理时机**。
2. **「`yield` 依赖在路由抛异常时会怎样？」**
   考察点：这是最容易背错的一题。答题要点：异常被抛回生成器的 `yield` 处，**`yield` 之后的代码不执行**、`finally` 会执行；所以「提交」必须放在 `try` 里、「回滚」放在 `except` 里。能主动指出「很多教程把这一步写错」是明显加分项。
3. **「中间件的执行顺序是怎样的？」**
   考察点：顺序与安全的关联。答题要点：洋葱模型；**后添加的在最外层**（FastAPI 官方文档原话），请求路径外层先跑、响应路径外层后跑。追问「认证该放哪」→ 放最外层，理由是未认证流量不该灌进日志、也不该走到业务逻辑。
4. **「中间件和依赖注入怎么选？」**
   考察点：技术选型判断力。答题要点：范围（全局 vs 精准）、错误处理（手动构造响应 vs 自动格式化）、能否改响应体。补一句「认证用依赖更合适，因为中间件里 `raise HTTPException` 不会被异常处理器接住（实测变成 500）」。
5. **「401 和 403 的区别？为什么顺序重要？」**
   考察点：安全细节。答题要点：401 是未认证、403 是无权限；先认证再鉴权，否则匿名请求拿到 403 会泄露接口的存在性。
6. **「CORS 预检请求是谁处理的？」**
   考察点：跨域排查经验。答题要点：浏览器自动发的 `OPTIONS`，由 `CORSMiddleware` 应答，不需要写 `OPTIONS` 路由；`max_age` 缓存的是预检结果；`allow_credentials=True` 时来源必须显式列出，用 `*` 会被回显成任意来源（这是安全问题，不是配置错误）。

## 本章小结

1. **依赖注入把「资源创建」从路由里搬到了签名上**，换来可测试、可清理、可组合；
   它是 IoC 的一种轻量实现。
2. `Depends` 的执行是三步：看声明 → 执行依赖函数（递归解析子依赖）→ 注入返回值；
   `Depends` 要的是函数本身，不是调用结果。
3. 带 `yield` 的依赖用 `try/except/finally` 管理资源；**异常时 `yield` 之后的提交不会执行**，
   必须显式回滚。
4. 依赖的 setup 自上而下、teardown 自下而上（栈式）；完整次序是
   **中间件请求前 → 依赖 setup → 路由 → 中间件响应后 → 后台任务 → 依赖清理**。
5. 全局依赖 `dependencies=[...]` 可挂在 app / router / 单个路由上，**也作用于文档页**；
   多依赖按声明顺序执行，据此实现「先 401 再 403」的 RBAC。
6. 依赖缓存只在**单次请求**内生效，与进程级的 `lru_cache` 不是一回事；
   `app.state` 与 `request.state` 的生命周期不同，判断属性存在用 `hasattr()`。
7. **中间件最后添加的在最外层**，请求路径外层先执行；顺序错了会导致认证内层化、
   CORS 头丢失、错误响应不可读。
8. 中间件适合跨域、压缩、重定向、主机校验、限流、请求 ID；
   依赖注入适合认证鉴权、参数打包、资源管理。判据是「关不关心路由上下文」和「要不要改响应」。

## 练习

- **基础**：写一个 `get_pagination` 依赖，用 `Annotated` 声明 `skip ≥ 0` 与 `1 ≤ limit ≤ 100`，
  并挂到三个路由上；在文档页确认约束都出现了。
- **进阶**：给「删除文章」路由写 `require_owner` 依赖：先取当前用户，再校验文章归属，
  越权返回 403，文章不存在返回 404；用 `dependency_overrides` 写两个测试分别覆盖两种失败。
- **挑战**：给综合示例加一个 `IdempotencyMiddleware`（幂等性中间件）：
  对带 `Idempotency-Key` 头的 `POST` 请求，缓存首次响应并在重复请求时原样返回。
  要求说明三件事：键的选取与过期策略、为什么必须放在限流之内层、以及它与
  「依赖注入 + 缓存」相比各自的优劣。
