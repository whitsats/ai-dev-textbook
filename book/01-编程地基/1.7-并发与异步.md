## 1.7.1 先把四个词分清：同步 / 异步、并发 / 并行

这两组词经常被混着说，但它们回答的是不同的问题：

| 维度 | 回答的问题 | 两种取值 |
| --- | --- | --- |
| 同步 / 异步 | **等待时**干什么 | 同步：等，什么都不做；异步：等的时候去做别的 |
| 并发 / 并行 | **同时**处理几个任务 | 并发：交替推进多个任务；并行：多个核心真正同时执行 |

一句话区分并发与并行：**并发是「一个厨师同时照看三口锅」，并行是「三个厨师各看一口锅」**。

```python
import asyncio
import time


async def task(name: str, seconds: float) -> None:
    print(f"{name}: 开始")
    await asyncio.sleep(seconds)          # 等待时把控制权交回事件循环
    print(f"{name}: 完成")


async def main() -> None:
    start = time.perf_counter()
    await asyncio.gather(task("A", 1.0), task("B", 0.5))
    print(f"总耗时 {time.perf_counter() - start:.2f}s")


asyncio.run(main())
```

```text
# 输出（顺序固定，耗时可能略有浮动）
A: 开始
B: 开始
B: 完成
A: 完成
总耗时 1.00s
```

串行要 1.5 秒（1.0 + 0.5），并发只要约 1.0 秒——**总耗时取决于最慢的那个任务**，
快的那个被“藏”进了慢任务的等待时间里。这就是并发收益的来源。

> ⚠️ **注意**：并发不是「变快」，而是**不浪费等待时间**。
> 如果任务本身没有等待（纯计算），并发不但没有收益，还会因为调度带来额外开销。

## 1.7.2 先分类任务：IO 密集型与 CPU 密集型

选哪种并发方案，只取决于一件事——**时间花在哪**：

| 类型 | 时间花在 | 例子 | 方案 |
| --- | --- | --- | --- |
| IO 密集型 | 等网络、等磁盘、等数据库 | 调模型 API、查向量库、读写文件 | 协程（首选）或线程 |
| CPU 密集型 | 算 | 分词、向量距离计算、图像处理 | 多进程（协程完全无效） |

判断方法很朴素：**看代码里有多少 `await` 之外的时间在等**。
在知舟项目里，检索链路 95% 的时间是等待（模型接口 + 向量库 + 数据库），
所以**协程是主线**；只有本地做 embedding 计算或大批量分词时，才轮到多进程。

> 💡 **提示**：不要凭直觉猜。第 7 篇会讲用计时与 profiling 量化
> 「这段时间到底花在哪」，先量再优化——这是最重要的工程习惯之一。

## 1.7.3 进程与线程：一套资源，两种调度单位

- **进程**：操作系统分配资源的最小单位。每个进程有自己的内存空间、文件句柄；
  进程之间互不干扰，一个崩了不影响另一个。
- **线程**：CPU 调度的最小单位。同一进程内的线程**共享内存**，
  所以通信便宜、但相互影响（一个线程改坏数据，别的线程一起遭殃）。

| 对比 | 进程 | 线程 |
| --- | --- | --- |
| 内存空间 | 各自独立 | 共享 |
| 创建/切换开销 | 大 | 小 |
| 通信方式 | 队列、管道、共享内存 | 直接读写共享变量 |
| 稳定性 | 一个崩了不影响其他 | 一个崩了可能带走整个进程 |
| 能否利用多核 | 能 | CPython 下**不能**（见 1.7.4） |

所以结论是**按任务类型选**：IO 密集型用线程（或协程）更省资源；
CPU 密集型必须用多进程才能吃到多核。

## 1.7.4 GIL：为什么 Python 多线程加速不了计算

CPython（最常用的 Python 解释器）有一把**全局解释器锁（Global Interpreter Lock, GIL）**：
它是一把互斥锁，用来保证**同一时刻只有一个线程在执行 Python 字节码**。

官方术语表的定义是：GIL 是一把互斥锁，阻止多个原生线程同时执行 Python 字节码，
它之所以必要，是因为 CPython 的内存管理（引用计数、垃圾回收）不是线程安全的。

四条要点：

1. **GIL 是 CPython 解释器的特点，不是 Python 语言的特点**（Jython、PyPy 的情况不同）。
2. 它保护的是**解释器级别的数据安全**，不是你的业务数据。
3. 它导致同一进程内的多线程**无法利用多核**——所以多线程跑 CPU 密集任务反而更慢。
4. **针对你自己的共享数据，仍然需要加锁**（见 1.7.5）。

为什么「IO 密集时多线程依然有用」？因为**线程一进入 IO 等待，GIL 就会被释放**，
其他线程可以趁机执行。这也解释了两个常见现象的成因：

| 任务类型 | 多进程 | 多线程 | 原因 |
| --- | --- | --- | --- |
| CPU 密集型（4 个任务各 10 秒） | 约 10+ 秒 | **约 40+ 秒** | 多线程抢 GIL，实际是轮流执行 |
| IO 密集型（4 个任务） | 能加速但浪费资源 | 能加速且更省 | 等待时 GIL 自动释放 |

> 🔥 **常见坑**：面试里被问「Python 多线程有用吗」，只答「没用，有 GIL」是错的。
> 正确的回答要落到任务类型上：**IO 密集型有用，CPU 密集型没用；要并行就用多进程**。

## 1.7.5 threading：基本用法与线程安全

```python
import threading
import time

counter = 0
lock = threading.Lock()


def increase(n: int, use_lock: bool) -> None:
    global counter
    for _ in range(n):
        if use_lock:
            with lock:                     # ✅ 临界区一次只进一个线程
                tmp = counter
                time.sleep(0.0001)
                counter = tmp + 1
        else:
            tmp = counter                  # 读
            time.sleep(0.0001)             # ❌ 在这里被切走
            counter = tmp + 1              # 写回


def run(n: int, use_lock: bool) -> int:
    global counter
    counter = 0
    threads = [threading.Thread(target=increase, args=(n, use_lock)) for _ in range(4)]
    for t in threads:
        t.start()
    for t in threads:
        t.join()                           # 等所有线程结束再往下走
    return counter


print("不加锁：", run(50, False), "（期望 200）")
print("加锁  ：", run(50, True), "（期望 200）")
```

```text
# 输出
不加锁： 50 （期望 200）
加锁  ： 200 （期望 200）
```

`counter += 1` 在字节码层面是「读取、加一、写回」三步。不加锁时，
线程读完旧值后被切走，另一个线程读到了**同一个旧值**，两次自增最终只留下一次——
这就是**竞态条件（race condition）**。例子里那句 `time.sleep(0.0001)` 不是为了拖延，
而是把「被切走」放大到必然发生；真实项目里它可能发生在任意两次字节码之间，
而且**只在高压并发下才偶尔出现**，更难排查。

`with lock:` 等价于 `lock.acquire()` + `try/finally: lock.release()`。
这再次用上了 1.5.11 的上下文管理器：**成对的资源操作都该用 `with`**。

三个线程使用的要点：

- **`join()` 必须调用**：主线程不会自动等子线程跑完，
  不 `join` 就会出现「程序结束了但打印还是旧值」的困惑。
- **守护线程**：`threading.Thread(target=f, daemon=True)` 的线程会随主线程退出而终止，
  适合心跳、监控这类后台任务；但**它随时可能被中断，不能用来保证数据落盘**。
- **少用共享可变状态**：加锁能修正确性，但代价是并发退化成串行。
  更好的做法是**让线程不共享数据**（各自处理各自的数据，最后汇合）。

## 1.7.6 线程池与进程池：不要手动开一堆线程

每来一个任务就开一个线程，几百个任务就会把内存和调度器压垮。
**池（Pool）**的思路是预先固定几个工作单元，任务排队复用它们：

```python
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

def fetch(url: str) -> int:
    """模拟一次网络请求，返回响应长度。"""
    return len(url) * 10


def pure_cpu(n: int) -> int:
    return sum(i * i for i in range(n))


with ThreadPoolExecutor(max_workers=4) as pool:
    futures = [pool.submit(fetch, f"https://example.com/{i}") for i in range(8)]
    print([f.result() for f in futures])        # result() 会阻塞直到该任务完成


if __name__ == "__main__":                      # 进程池必须包在这个守卫里
    with ProcessPoolExecutor(max_workers=4) as pool:
        futures = [pool.submit(pure_cpu, 200_000) for _ in range(4)]
        print(sum(f.result() for f in futures))
```

> 🔥 **常见坑**：进程池**必须**写在 `if __name__ == "__main__":` 里面。
> Windows 与 macOS 用 spawn 方式启动子进程，会重新导入主模块；没有这个守卫时
> 子进程会在导入阶段又把池创建一遍，直接抛
> `RuntimeError: An attempt has been made to start a new process before
> the current process has finished its bootstrapping phase`。
> 线程池没有这个限制。

要点：

- `submit()` **异步提交**，立即返回一个 `Future`；`future.result()` 才是同步等待结果。
- 用 `with` 管理池：退出时自动等待任务结束并回收工作单元，不会漏关。
- `map()` 是更省事的批量写法：`list(pool.map(fetch, urls))`。
- **默认大小不同**：`ThreadPoolExecutor` 不传参数时默认 `min(32, CPU 核数 + 4)`；
  `ProcessPoolExecutor` 默认等于 CPU 核数。**建议显式写 `max_workers`**，
  让并发数变成代码里看得见、可调的值。

> ⚠️ **进程池的额外限制**：被提交的函数必须能被 pickle（即定义在模块顶层），
> 参数与返回值也要能序列化；而且子进程**不共享内存**，父进程里改的全局变量不会生效。
> 这是从线程池切到进程池时最容易撞的墙。

## 1.7.7 asyncio：一个线程跑出多路并发

**协程（coroutine）**是可以用 `await` 暂停的函数。所有协程由**事件循环（event loop）**
在一个线程里调度：遇到 `await` 就让出控制权，去跑别的协程。

```python
import asyncio


async def fetch_doc(doc_id: str, seconds: float) -> str:
    await asyncio.sleep(seconds)               # 模拟 IO 等待
    return f"doc-{doc_id}"


async def main() -> None:
    # gather：并发等待，返回顺序与传入顺序一致
    results = await asyncio.gather(fetch_doc("1", 0.2), fetch_doc("2", 0.1))
    print(results)

    # create_task：立刻排入事件循环，不等待
    task = asyncio.create_task(fetch_doc("3", 0.3))
    print("任务已创建，先去干别的")
    print(await task)                          # 需要结果时再 await


asyncio.run(main())
```

```text
# 输出
['doc-1', 'doc-2']
任务已创建，先去干别的
doc-3
```

三个概念的关系可以这样记：**`async def` 定义协程函数，调用它得到协程对象；
`await` 等待它；`create_task` 把它变成「现在就排队的任务」。**

| 工具 | 作用 | 关键差异 |
| --- | --- | --- |
| `await coro` | 等待一个协程 | 阻塞当前协程直到完成 |
| `asyncio.gather(*coros)` | 并发等待多个协程 | 结果顺序与传入顺序一致 |
| `asyncio.create_task(coro)` | 排入事件循环并立即返回 | 不等待，需自己保管任务对象 |
| `asyncio.run(main())` | 启动事件循环 | 整个程序只在入口调用一次 |

`gather` 默认「一个失败全体抛错」；如果希望其余任务继续跑完，用
`return_exceptions=True`——它会**把异常当成结果返回**，你需要自己检查：

```python
results = await asyncio.gather(may_fail(1), fetch_doc("2", 0.1),
                               return_exceptions=True)
for r in results:
    if isinstance(r, Exception):
        print("这个任务失败了：", type(r).__name__)
```

> 💡 **提示**：协程与 1.4.6 的生成器是同一套机制的两个方向——
> 生成器用 `yield` **产出**值，协程用 `await` **让出**控制权，底层都是「可暂停的函数」。

## 1.7.8 异步工具箱：限流、超时与「不要阻塞」

### Semaphore：控制并发数

一次性发起 500 个请求会打爆对方（也会打爆自己的连接数）。信号量用来限定**同时进行**的任务数：

```python
import asyncio

semaphore = asyncio.Semaphore(5)        # 最多 5 个并发


async def limited_fetch(url: str) -> str:
    async with semaphore:               # 拿不到许可就在这里等
        await asyncio.sleep(0.1)        # 真实的 IO 调用
        return url


async def main() -> None:
    urls = [f"https://example.com/{i}" for i in range(20)]
    results = await asyncio.gather(*(limited_fetch(u) for u in urls))
    print(f"完成 {len(results)} 个请求")
```

### wait_for：给等待加上限

**任何跨网络的调用都必须有超时**，否则一个卡住的请求会拖垮整条链路：

```python
import asyncio


async def slow() -> str:
    await asyncio.sleep(10)
    return "完成"


async def main() -> None:
    try:
        print(await asyncio.wait_for(slow(), timeout=1.0))
    except TimeoutError:
        print("操作超时，走降级逻辑")
```

`asyncio.shield(task)` 用来「限时等待但不取消任务」——超时后任务仍在后台执行，
适合「已经提交、不想丢弃结果」的场景（比如已经发出去的付费模型调用）。

### 最重要的规矩：不要在异步函数里写阻塞调用

```python
async def bad() -> None:
    time.sleep(1)          # ❌ 整个事件循环被卡住 1 秒，所有请求一起等

async def good() -> None:
    await asyncio.sleep(1)  # ✅ 让出控制权，其他请求照常处理
```

同理，`requests`、同步数据库驱动、`open()` 读大文件都会阻塞事件循环。
异步场景要换成对应的异步库：

| 场景 | 同步写法 | 异步写法 |
| --- | --- | --- |
| 等待 | `time.sleep` | `await asyncio.sleep` |
| HTTP | `requests` | `httpx.AsyncClient` |
| 文件 | `open()` | `aiofiles` |
| 数据库 | 同步驱动 | `asyncpg` / `databases` |

## 1.7.9 run_in_executor：把同步任务搬到事件循环之外

现实里总有一些同步代码（老库、必须用 CPU 的计算），不能改写怎么办？
**别在事件循环里跑，扔到线程池或进程池**：

```python
import asyncio
from concurrent.futures import ProcessPoolExecutor


def heavy(n: int) -> int:
    return sum(i * i for i in range(n))


async def main() -> None:
    loop = asyncio.get_running_loop()
    result = await loop.run_in_executor(None, heavy, 1_000_000)   # 默认线程池
    print(result)

    with ProcessPoolExecutor(max_workers=4) as pool:
        # 真正的 CPU 密集任务交给进程池，才能吃到多核
        result = await loop.run_in_executor(pool, heavy, 2_000_000)
        print(result)


asyncio.run(main())
```

记住这条分工：**线程池解决「阻塞」，进程池解决「计算」**。
把 CPU 密集任务丢进线程池只解决了「不卡事件循环」，仍然受 GIL 限制；
要真正并行必须用进程池。

## 1.7.10 FastAPI 的并发模型：`def` 与 `async def` 差在哪

这是本章最实用的一节。FastAPI 对两种写法的处理完全不同：

| 写法 | 执行位置 | 适合 |
| --- | --- | --- |
| `async def` | 事件循环（单线程） | 全是 `await` 的异步调用链 |
| `def` | **线程池**（默认 40 个线程） | 同步的库、CPU 轻量计算、不确定的场景 |

```python
import asyncio

from fastapi import FastAPI, BackgroundTasks

app = FastAPI()


@app.get("/async")
async def async_endpoint() -> dict:
    await asyncio.sleep(1)          # 不阻塞事件循环，可以同时服务很多请求
    return {"type": "async"}


@app.get("/sync")
def sync_endpoint() -> dict:
    import time
    time.sleep(1)                    # 阻塞的是线程池里的一个线程，不是事件循环
    return {"type": "sync"}
```

由此推出三条**必须记住**的实践规则：

1. **`async def` 里绝不能有阻塞调用**。写 `time.sleep(1)` 会让**所有请求**一起变慢，
   而不只是当前请求——这是 FastAPI 里最严重的一类性能事故。
2. **`def` 不是「慢」的同义词**，它只是消耗线程池。默认 40 个线程意味着
   同时有 40 个 `def` 请求在阻塞时，第 41 个就要排队。**同步阻塞在高并发下会耗尽线程池**。
3. **不确定怎么选时，优先把依赖换成异步版本**，让路由保持 `async def`；
   实在改不动的同步库，用 `run_in_executor` 显式移交。

### 后台任务：`BackgroundTasks` 与 `create_task`

响应返回后还要做的事（发通知、写审计日志、预热缓存）有两种写法：

| 对比 | `asyncio.create_task` | `BackgroundTasks` |
| --- | --- | --- |
| 支持同步函数 | 不支持（要自己包成协程） | 支持（自动分配到线程池） |
| 客户端断开连接后 | 视实现而定，容易被取消 | **仍会继续执行** |
| 异常处理 | 需自己捕获 | 框架自动记录，但**不会返回给客户端** |
| 服务关闭时 | 立即中断 | 等待任务完成 |

```python
def send_email(to: str) -> None:
    import time
    time.sleep(0.5)
    print(f"邮件已发送给 {to}")


@app.post("/register")
async def register(username: str, background_tasks: BackgroundTasks) -> dict:
    background_tasks.add_task(send_email, username)   # 响应先返回，任务随后执行
    return {"message": "注册成功"}
```

需要「保证执行」就选 `BackgroundTasks`；只是「有机会就做」可以用 `create_task`。

### 连接的生命周期：`lifespan`

数据库连接、HTTP 客户端这类对象应该**整个应用启动一次、关闭一次**，
而不是每个请求新建。FastAPI 用 `lifespan` 表达这件事：

```python
from contextlib import asynccontextmanager

from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI):
    # 启动时：建立连接池
    yield
    # 关闭时：释放连接


app = FastAPI(lifespan=lifespan)
```

它又是一个上下文管理器（`async with`），与 1.5.11、1.6.5 一脉相承。
具体接数据库的写法放在 1.12。

## 1.7.11 综合示例：知舟的并发检索

把本章拼成一个真实场景：**同时检索多个来源，限流、加超时、允许部分失败**。

```python
# app/services/search.py
import asyncio
import logging

logger = logging.getLogger(__name__)

CONCURRENCY = 4          # 同时最多检索 4 个来源
TIMEOUT = 1.5            # 单个来源的等待上限（秒）


async def search_one(source: str, query: str) -> list[str]:
    """检索单个来源：真实实现里这里会是向量库或模型接口调用。"""
    await asyncio.sleep(0.3)
    return [f"{source}:{query}:{i}" for i in range(2)]


async def search_all(sources: list[str], query: str) -> dict[str, list[str]]:
    """并发检索多个来源：限流 + 超时 + 单个失败不影响整体。"""
    semaphore = asyncio.Semaphore(CONCURRENCY)

    async def guarded(source: str) -> tuple[str, list[str] | None]:
        async with semaphore:
            try:
                hits = await asyncio.wait_for(search_one(source, query), TIMEOUT)
                return source, hits
            except TimeoutError:
                logger.warning("来源 %s 检索超时，已跳过", source)
                return source, None
            except Exception as exc:                      # noqa: BLE001
                logger.error("来源 %s 检索失败：%s", source, exc)
                return source, None

    pairs = await asyncio.gather(*(guarded(s) for s in sources))
    # 只保留成功的来源：部分失败不应该让整个请求失败
    return {source: hits for source, hits in pairs if hits is not None}
```

```python
import asyncio
import logging

from app.services.search import search_all

logging.basicConfig(level=logging.INFO, format="%(levelname)s %(message)s")

result = asyncio.run(search_all(["milvus", "pgvector", "faiss"], "什么是 RAG"))
for source, hits in result.items():
    print(source, hits)
```

```text
# 输出
milvus ['milvus:什么是 RAG:0', 'milvus:什么是 RAG:1']
pgvector ['pgvector:什么是 RAG:0', 'pgvector:什么是 RAG:1']
faiss ['faiss:什么是 RAG:0', 'faiss:什么是 RAG:1']
```

这个示例体现了本章几乎全部要点：`Semaphore` 限流、
`wait_for` 加超时、`gather` 并发、单个失败降级为跳过、日志记录，
以及**返回值设计成「成功来源的字典」**——让调用方不必处理一堆 `None`。

## 常见坑

- **在 `async def` 里用 `time.sleep` / `requests`**。现象：所有请求一起变慢，
  并发量越高越明显。原因：阻塞了事件循环。修法：换 `asyncio.sleep` /
  `httpx.AsyncClient`，或用 `run_in_executor` 移交。
- **CPU 密集任务用多线程**。现象：多线程比单线程还慢。原因：GIL 让线程轮流执行。
  修法：用 `ProcessPoolExecutor` 多进程。
- **开了线程不 `join`**。现象：主线程提前结束，结果不对或打印旧值。
  原因：主线程不等待子线程。修法：`join()`，或用线程池的 `with`。
- **共享变量不加锁**。现象：计数总是少一点，而且每次结果都不一样。
  原因：`+=` 不是原子操作。修法：`with lock`，或改为不共享数据。
- **进程池里改全局变量**。现象：子进程里改了，父进程看不出变化。
  原因：进程不共享内存。修法：用 `future.result()` 把结果传回来。
- **并发数不设上限**。现象：被对方限流、连接池打满、内存暴涨。
  原因：一次性发起太多任务。修法：`Semaphore` 或线程池的 `max_workers`。
- **异步代码没有超时**。现象：偶发的请求永久挂起，把工作线程耗光。
  原因：网络调用不保证返回。修法：所有跨网络调用都包 `wait_for`。
- **`gather` 没处理异常**。现象：一个来源失败导致整个请求 500。
  原因：`gather` 默认「一错全抛」。修法：`return_exceptions=True` 或逐个包 `try`。

## 面试视角

> 🎯 **面试**：题库里「并发与异步」是后端岗的必考项。
> 高频问法是「你项目里哪里用了异步、为什么」，答题时一定要给出**具体场景与数字**。

1. **「并发和并行的区别？Python 怎么做并行？」**
   考察点：概念 + 实现。答题要点：并发是交替推进（一个核心够用），
   并行是多核同时执行；CPython 里并行只能用多进程，协程只能做 IO 并发。
2. **「GIL 是什么？为什么多线程跑 CPU 密集任务更慢？」**
   考察点：机制理解。答题要点：CPython 的全局互斥锁，同一时刻只有一个线程执行字节码；
   IO 等待时释放，所以 IO 密集型仍有效，CPU 密集型只能靠多进程。
3. **「协程和线程的区别？」**
   考察点：调度模型。答题要点：协程由事件循环在单线程调度、切换成本极低，
   但**需要显式 `await` 让出**，一旦写了阻塞调用会拖垮整个循环；
   线程由操作系统抢占式调度，写错了也不会卡住其他线程，但共享状态需要加锁。
4. **「FastAPI 里 `def` 和 `async def` 有什么区别？」**
   考察点：框架实践。答题要点：`async def` 跑在事件循环里，
   `def` 会被放到线程池（默认 40 线程）；`async def` 里写阻塞代码会拖慢所有请求，
   `def` 写多了会耗尽线程池。
5. **「你有超时和重试吗？为什么必须有？」**
   考察点：稳定性意识。答题要点：网络调用必有 `wait_for` 超时，
   失败要能降级或重试（第 1.4 节的 `@retry`）；否则一个慢下游会拖垮整条链路。
6. **「如果一个来源挂了，你希望整个检索失败吗？」**
   考察点：降级设计。答题要点：不应该——部分失败应跳过并记录，
   返回可用结果（本例的 `search_all`），必要时在响应里标注降级信息。

## 本章小结

- 同步/异步讲「等待时做什么」，并发/并行讲「同时处理几个」；并发靠交替，并行靠多核。
- 先分类任务：IO 密集型用协程或线程，CPU 密集型用多进程。协程对纯计算毫无帮助。
- 进程有独立内存、开销大、稳定；线程共享内存、开销小、需加锁。
- GIL 是 CPython 的特性：多线程无法利用多核，但 IO 等待时会释放，因此 IO 密集型仍有效。
- 线程三件套：`Thread` / `start` / `join`；共享可变状态必须加锁（`with lock`）。
- 用 `concurrent.futures` 的池代替手开线程：`submit` 返回 `Future`，`result()` 取结果，
  `with` 管理回收；显式设置 `max_workers`。
- `asyncio` 用一个线程跑出多路并发：`await` 等待、`gather` 并发、`create_task` 不等待；
  `Semaphore` 限流、`wait_for` 超时、`shield` 保护任务。
- **异步函数里绝不能有阻塞调用**；同步代码要移出事件循环用 `run_in_executor`
  （阻塞用线程池，计算用进程池）。
- FastAPI：`async def` 跑事件循环，`def` 跑 40 线程的线程池；
  `BackgroundTasks` 保证后台任务执行，`lifespan` 管理连接生命周期。
