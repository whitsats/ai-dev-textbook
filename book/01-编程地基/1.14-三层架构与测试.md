## 1.14.1 这一章补的是「可维护性」

一个能跑的接口和一个能维护的接口，差别不在功能列表上。举个具体的例子，
同一个「用户不存在」，四种写法会给出四种响应：

```text
{"detail": "User not found"}                      # 框架默认
{"detail": [{"loc": ["path", "user_id"], ...}]}   # 校验错误
"Internal Server Error"                            # 未捕获异常（纯文本！）
<none>                                             # 中间件里出错，连接直接断
```

前端要为四种形状写四段解析代码，日志里找不到「哪个请求、耗时多少、为什么失败」，
定位一个线上问题时只能靠猜。本章要做的四件事，正好对应四类症状：

| 杠杆 | 解决的问题 | 落点 |
| --- | --- | --- |
| 统一响应与异常格式 | 客户端解析成本、错误泄露 | 1.14.2–1.14.6 |
| 日志 | 出事后**无法还原现场** | 1.14.7–1.14.9 |
| 三层架构 | 逻辑堆在路由里、改一处崩三处 | 1.14.10–1.14.11 |
| 单元测试 | 改代码靠人肉回归 | 1.14.12–1.14.13 |
| 生命周期与生产配置 | 资源泄漏、生产暴露内部信息 | 1.14.14 |

> 💡 **提示**：这五件事有个共同点——**它们都不产出功能**。所以最容易被跳过，
> 然后在下一次需求变更时一次性还回来。第 2 篇用 AI 生成代码时，这一点更明显：
> 模型生成的代码默认是「一次性的」，骨架得你自己先立好。

## 1.14.2 统一响应格式：四种方案，只推两种

素材列了四种做法，判断标准只有一个：**它能不能同时保证「类型安全」和「统一」**。

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| Pydantic 响应模型 | `response_model=...` 声明响应结构 | 类型安全、自动文档、**自动过滤多余字段** | 包装层要手动加 |
| 全局异常处理器 | `@app.exception_handler(...)` | 错误格式一处定义、覆盖所有路由 | 只处理异常，管不到成功响应 |
| 自定义响应类 | 继承 `JSONResponse`，用 `response_class=` | 复用简单 | 每个路由都要指定；返回字典而非模型，丢掉校验 |
| 中间件包装 | 拦截所有响应重写 body | 全局生效、业务代码零改动 | **性能差、破坏流式响应、双编码** |

结论与素材一致：**Pydantic 响应模型 + 全局异常处理器**。
这两个分别解决「成功响应长什么样」和「失败响应长什么样」，互不重叠，
而且都不需要业务代码额外配合。

### 为什么不用中间件包装响应

素材给的理由是「需要读两次 body、性能差、破坏流式响应」。我把这段话实跑验证了一遍，
结果比预想的严重：**非 JSON 响应的响应体会直接变成空**。

```python
@app.middleware("http")
async def unify(request: Request, call_next):
    response = await call_next(request)
    body = b""
    async for chunk in response.body_iterator:      # ← 关键：迭代器被消费了
        body += chunk if isinstance(chunk, bytes) else chunk.encode()
    if response.headers.get("content-type", "").startswith("application/json"):
        data = json.loads(body.decode("utf-8"))
        return JSONResponse(content={"code": 200, "message": "success", "data": data})
    return response      # 非 JSON：原样返回，但 body_iterator 已经空了
```

实跑结果：

```text
GET /items   → 200 application/json  {"code": 200, "message": "success", "data": [{"id": 1}]}
GET /stream  → 200 text/plain        ''        ← 文件名、文件下载、流式输出全变成空响应
```

第二条是本该返回 `chunk0\nchunk1\nchunk2\n` 的流式接口，它拿到了
**200 状态码 + 空响应体**。这类故障最难查：状态码正常、日志正常，只有客户端说「下载的文件是 0 字节」。

> ⚠️ **注意**：`response.body_iterator` 是**一次性**的。一旦在中间件里迭代过它，
> 后面就没有任何东西可发。要让中间件方案真的可用，就得把所有响应都重新构造成
> 完整 body 的新响应——文件下载会退化成「先全部读进内存再发」，大文件直接把内存打满。

## 1.14.3 泛型响应模型与分页格式

统一格式本身只有四个字段，关键在于**它的 `data` 是任意形状**，所以要用泛型。
Pydantic v2 里这样写（实跑可用）：

```python
from typing import Generic, TypeVar

from pydantic import BaseModel, Field

T = TypeVar("T")


class BaseResponse(BaseModel, Generic[T]):
    """成功响应的统一外壳。"""
    code: int = 200
    message: str = "success"
    data: T | None = None


class ErrorResponse(BaseModel):
    """失败响应的统一外壳。"""
    code: int | str = 400           # 框架类错误用 HTTP 码；业务错误用字符串业务码（见 1.14.6）
    message: str = "error"
    error: dict = Field(default_factory=dict)     # 注意：不用 {} 当默认值
```

用起来必须**手动包装**，这一点素材说得很准：

```python
@app.get("/articles/{article_id}", response_model=BaseResponse[ArticleOut])
async def read_article(article_id: int):
    article = get_article(article_id)
    return BaseResponse(data=ArticleOut.model_validate(article))
```

`response_model` 只做两件事：**校验返回的数据**、**过滤掉模型里没声明的字段**。
它**不会**帮你把 `{"id": 1}` 变成 `{"code": 200, ..., "data": {"id": 1}}`。
想要外壳就得自己返回 `BaseResponse(...)`——这是很多人第一次用统一格式时最大的误解。

### 分页格式

分页信息是元数据而不是数据，所以要单独一层：

```python
class PageInfo(BaseModel):
    page: int = Field(..., description="当前页码")
    page_size: int = Field(..., description="每页数量")
    total: int = Field(..., description="总数")
    total_pages: int = Field(..., description="总页数")


class PaginatedData(BaseModel, Generic[T]):
    items: list[T]
    pagination: PageInfo


@router.get("/articles", response_model=BaseResponse[PaginatedData[ArticleOut]])
async def list_articles(
    page: Annotated[int, Query(ge=1)] = 1,
    page_size: Annotated[int, Query(ge=1, le=100)] = 10,
):
    total = await count_articles(db)
    items = await fetch_articles(db, skip=(page - 1) * page_size, limit=page_size)
    return BaseResponse(
        data=PaginatedData(
            items=[ArticleOut.model_validate(a) for a in items],
            pagination=PageInfo(
                page=page,
                page_size=page_size,
                total=total,
                total_pages=(total + page_size - 1) // page_size,   # 向上取整
            ),
        )
    )
```

`total_pages` 一定要向上取整：`total=11, page_size=10` 时 `11 // 10 = 1` 是错的，正确的是 2。
这类边界在第 1.12 已经踩过一次，这里再确认一遍写法。

### 业务码还是直接用 HTTP 码

素材的字段表里提到「建议与 HTTP 状态码对齐，特殊场景可自定义业务码」，
但要留意**两者混用会带来第二套真相**：

| 做法 | 优点 | 风险 |
| --- | --- | --- |
| `code` 复制 HTTP 状态码 | 只有一个真相，前端用 HTTP 码判断即可 | `code` 字段其实冗余 |
| `code` 用自定义业务码 | 能表达「HTTP 200 但业务失败」这种细粒度 | 与 HTTP 码不一致时，两层判断容易打架 |

本章的选择：**HTTP 状态码表达协议层结果，`code` 只用来承载业务语义**，
并且约定「`code` 为 0 或 200 表示业务成功」。如果团队里已经习惯了
「HTTP 永远 200，一切看 `code`」，那是一种可以接受的风格，
但要**全项目统一**——混着来比任何一种都糟。

## 1.14.4 异常的三类，与各自的默认行为

FastAPI 里的异常分三类，处理方式完全不同：

| 类型 | 谁抛出 | 默认响应 |
| --- | --- | --- |
| `HTTPException` | 业务代码主动抛 | `{"detail": ...}` + 你给的状态码 |
| `RequestValidationError` | 参数校验失败（Pydantic） | `422` + `{"detail": [错误列表]}` |
| 其他异常 | 任何未处理的错误（`RuntimeError`、`IntegrityError`…） | `500` + **纯文本** `Internal Server Error` |

第三类最值得警惕：它返回的是**纯文本**，不是 JSON。前端按 JSON 解析会直接抛错，
错误信息也淹没在日志里。所以兜底处理器不是「可选优化」，而是必需项。

### `HTTPException` 的三个参数

```python
raise HTTPException(
    status_code=404,
    detail="文章不存在",
    headers={"WWW-Authenticate": "Bearer"},     # 401 场景必带，见 1.13
)
```

### `RequestValidationError` 的触发场景

实跑四种输入，看它给出的 `loc` 与 `type`：

| 请求 | `loc` | `type` |
| --- | --- | --- |
| `POST /items` 缺 `price` | `["body", "price"]` | `missing` |
| `price` 传了字符串 `"abc"` | `["body", "price"]` | `float_parsing` |
| 请求体不是合法 JSON | `["body", 1]` | `json_invalid` |
| 查询参数/表单缺必填 | `["query", "price"]` | `missing` |

三个可直接用的结论：

1. `loc` 的第一个元素就是**错误来源**：`body` / `query` / `path` / `header` / `cookie`。
   前端可以据此决定把错误显示在哪个输入框下。
2. **错误列表的顺序不保证与参数声明顺序一致**（1.9 已实测过），别用下标定位。
3. `json_invalid` 的 `loc` 里是**字符偏移量**（上例中的 `1`），不是字段名——
   写统一的字段提示逻辑时要单独处理这一类。

### 异常处理器的匹配规则：按类型，不按注册顺序

素材给出的建议是「必须先注册具体异常，再注册基类兜底，否则会被基类覆盖」。
这条**不成立**，实跑可以证实：

```python
@app.exception_handler(Exception)          # 先注册基类
async def general(request, exc): ...

@app.exception_handler(HTTPException)      # 后注册具体类
async def http_exc(request, exc): ...

# 结果
GET /http   →  404 {"handler": "http", "detail": "没有"}     # 具体类生效
```

原因是 Starlette 查处理器时**沿着异常类型的 MRO 逐级向上找**，
命中第一个注册过的类型就返回。所以「最具体的类型天然优先」，
注册顺序怎么写都不影响结果。

> 💡 **提示**：结论虽然一样（兜底放最后），**理由必须写对**。
> 若真以为是顺序问题，就会推出「把兜底写前面就行」这种错误规则，
> 也就无法解释为什么中间件里的异常不按类型匹配、`debug=True` 时兜底也会失效
> （两件事都在下一节实测过）。

### 处理器的能力边界

素材的说法是「中间件里的异常处理器完全没参与」。这句话**一半对**：类型专用那一档确实接不住，
但兜底那一档接得住。实跑对照（同一份中间件代码，只改注册了哪些处理器）：

| 中间件里抛出的异常 | 注册的处理器 | 实跑响应 |
| --- | --- | --- |
| `HTTPException(401)` | 只注册 `HTTPException` 处理器 | **500 纯文本** `Internal Server Error` |
| `HTTPException(401)` | 注册了 `Exception` 兜底 | 兜底处理器的响应（**不是 401**） |
| `RuntimeError` | 注册了 `Exception` 兜底 | 兜底处理器的响应 |
| `RuntimeError` | 一个都没注册 | 500 纯文本 `Internal Server Error` |

**别读错这张表**：中间件里抛 `HTTPException(401)`，你得到的是兜底的 500，而不是 401。
原因是 Starlette 的 `ServerErrorMiddleware` 包在最外层（1.11 的洋葱顺序），中间件抛出的异常
直接落到它手里——**不会再回到 `HTTPException` 那一档的类型匹配**。这就是 1.11 那条
「中间件里 `raise HTTPException` 变成 500」的机制。

所以写法上有两条路，选一条：

- 中间件内部自己 `try/except` 并返回 `JSONResponse`（推荐，语义最清楚）；
- 或者抛一个**兜底处理器认识的自定义异常**，让兜底那档统一处理。

剩下两处边界：

1. **`debug=True` 时连兜底处理器也被绕过**（读 Starlette 源码确认：`ServerErrorMiddleware`
   在 `debug` 为真时走 `debug_response`，它排在 `handler` 之前）。返回的是**带完整堆栈的响应**：
   带 `Accept: text/html` 的浏览器拿到 HTML 调试页，其他客户端拿到纯文本堆栈。
   这是 1.14.14「本地也保持 `debug=False`」的另一半理由。
2. **响应序列化阶段的错误**：比如 `response_model` 校验失败（1.12 的 `expire_on_commit` 坑
   就是在这里暴露的），它发生得太晚，处理器拿不到。

## 1.14.5 全局异常处理器：三个处理器写完

一套够用的骨架只要三个处理器，形状统一如下：

```python
# errors.py
import logging
from typing import Any

from fastapi import FastAPI, HTTPException, Request, status
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse

logger = logging.getLogger(__name__)


def _body(code: int, message: str, error: dict[str, Any] | None = None) -> dict:
    return {"code": code, "message": message, "error": error or {}}


def register_exception_handlers(app: FastAPI) -> None:
    """把所有处理器集中注册，main.py 只需要调一次。"""

    @app.exception_handler(HTTPException)
    async def http_exception_handler(request: Request, exc: HTTPException):
        # detail 允许是任意结构（比如业务错误字典），原样放进 error
        return JSONResponse(
            status_code=exc.status_code,
            content=_body(exc.status_code, str(exc.detail), {"detail": exc.detail}),
            headers=exc.headers,
        )

    @app.exception_handler(RequestValidationError)
    async def validation_exception_handler(request: Request, exc: RequestValidationError):
        errors = [
            {
                "field": ".".join(str(x) for x in err["loc"]),
                "msg": err["msg"],
                "type": err["type"],
            }
            for err in exc.errors()
        ]
        return JSONResponse(
            status_code=status.HTTP_422_UNPROCESSABLE_ENTITY,
            content=_body(422, "参数校验失败", {"errors": errors}),
        )

    @app.exception_handler(Exception)
    async def unhandled_exception_handler(request: Request, exc: Exception):
        # 关键：先记日志（带堆栈），再返回脱敏响应
        logger.exception("未处理异常：%s %s", request.method, request.url.path)
        return JSONResponse(
            status_code=status.HTTP_500_INTERNAL_SERVER_ERROR,
            content=_body(500, "服务器内部错误"),
        )
```

四个细节值得单独说：

1. **`logger.exception(...)` 必须在处理器里调用**。它自动带上当前异常的堆栈，
   是唯一能让你事后还原现场的东西。少了这一句，500 在日志里只剩「有一条错误请求」。
2. **500 的响应体里绝不能出现异常原文**。素材的建议是区分环境：生产只回
   `"服务器内部错误"`，开发环境才回 `type(exc).__name__` 与堆栈。上面这段代码直接
   统一脱敏——**要调试信息就去日志里看**，不要通过 HTTP 暴露出去。
   把堆栈发给客户端等价于把内部结构、库版本、文件路径一并送出去。
3. **`HTTPException` 的 `headers` 要透传**。1.13 的 `WWW-Authenticate` 就是靠它带出去的；
   忘了透传，401 的语义就丢了。
4. **处理器集中注册**（`register_exception_handlers`）比散在 `main.py` 里好：
   测试时可以把同一套处理器装到任意 app 上。

## 1.14.6 业务异常：定义、分层与错误码

`HTTPException` 有一个缺点：它把**HTTP 语义写进了业务代码**。
Service 层抛出 `HTTPException(status_code=404)` 意味着「业务逻辑知道 HTTP 是什么」，
这层耦合会让 Service 无法在 CLI、定时任务、消息队列里复用。

解法是把业务异常定义在领域里，**在路由层（或全局处理器里）转换成 HTTP**：

```python
# exceptions.py
class BizError(Exception):
    """所有业务异常的基类。"""
    code = "BIZ_ERROR"
    status_code = 400

    def __init__(self, message: str, *, detail: dict | None = None):
        super().__init__(message)
        self.message = message
        self.detail = detail or {}


class NotFoundError(BizError):
    code = "NOT_FOUND"
    status_code = 404


class ConflictError(BizError):
    code = "CONFLICT"
    status_code = 409


class PermissionDeniedError(BizError):
    code = "PERMISSION_DENIED"
    status_code = 403
```

有了基类，转换只需要一个处理器，而不是每个路由都写 `try/except`：

```python
@app.exception_handler(BizError)
async def biz_error_handler(request: Request, exc: BizError):
    return JSONResponse(
        status_code=exc.status_code,
        content={"code": exc.code, "message": exc.message, "error": exc.detail},
    )
```

这一条**实跑验证过一件容易踩空的事**：依赖里抛出的业务异常也会被这个处理器接住。

```text
GET /dep                # 依赖函数里 raise BizError("依赖里出错")
→ 409 {"handler": "biz", "msg": "依赖里出错"}
```

素材说「依赖中抛出非 `HTTPException` 的异常，必须配合全局处理器才能正常返回响应」——
准确的表述是：**不加处理器就是 500，加了就能得到你想要的状态码**。
（还记得 1.13 的教训：这些异常在中间件里抛出时，处理器接不住。）

### 错误码表

| HTTP | 业务码示例 | 什么时候用 |
| --- | --- | --- |
| 400 | `INVALID_PARAM` / `BIZ_ERROR` | 参数不合法、业务规则拒绝 |
| 401 | `UNAUTHENTICATED` | 没带凭据、凭据过期（1.13） |
| 403 | `PERMISSION_DENIED` | 已认证但无权限 |
| 404 | `NOT_FOUND` | 资源不存在**或无权知道它是否存在**（1.13 的越权返回 404） |
| 409 | `CONFLICT` | 唯一约束冲突（邮箱已注册） |
| 422 | `VALIDATION_ERROR` | 参数校验失败（框架自动） |
| 429 | `RATE_LIMITED` | 触发限流（1.11） |
| 500 | `INTERNAL` | 服务器内部错误（兜底） |

> 💡 **提示**：`code` 用**字符串常量**而不是数字。数字业务码需要一张对照表才能读懂
> 日志与告警，而 `EMAIL_TAKEN` 自己就说明了问题；也避免了「1001 到底是哪个业务」这种追问。
> 前端要做国际化文案时，用这个字符串去映射更稳（数字码一旦重编就全乱）。

## 1.14.7 日志：四要素与一份能用的配置

日志的四个概念，用一句话记住各自的职责：

| 要素 | 比喻 | 决定什么 |
| --- | --- | --- |
| Logger | 服务员 | **谁来记**（按模块取 `logging.getLogger(__name__)`） |
| Handler | 日志本 / 打印机 | **记到哪里**（控制台、文件、网络） |
| Level | 重要程度筛选 | **记多少**（`DEBUG < INFO < WARNING < ERROR < CRITICAL`） |
| Formatter | 格式模板 | **记成什么样** |

两个容易搞错的地方：

1. **级别是「放行阈值」，不是「只记这一级」**。设 `INFO` 表示 INFO 及更严重的都放行，
   `DEBUG` 就被过滤掉。
2. **logger 与 handler 各有一道级别**，两道都要过。生产里常见的写法是
   「logger 开到 INFO，文件 handler 也 INFO，但错误文件 handler 只收 ERROR」——
   同一条日志进入不同文件，靠的是 handler 级别的差异。

### 一份可直接用的配置

```python
# log_config.py
import logging
import logging.handlers
import sys
from pathlib import Path

LOG_DIR = Path(__file__).parent / "logs"
LOG_DIR.mkdir(exist_ok=True)

SIMPLE_FORMAT = "%(asctime)s - %(levelname)s - %(message)s"
DETAIL_FORMAT = "%(asctime)s - %(name)s - %(levelname)s - %(filename)s:%(lineno)d - %(message)s"


def setup_logging(level: int = logging.INFO) -> None:
    """初始化根记录器。必须在应用启动时调用且只调用一次。"""
    root = logging.getLogger()
    root.setLevel(level)
    root.handlers.clear()          # 关键：避免热重载时 handler 越加越多

    # 1) 控制台：开发时看得见，级别放最宽，是否输出由 root 的 level 决定
    console = logging.StreamHandler(sys.stdout)
    console.setFormatter(logging.Formatter(SIMPLE_FORMAT))
    root.addHandler(console)

    # 2) 日常日志：按天轮转，保留 30 天
    daily = logging.handlers.TimedRotatingFileHandler(
        LOG_DIR / "app.log",
        when="midnight",
        interval=1,
        backupCount=30,
        encoding="utf-8",          # 必须显式指定，理由见下
        errors="replace",          # 无法编码的字符替换掉，而不是抛异常
        utc=True,                  # 按 UTC 轮转，避免服务器时区变化导致切分错乱
    )
    daily.setLevel(logging.INFO)
    daily.setFormatter(logging.Formatter(DETAIL_FORMAT))
    root.addHandler(daily)

    # 3) 错误日志：按大小轮转，只收 ERROR 以上
    errors = logging.handlers.RotatingFileHandler(
        LOG_DIR / "error.log",
        maxBytes=10 * 1024 * 1024,
        backupCount=5,
        encoding="utf-8",
        errors="replace",
    )
    errors.setLevel(logging.ERROR)
    errors.setFormatter(logging.Formatter(DETAIL_FORMAT))
    root.addHandler(errors)

    # 4) 压制框架噪音
    logging.getLogger("uvicorn.access").setLevel(logging.WARNING)
    logging.getLogger("uvicorn.error").setLevel(logging.INFO)
```

实跑验证三件事：

```text
一次 setup 后根 handler 数: 3
再 setup 一次（已 clear）: 3              ← 稳定，不会翻倍
不 clear 时重复 handler 数: 3
→ 同一条日志会被打印 3 次                  ← 「日志重复输出」的真实成因
error.log 只记 ERROR 以上: ['这是错误']     ← handler 级别按预期过滤
TimedRotatingFileHandler 支持 utc 参数: True
```

### 必须显式写 `encoding="utf-8"`

这是本机（Windows）实跑发现的问题，而且失败方式很隐蔽：

```text
不指定 encoding 写中文 → 文件字节 b'\xd6\xd0\xce\xc4...'    ← GBK 编码
locale.getpreferredencoding(False) = cp936
写 emoji → UnicodeEncodeError: 'gbk' codec can't encode character '\U0001f680'
```

三件事值得注意：

1. **不指定 `encoding` 时，`FileHandler` 用系统默认编码**（本机是 cp936）。
   中文能写进去，但**文件是 GBK 的**——换到用 UTF-8 打开的工具（ELK、编辑器、`grep`）里就是乱码。
   日志的价值在于能被检索，编码不一致等于白记。
2. 遇到编码不支持的字符（比如用户昵称里的 emoji），会抛 `UnicodeEncodeError`。
3. **这个异常被 logging 自己吞掉了**：程序继续运行、接口正常返回，只有 stderr 上多一段
   `Call stack`，而那一条日志**静默丢失**。所以「日志里少了某条记录」这种问题，
   先检查编码，再看级别。

加了 `encoding="utf-8"` 与 `errors="replace"` 之后，中文与 emoji 都能正常落盘。

### 按环境切级别

```python
import logging
import os

LEVEL_MAP = {
    "development": logging.DEBUG,
    "testing": logging.INFO,
    "production": logging.INFO,
}
env = os.getenv("ENVIRONMENT", "development").strip().lower()
setup_logging(LEVEL_MAP.get(env, logging.INFO))
```

生产用 INFO 而不是 DEBUG：DEBUG 会让每条 SQL、每个内部状态都落盘，
I/O 与磁盘占用的代价远大于它的调试价值。
（`logging.basicConfig` 只在**第一次**调用时生效，这也是本章用自建 `setup_logging` 的原因之一。）

## 1.14.8 请求日志中间件：一次定义，全局生效

中间件最擅长的正是这类「不关心是哪个接口」的横切逻辑（1.11 的结论）：

```python
# middleware.py
import logging
import time
import uuid

from fastapi import Request
from starlette.middleware.base import BaseHTTPMiddleware

logger = logging.getLogger("app.access")


class AccessLogMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next):
        request_id = request.headers.get("X-Request-ID") or uuid.uuid4().hex[:12]
        request.state.request_id = request_id          # 供后续日志与响应头使用
        start = time.perf_counter()
        try:
            response = await call_next(request)
        except Exception:
            elapsed = (time.perf_counter() - start) * 1000
            logger.exception(
                "request failed method=%s path=%s elapsed_ms=%.1f request_id=%s",
                request.method, request.url.path, elapsed, request_id,
            )
            raise                                       # 继续上抛，交给 ServerErrorMiddleware
        elapsed = (time.perf_counter() - start) * 1000
        response.headers["X-Request-ID"] = request_id
        response.headers["X-Process-Time"] = f"{elapsed:.1f}ms"
        logger.info(
            "method=%s path=%s status=%s elapsed_ms=%.1f request_id=%s",
            request.method, request.url.path, response.status_code, elapsed, request_id,
        )
        return response
```

四个设计点：

1. **`X-Request-ID`**：一个请求可能打十几条日志，靠它才能串起来。
   客户端也能拿它来报障——「我这单失败，ID 是 `a1b2c3d4e5f6`」比「我提交不了」有用得多。
2. **耗时用 `time.perf_counter()`**，不要用 `time.time()`。后者是墙钟时间，
   会被系统时间调整影响；`perf_counter` 是单调时钟，专门用来测间隔。
3. **异常要记完再 `raise`**。中间件里如果把异常吞掉，全局处理器就永远看不到它
   （上一节的边界），日志里会出现「有请求、无结果、无错误」的三无记录。
4. **用类而不是 `@app.middleware("http")`**：类可以被参数化（比如是否记录请求体）、
   可以复用、可以在测试里单独实例化。素材的对比表里也提到这一点。

日志格式建议改成**结构化字段**（`method=... path=...`）而不是散文式拼接。
原因很实际：以后要在日志平台里按 `status=500` 过滤、按 `elapsed_ms` 排序时，
结构化字段是直接可查的，而 `"响应状态: 500"` 只能全文匹配。

## 1.14.9 结构化日志与脱敏

要接 ELK / Loki / 云日志服务时，日志本身就是一条 JSON：

```python
import json
import logging
from datetime import datetime, timezone


class JSONFormatter(logging.Formatter):
    def format(self, record: logging.LogRecord) -> str:
        data = {
            "timestamp": datetime.fromtimestamp(record.created, timezone.utc).isoformat(),
            "level": record.levelname,
            "logger": record.name,
            "message": record.getMessage(),
            "module": record.module,
            "line": record.lineno,
            "process_id": record.process,
            "thread_id": record.thread,
        }
        if record.exc_info:
            data["exception"] = {
                "type": record.exc_info[0].__name__,
                "message": str(record.exc_info[1]),
                "traceback": self.formatException(record.exc_info),
            }
        return json.dumps(data, ensure_ascii=False)     # 保留中文，不转义成 \uXXXX
```

实跑输出（一条普通日志 + 一条带堆栈的）：

```json
{"timestamp": "2026-09-12T09:57:59.111074+00:00", "level": "INFO", "logger": "t2", "message": "用户登录 中文", "module": "l2", "line": 43, "process_id": 27336, "thread_id": 28684}
{"timestamp": "...", "level": "ERROR", "message": "计算出错", "exception": {"type": "ZeroDivisionError", "message": "division by zero", "traceback": "Traceback (most recent call last): ..."}}
```

两个细节：`ensure_ascii=False` 让中文保持可读（否则日志里全是 `\u767b\u5f55`，
直接搜「登录」搜不到）；`exc_info` 只在异常日志里出现，而且**堆栈要一并序列化**，
不然结构化日志反而比纯文本更难排查。

> ⚠️ **注意**：**结构化日志必须配 PII 脱敏**，否则等于把敏感数据整整齐齐地
> 送进日志平台（通常是权限更宽的第三方系统）。1.13 的安全清单里那条
> 「日志绝不记录口令与令牌」，落到代码上就是这个函数：

```python
from typing import Any

SENSITIVE_KEYS = {
    "password", "token", "access_token", "refresh_token", "secret", "api_key",
    "authorization", "cookie", "id_card", "phone", "credit_card", "cvv",
}


def mask_sensitive(data: Any, max_depth: int = 8) -> Any:
    """递归脱敏：命中字段名就替换；容器超出深度上限时整体换成占位符。"""
    if isinstance(data, dict):
        if max_depth <= 0:
            return "***MAX_DEPTH***"          # 关键：不是原样返回，否则深层的敏感字段会漏出去
        return {
            k: ("***MASKED***" if str(k).lower() in SENSITIVE_KEYS else mask_sensitive(v, max_depth - 1))
            for k, v in data.items()
        }
    if isinstance(data, (list, tuple)):
        if max_depth <= 0:
            return ["***MAX_DEPTH***"]
        return [mask_sensitive(v, max_depth - 1) for v in data]
    if isinstance(data, set):
        if max_depth <= 0:
            return {"***MAX_DEPTH***"}
        return {mask_sensitive(v, max_depth - 1) for v in data}
    return data
```

```text
{"username":"tom","password":"123456"}                → {"username":"tom","password":"***MASKED***"}
{"user":{"phone":"13800138000","token":"abc"}}        → {"user":{"phone":"***MASKED***","token":"***MASKED***"}}
{"Password":"x"}                                      → {"Password":"***MASKED***"}   ← 键名比较前先小写化
深度 20 的嵌套（密码在第 19 层）                        → 第 8 层起变成 "***MAX_DEPTH***"，全文搜不到明文
```

三点提醒：

1. **字段名比较要小写化**（`str(k).lower()`），否则 `Password` / `PASSWORD` 会漏过。
2. **深度上限必须「替换」而不是「放行」**。这是本节实跑抓到的真问题：
   最初我把上限写成 `if max_depth <= 0: return data`，结果**深度 20、密码埋在第 19 层的结构，
   明文原封不动地留在输出里**——脱敏在最需要它的地方静默失效。上限的作用是防爆栈，
   但对于脱敏函数，「放弃」必须是「换成占位符」，不能是「原样返回」。
3. **脱敏是最后一道防线，不是第一道**。更稳的做法是**根本不记录整个请求体**——
   只在确实需要时记录白名单字段。脱敏列表永远会漏掉新加的敏感字段。

## 1.14.10 三层架构：每层「不该做什么」

三层架构本身不难，难在边界。先把职责一条条写死：

| 层 | 职责 | **不该做** |
| --- | --- | --- |
| 表示层（路由） | 参数校验、调用 Service、映射响应、决定状态码 | 写业务规则、拼 SQL |
| 业务逻辑层（Service） | 业务规则、流程编排、事务意图 | 碰 `Request` / `HTTPException`、直接写 SQL |
| 数据访问层（DAO） | 增删改查、查询条件拼装 | 做业务判断（「邮箱是否重复」不是 SQL 问题） |

```text
请求 → 路由（表示层）→ Service（业务）→ DAO（数据）→ 数据库
        ↑ 参数校验           ↑ 规则            ↑ SQL
        ← 状态码/响应         ← 业务异常          ← ORM 对象
```

对应到目录（与 1.12 的分层一致，本章只新增 `service/` 与 `errors.py`）：

```text
app/
├── main.py            # 组装：注册中间件、异常处理器、路由、lifespan
├── config.py          # 配置
├── errors.py          # 业务异常 + 异常处理器
├── log_config.py      # 日志配置
├── middleware.py      # 访问日志中间件
├── models.py          # SQLAlchemy 模型
├── schemas.py         # Pydantic 请求/响应模型
├── database.py        # 引擎与会话工厂
├── dao/               # 数据访问层
│   └── article_dao.py
├── service/           # 业务逻辑层
│   └── article_service.py
└── routers/           # 表示层
    └── articles.py
```

### Service 抛业务异常，不抛 HTTP

```python
# service/article_service.py
from dao.article_dao import ArticleDAO
from errors import ConflictError, NotFoundError
from schemas import ArticleCreate


class ArticleService:
    def __init__(self, dao: ArticleDAO):
        self.dao = dao

    async def create(self, data: ArticleCreate, author_id: int):
        if await self.dao.get_by_title(data.title):
            raise ConflictError("同名文章已存在", detail={"title": data.title})
        return await self.dao.create(data, author_id)

    async def get(self, article_id: int):
        article = await self.dao.get(article_id)
        if article is None:
            raise NotFoundError("文章不存在")
        return article

    async def update(self, article_id: int, data: ArticleUpdate, user):
        article = await self.get(article_id)                       # 复用上面的规则
        if article.author_id != user.id and user.role != "admin":
            raise NotFoundError("文章不存在")                       # 越权也报 404（1.13）
        return await self.dao.update(article, data)
```

`ConflictError` / `NotFoundError` 里没有任何 HTTP 概念，Service 可以被 CLI、
定时任务、消息消费者复用——这是「不抛 `HTTPException`」真正的收益。

### 依赖注入链

```python
# routers/articles.py
from typing import Annotated

from fastapi import APIRouter, Depends
from sqlalchemy.ext.asyncio import AsyncSession

from dao.article_dao import ArticleDAO
from database import get_db
from service.article_service import ArticleService

router = APIRouter(prefix="/articles", tags=["文章"])


def get_article_dao(db: Annotated[AsyncSession, Depends(get_db)]) -> ArticleDAO:
    return ArticleDAO(db)


def get_article_service(dao: Annotated[ArticleDAO, Depends(get_article_dao)]) -> ArticleService:
    return ArticleService(dao)


@router.post("", status_code=201)
async def create_article(
    data: ArticleCreate,
    user: Annotated[User, Depends(get_current_user)],
    service: Annotated[ArticleService, Depends(get_article_service)],
):
    return await service.create(data, author_id=user.id)
```

这条链 `get_db → get_article_dao → get_article_service` 有三个性质，实跑都验证过：

| 性质 | 实测 | 意义 |
| --- | --- | --- |
| **同一请求内复用** | 同一个依赖在路由里声明两次，函数只被调用 1 次，拿到同一个对象 | 一个请求共享一个数据库会话 |
| **跨请求不缓存** | 第二次请求时调用计数变成 2 | 不会有「上次请求的会话」污染本次 |
| 手工构造实例 | `ArticleService(dao)` 直接 `new` | 测试时可以完全绕过 FastAPI |

> ⚠️ **注意**：跨请求不缓存意味着一件容易写错的事——**DAO 的实例属性不能当存储**。
> 我实跑时踩过一个：`UserDAO.__init__` 里写 `self.db = {}`（用字典模拟库），
> 结果「邮箱已注册」的检查永远不生效（每次请求都是新字典）。
> 状态必须放在真正的存储里（数据库 / Redis / `app.state`），
> DAO 与 Service 本身应当是**无状态**的。

### 事务边界

事务边界放在**依赖收尾**（1.12 的结论）：Service 只 `flush()` 表达意图，
真正的 `commit()` 在 `get_db` 的 `yield` 之后统一执行。
这样「一个请求内的多次写」天然成为一个事务，出错时整体回滚。

## 1.14.11 分层带来的三个收益

分层常被当成「规范」来学，其实它的收益是可验证的：

**① 错误转换只有一处。** 业务层抛 `NotFoundError`，全局处理器转成 404 JSON，
路由里不需要任何 `try/except`。对比一下不分层的写法：

```python
# 不分层：每个路由都要判断 + 转换，且错误形状容易写得不一致
@router.get("/articles/{article_id}")
async def read(article_id: int, db=Depends(get_db)):
    article = await db.get(Article, article_id)
    if article is None:
        raise HTTPException(404, "文章不存在")
    ...
```

**② 业务规则可以被独立测试。** `ArticleService` 不依赖 `Request`、不依赖数据库
（DAO 被 Mock 掉），所以「同名文章要拒绝」这条规则可以用一个纯 Python 测试验证，
毫秒级跑完，不需要起任何服务。

**③ 改动的波及范围可预测。** 换数据库 → 只改 `dao/` 与 `database.py`；
改业务规则 → 只改 `service/`；改响应格式 → 只改 `errors.py` 与 `schemas.py`。
这与第 2 篇「让 AI 改代码」直接相关：**你能指出改动该落在哪一层，AI 才不会改错地方**。

## 1.14.12 单元测试：`TestClient` 与三个断言习惯

测试的价值可以用一张表说清（素材的对比表，我加了第三列）：

| 场景 | 没有测试 | 有测试 | 有测试时你实际做的事 |
| --- | --- | --- | --- |
| 改代码 | 提心吊胆 | 跑一遍就知道 | 改完立刻验证 |
| 重构 | 不敢动 | 放心动 | 测试就是重构的安全网 |
| 交接 | 靠口口相传 | 测试即活文档 | 新人读测试就懂接口契约 |

### 最小可用写法

```python
# tests/test_articles.py
import pytest
from fastapi.testclient import TestClient

from app.main import app


@pytest.fixture
def client():
    # with 是必需的：app 有 lifespan（1.14.14）。裸建 TestClient 不会跑 startup，
    # 测到的是一个「资源没初始化」的应用，而断言可能因为空状态而「恰好通过」。
    with TestClient(app) as c:
        yield c


def test_list_articles_returns_unified_shape(client):
    response = client.get("/articles")
    assert response.status_code == 200
    body = response.json()
    assert body["code"] == 200
    assert isinstance(body["data"]["items"], list)


def test_create_article_without_title_returns_422(client):
    response = client.post("/articles", json={"content": "x"})
    assert response.status_code == 422

    assert response.status_code == 404
    assert response.json()["message"] == "文章不存在"
```

`TestClient` 做三件事：构造符合 HTTP 规范的请求、**直接调用应用的路由逻辑**
（不启动真实服务器、不占端口）、把结果封装成标准响应对象。它支持
`get` / `post` / `put` / `patch` / `delete` / `head` / `options`。

三个断言习惯：

1. **状态码 + 响应体 + 关键响应头**，三样都断。只断状态码的测试挡不住「200 但返回空数组」。
2. **断言要断「契约」而不是实现细节**。`assert body["code"] == 200` 是契约；
   `assert body["data"]["items"][0]["id"] == 1` 强依赖数据顺序，未来加个排序就红。
3. **命名要能当文档读**：`test_get_missing_article_returns_404` 比 `test_1` 好得多。

### 测试 500 必须改一个默认参数

这是实跑踩到的硬坑。默认的 `TestClient` 会把服务端异常**重新抛出来**：

```text
TestClient(app).get("/boom")                      → 抛 RuntimeError（测试直接报错）
TestClient(app, raise_server_exceptions=False)    → 500，可以断言响应体
```

所以要断言兜底处理器的输出，必须显式关掉这个行为（注意这里仍然要用 `with`）：

```python
def test_unhandled_error_returns_masked_500():
    with TestClient(app, raise_server_exceptions=False) as client:
        response = client.get("/boom")
        assert response.status_code == 500
        assert response.json() == {"code": 500, "message": "服务器内部错误", "error": {}}
        assert "RuntimeError" not in response.text    # 不泄露异常类型
```

如果测试较多，把这一条也写进 fixture 更省事：

```python
@pytest.fixture
def error_client():
    with TestClient(app, raise_server_exceptions=False) as c:
        yield c
```

> 💡 **提示**：这个默认值其实是好意——它让「代码里的 bug」在测试里立刻炸出来，
> 而不是被一个笼统的 500 掩盖。所以**只在需要验证兜底响应时才关掉它**。

### `TestClient` 与 `AsyncClient` 怎么选

| 场景 | 用什么 | 原因 |
| --- | --- | --- |
| 单个接口的功能验证 | `TestClient` | 同步写法更短，不用 `async/await` |
| 并发 / 异步时序（限流、竞态、异步 DB） | `AsyncClient`（需 `pytest-asyncio`） | `TestClient` 内部同步执行，测不出并发行为 |

> ⚠️ **实跑边界（必须说明）**：本机**没有安装 pytest / pytest-asyncio / pytest-cov**

> 实际验证时我用一个五行的运行器逐个调用它们：

## 1.14.13 测试的分层策略

三层的存在意义之一，就是**每层都能用最便宜的方式测**：

| 被测对象 | 手段 | 依赖 | 速度 |
| --- | --- | --- | --- |
| Service（业务规则） | 纯测试 + Mock DAO | 无 | 毫秒 |
| DAO（SQL 正确性） | 真数据库（SQLite 内存库） | 数据库 | 毫秒–秒 |
| 路由（契约/状态码/格式） | `TestClient` + 依赖覆盖 | 无（覆盖掉 DB） | 毫秒 |
| 全链路（真实交互） | 集成测试，真库真服务 | 全套 | 秒–分 |

### Service 层：Mock 掉 DAO

```python
# tests/test_article_service.py
from unittest.mock import AsyncMock          # 注意：不是 Mock

import pytest

from errors import ConflictError
from schemas import ArticleCreate
from service.article_service import ArticleService


@pytest.fixture
def mock_dao():
    return AsyncMock()


@pytest.fixture
def service(mock_dao):
    return ArticleService(mock_dao)


@pytest.mark.asyncio                            # 被测方法本身是协程
async def test_create_rejects_duplicate_title(service, mock_dao):
    mock_dao.get_by_title.return_value = object()          # 已存在同名文章

    with pytest.raises(ConflictError):
        await service.create(ArticleCreate(title="t", content="c"), author_id=1)

    mock_dao.create.assert_not_called()                     # 关键：不该走到写入
```

这段是**素材里最有价值的测试模式**，但素材没提两个会让它当场报错的细节（都实跑验证过）：

1. **DAO 方法都是协程，所以替身必须是 `AsyncMock` 而不是 `Mock`**。用普通 `Mock` 时，
   `await self.dao.get_by_title(...)` 会抛
   `TypeError: object object can't be used in 'await' expression`——
   报错指向 `await`，真因却是替身类型选错了。
2. **`AsyncMock` 不设 `return_value` 时，默认返回一个 mock 对象而不是 `None`**。
   所以测「标题不重复、应当创建成功」那条路时必须显式写
   `mock_dao.get_by_title.return_value = None`；忘了写，「文章不存在」的分支永远走不到，
   测试会以一个与业务无关的理由失败。反过来，测「重复」时也得显式给个非 `None` 值。

两个断言要点：

1. `assert_not_called()` 比「抛了异常」更强：它证明了「拒绝之后没有副作用」。
   只断异常的话，一个「先创建再报错」的实现也能通过。
2. 断言异常必须带**具体类型**（`ConflictError`），不要用裸的 `Exception`——
   否则把 `TypeError` 也当成「业务规则生效」了。

> ⚠️ **实跑边界**：上面两条协程替身的结论，是用标准库 `unittest.mock` + `asyncio.run`
> 写等价代码实跑验证的；`@pytest.fixture` / `@pytest.mark.asyncio` / `pytest.raises`
> 这几行是 pytest 专属机制，本机未装 pytest，未实跑。

### 路由层：用依赖覆盖换掉数据库

这是 FastAPI 测试体系里最重要的一个能力，1.11 已介绍过，这里给出完整形态：

```python
# tests/conftest.py（pytest 写法，未实跑）
from unittest.mock import AsyncMock

import pytest
from fastapi.testclient import TestClient

from app.main import app
from app.routers.articles import get_article_dao


@pytest.fixture
def fake_dao():
    dao = AsyncMock()                        # 同样是协程：不能用 Mock
    dao.list_articles.return_value = []
    return dao


@pytest.fixture
def client(fake_dao):
    app.dependency_overrides[get_article_dao] = lambda: fake_dao
    with TestClient(app, raise_server_exceptions=False) as c:    # with：触发 lifespan
        yield c
    app.dependency_overrides.clear()        # 关键：测试后必须清理
```

三个要点：

1. **覆盖的粒度选「最靠上的那一层」**：覆盖 `get_article_dao` 就同时切断了
   DAO 与数据库，比覆盖 `get_db` 更省事（不用再造一个假会话）。
2. **`clear()` 必须放在 `yield` 之后**。忘了清理，后面的测试会接着用假的 DAO，
   表现为「单独跑通过、全量跑失败」——这类问题极难定位。
3. **覆盖只影响 `app` 对象**。同一进程里如果还有别的 app（比如管理后台），
   它们的依赖不会被动到。

### 数据库测试

真库测试仍然必要：Mock 掉的 DAO 测不出 SQL 对不对（字段名拼错、约束缺失）。
用 SQLite 内存库跑 DAO 层是个好折中——快，且不需要起服务：

```python
# 未实跑（依赖 pytest fixture 的建表/清表生命周期）
@pytest.fixture
async def session():
    engine = create_async_engine("sqlite+aiosqlite:///:memory:")
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)

```

> 💡 **提示**：**别用生产库或开发库跑测试**。测试会写脏数据、会并发跑、
> 有时还会 drop 表。判据很简单：一个测试能不能让人安心地在别人的机器上跑。

### 关于覆盖率

素材建议用 `pytest-cov` 并设阈值（如 `--cov-fail-under=80`）。这是好实践，
但**别把覆盖率当目标**：100% 覆盖率里可以一个断言都没有（只调用不检查）。
更有用的指标是「**关键路径是否有测试**」：认证、支付、权限、数据写入这四类必须覆盖，
工具函数可以放一放。

## 1.14.14 生命周期与生产配置

`lifespan` 的基础（建表、引擎释放）在 1.12 已经给过，这里补三件 1.12 没讲的事。

### 逆序关闭

启动与关闭的顺序要**相反**：后启动的先关。
这样任何资源在关闭时，它依赖的东西都还在。

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    setup_logging()
    logger.info("应用启动中")
    app.state.engine = create_async_engine(settings.DATABASE_URL)
    try:
        async with app.state.engine.begin() as conn:
            await conn.run_sync(Base.metadata.create_all)
    except Exception:
        logger.exception("启动阶段初始化失败，终止启动")
        raise                                   # 关键：起不来就别起
    yield
    # 逆序关闭：后启动的先关
    await app.state.engine.dispose()
    logger.info("应用已关闭")
```

### 启动失败必须终止启动

实跑确认了这个行为：在 `yield` 之前抛异常，应用**直接起不来**。

```python
@asynccontextmanager
async def bad_lifespan(app: FastAPI):
    raise RuntimeError("数据库连不上")
    yield
```

```text
with TestClient(app) → 抛 RuntimeError: 数据库连不上
```

这正是我们要的：一个连不上数据库的实例若照常接受流量，只会把所有请求变成 500，
而且在负载均衡后面「看起来是健康的」。**启动即失败**让编排系统（K8s、Supervisor）
立刻发现并重试，比带病运行好得多。

关闭阶段的异常则相反——**不要因为清理失败而阻止进程退出**，用 `try/except` 包住、
记日志即可。启动失败要「响」，关闭失败要「稳」。

### 测试里的 lifespan 必须用 `with`

这是 1.12 没强调、实测很容易踩的一点：

```text
with TestClient(app) as c:      → ['db:open', 'db:close']     lifespan 正常执行
TestClient(app)                 → []                          startup 根本没跑
```

直接 `client = TestClient(app)` 时，lifespan 不会执行。所以
**凡是被测应用有 lifespan，测试必须用 `with` 语句**，否则你会测到一个
「资源没初始化」的应用，而那些断言可能因为空状态而「恰好通过」。

### 生产配置：三处开关

```python
env = os.getenv("ENVIRONMENT", "").strip().lower()
is_prod = env == "production"

app = FastAPI(
    title="知舟 API",
    debug=not is_prod,                                   # 生产关闭调试
    docs_url=None if is_prod else "/docs",               # 生产关文档
    redoc_url=None if is_prod else "/redoc",
    openapi_url=None if is_prod else "/openapi.json",
)
```

| 开关 | 生产取值 | 为什么 |
| --- | --- | --- |
| `debug` | `False` | 打开时会显示详细堆栈，且**绕过自定义异常处理器**（素材指出的冲突） |
| `docs_url` / `redoc_url` / `openapi_url` | `None` | 关掉文档等于关掉一份完整的接口清单——攻击者最爱的东西 |
| `ENVIRONMENT` | 环境变量传入 | 一切环境判断都从它派生，避免在代码里散落 `if xxx` |

> ⚠️ **注意**：`debug=True` 与自定义异常处理器**冲突**这件事值得单独记：
> 开发者本地打开 debug 图方便，而线上是关的——于是「本地看到的错误响应」
> 和「线上看到的」不一样，异常处理器的 bug 会被一路带到生产。
> 建议本地也保持 `debug=False`，靠日志看堆栈。

## 1.14.15 综合示例：给知舟装上这四层

把上面的内容组装成一个可运行的应用：统一响应、三类异常处理、访问日志、
三层架构，以及一套真实可跑的测试。为了聚焦，存储用内存字典代替数据库
（换回 1.12 的模型只需改 `dao/` 一层）。

```python
# zhizhou_app.py —— 可直接运行：python zhizhou_app.py
import json
import logging
import sys
import time
import uuid
from contextlib import asynccontextmanager
from typing import Annotated, Any, Generic, TypeVar

from fastapi import APIRouter, Depends, FastAPI, Query, Request
from fastapi.exceptions import RequestValidationError
from fastapi.responses import JSONResponse
from pydantic import BaseModel, Field
from starlette.middleware.base import BaseHTTPMiddleware

T = TypeVar("T")
logger = logging.getLogger("zhizhou")


# ---------- 日志 ----------
def setup_logging(level: int = logging.INFO) -> None:
    root = logging.getLogger()
    root.setLevel(level)
    root.handlers.clear()
    handler = logging.StreamHandler(sys.stdout)
    handler.setFormatter(logging.Formatter("%(levelname)s %(name)s %(message)s"))
    root.addHandler(handler)


# ---------- 统一响应 ----------
class BaseResponse(BaseModel, Generic[T]):
    code: int = 200
    message: str = "success"
    data: T | None = None


class ErrorResponse(BaseModel):
    code: int | str                # 框架类错误是 HTTP 码，业务错误是字符串业务码
    message: str
    error: dict = Field(default_factory=dict)


class PageInfo(BaseModel):
    page: int
    page_size: int
    total: int
    total_pages: int


# ---------- 业务异常 ----------
class BizError(Exception):
    code = "BIZ_ERROR"
    status_code = 400

    def __init__(self, message: str, detail: dict | None = None):
        super().__init__(message)
        self.message = message
        self.detail = detail or {}


class NotFoundError(BizError):
    code = "NOT_FOUND"
    status_code = 404


class ConflictError(BizError):
    code = "CONFLICT"
    status_code = 409


# ---------- 模型 ----------
class ArticleCreate(BaseModel):
    title: str = Field(..., min_length=1, max_length=100)
    content: str = Field(..., min_length=1)


class ArticleOut(BaseModel):
    id: int
    title: str
    content: str
    author_id: int


# ---------- DAO ----------
class ArticleDAO:
    """数据访问层：只做增删改查，不含业务判断。"""

    def __init__(self, store: dict[int, dict]):
        self.store = store                     # 存储由外部传入，DAO 自身无状态

    def list(self, skip: int, limit: int) -> list[dict]:
        items = sorted(self.store.values(), key=lambda a: a["id"])
        return items[skip:skip + limit]

    def count(self) -> int:
        return len(self.store)

    def get(self, article_id: int) -> dict | None:
        return self.store.get(article_id)

    def get_by_title(self, title: str) -> dict | None:
        return next((a for a in self.store.values() if a["title"] == title), None)

    def create(self, title: str, content: str, author_id: int) -> dict:
        article_id = max(self.store) + 1 if self.store else 1
        article = {"id": article_id, "title": title, "content": content, "author_id": author_id}
        self.store[article_id] = article
        return article


# ---------- Service ----------
class ArticleService:
    """业务逻辑层：规则在这里，HTTP 语义不在这里。"""

    def __init__(self, dao: ArticleDAO):
        self.dao = dao

    def create(self, data: ArticleCreate, author_id: int) -> dict:
        if self.dao.get_by_title(data.title) is not None:
            raise ConflictError("同名文章已存在", {"title": data.title})
        return self.dao.create(data.title, data.content, author_id)

    def get(self, article_id: int) -> dict:
        article = self.dao.get(article_id)
        if article is None:
            raise NotFoundError("文章不存在")
        return article

    def list_page(self, page: int, page_size: int) -> tuple[list[dict], PageInfo]:
        total = self.dao.count()
        items = self.dao.list(skip=(page - 1) * page_size, limit=page_size)
        return items, PageInfo(
            page=page, page_size=page_size, total=total,
            total_pages=(total + page_size - 1) // page_size,
        )


# ---------- 中间件 ----------
class AccessLogMiddleware(BaseHTTPMiddleware):
    async def dispatch(self, request: Request, call_next):
        request_id = request.headers.get("X-Request-ID") or uuid.uuid4().hex[:12]
        request.state.request_id = request_id
        start = time.perf_counter()
        try:
            response = await call_next(request)
        except Exception:
            logger.exception("request_failed method=%s path=%s request_id=%s",
                             request.method, request.url.path, request_id)
            raise
        elapsed = (time.perf_counter() - start) * 1000
        response.headers["X-Request-ID"] = request_id
        response.headers["X-Process-Time"] = f"{elapsed:.1f}ms"
        logger.info("method=%s path=%s status=%s elapsed_ms=%.1f request_id=%s",
                    request.method, request.url.path, response.status_code, elapsed, request_id)
        return response


# ---------- 组装 ----------
STORE: dict[int, dict] = {}

@asynccontextmanager
async def lifespan(app: FastAPI):
    setup_logging()
    app.state.store = STORE
    logger.info("应用启动完成")
    yield
    logger.info("应用已关闭")


app = FastAPI(title="知舟 API", debug=False, lifespan=lifespan)
app.add_middleware(AccessLogMiddleware)


@app.exception_handler(BizError)
async def biz_error_handler(request: Request, exc: BizError):
    # code 用字符串业务码（1.14.6）；HTTP 状态码另由 status_code 表达
    return JSONResponse(status_code=exc.status_code,
                        content=ErrorResponse(code=exc.code, message=exc.message,
                                              error=exc.detail).model_dump())


@app.exception_handler(RequestValidationError)

    errors = [{"field": ".".join(str(x) for x in e["loc"]), "msg": e["msg"], "type": e["type"]}
              for e in exc.errors()]
    return JSONResponse(status_code=422,
                        content={"code": 422, "message": "参数校验失败", "error": {"errors": errors}})


@app.exception_handler(Exception)
async def unhandled_handler(request: Request, exc: Exception):
    logger.exception("unhandled method=%s path=%s", request.method, request.url.path)
    return JSONResponse(status_code=500,
                        content={"code": 500, "message": "服务器内部错误", "error": {}})


# ---------- 依赖 ----------
def get_article_dao(request: Request) -> ArticleDAO:
    return ArticleDAO(request.app.state.store)


def get_article_service(dao: Annotated[ArticleDAO, Depends(get_article_dao)]) -> ArticleService:

    return 1        # 简化：真实项目用 1.13 的 get_current_user


router = APIRouter(prefix="/articles", tags=["文章"])

    data: ArticleCreate,

    return BaseResponse(data={"items": items, "pagination": pagination.model_dump()})


@router.get("/{article_id}", response_model=BaseResponse[ArticleOut])
async def read_article(
    article_id: int,
    service: Annotated[ArticleService, Depends(get_article_service)],
):
    return BaseResponse(data=service.get(article_id))


@router.get("/boom/error")
async def boom():
    raise RuntimeError("故意炸一个")


app.include_router(router)
```

## 常见坑

- **以为 `response_model` 会自动包装**。现象：接口返回 `{"id": 1}`，统一外壳没出现。
  原因：`response_model` 只校验与过滤，不改变结构。
  修法：手动返回 `BaseResponse(data=...)`，并把泛型参数写进 `response_model`。
- **用中间件包装所有响应**。现象：文件下载 0 字节、流式接口返回空 body，状态码却是 200。
  原因：`response.body_iterator` 被消费后无法再次发送（实跑复现）。
  修法：成功响应靠 `response_model`，失败响应靠异常处理器，中间件不碰 body。
- **500 返回的是纯文本**。现象：前端按 JSON 解析 500 时抛错。
  原因：没有 `@app.exception_handler(Exception)`，走了 Starlette 默认行为。
  修法：注册兜底处理器，返回统一 JSON。
- **兜底处理器把异常原文发给客户端**。现象：线上响应里出现文件路径与库版本。
  原因：直接把 `str(exc)` 或堆栈写进响应体。
  修法：响应固定为「服务器内部错误」，细节写日志（`logger.exception`）。
- **以为异常处理器注册顺序决定优先级**。现象：调换注册顺序后行为没变，误以为「兜底失效」。
  原因：匹配按异常类型的 MRO 进行，具体类型永远优先（实跑确认）。
  修法：不用担心顺序。真正该担心的是另外两件事：**中间件里抛出的异常只落兜底那一档**
  （`HTTPException(401)` 也变成 500），以及 **`debug=True` 时连兜底也被绕过**。
- **中间件里 `raise HTTPException` 拿不到你写的状态码**。现象：中间件里写 401，
  客户端收到 500（或兜底响应）而不是 401。
  原因：`ServerErrorMiddleware` 包在最外层，中间件抛的异常不再走类型匹配（实跑四组对照）。
  修法：中间件内部 `try/except` 后自行返回 `JSONResponse`，或抛兜底处理器认识的自定义异常。
- **日志重复打印**。现象：同一条日志出现两三次。
  原因：`setup_logging()` 被调用多次（热重载），每调用一次就加一组 handler（实跑：3 组 → 3 次）。
  修法：`root.handlers.clear()` 之后再添加，或加「已初始化」标志位。
- **日志里少了某些记录，程序却不报错**。现象：明明写了 `logger.info`，日志文件里没有。
  原因：Windows 下 `FileHandler` 默认用 cp936，遇到 emoji 抛 `UnicodeEncodeError`，
  而 logging 默认把它吞掉（只在 stderr 打一段 `Call stack`）。
  修法：显式 `encoding="utf-8"` + `errors="replace"`。
- **日志文件涨到几个 GB**。现象：磁盘告警。
  原因：用了裸 `FileHandler`，文件无限增长。
  修法：`TimedRotatingFileHandler`（按天）或 `RotatingFileHandler`（按大小）。
- **把整个请求体打进日志**。现象：日志平台里能搜到用户密码。
  原因：图省事 `logger.info(request_body)`。
  修法：先脱敏再记，或只记白名单字段；脱敏列表永远会漏，能不记就不记。
- **Service 里抛 `HTTPException`**。现象：换个入口（CLI、定时任务）复用 Service 时，
  只能拿到一个 HTTP 异常对象。
  原因：把 HTTP 语义写进了业务层。
  修法：定义 `BizError` 家族，在异常处理器里统一转成 HTTP 状态码。
- **测试 500 时直接报错**。现象：`TestClient(app).get("/boom")` 抛 `RuntimeError`，
  测试红一片。
  原因：`TestClient` 默认 `raise_server_exceptions=True`，会把服务端异常重新抛出。
  修法：断言兜底响应时用 `TestClient(app, raise_server_exceptions=False)`。
- **有 lifespan 的应用测试里没跑 startup**。现象：测试通过但资源没初始化。
  原因：`TestClient(app)` 不用 `with` 时 lifespan 不执行（实跑：事件列表为空）。
  修法：`with TestClient(app) as client:`。
- **依赖覆盖没清掉**。现象：单独跑通过，全量跑一片红。
  原因：`app.dependency_overrides` 是全局的，忘了 `clear()`。
  修法：在 fixture 收尾或 `finally` 里清理。
- **DAO 把数据放在自己的实例属性里**。现象：「邮箱已注册」的检查从不生效。
  原因：依赖跨请求不缓存，每次请求都是新实例（实跑：调用计数递增）。
  修法：状态放数据库 / Redis / `app.state`，DAO 与 Service 保持无状态。
- **`debug=True` 让本地与线上行为不一致**。现象：本地看到的是 FastAPI 调试页，
  线上是自定义 500 JSON，异常处理器的问题测不出来。
  原因：`debug=True` 时未捕获异常走内置调试页，绕过自定义处理器。
  修法：本地也保持 `debug=False`，靠日志看堆栈。

## 面试视角

> 🎯 **面试**：这一节的题目大多是「你踩过没踩过」型，背概念答不圆。

1. **「统一响应格式怎么做？三种方案你怎么选？」**
   考察点：是否真做过。答题要点：Pydantic 响应模型（成功路径，类型安全 + 自动文档）+
   全局异常处理器（失败路径，一处定义）；自定义响应类要多写 `response_class` 且丢掉校验；
   **中间件包装不推荐**——它要消费 `body_iterator` 重写响应，流式与文件下载会变成空 body，
   大文件还会把内存吃满（我实跑复现过空响应）。
2. **「`response_model` 和 `return` 一个字典有什么区别？」**
   考察点：基础是否扎实。答题要点：`response_model` 做**校验**与**字段过滤**
   （能挡住 `internal_cost`、`hashed_password` 这类字段外泄），并把结构写进 OpenAPI；
   但它**不会**帮你包装成统一外壳，外壳要手动返回。返回字典时没有校验，写错字段会静默通过。
3. **「FastAPI 的异常处理器是怎么匹配的？注册顺序有影响吗？」**
   考察点：是背的规则还是读的源码。答题要点：**按异常类型的 MRO 逐级向上查**，
   命中第一个注册过的类型即返回；所以具体类型天然优先，注册顺序不影响结果。
   边界更值得说：**中间件里抛出的异常不会回到类型匹配那一档**，只会落到兜底处理器
   （所以中间件里抛 401 得到的是 500）；`debug=True` 时连兜底也被绕过，返回带堆栈的响应；
   响应序列化阶段的错误发生得太晚，处理器拿不到。
4. **「业务异常和 HTTPException 怎么分工？」**
   考察点：分层意识。答题要点：业务层抛 `BizError` 家族（带业务码与状态码意图），
   HTTP 语义只在异常处理器或路由层出现。好处是 Service 能被 CLI / 定时任务 /
   消息消费者复用，也能脱离 HTTP 单测。依赖里抛出的业务异常同样会被全局处理器接住。
5. **「日志怎么配才算生产可用？」**
   考察点：有没有被日志坑过。答题要点：多 handler 分工（控制台 / 按天轮转的日常日志 /
   按大小轮转的错误日志）、显式 `encoding="utf-8"`（否则 Windows 上写 GBK，
   换工具看就是乱码）、`handlers.clear()` 防重复、生产 INFO 起步、
   结构化字段便于检索、**写入前脱敏**、请求 ID 贯穿全链路。
6. **「怎么让日志能还原一次事故现场？」**
   考察点：可观测性思路。答题要点：至少要有请求 ID、方法、路径、状态码、耗时、
   用户标识与错误堆栈，且这些字段能被检索；响应头回传 `X-Request-ID` 让用户能报号；
   错误日志独立成文件便于告警。缺任何一项都会让定位变成「翻全量日志」。
7. **「三层架构里路由层为什么不能写业务逻辑？」**
   考察点：分层价值。答题要点：写了就没法脱离 HTTP 测业务规则、也没法复用；
   而且规则散落在多个路由里，改一处漏三处。分层后「换库只改 dao、改规则只改 service、
   改格式只改 schemas/errors」，改动边界可预测——用 AI 改代码时这点尤其重要。
8. **「测试 FastAPI 应用，你一般怎么写？」**
   考察点：实战经验。答题要点：`TestClient` 打接口（同步、不占端口）；
   Service 层用 `Mock` 测规则，并断言 `assert_not_called()` 证明没有副作用；
   路由层用 `app.dependency_overrides` 覆盖依赖，且必须在收尾 `clear()`；
   断言 500 要传 `raise_server_exceptions=False`；有 lifespan 的 app 测试要用 `with`；
   需要并发场景时换 `AsyncClient` + `pytest-asyncio`。
9. **「怎么保证测试不会污染开发库？」**
   考察点：工程习惯。答题要点：绝不连生产/开发库；用 SQLite 内存库或事务回滚；
   每个测试自建自清（fixture 的 `yield` 之后清理）；依赖覆盖优先于真连库；
   CI 里用一次性容器。
10. **「生产环境有哪些必须关掉/打开的东西？」**
    考察点：安全意识。答题要点：关 `debug`、关 `/docs` `/redoc` `/openapi.json`；
    开结构化日志并脱敏；CORS 指定具体域名（1.11）；异常响应不含堆栈；
    启动失败即终止、关闭逆序且不阻塞；用 `ENVIRONMENT` 环境变量驱动这一切，
    不在代码里硬编码环境判断。

## 本章小结

1. 可维护性的四个杠杆都不产出功能，却决定项目三个月后还能不能改：**统一响应与异常、
   日志、分层、测试**，外加生命周期与生产开关。
2. 统一响应选 **Pydantic 响应模型 + 全局异常处理器**；`response_model` 只做校验与过滤，
   **不会自动包装**；分页要单独一层 `PageInfo`，`total_pages` 记得向上取整。
3. **不要用中间件包装响应**——它要消费一次性的 `body_iterator`，实跑结果是
   流式接口与文件下载变成 `200 + 空 body`。
4. 异常分三类：`HTTPException`（业务主动抛）、`RequestValidationError`（422，`loc`
   首段就是来源）、其他（默认 **500 纯文本**，必须自己兜底）。
5. 异常处理器**按异常类型的 MRO 匹配**，注册顺序无关。边界要记准：中间件里抛出的异常
   **不再回到类型匹配那一档**，只落兜底处理器（所以中间件里抛 401 会得到 500）；
   `debug=True` 时连兜底也被绕过，返回带堆栈的响应；响应序列化阶段的异常处理器拿不到。
6. 业务异常定义成 `BizError` 家族（业务码 + 意图状态码），HTTP 转换只写一处；
   500 的响应体里**绝不能出现异常原文**，细节进日志。
7. 日志四要素：logger / handler / level / formatter；级别是放行阈值，logger 与 handler
   两道都要过。配置里三件必需：`handlers.clear()`、显式 `utf-8` + `errors="replace"`、
   轮转 handler（按天 / 按大小）。
8. **编码问题的失败方式很隐蔽**：Windows 下不指定 `encoding` 会写 GBK、遇到 emoji 抛
   `UnicodeEncodeError`，而 logging 会**静默吞掉**——日志少了一条，程序却毫无异常。
9. 请求日志中间件负责「不关心是哪个接口」的横切逻辑：请求 ID、耗时、状态码；
   耗时用 `perf_counter`；异常记完再 `raise`；中间件里 `raise` 不会被异常处理器接住。
10. 结构化日志要配脱敏，且脱敏是最后一道防线——能不记录整个请求体就别记。
11. 三层边界一句话：**路由管协议、Service 管规则、DAO 管 SQL**。
    Service 不抛 `HTTPException`，DAO 不做业务判断，路由里没有业务逻辑。
12. 依赖的缓存规则是「**同请求内复用、跨请求不缓存**」，所以 DAO / Service 必须无状态，
    状态放数据库或 `app.state`。
13. 测试分层：Service 用 Mock（并断言没有副作用）、路由用 `TestClient` + 依赖覆盖、
    DAO 用真库（SQLite 内存库即可）。**`TestClient` 默认会把服务端异常重新抛出**，
    断言 500 要传 `raise_server_exceptions=False`。
14. 依赖覆盖是全局的，测试收尾必须 `clear()`；**有 lifespan 的 app 必须用
    `with TestClient(app) as c:`**，否则 startup 根本不执行。
15. 生命周期两句话：**启动失败要「响」（`raise` 终止启动），关闭失败要「稳」
    （`try/except` 记日志，不阻塞退出）**；关闭顺序与启动相反。
16. 生产三开关：`debug=False`、文档地址设为 `None`、环境由 `ENVIRONMENT` 驱动。
    `debug=True` 会绕过自定义异常处理器，导致本地与线上行为不一致。
