## 1.15.1 这一章做什么：蓝图、素材谱系与验收标准

### 素材是什么，本章用它的哪一部分

本章的素材不是讲义，而是**两个完整的真实项目**：

| 素材 | 规模 | 本章怎么用 |
| --- | --- | --- |
| `fastapi_project` | 后端 115 个文件（FastAPI + MySQL + Redis）+ Vue 前端 + 14 篇讲解 | **主体参考**：分层、表设计、路径契约、业务规则的现实版本 |

这里要先把一件事说清楚，否则后面的每句话都站不住：**本章只吸收这两个项目的「后端视角」**。
`fastapi_project` 里还有 7 篇前端讲解（3,597 汉字），第一章到第十五章都是后端工程，

另外，参考项目叫「水墨文章」，本书的项目叫**知舟**。本章沿用参考项目的分层与路径约定，

你在 GitHub 上仍能对照着读那份真实代码，而书里的代码是自洽的。

### 这个后端要支持什么

一页纸的需求，六个模块：

| 模块 | 能力 |
| --- | --- |
| 用户 | 图形验证码、邮箱验证码、注册、登录、注销、取当前用户 |
| 文章 | 首页列表（栏目筛选 + 搜索）、详情、草稿列表、草稿详情、保存（发布/存草稿）、上传头图 |
| 评论 | 发表评论、回复评论、评论树（含楼层号） |

### 验收标准：什么才算「做完了」

功能跑通只是及格线。本章的验收标准是四条，后面每节都在服务它们：

1. **能跑**：一条命令起服务，`/docs` 里能把六个模块的接口点一遍。
2. **有契约**：任何接口的返回形状都在第 1.15.2 节的表里查得到，不需要读代码猜。
3. **有测试**：关键路径（注册登录、发布、归属、上传、下载）有能一键跑的断言。
4. **能挑刺**：读者读完这一章，能对着这份真实代码说出它哪里会出问题。

> 💡 **提示**：第 4 条是本项目实战章独有的。素材里的讲解文档写了「这个项目怎么做」，
> 但没写「这个项目哪里做错了」。而后者才是你入职后最先需要的能力——
> 读别人的代码时，**知道自己在看什么、以及它在哪一步会崩**。

## 1.15.2 需求一页纸与接口契约

### 接口清单

先把素材六个模块的接口整理成一张表。这张表就是本章的地图：后面每一节都在实现它的某几行。

| 方法 | 路径 | 认证 | 入参 | 返回 |
| --- | --- | --- | --- | --- |
| GET | `/api/` | 否 | `page`、`article_type`、`keyword` | 文章列表 + 栏目列表 |
| GET | `/api/user/vcode` | 否 | — | `image/jpeg` 图片，并写 cookie |
| POST | `/api/user/ecode` | 否 | 邮箱 | 邮箱验证码 |
| POST | `/api/user/reg` | 否 | 用户名、口令、二次口令、邮箱码 | 注册结果 |
| POST | `/api/user/login` | 否 | 用户名、口令、图形码 | 用户信息 + 令牌 |
| POST | `/api/user/logout` | 否 | — | 注销结果 |
| GET | `/api/user/me` | 是 | — | 当前用户信息 |
| GET | `/api/article/detail` | 可选 | `article_id` | 文章详情 + 评论树 + 是否收藏 |
| GET | `/api/article/new-page` | 是 | — | 草稿列表 + 栏目/类型/标签字典 |
| POST | `/api/article/drafted` | 是 | 草稿 id | 草稿详情 |
| POST | `/api/article/save` | 是 | 文章保存请求体 | 文章 id |
| POST | `/api/article/upload` | 是 | 表单 `article_id` + 文件 | 图片访问路径 |
| POST | `/api/comment/add` | 是 | 文章 id、内容 | 评论结果 |
| POST | `/api/comment/reply` | 是 | 文章 id、内容、`reply_id`、`base_reply_id` | 回复结果 |
| POST | `/api/favorite/update_status` | 是 | 文章 id、`canceled` | 收藏结果 |
| GET | `/api/personal/` | 是 | `type_name`、`drafted` | 我的文章/收藏/评论 |

三处值得注意的设计：**只有两个接口是「可选登录」**（首页与文章详情，未登录也能看，
登录后多返回一个字段）；**上传接口用了表单编码**（1.15.9 讲）；**注销与登录都碰 cookie**。

### 响应契约：先把外壳定下来

参考项目的外壳是 `{code, msg, data}`：

```python
class Result(BaseModel):
    """统一响应外壳。"""
    code: int
    msg: str
    data: Any = None

    @staticmethod
    def success(data: Any = None, msg: str = "success") -> "Result":
        return Result(code=200, msg=msg, data=data)
```

它给每个状态码配了一个构造方法（`error` / `other` / `unauthorized` / `forbidden` / `not_found`），
在 Service 与 API 之间传 dict，最后由 API 层包成 `Result`。这个形状能工作，
但它埋了一件事，第 1.15.6 节会展开：**`code` 里同时装着 HTTP 码和业务码，就会出现两层真相**。

> ⚠️ **实跑边界（本章必须先声明）**：参考项目要 MySQL 与 Redis 的**服务端**，本机只装了客户端库，
> 所以**项目本体没有实跑**。本章的实验结果分两类，正文里逐处标明：
> 
> - **实跑**：表单、上传、下载、静态挂载、图片压缩这些技术点，本机依赖齐全，是真的跑了；
> - **拼接验证**：涉及数据库的业务路径，我把「Service 的那段代码」与「API 的那段代码」
>   拼成一个最小应用跑起来——这足以验证返回约定是否对得上，但**不能**代表整项目跑通。
>
> 这样标注才诚实：读者知道哪些结论可以照抄，哪些还需要自己在真环境里验一遍。

## 1.15.3 数据库设计：四张表、两个「位」与三条索引

### 初始化方式

```sql
DROP DATABASE IF EXISTS zhizhou;
CREATE DATABASE zhizhou CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
USE zhizhou;
```

`utf8mb4` 是必须的，不是可选项：MySQL 的 `utf8` 是**三个字节**的残缺实现，
存不下 emoji 与一部分生僻汉字（第 1.3 节讲过编码）。参考项目在这里是对的。

### 四张表

| 表 | 业务含义 | 关键字段 |
| --- | --- | --- |
| `user` | 用户 | `username`（唯一，邮箱格式）、`password`（bcrypt 哈希）、`nickname/picture/job` |
| `article` | 文章（含草稿） | `drafted`、`label_name`、`article_tag`、`browse_num`、`article_image` |
| `comment` | 评论与回复（同表） | `reply_id`、`base_reply_id`、`floor_number`、`ipaddr` |
| `favorite` | 收藏 | `canceled`（软删除） |

**两个「位」是这张表设计的核心**，都值得单独说明：

- `article.drafted`：`0` = 草稿，`1` = 已发布。用一位区分两种状态，而不是两张表。
  理由是**它们的字段完全相同**（草稿只差一次校验），拆表会带来两套 CRUD 与一次迁移。
- `favorite.canceled`：`0` = 收藏中，`1` = 已取消。这叫**软删除**——
  取消收藏不删行，只翻位。好处是「用户曾经收藏过」这个事实被保留了，
  而且高频操作从 `DELETE` 变成 `UPDATE`（第 1.12 节讲过两者的代价差别）。

> 💡 **提示**：什么时候该用「位」，什么时候该用状态表？判据是**状态会不会带自己的属性**。
> `drafted` 不需要（草稿没有"草稿时间"这种独立属性），`canceled` 不需要，所以用位。
> 一旦某个状态需要自己的字段（比如「已下架」要记下架原因与操作人），就该升格成表——
> 否则你会在主表上堆一排只有特定状态才有意义的列。

### 三条索引与它们对应的查询

```sql
ALTER TABLE article ADD INDEX idx_user_id (user_id);         -- 我的文章 / 个人中心
ALTER TABLE article ADD INDEX idx_label_name (label_name);   -- 首页按栏目筛选
ALTER TABLE article ADD INDEX idx_drafted (drafted);         -- 只查已发布
```

索引不是"加上更保险"，而要能对着查询说清楚：这三条分别服务
`WHERE user_id = ?`、`WHERE label_name = ?`、`WHERE drafted = 1`。

**这里要说一句容易忽略的话**：`drafted` 这种只有两个取值、且分布极不均的列，
单列索引的价值有限（优化器可能干脆不用它）。真正让首页列表跑得快的是
`(drafted, browse_num)` 这样的**复合索引**——它同时满足过滤与排序。
参考项目建了单列索引，属于"有用但不够"。

### 为什么不建外键

参考项目的 SQL 里**没有外键**，表间关系只存在于逻辑上：

```text
article.user_id   → user.user_id
comment.user_id   → user.user_id
comment.article_id→ article.id
favorite.user_id  → user.user_id
favorite.article_id → article.id
```

这是互联网项目的常见选择，理由是**外键的检查成本落在写路径上**，
而且分库分表后外键无法跨库。代价是**一致性靠应用层保证**：
删除用户时你得自己决定他的文章、评论、收藏怎么办——否则就是一堆没人认领的孤儿数据。

> ⚠️ **注意**：不建外键是一个**可以接受的取舍**，但它必须配一条兜底策略：
> 要么应用层做级联（删除用户时一并处理），要么把用户改成"逻辑删除"（也加一个位）。
> 参考项目两者都没有，属于取舍没做完——第 1.15.14 节会把它列进审读清单。

## 1.15.4 目录与分层骨架

### 九个目录

```text
app/
├── main.py           # 应用工厂与生命周期
├── api/              # 表示层：路由、参数解析、包统一响应
├── services/         # 业务层：规则校验、归属校验、多表编排
├── dao/              # 数据层：只做增删改查
├── models/           # SQLAlchemy ORM 模型
├── schemas/          # Pydantic 请求/响应模型（req/ 与 res/ 分开）
├── config/           # 配置、数据库、Redis
├── dependencies/     # 依赖组装（api_dp/ 与 service_dp/）
└── core/             # 通用能力：安全、图片处理、验证码、邮件
```

三层职责在 1.14.10 已经讲透了（路由管协议、Service 管规则、DAO 管 SQL），
这里只补一件 1.14 没讲的事：**这个项目把依赖组装单独抽了一层**。

### 依赖组装为什么分两层

```python
# dependencies/api_dp/article_dp.py —— FastAPI 的注入入口
def get_article_service(db: Session = Depends(get_db)) -> ArticleService:
    return build_article_service(db)


# dependencies/service_dp/article_dp.py —— 纯手工的构造函数注入
def build_article_service(db: Session) -> ArticleService:
    return ArticleService(
        db,
        ArticleDao(db),
        UserDao(db),
        CommentDao(db),
        FavoriteDao(db),
    )
```

分成两层的收益是**第二个文件完全不认识 FastAPI**：

| 收益 | 具体表现 |
| --- | --- |
| 组装关系一眼可见 | 一个函数列出 Service 的全部依赖，不用翻构造函数 |
| 可脱离框架复用 | `build_article_service(db)` 是普通函数，脚本、定时任务、测试都能调 |
| 换实现改动集中 | 以后给 ArticleDao 加缓存，只改这一处 |

代价是**多了一层间接**：想搞清楚「这个路由最终用到哪些 DAO」，要跳两个文件。
这一层值不值得加，取决于项目规模——**五个 Service 以上就值**，
因为它把「谁依赖谁」从散落各处变成了一处清单。

> 💡 **提示**：`dependencies/` 不放进 `api/`，是个好习惯。它让"依赖组装"成为
> 一个和"路由""业务""数据"平级的关注点，而不是散在路由文件顶部的装饰性函数。

### 对照：最小骨架去掉什么

素材里的 `fastapi_best_practice` 是同一套分层的最小形态。它保留了
`api / dao / models / schemas / services / dependencies`，但去掉了
CORS 中间件与静态挂载——**这两样是"部署形态"而非"代码结构"**，
所以最小骨架先不管它们。这个对照很有用：它说明骨架里哪些是**结构必需**的
（分层与依赖注入），哪些是**场景可选**的（跨域、静态资源、验证码、邮件）。

## 1.15.5 配置、启动与静态挂载

### 配置类

```python
# config/app_config.py
from pathlib import Path
from pydantic_settings import BaseSettings, SettingsConfigDict


class AppConfig(BaseSettings):
    env: str = "test"
    db_url: str = "sqlite:///./zhizhou.db"        # 只放无口令的默认值
    db_echo: bool = False                          # 生产关掉：否则每条 SQL 都落日志

    page_count: int = 10
    article_header_image_path: str = "/images/"
    upload_dir: str = "resource/images/article/header"

    jwt_secret_key: str = ""                       # 必须由环境变量提供，见下
    jwt_algorithm: str = "HS256"
    jwt_access_token_expire_minutes: int = 60 * 24

    model_config = SettingsConfigDict(env_file=".env", env_file_encoding="utf-8")

    @property
    def project_root(self) -> Path:
        return Path(__file__).resolve().parents[2]

    @property
    def upload_dir_abs(self) -> Path:
        return self.project_root / self.upload_dir


settings = AppConfig()
```

四处与参考项目不同，每一处都有理由：

| 参考项目 | 本章写法 | 为什么改 |
| --- | --- | --- |
| `db_url` 里写 `root:123456` | 默认值不含口令 | 写进代码默认值等于**提交进 Git**；真实的库地址从环境变量来 |
| `db_echo: bool = True` | `False` | 打开时每条 SQL 都打印，生产上等于把 I/O 送给日志 |
| `jwt_secret_key` 有默认值 | 空串，强制外部提供 | 1.13 讲过：默认密钥忘了改 = 任何人可伪造令牌。空串会让它在启动时就暴露 |
| `class Config` | `model_config = SettingsConfigDict(...)` | `class Config` 在 Pydantic v2 已废弃（实跑会拿到 `PydanticDeprecatedSince20` 警告，注释里写明 v3 将移除） |

### 应用工厂与生命周期

```python
# main.py
@asynccontextmanager
async def lifespan(app: FastAPI):
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)     # 轻量建表；生产用 Alembic
    images_dir.mkdir(parents=True, exist_ok=True)          # 静态目录不存在会挂载失败
    yield
    await engine.dispose()                                 # 逆序关闭（1.14.14）


def create_app() -> FastAPI:
    app = FastAPI(title="知舟 API", lifespan=lifespan)
    app.add_middleware(CORSMiddleware,
                       allow_origins=settings.cors_origins,   # 具体域名，不用 ["*"]
                       allow_credentials=True,
                       allow_methods=["*"], allow_headers=["*"])
    app.include_router(router)
    app.mount("/images", StaticFiles(directory=str(images_dir)), name="images")
    return app
```

`images_dir.mkdir(...)` 这句看着多余，其实是必需的：目录不存在时
`StaticFiles` 挂载会直接失败，而**首次部署时那个目录就是不存在**。

### 一处必须点出的真实隐患：CORS

参考项目里是 `allow_origins=["*"]` 配 `allow_credentials=True`。1.11 已经实测过：
Starlette 在这种情况下**不报错**，而是回显请求来源——任何网站都能带着 Cookie 读你的接口。
这是**静默的越权放行**，不是配置错误。参考项目按开发期写、上线忘了改，
正是这类配置最典型的走法。

### 静态挂载的行为（实跑）

```text
GET /images/a.txt          → 200  （命中，直接返回文件）
GET /images/sub/b.txt      → 200  （子目录也可）
GET /images/nope.txt       → 404
GET /images/               → 404  （没有 index.html 时不列目录）
GET /images/../main.py     → 404  （穿越被 StaticFiles 拦住）
GET /images/%2e%2e/main.py → 404  （百分号编码也拦）
```

四条 `404` 都符合预期。挂载的好处是**不用给每个文件写下载接口**：
静态资源交给它，业务文件（需要授权的）才自己写接口。

## 1.15.6 统一响应与错误码：两层真相的来处

`{code, msg, data}` 这个外壳本身没问题，问题在于**`code` 字段装的是什么**。

参考项目的实际行为是两种混用：

```text
① Service 正常返回 → API 层 Result(code=200, ...)   → HTTP 200 + 业务 200
② Service 校验失败 → Result(code=400, msg="请输入文章标题") → HTTP 200 + 业务 400
③ 依赖抛 HTTPException → 框架返回 {"detail": "未登录"}     → HTTP 401，**没有 code 字段**
```

②③ 合起来就是两层真相：**同一件事（失败）有两种表达**，
而前端要同时看 HTTP 状态码和响应体里的 `code` 才能判断。要看这有多容易出错，
翻一下参考项目自己的前端代码就够了：

```javascript
// 前端的响应拦截器（节选）
if (res.code === 401) { removeToken(); window.location.href = '/#/login' }
```

这一行的意图是"业务码 401 时跳登录"，但**它永远不成立**——因为 401 在参考项目里
是 ③ 那条路来的（`HTTPException` → `{"detail": ...}`，没有 `code`）。
真正兜住它的是下面那个 `error.response?.status === 401` 分支。
一个分支是死代码，另一个分支在工作，而两者写着同一个意图。

本章的约定（与 1.14.6 一致）是**分开装**：

| 装什么 | 谁来表达 | 例子 |
| --- | --- | --- |
| 协议层结果 | HTTP 状态码 | 401 未认证、403 无权限、404 不存在、409 冲突、422 校验失败 |
| 业务语义 | 字符串业务码 | `EMAIL_TAKEN`、`ARTICLE_NOT_FOUND` |

于是失败响应统一长这样，前端只需判断一处：

```json
{"code": "CONFLICT", "message": "同名文章已存在", "error": {"title": "知舟入门"}}
```

> ⚠️ **注意**：本节说的"参考项目有缺陷"，指的是**它自己的约定不统一**，
> 而不是"HTTP 200 + 业务码"这种风格错了。那种风格（前端只看 `code`）
> 在内部系统里很常见，也能自洽——**前提是全项目统一**，包括 401 这类框架产生的错误
> 也要换成它的形状。参考项目恰恰缺的就是这一步：它在 Service 层统一了，却没接住框架层。

## 1.15.7 用户模块：认证闭环

### 六个接口连成一条链

```text
GET  /api/user/vcode  → 生成图形码，写 cookie vcode（300 秒）
POST /api/user/ecode  → 生成邮箱码，写 Redis（300 秒）
POST /api/user/reg    → 校验图形码/邮箱码 → 查重 → bcrypt 存口令 → 建用户
POST /api/user/login  → 校验图形码 → 校验口令 → 签发令牌
POST /api/user/logout → 删 cookie
GET  /api/user/me     → 认证依赖 → 查库 → 返回脱敏后的用户
```

三个工程细节值得单独说：

1. **两种验证码的存法不同**：图形码放 **cookie**（它本来就由同一次请求下发、下一次请求带上，
   天然是会话性质）；邮箱码放 **Redis**（服务端校验、带过期、可能被多次尝试）。
2. **注册的校验顺序有讲究**：先格式（邮箱、口令长度、二次一致）→ 再验证码 → 最后查重。
   顺序反了会让"邮箱已被注册"变成一种探测手段（每次探测都要先过验证码也不亏）。
3. **登录成功后要移除口令字段**：参考项目在 Service 里显式做这一步——
   这是对的，但更稳的做法是用 Pydantic 响应模型在出口处过滤（1.14 的 `response_model`），
   因为它不会因为"忘了某一个接口"而漏掉。

### 令牌放在哪：一个真实的跨模块不一致

参考项目的登录接口做了两件事：**把令牌写进 cookie**，同时把令牌放进响应体 `data`。
而它的认证依赖读的是请求头：

```python
def get_current_user(authorization: Optional[str] = Header(None)) -> dict:
    if not authorization:
        raise HTTPException(401, "未登录，请先登录")
    parts = authorization.split()
    if len(parts) != 2 or parts[0].lower() != "bearer":
        raise HTTPException(401, "Token 格式错误")
    payload = decode_access_token(parts[1])
    ...
```

那写入 cookie 的那一半有没有被用上？我去读了它的前端代码：

```javascript
// frontend/src/utils/request.js
const token = getToken()                       // ← 从 localStorage 读
if (token) config.headers.Authorization = `Bearer ${token}`
```

```javascript
// frontend/src/utils/auth.js
const TOKEN_KEY = 'fastapi_token'
export function getToken() { return localStorage.getItem(TOKEN_KEY) }
```

**结论：cookie 那条路是死代码。** 前端的令牌来自响应体（登录时存进 localStorage），
请求时放进 `Authorization` 头。而后端写 cookie 用的还是 `httponly=True`——
一个更安全、但**根本没被读**的通道。

这件事的教学价值在于：它**只能靠读两端才能发现**。只读后端，你会以为认证走 cookie；
只读前端，你会以为后端也读 localStorage。第 1.15.14 节把它列进审读清单，
修法也很直接：**要么改成读 cookie，要么删掉写 cookie 那两行**——
留着它比删掉更危险，因为下一个接手的人会以为它有用。

### 认证依赖里的一个取舍

参考项目在 `get_current_user` 里**自己 `SessionLocal()`**，而不是 `Depends(get_db)`：

```python
db = SessionLocal()
try:
    user = UserDao(db).find_by_userid(int(user_id))
finally:
    db.close()
```

好处是依赖签名简单、可以脱离请求上下文复用；代价是**事务边界不统一**——
其他依赖都走 `get_db` 的 `yield` 收尾，只有它自建会话。1.12 讲过，
事务边界统一在依赖收尾才能保证"一个请求一个事务"，所以本章的写法是：

```python
def get_current_user(
    db: Annotated[AsyncSession, Depends(get_db)],
    authorization: str | None = Header(None),
) -> User:
    ...
```

一个会话、一个边界、一个关闭点。

## 1.15.8 文章模块：草稿与发布、归属校验、伪分页

### 保存文章的判定顺序

`save_article` 是全章最值得抄的一段逻辑，因为它把三类判定排成了固定顺序：

```python
def save_article(self, user_id: int, article_id: int, title, content, drafted, **rest):
    self._check_ownership(article_id, user_id)          # ① 先问「这是你的吗」

    if drafted == 1:                                     # ② 再问「发布的内容合法吗」
        if not title_str:
            raise InvalidParamError("请输入文章标题")
        if not content_str:
            raise InvalidParamError("请输入文章内容")
    else:
        if not title_str and not content_str:             # 草稿更宽：有一个就行
            raise InvalidParamError("草稿至少需要填写标题或内容")

    safe_image = self._filter_image(rest.get("article_image"))   # ③ 最后过滤不可信输入

    if article_id == -1:
        return self.dao.insert_article(...)              # ④ 落库：新建
    return self.dao.update_article(article_id, ...)      #    或更新
```

顺序不能换：**先做归属判断、再校验内容**，否则别人可以通过错误文案的变化探测到
「这篇文章存在但内容为空」这类信息。而 `article_id == -1` 表示新建这个约定，
是前端与后端之间的一种暗号——它不直观，但在这个项目里是一致的。

> ⚠️ **注意**：`article_id == -1` 是**用魔法值表达语义**。它的危险在第 ④ 步的条件上：
> 参考项目写的是 `if article_id == -1: ... elif article_id > -1: ...`。
> 那 `article_id = -2` 呢？两个分支都不命中，函数**隐式返回 `None`**，
> 而 API 层紧接着 `r["code"]`——第 1.15.14 节会给出这次的实测结果（是 500）。
> 更稳的写法是把新建表达成 `article_id: int | None = None`，让"没有 id"这件事显式。

### 归属校验：判据是资源归属，不是登录状态

```python
def _check_ownership(self, article_id: int, user_id: int) -> None:
    if article_id <= -1:
        return                                   # 新建：没有归属问题
    owner_id = self.dao.get_article_owner_id(article_id)
    if owner_id is None:
        raise NotFoundError("文章不存在")          # 不存在与越权返回同一个响应
    if owner_id != user_id:
        raise NotFoundError("文章不存在")          # 越权也报 404（1.13.9）
```

登录只回答"你是谁"，不回答"这篇文章是不是你的"。
而越权时返回 404 而不是 403，是为了不泄露"这个 id 存在"这一事实。

异常用 `PermissionError`（参考项目）还是自定义的 `NotFoundError`（本章）？
参考项目在 API 层用 `except PermissionError` 转成 403——能工作，但有两个问题：
`PermissionError` 是内置异常，**别的地方抛出它会被同一个处理器误接**；
而且每个接口都要重复写这段 `try/except`。本章的做法是 1.14.6 那一套：
自定义业务异常 + 一个全局处理器，路由里不出现 `try`。

### 分页：一个必须点出来的「伪分页」

```python
count = page * 10
query.filter(Article.drafted == 1).order_by(Article.browse_num.desc()).limit(count)
```

这是**累加式截断**，不是分页：`page=2` 时返回**前 20 条**（包含第 1 页的 10 条），
而不是第 11–20 条。前端把返回列表每次替换掉，看起来"翻页正常"，
但数据量一大就会露馅：第 5 页要传 50 条，第 50 页要传 500 条——
**越翻越慢，越翻越浪费**。

正确写法在第 1.12 节给过：`offset = (page - 1) * page_size`，并且返回 `total` 让前端渲染页码。
素材自己的讲解文档里也承认了这一点（"建议 DAO 返回 limit/offset，避免伪分页"），
这一条算是素材的自我修正。

### 收藏与个人中心：同一模式的两次复用

`favorite` 只有两个操作，而它的实现把「一次写入表达两种意图」做得挺干脆：

```python
def update_status(self, article_id, user_id, canceled) -> None:
    row = self.dao.get(user_id, article_id)
    if row is None:
        self.dao.insert(user_id, article_id, canceled)   # 第一次：插入
    else:
        row.canceled = canceled                          # 之后：改位
```

配套的读取函数有个**反直觉的约定**：没有收藏记录时返回 `1`（表示"未收藏"）。
`is_favorite: 1` 表示**没收藏**——这跟字段名正好相反，前端很容易搞反。
本章改成 `bool`，并把「无记录」显式当成 `False`：

```python
async def is_favorited(self, user_id: int, article_id: int) -> bool:
    row = await self.dao.get(user_id, article_id)
    return row is not None and row.canceled == 0
```

个人中心是同一模式的第三次应用（三个列表共用一次字段加工）：

```python
def _enrich(self, articles: list[Article]) -> list[dict]:
    """把 ORM 转 dict，并把图片路径归一为对外 URL。"""
    out = []
    for a in articles:
        item = to_dict(a)
        item["article_image"] = normalize_article_image(item.get("article_image"))
        out.append(item)
    return out
```

> 💡 **提示**：这三个模块（收藏、个人中心、我的评论）在分层上做的是同一件事——
> **查数据 → 加工展示字段 → 返回**。所以它们最适合用来检验分层是否分干净了：
> 如果这三处都要改路由层，说明业务逻辑漏在表示层了。

## 1.15.9 表单处理：`Form` 的两种写法与四个陷阱

FastAPI 收表单有两条路：**声明式**（`Form(...)`，有类型与校验）和
**原始方式**（`await request.form()`，字段名不定时用）。先把两条路都跑一遍。

### 声明式：`Form(...)`

```python
from typing import Annotated
from fastapi import FastAPI, Form
from pydantic import Field

app = FastAPI()


@app.post("/login")
def login(
    username: str = Form(...),                              # 必填
    password: str = Form(...),
    bio: str | None = Form(None),                           # 可选，缺省为 None
    subscribe: bool = Form(False),                          # 带默认值
):
    return {"username": username, "bio": bio, "subscribe": subscribe}


@app.post("/register")
def register(
    username: Annotated[str, Form(min_length=3, max_length=20,
                                 pattern=r"^[a-zA-Z0-9_]+$",
                                 description="用户名（3-20 位字母、数字、下划线）")],
    password: Annotated[str, Form(min_length=8)],
):
    return {"ok": True}
```

表单字段的校验规则与查询参数完全一致（`min_length` / `max_length` / `pattern` / `description`），
失败时也是 422，只是 `loc` 的第一段是 `body`：

```text
POST /register  username=al&password=123
→ 422  detail[0].loc = ["body", "username"]   type = string_too_short
       detail[1].loc = ["body", "password"]   type = string_too_short
```

顺带一个现代写法：FastAPI 0.113 起支持**表单模型**，字段多时比一长串参数清楚：

```python
class ArticleForm(BaseModel):
    title: Annotated[str, Field(min_length=1)]
    tags: str = ""


@app.post("/article")
async def create(data: Annotated[ArticleForm, Form()]):
    return data.model_dump()
```

实跑可用。它把"表单字段"变成了一个普通的 Pydantic 模型，于是校验、
序列化、文档三件事都复用已有的机制。

### 原始方式：`await request.form()`

字段名未知或数量不定时（例如来自第三方编辑器的多段上传），声明式没法写：

```python
@app.post("/raw")
async def raw(request: Request):
    form = await request.form()                 # 类字典结构，值可能是 str 或 UploadFile
    return {
        "keys": sorted(form.keys()),
        "categories": form.getlist("category"),  # 同名多值
        "total": len(form),
    }
```

三件事要知道（都实跑确认过）：

1. **多值必须用 `getlist()`**。`form["category"]` 与 `form.get("category")` 在
   同名多值时返回的是**最后一个**值，不是第一个、也不是列表——
   写成 `get()` 会静默拿到一部分数据。
2. **值可能是 `UploadFile`**：遍历时要用 `isinstance(value, UploadFile)` 分开处理。
3. **测试里传多值的写法有坑**：`client.post(..., data={"category": ["a", "b"]})` 是对的；
   写成 `data=[("category", "a"), ("category", "b")]`（元组列表）时，
   httpx 会**一个字段都不发、连 `Content-Type` 都没有**，于是 `request.form()` 安静地返回空字典。

### 四个陷阱（全部实跑验证）

**陷阱一：缺 `python-multipart` 时，报错发生在「定义接口」那一刻。**

素材说"使用表单功能前需安装依赖"，实际比这更早也更响：

```text
未安装 python-multipart：
  定义普通 JSON 接口          → 正常
  定义 Form 接口（装饰器执行） → RuntimeError: Form data requires "python-multipart"
                                 to be installed. You can install "python-multipart" with:
                                 pip install python-multipart
```

这个失败方式是**好事**：它在 import 阶段就把问题摆出来，而不是等你上生产才发现。
（FastAPI 还专门区分了"装成了 `multipart` 这个包"的情况，并给出卸载提示。）

**陷阱二：`Form` 与 JSON Body 互斥，但不会报错——只是有一个永远缺字段。**

```python
@app.post("/mix")
async def mix(body: str = Body(...), name: str = Form(...)): ...
```

这个路由**能成功注册**，请求时才炸：发 JSON 时 `name` 永远 `missing`，
发表单时 `body` 永远 `missing`。所以「混用」的代价不是报错，而是
**一个参数静默永远取不到值**。

**陷阱三：`bool` 字段的值域比你以为的宽，也比你以为的坑。**

| 表单值 | 结果 | 表单值 | 结果 |
| --- | --- | --- | --- |
| `true` / `TRUE` / `True` | `True` | `false` / `FALSE` | `False` |
| `1` / `yes` / `on` | `True` | `0` / `no` / `off` | `False` |
| `2` / `abc` | **422 `bool_parsing`** | **空字符串 `""`** | **`False`（不报错）** |

最后一行是最现实的坑：浏览器**未勾选的复选框**提交的就是空字符串。
如果你的语义是"这个字段必填"，那它会被静默当成 `False` 通过。
要区分"没勾选"与"没提供"，就得用 `bool | None = Form(None)`。

**陷阱四：`File(...)` 的默认值写法不统一。**

```python
cover: UploadFile = File(...)                      # 必填
thumbnail: UploadFile | None = File(default=None)  # 可选：要写 default=
```

写成 `File(None)` 虽然也能跑，但 `File(...)` 与 `File(default=...)` 是两种语法，
团队里最好只留一种，省得每次都要想。

## 1.15.10 文件上传：`UploadFile`、校验与路径穿越防护

### `UploadFile` 的能力

| 属性/方法 | 说明 |
| --- | --- |
| `file.filename` | 上传时的原始文件名（**不可信**，见下文） |
| `file.content_type` | MIME 类型，如 `image/png` |
| `file.size` | 文件大小（字节） |
| `await file.read(size)` | 读取；不指定 `size` 读全部 |
| `await file.write(data)` | 写入 |
| `await file.seek(offset)` | 移动指针 |
| `await file.close()` | 关闭（请求结束时会自动关） |

> ⚠️ **实跑纠正**：素材说"`file.size` 在 FastAPI 中通常为 `None`，需通过读取内容或文件系统获取"。
> 在本版本（FastAPI 0.136.3 + Starlette 1.6.0）实测**有值**：传 5 字节文件得到 `size = 5`。
> 所以做大小校验可以直接看 `file.size`，不必先整体读进内存——
> 对一个 10 MB 的上限判断来说，这个差别意味着**不用先吃下 10 MB 再拒绝**。

它底层是 `SpooledTemporaryFile`：小文件在内存、超过阈值落临时文件，
所以**不会一次性把整个文件读进内存**（这是它比 `bytes = File(...)` 好的地方）。

### 三种保存方式

```python
# ① 一次性读写：简单，但内存里先有一份完整副本
content = await file.read()
Path(dest).write_bytes(content)

# ② aiofiles 异步写入：读到内存后在事件循环外落盘，不阻塞
content = await file.read()
async with aiofiles.open(dest, "wb") as f:
    await f.write(content)

# ③ 分块流式：始终只有 1 个 chunk 在内存，GB 级文件的唯一选择
CHUNK = 1024 * 1024
async with aiofiles.open(dest, "wb") as f:
    while chunk := await file.read(CHUNK):
        await f.write(chunk)
```

| 方式 | 内存占用 | 适用 |
| --- | --- | --- |
| ① 一次性 | 高（全量） | 小于 10 MB、图省事 |
| ② `aiofiles` | 中 | 一般生产环境 |
| ③ 分块流式 | 极低 | 超大文件 |

选用判据只有一条：**最大的合法文件有多大**。上限是 5 MB 的图片，
② 就够了；允许传 2 GB 的压缩包，只有 ③ 能活。

### 校验：类型白名单 + 大小 + `seek(0)`

```python
ALLOWED_TYPES = {"image/jpeg", "image/png", "image/webp"}
MAX_FILE_SIZE = 10 * 1024 * 1024


@app.post("/upload-validated")
async def upload_validated(file: UploadFile = File(...)):
    if file.content_type not in ALLOWED_TYPES:
        raise UnsupportedMediaTypeError(f"不支持的类型：{file.content_type}")
    content = await file.read()
    if len(content) > MAX_FILE_SIZE:
        raise PayloadTooLargeError(f"文件超过限制：{len(content)}/{MAX_FILE_SIZE} 字节")
    await file.seek(0)           # ★ 关键：read() 后指针停在末尾
    return {"filename": file.filename, "size": len(content)}
```

`seek(0)` 那句是实跑踩出来的：读一次之后再读**得到 0 字节**。

```text
read#1 = 10  →  read#2 = 0  →  seek(0) 后 read#3 = 10
```

所以"先校验大小、再保存到磁盘"这种最自然的写法，如果不 `seek(0)`，
**落盘的文件会是 0 字节**——而且请求还返回 200。

> ⚠️ **注意**：`content_type` 是**客户端声称**的类型，不要当安全边界。
> 真正的校验要看内容（图片就试着用 Pillow 打开一次）——打不开就拒绝。
> 这一条参考项目没做：它的上传接口不看类型也不看大小，直接把内容写盘，
> 然后把整个文件交给 Pillow 去压缩。传一个 1 GB 的 `.txt`，它会先落盘、再抛异常。

### 路径穿越防护：三层，但只有第三层真的拦住

用户提供的文件名里可以是 `../../etc/passwd` 或 `..\..\windows\system32\cmd.exe`，
直接拼接就是目录穿越。三层防护：

```python
UPLOAD_DIR = Path("./uploads").resolve()


def safe_filename(name: str) -> str:
    name = Path(name).name                       # ① 取文件名
    name = re.sub(r"[^\w\-.]", "_", name)        # ② 只留安全字符
    return name or "unnamed"


def save_path(name: str) -> Path:
    path = UPLOAD_DIR / safe_filename(name)
    if not path.resolve().is_relative_to(UPLOAD_DIR):   # ③ 二次验证
        raise InvalidPathError("非法文件路径")
    return path
```

**实跑结果会让人意外**：

| 输入 | ① `Path(name).name` | ② 正则后 | ③ 是否仍在目录内 |
| --- | --- | --- | --- |
| `../../etc/passwd` | `passwd` | `passwd` | ✅ |
| `a/b/c.png` | `c.png` | `c.png` | ✅ |
| `a b;c.png` | `a b;c.png` | `a_b_c.png` | ✅ |
| `evil.php%00.png` | 同左 | `evil.php_00.png` | ✅ |
| **`..`** | **`..`** | **`..`** | **❌ 拦住了** |

前两层看着很可靠，但**单独用它俩会漏掉 `..`**：`Path("..").name` 返回的就是 `..`，
而正则的白名单里含 `.`，所以 `..` 原样通过。真正拦住它的只有第三层
`is_relative_to`。这条结论只有把三层**逐层打印出来**才看得见——
"我做了三层防护"和"这三层各自拦住了什么"是两件事。

（`is_relative_to` 需要 Python 3.9+；3.8 及更早用 `str.startswith` 判断，
但要小心 `/data/uploads2` 这种前缀相同的目录。）

## 1.15.11 评论与回复：楼层号、评论树与 N+1

### 一张表存两级

评论与回复放在同一张 `comment` 表里，靠三个字段区分：

| 字段 | 一级评论 | 回复 |
| --- | --- | --- |
| `reply_id` | `0` | 被回复的那条评论 id |
| `base_reply_id` | `0` | 所属一级评论的 id |
| `floor_number` | `max + 1`（按文章递增） | 无意义（可存 0） |

为什么要有 `base_reply_id`？因为**回复可以嵌套**：A 评论 → B 回复 → C 回复 B。
若只有 `reply_id`，"C 属于哪一层楼"就要靠递归向上找；
有了 `base_reply_id`，一次 `WHERE base_reply_id = ?` 就能拿到整条楼的所有回复。
这是**用冗余字段换查询扁平化**的典型案例，代价是插入时要多写一个值。

楼层号的生成靠"查最大值再加一"：

```python
async def insert_comment(self, article_id: int, user_id: int, content: str, ipaddr: str):
    result = await self.db.execute(
        select(func.max(Comment.floor_number)).where(Comment.article_id == article_id)
    )
    next_floor = (result.scalar() or 0) + 1
    self.db.add(Comment(article_id=article_id, user_id=user_id, content=content,
                        ipaddr=ipaddr, reply_id=0, base_reply_id=0,
                        floor_number=next_floor))
```

> ⚠️ **注意**：`max + 1` 在**并发**下会重复：两个请求同时读到 5，就都会写 6。
> 单机低并发没事，但这是那种"平时没事、某天出现两条 6 楼"的问题。
> 彻底的做法是把楼层号交给数据库（自增列或 `SELECT ... FOR UPDATE`），
> 或者接受重复并在展示层按时间排序——**但必须知道自己选的是哪一种**。

### 评论树的组装与它自带的 N+1

```python
async def get_comment_tree(self, article_id: int) -> list[dict]:
    roots = await self._roots(article_id)              # 一级评论
    out = []
    for root in roots:
        replies = await self._replies(root.id)         # ← 每条一级评论一次查询
        for r in replies:
            from_user = await self._user(r.user_id)    # ← 每条回复再一次
            to_user = await self._user(r.reply_id 的作者)  # ← 再一次
            ...
```

一段二十条评论的文章会打出几十次查询，这就是 **N+1**（1.12 讲过原理）。
修法有两条，都要知道代价：

| 做法 | 查询次数 | 代价 |
| --- | --- | --- |
| 预加载 / `selectinload` | 固定 3 次 | 需要 ORM 关系定义，返回结构要重新塑形 |
| 一次查询全表该文的评论 + 用户表 join | 1–2 次 | SQL 变复杂，需要在内存里拼树 |

> 💡 **提示**：评论树这种"天然嵌套、层级不深"的结构，**在应用层拼**通常比
> 在 SQL 里递归更可读。关键是别在循环里查库——先把该文所有评论与涉及的用户
> 一次性取回来，再在内存里按 `base_reply_id` 分组。1.12 的 N+1 一节给的正是这个思路。

还有一处细节做得对、值得抄：返回结构里的用户信息**必须脱敏**，
因为 `model_to_dict` 会把 ORM 对象的全部字段带出来，**包括 `password`**：

```python
def _sanitize_user(self, user: dict) -> dict:
    return {k: v for k, v in user.items() if k != "password"}
```

漏了这一步，文章详情接口就会把作者的口令哈希发给任何访客。

## 1.15.12 文件下载与断点续传：Range 必须手写对

### 三种下载方式怎么选

| 方式 | 适用 | 内存 | 断点续传 |
| --- | --- | --- | --- |
| `FileResponse` | 磁盘上的文件 | 低 | **自带**（见下） |
| `StreamingResponse` | 大文件 / 动态生成 | 极低 | 需自己解析 `Range` |
| 静态挂载 | 公开的静态资源 | 低 | 由 `StaticFiles` 处理 |

> ⚠️ **实跑纠正**：素材的速查表把 `FileResponse` 的断点续传写成"否"。实测不是：
> 请求 `GET /dl` 带 `Range: bytes=10-19`，`FileResponse` 返回 **206** 且
> `Content-Range: bytes 10-19/100`，`Content-Length: 10`，响应体正好是那 10 个字节；
> 它还会自动带上 `Accept-Ranges: bytes`。
> **结论：磁盘上的文件，`FileResponse` 就够用，不用手写 Range。**

### 手写 `Range` 时，素材那版代码有两个缺陷

需要自己控制读取过程时（比如文件解密、权限校验后才允许下载），
就得解析 `Range` 自己发。基础形状是：

```python
@app.get("/download/{filename}")
async def download(request: Request, filename: str):
    path = safe_path(filename)
    if not path.exists():
        raise NotFoundError("文件不存在")
    size = path.stat().st_size
    range_header = request.headers.get("Range")
    if not range_header:
        resp = StreamingResponse(iter_file(path), media_type="application/octet-stream")
        resp.headers["Content-Length"] = str(size)
        resp.headers["Accept-Ranges"] = "bytes"
        return resp

    start, end = _parse_range(range_header, size)          # ★ 解析与校验都在这里
    resp = StreamingResponse(iter_range(path, start, end),
                             status_code=206, media_type="application/octet-stream")
    resp.headers["Content-Range"] = f"bytes {start}-{end}/{size}"
    resp.headers["Content-Length"] = str(end - start + 1)
    return resp
```

素材那版把解析直接写在路由里，**照抄它跑三个请求就会看到两处错**：

```text
Range: bytes=50-40   → 206  Content-Range: bytes 50-40/100   Content-Length: -9    ← 负长度
Range: bytes=200-    → 206  Content-Range: bytes 200-99/100  Content-Length: -100  ← 起始越界
Range: bytes=-20     → 206  Content-Range: bytes 0-20/100    响应体 21 字节         ← 语义错
```

- 前两条：`start > end`、`start >= size` 时它没做边界判断，于是发出了**负数**
  `Content-Length`——客户端解析这个头就会出错。
- 第三条：`bytes=-20` 按 RFC 9110 的语义是**最后 20 个字节**，
  不是"从 0 到 20"。它把后缀区间当成了普通区间。

正确的解析函数要把四种情况都覆盖，而且 `416` 要按规范带上文件总大小：

```python
class RangeNotSatisfiableError(HTTPException):
    """416：请求的范围不可满足。按规范同时告知总大小，客户端才知道该从哪续。"""

    def __init__(self, size: int):
        super().__init__(status_code=416, detail="Range 无效",
                         headers={"Content-Range": f"bytes */{size}"})


def _parse_range(header: str, size: int) -> tuple[int, int]:
    """解析 `Range: bytes=start-end`。非法或越界一律 416。"""
    if not header.startswith("bytes="):
        raise RangeNotSatisfiableError(size)
    spec = header[len("bytes="):]
    if spec.startswith("-"):                      # bytes=-N：最后 N 字节（不是 0 到 N）
        n = int(spec[1:] or 0)
        if n <= 0:
            raise RangeNotSatisfiableError(size)
        return max(size - n, 0), size - 1
    start_str, _, end_str = spec.partition("-")
    try:
        start = int(start_str)
        end = int(end_str) if end_str else size - 1
    except ValueError:
        raise RangeNotSatisfiableError(size)
    if start >= size or start > end:              # ★ 这两条判断是素材缺的
        raise RangeNotSatisfiableError(size)
    return start, min(end, size - 1)
```

改完之后各种输入各归其位（实跑，文件 100 字节）：

```text
无 Range            → 200  Content-Length: 100  Accept-Ranges: bytes
bytes=10-19         → 206  Content-Range: bytes 10-19/100   Content-Length: 10
bytes=90-           → 206  Content-Range: bytes 90-99/100   Content-Length: 10
bytes=0-999         → 206  Content-Range: bytes 0-99/100    Content-Length: 100（end 被夹到末尾）
bytes=-20           → 206  Content-Range: bytes 80-99/100   Content-Length: 20
bytes=abc           → 416  Content-Range: bytes */100
bytes=200-          → 416  Content-Range: bytes */100        （起始越过文件末尾）
bytes=50-40         → 416  Content-Range: bytes */100        （start > end）
items=1-2 / bytes=  → 416                                     （单位或取值非法）
```

## 1.15.13 图片路径契约：存相对路径、对外拼前缀

这一节短，但它是本项目**最容易在跨模块时出错**的一块：数据库里存什么、
磁盘上放哪里、对外 URL 长什么样——三个地方必须约定一致。

### 三层约定

| 位置 | 形态 | 例子 |
| --- | --- | --- |
| 磁盘 | `项目根/resource/images/article/header/<文件名>` | `resource/images/article/header/a.jpg` |
| 数据库 | **相对路径** | `article/header/a.jpg` |
| 对外 URL | 前缀 + 相对路径 | `/images/article/header/a.jpg` |

**数据库存相对路径**是关键决策：换域名、换 CDN、加静态前缀都不用改数据。
存绝对 URL 的话，一次域名迁移就要写数据订正脚本。

### 兼容旧数据的归一函数

```python
IMAGE_URL_PREFIX = "/images/"


def normalize_article_image(raw: str | None) -> str:
    if not raw:
        return ""
    img = raw.lstrip("/")
    if "/" not in img:                       # 旧数据只存了文件名
        img = f"article/header/{img}"
    return IMAGE_URL_PREFIX + img
```

实跑它的六种输入：

```text
存 None                          → ""
存 ""                            → ""
存 "article_001.jpg"             → "/images/article/header/article_001.jpg"   ← 旧数据被补全
存 "article/header/a.jpg"        → "/images/article/header/a.jpg"
存 "/article/header/a.jpg"       → "/images/article/header/a.jpg"             ← 前导斜杠被吃掉
存 "https://cdn.example.com/a.jpg" → "/images/https://cdn.example.com/a.jpg"  ← 垃圾
```

最后一行说明这个兼容函数**只对"文件名或相对路径"成立**。所以在写入口
必须把外来的 URL 挡掉（参考项目确实是这么做的）：

```python
def filter_image(raw: str | None) -> str:
    """只接受相对路径：过滤前端临时 blob、外链与协议相对地址。"""
    if not raw or not isinstance(raw, str):
        return ""
    s = raw.strip()
    if s.startswith(("blob:", "http", "//")):
        return ""
    return s
```

> ⚠️ **注意**：这个过滤与归一函数**必须配套使用**，缺一个就会出问题：
> 只有归一没有过滤，外链会被拼成 `/images/https://...`；
> 只有过滤没有归一，旧数据的图片全是 404。这也是为什么这类"路径契约"
> 要写成一对函数、放在一个文件里，而不是散在 Service 的各处。

### 上传接口的完整流程

```text
① ensure_upload_dir()                       保证目录存在
② 生成文件名                                  ★ 别用秒级时间戳，见下
③ 校验类型与大小                             content_type 白名单 + size
④ 分块写盘                                   避免整文件进内存
⑤ 用 Pillow 压缩成 jpg                        宽 1200、quality 80
⑥ 数据库存相对路径                            article/header/<文件名>
⑦ 返回对外 URL                                /images/article/header/<文件名>
```

第 ② 步参考项目用的是 `time.strftime('%Y%m%d_%H%M%S')`。实跑一下就知道问题在哪：

```text
连续生成 2000 次文件名 → 只有 1 个不同的名字（同一秒内）
```

**同一秒内的两次上传会覆盖**，前一张图就永久丢了。改成
`uuid4().hex` 或"时间戳 + 随机后缀"都能解决：

```python
newname = f"{datetime.now():%Y%m%d_%H%M%S}_{uuid4().hex[:8]}.jpg"
```

- **`tests/` 目录只有一个空 `__init__.py`**，而 `pyproject.toml` 里配了

- **`get_article_detail` 是 `async def`，但它调用的是同步的 SQLAlchemy 查询**。

> 💡 **提示**：把 1、2、4 三条放一起看，能看出一个共同的病根：
> **Service 层的返回约定不唯一**。有的方法返回 `{code, msg, data}`，有的返回裸 dict，
> 有的返回 `{state, url}`。只要约定不唯一，调用方就一定会漏掉某一种——
> 而漏掉的代价是 500。这也是第 1.14 章为什么坚持"响应形状只在一个地方定义、
> 失败路径走异常处理器"：**不确定的形状比错误的形状更贵**。

### 部署脚本

参考项目的 `scripts/start.sh` 值得学它的四个点：

```bash
#!/usr/bin/env bash
set -euo pipefail                                   # ① 任何一步失败就整体失败
cd "$(dirname "$0")/.."                             # ② 不依赖调用者的当前目录

mkdir -p logs run

# ③ 兼容 Linux/macOS 与 Windows(Git Bash) 的虚拟环境路径
PYTHON=""
if [ -x ".venv/bin/python" ]; then PYTHON=".venv/bin/python"
elif [ -f ".venv/Scripts/python.exe" ]; then PYTHON=".venv/Scripts/python.exe"
else echo "[start] ERROR: 找不到 .venv" >&2; exit 1; fi

# ④ 用 pid 文件防重复启动
PID_FILE="run/app.pid"; LOG_FILE="logs/app.log"
if [ -f "$PID_FILE" ] && kill -0 "$(cat "$PID_FILE" 2>/dev/null)" 2>/dev/null; then
  echo "[start] 已在运行 (pid=$(cat "$PID_FILE"))"; exit 0
fi

nohup "$PYTHON" -u main.py > "$LOG_FILE" 2>&1 &     # -u：日志不缓冲，否则出事时看不到最后几行
echo $! > "$PID_FILE"
```

`-u` 这个参数容易被忽略但很关键：不加它，Python 会缓冲标准输出，
**进程崩溃时最后几行日志还在缓冲区里**——而那几行往往正是原因。

## 常见坑

- **Service 返回裸 dict，API 层按 `{code, msg, data}` 取值**。现象：某个接口必崩，
  报 `KeyError: 'code'` 或 `TypeError: 'NoneType' object is not subscriptable`。
  原因：同一层里存在两套返回约定，调用方只处理了一套。
  修法：约定唯一——成功走统一的响应模型，失败走异常（1.14.6）。
- **分支出错时函数隐式返回 `None`**。现象：某些 id 取值下 500，其他值正常。
  原因：`if a == X / elif a > X` 漏掉了第三种取值。
  修法：让入口条件穷尽（`else` 兜底并抛异常），或用 `None` 显式表达"没有 id"。
- **`Form` 接口收不到字段，但报的是 422 `missing`**。现象：字段明明传了。
  原因：请求用了 JSON 编码，而该接口声明的是表单；两者互斥且**不报编码错误**。
  修法：确认客户端用 `application/x-www-form-urlencoded` 或 `multipart/form-data`（1.15.9）。
- **`file.read()` 之后再次读取得到 0 字节**。现象：文件落盘是 0 字节，接口返回 200。
  原因：指针停在末尾。
  修法：第二次读之前 `await file.seek(0)`。
- **未勾选的复选框让 `bool` 字段静默为 `False`**。现象："必填的同意条款"没勾也通过了。
  原因：空字符串被解析为 `False`。
  修法：用 `bool | None = Form(None)` 区分"没提供"。
- **上传文件名没做唯一化**。现象：用户反馈"上传的新头图不生效"。
  原因：秒级时间戳文件名，同秒覆盖。
  修法：`uuid4().hex` 或"时间戳 + 随机后缀"。
- **只靠 `Path(name).name` 与正则防穿越**。现象：以为做了两层防护，其实 `..` 能过。
  原因：`Path("..").name` 就是 `..`，正则白名单含 `.`。
  修法：必须加第三层 `path.resolve().is_relative_to(UPLOAD_DIR)`。
- **`Range` 解析缺边界判断**。现象：客户端收到负数 `Content-Length`。
  原因：`start > end` 或 `start >= size` 时没返回 416。
  修法：解析与校验放在一个函数里，四种情况都覆盖（1.15.12）。
- **把 `bytes=-20` 当成"从 0 到 20"**。现象：客户端请求最后 20 字节，拿到前 21 字节。
  原因：后缀区间在 RFC 9110 里是"末尾 N 字节"。
  修法：`bytes=-N` 单独分支处理。
- **静态挂载目录不存在**。现象：启动直接报错。
  原因：`StaticFiles` 要求目录存在。
  修法：`mkdir(parents=True, exist_ok=True)` 之后再 mount。
- **`allow_origins=["*"]` 配 `allow_credentials=True`**。现象：接口照常工作，
  但任何网站都能带着 Cookie 读数据。原因：这不是配置错误，而是静默放行。
  修法：列具体域名（1.11、1.15.5）。
- **同步查询写在 `async def` 路由里**。现象：并发一上来所有请求都变慢。
  原因：阻塞调用卡住事件循环。
  修法：路由改用 `def`（自动进线程池），或整链路换异步驱动。
- **`model_to_dict` 把 `password` 一起返回**。现象：接口响应里出现口令哈希。
  原因：按 `__dict__` 遍历 ORM 对象会带出所有列。
  修法：出口处用响应模型过滤，或显式脱敏（1.14.9）。
- **写 cookie 与读请求头不一致**。现象：认证"时好时坏"，或某个通道完全没生效。
  原因：跨模块约定不统一，且两边都能跑通（一边是死代码）。
  修法：只留一条通道，删掉另一条。

## 面试视角

> 🎯 **面试**：这一节的题目是"你做过什么项目、踩过什么坑"的实战版。背框架概念答不圆，
> 能讲出具体现象与修法才是真做过。

1. **「你怎么从一个需求开始设计一个后端？」**
   考察点：有没有完整走过一遍。答题要点：先出三张纸——**接口清单**（方法/路径/认证/入参/返回）、
   **表设计**（表、关键字段、索引）、**目录与分层骨架**；然后才是写代码。
   顺序反了（先写路由）会得到一堆需要回头改的接口形状。
2. **「这张表的状态字段，你怎么决定用位还是单独建表？」**
   考察点：建模判断力。答题要点：看**状态是否需要自己的属性**。
   `drafted`（草稿/发布）、`canceled`（收藏/取消）不需要，用位；
   一旦需要"下架原因/操作人"，就必须升格成表，否则主表会堆一排只有特定状态才有意义的列。
3. **「为什么不建外键？」**
   考察点：知不知道取舍的另一半。答题要点：外键的检查成本在写路径上、分库后无法跨库，
   所以互联网项目常不建；**但必须配兜底策略**——应用层级联删除，或用户也做逻辑删除。
   只说"为了性能"而说不出兜底方案，说明取舍没做完。
4. **「上传功能你怎么做才安全？」**
   考察点：有没有被真实攻击打过。答题要点：类型白名单（且以内容为准，不只看 `content_type`）、
   大小上限、**文件名唯一化**、**路径穿越三层防护**（`Path().name` + 正则 + `is_relative_to`）、
   下载不要直接把用户文件名拼进路径、清理用定时任务而不是 HTTP 接口。
5. **「怎么实现断点续传？」**
   考察点：读没读过 RFC。答题要点：解析 `Range` 头，返回 206 +
   `Content-Range: bytes start-end/size`；`accept-ranges: bytes` 告诉客户端支持；
   越界或格式错返回 416（最好带 `Content-Range: bytes */size`）；
   **`bytes=-N` 是末尾 N 字节**，不能当普通区间处理；磁盘文件直接用 `FileResponse` 就有。
6. **「评论这种带层级的结构怎么存？」**
   考察点：数据结构设计。答题要点：同表存两级，`reply_id`（回复谁）+
   `base_reply_id`（属于哪条一级评论）——**冗余一个字段换查询扁平化**；
   一级评论的楼层号按文章维度 `max+1`，注意并发下会重复。
7. **「这个项目的评论列表为什么慢？」**
   考察点：N+1 意识。答题要点：循环里逐条查用户与回复 → N+1；
   修法是把该文的评论与涉及的用户一次性取回，在内存里按 `base_reply_id` 拼树；
   或 `selectinload` 预加载。别在循环里查库——这是最常见也最容易修的性能问题。
8. **「接手一个别人的项目，你怎么开始？」**
   考察点：能否发现真问题。答题要点：先跑起来，再按数据流读一遍
   （路由 → Service → DAO），重点看三处：**返回约定是否唯一**、
   **事务边界是否一致**、**配置里有没有硬编码密钥与错误的默认值**。
   本章 1.15.14 那张 12 条的清单就是这个过程的产出。
9. **「业务异常和 HTTP 状态码怎么对应？」**
   考察点：分层与协议素养。答题要点：业务层抛自定义异常（不带 HTTP 语义），
   在处理器里集中映射；401/403/404/409/422 各司其职；
   **越权返回 404 而不是 403**，避免确认资源存在。
10. **「上线前你要检查什么？」**
    考察点：工程习惯。答题要点：配置外置（密钥/口令不进 Git）、
    CORS 不用通配、关文档、Alembic 而不是 `create_all`、上传下载的校验、
    日志脱敏与轮转、500 不含堆栈、关键路径有测试、静态资源交给 Nginx。

## 本章小结

1. 项目从**三张纸**开始：接口清单、表设计、目录与分层骨架。顺序不能反。
2. 表设计的两个手法：**状态用位**（当状态没有自己的属性时）、**软删除**（
   `canceled` 翻位而不删行，保住"曾经收藏过"这个事实）；索引要对着具体查询说清楚服务谁。
3. 不建外键是可接受的取舍，**但必须配一条兜底策略**，否则留下孤儿数据。
4. 依赖组装分两层（`api_dp` / `service_dp`）的收益是"组装关系一处可见、且能脱离框架复用"，
   代价是多一次跳转；五个 Service 以上就值得加。
5. **配置里三个绝不能留的默认值**：密钥、明文口令、`db_echo=True`。
   `class Config` 在 Pydantic v2 已废弃，用 `model_config`。
6. CORS 的 `["*"]` + `allow_credentials=True` 是**静默越权**，不是配置错误（1.11 实测）。
7. **统一响应外壳的关键不是形状，而是唯一性**：`code` 要么装 HTTP 码、要么装业务码，
   全项目一致；而框架产生的 401 也要纳入同一形状，否则会出现"前端判了但永远不成立"的死分支。
8. 表单两条路：**声明式 `Form(...)` 优先**（有类型与校验），字段名不定时用 `await request.form()`；
   多值必须 `getlist()`（`get()` 给的是最后一个）；`Form` 与 JSON Body 互斥且**不报编码错误**。
9. `bool` 表单字段接受 `1/yes/on` 等，且**空字符串静默为 `False`**；
   `file.size` 在本版本**有值**（素材说没有，已纠正）。
10. 上传四件套缺一不可：**类型白名单、大小上限、`seek(0)`、文件名唯一化**；
    `read()` 之后不 `seek(0)` 会落盘 0 字节而接口返回 200。
11. 路径穿越防护三层里，**只有第三层 `is_relative_to` 拦得住 `..`**——
    `Path("..").name` 就是 `..`，正则白名单也含 `.`。
12. 图片路径契约：**磁盘放文件、数据库存相对路径、对外拼前缀**；
   归一函数与过滤函数必须配套，否则要么外链变垃圾路径、要么旧数据全 404。
13. 下载：磁盘文件用 `FileResponse`（**它自带 Range 支持**，素材说反了）；
   手写时 `Range` 的四种情况都要覆盖，`bytes=-N` 是**末尾 N 字节**，
   越界一律 416，否则会发出负数 `Content-Length`。
14. 读别人的项目时，**返回约定是否唯一**与**事务边界是否一致**是最容易出事的两处；
   本章的 12 条清单里有 3 条都源自前者的不唯一。
15. 部署脚本四个细节：`set -euo pipefail`、不依赖当前目录、兼容两种虚拟环境路径、
   pid 文件防重复启动；`python -u` 让崩溃前的日志不被缓冲吞掉。
