## 1.8.1 一次访问到底发生了什么

在地址栏输入 `https://www.example.com` 并回车，到页面显示出来，大致经过八步：

| 步骤 | 发生了什么 | 用到的协议 |
| --- | --- | --- |
| 1 | 查本机 IP / 子网掩码 / 网关 / DNS（开机时由 DHCP 下发或静态配置） | DHCP |
| 2 | 把域名解析成 IP 地址 | DNS |
| 3 | 与目标 IP 的 443 端口建立连接 | TCP（三次握手） |
| 4 | 协商加密参数、验证证书 | TLS |
| 5 | 发出 HTTP 请求报文 | HTTP |
| 6 | 服务端返回 HTTP 响应报文 | HTTP |
| 7 | 浏览器解析 HTML、请求 CSS/JS/图片（重复 2–6） | HTTP |
| 8 | 渲染页面 | — |

工程上要记住两个「容易忽略但面试常问」的点：

- **DNS 也走网络**，所以它同样会超时、会被污染、会缓存。
  本地开发常用的 `hosts` 文件就是「绕过 DNS」；改了 `hosts` 不生效通常是浏览器自己的
  DNS 缓存没清（Chrome 可以访问 `chrome://net-internals/#dns` 清缓存）。
- **第 3–4 步（连接与加密）在首次请求里占掉相当一部分耗时**。
  这就是 HTTPS 服务端要开启会话复用、客户端要用连接池（1.7 的 `httpx.AsyncClient`
  就是这个目的）的原因。

## 1.8.2 五层模型：一层一层套信封

网络协议是分层的，每一层只关心自己的事，**并为上一层提供服务**：

| 层 | 数据单位 | 关键地址 | 代表协议 |
| --- | --- | --- | --- |
| 应用层 | 报文（message） | 域名 / URL | HTTP、DNS、SMTP |
| 传输层 | 段（segment） | **端口** | TCP、UDP |
| 网络层 | 包（packet） | **IP 地址** | IP、ICMP |
| 数据链路层 | 帧（frame） | **MAC 地址** | Ethernet |
| 物理层 | 比特 | — | 电信号 / 光信号 |

发送时**逐层加头**，接收时逐层拆头——像套信封：

```text
# 发送方（逐层封装）
HTTP 报文
  → + TCP 头（源端口、目标端口、序号…）
  → + IP 头（源 IP、目标 IP…）
  → + 以太网头（源 MAC、目标 MAC…）
  → 二进制电信号

# 接收方（逐层解封装），顺序相反
```

每一层的头都必须**定长或自带长度信息**，否则对方不知道到哪里为止。
这也解释了一个经典问题：**为什么需要 IP 又要 MAC？**
IP 是「最终目的地」，MAC 是「下一跳」——数据先发给网关（用网关的 MAC），
再由网关一段一段转发到目的地，如同寄快递时写的是收件人地址，
但每一站的分拣中心只看「下一站」的标签。

## 1.8.3 IP、子网掩码与端口

- **IP 地址**回答「哪台机器」。IPv4 是 32 位，写成一串四段十进制数，如 `192.168.1.100`。
- **端口**回答「机器上的哪个程序」。HTTP 默认 80，HTTPS 默认 443；
  客户端一侧的端口由操作系统从**临时端口范围**里分配
  （IANA 建议 `49152–65535`，Linux 默认 `32768–60999`）。
- **子网掩码**回答「是不是同一个局域网」：把 IP 与掩码做**按位与**，
  结果相同就在同一子网，可以直接通信；否则要交给网关转发。

```text
192.168.1.10  → 11000000.10101000.00000001.00001010
255.255.255.0 → 11111111.11111111.11111111.00000000
按位与结果     → 11000000.10101000.00000001.00000000  = 192.168.1.0
```

`192.168.1.20` 与它按位与的结果同样是 `192.168.1.0`，所以两者在同一子网。
CIDR 记法 `192.168.1.10/24` 里的 `/24` 就是「掩码前 24 位是 1」。

> 💡 **提示**：`127.0.0.1`（localhost）永远指向本机；`0.0.0.0` 表示「所有网卡」，
> 服务监听 `0.0.0.0:8000` 才能被局域网内其他机器访问，
> 只监听 `127.0.0.1:8000` 则只有本机连得上——这是部署 AI 服务时最常踩的坑之一。

## 1.8.4 TCP 与 UDP：可靠与快

| 对比 | TCP | UDP |
| --- | --- | --- |
| 是否建立连接 | 是（三次握手） | 无连接 |
| 可靠性 | 可靠：有确认与重传 | 不可靠：发出去就不管 |
| 顺序 | 保证按序到达 | 不保证 |
| 开销 | 大 | 小 |
| 典型用途 | HTTP、数据库、SSH | DNS、音视频、游戏状态同步 |

**三次握手**的目的是双方都确认「我能发、能收，对方也能发、能收」：

```text
客户端                          服务端
  |------ SYN（seq=x）----------->|      第一次：我想连你
  |<----- SYN+ACK（seq=y, ack=x+1）|      第二次：收到，我也想连你
  |------ ACK（ack=y+1）---------->|      第三次：收到，连接建立
```

**为什么是三次而不是两次？** 两次的话，服务端无法确认客户端是否收到了自己的 SYN；
一个延迟到达的旧 SYN 会让服务端白白建立连接并等在那里。

**四次挥手**则是因为 TCP 是**双向**的，每一方的「我不发了」要单独确认：

```text
客户端                          服务端
  |------ FIN ------------------->|      我要关了
  |<----- ACK --------------------|      知道了（但我可能还有数据要发）
  |<----- FIN --------------------|      我也发完了
  |------ ACK ------------------->|      知道了，关闭
```

主动关闭的一方会进入 **`TIME_WAIT`** 状态并等待 `2MSL`（报文最大生存时间的两倍），
目的是确保最后的 `ACK` 能到达、并让本次连接的迟到报文自然消亡。
所以「服务端出现大量 `TIME_WAIT`」通常意味着**这台机器在主动大量关闭连接**——
在压测或高并发反向代理场景下很常见，也是排查连接数问题的常见入口。

## 1.8.5 HTTP 报文长什么样

HTTP 是**文本协议**，这一点很重要：它能被人直接读懂，也能被日志直接记录。

**请求报文**：

```http
POST /api/v1/documents HTTP/1.1
Host: api.example.com
Content-Type: application/json
Authorization: Bearer eyJhbGciOi...
Accept: application/json
Content-Length: 42

{"title": "公告", "content": "正文"}
```

```text
请求行：方法 + 路径 + 协议版本
请求头：一组「键: 值」（Host / Content-Type / Authorization / Accept…）
空行：分隔头与体（不能省）
请求体：POST / PUT / PATCH 才有，GET 通常没有
```

**响应报文**：

```http
HTTP/1.1 201 Created
Content-Type: application/json; charset=utf-8
Location: /api/v1/documents/42
Set-Cookie: session=abc123; HttpOnly; Secure

{"id": 42, "title": "公告"}
```

```text
状态行：协议版本 + 状态码 + 原因短语
响应头：Content-Type / Set-Cookie / Cache-Control…
空行
响应体：JSON / HTML / 二进制
```

几个必须记住的头：

| 头 | 方向 | 作用 |
| --- | --- | --- |
| `Host` | 请求 | 目标域名（同一 IP 上区分多个站点） |
| `Content-Type` | 双向 | 体的类型与编码，如 `application/json; charset=utf-8` |
| `Content-Length` | 双向 | 体的字节数 |
| `Authorization` | 请求 | 认证凭据（如 `Bearer <token>`） |
| `Accept` | 请求 | 我能接受什么类型 |
| `Set-Cookie` | 响应 | 让客户端保存 Cookie |
| `Cache-Control` | 双向 | 缓存策略 |

> 🔥 **常见坑**：**中文字符乱码**绝大多数是 `Content-Type` 里少了 `charset=utf-8`，
> 或者声称 `Content-Length` 却按字符数而不是**字节数**计算。
> HTTP 的头是按字节走的，长度一定用 `len(body.encode("utf-8"))`。

## 1.8.6 方法、幂等性与 REST 设计

| 方法 | 语义 | 幂等 | 有请求体 |
| --- | --- | --- | --- |
| `GET` | 读取资源 | 是 | 通常无 |
| `POST` | 创建资源 / 执行操作 | **否** | 有 |
| `PUT` | 整体替换资源 | 是 | 有 |
| `PATCH` | 局部更新资源 | 不保证 | 有 |
| `DELETE` | 删除资源 | 是 | 通常无 |
| `HEAD` | 只要响应头 | 是 | 无 |

**幂等**的意思是：同一个请求执行一次和执行多次，**服务端的状态结果相同**。
这不是学术概念，它直接决定能不能安全重试：

- `GET`、`PUT`、`DELETE` 幂等，所以**客户端超时后可以放心重试**；
- `POST` 不幂等，重试可能**创建出两条订单**。要支持重试就得引入
  **幂等键（Idempotency-Key）**——客户端生成一个唯一键，服务端记录并拒绝重复提交。

REST 的资源设计约定：

```text
GET    /api/v1/documents            列表（分页用 ?limit=&offset=）
POST   /api/v1/documents            创建
GET    /api/v1/documents/{id}       详情
PUT    /api/v1/documents/{id}       整体替换
PATCH  /api/v1/documents/{id}       局部更新
DELETE /api/v1/documents/{id}       删除
GET    /api/v1/documents/{id}/chunks  子资源
```

三条经验：

1. **路径用名词的复数**（`/documents`），动作交给 HTTP 方法，不要写 `getDocumentList`；
2. **路径里带版本**（`/api/v1`），否则将来改动会破坏老客户端；
3. **过滤、排序、分页用查询串**（`?status=ready&sort=-created_at&limit=20`），
   不要塞进路径。

> ⚠️ **注意**：`GET` 不应该有副作用——「用 GET 删除」会同时坏掉幂等语义、
> 缓存与爬虫行为，是典型的反面教材。

## 1.8.7 状态码：按类别记，再记特例

状态码是**三类信息**：类别（第一位）、具体含义（后两位）、给谁看。

| 类别 | 含义 | 出现问题时先看谁 |
| --- | --- | --- |
| `1xx` | 信息性（`101` 切换协议） | 少见，主要在 WebSocket |
| `2xx` | 成功 | — |
| `3xx` | 重定向 | 客户端要跟着跳 |
| `4xx` | **客户端**的错（请求本身有问题） | 改客户端 |
| `5xx` | **服务端**的错 | 查服务端日志 |

必背的九个：

| 码 | 含义 | 什么时候用 |
| --- | --- | --- |
| `200 OK` | 成功 | 查询、更新成功返回数据 |
| `201 Created` | 已创建 | `POST` 成功，配 `Location` 头 |
| `204 No Content` | 成功但没有响应体 | `DELETE` 成功 |
| `301` / `302` | 永久 / 临时重定向 | 换域名、跳登录 |
| `400 Bad Request` | 请求格式/参数不合法 | 参数校验失败 |
| `401 Unauthorized` | **未认证**（没登录、token 无效） | 缺凭据或凭据过期 |
| `403 Forbidden` | **已认证但无权限** | 登录了但不是管理员 |
| `404 Not Found` | 资源不存在 | 也可以用来隐藏资源是否存在 |
| `409 Conflict` | 与当前状态冲突 | 唯一键重复、重复提交 |
| `500` / `502` / `504` | 服务端内部错误 / 网关收到无效响应 / 网关超时 | 未捕获异常、下游挂了 |

两个高频追问：

- **`401` 与 `403` 的区别**：`401` 是「你是谁我不知道」，`403` 是「我知道你是谁，但你不能」。
- **`502` 与 `504` 的区别**：都是网关（Nginx）说的话——`502` 是**上游返回了无效响应**
  （进程崩了、端口没起），`504` 是**上游超时**（进程活着但太慢）。
  排查方向完全不同。

## 1.8.8 无状态、Cookie、Session 与 Token

HTTP 本身是**无状态**的：服务端不记得上一个请求是谁发的。
但「登录状态」又必须跨请求保持，于是有了三种机制：

| 机制 | 数据存在哪 | 特点 |
| --- | --- | --- |
| Cookie | **客户端**（浏览器自动带上） | 只能存少量文本；必须设 `HttpOnly` / `Secure` |
| Session | **服务端**（通常放 Redis） | 服务端可随时失效；需要存储与查询 |
| Token（JWT 等） | 客户端持有、服务端只验签 | 无状态、易水平扩展；**签发后难以撤销** |

```http
Set-Cookie: session=abc123; HttpOnly; Secure; SameSite=Lax; Path=/
```

- `HttpOnly`：JS 读不到，挡住 XSS 偷 Cookie；
- `Secure`：只在 HTTPS 下发送；
- `SameSite`：限制跨站携带，缓解 CSRF。

选型经验：**会话放服务端（Redis）更好撤销，JWT 更利于水平扩展**。
真实项目常常两者混用：refresh token 存服务端，access token 用 JWT 短期有效。

## 1.8.9 HTTPS：加密、完整性与身份

HTTPS = HTTP + TLS。它解决三件事：

| 目标 | 手段 |
| --- | --- |
| 机密性 | 对称加密传输数据（密钥用非对称加密协商出来） |
| 完整性 | 消息认证码，防篡改 |
| 身份认证 | 证书链，确认「服务器就是它声称的那台」 |

浏览器地址栏的锁定图标就是验证结果。**自签证书会被浏览器拦下**，
所以本地开发要么用 `mkcert` 之类的工具生成本地信任的证书，要么走反向代理。

> ⚠️ **注意**：调模型 API、调支付接口**必须**走 HTTPS。
> 用 HTTP 传 `Authorization` 头，等于把 token 明文发给了链路上所有人。

## 1.8.10 跨域与 CORS

浏览器的**同源策略**规定：`协议 + 域名 + 端口` 三者任一不同即为跨域，
JavaScript 默认不能读取跨域响应。这就是前后端分离开发时的
`http://localhost:5173` 访问 `http://localhost:8000` 会被拦的原因。

CORS（跨域资源共享）是服务端**主动开的口子**：

```text
浏览器先发预检请求（preflight）：
  OPTIONS /api/v1/documents
  Origin: http://localhost:5173
  Access-Control-Request-Method: POST

服务端回应：
  Access-Control-Allow-Origin: http://localhost:5173
  Access-Control-Allow-Methods: GET, POST
  Access-Control-Allow-Headers: Content-Type, Authorization
```

四个要点：

1. **CORS 是浏览器行为，不是服务端拒绝**——用 `curl` 直接请求往往能成功，
   这也是「Postman 能通、浏览器不行」的原因。
2. 预检只在**非简单请求**时发生（自定义头、`PUT`/`DELETE`、`application/json` 等）。
3. 生产环境**不要用 `allow_origins=["*"]` 配合凭据**，浏览器会拒绝，且等于对外全开。
   应该显式列出来源（FastAPI 的配置在 1.11 讲）。
4. 跨域与认证一起要考虑 `credentials`：带 Cookie 时不能用通配符来源。

## 1.8.11 综合示例：亲手看一次 HTTP 报文

理解协议最好的方式是把报文打出来。用标准库起一个最小服务端，
再观察真实请求——这就是 1.9 FastAPI 要帮你自动做的事。

```python
# http_demo.py
import json
from http.server import BaseHTTPRequestHandler, HTTPServer


class Handler(BaseHTTPRequestHandler):
    def do_POST(self) -> None:
        length = int(self.headers.get("Content-Length", 0))
        body = self.rfile.read(length)
        payload = json.loads(body or b"{}")

        if not payload.get("title"):
            # 400：客户端传来的数据不合法
            self.send_response(400)
            self.send_header("Content-Type", "application/json; charset=utf-8")
            self.end_headers()
            self.wfile.write(json.dumps({"detail": "title 不能为空"},
                                        ensure_ascii=False).encode("utf-8"))
            return

        data = {"id": 42, "title": payload["title"]}
        raw = json.dumps(data, ensure_ascii=False).encode("utf-8")
        self.send_response(201)                      # 201：创建成功
        self.send_header("Content-Type", "application/json; charset=utf-8")
        self.send_header("Content-Length", str(len(raw)))   # 字节数，不是字符数
        self.send_header("Location", "/api/v1/documents/42")
        self.end_headers()
        self.wfile.write(raw)

    def log_message(self, fmt: str, *args) -> None:
        print("[server]", fmt % args)                # 把请求行打到终端


if __name__ == "__main__":
    HTTPServer(("127.0.0.1", 8000), Handler).serve_forever()
```

```python
# client_demo.py
import json
import urllib.request

request = urllib.request.Request(
    "http://127.0.0.1:8000/api/v1/documents",
    data=json.dumps({"title": "公告"}).encode("utf-8"),
    headers={"Content-Type": "application/json; charset=utf-8"},
    method="POST",
)
with urllib.request.urlopen(request) as resp:
    print("状态码：", resp.status)
    print("Location：", resp.headers["Location"])
    print("响应体：", json.loads(resp.read().decode("utf-8")))
```

```text
# 输出
状态码： 201
Location： /api/v1/documents/42
响应体： {'id': 42, 'title': '公告'}

# 服务端终端
[server] "POST /api/v1/documents HTTP/1.1" 201 -
```

在浏览器里访问 `/api/v1/documents` 用 `GET` 会得到 `501 Unsupported method`——
因为上面只实现了 `do_POST`。**这个 501 恰好说明状态码是服务端主动选的**：
你实现了哪个方法，就决定了哪些请求会被正确处理。1.9 开始，FastAPI 会用
装饰器把这些「选状态码、解析请求体、拼响应头」的活全部包掉。

## 常见坑

- **`Content-Length` 按字符数算**。现象：中文响应被截断或客户端一直等。
  原因：HTTP 的长度单位是**字节**。修法：`len(body.encode("utf-8"))`。
- **忘了 `charset=utf-8`**。现象：中文乱码。修法：响应头写
  `Content-Type: application/json; charset=utf-8`。
- **用 GET 做有副作用的操作**。现象：爬虫或预取导致数据被改。
  修法：改状态一律用 POST/PUT/PATCH/DELETE。
- **把 401 当 403 用**。现象：前端拿到 401 以为是权限不够，没去刷新 token。
  修法：`401` 表示未认证（该去登录/刷新令牌），`403` 表示已认证但没权限。
- **`502` 与 `504` 混着排查**。现象：一直以为是代码超时，其实进程根本没起来。
  修法：先看上游进程与端口，再看响应时间。
- **`allow_origins=["*"]` 上线**。现象：接口等于对所有站点开放，或带 Cookie 时报错。
  修法：显式列出允许的来源。
- **`0.0.0.0` 与 `127.0.0.1` 混用**。现象：本机能访问，同事访问不到。
  原因：只监听了回环地址。修法：需要外部访问时监听 `0.0.0.0`，
  并用防火墙控制暴露范围。

## 面试视角

> 🎯 **面试**：这是后端与 AI 应用岗**出现频率最高的基础题组**。
> 题库里「网络 / HTTP」相关的题目，考察点基本都在下面这七问里。

1. **「在浏览器输入网址回车，发生了什么？」**
   考察点：全局串联。答题要点：DNS 解析 → TCP 三次握手 → TLS 握手 →
   发 HTTP 请求 → 服务端处理返回 → 解析渲染 → 继续请求静态资源。
   能按顺序讲清、并指出「连接与 TLS 是首次请求的主要开销」就已经很好。
2. **「TCP 三次握手为什么不是两次？四次挥手为什么是四次？」**
   考察点：协议细节。答题要点：三次是为确认双方收发能力都在（并防旧 SYN 建立无效连接）；
   四次是因为 TCP 双向独立，一方说「我不发了」不代表另一方也发完。
3. **「TCP 和 UDP 怎么选？」**
   考察点：取舍。答题要点：要可靠有序选 TCP（HTTP/数据库）；
   要低延迟、能容忍丢包选 UDP（DNS、音视频、实时状态）。
4. **「`401` 和 `403` 的区别？」**
   考察点：状态码理解。答题要点：未认证 vs 无权限；
   强调 401 要带 `WWW-Authenticate`，客户端应去登录或刷新令牌。
5. **「什么是幂等？为什么它重要？」**
   考察点：接口设计。答题要点：多次执行结果相同；
   GET/PUT/DELETE 幂等可安全重试，POST 不幂等，需要幂等键支持重试。
6. **「Cookie、Session、JWT 有什么区别？」**
   考察点：会话管理。答题要点：存储位置与状态的归属不同；
   Session 易撤销、需存储；JWT 无状态、易扩展但难撤销；
   Cookie 只是载体，且要配 `HttpOnly` / `Secure` / `SameSite`。
7. **「跨域是什么？CORS 怎么解决？」**
   考察点：前端协作。答题要点：同源策略是**浏览器**的安全机制；
   CORS 由服务端通过响应头授权；预检请求 `OPTIONS` 的触发条件；
   生产环境不要用通配符来源。

## 本章小结

- 一次访问：DHCP → DNS → TCP 握手 → TLS → HTTP 请求/响应 → 渲染；
  连接与加密是首次请求的主要开销。
- 五层模型：应用层 / 传输层 / 网络层 / 数据链路层 / 物理层，
  每层「头部 + 数据」逐层封装；IP 定终点、MAC 定下一跳，端口定进程。
- TCP 可靠有序（三次握手、四次挥手、`TIME_WAIT` 等 `2MSL`），UDP 快但不可靠。
- HTTP 是文本协议：请求行 + 头 + 空行 + 体；响应是状态行 + 头 + 空行 + 体。
  `Content-Length` 算的是**字节**，中文必须声明 `charset=utf-8`。
- 方法与幂等性决定能否安全重试；REST 用「名词复数 + 方法 + 查询串」表达操作，路径带版本。
- 状态码按类别记：4xx 改客户端、5xx 查服务端；`401` 与 `403`、`502` 与 `504` 别混。
- HTTP 无状态，状态靠 Cookie / Session / Token 维持；三条 Cookie 属性缺一不可。
- HTTPS 提供机密性、完整性与身份认证；CORS 是浏览器同源策略下的服务端授权。

## 练习

- **基础**：用 `urllib` 分别请求一个返回 `200` 和 `404` 的地址，
  打印状态码、`Content-Type` 与响应头字典；把两次结果对比，说明 4xx 为什么不抛异常之外的处理逻辑。
- **进阶**：把 1.8.11 的服务端补全：实现 `do_GET`（返回列表与分页参数）、
  `do_DELETE`（成功返回 `204` 无响应体）、`do_PUT`（整体替换，不存在返回 `404`）。
  要求为每个分支选对状态码，并在服务端日志里打印方法、路径与状态码。
- **挑战**：设计一个「创建订单」接口并写出它的完整约定：
