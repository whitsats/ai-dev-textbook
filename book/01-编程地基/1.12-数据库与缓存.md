## 1.12.1 数据层要解决什么：ORM 的边界

数据要落到磁盘上，就绕不开两件事：**表结构**和**查询语句**。
如果全程手写 SQL，代码里会散落着字符串拼出来的语句，改一个字段名要全局搜索，
字段类型和 Python 类型永远对不上。

**对象关系映射（Object Relational Mapping, ORM）** 解决的就是这个错位：
用 Python 类描述表，用对象操作行，让框架去生成 SQL。

```python
class Book(Base):
    __tablename__ = "book"
    id: Mapped[int] = mapped_column(primary_key=True)
    title: Mapped[str] = mapped_column(String(255))
```

这一小段同时定义了「数据库里有一张 `book` 表」和「Python 里有一个 `Book` 类」，
并声明了两者的每一列与每个属性的对应关系。

ORM 的好处常见说法有五项，其中三项值得展开：

| 好处 | 具体含义 | 代价或前提 |
| --- | --- | --- |
| 简化开发 | 不再手写 `INSERT` / `UPDATE` / `SELECT` 的拼装 | 学习一套 DSL，复杂 SQL 仍要落到 `text()` |
| 可维护 | 表结构变化只改模型类 | 改模型不等于改库，需要迁移工具（见 1.12.4） |
| 跨数据库 | 换库多半只改连接串与驱动 | 用了方言特有功能就换不动了 |
| 面向对象 | 继承、多态、封装都能用在模型上 | 容易被当成普通类，忘了它是数据库映射 |
| 性能优化 | 延迟加载、批量处理 | **配置不当会引入 N+1 查询** |

### ORM 的边界：什么时候不该用

ORM 不是万能的，硬用会写出比 SQL 更难维护的东西。三种情况应该是手写 SQL：

1. **批量导入**：逐条 `add()` 一条条 INSERT，比 `insert().values([...])` 慢一个数量级。
2. **报表与复杂聚合**：五张表 JOIN 加窗口函数，用 ORM 拼出来的代码没人看得懂，
   这时候直接写 SQL（`text()`）更清楚。
3. **性能敏感的逐行处理**：需要控制游标、分批拉取时，ORM 的抽象会挡住你。

> 💡 **提示**：判断标准是「这段查询是否需要被复用和组合」。
> 需要 → 用 ORM 表达式（能被别处拼装）；一次性且复杂 → 写 SQL，
> 但仍从同一个引擎取连接，别另开一套。

## 1.12.2 建引擎：URL、驱动与连接池

### 装两个东西

```bash
pip install "sqlalchemy[asyncio]"
```

- **SQLAlchemy 核心库**：负责 ORM 语法、模型定义、会话管理；
- **数据库异步驱动**：负责真的跟数据库说话。

`sqlalchemy[asyncio]` 会把异步所需的额外依赖（含 `greenlet`）一起装上。
驱动按数据库选，**只装需要的那个**：

| 数据库 | 驱动包 | 连接串前缀 |
| --- | --- | --- |
| MySQL | `aiomysql` 或 `asyncmy` | `mysql+aiomysql://` 或 `mysql+asyncmy://` |
| PostgreSQL | `asyncpg` | `postgresql+asyncpg://` |
| SQLite | `aiosqlite` | `sqlite+aiosqlite://` |

```bash
# MySQL
pip install "sqlalchemy[asyncio]" aiomysql
# PostgreSQL
pip install "sqlalchemy[asyncio]" asyncpg
# 本地开发用 SQLite（零配置，本章示例用它）
pip install "sqlalchemy[asyncio]" aiosqlite
```

### 连接串怎么读

```python
ASYNC_DATABASE_URL = (
    "mysql+aiomysql://root:123456@localhost:3306/zhizhou?charset=utf8mb4"
)
```

| 片段 | 含义 |
| --- | --- |
| `mysql+aiomysql://` | 数据库类型 + 异步驱动 |
| `root:123456` | 用户名与密码 |
| `localhost:3306` | 主机与端口 |
| `zhizhou` | 库名 |
| `?charset=utf8mb4` | 字符集，**不写这个中文可能乱码** |

> ⚠️ **注意**：连接串里有密码，所以它必须来自环境变量或 `.env`，
> 绝不能提交进仓库（1.9.2 的配置读取就是为此）。

### 引擎与连接池

**没有连接池**：每个请求都「创建连接 → 查询 → 关闭连接」，
而建一次 TCP 连接 + 认证的开销往往比查询本身还大。
有了池，连接用完**归还**而不是销毁，下个请求直接复用。

```python
from sqlalchemy.ext.asyncio import create_async_engine

engine = create_async_engine(
    ASYNC_DATABASE_URL,
    echo=False,          # True 时打印每条 SQL，调试用，生产关掉
    pool_size=10,        # 池里常驻的连接数
    max_overflow=20,     # 高峰时允许临时超出的连接数（总数上限 30）
    pool_recycle=3600,   # 1 小时回收一次，避开 MySQL 的 wait_timeout 断连
    pool_pre_ping=True,  # 取连接前先探活，失效就重建
)
```

| 参数 | 防的是什么 | 调错的后果 |
| --- | --- | --- |
| `pool_size` | 连接创建开销 | 太小 → 请求排队；太大 → 数据库连接数打满 |
| `max_overflow` | 突发流量 | 太小 → 高峰直接报「连接池耗尽」 |
| `pool_recycle` | 数据库端主动断开空闲连接（MySQL 默认 8 小时） | 不设 → 偶发「server has gone away」 |
| `pool_pre_ping` | 拿到已失效的连接 | 不设 → 偶发查询失败，重试就好，极难复现 |

两点值得注意（本地 SQLite）：

```text
文件库 sqlite+aiosqlite:///./app.db  →  池类 AsyncAdaptedQueuePool（上面的参数都接受）
内存库 sqlite+aiosqlite:///:memory:  →  池类 StaticPool（单连接复用，参数无意义）
```

所以本地用 SQLite 开发时，这些池参数不会报错，但也**测不出**生产上真实的池行为——
拿 SQLite 压测连接池上限是没有意义的。生产用 PostgreSQL 或 MySQL，
并把 `pool_size` 与数据库的 `max_connections` 一起估算：`pool_size × 副本数 < max_connections`。

> 🔥 **常见坑**：加了副本却不改连接池参数。3 个副本 × 30 个连接 = 90 个连接，
> 很容易把数据库的连接上限打满，而且**平时看不出来**——只在流量上来时集体报错。

## 1.12.3 定义模型：`DeclarativeBase` 与 `Mapped`

SQLAlchemy 2.0 的写法分两层：**一个基类**放公共字段，**每个模型类**描述一张表。

```python
# models/models.py
from datetime import datetime

from sqlalchemy import CheckConstraint, DateTime, Float, String, func
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column


class Base(DeclarativeBase):
    """所有模型的基类：统一带创建时间与更新时间。"""

    create_time: Mapped[datetime] = mapped_column(
        DateTime, insert_default=func.now(), comment="创建时间"
    )
    update_time: Mapped[datetime] = mapped_column(
        DateTime, insert_default=func.now(), onupdate=func.now(), comment="修改时间"
    )


class Book(Base):
    __tablename__ = "book"

    id: Mapped[int] = mapped_column(primary_key=True, comment="书籍 id")
    title: Mapped[str] = mapped_column(String(255), comment="书名")
    author: Mapped[str] = mapped_column(String(255), comment="作者")
    price: Mapped[float] = mapped_column(Float, comment="价格")
    stock: Mapped[int | None] = mapped_column(comment="库存，可不填")

    __table_args__ = (CheckConstraint("price >= 0", name="ck_book_price"),)
```

### `Mapped` 不只是类型注解

它同时决定了**列是否可空**。实跑打印各列的可空性：

```text
[('title', False), ('author', False), ('price', False), ('stock', True), ('id', False)]
```

规律：`Mapped[str]` → `NOT NULL`；`Mapped[int | None]` → 允许 `NULL`。
这条规则省掉了大量 `nullable=`，也是 2.0 写法相比 1.x 最实用的改动。

> ⚠️ **注意**：`Mapped[str]` 非空只表示**数据库层面**不允许 NULL。
> 请求体校验是另一回事（Pydantic 管），两者要对上，否则会出现
> 「请求校验通过、写库时报 `IntegrityError`」的割裂感。

### 公共字段与库级约束

- 基类里的 `create_time` / `update_time` 会**自动加到每张表**，
  避免每个模型都抄一遍；
- `insert_default=func.now()` 让数据库在插入时填当前时间，
  `onupdate=func.now()` 让每次 UPDATE 自动刷新修改时间；
- `__table_args__` 里放的是**库级约束**。`CheckConstraint("price >= 0")` 是最后一道防线：
  应用层的 Pydantic 校验可以被绕过（比如脚本直连数据库），库级约束不会。

实跑违反这个约束的结果：

```text
IntegrityError | CHECK constraint failed: ck_book_price
```

## 1.12.4 建表与生命周期：`lifespan`

表要在应用启动时建好，引擎要在应用关闭时释放。这两件事**都写在 `lifespan` 里**：

```python
# main.py
from contextlib import asynccontextmanager

from fastapi import FastAPI

from config.database import engine
from models.models import Base


@asynccontextmanager
async def lifespan(app: FastAPI):
    # 启动：建表（幂等，表已存在则跳过）
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
    yield                      # ← 应用在此运行
    # 关闭：释放所有连接
    await engine.dispose()


app = FastAPI(title="知舟 API", lifespan=lifespan)
```

三个细节：

- `engine.begin()` 从池里取一个连接并**开启事务**，退出时自动提交；
- `conn.run_sync(...)` 把同步的 `create_all` 放到异步连接上执行（SQLAlchemy 的过渡桥）；
- `await engine.dispose()` 关闭池里所有连接——不写它，进程退出可能残留连接，
  反复重启的开发环境里会看到数据库连接数只涨不跌。

> 💡 **提示**：`lifespan` 取代了已废弃的 `@app.on_event("startup")` / `("shutdown")`（0.104 起不推荐）。
> 好处是**启动与关闭逻辑写在一处**，看一个函数就知道应用的一生。
> 1.11.7 提过的「全局依赖」与它无关：`lifespan` 不参与请求流程。

### `create_all` 与 Alembic 的分工

`create_all` 只做一件事：**表不存在就建**。它不会改已有表的结构。

所以：

| 阶段 | 工具 | 说明 |
| --- | --- | --- |
| 本地开发、教学示例 | `create_all` | 删掉本地库重建即可，零配置 |
| 生产环境 | **Alembic** | 生成迁移脚本，可回滚、可审计、可在上线前 review |

把 `create_all` 留在生产的后果是：加了一个字段，模型改了、代码部署了，
**数据库里没有这一列**，接口在第一次查询时报 `UndefinedColumn`。
对本章的示例来说 `create_all` 足够；一旦有真实数据不能删，就该引入 Alembic。

## 1.12.5 会话依赖：事务边界与 `expire_on_commit`

会话（`Session`）是 ORM 的工作区：对象先被放进会话，提交时才真正写库。
它的生命周期必须**跟请求一样长**，这正是 1.11 讲的 `yield` 依赖。

```python
# config/database.py
from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker

AsyncSessionLocal = async_sessionmaker(
    bind=engine,
    class_=AsyncSession,
    expire_on_commit=False,      # 见下文：这一项不是可选项
)


async def get_db():
    """一个请求一个会话：正常提交、异常回滚、无论如何关闭。"""
    async with AsyncSessionLocal() as session:
        try:
            yield session           # 交给路由
            await session.commit()  # 路由正常结束 → 提交
        except Exception:
            await session.rollback()  # 任何异常 → 回滚
            raise                     # 别吞掉异常，交给上层转成 HTTP 错误
        finally:
            await session.close()     # 归还连接
```

这段结构直接来自 1.11.3 的结论：**异常时 `yield` 之后的「提交」不会执行**，
所以「回滚」必须写在 `except` 里，清理写在 `finally` 里。三件事缺一不可。

### `expire_on_commit` 为什么必须是 `False`

它的默认值是 `True`，含义是「提交后让对象里的属性**过期**，
下次访问时重新查库，保证读到的是最新值」。听起来很安全，但在异步 ORM 里会炸。

反例（**实跑复现**）：路由里先提交，再返回 ORM 对象：

```python
@app.post("/books", response_model=BookOut, status_code=201)
async def create(b: dict, db: AsyncSession = Depends(get_db)):
    obj = Book(**b)
    db.add(obj)
    await db.commit()      # 提交发生在「序列化之前」
    return obj             # 返回 ORM 对象，交给 response_model 读属性
```

```text
expire_on_commit=False  路由内 commit → 201 {"id":1,...}
expire_on_commit=True   路由内 commit → 500
```

500 的真实原因（异常原文）：

```text
ResponseValidationError: 2 validation errors:
  {'type': 'get_attribute_error', 'loc': ('response', 'id'),
   'msg': "Error extracting attribute: MissingGreenlet: greenlet_spawn has not been called;
           can't call await_only() here. Was IO attempted in an unexpected place?"}
```

读法：`response_model` 要读 `id`，但这个属性在提交时被标记为过期，
于是 SQLAlchemy 想要**同步地**去数据库取——而这里是异步上下文，它做不到，
只能抛 `MissingGreenlet`。**这跟项目里多数人第一次遇到时的直觉相反**：
报错指向 `response_model`，真凶却是 `expire_on_commit` 与提交时机。

为什么把提交放在依赖里却没事？因为 FastAPI 的响应序列化发生在
**依赖的收尾代码之前**（1.11.6 实测的次序）：对象被读完了，才轮到提交。

| 提交位置 | `expire_on_commit=True` | `expire_on_commit=False` |
| --- | --- | --- |
| 依赖的收尾（`yield` 之后） | 可以（序列化在前） | 可以 |
| 路由 / DAO / Service 内部 | **500 `MissingGreenlet`** | 可以 |

结论：**只要有一处代码可能先提交再返回 ORM 对象（DAO 层几乎是必然的），
`expire_on_commit` 就必须设成 `False`。** 这不是优化，是正确性。

> 🔥 **常见坑**：自己写 DAO 时在方法里 `commit()`，路由返回 ORM 对象，
> 测试里用 `expire_on_commit=False` 的工厂没事，一上生产换了配置就全 500。
> 修法：把 `expire_on_commit=False` 与 `async_sessionmaker` 写在一起，
> 让「会话工厂」成为唯一配置点，别在测试里另建一个。

### 不用依赖注入的写法（以及为什么不用它）

另一种拿会话的方式是中间件把它塞进 `request.state`：

```python
# ⚠️ 能用，但不推荐
@app.middleware("http")
async def db_session_middleware(request: Request, call_next):
    async with AsyncSessionLocal() as session:
        request.state.db = session
        return await call_next(request)
```

它有三个问题：**事务边界失控**（无法在某个 DAO 上控制提交点）、
**类型丢失**（`request.state.db` 是 `Any`，IDE 与类型检查都帮不上）、
**绑定路由**（会话对所有请求创建，哪怕这个接口根本不查库）。
依赖注入版能按需创建、能被 `dependency_overrides` 替换，所以是唯一推荐写法。

## 1.12.6 查询基础：`select` 与结果提取

查询分两步：**构造语句** → **执行并提取结果**。

```python
from sqlalchemy import select

@app.get("/books")
async def list_books(db: AsyncSession = Depends(get_db)):
    result = await db.execute(select(Book))     # ① 执行，拿到结果集
    return result.scalars().all()               # ② 提取 ORM 对象
```

`select(Book)` 生成 `SELECT ... FROM book`；`await db.execute(...)` 真的去查；
返回的 `result` 还不是 Python 对象，需要再过一道 `scalars()`。

### 为什么需要 `scalars()`

`execute()` 返回的结果集里每一行是「一列或多列」的元组。
`scalars()` 告诉 SQLAlchemy「我只要每行的第一列」，也就是 ORM 对象本身，
省掉手工把行转成对象的步骤。

### 四提取方法的语义

| 方法 | 语义 | 查不到时 |
| --- | --- | --- |
| `scalars().all()` | 全部结果，返回列表 | `[]` |
| `scalars().first()` | 第一条，或 `None` | `None` |
| `scalar_one_or_none()` | 预期**最多一条**；多于一条会抛错 | `None` |
| `scalar()` | 单个标量值（配合 `func.count()` 等聚合） | `None` |

实跑对照：

```text
scalars().all()          → ['红楼梦', '三国演义', '曹某人集']
scalars().first()        → 曹某人集
scalar_one_or_none()     → None            （id=999 不存在）
scalar()  count          → 3
scalar()  avg            → 132.33333333333334
```

> ⚠️ **注意（面试高频）**：`first()` 与 `scalar_one_or_none()` 的差别不只是名字。
> 前者**容忍多行**（只取第一条，多余的静默丢弃），后者**预期唯一**
> （多行会直接抛 `MultipleResultsFound`）。按主键查用后者——
> 如果因为逻辑错误返回了多行，你希望它当场报错，而不是悄悄返回一条错数据。

## 1.12.7 查询进阶：条件、聚合与分页

### `where` 的多种写法

```python
# 多个条件用逗号分隔 = AND
select(Book).where(Book.author == "曹雪芹", Book.price > 100)

# 比较
select(Book).where(Book.price >= 200)

# 模糊查询：% 匹配任意多个字符，_ 匹配单个字符
select(Book).where(Book.author.like("曹%"))     # 姓曹的
select(Book).where(Book.author.like("曹__"))    # 姓曹且三个字

# 包含
select(Book).where(Book.id.in_([1, 3, 5, 7]))

# 组合：& 与、| 或、~ 非
select(Book).where((Book.author.like("曹%")) & (Book.price > 100))
```

> ⚠️ **注意**：用 `&`、`|` 组合条件时**每个条件必须加括号**。
> 不加括号会按 Python 的位运算符优先级重新结合，生成你意想不到的 WHERE 子句——
> 而且是静默的：SQL 合法、能跑，只是筛错了数据。

### 聚合与分页

```python
from sqlalchemy import func

# 聚合：用 func 命名空间调用数据库函数
result = await db.execute(select(func.avg(Book.price)))
return {"avg_price": result.scalar()}
```

分页要查两次：**一次总条数，一次当前页**。

```python
@app.get("/books/page", response_model=PaginationResponse)
async def page_books(
    page: int = 1,
    page_size: int = 10,
    db: AsyncSession = Depends(get_db),
):
    page = max(page, 1)                 # 防止 page=0 或负数
    page_size = max(page_size, 1)
    skip = (page - 1) * page_size

    total = await db.scalar(select(func.count(Book.id)))
    total_pages = (total + page_size - 1) // page_size      # 向上取整

    result = await db.execute(select(Book).offset(skip).limit(page_size))
    return {
        "items": result.scalars().all(),
        "total": total,
        "page": page,
        "page_size": page_size,
        "total_pages": total_pages,
    }
```

`skip` 公式要记牢：**第 1 页 skip=0、第 2 页 skip=page_size**。
`total_pages` 用 `(total + page_size - 1) // page_size` 向上取整；
若写成 `total // page_size`，21 条记录按每页 10 条会算出 2 页，**最后一页丢失**。

> 💡 **提示**：`offset/limit` 分页在深翻页时很慢（数据库仍要扫描前 `skip` 行）。
> 数据量大的列表用**游标分页**（按 `id > 上一页最后一个 id` 查），
> 代价是不能直接跳到第 N 页。第 5 篇的检索接口会用后者。

## 1.12.8 写入：新增、更新、删除

### 新增

```python
@app.post("/books", response_model=BookOut, status_code=201)
async def create_book(data: BookCreate, db: AsyncSession = Depends(get_db)):
    obj = Book(**data.model_dump())     # Pydantic 模型 → 字典 → ORM 对象
    db.add(obj)                          # 放进会话，生成 INSERT（还没执行）
    await db.flush()                     # 立即发送 INSERT，拿到自增 id
    return obj                           # 提交由 get_db 的收尾负责
```

三步：`model_dump()` 把请求体转成字典、`Book(**...)` 建 ORM 对象（此时**在内存里**）、
`flush()` 把 INSERT 发给数据库。

这里用 `flush()` 而不是 `commit()`，是为了**让事务边界留在依赖里**：
路由只管业务，提交统一在 `get_db` 收尾。这正是上一节 `expire_on_commit` 讨论的那条路径。

> 💡 **提示**：`flush()` 与 `refresh()` 的分工：`flush` 把待执行的 SQL 发出去
> （因此能拿到数据库生成的自增 id 与默认值）；`refresh` 则**重新从库读取**该对象。
> 拿到 id 只需要 `flush`，不需要 `refresh`（很多 DAO 会把两句连写，
> 那次 `refresh` 是多余的一次查询）。

### 更新：脏检查

```python
@app.put("/books/{book_id}", response_model=BookOut)
async def update_book(book_id: int, data: BookUpdate, db: AsyncSession = Depends(get_db)):
    obj = await db.get(Book, book_id)          # 按主键查
    if obj is None:
        raise HTTPException(status_code=404, detail="书籍不存在")
    for field, value in data.model_dump(exclude_unset=True).items():
        setattr(obj, field, value)             # 直接改属性
    return obj                                  # 提交时自动生成 UPDATE
```

**不用手写 UPDATE**。SQLAlchemy 会跟踪对象状态，提交时对比新旧值，
只更新真正改过的列。实跑捕获到的 SQL：

```text
UPDATE book SET price=? WHERE book.id = ?
```

只改了 `price`，语句里就只有 `price`。这个机制叫**脏检查（dirty checking）**，
它同时意味着：如果什么都没改，提交时**不会产生任何 UPDATE**。

### 删除

```python
@app.delete("/books/{book_id}", status_code=204)
async def delete_book(book_id: int, db: AsyncSession = Depends(get_db)):
    obj = await db.get(Book, book_id)
    if obj is None:
        raise HTTPException(status_code=404, detail="书籍不存在")
    await db.delete(obj)
```

`delete()` 只是标记，真正的 `DELETE` 在提交时发出。先 `get` 再删是为了给出 404，
而不是让客户端拿着一个「成功」的响应去猜。

## 1.12.9 与 Pydantic 衔接和错误处理

### 一套模型分四种用途

```python
# schemas/schemas.py
from datetime import datetime

from pydantic import BaseModel, ConfigDict


class BookBase(BaseModel):
    title: str
    author: str
    price: float
    publisher: str


class BookCreate(BookBase):
    """创建时的请求体。"""


class BookUpdate(BaseModel):
    """更新时的请求体：全部可选，只传要改的字段。"""

    title: str | None = None
    author: str | None = None
    price: float | None = None
    publisher: str | None = None


class BookResponse(BookBase):
    """响应模型：额外带 id 与时间戳。"""

    id: int
    create_time: datetime
    update_time: datetime

    model_config = ConfigDict(from_attributes=True)   # ← 能直接接 ORM 对象
```

`from_attributes=True` 是关键：它让 Pydantic 可以用**属性访问**取值，
于是 `response_model=BookResponse` 能直接吃 ORM 对象，不必先转字典。
这是 1.10.9 讲过、在这里落地的写法。

配合 `response_model` 还有一层安全收益：**ORM 对象上的其他字段不会被带出去**。
将来给 `Book` 加了 `internal_cost`，只要响应模型里没写，它就不会出现在响应里。

### 把数据库异常转成 HTTP 错误

数据库会拒绝非法数据，此时的异常是 `IntegrityError`，
它属于**库层错误**，默认会变成 500。应该翻译成 4xx：

```python
from fastapi import Request
from fastapi.responses import JSONResponse
from sqlalchemy.exc import IntegrityError


@app.exception_handler(IntegrityError)
async def integrity_error_handler(request: Request, exc: IntegrityError):
    return JSONResponse(
        status_code=409,
        content={"detail": "数据冲突：唯一约束或检查约束不通过"},
    )
```

实跑结果：

```text
$ curl -X POST .../books -d '{"title":"重复的书",...}'   # 第二次
409 {"detail":"数据冲突：唯一约束或检查约束不通过"}
```

> ⚠️ **注意**：处理器注册在 `IntegrityError` 上，意味着**它不区分约束类型**。
> 生产上应该按 `exc.orig` 里的约束名分支：唯一约束 → 409，检查约束 → 400，
> 外键约束 → 422。统一返回 409 在示例里够用，但会让前端无法给出准确提示。
> 另外：**异常处理器必须在异常抛出前注册完成**，所以放在 `main.py` 里、
> 创建 `app` 之后立刻写。

> 🔥 **常见坑**：捕获了 `IntegrityError` 却没有 `rollback()`。
> 会话在这个异常后处于「失败」状态，后续任何操作都会继续报错，
> 而错误信息会指向第二处操作——真正的原因被埋掉了。
> 修法：`get_db` 的 `except` 里已经统一回滚，不要在路由里自己 `try` 掉异常。

## 1.12.10 分层：router / dao / schemas

路由里直接写查询能跑，但三件事混在一起：**HTTP 语义**（状态码、错误）、
**业务规则**、**SQL 细节**。分层就是把这三种职责分开：

```text
app/
├── main.py                  # 应用入口：lifespan + 注册路由
├── config/
│   └── database.py          # 引擎、会话工厂、get_db
├── models/
│   └── models.py            # ORM 模型（Base + Book）
├── schemas/
│   └── schemas.py           # Pydantic 输入/输出模型
├── dao/
│   └── book_dao.py          # 数据访问层：只做 SQL
└── routers/
    └── book_router.py       # 路由层：只做 HTTP
```

| 层 | 职责 | 不该做的事 |
| --- | --- | --- |
| `routers/` | 收请求、调 DAO、返回响应、抛 HTTP 错误 | 不写 SQL |
| `dao/` | 增删改查、查询构造 | 不抛 `HTTPException`、不知道请求长什么样 |
| `models/` | 表结构 | 不写业务逻辑 |
| `schemas/` | 输入输出契约 | 不碰数据库 |

DAO 的样子：

```python
# dao/book_dao.py
from typing import Optional

from sqlalchemy import select
from sqlalchemy.ext.asyncio import AsyncSession

from models.models import Book


class BookDAO:
    def __init__(self, session: AsyncSession):
        self.session = session

    async def create(self, data: dict) -> Book:
        book = Book(**data)
        self.session.add(book)
        await self.session.flush()      # 只 flush：拿 id，事务交给 get_db
        return book

    async def get_by_id(self, book_id: int) -> Optional[Book]:
        return await self.session.get(Book, book_id)

    async def list_all(self) -> list[Book]:
        result = await self.session.execute(select(Book))
        return list(result.scalars().all())

    async def update(self, book_id: int, data: dict) -> Optional[Book]:
        book = await self.get_by_id(book_id)
        if book is None:
            return None
        for field, value in data.items():
            setattr(book, field, value)
        await self.session.flush()
        return book

    async def delete(self, book_id: int) -> bool:
        book = await self.get_by_id(book_id)
        if book is None:
            return False
        await self.session.delete(book)
        return True
```

DAO 自己也是通过依赖注入拿到的——依赖可以依赖依赖（1.11.4）：

```python
# routers/book_router.py
from fastapi import APIRouter, Depends, HTTPException, status
from sqlalchemy.ext.asyncio import AsyncSession

from config.database import get_db
from dao.book_dao import BookDAO
from schemas.schemas import BookCreate, BookResponse, BookUpdate


def get_book_dao(session: AsyncSession = Depends(get_db)) -> BookDAO:
    return BookDAO(session)


router = APIRouter(prefix="/books", tags=["书籍管理"])


@router.post("/", response_model=BookResponse, status_code=status.HTTP_201_CREATED)
async def create_book(data: BookCreate, dao: BookDAO = Depends(get_book_dao)):
    return await dao.create(data.model_dump(exclude_unset=True))


@router.get("/{book_id}", response_model=BookResponse)
async def get_book(book_id: int, dao: BookDAO = Depends(get_book_dao)):
    book = await dao.get_by_id(book_id)
    if book is None:
        raise HTTPException(
            status_code=status.HTTP_404_NOT_FOUND,
            detail=f"书籍 id={book_id} 不存在",
        )
    return book
```

注意 `get_book_dao` 依赖 `get_db`：**一个请求内两者共享同一个会话**
（1.11.8 的依赖缓存），路由与 DAO 不会各拿一条连接。

DAO 的收益在测试时最明显：`dependency_overrides` 把 `get_book_dao` 换成假实现，
路由层的测试完全不需要数据库。

> 💡 **提示**：DAO 只 `flush` 不 `commit`，是「事务边界归依赖层」的体现。
> 代价是**同一个请求里的多次写操作要么全成、要么全败**——这通常正是你要的；
> 但如果某一步必须独立提交（比如记录审计日志），就得显式开一个独立会话。

## 1.12.11 Redis：数据结构、Key 规范与接入

数据库读一次是**磁盘 IO**（毫秒级），Redis 读一次是**内存 IO**（亚毫秒级），
所以把「读多写少」的结果放进 Redis，能把响应时间压下一个数量级。

> ⚠️ **本节起未实跑**：本机 `redis` 包是 3.5.3，**没有** `redis.asyncio`（需 ≥ 4.2），
> 也没有可连的 Redis 服务。下面代码与官方文档一致，但请以你的环境实测为准：
> `pip install "redis>=4.2"`。

### 五种数据结构，按场景记

| 结构 | 特点 | 典型场景 |
| --- | --- | --- |
| String | 最简单，`key → value` | 令牌、验证码、计数器、页面缓存 |
| Hash | 一个 key 存多个字段 | 用户信息、商品详情（避免整体序列化） |
| List | 有序，两端进出 | 任务队列、最近浏览 |
| Set | 自动去重 | 标签、关注列表、去重统计 |
| Sorted Set | 每个元素带分数 | 排行榜、评分、延迟队列 |

```python
# 字符串：带过期时间（最常用）
await redis.setex("token:user:123", 3600, token)
await redis.incrby("stat:visits", 5)

# 哈希：存对象，可以只改一个字段
await redis.hset("user:1001", mapping={"name": "张三", "email": "z@example.com"})
await redis.hget("user:1001", "name")

# 集合：天然去重
await redis.sadd("tags:article:1", "Python", "FastAPI")
await redis.sismember("tags:article:1", "Python")

# 有序集合：排行榜
await redis.zadd("rank:week", {"张三": 100, "李四": 90})
await redis.zrevrange("rank:week", 0, -1, withscores=True)
```

### Key 的命名规范

**格式 `业务:模块:标识:属性`**，全小写、冒号分隔，例如
`user:session:12345`、`zhizhou:article:1001:views`。

四条硬要求：

1. **别用空格、换行、中文**（中文虽可编码，但排错时极难辨认）；
2. **长度控制**：超过 100 字符的 key 既占内存又拖慢比较；
3. **统一前缀**：便于按模式批量删除与统计（`SCAN MATCH zhizhou:article:*`）；
4. **带过期时间**：除非是必须长期保留的数据，否则一律 `setex()` / `expire()`——
   缓存忘记设过期是内存被吃满的头号原因。

> ⚠️ **注意**：生产环境**不要用 `KEYS pattern`**。它是 O(N) 且会阻塞整个实例，
> 在几百万 key 上足以让服务卡住几秒。用 `SCAN` 游标迭代（`redis-cli --scan` 或客户端的 `scan_iter`）。

### 接入 FastAPI

```python
# config/redis_client.py
import redis.asyncio as aioredis
from redis.asyncio.connection import ConnectionPool

pool = ConnectionPool(
    host="localhost",
    port=6379,
    db=0,
    decode_responses=True,     # 返回 str 而不是 bytes
    max_connections=100,
    socket_timeout=5,
    socket_keepalive=True,
)


async def init_redis() -> aioredis.Redis:
    client = aioredis.Redis(connection_pool=pool)
    try:
        await client.ping()                 # 启动就校验，别等第一个请求才炸
    except Exception as exc:
        raise RuntimeError(f"Redis 连接失败: {exc}") from exc
    return client
```

```python
# main.py（与数据库的 lifespan 合并成一个）
@asynccontextmanager
async def lifespan(app: FastAPI):
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
    app.state.redis = await init_redis()      # 挂在 app.state 上（1.11.8）
    yield
    await app.state.redis.aclose()            # 关闭连接池
    await engine.dispose()
```

**为什么要连接池**：和数据库同理。Redis 每个连接都要一次握手 + 认证，
高并发下频繁建连会成为瓶颈。`max_connections=100` 要与 Redis 的
`maxclients`（默认 10000）以及副本数一起看。

> ⚠️ **注意**：`decode_responses=True` 必须显式写。默认返回 `bytes`，
> `await redis.get("k")` 拿到的是 `b"value"`，与字符串比较永远不相等——
> 这类 bug 通常表现为「缓存永远不命中」。
> 另外：客户端是**异步**的（`redis.asyncio`），同步版会在事件循环里阻塞，
> 与 1.7 讲的 `time.sleep()` 是同一类错误。

## 1.12.12 缓存模式与三大问题

### 缓存读取的标准流程

```text
请求 → 查缓存 → 命中 → 直接返回
              ↓ 未命中
         查数据库 → 返回数据 → 写入缓存（带过期时间）
```

```python
async def get_article(article_id: int, db: AsyncSession, redis) -> dict | None:
    cache_key = f"zhizhou:article:{article_id}"
    cached = await redis.get(cache_key)
    if cached is not None:
        return json.loads(cached)

    article = await fetch_from_db(article_id, db)     # 你的事务性查询
    if article is None:
        await redis.setex(cache_key, 60, "NULL")      # 空值也缓存，见「穿透」
        return None
    await redis.setex(cache_key, 3600, json.dumps(article, ensure_ascii=False))
    return article
```

> 🔥 **常见坑**：为了让「存什么都能取回来」，很常见的写法是用 `eval(cached)` 反序列化。
> **绝对不要用 `eval`**——
> 缓存里若被写入恶意内容就是远程代码执行漏洞。
> 一律用 `json.loads()` / `pickle` 之外的显式格式。

### 过期时间怎么定

| 数据 | 建议过期 | 理由 |
| --- | --- | --- |
| 验证码 | 5–10 分钟 | 短时效，够用即失效 |
| 商品 / 文章详情 | 1–24 小时 | 平衡新鲜度与命中率 |
| 认证令牌 | 1–7 天 | 与刷新令牌机制配套 |
| 空值标记 | 1–5 分钟 | 防穿透，但不能长期占位 |

### 更新时怎么处理缓存

**推荐：先更新数据库，再删除缓存。**

```python
await update_db(article_id, data, db)      # ① 先更库
await redis.delete(f"zhizhou:article:{article_id}")   # ② 再删缓存
```

为什么不「直接更新缓存」？高并发下两个请求可能以相反顺序写缓存，
留下一个**永远过期不了**的旧值。删除是幂等的，谁先谁后都一样。

为什么不是「先删缓存再更库」？删除与更库之间若有请求进来，
它会读到旧数据并**重新写进缓存**，于是旧值又活了。

极端并发下仍有窗口期，可以加**延迟双删**：更库 → 删缓存 → 等 1 秒 → 再删一次。
代价是复杂度，只在数据一致性要求高的场景用。

### 三大问题

**① 缓存穿透：查一个不存在的数据**

```text
查 id=99999（不存在）→ 缓存没有 → 查库也没有 → 返回空
→ 反复请求 → 每次都打到数据库
```

恶意请求可以拿不存在的 id 持续压库。**解法：把「空」也缓存**，
用短过期（1–5 分钟）标记：

```python
await redis.setex(cache_key, 60, "NULL")     # 读取时判断 == "NULL" 直接返回 None
```

生产规模下更好的方案是布隆过滤器（Bloom Filter）先挡一层，
但它有误判率，且删除元素麻烦，属于进阶话题。

**② 缓存雪崩：大量 key 同时失效**

因为过期时间是**同一批设定的**，1 小时后同时失效，请求一起涌向数据库。

**解法：给过期时间加随机偏移。**

```python
import random

expiry = 3600 + random.randint(-360, 360)    # 3600 ± 10%
await redis.setex(cache_key, expiry, payload)
```

更彻底的方案是多级缓存（本地缓存 + Redis），以及给数据库加限流兜底。

**③ 缓存击穿：热点 key 失效瞬间**

单个超热 key（首页、爆款商品）过期的瞬间，成千上万并发同时去查库。
与雪崩的区别：**雪崩是「很多 key 同时失效」，击穿是「一个 key 被同时打」**。

**解法：双重检查锁（double-checked locking）**——只让一个请求去查库，其余等待后重试：

```python
import asyncio
import json

async def get_hot(article_id: int, db, redis):
    cache_key = f"zhizhou:article:{article_id}"

    cached = await redis.get(cache_key)                  # 第一次检查
    if cached is not None:
        return json.loads(cached)

    lock_key = f"lock:{cache_key}"
    got_lock = await redis.set(lock_key, "1", ex=5, nx=True)

    if not got_lock:
        for _ in range(5):                               # 重试，而不是递归
            await asyncio.sleep(0.1)
            cached = await redis.get(cache_key)
            if cached is not None:
                return json.loads(cached)
        return None                                      # 别死等，给个兜底

    try:
        cached = await redis.get(cache_key)              # 第二次检查
        if cached is not None:
            return json.loads(cached)
        data = await fetch_from_db(article_id, db)
        await redis.setex(cache_key, 3600, json.dumps(data, ensure_ascii=False))
        return data
    finally:
        await redis.delete(lock_key)                     # 无论成败都放锁
```

四个细节：**锁必须有过期时间**（否则进程崩了就永久死锁）；
**锁的过期时间要大于「查库 + 写缓存」的耗时**（建议多留 2–3 秒）；
**等待方要限制重试次数**（用 `for` 循环而不是递归——
递归在流量大时会堆栈溢出）；**拿到锁后要再检查一次缓存**
（这就是「双重检查」的由来：可能在等锁期间别人已经填好了）。

> ⚠️ **注意**：上面的锁是「防击穿」的**软锁**，不是严格的分布式锁。
> 它不保证互斥性（锁到期后第二个请求也能拿到），只是把并发压到可接受水平。
> 需要严格互斥时要用带唯一值校验的锁（Lua 脚本比较并删除），属于进阶话题。

### 生产环境的 Redis 配置

| 项 | 建议 | 原因 |
| --- | --- | --- |
| 持久化 | RDB + AOF 混合 | RDB 便于备份与快速恢复，AOF 保证最近写入不丢 |
| 淘汰策略 | `volatile-lru` | 只淘汰设了过期时间的 key，避免误删长效数据 |
| 部署 | 哨兵或集群 | 单点故障会让「缓存挂了」变成「服务挂了」 |

> ⚠️ **注意**：**缓存不是数据库**。Redis 挂了，业务应当降级为「直接查库」，
> 而不是整个接口 500。做法是在缓存层外面套 `try/except`，
> 记录告警后放行到数据库——缓存是加速器，不是依赖。

## 1.12.13 综合示例：知舟的文章接口

把整章串起来：三层架构 + 会话依赖 + 缓存 + 错误转换。为了可运行，用 SQLite 作数据库、
缓存部分用**一个内存字典替代 Redis**（因为它在本机装不了），

```python
# app/db.py
from sqlalchemy.ext.asyncio import AsyncSession, async_sessionmaker, create_async_engine

DATABASE_URL = "sqlite+aiosqlite:///./zhizhou.db"

engine = create_async_engine(
    DATABASE_URL,
    pool_pre_ping=True,
    pool_recycle=3600,
)

AsyncSessionLocal = async_sessionmaker(
    bind=engine,
    class_=AsyncSession,
    expire_on_commit=False,        # 见 1.12.5：不是可选项
)


async def get_db():
    async with AsyncSessionLocal() as session:
        try:
            yield session
            await session.commit()
        except Exception:
            await session.rollback()
            raise
        finally:
            await session.close()
```

```python
# app/main.py
import json
from contextlib import asynccontextmanager

from fastapi import Depends, FastAPI, HTTPException, Query, Request, status
from fastapi.responses import JSONResponse
from sqlalchemy import func, select
from sqlalchemy.exc import IntegrityError
from sqlalchemy.ext.asyncio import AsyncSession

from app.db import engine, get_db
from app.models import Article, Base
from app.schemas import ArticleCreate, ArticleOut, PaginationOut

# ——— 缓存层：本机用内存字典替代 Redis，接口形状与 Redis 一致 ———
class MemoryCache:
    """只用于示例：真实项目换成 redis.asyncio 客户端。"""

    def __init__(self) -> None:
        self._data: dict[str, str] = {}

    async def get(self, key: str) -> str | None:
        return self._data.get(key)

    async def setex(self, key: str, ttl: int, value: str) -> None:
        self._data[key] = value          # 示例忽略 TTL，真实实现会过期

    async def delete(self, key: str) -> None:
        self._data.pop(key, None)

    async def aclose(self) -> None:
        self._data.clear()


@asynccontextmanager
async def lifespan(app: FastAPI):
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)
    app.state.cache = MemoryCache()
    yield
    await app.state.cache.aclose()
    await engine.dispose()


app = FastAPI(title="知舟 API", lifespan=lifespan)


@app.exception_handler(IntegrityError)
async def integrity_handler(request: Request, exc: IntegrityError):
    return JSONResponse(status_code=409, content={"detail": "标题已存在"})


@app.post("/articles", response_model=ArticleOut, status_code=status.HTTP_201_CREATED)
async def create_article(data: ArticleCreate, db: AsyncSession = Depends(get_db)):
    article = Article(**data.model_dump())
    db.add(article)
    await db.flush()
    return article


@app.get("/articles", response_model=PaginationOut)
async def list_articles(
    page: int = Query(1, ge=1),
    page_size: int = Query(10, ge=1, le=50),
    db: AsyncSession = Depends(get_db),
):
    total = await db.scalar(select(func.count(Article.id)))
    total_pages = (total + page_size - 1) // page_size
    result = await db.execute(
        select(Article)
        .order_by(Article.id)
        .offset((page - 1) * page_size)
        .limit(page_size)
    )
    return {
        "items": list(result.scalars().all()),
        "total": total,
        "page": page,
        "page_size": page_size,
        "total_pages": total_pages,
    }


@app.get("/articles/{article_id}", response_model=ArticleOut)
async def get_article(article_id: int, request: Request, db: AsyncSession = Depends(get_db)):
    """缓存旁路（cache-aside）读取：命中直接返回，未命中回源并写缓存。"""
    cache = request.app.state.cache
    cache_key = f"zhizhou:article:{article_id}"

    cached = await cache.get(cache_key)
    if cached is not None:
        return json.loads(cached)          # 命中：不碰数据库

    article = await db.get(Article, article_id)
    if article is None:
        raise HTTPException(status_code=404, detail=f"文章 id={article_id} 不存在")

    await cache.setex(cache_key, 3600, json.dumps(
        ArticleOut.model_validate(article).model_dump(mode="json"), ensure_ascii=False))
    return article


@app.post("/articles/{article_id}/read", response_model=ArticleOut)
async def read_article(article_id: int, request: Request, db: AsyncSession = Depends(get_db)):
    """浏览量 +1：先更新数据库，再删除缓存。"""
    cache = request.app.state.cache
    article = await db.get(Article, article_id)
    if article is None:
        raise HTTPException(status_code=404, detail=f"文章 id={article_id} 不存在")

    article.views += 1                 # 脏检查只更新 views 一列
    await db.flush()
    await cache.delete(f"zhizhou:article:{article_id}")   # 先更库、再删缓存
    return article
```

```python
from fastapi.testclient import TestClient

from app.main import app

    assert client.get(f"/articles/{first_id}").json()["title"] == "第一篇"
```

四个设计点：

1. **提交统一在 `get_db` 收尾**，路由里只 `flush()`——
   事务边界只有一处，`expire_on_commit=False` 让返回 ORM 对象变得安全。
2. **`views` 的更新走脏检查**，不必手写 `UPDATE ... SET views = views + 1`。
   代价是「读-改-写」有并发窗口：两个请求同时读到 `views=0` 会都写成 1。
   真要高并发计数应该交给 Redis 的 `INCR`（原子操作），再定期回写数据库。
3. **缓存替换成 `MemoryCache` 只改了实现，没改调用形状**——
   这正是「接入层」该有的样子：换 Redis 只改 `lifespan` 里那一行。
   注意 `get_article` 命中缓存时**完全不碰数据库**，这才是缓存的意义；
   而写路径先更库、再删缓存，保证下一次读会回源拿到新值。
4. **`with TestClient(app)` 才触发 `lifespan`**。不用上下文管理器时，
   `create_all` 不会执行，测试会报「表不存在」——这是用 `lifespan` 建表后最常见的困惑。

## 常见坑

- **忘记 `await engine.dispose()`**。现象：反复重启后数据库连接数只涨不跌。修法：写在 `lifespan` 的 `yield` 之后。
- **`expire_on_commit` 用了默认值 `True`**。现象：路由内 `commit()` 后返回 ORM 对象，报 `ResponseValidationError` / `MissingGreenlet`，错误却指向 `response_model`。修法：在 `async_sessionmaker` 上显式设 `expire_on_commit=False`。
- **生产环境靠 `create_all` 改表结构**。现象：模型加了字段，接口第一次查询报「列不存在」。修法：引入 Alembic 迁移；`create_all` 只用于本地。
- **`decode_responses=True` 漏写**。现象：缓存永远不命中，因为拿到的是 `b"..."`。修法：连接池上加该项，或手工 `decode()`。
- **用 `eval()` 反序列化缓存**。现象：能跑，但缓存内容可被构造成任意代码执行。修法：`json.loads()`。
- **缓存忘了设过期时间**。现象：Redis 内存缓慢涨满，最后触发淘汰把热数据挤掉。修法：一律 `setex()` / `expire()`。
- **缓存挂了就整个接口 500**。现象：Redis 抖一下，全站不可用。修法：缓存读写包 `try/except`，失败就降级查库并告警。
- **分页 `total_pages` 用了整除**。现象：21 条数据每页 10 条时只有 2 页，最后一页永远看不到。修法：`(total + page_size - 1) // page_size`。
- **`&` / `|` 组合条件没加括号**。现象：SQL 合法但筛错数据。修法：每个条件都加括号。
- **连接池参数没跟副本数一起估算**。现象：平时正常，流量上来后集体报「连接池耗尽」。修法：`pool_size × 副本数 < 数据库 max_connections`。

## 面试视角

> 🎯 **面试**：数据库是后端岗的必考区，也是「有没有写过真项目」的分水岭——只会 ORM 增删改查的人讲不出事务边界与 N+1。题库里「数据库」相关的考点基本落在下面六问。

1. **「ORM 的优缺点？什么时候你会放弃它？」**
   考察点：技术选型的判断力。答题要点：优点是映射明确、跨库、可维护；代价是有学习成本、复杂查询会被抽象拖累、配置不当引入 N+1。放弃的场景：批量导入、复杂报表、需要精确控制游标的逐行处理。
2. **「`expire_on_commit` 是干什么的？为什么一般设 `False`？」**
   考察点：踩过坑没有。答题要点：`True` 时提交会让对象属性过期，下次访问触发重新查库；在异步 ORM 里，若提交发生在响应序列化**之前**（路由或 DAO 里 commit），序列化读属性时会抛 `MissingGreenlet`。所以只要有先提交再返回 ORM 对象的代码，就必须设 `False`。
3. **「事务边界放在哪里？」**
   考察点：架构意识。答题要点：放在**请求生命周期**上，即 `get_db` 依赖的收尾：正常提交、异常回滚、始终关闭。路由与 DAO 只 `flush()` 不 `commit()`，好处是一个请求内的多次写要么全成要么全败。确实需要独立提交的（审计日志）另开会话。
4. **「N+1 查询是什么？怎么发现和解决？」**
   考察点：性能经验。答题要点：查 N 条主记录后，逐条去查它的关联对象，于是 1 次查询变成 N+1 次。发现手段：打开 `echo=True` 数 SQL 条数，或用慢查询日志。解法：用 `selectinload()` / `joinedload()` 预加载，或干脆用一条 JOIN 查询直接拿平铺结果。
5. **「缓存穿透、雪崩、击穿分别怎么解？」**
   考察点：是否真的处理过线上缓存问题。答题要点：穿透是查不存在的数据 → 缓存空值或布隆过滤器；雪崩是大量 key 同时失效 → 过期时间加随机偏移；击穿是热点 key 失效 → 双重检查锁，且只让一个请求回源。
6. **「更新数据时缓存怎么处理？为什么不直接更新缓存？」**
   考察点：一致性理解。答题要点：**先更新数据库、再删除缓存**。直接更新缓存在并发下顺序会乱，留下永久脏值；删除是幂等的。极端并发下可加延迟双删。

## 本章小结

1. **ORM 把表映射成类**，收益在一致性与可维护性；但批量导入、复杂报表、精细的性能控制仍应交给原生 SQL。
2. 引擎配 **`sqlalchemy[asyncio]` + 对应数据库的异步驱动**；连接池的 `pool_size` / `max_overflow` / `pool_recycle` / `pool_pre_ping` 各自防的是不同问题，且要与副本数一起估算。
3. SQLAlchemy 2.0 用 `DeclarativeBase` + `Mapped` + `mapped_column` 定义模型；**`Mapped[str]` 自动非空、`Mapped[str | None]` 自动可空**，库级约束（`CheckConstraint`）是应用层校验之外的最后一道防线。
4. **`lifespan` 一处管好启动与关闭**：建表用 `create_all`、退出用 `engine.dispose()`；生产环境的表结构变更必须用 Alembic。
5. 会话依赖写全 `try / except / finally` 三件事；**`expire_on_commit=False` 是正确性要求而非优化**——它决定了「先提交再返回 ORM 对象」会不会 500。
6. 查询用 `select()` 构造、`scalars()` 提取；`first()` 容忍多行，`scalar_one_or_none()` 预期唯一。分页要查总条数，`total_pages` 记得向上取整。
7. 写入靠**脏检查**：改了属性，提交时只生成改过那几列的 `UPDATE`；新增用 `flush()` 拿自增 id，提交交给依赖层。
8. 数据库异常要**翻译**：`IntegrityError` 默认是 500，应转成 409（唯一约束）或 400（检查约束），并且别忘了回滚。
9. 分层把 HTTP 语义、业务规则、SQL 细节分开；DAO 依赖 `get_db`，同一请求共享同一会话，测试时用 `dependency_overrides` 换掉 DAO 即可脱离数据库。
10. Redis 按场景选结构（String / Hash / List / Set / ZSet），key 用 `业务:模块:标识` 命名；缓存按「查缓存 → 回源 → 写缓存」走，更新时**先更库再删缓存**。
11. 穿透用空值标记、雪崩用随机过期、击穿用双重检查锁；**缓存必须能降级**——它挂了业务要能退回数据库。
