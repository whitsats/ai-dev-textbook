## 1.5.1 面向对象的四个词

面向对象不神秘，它只是把「数据」和「操作数据的方法」放在一起：

| 词 | 含义 | 在知舟项目里 |
| --- | --- | --- |
| 类（class） | 模板，定义有哪些属性和方法 | `Chunk` 表示一个待检索的文本块 |
| 对象（object） | 按模板创建出来的实例 | `Chunk(doc_id="d1", text="…", index=0)` |
| 属性（attribute） | 对象身上的数据 | `chunk.text`、`chunk.score` |
| 方法（method） | 对象身上的函数 | `chunk.summarize()` |

这里要先把一个直觉建立起来：**类是一个命名空间 + 一张方法表**。
`obj.method()` 真正发生的事是「在类的方法表里找到 `method`，把 `obj` 作为第一个参数传进去」。
记住这一点，本章后面的 `self`、`super()`、`MRO` 都能自己想明白。

## 1.5.2 定义一个类：`__init__` 与实例化的三步

```python
class Document:
    """一个文档。"""

    kind = "text"                      # 类属性：由所有实例共享

    def __init__(self, title: str, content: str) -> None:
        self.title = title             # 实例属性：每个实例独立
        self.content = content

    def summary(self) -> str:
        return f"{self.title}（{len(self.content)} 字）"


doc = Document("产品公告", "本次发布包含……")
print(doc.summary())                   # 产品公告（8 字）
print(Document.kind, doc.kind)         # text text
```

写 `Document("产品公告", "…")` 时，Python 做了三件事：

1. 造一个**空对象**；
2. 自动调用 `__init__`，把刚建的空对象作为 `self` 传进去；
3. 把初始化完成的这个对象**返回**给调用者。

`__init__` 不是构造函数（真正分配对象的是 `__new__`），它只负责**初始化**。
所以 `__init__` 里不该出现 `return`，也不该在里面做数据库查询、发 HTTP 请求这类耗时操作——
对象创建应该便宜且可预测。

> 💡 **提示**：类名用 `PascalCase`，模块名与函数名用 `snake_case`（见 1.2.2）。
> 类体是一段代码块，**定义时就会执行**——所以类属性在导入模块时就被求值，
> 这一点在 1.5.3 会变成一个真实的坑。

## 1.5.3 类属性与实例属性：共享还是各自持有

```python
class Document:
    kind = "text"          # 类属性
    tags: list[str] = []   # ❌ 可变类属性：所有实例共用同一个列表

a, b = Document(), Document()
a.tags.append("rag")
print(b.tags)              # ['rag'] ← b 被 a 污染了
```

这是 Python 新手最常见的 bug 之一，成因同样是 1.4.2 讲过的**定义时求值一次**：
`tags` 只在类定义时创建了一个列表。修法是把可变容器放进 `__init__`：

```python
class Document:
    kind = "text"

    def __init__(self, title: str) -> None:
        self.title = title
        self.tags: list[str] = []      # ✅ 每个实例一份
```

**属性查找顺序**是「先实例字典，后类字典」：

```python
class Doc:
    kind = "text"

d = Doc()
d.kind = "markdown"        # 这是「新建实例属性」，不是修改类属性
print(d.kind, Doc.kind)    # markdown text
print(d.__dict__)          # {'kind': 'markdown'}
```

想改类属性必须走类：`Doc.kind = "markdown"`。二者的分工可以这样记：
**类属性放所有实例都相同的常量**（默认配置、枚举值），**实例属性放每个对象不同的状态**。

### 顺带说说 `__slots__`

每个实例默认带一个 `__dict__`（字典）存放属性，字典很灵活，但开销不小。
如果项目要同时持有百万级对象，可以声明 `__slots__` 取消 `__dict__`：

```python
class Chunk:
    __slots__ = ("text", "score")

    def __init__(self, text: str, score: float = 0.0) -> None:
        self.text = text
        self.score = score

c = Chunk("hello")
print(c.score)             # 0.0
# c.extra = 1              # AttributeError：没有 __dict__，不能动态加属性
```

代价是不能再动态添加属性，也不能随便多继承。**所以正常写业务类不要用它**，
只有在明确做过 profiling、确认对象数量与内存是瓶颈时才用（第 8 篇会讲怎么量）。

## 1.5.4 三种方法：实例方法、类方法、静态方法

```python
class Chunk:
    default_size = 500

    def __init__(self, text: str) -> None:
        self.text = text

    def render(self, limit: int | None = None) -> str:
        """实例方法：需要用到对象自己的状态。"""
        return self.text[: limit or self.default_size]

    @classmethod
    def from_file(cls, path: str) -> "Chunk":
        """类方法：备选构造器，返回 cls 的实例。"""
        with open(path, encoding="utf-8") as f:
            return cls(f.read().strip())

    @staticmethod
    def count_chars(text: str) -> int:
        """静态方法：与 cls / self 都无关的工具函数。"""
        return len(text)
```

| 类型 | 第一个参数 | 能访问什么 | 典型用途 |
| --- | --- | --- | --- |
| 实例方法 | `self` | 实例属性 + 类属性 | 绝大多数业务逻辑 |
| `@classmethod` | `cls` | 类属性；能创建实例 | 备选构造器（`from_config` / `from_json`） |
| `@staticmethod` | 无 | 都访问不到 | 纯函数工具，放这里只是因为「和这个类有关」 |

两个容易忽略的细节：

- **`cls` 是子类传入的**。`SubChunk.from_file(...)` 里 `cls` 是 `SubChunk` 而不是 `Chunk`，
  所以类方法天然对继承友好——这就是为什么备选构造器要用 `cls()` 而不是写死 `Chunk()`。
- **静态方法与写在模块里的普通函数没有本质区别**。如果它和类没有概念上的归属关系，
  就老老实实写成模块级函数，别为了「看起来面向对象」塞进类里。

## 1.5.5 封装与「私有」的真相

```python
class Account:
    def __init__(self, balance: float) -> None:
        self.__balance = balance           # 双下划线开头

    def get_balance(self) -> float:
        return self.__balance


account = Account(1000)
# account.__balance       # AttributeError: 'Account' object has no attribute '__balance'
print(account._Account__balance)       # 1000  ← 改了个名字而已
```

Python 没有真正的访问控制。`__x` 会被**名字改写（name mangling）**成 `_类名__x`：
它的用途是**避免子类意外覆盖父类的内部名**，而不是防住外人。
规则有两条：「对外不对内」（类内部仍可正常访问），且改写只发生一次
（类定义时检查语法后就固定，之后用 `setattr` 动态加 `__y` 不会改写）。

工程上的正确用法是**约定的单下划线**：

| 写法 | 含义 | 外部能否访问 |
| --- | --- | --- |
| `name` | 公开接口 | 可以，属于契约的一部分 |
| `_name` | 内部实现，**随时可能改动** | 技术上可以，但请不要依赖 |
| `__name` | 防止子类撞名的内部名 | 会被改名，不建议当「私有」用 |

## 1.5.6 property：把访问控制写成接口

真正需要「读的时候计算、写的时候校验」时，用 `property`。
好处是**调用方仍然像用普通属性**，将来想改成方法或加逻辑都不用改动调用方代码。

```python
class User:
    def __init__(self, name: str, age: int) -> None:
        self.name = name
        self.age = age                     # 走 setter 校验

    @property
    def age(self) -> int:
        return self._age

    @age.setter
    def age(self, value: int) -> None:
        if not 0 <= value <= 150:
            raise ValueError(f"年龄不合法：{value}")
        self._age = value


user = User("阿宁", 22)
user.age = 200          # ValueError: 年龄不合法：200
print(user.age)         # 22
```

计算属性则连存储都省了：

```python
class Chunk:
    def __init__(self, text: str) -> None:
        self.text = text

    @property
    def size(self) -> int:
        return len(self.text)

    @property
    def preview(self) -> str:
        return self.text[:50] + ("…" if len(self.text) > 50 else "")
```

三种写法本质相同：装饰器写法（最常见）、`property(getter, setter)` 函数式写法、
以及给 setter / deleter 再套 `@age.setter` / `@age.deleter`。
日常只用装饰器写法就够了，**别为了「Java 风格」给每个属性都套一层 property**——
那只是把简单的事写复杂。

## 1.5.7 继承、重写与 super()

继承表达的是 **is-a** 关系：`ClaudeLLM` 是一种 `BaseLLM`。

```python
class BaseLLM:
    def __init__(self, model: str) -> None:
        self.model = model

    def chat(self, prompt: str) -> str:
        raise NotImplementedError("子类必须实现 chat")


class EchoLLM(BaseLLM):
    def chat(self, prompt: str) -> str:        # 重写（override）
        return f"echo: {prompt}"


class ClaudeLLM(BaseLLM):
    def __init__(self, model: str = "claude-sonnet-4-5", *, api_key: str) -> None:
        super().__init__(model)                # ✅ 先让父类完成它那部分初始化
        self.api_key = api_key

    def chat(self, prompt: str) -> str:
        return f"[{self.model}] 收到：{prompt}"
```

三个要点：

1. **单继承下用 `super()`，不要写 `BaseLLM.__init__(self, model)`。**
   写死父类名会在多继承时把 MRO 里本该只执行一次的初始化执行多次。
2. **重写要兼容父类的契约**：参数含义、返回值类型、异常都要能对上，
   否则调用方拿父类当接口用就会崩（这就是「里氏替换」的通俗版本）。
3. 需要「在父类行为之上再加一点」时，先 `super().chat(prompt)` 拿到结果再加工，
   而不是把父类代码抄一遍。

`isinstance` / `issubclass` 用来做类型判断，**用于对外部输入做防御**是合理的，
但**用它写业务分支往往是设计问题**——`if isinstance(x, A): … elif isinstance(x, B): …`
越长，越说明这里该用多态（见 1.5.10）。

## 1.5.8 MRO：多继承的查找顺序与菱形问题

Python 支持多继承。`D(B, C)` 的属性查找顺序由 **MRO（Method Resolution Order）**决定，
它是一张用 C3 线性化算法算出的、线性的类列表：

```python
class A:
    def hello(self) -> str:
        return "A"


class B(A):
    pass


class C(A):
    pass


class D(B, C):
    pass


print([c.__name__ for c in D.mro()])   # ['D', 'B', 'C', 'A', 'object']
```

判断顺序的三条经验规则（与 C3 算法的结果一致）：

1. **子类先于父类**被检查；
2. 多个父类**按声明顺序**被检查；
3. 对下一个位置若有两个合法候选，**选先出现的那个**。

`B` 与 `C` 都继承 `A`、`D` 又同时继承 `B`、`C` 时，这个结构画出来是个菱形，
被称为**菱形问题（diamond problem）**——如果语言用「深度优先」查找，
`A` 的方法可能被访问两次，状态就会重复初始化。

```python
class A:
    def setup(self) -> None:
        print("A.setup")


class B(A):
    def setup(self) -> None:
        print("B.setup")
        super().setup()          # 按 MRO 找下一个，而不是写死 A


class C(A):
    def setup(self) -> None:
        print("C.setup")
        super().setup()


class D(B, C):
    def setup(self) -> None:
        print("D.setup")
        super().setup()


D().setup()
```

```text
# 输出
D.setup
B.setup
C.setup
A.setup       ← 只执行了一次，这正是 super() 的价值
```

这就是**协作式多继承**：每个类只负责自己那一层，`super()` 沿 MRO 往下传递。
如果你把 `B.setup` 里的 `super().setup()` 换成 `A.setup(self)`，
`A.setup` 就会被执行两次。**规则：多继承场景下一律用 `super()`。**

> ⚠️ **注意**：Python 2 的「经典类」用深度优先，「新式类」用 C3。
> 现代 Python 只有新式类（所有类都继承 `object`），所以**只需要记住 C3 / `mro()`**，
> 面试里被问到「深度优先还是广度优先」时，回答「Python 3 是 C3 线性化，
> 不是二选一」比背结论更准确。

## 1.5.9 Mixin：用继承表达「能做什么」

继承表达 is-a，但有一类需求表达的是 **can-do（能做什么）**：

```python
class Vehicle:
    pass


class FlyableMixin:              # 只提供「能飞」这一个功能
    def fly(self) -> str:
        return f"{type(self).__name__} 起飞"


class CivilAircraft(FlyableMixin, Vehicle):    # 民航飞机能飞
    pass


class Helicopter(FlyableMixin, Vehicle):       # 直升机也能飞
    pass


class Car(Vehicle):                            # 汽车不能飞，也不该"会飞"
    pass
```

把 `fly` 放进 `Vehicle` 会造成「汽车也会飞」的荒唐继承；放到 Mixin 里就干净了。
写 Mixin 的三条惯例：

1. **命名以 `Mixin` 结尾**，让人一眼看出它不是一条真实的「is-a」；
2. **单一职责**：一个 Mixin 只加一种能力，需要多种能力就写多个；
3. **可有可无**：不继承它的子类照样能正常工作，只是少了那个功能。

> 💡 **提示**：日志、重试、计时、序列化这类**横切关注点**最适合做成 Mixin
> （注意与 1.4.5 的装饰器区分：装饰器改的是**函数**，Mixin 加的是**类的能力**）。

## 1.5.10 多态与鸭子类型

多态指「同一个调用，落到不同对象的实现上」：

```python
class BaseLLM:
    def chat(self, prompt: str) -> str:
        raise NotImplementedError

class EchoLLM(BaseLLM):
    def chat(self, prompt: str) -> str:
        return f"echo: {prompt}"

class ReverseLLM(BaseLLM):
    def chat(self, prompt: str) -> str:
        return prompt[::-1]


def ask_all(llm: BaseLLM, prompt: str) -> None:
    print(llm.chat(prompt))            # 不关心具体是哪个子类


for llm in (EchoLLM(), ReverseLLM()):
    ask_all(llm, "你好")
```

Python 更进一步：**只要对象有 `chat` 方法就能传进来，不要求继承同一个基类**——
这叫**鸭子类型（duck typing）**：「走起来像鸭子、叫起来像鸭子，那就是鸭子」。

```python
def total_size(chunks: list) -> int:
    return sum(len(c) for c in chunks)     # 只要求「能被 len()」，不关心它是什么类
```

鸭子类型灵活，但**静态检查工具看不出错误**，所以工程上把它「写成类型」：

```python
from typing import Protocol


class SupportsChat(Protocol):
    def chat(self, prompt: str) -> str: ...


def ask(llm: SupportsChat, prompt: str) -> str:
    return llm.chat(prompt)
```

`Protocol` 是**结构化类型**：任何有 `chat` 方法的类都自动满足它，不需要显式继承。
需要「强制子类实现」时则用抽象基类：

```python
from abc import ABC, abstractmethod


class VectorStore(ABC):
    @abstractmethod
    def search(self, query: str, k: int) -> list[str]:
        """子类必须实现，否则实例化就报 TypeError。"""


# VectorStore()        # TypeError: Can't instantiate abstract class
```

什么时候用哪个：

| 需求 | 选择 |
| --- | --- |
| 只想要类型提示，不想强制继承 | `Protocol` |
| 要求子类必须实现某些方法 | `ABC` + `@abstractmethod` |
| 只是想让相关工具函数有个家 | 普通模块级函数 |

## 1.5.11 魔术方法：让对象像内置类型一样工作

以双下划线开头和结尾的方法叫**魔术方法**（也叫内置方法 / dunder method），
它们由 Python 在特定时机**自动触发**，目的是「定制你的对象在语言层面的行为」。

```python
class Chunk:
    def __init__(self, text: str, score: float = 0.0) -> None:
        self.text = text
        self.score = score

    def __repr__(self) -> str:            # 给开发者：调试、日志
        return f"Chunk(text={self.text!r}, score={self.score})"

    def __str__(self) -> str:             # 给用户：print / f-string
        return self.text

    def __len__(self) -> int:             # 支持 len()
        return len(self.text)

    def __eq__(self, other: object) -> bool:
        if not isinstance(other, Chunk):
            return NotImplemented         # 交给对方去比较，而不是直接 False
        return (self.text, self.score) == (other.text, other.score)

    def __hash__(self) -> int:            # 与 __eq__ 成对定义
        return hash((self.text, self.score))


c = Chunk("检索增强生成", 0.91)
print(c)               # 检索增强生成
print(repr(c))         # Chunk(text='检索增强生成', score=0.91)
print(len(c))          # 6
print(c == Chunk("检索增强生成", 0.91))   # True
print(len({c}))        # 1
```

`__repr__` 与 `__str__` 的分工要记清：`__str__` 面向使用者（可读），
`__repr__` 面向开发者（**最好是能重建该对象的表达式**）。只写一个时，**写 `__repr__`**——
未定义 `__str__` 时会自动退化为 `__repr__`，反过来则不成立。

上下文管理器是另一个高频魔术方法，它让 `with` 语句可用：

```python
import time


class Timer:
    def __enter__(self):
        self.start = time.perf_counter()
        return self

    def __exit__(self, exc_type, exc, tb) -> bool:
        self.cost = time.perf_counter() - self.start
        return False          # 返回 True 会「吞掉」异常，通常不要这么做


with Timer() as timer:
    time.sleep(0.05)
print(f"耗时 {timer.cost:.3f}s")
```

值得记住的还有几个：

| 魔术方法 | 触发时机 | 典型用途 |
| --- | --- | --- |
| `__init__` | 创建实例 | 初始化属性 |
| `__repr__` / `__str__` | `repr()` / `print()` | 调试与展示 |
| `__eq__` / `__hash__` | `==` / `hash()`、放进 `set` 或 `dict` 键 | 值比较与去重 |
| `__len__` | `len()` | 让容器类可测长度 |
| `__iter__` | `for` 循环 | 让对象可迭代（配合 1.4.6 的生成器） |
| `__call__` | 像函数一样调用 `obj()` | 有状态的「函数」 |
| `__enter__` / `__exit__` | `with` 语句 | 资源获取与释放 |
| `__del__` | 对象被回收前 | **不要依赖它**，清理请用 `with` |

> 🔥 **常见坑**：一旦定义了 `__eq__`，Python 会把 `__hash__` 置为 `None`，
> 于是 `Chunk(...)` 不能再放进 `set` 或当 `dict` 的键（`TypeError: unhashable type`）。
> 这在 1.3.4 讲的去重、缓存场景里会立刻踩到。**规则：定义 `__eq__` 就顺手定义 `__hash__`**，
> 且 `__hash__` 只能基于**不可变**字段计算。
>
> ⚠️ `__del__` 的调用时机由垃圾回收决定，进程退出时不保证执行。
> 清理文件、连接、锁一律用 `with`，不要指望它。

## 1.5.12 选型：什么时候用类、什么时候不用

先看「只有数据、没有行为」的场景，四种写法的取舍：

| 写法 | 特点 | 适用 |
| --- | --- | --- |
| 普通类手写 `__init__` | 最灵活，也最啰嗦 | 有行为、有不变量的领域对象 |
| `@dataclass` | 自动生成 `__init__` / `__repr__` / `__eq__` | 内部数据结构、配置对象 |
| `NamedTuple` | 不可变、可解包、有索引 | 轻量值对象（坐标、区间） |
| Pydantic `BaseModel` | **带校验与解析**，把 JSON 变成对象 | 接口出入参（见 1.10） |

```python
from dataclasses import dataclass, field


@dataclass(frozen=True)          # frozen=True：不可变，且自动可哈希
class Source:
    doc_id: str
    page: int = 0


@dataclass
class Chunk:
    text: str
    source: Source
    score: float = 0.0
    tags: list[str] = field(default_factory=list)   # 可变默认值必须用 factory


print(Chunk("正文", Source("d1", 3)))
# Chunk(text='正文', source=Source(doc_id='d1', page=3), score=0.0, tags=[])
```

`@dataclass` 恰好绕开了本章反复出现的两个坑：`field(default_factory=...)` 解决可变默认值，
`frozen=True` 顺手给出不可变与可哈希。**内部数据优先用它，别手写二十行样板代码。**

反过来，有三种情况**不该**用类：

1. **只有数据没有行为**，又不涉及校验：直接 `dict` 或 `dataclass`，不要造一个空壳类；
2. **只是一组相关函数**：写成模块级函数，不要硬塞进「工具类」；
3. **一个类什么都管**（俗称「神类」）：出现几百行、几十个方法时，
   按职责拆成多个类或回到函数，比继续加方法好。

## 1.5.13 综合示例：知舟的领域模型

把本章内容组装成知舟项目的领域模型，后面第 5 篇的检索链路会直接复用：

```python
# app/domain/models.py
from abc import ABC, abstractmethod
from dataclasses import dataclass, field


@dataclass(frozen=True)
class Source:
    """检索结果的出处，不可变因此可哈希。"""
    doc_id: str
    page: int = 0


@dataclass
class Chunk:
    """一个待检索的文本块。"""
    text: str
    source: Source
    score: float = 0.0
    tags: list[str] = field(default_factory=list)

    def __len__(self) -> int:
        return len(self.text)

    def __repr__(self) -> str:                       # 调试友好，不打印全文
        return f"Chunk({self.text[:12]!r}…, score={self.score:.2f})"


class VectorStore(ABC):
    """向量库的统一接口：换实现不改调用方。"""

    @abstractmethod
    def add(self, chunks: list[Chunk]) -> None: ...

    @abstractmethod
    def search(self, query: str, k: int = 3) -> list[Chunk]: ...


class LoggableMixin:
    def log(self, message: str) -> None:
        print(f"[{type(self).__name__}] {message}")


class InMemoryStore(LoggableMixin, VectorStore):
    """教学用的内存实现：真实现换成 Milvus / pgvector（第 5 篇）。"""

    def __init__(self) -> None:
        self._items: list[Chunk] = []

    def add(self, chunks: list[Chunk]) -> None:
        self._items.extend(chunks)
        self.log(f"已写入 {len(chunks)} 个文本块")

    def search(self, query: str, k: int = 3) -> list[Chunk]:
        hits = [c for c in self._items if query in c.text]
        return sorted(hits, key=lambda c: -c.score)[:k]


store = InMemoryStore()
store.add([Chunk("检索增强生成把外部知识放进上下文", Source("d1", 3), 0.91),
           Chunk("向量数据库负责相似度检索", Source("d2", 7), 0.66)])
for chunk in store.search("检索"):
    print(repr(chunk), len(chunk))
```

```text
# 输出
[InMemoryStore] 已写入 2 个文本块
Chunk('检索增强生成把外部知识放'…, score=0.91) 16
Chunk('向量数据库负责相似度检索'…, score=0.66) 12
```

这个示例一次性用到了本章六个概念：抽象基类定接口、Mixin 加日志能力、
`dataclass` 承载数据、`__len__` / `__repr__` 让对象好用、
字段类型注解为后续接 Pydantic 与类型检查铺路。

## 常见坑

- **可变对象作类属性**。现象：改一个实例，别的实例跟着变。
  原因：类属性在定义时创建一次、被所有实例共享。修法：在 `__init__` 里 `self.x = []`，
  或 `dataclass` 用 `field(default_factory=list)`。
- **把 `__` 当访问控制**。现象：以为外部访问不到，结果 `obj._Cls__x` 照样能读写。
  原因：名字改写只是防子类撞名。修法：对外接口用单下划线约定 + `property` 校验。
- **多继承里写死父类名**。现象：某个初始化被执行两次，或父类方法莫名被跳过。
  原因：`Base.__init__(self, …)` 绕开了 MRO。修法：一律 `super().__init__(…)`。
- **定义了 `__eq__` 却忘了 `__hash__`**。现象：对象放进 `set` 报
  `TypeError: unhashable type`。原因：定义 `__eq__` 会把 `__hash__` 置为 `None`。
  修法：成对定义，且只用不可变字段算哈希。
- **在 `__init__` 里做重活**。现象：导入或创建对象时突然变慢，测试里还连了数据库。
  原因：把「初始化」和「加载数据」混在一起。修法：`__init__` 只赋值，
  取数据用单独方法或类方法（如 `from_file`）。
- **只写 `__str__` 不写 `__repr__`**。现象：调试时打印的是
  `<__main__.Chunk object at 0x…>`。原因：`repr` 退化方向是反的。
  修法：优先实现 `__repr__`。
- **依赖 `__del__` 做清理**。现象：程序退出时文件没关、连接没断。
  原因：`__del__` 的执行时机不确定。修法：用 `with` 和 `__enter__` / `__exit__`。

## 面试视角

> 🎯 **面试**：1.4 的装饰器与本章的魔术方法，是 Python 岗最常被要求「现场手写」的两类题。
> 题库里「面向对象」相关的题目，考察点基本落在下面的第 2、4、5 题。

1. **「类属性和实例属性有什么区别？」**
   考察点：属性查找顺序。答题要点：查找先实例字典后类字典；读取会回退到类属性，
   但赋值一定是创建实例属性；可变类属性被所有实例共享，是最常见的 bug 来源。
2. **「Python 的私有属性是真的私有吗？」**
   考察点：名字改写机制。答题要点：`__x` 被改写为 `_类名__x`，只是防子类撞名，
   不是访问控制；工程上用 `_x` 表示内部实现，用 `property` 做校验。
3. **「`@classmethod` 和 `@staticmethod` 有什么区别？」**
   考察点：绑定机制。答题要点：前者第一个参数是 `cls`（对继承友好，适合备选构造器），
   后者不自动传参；只跟类「概念相关」的工具函数用 staticmethod，否则写成模块函数。
4. **「多继承的查找顺序是怎么定的？菱形问题怎么解决？」**
   考察点：MRO。答题要点：C3 线性化，`Cls.mro()` 可查；子类先于父类、按声明顺序、
   选先出现的候选；协作式多继承中统一用 `super()`，保证父类方法只执行一次。
5. **「鸭子类型是什么？为什么要用 `Protocol` 或抽象基类？」**
   考察点：接口设计。答题要点：只关心「有没有这个方法」；
   `Protocol` 提供结构化类型（不强制继承），`ABC` 强制子类实现；
   两者都是把运行期的约定提前到静态检查阶段。
6. **「什么时候不该用面向对象？」**
   考察点：工程判断。答题要点：只有数据没有行为用 `dataclass` / `dict`；
   一组相关函数用模块级函数；避免几百行的「神类」。

## 本章小结

- 类是命名空间 + 方法表；`obj.m()` 等价于 `Cls.m(obj)`。
- 实例化三步：造空对象 → 调 `__init__` → 返回对象；`__init__` 里只做赋值。
- 属性查找先实例后类；**可变类属性会被所有实例共享**，容器一律放进 `__init__`。
- 三种方法：实例方法用 `self`；`@classmethod` 用 `cls`，适合备选构造器；
  `@staticmethod` 不自动传参，等价于模块函数。
- Python 没有访问控制：`__x` 只是改名为 `_类名__x`；`_x` 是「内部实现」的约定。
- `property` 让调用方继续像用属性一样访问，同时获得计算与校验能力。
- 继承是 is-a，Mixin 是 can-do；多继承下**一律用 `super()`**，避免父类初始化重复执行。
- MRO 由 C3 线性化决定，`Cls.mro()` 可查；Python 3 不存在「深度优先还是广度优先」的二选一。
- 多态看行为不看类型；`Protocol` 给鸭子类型加类型检查，`ABC` 强制子类实现。
- 魔术方法让自定义对象支持 `print` / `len` / `==` / `for` / `with`；
  定义 `__eq__` 必须同时定义 `__hash__`；清理资源用 `with` 而不是 `__del__`。
- 内部数据结构优先用 `@dataclass`（可变默认值用 `field(default_factory=…)`）。
