# 1.1 环境搭建：Python、依赖管理、IDE 与 Git

> **本章导读**：几乎所有「代码跑不起来」的问题，都出在环境这一步。
> 本章把环境拆成四个问题：用哪个 Python、依赖装在哪里、编辑器怎么配、代码怎么管。
> 学完你会得到三样东西——一个干净的虚拟环境、一个能访问 `/docs` 的 FastAPI 应用，
> 以及一个结构规范的 Git 仓库。后面的每一章都建立在它们之上。

## 学习目标

- [ ] 独立安装并验证 Python 3.11+，说清「为什么不用系统自带的 Python 装依赖」
- [ ] 用 `venv` 创建、激活虚拟环境，并用 `requirements.txt` 复现依赖
- [ ] 写出并启动第一个 FastAPI 应用，访问 `/docs` 看到交互式文档
- [ ] 说明 FastAPI 相对 Flask / Django 的取舍，以及它依赖的核心技术栈
- [ ] 用 `.gitignore` 排除虚拟环境与密钥，完成一次规范的提交

## 前置知识

无。这是全书第一章，只需要你会基本的命令行操作（`cd`、`ls`）。

## 1.1.1 环境要解决的三个问题

在装任何东西之前，先明确环境搭建到底在解决什么：

| 问题 | 不解决会怎样 | 本章方案 |
| --- | --- | --- |
| 用哪个 Python | 系统里三四个 Python，装的库互相看不见 | 固定 Python 3.11+，用虚拟环境隔离 |
| 依赖装在哪 | 项目 A 升级一个库，项目 B 崩了 | 每个项目一个 `.venv` |
| 怎么复现 | 换台电脑就装不出同样环境 | `requirements.txt` 锁定依赖 |

> ⚠️ **注意**：本书所有示例基于 **Python 3.11+**（截至 2026-09-11）。
> 3.10 及以下会缺少部分类型语法（如 `X | None` 的写法在旧版本上语义不同），
> 请先确认版本再往下读。

## 1.1.2 安装 Python 3.11+ 并验证

先看你机器上有什么：

```bash
# 检查版本（输出）
python --version     # Python 3.11.9
pip --version        # pip 24.x
```

不同系统的安装方式：

| 系统 | 推荐方式 | 注意 |
| --- | --- | --- |
| Windows | 官网安装包，勾选 **Add python.exe to PATH** | 不要用 Microsoft Store 版，路径容易混乱 |
| macOS | 官网安装包或 Homebrew（`brew install python@3.12`） | 系统自带的 `/usr/bin/python3` 不要用来装项目依赖 |
| Linux | 发行版包管理器 + `python3.11-venv` | 需要额外装 `python3-venv` 才能创建虚拟环境 |

一条通用原则：**系统自带的 Python 只用来创建虚拟环境，不用来装项目依赖。**
原因很直接——系统工具可能依赖某个特定版本的库，你升级它会连带弄坏系统组件。

如果机器上装了多个 Python，先搞清楚默认那个到底是谁：

```bash
# Windows
where python
# macOS / Linux
which -a python3
```

输出的**第一行**就是你输入 `python` 时实际调用的解释器。若它不是 3.11+，
要么在创建虚拟环境时写全路径（例如 `python3.11 -m venv .venv`），
要么把 PATH 顺序调好——**不要**去改系统里已有的 Python。

## 1.1.3 虚拟环境：每个项目一个隔离空间

虚拟环境（virtual environment）是一个只属于当前项目的依赖目录。创建与激活：

```bash
cd 项目目录
python -m venv .venv          # 创建，目录名约定用 .venv

# 激活（输出：命令行提示符前出现 (env) 或 (.venv)）
# Windows（PowerShell）
.venv\Scripts\Activate.ps1
# Windows（Git Bash）
source .venv/Scripts/activate
# macOS / Linux
source .venv/bin/activate

python -m pip install --upgrade pip    # 顺手升级 pip
```

激活之后，`pip install` 装的库只进 `.venv`；退出用 `deactivate`。

> 💡 **提示**：`.venv` 目录**必须**写进 `.gitignore`。它体积大、且包含绝对路径，
> 提交上去除了污染仓库没有任何好处（1.1.8 会给完整清单）。

如果团队里有人用 Conda，关系可以这样理解：Conda 管「环境 + 非 Python 依赖（如 CUDA）」，
venv 只管「Python 依赖」。本书统一用 `venv`，因为它的行为最可预测。

## 1.1.4 依赖管理：requirements.txt 与锁定

装依赖的两种姿势，推荐用第二种：

```bash
# 方式一：直接装（快，但别人复现不了你的版本）
pip install "fastapi[standard]" "uvicorn[standard]" "sqlalchemy" "pytest"

# 方式二：声明式安装（推荐）
pip install -r requirements.txt
```

```text
# requirements.txt
fastapi[standard]>=0.115,<1.0
uvicorn[standard]>=0.30
sqlalchemy>=2.0,<3.0
pytest>=8.0
```

关于版本号，记住三条：

- `>=1.2,<2.0` 表示「接受 1.x，不跨大版本」——日常开发用这种写法；
- `==1.2.3` 是**锁定**写法，通常由工具生成，用于生产部署；
- `fastapi[standard]` 里的方括号是**附加依赖**，会一并装上文档页、命令行工具等常用组件。

> 💡 **提示**：`uv` 是目前安装依赖更快的选择（Rust 实现），
> 用法与 pip 接近：`uv init` 建项目、`uv add fastapi uvicorn` 加依赖、`uv run uvicorn main:app --reload` 运行。
> 本书正文统一用 `pip` + `requirements.txt`，因为这是面试与团队协作中最通用的口径。

## 1.1.5 认识 FastAPI：它是什么，为什么学它

装完之后，先建立对框架的整体认知——这决定了你后面每一章的代码长什么样。

| 特点 | 说明 |
| --- | --- |
| 类型提示驱动 | 用 Python 类型注解声明输入输出，框架据此做**运行时校验** |
| 自动文档 | 根据代码自动生成 Swagger UI 与 ReDoc，不用手写接口文档 |
| 数据校验 | 由 Pydantic 完成校验与序列化，类型错误在进入业务代码前就被拦下 |
| 异步支持 | 支持 `async def`，适合 IO 密集场景（调用模型 API 正是典型 IO） |
| 依赖注入 | 内置依赖注入系统，便于复用认证与授权、数据库会话等逻辑 |
| 认证与中间件 | 内置 OAuth2 / JWT 支持，中间件覆盖 CORS、GZip 等常见需求 |

与其他框架的取舍：

| 框架 | 特点 | 适用场景 |
| --- | --- | --- |
| **FastAPI** | 高性能、自动文档、类型提示、原生异步 | API 后端、AI 应用服务、微服务 |
| Flask | 轻量、灵活、生态老 | 小工具、原型、已有历史项目 |
| Django | 全功能、自带管理后台与 ORM | 内容型网站、后台管理系统 |

选 FastAPI 的理由不是「它最流行」，而是**它的核心机制与 AI 应用的需求高度重合**：
你要校验模型输出、要做异步调用、要给接口自动生成文档，这些恰好都是它的强项。

它依赖的技术栈分层如下，后面各章会逐层展开：

| 层级 | 技术 | 本书对应章节 |
| --- | --- | --- |
| 框架层 | Starlette（Web 服务核心） | 1.9–1.11 |
| 数据层 | Pydantic（模型、校验、序列化） | 1.10 |
| ORM 层 | SQLAlchemy（数据库交互） | 1.12 |
| 运行层 | Uvicorn（ASGI 服务器） | 1.1、8.1 |
| 部署层 | Docker（容器化） | 8.1 |

## 1.1.6 第一个应用：从零到能访问

先建立项目骨架：

```text
zhizhou/
├── app/
│   └── main.py
├── requirements.txt
└── .gitignore
```

```python
# app/main.py
from fastapi import FastAPI

app = FastAPI(title="知舟 API", version="0.1.0")

@app.get("/")
def read_root():
    return {"service": "zhizhou", "status": "ok"}
```

启动：

```bash
uvicorn app.main:app --reload
```

```text
# 输出
INFO:     Uvicorn running on http://127.0.0.1:8000 (Press CTRL+C to quit)
INFO:     Started reloader process [12345] using StatReload
INFO:     Application startup complete.
```

打开浏览器：

| 地址 | 作用 |
| --- | --- |
| http://127.0.0.1:8000/ | 你写的根路由 |
| http://127.0.0.1:8000/docs | Swagger UI，可直接在页面上试接口 |
| http://127.0.0.1:8000/redoc | ReDoc，另一种风格的接口文档 |
| http://127.0.0.1:8000/openapi.json | 机器可读的接口描述文件 |

常用启动参数：

| 参数 | 说明 | 示例 |
| --- | --- | --- |
| `--reload` | 代码变更后自动重载（**仅开发环境**） | `uvicorn app.main:app --reload` |
| `--host` | 绑定地址，`0.0.0.0` 允许外部访问 | `--host 0.0.0.0` |
| `--port` | 端口，默认 8000 | `--port 8080` |
| `--workers` | 工作进程数（生产用） | `--workers 4` |

> 🔥 **常见坑**：`--workers` 与 `--reload` 不能同时使用。
> 前者是生产多进程，后者是开发热重载，语义互斥，同时给会直接报错。

## 1.1.7 编辑器配置：让工具替你把关

以 VS Code 为例，装好 Python 扩展后做三件事：

1. **选择解释器**：`Ctrl+Shift+P` → `Python: Select Interpreter` → 选 `./.venv`。
   这一步不做，代码里会到处是「找不到模块」的红线。
2. **开启保存时格式化**，并把默认格式化器设为 Ruff 或 Black——两者都遵循 PEP 8。
3. **打开静态检查**（Pylance 默认开启），把警告当成待办清单。

```json
// .vscode/settings.json
{
  "python.defaultInterpreterPath": "${workspaceFolder}/.venv",
  "editor.formatOnSave": true,
  "editor.rulers": [88]
}
```

## 1.1.8 Git：先把仓库管起来

从第一天就上版本控制，理由很实际：**面试官会看你的提交历史**，
而干净的提交历史能证明这个项目是你一步步长出来的。

```bash
git init
git add .
git commit -m "chore: 初始化项目骨架与依赖清单"
```

```text
# .gitignore
.venv/
__pycache__/
*.py[cod]
.env
.pytest_cache/
.ruff_cache/
```

三条约定，从这一章开始执行：

- **不提交**虚拟环境、缓存、`.env` 密钥文件；
- **环境变量用 `.env` 存放**，代码里通过 `os.environ` 或配置模块读取；
  需要给协作者参考时，提交一份 `.env.example`（只含占位符）；
- **提交粒度按「一件事」**：加了一个接口就提交一次，不要攒一周再提交一个「update」。

## 1.1.9 环境自检：三行命令

以后每换一台机器（或每接一个新项目），先跑这三行，能提前干掉 80% 的环境问题：

```bash
python --version                        # 1. 版本对不对：应输出 Python 3.11+
python -c "import sys; print(sys.prefix)"   # 2. 是否在虚拟环境里：路径应含 .venv
python -c "import fastapi, pydantic; print(fastapi.__version__, pydantic.VERSION)"  # 3. 依赖装了没
```

三条都正常，再开始写业务代码。把这三行写进你的项目 `README.md`，
顺手也解决了 1.1.8 提到的「别人能不能跑起来」的问题。

> 💡 **提示**：如果第 2 行输出的路径不含 `.venv`，说明你当前不在虚拟环境里。
> 这是新手最高频的错误，也是最容易误判为「代码有问题」的一种。

## 常见坑

- **忘了激活虚拟环境**。现象：`pip install` 装完，代码仍报 `ModuleNotFoundError`。
  原因：装到了系统 Python。修法：看命令行提示符是否有 `(.venv)`，或执行 `python -c "import sys; print(sys.prefix)"`。
- **把 `.venv` 提交进仓库**。现象：仓库突然多出几千个文件、几百 MB。
  原因：忘了 `.gitignore` 或提交在创建它之前。修法：加 `.gitignore` 后 `git rm -r --cached .venv`。
- **密钥写进代码**。现象：`API_KEY = "sk-..."` 被推上 GitHub。
  原因：图省事。修法：改用 `.env` + 环境变量；**已经泄露的密钥要立刻作废重建**，删提交没用。
- **`--reload` 上了生产**。现象：服务频繁重启、内存持续增长。
  原因：把开发参数当成了通用参数。修法：生产用 `--workers`，热重载只在本地。
- **端口被占用**。现象：报 `address already in use`。
  原因：上一次的服务没退干净，或别的程序占用 8000。修法：`--port 8080` 换端口，或找到并结束占用进程。

## 面试视角

> 🎯 **面试**：环境与工程习惯类问题多出现在一面开头，答不好会显得「只跑过教程」。

1. **「你项目里的依赖是怎么管理的？」**
   考察点：是否理解隔离与复现。答题要点：每个项目一个 `venv` + `requirements.txt`；
   能区分「范围约束」与「锁定版本」，并能说清生产环境为什么要锁定。
2. **「怎么保证代码在别人电脑上跑得起来？」**
   考察点：工程意识。答题要点：README 三步启动、依赖清单、`.env.example`、启动命令固定。
3. **「API 密钥怎么管理？」**
   考察点：安全意识。答题要点：环境变量 / 密钥管理服务，绝不入库；泄露后的处理是**轮换**而非删除。
4. **「为什么选 FastAPI 而不是 Flask / Django？」**（高频）
   考察点：技术选型能力。答题要点：类型驱动校验 + 自动文档 + 原生异步，
   并说明它与 AI 应用场景（校验模型输出、异步调外部 API）的匹配关系。

## 本章小结

- 环境搭建要同时解决三件事：**用哪个 Python、依赖装在哪、怎么复现**。
- 系统自带 Python 只用来创建虚拟环境；每个项目一个 `.venv`，并写进 `.gitignore`。
- 依赖用 `requirements.txt` 声明式安装；`>=x,<y` 约束范围，`==x.y.z` 用于锁定。
- FastAPI 的优势来自类型提示驱动、Pydantic 校验、自动文档与原生异步。
- 技术栈分层：Starlette（框架）、Pydantic（数据）、SQLAlchemy（ORM）、Uvicorn（运行）、Docker（部署）。
- `uvicorn app.main:app --reload` 启动开发服务；`--reload` 与 `--workers` 互斥。
- 密钥一律走环境变量；提交粒度按「一件事」，因为面试官会看提交历史。
