## 1.6.1 三类错误与七种常见异常

写代码遇到的错误分两层：

| 类型 | 例子 | 何时发现 |
| --- | --- | --- |
| 语法错误（SyntaxError） | 少一个冒号、括号不配对 | 程序启动前，解释器直接拒绝执行 |
| 运行期异常 | 除零、键不存在、类型不匹配 | 执行到那一行时才发生 |

语法错误**只能改代码解决**，不能用 `try` 兜住；所以本章讲的异常处理全部针对运行期异常。
七种最常撞到的内置异常，建议直接背下来：

| 异常 | 触发场景 | 典型代码 |
| --- | --- | --- |
| `TypeError` | 类型不对 | `1 + "2"` |
| `ValueError` | 类型对但值不对 | `int("hello")` |
| `NameError` | 用了不存在的名字 | 变量名拼错 |
| `IndexError` | 列表下标越界 | `["a"][3]` |
| `KeyError` | 字典键不存在 | `{"name": "a"}["age"]` |
| `AttributeError` | 属性不存在 | `obj.not_exist` |
| `ZeroDivisionError` | 除数为 0 | `1 / 0` |

记住它们的**实际用途是排查**：报错信息里的异常类型直接指向问题类别。
比如看到 `KeyError: 'age'`，就不必再怀疑类型问题，去检查字典里为什么没有这个键。

## 1.6.2 完整结构：try / except / else / finally

```python
def parse_age(raw: str) -> int:
    try:
        age = int(raw)                     # 可能失败的代码只放这里
    except ValueError as exc:              # 只接自己能处理的
        print(f"输入不是数字：{raw}")
        raise
    except (TypeError, OverflowError) as exc:
        print(f"输入类型不支持：{type(raw).__name__}")
        raise
    else:
        print("解析成功，这里可以放只有成功时才做的事")
        return age
    finally:
        print("无论成功还是失败都会执行：适合放清理逻辑")
```

四段的执行时机，用一张表锁死：

| 段 | 何时执行 |
| --- | --- |
| `try` | 总是（可能抛异常的代码） |
| `except` | 匹配到对应异常时 |
| `else` | `try` 全部顺利执行完、**没有发生异常**时 |
| `finally` | **一定执行**（即使中途 `return` 或抛异常） |

三条容易记错的规则：

1. **异常发生后，`try` 块里同级别后面的代码不再执行**——它直接跳到 `except`。
   所以 `try` 里要尽量只放「可能出错的那一句」，不要把十行逻辑都塞进去，
   否则你无法判断到底是哪一行爆的。
2. **`except` 的顺序是从上往下匹配**，所以具体的异常要写在前面，
   `except Exception` 必须放最后，否则后面的分支永远不会被执行。
3. `finally` 里有 `return` 会覆盖 `try` 里的返回值，**这是 bug 的常见来源**，
   清理逻辑里不要写 `return`。

## 1.6.3 只捕获你处理得了的异常

能写出 `try/except` 只是第一步，**判断「该不该接」才是工程能力**：

- **能处理才接**：接住之后要能做点什么（重试、降级、转成返回值、翻译成用户可读的错误）。
  如果只是 `except Exception: pass`，那是把问题藏起来，出故障时现场全无。
- **不知道怎么办就让它抛**：往上抛给调用方或全局处理器，由它决定怎么响应。
  在 Web 服务里，这最终会变成 FastAPI 的异常处理器（第 1.14 章）。
- **必须记日志**：`except` 里至少记一条，否则这个 bug 永远不会被发现。

Python 两种风格要分清：

```python
# LBYL：先检查再动手（Look Before You Leap）
if "age" in data:
    age = data["age"]

# EAFP：先动手，出错再处理（Easier to Ask Forgiveness than Permission）
try:
    age = data["age"]
except KeyError:
    age = None
```

Python 社区更推荐 **EAFP**，因为检查与操作之间的状态可能变化，
检查得再仔细也不等于操作一定成功（并发场景尤其明显）。但两种风格都有合理场合：
**边界校验用 `if`（可预知），内部逻辑用异常（不可预知）**。

### 自定义异常与异常链

工程代码不该到处抛 `ValueError`，而应该有自己的异常层级：

```python
# app/errors.py
class AppError(Exception):
    """知舟所有业务异常的基类：统一捕获出口。"""


class DocumentNotFound(AppError):
    def __init__(self, doc_id: str) -> None:
        super().__init__(f"文档不存在：{doc_id}")
        self.doc_id = doc_id


class VectorStoreError(AppError):
    """向量库故障，属于可重试或需降级的错误。"""


class ConfigError(AppError):
    """配置读取失败。"""


class DataError(AppError):
    """数据格式不合预期（如 JSONL 坏行）。"""
```

好处有三点：调用方可以按层级捕获（`except DocumentNotFound` 或 `except AppError`）；
异常类型本身就是文档；上层可以据此决定 HTTP 状态码（404 还是 500）。

包装底层异常时用 `raise … from`，保留原始原因：

```python
def load_config(path: str) -> dict:
    try:
        with open(path, encoding="utf-8") as f:
            return json.load(f)
    except FileNotFoundError as exc:
        # 不要写 raise ConfigError(...) 然后丢掉原始异常
        raise ConfigError(f"配置文件缺失：{path}") from exc
```

`from exc` 会让 traceback 打印出「The above exception was the direct cause of …」，
把两个异常串起来。**没有它，原始报错就永远查不到了。**

## 1.6.4 文件读写：模式、方法与编码

```python
with open("data/notes.txt", "r", encoding="utf-8") as f:
    text = f.read()                     # 一次读完，大文件不要用

with open("data/notes.txt", "a", encoding="utf-8") as f:
    f.write("追加一行\n")
```

七种常用模式：

| 模式 | 含义 | 注意 |
| --- | --- | --- |
| `r` | 只读（默认） | 文件必须存在，否则 `FileNotFoundError` |
| `w` | 只写 | **已存在会被清空**，这是最容易丢数据的一种 |
| `a` | 追加 | 不存在则创建 |
| `b` | 二进制 | 与上面组合成 `rb` / `wb`，用于图片、模型文件 |
| `r+` | 读写 | 文件必须存在 |
| `w+` | 读写 | 同样会清空 |
| `a+` | 读写（追加） | 指针在末尾 |

三种读法怎么选：

```python
f.read()            # 整个文件读成一个字符串：只适合小文件
f.readline()        # 读一行：通常配合 while 使用，现代写法直接 for line in f
f.readlines()       # 读成列表：文件大时内存翻倍，谨慎
```

**大文件用 `for` 循环逐行迭代**——文件对象本身就是迭代器，一次只在内存里放一行
（与 1.4.6 的生成器是同一套惰性思路）：

```python
def iter_lines(path: str):
    with open(path, encoding="utf-8") as f:
        for line in f:
            yield line.rstrip("\n")
```

> 🔥 **常见坑**：不写 `encoding` 会使用**操作系统默认编码**——Windows 上通常是 GBK，
> Linux / macOS 上是 UTF-8。同一份代码在两个平台上读出不同结果，
> 甚至直接 `UnicodeDecodeError`。**规则：`open()` 必须显式写 `encoding="utf-8"`**，
> 二进制模式（`rb` / `wb`）本身返回 `bytes`，不需要也不能写 `encoding`。

写文件的换行符也有讲究：文本模式默认会把 `\n` 翻译成当前平台的换行符，
需要精确控制时用 `newline=""`。

## 1.6.5 with：资源一定要被释放

```python
f = open("a.txt", "w", encoding="utf-8")
f.write("hello")
f.close()               # ❌ 中间一旦抛异常，这一行就不会执行，文件句柄泄漏
```

```python
with open("a.txt", "w", encoding="utf-8") as f:
    f.write("hello")     # ✅ 无论正常结束还是抛异常，都会自动 close()
```

`with` 之所以能自动关闭，靠的正是 1.5.11 讲过的两个魔术方法：
进入时调用 `__enter__`，退出时调用 `__exit__`（**异常也会触发**）。
理解这一点后，就能把它用在任何需要「成对操作」的地方——数据库会话、锁、临时目录：

```python
class Timer:                       # 1.5.11 的 Timer 用在这里同样成立
    def __enter__(self): ...
    def __exit__(self, exc_type, exc, tb): ...
```

## 1.6.6 pathlib：别再手拼路径

```python
from pathlib import Path

root = Path("data")
file = root / "documents" / "d1.txt"        # 用 / 拼路径，跨平台
file.parent.mkdir(parents=True, exist_ok=True)

for path in root.rglob("*.txt"):             # 递归找文件
    print(path.name, path.stat().st_size)

print(Path("data/a.txt").suffix)             # .txt
print(Path("data/a.txt").stem)               # a
```

`Path` 比 `os.path.join` 拼字符串更安全：路径分隔符由它处理，
`.parent` / `.suffix` / `.stem` / `.name` 这些属性也比手写切串可靠。
**新代码一律用 `pathlib`。**

## 1.6.7 JSON：与外部世界交换数据

```python
import json
from pathlib import Path

data = {"doc_id": "d1", "tags": ["rag", "tutorial"], "score": 0.91}

Path("data").mkdir(exist_ok=True)
with open("data/doc.json", "w", encoding="utf-8") as f:
    json.dump(data, f, ensure_ascii=False, indent=2)   # 不转义中文，便于人读

with open("data/doc.json", encoding="utf-8") as f:
    loaded = json.load(f)
print(loaded["tags"])       # ['rag', 'tutorial']
```

三个要点：

1. **`ensure_ascii=False`**：否则中文会被写成 `\uXXXX`，文件没法看。
2. `dumps` / `loads` 用于**字符串**，`dump` / `load` 用于**文件对象**（多个 s = string）。
3. JSON 与 Python 类型并不完全一一对应：`true/false/null` 对应 `True/False/None`，
   元组会变成列表，字典的键会变成字符串（见 1.3.7 的对照表）。

> 💡 **提示**：每行一个 JSON 对象的 **JSONL** 格式更适合日志与数据集——
> 追加一行就是一条记录，不用把整个文件读进内存再解析。

## 1.6.8 日志：从 print 到 logging

`print` 的四个问题：没有级别、没有时间、无法关闭、无法输出到文件（除非改代码）。
`logging` 一次解决：

```python
import logging

logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s %(message)s",
)
logger = logging.getLogger(__name__)

logger.debug("调试细节，默认不显示")
logger.info("服务启动完成")
logger.warning("检索结果不足，已降级")
logger.error("调用向量库失败")
```

| 级别 | 数值 | 什么时候用 |
| --- | --- | --- |
| `DEBUG` | 10 | 开发期排查细节，生产环境通常关掉 |
| `INFO` | 20 | 正常但值得记录的事件（启动、任务完成） |
| `WARNING` | 30 | 有异常但服务还能用（降级、重试成功） |
| `ERROR` | 40 | 功能失败，需要人介入 |
| `CRITICAL` | 50 | 服务不可用 |

四个要点：

- **默认级别是 `WARNING`**，所以只配了 `basicConfig(level=INFO)` 才能看到 `info()`。
- `getLogger(__name__)` 用模块名做 logger 名，日志里能直接看出是哪个模块打的。
- `basicConfig` 里的 `filename` 让日志落文件，`format` 用 `%(字段)s` 占位
  （`%(asctime)s` / `%(levelname)s` / `%(name)s` / `%(message)s` 是最常用的一组）。
- `basicConfig` 只在**没有 handler 时生效一次**，重复调用不会改变已有配置——
  所以在项目里通常由入口文件统一初始化一次，其余模块只 `getLogger`。

> 💡 **提示**：第 7 篇会讲结构化日志（每行一个 JSON）。这里先建立一条判断标准：
> **给人看的那一刻用 `print` 没问题，给系统看、需要检索与告警的一律用 `logging`。**

## 1.6.9 模块与包：import 到底做了什么

**模块**就是一个 `.py` 文件；**包**是含 `__init__.py` 的文件夹（Python 3.3 之后
命名空间包可以不写，但正式项目**仍建议保留 `__init__.py`**，让包的结构显式可读）。
模块有四种形式：自己写的 `.py`、C/C++ 扩展、包、内置模块。

首次 `import foo` 会发生三件事：

1. **执行** `foo.py`（注意：模块里的顶层代码会被运行，这也是 `foo.py` 里
   不该写 `print` 调试语句的原因）；
2. 产生 `foo` 的**命名空间**（模块里的变量与函数都在这个字典里）；
3. 当前文件里出现一个名字 `foo`，指向这个命名空间。

已导入的模块会被缓存进 `sys.modules`，因此**第二次 import 不会重新执行**
（这也解释了为什么改了模块代码要重启进程）。

导入顺序按规矩排三类，中间空一行：

```python
import json            # 1. 标准库
from pathlib import Path

import fastapi         # 2. 第三方

from app.errors import AppError    # 3. 自己的代码
```

三条实用约定：

```python
import numpy as np                    # 别名：社区约定俗成的缩写才用
from app.domain.models import Chunk    # 只导入需要的名字

if __name__ == "__main__":             # 只在直接运行时执行，被 import 时不执行
    main()
```

`__name__` 是每个文件内置的名字：**直接运行**时它是 `"__main__"`，
**被导入**时它是模块名。把测试与命令行入口放进 `if __name__ == "__main__":`
里，模块就既能当库用、又能当脚本跑。

`from foo import *` 会导入 `foo.__all__` 里列出的名字（没定义 `__all__` 时导入所有
不以下划线开头的名字）。它省事但有两个代价：**来源不明**（读代码时不知道 `x` 从哪来）、
**容易覆盖**。所以除非在交互式环境里，不要用。

## 1.6.10 sys.path、循环导入与项目目录规范

`import` 找不到模块时，会按 `sys.path` 的顺序查找：

1. 内存中已导入的模块（`sys.modules`）；
2. 当前执行脚本所在目录；
3. 环境变量 `PYTHONPATH` 指定的目录；
4. 标准库与 `site-packages`。

所以「明明文件就在旁边，为什么 import 不到」的答案通常是：**运行入口不对**——
Python 把「入口脚本所在目录」放进 `sys.path`，而不是「当前工作目录」。
工程上的解法不是手动 `sys.path.append`，而是把项目结构固定下来：

```text
zhizhou/
├── app/
│   ├── __init__.py
│   ├── main.py            # 入口：uvicorn app.main:app
│   ├── config.py          # 配置加载
│   ├── errors.py          # 自定义异常
│   ├── domain/            # 领域模型（1.5.13）
│   ├── services/          # 业务逻辑
│   └── api/               # 路由
├── tests/
└── pyproject.toml
```

**循环导入**是两个模块互相 `import` 造成的（`a.py` 导 `b.py`，`b.py` 又导 `a.py`）。
三种解法，按优先级：

1. **调整依赖方向**（首选）：把公共部分下沉到第三个模块，
   例如两边都需要的异常放进 `app/errors.py`，`config` 不要反过来去导 `services`；
2. **把 import 移到函数内部**（延迟到调用时）；
3. **只导入模块、不导入具体名字**（`import app.services as services`），
   配合 `from __future__ import annotations` 让类型注解延迟求值。

第 1 种是根治，第 2、3 种是止痛。看到循环导入，先问「这两个模块的依赖方向是不是反了」。

## 1.6.11 综合示例：把本章拼成一个小工具

```python
# app/config.py
import json
import logging
from pathlib import Path

from app.errors import ConfigError

logger = logging.getLogger(__name__)


def load_config(path: str | Path = "config.json") -> dict:
    """读配置：文件不存在或格式错误时抛 ConfigError。"""
    path = Path(path)
    if not path.exists():
        raise ConfigError(f"配置文件不存在：{path}")
    try:
        with path.open(encoding="utf-8") as f:
            config = json.load(f)
    except json.JSONDecodeError as exc:
        raise ConfigError(f"配置文件不是合法 JSON：{path}") from exc
    logger.info("已加载配置 %s（%d 项）", path.name, len(config))
    return config
```

```python
# app/storage.py
import json
from pathlib import Path

from app.errors import DataError


def append_jsonl(path: str | Path, record: dict) -> None:
    """每行一个 JSON 对象：追加写入，不会覆盖历史数据。"""
    with Path(path).open("a", encoding="utf-8") as f:
        f.write(json.dumps(record, ensure_ascii=False) + "\n")


def read_jsonl(path: str | Path):
    """逐行读出，内存占用与文件大小无关。"""
    with Path(path).open(encoding="utf-8") as f:
        for lineno, line in enumerate(f, start=1):
            line = line.strip()
            if not line:
                continue
            try:
                yield json.loads(line)
            except json.JSONDecodeError as exc:
                # 带上行号，并保留原始异常原因
                raise DataError(f"第 {lineno} 行不是合法 JSON") from exc
```

```python
# 入口：python -m app.demo
import logging
from app.config import load_config
from app.errors import AppError
from app.storage import append_jsonl, read_jsonl


def main() -> None:
    logging.basicConfig(
        level=logging.INFO,
        format="%(asctime)s %(levelname)s %(name)s %(message)s",
    )
    try:
        config = load_config("config.json")
        append_jsonl("data/chunks.jsonl", {"doc_id": "d1", "text": "第一条"})
        append_jsonl("data/chunks.jsonl", {"doc_id": "d2", "text": "第二条"})
        print([r["doc_id"] for r in read_jsonl("data/chunks.jsonl")])
    except AppError as exc:
        # 业务异常统一出口：记日志 + 返回非零退出码
        logging.getLogger(__name__).error("启动失败：%s", exc)
        raise SystemExit(1)


if __name__ == "__main__":
    main()
```

```text
['d1', 'd2']
```

这个示例串起了本章全部要素：`pathlib` 处理路径、`with` 保证关闭、
显式 `encoding` 避免乱码、`json` 交换数据、自定义异常分级、`logging` 记录、
`__name__ == "__main__"` 做入口、JSONL 让读写与文件大小无关。

## 常见坑

- **`except Exception: pass`**。现象：出错了却什么都没发生，排查时无线索。
  原因：图省事。修法：能处理就处理并记日志；不能处理就往上抛。
- **`except` 顺序写反**。现象：具体分支永远不执行。
  原因：`except Exception` 排在前面把异常全接了。修法：从具体到宽泛排列。
- **`finally` 里 `return`**。现象：返回值被莫名替换，异常被吞。
  原因：`finally` 的 `return` 覆盖了前面的返回。修法：清理逻辑里不写 `return`。
- **`w` 模式误清空文件**。现象：运行一次程序，原文件内容没了。
  原因：`w` 会截断已存在的文件。修法：确认要覆盖才用 `w`，否则用 `a`。
- **`open()` 不写 `encoding`**。现象：换台机器就读出乱码或报
  `UnicodeDecodeError`。原因：默认编码随操作系统变化。修法：一律显式 `encoding="utf-8"`。
- **忘关文件**。现象：文件句柄耗尽、Windows 上文件被占用删不掉。
  原因：没有用 `with`。修法：所有文件操作都包在 `with` 里。
- **在模块顶层写重逻辑**。现象：`import` 一下就跑了几秒、甚至连了数据库。
  原因：模块首次导入会执行顶层代码。修法：把逻辑装进函数，
  入口放 `if __name__ == "__main__":`。
- **循环导入**。现象：`ImportError: cannot import name 'x' from partially initialized module`。
  原因：两个模块互相导入，且被导入的名字在对方还没定义时就使用了。
  修法：调整依赖方向（首选）、函数内导入、或只导入模块不导入名字。

## 面试视角

> 🎯 **面试**：这一章对应题库里的「Python 异常/文件/模块」类问题。
> 面试官最常问的不是语法，而是「你在项目里怎么处理错误」——那考的是判断力。

1. **「`try/except/else/finally` 各自什么时候执行？」**
   考察点：完整结构。答题要点：`try` 总是执行；`except` 匹配到异常时；
   `else` 只在没有异常时；`finally` 一定执行（含 `return` 与异常场景）。
2. **「`except Exception` 有什么问题？」**
   考察点：错误处理判断力。答题要点：会把 `KeyboardInterrupt` 之外的几乎所有错误
   一起吞掉，掩盖 bug；应只捕获能处理的异常，宽泛捕获必须记日志或在最外层统一兜底。
3. **「`with` 为什么能自动关闭文件？和 `__del__` 比优势在哪？」**
   考察点：上下文管理器。答题要点：`__enter__` / `__exit__` 成对调用、异常也触发；
   `__del__` 时机不确定，不能当作清理保证（呼应 1.5.11）。
4. **「`import foo` 时发生了什么？为什么改了模块要重启？」**
   考察点：导入机制。答题要点：执行模块顶层代码、产生命名空间、当前文件绑定名字；
   之后模块被缓存进 `sys.modules`，所以不会重复执行。
5. **「`__name__ == "__main__"` 有什么用？」**
   考察点：模块复用。答题要点：直接运行时 `__name__` 是 `"__main__"`，
   被导入时是模块名；据此把测试与命令行入口隔开。
6. **「EAFP 和 LBYL 怎么选？」**
   考察点：风格判断。答题要点：Python 偏好 EAFP（先做再说），
   避免检查与操作之间的状态变化；但边界校验用 `if` 更直观。

## 本章小结

- 语法错误只能改代码；运行期异常才谈得上处理。七种常见异常的类型名就是排查线索。
- `try` / `except` / `else` / `finally`：`try` 里只放可能出错的最小代码块；
  `else` 是无异常分支；`finally` 一定执行且不要写 `return`。
- `except` 从具体到宽泛排列；**只捕获能处理的异常**，其余往上抛；
  自定义异常层级让上层能按需捕获并映射到 HTTP 状态码。
- 包装异常用 `raise … from exc` 保留原始原因。
- 文件模式记牢 `w` 会清空；读大文件用 `for line in f` 或生成器；
  `open()` 必须显式 `encoding="utf-8"`；所有文件操作用 `with`。
- `pathlib.Path` 取代字符串拼路径；`json` 读写记住 `ensure_ascii=False` 与
  `dump/load`（文件）对比 `dumps/loads`（字符串）。
- 日志用 `logging` 而不是 `print`：级别、时间、模块名、可落文件；
  默认级别是 `WARNING`，`basicConfig` 只生效一次。
- `import` 首次会执行模块顶层代码并缓存进 `sys.modules`；
  `__name__ == "__main__"` 用来区分「当脚本跑」与「被导入」。
- 目录结构固定下来比手动改 `sys.path` 更好；循环导入的根治办法是调整依赖方向。

## 练习

- **基础**：写一个 `safe_int(raw: str, default: int = 0) -> int`，
  只捕获 `ValueError`，捕获后记一条 `WARNING` 日志并返回默认值。
  再写一个 `safe_read(path)`，文件不存在时抛自定义的 `ConfigError` 并保留原始异常。
- **进阶**：实现 `iter_jsonl(path)`：逐行读取 JSONL，跳过空行；
  遇到坏行时记 `ERROR` 日志并**继续**处理，最后返回成功/失败条数。
  要求用 `pathlib` 与 `with`，并在函数开始处校验文件是否存在。
- **挑战**：给知舟搭一个 `app/` 骨架（`errors.py` / `config.py` / `storage.py` /
  `main.py`），要求（1）除 `main.py` 外任何模块都不在顶层做 I/O；
  （2）用 `logging` 统一输出格式；（3）故意制造一次循环导入，再用
