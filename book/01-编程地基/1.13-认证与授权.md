## 1.13.1 三个概念的边界：认证、授权、会话

这三个词在日常对话里常被混用，但在代码里对应三件不同的事：

| 概念 | 英文 | 回答的问题 | 本章对应实现 |
| --- | --- | --- | --- |
| 认证 | Authentication | **你是谁**？ | 口令校验 + 令牌签发与校验 |
| 授权 | Authorization | **你能做什么**？ | scope、角色、资源归属检查 |
| 会话 | Session | 这段关系**怎么维持**？ | 令牌（客户端持有）或会话 Cookie（服务端持有） |

混用的代价很实际：把「登录」当成「权限」，于是每个接口都只检查「有没有令牌」，
不检查「这个人能不能碰这条数据」——这正是绝大多数越权漏洞的成因（见 1.13.9）。

### 会话放哪儿：两种架构

认证的难点不在「验证密码」，而在**验证完之后，怎么记住这个人已经登录了**。
HTTP 是无状态的，每次请求都是陌生人。两条路：

| 维度 | 服务端会话（Session） | 客户端令牌（Token） |
| --- | --- | --- |
| 状态位置 | 服务端内存 / Redis / 数据库 | 客户端（Cookie 或请求头） |
| 服务端负担 | 每个在线用户占一份存储 | 不占存储（令牌自带信息） |
| 撤销 | **立即生效**（删掉那条会话记录） | 困难：签发到过期之间一直有效 |
| 水平扩展 | 需要共享存储（Redis），否则多副本各自为政 | 天然可扩展（各副本验签即可） |
| 跨域与第三方调用 | 不便（浏览器自动带 Cookie，服务间调用没有 Cookie） | 方便（请求头里带令牌，移动端 / 微服务友好） |
| 泄露面 | 会话 ID 泄露 = 被冒用，但服务端能踢掉 | 令牌泄露 = 在有效期内被冒用，较难拦 |

> 💡 **提示**：这不是二选一。生产系统的常见形态是**两者并存**——浏览器端把令牌放在
> `HttpOnly` Cookie 里（兼顾浏览器体验与 JS 不可读），服务间调用把令牌放在
> `Authorization` 头里。本章两种都会实现。

还有一个常被忽略的中间态：**令牌 + 服务端可撤销名单**。JWT 本身无状态，
但你可以额外维护一份「已撤销的 `jti`」黑名单（放 Redis），
在「无状态的性能」与「可撤销的安全」之间取一个平衡点。见 1.13.10。

## 1.13.2 口令存储：只存哈希，别存密码

### 为什么不能加密

口令一旦落库，就必须假设**数据库迟早会泄露**。于是有两种处理：

| 做法 | 可逆？ | 泄露后果 |
| --- | --- | --- |
| 加密（encryption，如 AES） | 可逆 | 拿到密钥即可还原全部明文口令 |
| 哈希（hashing） | **不可逆** | 只能逐个猜，猜中才拿到那一个 |

认证场景要的是**验证**，不是**还原**，所以正确答案是哈希：
登录时把用户输入的口令用同样的方式哈希一遍，与库里存的值比对。
服务端自己也不知道用户的口令是什么。

哈希用于口令时，还额外需要三个性质：

1. **单向**：由哈希推不回原口令（所以不能用 Base64、不能可逆加密）。
2. **加盐**：同一口令两次哈希的结果必须不同，否则一张彩虹表能同时命中一片用户。
3. **可调慢**：故意让单次计算变贵，把离线爆破的成本抬上去（这正是 SHA-256 不够用的原因——
   它快到 GPU 每秒能试几十亿次）。

bcrypt 三者都满足。而且盐不用自己生成，`gensalt()` 会随机产生并编码进结果里：

```python
import bcrypt

def hash_password(password: str) -> str:
    """把口令变成哈希串（注册时调用）。"""
    return bcrypt.hashpw(password.encode("utf-8"), bcrypt.gensalt(rounds=12)).decode()

def verify_password(password: str, hashed: str) -> bool:
    """校验口令（登录时调用）。"""
    return bcrypt.checkpw(password.encode("utf-8"), hashed.encode("utf-8"))
```

哈希串本身带着全部参数：

```text
$2b$12$EixZaYVK1fsbw1ZfbX3OXePaWxn96p36WQoeG6Lruj3vjPGga31lW
 │   │  └── 22 字符盐 + 31 字符摘要（盐就在里面，不用另存一列）
 │   └───── 工作因子：2^12 轮
 └───────── 算法版本（2b 是 bcrypt）
```

实跑验证三件事：

```python
h1 = hash_password("123456")
h2 = hash_password("123456")
print(h1 == h2)                       # False —— 盐不同，结果不同
print(verify_password("123456", h1))  # True
print(verify_password("000000", h1))  # False
```

### 工作因子怎么定

`rounds` 每加 1，耗时翻倍。本机实测：

| `rounds` | 单次耗时 | 说明 |
| --- | --- | --- |
| 4 | 约 1 ms | 只用在小规模测试（图快），生产不要用 |
| 12 | 约 210 ms | OWASP 的建议区间（≥10）；本章采用值 |

> ⚠️ **注意**：210 ms 是**故意**的。它的另一面是：登录接口很容易被用来做 CPU 消耗攻击——
> 攻击者拿一堆用户名狂打登录接口，每个请求都让你烧 200 ms CPU。
> 所以登录接口**必须限流**（见 1.11 的限流中间件），这不是可选项。

### 72 字节：中文口令最容易被忽视的坑

bcrypt 的输入上限是 72 字节。老版本是**静默截断**（超出的部分被丢掉），
`bcrypt 5.0.0` 起改成**直接抛异常**：

```python
bcrypt.hashpw(("我" * 40).encode(), bcrypt.gensalt())   # 120 字节
# ValueError: password cannot be longer than 72 bytes, truncate manually if necessary
```

这不是理论问题：**一个汉字占 3 字节，24 个汉字就顶到 72 字节**。
用户设一句 30 字的密码短语，注册接口就会 500。

两种解法，各有适用场景：

| 方案 | 做法 | 适用 |
| --- | --- | --- |
| 限长 | 注册时校验口令长度（如 8–64 **字符**，同时校验字节数 ≤ 72） | 绝大多数业务系统，用户可接受 |
| 预哈希 | 先 `sha256` 再 `base64`，把任意长度压成固定 44 字节再交给 bcrypt | 必须支持长口令/密码短语的系统 |

预哈希的实现在验证时也必须走同一步，否则永远校验不过：

```python
import base64, hashlib

def _prehash(password: str) -> bytes:
    """把任意长度的口令压成固定 44 字节（base64 之后不会触到 72 字节上限）。"""
    return base64.b64encode(hashlib.sha256(password.encode("utf-8")).digest())

def hash_password_v2(password: str) -> str:
    return bcrypt.hashpw(_prehash(password), bcrypt.gensalt(rounds=12)).decode()

def verify_password_v2(password: str, hashed: str) -> bool:
    return bcrypt.checkpw(_prehash(password), hashed.encode("utf-8"))
```

> ⚠️ **注意**：预哈希**不能**用裸的 `sha256` 摘要直接当 bcrypt 输入——
> 摘要里可能含 `\x00`，而 bcrypt 会把 `\x00` 当字符串结束。加上 `base64` 编码既消除了空字节，
> 又让长度固定。另外预哈希意味着**换算法就换哈希**，老用户必须重设口令，
> 所以要么一开始就选它，要么留好迁移路径。

### 素材用的库，与本章为什么换掉

素材用的是 `python-jose` + `passlib[bcrypt]`，这是很多教程的写法。本章换成
**PyJWT + bcrypt**，两个原因都有官方出处：

1. FastAPI 官方教程现在用 **PyJWT + pwdlib**，并且明确推荐 Argon2 算法
   （见「延伸阅读」的 `oauth2-jwt`）。
2. `passlib` 与新版 bcrypt 有已知冲突：`bcrypt 5.0.0` 把「超过 72 字节」从静默截断
   改成了抛异常，而 `passlib 1.7.4`（2020 年发布）仍按旧行为调用，
   于是升级依赖之后登录会报一个**指向错误的** `ValueError`
   （见「延伸阅读」的 bcrypt CHANGELOG 与 passlib 相关条目）。

`pwdlib + Argon2` 是更好的选择，但本机未安装，本章代码未在它上面实跑，
所以主线仍走 bcrypt——**能在你机器上跑通的代码比「更先进但不验证」的代码有用**。

## 1.13.3 JWT 的三段结构

**JWT（JSON Web Token）** 是一个开放标准（RFC 7519），它把一组声明（claims）
编码成一段字符串并**签名**，用来在各方之间可信地传递身份信息。

一个令牌长这样，用两个点分成三段：

```text
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9 . eyJzdWIiOiJ1MTAwMSIsImV4cCI6MTc4OTIwNDA5Mn0 . dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
└──────────── Header ────────────┘   └──────────── Payload ────────────┘   └──────────── Signature ────────────┘
```

### Header：算法与类型

```json
{"alg": "HS256", "typ": "JWT"}
```

`alg` 告诉验证方用哪种算法验签，`typ` 固定是 `JWT`。

### Payload：声明

Payload 是**明文可读**的，这一点必须先记住。把上面那段 Payload 直接做 Base64URL 解码：

```python
import base64
p = "eyJzdWIiOiJ1MTAwMSIsImV4cCI6MTc4OTIwNDA5Mn0"
print(base64.urlsafe_b64decode(p + "==").decode())
# {"sub":"u1001","exp":1789204092}
```

> ⚠️ **注意**：签名保证的是「**没被改过**」，不是「**看不见**」。
> 所以口令、身份证号、手机号、内部定价这类信息**绝不能放进 Payload**。
> jwt.io 这类在线解码器人人都能用。

声明分三类，先掌握前两类：

| 类别 | 含义 | 例子 |
| --- | --- | --- |
| Registered Claims | 规范定义的标准字段，全球通用 | `sub`、`exp`、`iat` |
| Private Claims | 你和前端约定好的自定义字段 | `role`、`type`、`scope` |
| Public Claims | 需向 IANA 注册的公共声明 | 很少用到 |

七个标准声明，前两个基本是必填：

| 声明 | 全称 | 通俗理解 | 常用度 |
| --- | --- | --- | --- |
| `sub` | Subject | 这张令牌属于谁 | ⭐ 必须 |
| `exp` | Expiration Time | 什么时候失效 | ⭐ 必须 |
| `iat` | Issued At | 什么时候签发的 | 常用 |
| `iss` | Issuer | 谁签发的 | 常用 |
| `aud` | Audience | 签给谁用的 | 较少 |
| `nbf` | Not Before | 什么时候开始有效 | 较少 |
| `jti` | JWT ID | 令牌的唯一编号 | 较少但**撤销时必用** |

### Signature：防伪水印

签名的生成就三步：把 Header 与 Payload 的 Base64URL 串用 `.` 拼起来，
用密钥对这个串做 HMAC，再 Base64URL 编码：

```text
签名 = Base64URL( HMAC-SHA256( Base64URL(header) + "." + Base64URL(payload), SECRET ) )
```

实跑一下「改了就露馅」：拿一个有效令牌，只改 Payload 里的一个字符（把 `role` 从
`user` 改成 `admin`），再拿去验证：

```text
InvalidSignatureError: Signature verification failed
```

服务端不需要查库就知道这个令牌被动过手脚——这正是无状态认证成立的前提。

### HS256 还是 RS256

| 对比项 | HS256（对称） | RS256（非对称） |
| --- | --- | --- |
| 密钥 | 签名与验证用**同一把**密钥 | 签名用私钥，验证用公钥 |
| 密钥分发 | 每个参与方都要拿到那把密钥 | 只分发公钥，私钥不外传 |
| 性能 | 快 | 慢（RSA 运算更重） |
| 适用 | 单体应用、内部服务 | 微服务、开放平台（第三方验签） |

选择判据很简单：**验证方是不是「自己人」**。都是自己人 → HS256，简单高效；
有第三方或多服务需要独立验签 → RS256，避免把签名密钥撒得到处都是。

### 算法篡改攻击

JWT 历史上最著名的一类漏洞是**攻击者把 `alg` 改成 `none`**（改成「不签名」），
期待服务端偷懒接受它。实跑两种写法：

```python
jwt.decode(forged_token, SECRET, algorithms=["HS256"])
# InvalidAlgorithmError: The specified alg value is not allowed

jwt.decode(forged_token, SECRET)          # 忘记传 algorithms
# DecodeError: It is required that you pass in a value for the "algorithms" argument when calling decode()
```

第二种反而更安全——PyJWT 强制要求显式传白名单。
所以规矩是：**`algorithms` 永远写成只含你实际使用的那一个算法的列表**，
不要写 `["HS256", "RS256", "none"]`，也不要用从令牌头上读来的 `alg`。

## 1.13.4 签发令牌

### 装依赖

```bash
pip install pyjwt bcrypt python-multipart
```

第三个包容易漏：**FastAPI 解析表单数据必须装 `python-multipart`**，
而 OAuth2 的密码模式登录接口用的是表单（不是 JSON）。漏装会在定义路由时报错，
错误信息里会明确提示缺这个包。

### 配置与密钥

```python
from pydantic_settings import BaseSettings, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", env_prefix="ZHIZHOU_")

    SECRET_KEY: str                      # 无默认值：漏配就启动失败，好过用默认密钥上线
    ALGORITHM: str = "HS256"
    ACCESS_TOKEN_EXPIRE_MINUTES: int = 30
    REFRESH_TOKEN_EXPIRE_DAYS: int = 7


settings = Settings()
```

密钥怎么来：

```bash
python -c "import secrets; print(secrets.token_urlsafe(32))"   # 43 个字符
openssl rand -hex 32                                           # 官方教程用的写法
```

**密钥长度不是装饰**。HMAC-SHA256 的密钥建议长度是 256 位（32 字节），
PyJWT 2.11 起会对过短的密钥发 `InsecureKeyLengthWarning`：

```text
InsecureKeyLengthWarning: The HMAC key is 5 bytes long, which is below the minimum
recommended length of 32 bytes for SHA256. See RFC 7518 Section 3.2.
```

能不能把它升级成硬错误？能，但**版本有讲究**。实跑本机的 PyJWT 2.12.1：

| 写法 | 结果 |
| --- | --- |
| `jwt.decode(..., options={"enforce_minimum_key_length": True})` | 只告警，**不抛异常** —— 调用级选项被忽略 |
| `jwt.PyJWT(options={"enforce_minimum_key_length": True}).decode(...)` | 抛 `InvalidKeyError` —— 实例级生效 |

调用级失效是 2.12.1 的一个已知缺陷，PyJWT 2.13 的更新日志里专门写了这一条
（「Forward per-call options … so the option actually takes effect when set at the call site」）。
也就是说：**你以为开了一个安全开关，它在你的版本上没有任何作用**。
这类「开关看着生效其实没有」的坑，只能靠写测试或读更新日志发现。

### 签发函数

```python
import datetime as dt
import uuid

import jwt

def create_token(subject: str, token_type: str, expires_delta: dt.timedelta) -> tuple[str, str]:
    """签发一个令牌，返回 (令牌串, jti)。"""
    now = dt.datetime.now(dt.timezone.utc)
    jti = uuid.uuid4().hex
    payload = {
        "sub": subject,          # 必须是非空字符串
        "type": token_type,      # access / refresh：两种令牌不能混用
        "jti": jti,              # 唯一编号，撤销名单靠它
        "iat": now,
        "exp": now + expires_delta,
    }
    token = jwt.encode(payload, settings.SECRET_KEY, algorithm=settings.ALGORITHM)
    return token, jti
```

五个细节值得逐个说清：

1. **`sub` 必须是非空字符串。** PyJWT 2.10 起会校验 `sub` 与 `jti` 的类型，
   传 `int` 直接报错：`InvalidSubjectError: Subject must be a string`。
   用户 ID 在数据库里是整数，这里要写 `str(user.id)`。
   （这条是实跑发现的，素材里没有。）
2. **时间统一用 `datetime.now(timezone.utc)`**，不要用已废弃的 `datetime.utcnow()`。
   混用 naive 与 aware 时间会在比较时出错。
3. **`type` 区分访问令牌与刷新令牌。** 没有它，一个 7 天有效期的刷新令牌
   就能当访问令牌用——把短有效期设计整个抹掉。
4. **`jti` 是撤销的前提。** 不签发 `jti`，将来想踢掉某个令牌只能等它自然过期。
5. **权限别只放令牌里。** 把 `role` 写进令牌很省事，但用户被降权后，
   旧令牌在有效期内仍然是管理员。要么把有效期压得很短（本章做法：30 分钟），
   要么每次请求回查数据库（见 1.13.9）。

## 1.13.5 校验令牌

`jwt.decode` 一次做三件事：**验签**（内容没被改）、**验时间**（未过期、已生效）、
**验声明**（`aud` / `iss` 对不对）。

### 默认不要求 `exp` 存在

这是最容易被忽略的一条。实跑：

```python
token = jwt.encode({"sub": "u1001"}, SECRET, algorithm="HS256")   # 故意不给 exp
jwt.decode(token, SECRET, algorithms=["HS256"])                    # 通过！
```

也就是说：**签发时忘了设 `exp`，令牌就永不过期，而验证方不会有任何抱怨**。
把检查显式打开：

```python
jwt.decode(token, SECRET, algorithms=["HS256"], options={"require": ["exp"]})
# MissingRequiredClaimError: Token is missing the "exp" claim
```

> 💡 **提示**：`require` 里可以同时列上 `["exp", "iat", "sub"]`，
> 把「令牌必须带哪些声明」变成一条可执行的约定，而不是靠记性。

### 异常层次：先捕子类

```text
PyJWTError（所有错误的基类）
├── InvalidSignatureError      签名不对（被改过、或用错了密钥）
├── ExpiredSignatureError      已过期
├── ImmatureSignatureError     nbf 未到（令牌还没生效）
├── InvalidAudienceError       aud 不匹配
├── InvalidIssuerError         iss 不匹配
├── MissingRequiredClaimError  require 的声明缺失
├── InvalidSubjectError / InvalidJTIError  sub / jti 类型不对
└── DecodeError                格式错、exp 不是整数等
```

`ExpiredSignatureError` 是 `PyJWTError` 的**子类**（实跑确认 `issubclass` 为真）。
所以这样写会把「已过期」埋进「无效」里，前端永远无法提示用户「登录已过期，请重新登录」：

```python
try:
    payload = jwt.decode(token, SECRET, algorithms=[ALG])
except jwt.PyJWTError:            # 过期也走这里
    return None                   # 丢失了具体原因
```

正确顺序是**先具体后笼统**：

```python
def verify_token(token: str) -> tuple[dict | None, str]:
    """返回 (载荷, 失败原因)。原因用字符串回传，便于路由决定响应文案。"""
    try:
        payload = jwt.decode(
            token,
            settings.SECRET_KEY,
            algorithms=[settings.ALGORITHM],
            options={"require": ["exp", "iat", "sub"]},
            leeway=10,                 # 容忍 10 秒时钟偏差
        )
    except jwt.ExpiredSignatureError:
        return None, "expired"
    except jwt.PyJWTError:
        return None, "invalid"
    return payload, ""
```

`leeway` 是为客户端时钟漂移准备的：手机时间比服务器快 5 秒，
刚签发的令牌会被判成「还没生效」或刚过期，加一点容差能让这类报错消失。

### 各选项对应的报错

| 场景 | 实跑结果 |
| --- | --- |
| 过期 10 秒 | `ExpiredSignatureError: Signature has expired` |
| 同上但 `leeway=30` | 通过 |
| `nbf` 在未来 | `ImmatureSignatureError: The token is not yet valid (nbf)` |
| `aud` 不符 | `InvalidAudienceError: Audience doesn't match` |
| `iss` 不符 | `InvalidIssuerError: Invalid issuer` |
| 用错密钥 | `InvalidSignatureError: Signature verification failed` |
| `exp` 是字符串 | `DecodeError: Expiration Time claim (exp) must be an integer.` |

`aud` 与 `iss` 在单体应用里常被省略，但一旦出现**多服务共用一个密钥**的架构，
它们就是唯一能区分「这个令牌是签给谁的」的字段——不校验的话，
给 A 服务签的令牌可以直接拿去调 B 服务。

## 1.13.6 OAuth2：四个角色与四种授权方式

**OAuth2**（RFC 6749）是一套**授权框架**，一句话概括：
「在不告诉别人密码的前提下，允许别人访问你的东西」。

最直白的类比是酒店：你把身份证给前台登记，前台还给你，
登记这件事让前台在你住店期间能确认你是谁，但它不能拿你的身份证去办别的事。
**授权访问，而不是共享密码**——这就是 OAuth2 的全部动机。

### OAuth2 与 JWT 不是二选一

两者解决的问题不同，很多人把它们当成竞争关系：

| 对比项 | OAuth2 | JWT |
| --- | --- | --- |
| 本质 | 授权**流程**：怎么拿到访问权限 | 令牌**格式**：凭证长什么样 |
| 类比 | 酒店的入住流程 | 房卡本身 |
| 规范 | RFC 6749 | RFC 7519 |
| 关系 | 定义如何获取令牌 | OAuth2 中最常用的令牌格式 |

一句话：**OAuth2 负责发卡，JWT 是那张卡的样子**。OAuth2 也可以用不透明字符串当令牌。

### 四个角色

| 角色 | 说明 | 类比 | 在本章代码里 |
| --- | --- | --- | --- |
| 资源所有者 | 数据的主人 | 寄件人 | 登录的普通用户 |
| 客户端 | 想访问数据的应用 | 收件人 | 你的前端 / 第三方 App |
| 授权服务器 | 验证身份、签发令牌 | 快递公司 | 知舟的 `/auth/token` |
| 资源服务器 | 存储并提供数据 | 仓库 | 知舟的业务接口 |

授权服务器与资源服务器**可以是同一个服务**。知舟就是如此——
所以直觉上「OAuth2 好像没怎么用上」是对的：单人项目里四角合一，
但概念上的分工仍划清了「谁负责发身份、谁负责按身份放行」。

### 四种授权方式

| 授权方式 | 适用场景 | 通俗理解 |
| --- | --- | --- |
| 授权码（Authorization Code） | 第三方网站登录（微信 / Google 登录），移动端配 PKCE | 最安全：扫码授权 |
| 密码（Password / Resource Owner） | **你自己的**第一方 App | 用户直接给账号密码 |
| 客户端凭证（Client Credentials） | 服务之间调用，没有用户参与 | 员工卡刷门 |
| 隐式（Implicit） | 已淘汰，用授权码 + PKCE 替代 | 令牌暴露在 URL 里，不要用 |

选择表（照着填就行）：

| 你的情况 | 推荐方式 |
| --- | --- |
| 第三方网站想用微信登录 | 授权码 |
| 自己开发的前后端应用，用户直接登录 | 密码模式（简化）或授权码 + PKCE（更推荐） |
| 后端服务 A 调用后端服务 B | 客户端凭证 |
| 微信小程序 / 手机 App | 授权码 + PKCE |

授权码流程为什么更安全，只差一个细节：**它把「令牌传输」从浏览器搬到了后端**。
浏览器地址栏里只出现一次性的 `code`，后端拿 `code` 加自己的 `client_secret`
去换令牌——令牌从不经过浏览器历史、不经过前端日志、不经过用户设备。

> ⚠️ **注意（这一段很重要）**：**FastAPI 只帮你实现了「密码模式 + Bearer 令牌」这一小块**。
> `OAuth2PasswordBearer` 与 `OAuth2PasswordRequestForm` 合起来做的事是：
> 收一个表单形式的用户名密码 → 给你一个令牌 → 以后从 `Authorization: Bearer xxx` 里取值。
> 授权码流程、客户端凭证、PKCE、scope 的授权确认页**都要自己实现**，
> 或者交给 Keycloak / Auth0 / 微信开放平台这类授权服务器。
> 很多教程把「FastAPI 的安全工具」说成「OAuth2 支持」，会让你以为整套协议都齐了。

## 1.13.7 落地登录接口：Bearer 与表单

### `OAuth2PasswordBearer` 做了什么

```python
from fastapi.security import OAuth2PasswordBearer

oauth2_scheme = OAuth2PasswordBearer(tokenUrl="/auth/token")
```

它就两件事：

1. 从请求头里取 `Authorization: Bearer <token>`，把 `<token>` 交给依赖；
2. 在 OpenAPI 里声明一个 `oauth2` 安全方案，让 `/docs` 出现「Authorize」按钮。

`tokenUrl` 是**给文档用的**：Swagger UI 上的 Authorize 按钮会去这个地址提交表单换令牌。
所以它必须指向你真实的登录接口。实跑查看生成的 OpenAPI：

```json
{"OAuth2PasswordBearer": {"type": "oauth2", "flows": {"password": {"scopes": {}, "tokenUrl": "auth/token"}}}}
```

`tokenUrl` 会**原样输出**（这里我写的是相对路径 `auth/token`，它就照抄）。
相对路径在 `/docs` 页面里能正常工作，但更稳妥的写法是与路由前缀一致的绝对路径，
例如 `/auth/token`。

### 表单登录接口

```python
from typing import Annotated

from fastapi import APIRouter, Depends, HTTPException, status
from fastapi.security import OAuth2PasswordRequestForm
from pydantic import BaseModel

router = APIRouter(prefix="/auth", tags=["认证"])


class TokenOut(BaseModel):
    access_token: str
    refresh_token: str
    token_type: str = "bearer"
    expires_in: int = ACCESS_TOKEN_EXPIRE_MINUTES * 60


@router.post("/token", response_model=TokenOut)
async def login(form: Annotated[OAuth2PasswordRequestForm, Depends()]):
    user = authenticate_user(form.username, form.password)
    if user is None:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="用户名或口令错误",
            headers={"WWW-Authenticate": "Bearer"},
        )
    access_token, _ = create_token(str(user.id), "access", dt.timedelta(minutes=30))
    refresh_token, _ = create_token(str(user.id), "refresh", dt.timedelta(days=7))
    return TokenOut(access_token=access_token, refresh_token=refresh_token)
```

`OAuth2PasswordRequestForm` 声明的字段（实跑取自签名）：

```text
grant_type, username, password, scope, client_id, client_secret
```

两个实跑到的行为：

- **漏 `password` → 422**（`username` 与 `password` 是必填）；
- **多传未知字段 → 照常 200**（默认忽略额外字段，与 Pydantic 模型不同）。

> 💡 **提示**：为什么登录要用**表单**而不是 JSON？技术上 JSON 完全可以（自己定义
> 请求模型即可），但 OAuth2 规范规定用 `application/x-www-form-urlencoded`，
> 而 `/docs` 的 Authorize 按钮只按规范的表单格式提交。写表单能白拿一个可用的调试入口。

### 别泄露「这个用户名存不存在」

下面是本章认为值得单独讲的一处细节。错误的写法：

```python
def authenticate_user(username: str, password: str):
    user = get_user(username)
    if user is None:
        return None                      # 立刻返回：快
    if not verify_password(password, user.hashed_password):
        return None                      # 走完 bcrypt：慢 200 ms
    return user
```

登录接口的**响应耗时**会泄露用户是否存在：不存在的用户名几毫秒返回，
存在的用户名要烧 200 ms。攻击者据此可以批量枚举出哪些账号真实存在。
解法是对不存在的用户也**跑一次哈希校验**：

```python
DUMMY_HASH = hash_password("zhizhou-dummy-password")   # 模块导入时算一次

def authenticate_user(username: str, password: str):
    user = get_user(username)
    if user is None:
        verify_password(password, DUMMY_HASH)           # 白烧一次 CPU，让耗时对齐
        return None
    if not verify_password(password, user.hashed_password):
        return None
    return user
```

这是 FastAPI 官方教程里的做法，它也把「不许通过响应时间区分用户是否存在」
这条规则变成了几行代码。

## 1.13.8 认证依赖：`get_current_user`

认证逻辑必须只写一处，然后被所有需要登录的接口复用。这就是依赖注入的用武之地：

```python
async def get_current_user(token: Annotated[str, Depends(oauth2_scheme)]) -> User:
    payload, reason = verify_token(token)
    if payload is None:
        raise HTTPException(
            status_code=status.HTTP_401_UNAUTHORIZED,
            detail="登录状态已失效，请重新登录" if reason == "expired" else "凭据无效",
            headers={"WWW-Authenticate": "Bearer"},
        )
    if payload.get("type") != "access":
        raise HTTPException(401, "令牌类型不正确", headers={"WWW-Authenticate": "Bearer"})
    user = await get_user_by_id(int(payload["sub"]))
    if user is None or user.disabled:
        raise HTTPException(401, "账号不存在或已停用", headers={"WWW-Authenticate": "Bearer"})
    return user
```

### 401 必须带 `WWW-Authenticate`

这不是风格问题。RFC 6750 规定：Bearer 令牌认证失败时，资源服务器**应当**返回
`WWW-Authenticate` 头，告诉客户端「这里用 Bearer 认证」。
少了它，前端无法区分「需要登录」与「接口出错」，很多客户端库也不会自动触发登录流程。

FastAPI 在**缺少凭据**时会自动补上这个头。实跑默认行为：

```text
GET /me（不带 Authorization）
→ 401  {"detail": "Not authenticated"}
→ WWW-Authenticate: Bearer
```

而**凭据无效**（令牌过期、签名错）时，它不知道原因，头要你自己加——就是上面代码里
每一处 `headers={"WWW-Authenticate": "Bearer"}` 的来历。忘了加，客户端只能看到一个
裸的 401。

> ⚠️ **注意**：RFC 6750 还定义了 `error` 参数（`invalid_token`、`insufficient_scope`），
> 用来让客户端精确区分失败原因；**FastAPI 的默认响应里没有它**
> （规范对「完全未带凭据」的场景本就建议只回 401、不带 `error`，
> 所以这个默认行为在缺凭据时是合规的，令牌无效时则不够用）。
> 需要的话自己拼进去：
> `headers={"WWW-Authenticate": 'Bearer error="invalid_token", error_description="令牌已过期"'}`。
> 客户端要按不同的 `error` 值分支时，这一条就是必需的。

### 游客模式：`auto_error=False`

有些接口「登录了看到更多，没登录也能看」。这时不要让 FastAPI 直接抛 401：

```python
oauth2_scheme_optional = OAuth2PasswordBearer(tokenUrl="/auth/token", auto_error=False)

@router.get("/articles")
async def list_articles(token: Annotated[str | None, Depends(oauth2_scheme_optional)]):
    if token is None:
        return {"items": [...], "viewer": None}       # 游客视角
    ...
```

实跑的四种输入：

| 请求 | 结果 |
| --- | --- |
| 不带 `Authorization` | `token=None` |
| `Bearer <有效令牌>` | 令牌串 |
| `Bearer <过期令牌>` | 令牌串（**取到了才轮到你判断**） |
| `Authorization: Basic xxx` | `token=None`（scheme 不对按没有处理） |

最后一行值得注意：**`auto_error=False` 之后，判断过期是你的责任**。
它不再帮你拦任何东西。

### `HTTPBearer` 与 `OAuth2PasswordBearer` 的差别

`HTTPBearer` 更通用（不绑定 OAuth2 的密码模式），两者实跑行为一致：

| 工具 | 缺凭据 | 错误 scheme | 作用 |
| --- | --- | --- | --- |
| `OAuth2PasswordBearer` | 401 + `WWW-Authenticate: Bearer` | 同上 | 带 `tokenUrl`，文档里能换令牌 |
| `HTTPBearer` | 401 + `WWW-Authenticate: Bearer` | 同上 | 通用，可在 `credentials` 里拿到原始串 |

> 💡 **提示**：老版本 FastAPI 里 `HTTPBearer` 缺凭据返回的是 **403**，现在两个都是 401。
> 这类「版本间行为变化」正是本章所有断言都要实跑的原因——
> 抄一篇两年前的教程，你可能就写错状态码了。

## 1.13.9 授权：作用域、角色与资源归属

### scope 声明 ≠ scope 检查

FastAPI 的 scope 有**两层**，必须分清：

1. **声明层**：`OAuth2PasswordBearer(scopes={...})` 与
   `Security(get_current_user, scopes=["items:write"])` ——
   这层只影响 OpenAPI 文档（Authorize 按钮里能勾选哪些权限）。
2. **检查层**：依赖函数里真的去比对令牌的 scope ——**这层必须自己写**。

官方文档把这句话写得很直白：你**仍然**要在代码里执行那些 scope 检查。
只声明不检查，接口看起来受保护，实际谁都能调。

```python
from fastapi import Security
from fastapi.security import SecurityScopes


def require_scope(required: str):
    """依赖工厂：生成一个「要求指定 scope」的依赖。"""
    async def dep(
        security_scopes: SecurityScopes,
        token: Annotated[str, Depends(oauth2_scheme)],
    ) -> dict:
        if security_scopes.scopes:
            authenticate_value = f'Bearer scope="{security_scopes.scope_str}"'
        else:
            authenticate_value = "Bearer"
        payload, _ = verify_token(token)
        if payload is None:
            raise HTTPException(401, "凭据无效", headers={"WWW-Authenticate": authenticate_value})
        granted = set(payload.get("scope", "").split())
        missing = set(security_scopes.scopes) - granted
        if missing:
            raise HTTPException(
                403,
                f"缺少权限：{'、'.join(sorted(missing))}",
                headers={"WWW-Authenticate": authenticate_value},
            )
        return payload
    return dep
```

用法上，`Security` 与 `Depends` 的区别只有一个：`Security` 能顺带声明所需 scope，
`Depends` 不能。

```python
@router.get("/articles")
async def list_articles(user: Annotated[dict, Security(require_scope("articles:read"), scopes=["articles:read"])]):
    return {"items": [], "viewer": user["sub"]}
```

实跑四种情形：

| 情形 | 结果 |
| --- | --- |
| 无令牌 | 401 + `WWW-Authenticate: Bearer` |
| 令牌缺 `articles:read` | 403 + `WWW-Authenticate: Bearer scope="articles:read"` |
| 令牌有该 scope | 200 |
| 令牌签名错 | 401 |

### 权限不足该用 401 还是 403

这里有一处**官方文档与规范不一致**，值得知道：

| 出处 | 权限不足时用的状态码 |
| --- | --- |
| FastAPI 的 OAuth2 scopes 教程示例 | **401** |
| RFC 6750 §3.1 Error Codes（`insufficient_scope`） | **403** |

本章按 HTTP 语义与 RFC 选 **403**：
`401` 的含义是「你没有提供有效凭据，去认证一次再来」，
而权限不足时用户**已经**认证成功，只是不允许——`403` 才是准确的。
（这也是「读文档也要读规范」的一个具体例子：跟着示例抄，状态码就会抄错。）

判据表：

| 状态码 | 什么时候用 | 客户端该做什么 |
| --- | --- | --- |
| `401` | 没带令牌、令牌过期 / 无效 | 跳登录页 |
| `403` | 令牌有效，但没这个权限 | 提示「无权限」，**不要**跳登录页 |
| `404` | 资源不存在，或**存在但不该让你知道** | 提示不存在 |

### 角色（RBAC）

角色是 scope 的粗粒度版本，工程里更常用：

```python
def require_role(*roles: str):
    async def dep(user: Annotated[User, Depends(get_current_user)]) -> User:
        if user.role not in roles:
            raise HTTPException(403, "权限不足")
        return user
    return dep


@router.delete("/articles/{article_id}", status_code=204)
async def delete_article(_: Annotated[User, Depends(require_role("admin", "editor"))]):
    ...
```

实现上只有一处需要判断：**角色从库里读，还是信令牌里的 `role`？**

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| 信令牌（`role` 写在 JWT 里） | 不查库，最快 | 降权要等令牌过期才生效（最长 = 访问令牌有效期） |
| 每次查库（`get_current_user` 里查用户） | 权限变更立即生效 | 每个请求多一次查询（可用缓存抵消） |

本章选后者：`get_current_user` 已经查了用户，顺带拿到最新角色，
避免出现「已经封禁的用户还能用旧令牌删数据」这种事故。

### 对象级授权：越权访问（IDOR）

最容易被漏掉的一类漏洞不是「没有权限检查」，而是**权限检查粒度太粗**：
接口要求登录，但没检查「这条数据是不是他的」。

```python
@router.get("/articles/{article_id}", response_model=ArticleResponse)
async def read_article(
    article_id: int,
    user: Annotated[User, Depends(get_current_user)],
    db: Annotated[AsyncSession, Depends(get_db)],
):
    article = await db.get(Article, article_id)
    if article is None or (article.author_id != user.id and user.role != "admin"):
        raise HTTPException(404, "文章不存在")        # 越权也报 404
    return article
```

三个要点：

1. **判据是「资源归属」，不是「有没有登录」**。`get_current_user` 拦不住这类问题。
2. **越权时返回 404 而不是 403**：403 等于确认「这条数据存在，只是不给你看」，
   攻击者拿到的是「ID 有效」这一信息，可以继续枚举。
3. 列表接口同样要过滤：`where(Article.author_id == user.id)`，
   别指望前端不传别人的 ID。

> 💡 **提示**：这个漏洞在 OWASP 里对应「失效的对象级授权」
> （Broken Object Level Authorization），连续多年排 API 安全风险第一位。
> 它不需要任何技术漏洞，只需少写一个 `and article.author_id != user.id`。

## 1.13.10 刷新、轮换与撤销

### 为什么要两个令牌

无状态令牌的固有矛盾：**有效期越短越安全，越长越省事**。
解法是拆成两个，各司其职：

| 令牌 | 有效期 | 存放位置 | 作用 |
| --- | --- | --- | --- |
| 访问令牌（access） | 15–30 分钟 | 内存 / 请求头 | 每次请求都带，被泄露的窗口有限 |
| 刷新令牌（refresh） | 7–30 天 | `HttpOnly` Cookie / 安全存储 | 只用来换新的访问令牌 |

这两种令牌**必须不能互换**。否则一个能活 7 天的刷新令牌就能直接访问业务接口，
把「访问令牌短有效期」这个设计整个作废。实现就是签发时写死 `type`，校验时核对：

```python
if payload.get("type") != "access":
    raise HTTPException(401, "令牌类型不正确")
```

### 轮换：刷新令牌一次性使用

刷新令牌的有效期最长，因此是最值钱的攻击目标。**轮换（rotation）** 的做法是：
每次用它换新令牌时，把旧的立刻作废，同时发一对新的。

规范层面这条已经是硬要求：RFC 9700（OAuth 2.0 安全最佳实践）要求公共客户端
必须轮换刷新令牌；一旦检测到已用过的刷新令牌被再次提交，
应当把该用户的**整条令牌链**全部作废——因为这几乎可以确定是令牌被盗后双方都在用。

```python
@router.post("/refresh", response_model=Token)
async def refresh(refresh_token: Annotated[str, Body(embed=True)]):
    payload, _ = verify_token(refresh_token)
    if payload is None or payload.get("type") != "refresh":
        raise HTTPException(401, "刷新令牌无效")

    jti = payload["jti"]
    if not await refresh_store.pop(jti):          # 原子地取出并删除
        await revoke_all(payload["sub"])          # 已被用过：整链作废
        raise HTTPException(401, "刷新令牌已失效，请重新登录")

    access, _ = create_token(payload["sub"], "access", dt.timedelta(minutes=30))
    new_refresh, new_jti = create_token(payload["sub"], "refresh", dt.timedelta(days=7))
    await refresh_store.set(new_jti, payload["sub"], ttl=7 * 86400)
    return Token(access_token=access, refresh_token=new_refresh)
```

实跑（内存版存储）：

```text
1 登录              → 200，拿到 access + refresh
2 用 refresh 换新   → 200，拿到新的一对
3 旧 refresh 再用   → 401 {"detail": "刷新令牌已使用或失效"}
4 新 refresh 可用   → 200
```

第 3 行就是防重放的核心：**同一个刷新令牌只能用一次**。

### 撤销：两种方案

无状态令牌最难的是「立刻踢人」。有两种办法：

| 方案 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| `jti` 黑名单 | 把要作废的令牌 `jti` 写进 Redis（TTL = 令牌剩余有效期） | 精确到单个令牌 | 每请求要查一次 Redis；存储量随撤销数增长 |
| 令牌版本号 | 用户表加 `token_version`，签发时写进令牌；不匹配即拒绝 | 一次操作作废该用户**全部**令牌 | 每请求要查库（可与用户查询合并） |

日常「登出」用黑名单，事故处理（改口令、封号）用版本号——改口令时把
`token_version` 加一，所有旧令牌瞬间失效。两者可以同时存在。

> ⚠️ **注意**：无论哪种方案，**登出都要做三件事**：删掉服务端的刷新令牌记录、
> 把当前访问令牌加进黑名单、清掉客户端 Cookie。
> 只做第三件（很多教程就写到这）意味着：Cookie 没了，但那个访问令牌在
> 剩下的有效期里仍然能用——如果有 XSS 或已经抓到了抓包记录，这叫「登出失败」。

## 1.13.11 Cookie 与会话

浏览器场景下，把令牌放 `HttpOnly` Cookie 比放 `localStorage` 更安全：
JavaScript 读不到它，XSS 拿不到令牌本身（但**能代替用户发请求**，所以 CSRF 仍要防）。

### `set_cookie` 的七个属性

```python
response.set_cookie(
    key="access_token",
    value=access_token,
    max_age=1800,          # 过期时间（秒）；与 expires 同时给时以 max_age 为准
    path="/",              # 有效路径
    domain=None,           # 有效域名，默认仅当前主机
    secure=True,           # 仅 HTTPS 传输
    httponly=True,         # 禁止 JavaScript 访问（防 XSS 窃取）
    samesite="lax",        # CSRF 防护（strict / lax / none）
)
```

实跑出来的响应头：

```text
Set-Cookie: sid=abc123; HttpOnly; Max-Age=86400; Path=/; SameSite=lax
Set-Cookie: sid=abc123; HttpOnly; Path=/; SameSite=lax; Secure     ← secure=True
```

`SameSite` 三档的含义：

| 取值 | 同站请求 | 跨站 GET | 跨站 POST |
| --- | --- | --- | --- |
| `strict` | 携带 | 不携带 | 不携带 |
| `lax` | 携带 | 携带 | **不携带** |
| `none` | 携带 | 携带 | 携带（必须配 `secure=True`） |

`lax` 是生产环境的常用选择：它挡住了「跨站 POST」（表单伪造这类 CSRF 的主要形态），
同时保留从外部链接点进来时仍然带着登录态（否则每次从别的网站跳过来都要重新登录）。

> ⚠️ **注意**：`samesite="none"` 而 `secure=False` 时，**Starlette 不会报错**，
> 它会老老实实发出 `SameSite=none` 但没有 `Secure` 的 Cookie——
> 现代浏览器会直接丢弃它。这类「不报错的无效配置」只能靠检查响应头发现。

### 删除 Cookie 的路径陷阱

`delete_cookie` 的原理是「发一个同名、已过期的 Cookie」。因此
**设置时用了什么 `path` / `domain`，删除时就必须传同样的值**。
实跑对比：

```text
设置：Set-Cookie: sid=abc123; Path=/
用 delete_cookie("sid")            删除 → Set-Cookie: sid=""; ... Path=/      ✅ 删掉了
用 delete_cookie("sid", path="/api") 删除 → Set-Cookie: sid=""; ... Path=/api  ❌ 没删掉
```

第二行的 Cookie 仍然留在浏览器里。这个坑的典型现场是「退出登录点了没反应」。

删除的响应头也值得记一下（素材里写的是 1970 年那个时间点，实际不是）：

```text
Set-Cookie: sid=""; expires=<当前时间>; Max-Age=0; Path=/; SameSite=lax
```

关键在于 `Max-Age=0`——浏览器看到它就立刻删除。

### Cookie 还是 Session

| 对比项 | Cookie（客户端存储） | Session（服务端存储） |
| --- | --- | --- |
| 存储位置 | 浏览器本地 | 服务端内存 / Redis / 数据库 |
| 数据安全 | 暴露在客户端，敏感信息不能放 | 相对安全 |
| 每次请求的传输量 | 全量携带，增大报文 | 只带一个 `session_id` |
| 容量 | 单个 ≤ 4KB，单域名 20–50 个 | 不受限 |
| 能否立即失效 | 不能（内容在客户端） | 能（删掉服务端记录） |

推荐组合是两者各退一步：**Cookie 里只放一个 `session_id`（`HttpOnly`），
真正的数据放服务端 Redis**。

### `SessionMiddleware`：签名，但不加密

Starlette 内置的会话中间件是「签名 Cookie 会话」。官方文档的原话是
「会话信息**可读但不可修改**」。实跑看一眼就明白：

```text
Set-Cookie: sid=eyJ1c2VyIjogImFkbWluIiwgInJvbGUiOiAiYWRtaW4ifQ==.aqUVSQ.xEkNddVfLVdYCR15ZEcnUEKKNnM
去掉签名后直接 Base64 解码 → {"user": "admin", "role": "admin"}
```

所以 `SessionMiddleware` 的正确用法是**只放不敏感的小数据**（用户 ID、语言偏好、
CSRF token），而不要往里塞手机号、内部备注。

另一个实跑到的行为很值得注意：**篡改会话 Cookie 不会报错**，
签名校验失败时会话被**静默丢弃**，请求照常进入路由。表现为「用户莫名其妙变成未登录」。
如果你的日志里没有任何记录，排查起来会很痛苦——所以会话依赖里
「判断未登录」的分支要打日志。

```python
from starlette.middleware.sessions import SessionMiddleware

app.add_middleware(
    SessionMiddleware,
    secret_key=settings.SESSION_SECRET,
    session_cookie="sid",
    max_age=14 * 86400,     # 默认两周
    same_site="lax",        # 默认 lax
    https_only=True,        # 默认 False —— 生产环境务必显式打开
)
```

> 💡 **提示**：签名的意思是「内容被改过就能发现」，**不是**「内容别人看不到」。
> 需要「看不到」就得加密（JWE 或服务端存储），成本高得多。先问自己：
> 这些字段泄露了会怎样？答案通常决定了该用哪一种。

## 1.13.12 全局认证：中间件还是依赖注入

两种都能做「所有接口都要登录」，选错会带来长期的维护代价。

### 中间件写法

素材用的是 `fastapi-jwt-auth` 这个第三方库。本章不采用它（未安装、未实跑，
且这类封装会隐藏细节），改成用 PyJWT 手写，核心不到 20 行：

```python
EXEMPT_PATHS = {"/auth/token", "/auth/refresh", "/health", "/docs", "/redoc", "/openapi.json"}


@app.middleware("http")
async def auth_middleware(request: Request, call_next):
    if request.url.path in EXEMPT_PATHS:
        return await call_next(request)
    auth = request.headers.get("Authorization", "")
    if not auth.startswith("Bearer "):
        return JSONResponse(status_code=401, content={"detail": "缺少令牌"})
    payload, reason = verify_token(auth[7:])
    if payload is None:
        detail = "令牌已过期" if reason == "expired" else "令牌无效"
        return JSONResponse(status_code=401, content={"detail": detail})
    request.state.user_id = payload["sub"]
    return await call_next(request)
```

三个实跑过的注意点：

1. **白名单必须自己列全**。漏掉 `/docs` 会让文档页打不开；漏掉 `/openapi.json`
   会让 `/docs` 白屏（页面能开，但它取不到 schema）；漏掉健康检查会让探针把你判成不健康。
2. **中间件里 `raise HTTPException` 不会被异常处理器接住**（1.11 实跑过这一点），
   所以这里直接返回 `JSONResponse`。
3. **中间件注册顺序会影响执行顺序**：最后注册的在最外层（1.11 用源码与官方文档确认过）。

### 依赖注入写法（推荐）

| 对比项 | 中间件 | 依赖注入 |
| --- | --- | --- |
| 作用粒度 | 全局，只能靠路径白名单排除 | 逐路由可选，天然支持「游客也能看」 |
| 与 OpenAPI 的关系 | 完全不可见，文档里看不出要认证 | `Security` 会写进 schema，`/docs` 有 Authorize 按钮 |
| 错误响应的可读性 | 自己拼，容易与其他错误格式不一致 | 与 1.14 的统一异常处理器天然一致 |
| 可测试性 | 要绕过中间件才能单测 | 用 `dependency_overrides` 一行替换 |
| 拿到的东西 | 只能拿到 `request` | 能拿到完整的 `User` 对象、数据库会话等 |
| 适合 | 与业务无关的横切逻辑（请求 ID、访问日志、限流） | **认证与授权** |

FastAPI 官方文档也把依赖注入列为推荐做法。中间件真正擅长的其实是
「不关心是哪个接口」的那类逻辑：加请求 ID、记访问日志、限流、压缩。

> ⚠️ **一个容易搞错的细节**：全局依赖**不会**作用于 `/docs`、`/redoc`、
> `/openapi.json`——实测这三个路径都返回 200（这条在 1.11 已实跑确认）。
> 所以「用全局依赖保护文档」是行不通的；要保护文档只能用中间件。
> 反过来说，用依赖注入做认证是好事：文档页不会被自己锁上。

## 1.13.13 综合示例：知舟的认证模块

把上面的内容组装成一个可运行的模块：注册、登录、刷新、登出、取当前用户，
以及一个「只能改自己的文章」的接口。为了聚焦认证，这里用内存字典当数据库，
换成 1.12 的 SQLAlchemy 会话只需替换三个函数。

```python
# auth_demo.py —— 可直接运行：python auth_demo.py
import datetime as dt
import base64
import hashlib
import secrets
import uuid
from typing import Annotated

import bcrypt
import jwt
from fastapi import APIRouter, Body, Depends, FastAPI, HTTPException, Request, Security, status
from fastapi.security import OAuth2PasswordBearer, OAuth2PasswordRequestForm, SecurityScopes
from fastapi.testclient import TestClient
from pydantic import BaseModel
from starlette.middleware.sessions import SessionMiddleware

SECRET_KEY = secrets.token_urlsafe(48)
ALGORITHM = "HS256"
ACCESS_MINUTES, REFRESH_DAYS = 30, 7

# ---------- 口令 ----------
def _prehash(pw: str) -> bytes:
    return base64.b64encode(hashlib.sha256(pw.encode("utf-8")).digest())

def hash_password(pw: str) -> str:
    return bcrypt.hashpw(_prehash(pw), bcrypt.gensalt(rounds=12)).decode()

def verify_password(pw: str, hashed: str) -> bool:
    return bcrypt.checkpw(_prehash(pw), hashed.encode("utf-8"))

DUMMY_HASH = hash_password("zhizhou-dummy")

# ---------- 存储（生产换成数据库 + Redis）----------
class User(BaseModel):
    id: int
    username: str
    role: str = "user"

USERS: dict[str, dict] = {}
REFRESH_STORE: dict[str, str] = {}   # jti -> 用户 id
REVOKED: set[str] = set()            # 已登出的 access jti
ARTICLES = {1: {"id": 1, "title": "第一篇", "author": "alice"},
            2: {"id": 2, "title": "别人的文章", "author": "bob"}}

# ---------- 令牌 ----------
def create_token(user_id: int, token_type: str, delta: dt.timedelta) -> tuple[str, str]:
    now = dt.datetime.now(dt.timezone.utc)
    jti = uuid.uuid4().hex
    payload = {"sub": str(user_id), "type": token_type, "jti": jti, "iat": now, "exp": now + delta}
    return jwt.encode(payload, SECRET_KEY, algorithm=ALGORITHM), jti

def verify_token(token: str) -> tuple[dict | None, str]:
    try:
        payload = jwt.decode(token, SECRET_KEY, algorithms=[ALGORITHM],
                             options={"require": ["exp", "iat", "sub"]}, leeway=10)
    except jwt.ExpiredSignatureError:
        return None, "expired"
    except jwt.PyJWTError:
        return None, "invalid"
    return payload, ""

# ---------- 依赖 ----------
oauth2_scheme = OAuth2PasswordBearer(
    tokenUrl="/auth/token",
    scopes={"articles:read": "读取文章", "articles:write": "写入文章"},
)

def _unauthorized(detail: str, authenticate: str = "Bearer") -> HTTPException:
    return HTTPException(401, detail, headers={"WWW-Authenticate": authenticate})

async def get_current_user(token: Annotated[str, Depends(oauth2_scheme)]) -> User:
    payload, reason = verify_token(token)
    if payload is None:
        raise _unauthorized("登录已过期，请重新登录" if reason == "expired" else "凭据无效")
    if payload.get("type") != "access":
        raise _unauthorized("令牌类型不正确")
    if payload["jti"] in REVOKED:
        raise _unauthorized("令牌已登出")
    record = USERS.get(payload["sub"])
    if record is None:
        raise _unauthorized("账号不存在")
    return User(id=int(payload["sub"]), username=record["username"], role=record["role"])

def require_role(*roles: str):
    async def dep(current: Annotated[User, Depends(get_current_user)]) -> User:
        if current.role not in roles:
            raise HTTPException(403, "权限不足")
        return current
    return dep

# ---------- 路由 ----------
app = FastAPI(title="知舟认证示例")
app.add_middleware(SessionMiddleware, secret_key=secrets.token_urlsafe(32),
                   session_cookie="sid", same_site="lax", https_only=False)
router = APIRouter(prefix="/auth", tags=["认证"])

class RegisterIn(BaseModel):
    username: str
    password: str
    role: str = "user"

class TokenOut(BaseModel):
    access_token: str
    refresh_token: str
    token_type: str = "bearer"
    expires_in: int = ACCESS_MINUTES * 60

@router.post("/register", status_code=status.HTTP_201_CREATED)
async def register(data: RegisterIn):
    if len(data.password.encode("utf-8")) > 72 or len(data.password) < 8:
        raise HTTPException(422, "口令长度须在 8–72 字节之间")
    if any(u["username"] == data.username for u in USERS.values()):
        raise HTTPException(409, "用户名已存在")
    uid = len(USERS) + 1
    USERS[str(uid)] = {"username": data.username, "hashed": hash_password(data.password),
                       "role": data.role}
    return {"id": uid, "username": data.username}

@router.post("/token", response_model=TokenOut)
async def login(form: Annotated[OAuth2PasswordRequestForm, Depends()]):
    record = next((u for u in USERS.values() if u["username"] == form.username), None)
    if record is None:
        verify_password(form.password, DUMMY_HASH)      # 对齐耗时，防用户名枚举
        raise _unauthorized("用户名或口令错误")
    if not verify_password(form.password, record["hashed"]):
        raise _unauthorized("用户名或口令错误")
    uid = next(int(k) for k, v in USERS.items() if v is record)
    access, _ = create_token(uid, "access", dt.timedelta(minutes=ACCESS_MINUTES))
    refresh, jti = create_token(uid, "refresh", dt.timedelta(days=REFRESH_DAYS))
    REFRESH_STORE[jti] = str(uid)
    return TokenOut(access_token=access, refresh_token=refresh)

@router.post("/refresh", response_model=TokenOut)
async def refresh(refresh_token: Annotated[str, Body(embed=True)]):
    payload, _ = verify_token(refresh_token)
    if payload is None or payload.get("type") != "refresh":
        raise _unauthorized("刷新令牌无效")
    if REFRESH_STORE.pop(payload["jti"], None) is None:
        raise _unauthorized("刷新令牌已失效，请重新登录")     # 已用过 → 拒绝
    uid = int(payload["sub"])
    access, _ = create_token(uid, "access", dt.timedelta(minutes=ACCESS_MINUTES))
    new_refresh, jti = create_token(uid, "refresh", dt.timedelta(days=REFRESH_DAYS))
    REFRESH_STORE[jti] = str(uid)
    return TokenOut(access_token=access, refresh_token=new_refresh)

@router.post("/logout")
async def logout(
    refresh_token: Annotated[str, Body(embed=True)],
    token: Annotated[str, Depends(oauth2_scheme)],
):
    payload, _ = verify_token(refresh_token)
    if payload is not None:
        REFRESH_STORE.pop(payload["jti"], None)          # 1 删掉刷新令牌
    access_payload, _ = verify_token(token)
    if access_payload is not None:
        REVOKED.add(access_payload["jti"])               # 2 作废当前访问令牌
    return {"ok": True}                                  # 3 清 Cookie 由前端/响应头完成

app.include_router(router)

@app.get("/articles/{article_id}")
async def read_article(article_id: int, user: Annotated[User, Depends(require_role("user", "editor", "admin"))]):
    article = ARTICLES.get(article_id)
    if article is None or (article["author"] != user.username and user.role != "admin"):
        raise HTTPException(404, "文章不存在")           # 越权也报 404
    return article

@app.delete("/articles/{article_id}", status_code=204)
async def delete_article(article_id: int, _: Annotated[User, Depends(require_role("admin"))]):
    ARTICLES.pop(article_id, None)
    return None

@app.get("/me")
async def me(current: Annotated[User, Security(get_current_user)]):
    return {"id": current.id, "username": current.username, "role": current.role}

# ---------- 会话 Cookie（浏览器场景）----------
@app.post("/session/login")
async def session_login(request: Request, form: Annotated[OAuth2PasswordRequestForm, Depends()]):
    record = next((u for u in USERS.values() if u["username"] == form.username), None)
    if record is None or not verify_password(form.password, record["hashed"]):
        raise _unauthorized("用户名或口令错误")
    request.session["user_id"] = next(int(k) for k, v in USERS.items() if v is record)
    return {"ok": True}

@app.get("/session/me")
async def session_me(request: Request):
    uid = request.session.get("user_id")
    if uid is None:
        raise HTTPException(401, "未登录")
    return {"user_id": uid}
```

## 1.13.14 上线前的安全清单

认证模块的代码量不大，出错的代价却最大。上线前逐条过一遍：

| 项目 | 要求 | 不做会怎样 |
| --- | --- | --- |
| 密钥 | 从环境变量读取，≥32 字节随机值，**不进代码库** | 泄露即可伪造任意用户的令牌 |
| 传输 | 全站 HTTPS；Cookie 带 `Secure` | 令牌在链路上明文可抓 |
| 口令 | bcrypt / Argon2，工作因子 ≥10，限长且按字节校验 | 拖库后口令被直接还原 |
| 访问令牌有效期 | 15–30 分钟 | 令牌泄露的窗口被拉长 |
| 刷新令牌 | 轮换 + 一次性使用 + 服务端存 `jti` | 一个刷新令牌能永久续命 |
| 登出 | 删刷新记录 + 令牌进黑名单 + 清 Cookie | 「登出」只是客户端的错觉 |
| 登录限流 | 按 IP / 用户名限速，并记录失败次数 | 撞库与 CPU 消耗攻击 |
| 错误信息 | 「用户名或口令错误」统一文案 + 耗时对齐 | 泄露账号是否存在 |
| 日志 | **绝不**记录密码、令牌、Cookie 原文 | 日志系统成了令牌仓库 |
| 依赖更新 | 关注 PyJWT 等的安全公告 | 认证库自身的漏洞会穿透所有防护 |
| 授权粒度 | 每个涉及资源的接口都有归属校验 | 越权访问（API 风险第一名） |
| CORS | 不用 `allow_origins=["*"]` 配 `allow_credentials=True` | 任意站点可带 Cookie 读你的数据（1.11 已实测） |

关于倒数第二行的「依赖更新」，PyJWT 2.13 与 2.14 两个版本里就修了十来个安全问题：
算法混淆（`alg` 与允许列表的绑定被绕过）、把 JWK JSON 当 HMAC 密钥传入、
空 HMAC 密钥、JWKS 重定向到不受信任的地址、嵌套 JWS/JWK 输入导致递归异常……
**认证库是少数几个「必须跟进版本」的依赖**，因为它的漏洞不会被你的业务逻辑兜住。

## 常见坑

- **把「登录」当成「授权」**。现象：接口都要求令牌，但 A 用户能读 B 用户的数据。
  原因：`get_current_user` 只回答「你是谁」，没回答「这条数据是不是你的」。
  修法：每个涉及资源的接口加归属判断（`article.author_id != user.id`），越权时返回 404。
- **令牌里放敏感信息**。现象：抓包或 Base64 解码就能看到用户手机号。
  原因：JWT 的 Payload 只是编码，签名只保证不被篡改。
  修法：只放 `sub`、`type`、`jti`、时间戳；要传递的资料回查数据库。
- **忘了设 `exp`**。现象：测试环境的令牌几天后还能用。
  原因：`jwt.decode` 默认不要求 `exp` 存在，没有该声明就不做过期检查。
  修法：签发时必写 `exp`，校验时加 `options={"require": ["exp", "iat", "sub"]}`。
- **`sub` 传了整数**。现象：签发或校验报 `InvalidSubjectError: Subject must be a string`。
  原因：PyJWT 2.10 起校验 `sub` / `jti` 的类型。
  修法：统一用 `str(user.id)`。
- **只捕 `PyJWTError`**。现象：前端永远显示「凭据无效」，用户不知道是登录过期。
  原因：`ExpiredSignatureError` 是它的子类，被父类分支先接走了。
  修法：先捕具体子类，再捕父类兜底。
- **中文长口令注册 500**。现象：`ValueError: password cannot be longer than 72 bytes`。
  原因：bcrypt 5.0 起不再静默截断（一个汉字 3 字节，24 个汉字就到上限）。
  修法：入口处按字节校验长度，或先 `sha256 + base64` 预哈希。
- **用户不存在时登录更快**。现象：可以用响应耗时判断账号是否注册过。
  原因：不存在的用户直接返回，存在的用户要走一次 200 ms 的 bcrypt。
  修法：对不存在的用户名也跑一次 `verify_password(password, DUMMY_HASH)`。
- **`delete_cookie` 没删掉**。现象：点了登出，刷新页面还是登录状态。
  原因：设置时 `path="/"`，删除时传了 `path="/api"`，路径不匹配。
  修法：删除时传与设置完全相同的 `path` / `domain`。
- **`secure=True` 在 HTTP 下「读不到」**。现象：本地调试设置了 Cookie，下一次请求却收不到。
  原因：浏览器不会通过 HTTP 发送 `Secure` Cookie。
  修法：用配置区分环境（`secure=is_prod`），别在生产里为了调试关掉。
- **会话莫名丢失**。现象：用户偶尔被踢成未登录，日志里什么都没有。
  原因：`SessionMiddleware` 验签失败时**静默丢弃**会话。
  修法：在会话依赖的「未登录」分支打日志（含是否有 Cookie），别让它无声无息。
- **以为 scope 声明就等于检查**。现象：`/docs` 里显示需要 `items:write`，但没这个权限照样能调。
  原因：声明只进 OpenAPI，检查必须在依赖代码里写。
  修法：在依赖里比对令牌的 scope 集合，缺失时返回 403。
- **权限不足返回 401**。现象：前端收到 401 就把用户踢到登录页，用户困惑「我明明登录了」。
  原因：401 与 403 混用。
  修法：缺凭据 / 凭据无效 → 401；凭据有效但无权限 → 403。
- **中间件保护文档失败**。现象：全局依赖加上了，`/docs` 仍能匿名打开。
  原因：全局依赖不作用于 `/docs`、`/redoc`、`/openapi.json`（实跑确认）。
  修法：要保护文档就用中间件，并把 `/openapi.json` 一起放进保护范围。

## 面试视角

> 🎯 **面试**：这一节的每一题都能在两分钟内暴露候选人做过没做过真实项目。

1. **「认证和授权有什么区别？JWT 解决的是哪一个？」**
   考察点：概念边界。答题要点：认证回答「你是谁」，授权回答「你能做什么」。JWT 两者都能承载，
   但它本身是**凭证格式**，解决的是「认证结果怎么携带」；授权仍需在服务端逐接口判断
   （scope、角色、资源归属），令牌里带了 `role` 也不等于做完授权。
2. **「JWT 和 Session 怎么选？」**
   考察点：架构取舍。答题要点：看三件事——要不要立即撤销（要 → Session 或加黑名单）、
   要不要水平扩展（要 → Token 免共享存储）、调用方是不是浏览器之外（是 → Token）。
   生产常见形态是两者结合：令牌放 `HttpOnly` Cookie，服务端另有可撤销名单。
3. **「JWT 的 Payload 是加密的吗？能放用户手机号吗？」**
   考察点：是否知道 JWT 只签名不加密。答题要点：不是加密，Base64URL 解码即得明文，
   任何拿到令牌的人都能读。放敏感信息要用 JWE 或干脆只放 ID 回查数据库。
4. **「口令为什么要用 bcrypt，不用 SHA-256？」**
   考察点：口令存储原理。答题要点：SHA-256 太快，GPU 每秒可试数十亿次；bcrypt 有内置随机盐、
   工作因子可调慢（本机 rounds=12 约 200 ms），三者缺一不可。另外要知道 bcrypt 的 72 字节上限，
   以及 5.0 起超长口令直接抛异常。
5. **「访问令牌为什么短有效期？刷新令牌怎么防被盗？」**
   考察点：是否实现过刷新流程。答题要点：短有效期限制泄露窗口，刷新令牌负责续期。
   刷新令牌必须**轮换 + 一次性使用**（RFC 9700 要求），服务端存 `jti`；
   检测到已用过的刷新令牌再被提交，就作废整条令牌链——这通常意味着令牌被盗。
6. **「怎么立刻让一个已签发的 JWT 失效？」**
   考察点：无状态令牌的经典难题。答题要点：两条路——`jti` 黑名单（存 Redis，
   TTL 设为令牌剩余有效期）精确到单个令牌；或用户表加 `token_version` 写进令牌，
   改口令 / 封号时加一，一次性作废该用户全部令牌。两者都要付出「每请求一次查询」的代价。
7. **「前端说拿到 401，你怎么排查？」**
   考察点：调试路径。答题要点：先看请求有没有带 `Authorization: Bearer`；
   再看令牌是否过期（本地解码 `exp` 比对时间，注意时区）；再核对服务端 `algorithms`
   与签发算法是否一致、密钥是否同一份；最后看服务端是否在 401 里带了
   `WWW-Authenticate`（有 `error="invalid_token"` 才好定位）。
8. **「越权访问（IDOR）怎么防？」**
   考察点：授权粒度。答题要点：判据是资源归属而不是登录状态；所有按 ID 取资源的接口
   都要校验 `resource.owner_id == current_user.id`（管理员例外）；越权返回 404 而非 403，
   避免确认资源是否存在；列表接口也要按归属过滤。

## 本章小结

1. **认证、授权、会话是三件事**。会话放服务端（可撤销、需共享存储）还是客户端
   （免存储、可扩展、撤销难）是一道架构题，生产系统的答案常常是两者结合。
2. **口令只存哈希**：单向、加盐、可调慢三者缺一不可。bcrypt 的 `gensalt()` 自带随机盐，
   工作因子 12 约 200 ms；**72 字节上限**是中文口令的实际雷区（bcrypt 5.0 起直接抛异常），
   可用「入口限长」或「sha256 + base64 预哈希」解决。
3. 素材用的 `python-jose + passlib` 已被官方教程替换为 **PyJWT (+ pwdlib)**；
   passlib 与新版 bcrypt 存在已知冲突，本章主线代码走 PyJWT + bcrypt，
   且每个结论都在本机实跑过。
4. **JWT 三段**：Header.Payload.Signature。Payload 明文可读，签名只防篡改。
   `algorithms` 必须显式传白名单（PyJWT 强制要求），算法混淆攻击就防住了。
5. 签发时的五个细节：`sub` 必须字符串、时间用 aware UTC、必给 `jti`、
   用 `type` 隔开两种令牌、密钥 ≥32 字节（短密钥只警告，且 2.12.1 的调用级强制开关**不生效**）。
6. **`decode` 默认不要求 `exp` 存在**——忘了签发就是永久令牌。用
   `options={"require": ["exp", "iat", "sub"]}` 把约定变成检查。异常要**先捕子类**
   （`ExpiredSignatureError` 是 `PyJWTError` 的子类），否则过期会被误报成无效。
7. **OAuth2 是流程，JWT 是格式**。FastAPI 只实现了「密码模式 + Bearer」这一小块，
   授权码、客户端凭证、PKCE 都要自己接或交给授权服务器。
8. 认证依赖 `get_current_user` 是唯一入口：**401 必须带 `WWW-Authenticate`**，
   `auto_error=False` 可做游客模式；对不存在的用户名也跑一次哈希校验，
   避免用响应耗时枚举账号。
9. **声明 scope 不等于检查 scope**。用 `Security(..., scopes=[...])` 声明，
   在依赖里比对实际权限。权限不足用 **403**（官方示例用 401，但 RFC 6750 与 HTTP 语义是 403）。
   角色从库读而不是只信令牌。**资源归属校验（IDOR）是最常被漏掉的一层**，越权报 404。
10. **刷新令牌轮换 + 一次性使用**（RFC 9700）：旧令牌再次出现即拒绝并作废整链。
    撤销两条路：`jti` 黑名单（精确）与 `token_version`（一次作废全部）。
    登出必须同时做三件事，只清 Cookie 等于没登出。
11. **Cookie 的安全三件套**：`httponly` + `secure` + `samesite="lax"`。
    删除时 `path` / `domain` 必须与设置一致（否则删不掉）。
    `SessionMiddleware` **只签名不加密**（官方原话「可读不可改」），
    验签失败会静默丢会话——排查时要有日志。
12. 全局认证**推荐依赖注入**：可局部、可测试、进 OpenAPI、能拿到完整 `User`；
    中间件适合请求 ID、日志、限流这类横切逻辑。注意全局依赖**不作用于** `/docs`、
    `/openapi.json`，要保护文档只能用中间件。
13. 上线前过一遍 1.13.14 的清单，其中两条最容易漏：**日志里绝不能出现口令与令牌**；
    **认证库要跟进版本**（PyJWT 2.13/2.14 就修了十来个安全问题）。

**官方文档**（本章结论的权威依据）

- FastAPI · OAuth2 with Password (and hashing), Bearer with JWT tokens — https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/ ｜ 官方现用栈：PyJWT + pwdlib（推荐 Argon2）、`DUMMY_HASH` 防账号枚举、`datetime.now(timezone.utc)`
- FastAPI · OAuth2 scopes — https://fastapi.tiangolo.com/advanced/security/oauth2-scopes/ ｜ `SecurityScopes`、scope 是空格分隔的字符串、以及官方示例里「权限不足用 401」的取舍
- FastAPI · Get Current User — https://fastapi.tiangolo.com/tutorial/security/get-current-user/ ｜ `get_current_user` 依赖的标准写法
- FastAPI · Simple OAuth2 with Password and Bearer — https://fastapi.tiangolo.com/tutorial/security/simple-oauth2/ ｜ 表单登录与 `OAuth2PasswordRequestForm`
- FastAPI · Security — https://fastapi.tiangolo.com/tutorial/security/ ｜ 安全工具总览与各章入口
- PyJWT · Usage — https://pyjwt.readthedocs.io/en/stable/usage.html ｜ `encode` / `decode` 的参数与选项（`leeway`、`require`、`audience`）
- PyJWT · Changelog — https://pyjwt.readthedocs.io/en/stable/changelog.html ｜ `sub` / `jti` 类型校验（2.10）、最短密钥长度与调用级选项失效修复（2.11 / 2.13）、2.13–2.14 的安全修复清单
- Starlette · Middleware — https://starlette.dev/middleware/ ｜ `SessionMiddleware`「可读但不可改」的原话与各参数默认值
- bcrypt · CHANGELOG — https://github.com/pyca/bcrypt/blob/main/CHANGELOG.rst ｜ 5.0.0 起超过 72 字节的口令由静默截断改为抛 `ValueError`
- RFC 7519 · JSON Web Token (JWT) — https://www.rfc-editor.org/rfc/rfc7519.html ｜ 标准声明与签名语义
- RFC 6749 · The OAuth 2.0 Authorization Framework — https://www.rfc-editor.org/rfc/rfc6749.html ｜ 四个角色与四种授权方式
- RFC 6750 · Bearer Token Usage — https://www.rfc-editor.org/rfc/rfc6750.html ｜ §3.1 Error Codes：`invalid_token` → 401、`insufficient_scope` → 403，以及「完全未带凭据时不带 `error` 码」
- RFC 7518 · JSON Web Algorithms — https://www.rfc-editor.org/rfc/rfc7518.html ｜ §3.2「HMAC 密钥不得短于哈希输出长度」，即 HS256 需 ≥32 字节
- RFC 9700 · Best Current Practice for OAuth 2.0 Security — https://www.rfc-editor.org/rfc/rfc9700.html ｜ 刷新令牌轮换与已用令牌再提交时作废整链
- OWASP · Password Storage Cheat Sheet — https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html ｜ 工作因子建议、bcrypt 的 72 字节限制与预哈希注意事项
- OWASP · Authorization Cheat Sheet — https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html ｜ 对象级授权的检查清单（IDOR）
- OWASP · Authentication Cheat Sheet — https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html ｜ 口令策略、错误文案与限流要求
