## 10.5.1 换体系不是换题：处置的三个取值

上一章把题库拆成三层（题面可用、考点可当索引、答案不可信），这一章沿用同一套三层，但多了一道动作，而这道动作才是本章的立论：**当题库的体系与岗位的体系不一致时，逐板块判处置比逐题筛有用得多。**

| 处置 | 判据 | 判错的样子 | 本章的板块 |
| --- | --- | --- | --- |
| 留 | AI／Python 岗位也会问同一件事，只是名字不同 | 把体系当岗位（因为写着 Java 就跳过） | 并发、消息队列、缓存、数据库、RPC、监控告警、容器 |
| 换视角 | 考的是同一个思想，但例子与栈要替换 | 照题背答案（背的是 JVM 的参数） | Java 语言核心、Spring 框架、系统设计、海量数据 |
| 弃 | **岗位不会问**，不是「这一块不重要」 | 舍不得（因为它难、看起来高级） | JVM 虚拟机（7 道） |

三个取值里最容易判错的是第三个。**「弃」的依据是岗位的口径，不是知识的价值**：JVM 的内存模型与垃圾回收对后端岗（尤其 Java 岗）是高频，而你投的是 Python／AI 岗——那边问的是「你的服务为什么在 p99 上抖」，而不是「G1 的分区怎么回收」。所以弃那 7 道不是删掉知识，而是**把复习时间从它身上挪走**（按本章的账，那是 4.2% 的题量）。

第二个容易判错的是「留」：写着 Java 的题不代表问的是 Java。比如「消息重复消费怎么办」这一道，题面里一个 Java 词都没有，而它在两个岗位上都问——它就是「留」。判据是**把题面里的栈名去掉，看剩下的问题还成不成立**（成立就是留，不成立就看它是不是「换视角」）。

为什么这份题库会错位，值得说清，因为它解释了「为什么不能逐题筛」。题库是按**一家公司的技术栈**编的：它把 Java 生态里的每一个部件都问一遗（语言、并发、虚拟机、框架、缓存、队列、数据库、运维），而每一个部件在两个岗位上的**名字不同、而问题相同**。逐题筛的代价是你得把 165 道都读一遗（而其中 7 道读完就该扔）；逐板块判处置的代价是多了一道判断，而这道判断一次管一个板块。

把几个高频例子摆在一起，错位的形状就很清楚了：

| 题库的问法（Java） | 岗位里的问法（Python／AI） | 处置 |
| --- | --- | --- |
| `HashMap` 的底层与冲突解决 | 字典的哈希与可变键（为什么列表不能当 key） | 换视角 |
| `synchronized` 与 AQS | 「为什么不多加几个线程」（GIL） | 留（换例子） |
| 线程池参数怎么调 | 线程池 vs 进程池 vs 事件循环 | 留（换例子） |
| Spring 的 AOP 与事务传播 | 中间件与依赖注入（FastAPI 的 `Depends`） | 换视角 |
| JVM 的 GC 与内存模型 | 「服务为什么在 p99 上抖」（观测而非 GC） | 弃 |
| Redis 的穿透与雪崩 | 同一件事（字都没变），另加语义缓存的分界 | 留 |
| Kafka 的重复消费 | 同一件事（字都没变） | 留 |

这张表里最值得注意的是最后两行：**存储与消息那两堆几乎不需要换视角**——它们的问法跨语言不变（因为它们是外部系统，不是语言特性）。而前面几行都在语言与框架里，所以那一堆的处置才是「换视角」。

处置表本身也有一份维护成本，而它的好处恰好在这里：**判据写在脚本里，改它要动代码、而代码进提交门**。题库换了（比如换成 Python 题库）、或者你的岗位换了（从 AI 应用换成数据平台），要做的不是重读一遍题，而是把 `DISPOSITION` 那一张十二行的表重判一次——而正文那张表会跟着 `--check` 报错，逼你同步。

## 10.5.3 并发与异步：同一件事的两种叫法

JUC 那 15 道题问的是 Java 的并发工具，而它们的问题本身与语言无关——只是答案要换成 Python 的：

| JUC 里的问法 | Python 岗的对应物 | 该给的那个数或判据 | 本书哪里给 |
| --- | --- | --- | --- |
| 线程池参数怎么定 | `ThreadPoolExecutor` 的 `max_workers` 与队列 | 按**阻塞时长与 CPU 占用**分：I/O 密集可多、CPU 密集无益 | 1.7；8.5 的容量账 |
| 为什么要有 AQS／锁 | `threading.Lock`／`asyncio.Lock` | 临界区有多长、锁的粒度在哪 | 8.4 的配额动作 |
| `volatile` 的作用 | 没有直接对应物：`asyncio` 里用消息传递不用共享内存 | 换成「共享可变状态存在于哪」这个问题 | 3.6 的会话态 |
| `ThreadLocal` | `contextvars` | 每个请求一份的上下文（追踪 id、租户） | 7.2 的轨迹 |
| 线程安全的数据结构 | `queue.Queue`／`asyncio.Queue` | 消费者是几个、慢消费者怎么办 | 8.3 的缓冲长度 |

而真正的分界线只有一个词：**GIL**。它决定了 Python 侧那道最常被问的问题怎么答——**CPU 密集要换进程，不是加线程**（多进程绕开 GIL；加线程只会在 I/O 释放 GIL 的那些窗口里有效）。这条判据的完整形态是三分法：

1. **I/O 密集**：`asyncio`（单线程事件循环）或线程池；瓶颈在网络或磁盘。
2. **CPU 密集**：多进程（或把那段挪到 C 扩展／向量化库里）；瓶颈在解释器。
3. **混合**：拆开——把 CPU 那段丢给进程池，I/O 那段留在事件循环里。

第 1.7 章已经把这三条各给过一次账，而面试里更值分的是**第三条的下半句**：混合负载最常见的坏形态是**在协程里做了阻塞调用**（一个同步的数据库驱动、一次 `requests.get`、一次大文件读），它会让整个事件循环停住——**表面上是「慢」，实际是「所有并发请求一起慢」**。发现它的办法不在代码里而在读数里：**单请求延迟没变、而并发请求的 p95 一起抬**（这是第 7.2 章黄金信号里最典型的一种形状）。

题面那一侧给出的读数很直白：**「锁 6 道、线程池 2 道、ThreadLocal 3 道」，而「Python 0 道、asyncio 0 道、GIL 0 道、协程 0 道、多进程 0 道」**。这不是题库的缺陷——它本来就不是为你写的。**这一节的动作就是把左边那列换成右边那列**，而换完以后你会发现：题还是那些题，例子全变了。

三分法里有一条容易被略过的代价：**多进程不是免费的**。进程池的每一次任务提交都要把参数序列化、把结果序列化回来（而这一步的代价往往比那段 CPU 计算还大）——所以判据不是「CPU 密集就上进程」，而是**「单次任务算得够久，序列化才不算浪费」**。经验上的分界线是任务粒度：把一万条各花 1 毫秒的记录丢给进程池，开销全在传递上；把一百条各花 200 毫秒的丢过去，才真的快。所以同一条追问（「为什么不用多线程」）其实有两层：第一层是 GIL（认知），第二层是「你怎么量的」（工程）。

而这两层在面试里的答法也不同。第一层可以背（GIL 是什么、为什么它在 I/O 时释放）；第二层只能给一个具体形状：**先量三种实现下的吞吐与延迟，再选**，并说出你量的那两三个数（任务数、单次耗时、序列化开销）。第 1.7 章的账已经验过这条路径一次，而它在面试里的价值是：**当你说「我量过」，追问会从「你知不知道」降到「你怎么量的」**——后者永远好答。

异步还有三种常见误用，它们的共同症状是「本地跑得快、一上量就塔」：**其一**，把重活（图像处理、大文件解析）丢在事件循环里；**其二**，用 `time.sleep` 代替 `asyncio.sleep`（前者会卡住整个循环）；**其三**，忘了 `await`（协程对象被创建而从未执行，最后的报错离现场很远）。三者都是同一个根因：**事件循环只有一个线程**，任何占用它的动作都不是「这一段慢」，而是「所有并发请求一起慢」。把它们写成一张自检清单挂在记忆里，比记 asyncio 的 API 有用得多。

最后是该用哪种同步原语的对照组（面试里经常被顺口问一句）：

```
需要保护什么            用什么                    最容易写错的地方
计数器／共享变量         asyncio.Lock（异步）       跨 await 拿着锁
一段临界区的独占         threading.Lock            锁里做了阻塞调用
每个请求一份的上下文     contextvars              用全局变量代替（串了租户）
生产者与消费者解耦       asyncio.Queue             无界队列（内存先满）
```

（围栏 3：同步原语对照。**四行的共同判据是「等的时候会不会把别人也卡住」**——这也是选 asyncio 还是选线程的那道分界线。）

## 10.5.4 缓存：三件老问题，一条新界线

缓存那一板块 18 道（均 3.39★，其中 8 道在 4★ 以上），问的是三件老问题加一条新界线：

| 老问题 | 它是什么 | 解法 | 常见答错的点 |
| --- | --- | --- | --- |
| 穿透 | 查一个**不存在**的键，每次都落到数据库 | 空值也缓存（带短过期）或布隆过滤器 | 只说「加缓存」而没说空值也要缓存 |
| 击穿 | 一个**热点键**过期，瞬间全打到数据库 | 单飞（只让一个请求去回填，其余等）或逻辑过期 | 把击穿与雪崩混着说 |
| 雪崩 | **大量键同时过期**，或缓存整体不可用 | 过期时间加随机、多级缓存、降级到限流 | 只说「过期时间打散」而不说缓存挂了怎么办 |

三个词的区别可以用一句话记住：**穿透是「没有」，击穿是「一个」，雪崩是「一片」。** 这句话之所以值钱，是因为面试官常在第一层追问里就切进去（「你说说这三个的区别」），而答错一句，后面关于一致性的话都会被降权。

一致性那部分的问法固定：「先删缓存还是先写库？」正确的答法不是选一个，而是**承认两条路都会有不一致窗口，然后说清窗口有多长、谁在看**：先写库再删缓存（常用）的窗口是「删之前有人读到了旧值」；先删缓存再写库的窗口更大（写库还没完成时，读请求回填的仍是旧值）。处置与 6.3 的思路同一条：**把不一致窗口当作已知代价，再用过期时间与版本号把它压到可接受**。

一致性那部分还常被追一句「多级缓存怎么保证一致」。这一句的答法不是「保证」，而是**分层说清各自的失效代价**：本地缓存（进程内）最快但**只能等过期**（广播失效在多数框架里不可靠）；远程缓存（Redis）可以精确删，但多一跳网络；而两层叠起来会出现一个很容易踩的顺序问题——**删了远程而本地还留着**（于是不一致的窗口变成「本地那层的 TTL」）。处置与 8.4 的配额同一条思路：**把两个窗口都写成数（本地 TTL 多少秒、网络那一跳多少毫秒），然后说清哪个能忍**。

而这一节真正的新东西是那条界线：**这一章说的缓存（键相等的缓存）与第 5 篇的语义缓存（按相似度命中的缓存）不是一回事**。它们的判据不同（一个看 key 是否相同，一个看向量距离是否够近）、失效方式不同（一个靠删 key，一个靠阈值与版本）、错的代价也不同（前者最多读到旧值，后者**答错还像对的**）。面试里把两者混着说（「我们用 Redis 做语义缓存，命中就返回」）会立刻暴出一个问题：**你凭什么判断这次命中是对的？**——那正是第 5 篇的回归集要回答的事。

## 10.5.5 数据库与索引：15 道题，两种索引

MySQL 那一板块 15 道（≥4★ 9 道，均 3.40★），题面里「索引」出现 7 道、「事务」只有 1 道——**这个比例本身就是一条判据**：题库爱问索引（能画图、能对比），而事务与隔离级别问得少（结论性强、不好出选择题），但面官几乎必问一句。所以这一节要按**「按题库的密度复习、按岗位的密度准备」**来分配时间。

索引那部分在三层里都有可答的话：最上面一层是判据（**联合索引的最左前缀、覆盖索引避免回表、区分度决定选不选它**），中间一层是工具（`EXPLAIN` 看走了哪个索引、`type` 那一列的含义），最下面一层才是调优（把一条 2 秒的查询压到 20 毫秒，改的是索引而不是 SQL 写法）。

事务那部分只有一句核心：**隔离级别决定你可能看到什么怪象**（脏读、不可重复读、幻读），而多数业务系统选的是「读已提交」（Oracle/PostgreSQL 的默认，也常是 MySQL 部署时的选择），因为「可重复读」的代价（间隙锁、更多等待）在很多场景里换不回来。这一句话背后是第 8.4 章那笔账：**隔离级别越高，同一份配额能支撑的并发越低**——面试里把它连起来答，比背四个级别的名字有效。

调优那部分的工具是 `EXPLAIN`，而它只有三个列真的要读懂：**`type`（访问方式：全表扫描、索引扫描、还是索引查找）、`rows`（预计读多少行）、`Extra`（有没有出现 `Using temporary` 与 `Using filesort`）**。三列的用法各不相同：`type` 告诉你「索引用没用上」，`rows` 告诉你「代价大不大」，`Extra` 则直接指向要改的地方（临时表与文件排序几乎都可以通过索引消掉）。这一节的实操动作只有一个：**把你手上最慢的那条查询的 `EXPLAIN` 拍下来，改一个索引，再拍一张**——两张图放一起就是一次面试答案。

连接池那部分则与 8.4 的配额相接：池子大小不是越大越好（数据库的连接数是有限的共享资源，而每一个连接都占内存与文件描述符）；正确的取值是**（并发请求数 × 单次占用时长）／可接受等待时长**，并且必须带超时（池子满时的等待也要有一个上限，否则请求会堆在池子前面——那是 8.5 那类「排队先坏」问题的一个变体）。

还有一个考点在题库里只出现一次、而被追问的频率很高：**深分页**。`LIMIT 100000, 20` 这种写法会让数据库先扫过十万行再丢掉——它不是「慢一点」，而是**越翻到后面越慢**（且与并发叠加后很容易超时）。处置有三条路，而它们的代价各不相同：记住上次的位置（游标分页，最常用）、用延迟关联（先用索引拿 id 再回表）、或者干脆不给深分页（产品层限制翻页深度）。**面试里答这一道的时候，把「为什么不能用 offset」说清比背解法更重要**。

而 AI 岗位的追问会在这里拐一个弯：**「你的向量索引与数据库索引有什么不一样？」** 那是一道能把第 5 篇的账直接搬过来的题——普通索引是精确的 B 树（能找到就是找到了），向量索引是近似的（HNSW／IVF 用召回换速度，参数一改召回就变），所以**它的「索引选择」不只是快慢问题，还是一次召回率的取舍**，而取舍要有评测集兜底（5.6）。答出这一层，就与只会背「加索引」的人分开了。

缓存还有一个与限流纠缠在一起的问题，面试里常常与缓存一起问：**缓存击穿的那一瞬间，未命中回填的并发数怎么控？** 正确的做法不是「把过期时间拉长」（那是把击穿换成雪崩），而是**在回填那一层加一道单飞与并发上限**——换句话说是拿 8.4 的限流去保护数据库（而不是保护接口）。这一句话能把两个板块接起来，也是「你想想上下游」这类追问的起点：**缓存的保护对象是数据库，不是缓存自己。**

## 10.5.6 消息队列与分布式：35 ＋ 9 道

MQ 是十二个板块里题最多的一个（35 道，≥4★ 13 道），而它的考点收成三道关就够了：

| 关 | 问法 | 答法 | 本书哪里给 |
| --- | --- | --- | --- |
| 幂等 | 「消息重复消费怎么办？」 | 消费者侧做幂等键（或让写入天然幂等），不靠「保证不重复投递」 | 3.5；6.3 的错误分档 |
| 顺序 | 「怎么保证顺序？」 | 同一分区（或同一 key）内有序；跨分区别奢望全局有序 | 8.2 的异步任务 |
| 死信 | 「处理不了的消息去哪？」 | 死信队列 ＋ 人工（或重试上限后落库），**并给它一个读数** | 6.3；8.5 的告警 |

三关里的第一关最常被答错，而错法只有一种：**把幂等当成投递侧的责任**（「让 MQ 保证只投一次」）。第 3.5 与 6.3 已经把这件事说透了——**投递语义里「恰好一次」只在两端配合时成立**，而工程上真正能站住的写法是：**消息可能重复，消费必须幂等**。这一句在两个岗位上是同一个答案，所以它是「留」的典型：把 `Kafka` 换成别的队列，那句话一个字都不用改。

幂等键怎么选，是这三关里唯一需要动脑的一步（其余两步是套路）。可用的四类键按可靠性排下来是：**幂等键**（发送方生成的唯一 id，最可靠）→ **自然键**（订单号 ＋ 业务动作）→ **内容哈希**（同一内容算同一值）→ **时间窗口**（「一分钟内同一用户同一动作只算一次」，最弱、且会误杀）。选择它同时决定了存储：幂等键要落库或落缓存并带过期（否则表会无限长），而过期时长等于你能容忍的「重复窗口」——这一句直接把幂等与 8.4 的配额接了起来。

「死信 3 道」是这一板块题面里唯一的专有词读数，而它值得记一句：**死信队列不是垃圾桶**。它的价值在于**给「处理不了」这件事一个去处与一个读数**——没有死信队列时，处理不了的消息会阻塞分区（消费卡住），而有了它，卡住变成一条可以看的计数（第 8.5 章的症状告警在这里第一次有地方挂）。

微服务与 RPC 只有 9 道，但它是全库**平均难度最高的一板块**（3.56★）——题少而深。它的核心是一次换栈：**把 Dubbo／Spring Cloud 的问题换成「进程间怎么说话」**：

| 问法 | Python／AI 岗的答法 | 取舍 |
| --- | --- | --- |
| 服务间怎么调 | gRPC（有契约、有代码生成）或 REST（好调试、好被别人调） | 契约强 ↔ 调试与兼容性 |
| 四种调用类型 | 一元、服务端流、客户端流、双向流 | 流式用在「生成」这类场景（接 8.3 的 SSE） |
| 超时重试 | 每个调用带 deadline，重试要有上限与退避 | 与 6.3 同一套（含「重试会不会重复扣款」） |
| 服务发现与负载均衡 | 由基础设施给（K8S Service），代码里不写地址 | 与容器那一板块接上 |

这一板块还有一道必然会被问到的收尾题：**「你们的接口是同步还是异步的？」**——它考的是你有没有把整条链路的形状想清楚，而答法要把三样分开：**REST／gRPC 用于「调用方要一个结果」**，**队列用于「不必等」**（提交任务、异步重试），**SSE／流式用于「结果是一段段出来的」**（第 8.3 章）。三者的选择叉口只有一个问题：**调用方能不能等？** 能等就同步（最好调试）；不能等就队列（要有幂等与死信）；而结果本身是流式的（生成类任务），就选第三种。面试里把这三个答案分开说清，比笼统地答「我们用微服务」有价值得多。

## 10.5.7 系统设计与稳定性：43 道

这一堆里题量最小的两个板块恰恰最需要「外部补课」：**系统设计板块 3 道、容器和 K8S 1 道**——它们不是不重要，而是这份题库的作者不擅长这两块。所以这里的处置是**「换视角 ＋ 换来源」**：

- **系统设计 3 道**：题目本身（「设计一个短链服务」）可以用 10.3 那套走（澄清五问 → 范围表 → 一条请求线 → 四类失败），而题库给不了的那部分（AI 系统的设计面）在第 10.3 章里。
- **容器 1 道**：唯一那道是 4★（唯一的满星板块），但 1 道撑不起一个板块；镜像与编排的账在 8.1 与 8.2 里，而这两章正是「部署」这条线的正解。

监控告警 12 道（≥4★ 6 道）与 8.5 的三条接口几乎一一对应：**症状告警**（按用户看到的坏来报警，不按资源阈值）、**错误预算**（坏了多少还能继续发版）、**演练**（主动去坏一次，验证告警真的响）。这一板块是「留」得最彻底的一堆——它的问法在两种岗位上完全一样，唯一的差别是你举的例子。

容器那 1 道题之外，值得补的还有两件与它同源的事：**健康检查要分两神**（`liveness` 管「要不要重启」、`readiness` 管「要不要接流量」，把后者写成前者会弄出一个重启风暴），以及**批处理与在线路径必须分开**（离线重建索引不能把在线服务的 CPU 吃光——这正是 8.5 的预留余量与「排队先坏」那条因果链的另一面）。

系统设计那 3 道题的处理方式值得单独说一句，因为它是本章唯一一处「题不够、要自己加」：**把一道题当十道练**。做法是拿那三道题里的任意一道，自己往上加约束（用户从一千变成十万、成本砍一半、要支持多租户）——每加一条约束，方案里就会有一处决定跟着变；而那三处变与不变的地方，才是面官真正会追的。这也是第 10.3 章那套（澄清五问 ＋ 范围表 ＋ 一条请求线 ＋ 四类失败）在这里的用法：**它不是一套答题模板，而是一台能造题的机器**。

海量数据处理 18 道（≥4★ 10 道，均 3.61★ 全库最高）是最需要换视角的一块：题库里的答案会讲 MapReduce、Spark 与 Hive，而你的岗位里它的形态是**批处理与向量化**——离线评测集怎么跑（7.1）、数据怎么入库（5.2 的切分与入库）、以及「一万条文档重建索引要多久」这类能算出来的问题（10.3.3 那张 53 分钟的表）。**它的追问几乎总会落在「多久」与「多少钱」两个量上**，而这两样都不需要你懂 Java 的分布式框架。

系统与稳定性那一堆里还有一条不会被写进题库、而面试官很爱问的事：**告警噪音**。它的形状很好认——「每周两百条告警，其中 150 条无人处理」，而它的代价是真正的故障淹没在噪音里。处置与 8.5 的三条接口同源：先把告警从资源阈值改成症状（“用户看到慢了”而不是“ CPU 高了”），再给每一条告警一个行动项（没有行动项的告警就该删掉），最后用一次演练去验它是否真的响。**它考的不是工具，是治理习惯**——而这是题库给不了的。

十条里有一条比其他九条都难补，值得单独点出来：**评测**。它排在第三是因为它同时满足两个条件——**面官几乎必问**（「你怎么知道这次改动没把上一版弄坏」），而**你很难临时桥**（它需要一份数据集、一套口径与一次真跑）。其余九条都可以在一天里补出能听的答案（读一节、背三个数、讲一次），而评测要的是**你手里真的有一个能跑的东西**：200 条离线集、一个越线就拦的门槛、一条说得出参照的数字。这也是本书从第 7.1 章到 10.3.6 反复练同一件事的原因——**它是唯一一件「不能提前一晚准备」的事**。

十条里还有三条是「一旦不会就整场冷场」的那类，值得排在复习的最前面：**评测（第 3 条）**、**成本（第 2 条）**与**词元（第 5 条）**。它们与前三条不完全重合的地方在于：幂等是工程习惯（说一遍就能记住），而这三条各自有一整套账（离线集与门槛、每千次与月账、上下文预算与压缩顺序），而面官只要往下追一问就能听出来你是背了一句还是一直在用。

这张表还有一个用法，与复习顺序有关：**十条里前三条（幂等、成本、评测）是所有追问的收口**。你可以把它们看成「三张底牌」：无论前面聊的是缓存还是队列，后面的第二层追问几乎总会拐到这三样里的一样——「重复了怎么办」（幂等）、「这么贵吗」（成本）、「怎么验证」（评测）。先拿下这三条，剩下的七条才是锦上添花。

## 常见坑

1. **把「Java 写的」当成「与我无关」。** 一份题库的价值在问题，不在栈；去掉栈名还成立的问题，就是你要复习的问题（本章「留」的那一堆）。
2. **舍不得弃。** JVM 那 7 道是 4.2% 的题量，而你投的岗位不问它；把它留在复习清单里，代价是挤掉并发与存储那两堆。
3. **把「换视角」做成「跳过」。** Java 语言核心 13 道里问的是「可变性」「哈希」「字符串拼接」，换成 Python 就是另一批坑（可变默认参数、`is` 与 `==`、f-string 与 `join`）。
4. **按题数排复习顺序。** 题最多的那一堆（68 道）要先于题最少的那一堆（15 道）复习——这是本章最反直觉的一条，而它的依据是难度与答错代价，不是题量。
5. **只会说三个词，不会说区别。** 穿透、击穿、雪崩的顺序是「没有／一个／一片」；说混了，后面的一整段都被降权。
6. **把幂等放在投递侧。** 「让 MQ 保证只投一次」是一句会被追问到墙角的话：**消息可能重复，消费必须幂等**。
7. **说「加缓存」不说失效。** 任何缓存方案都要答两件事：什么时候删、删不掉时读到旧值怎么办。
8. **把语义缓存与键缓存混着说。** 前者按相似度命中，代价是「答错还像对的」；后者最多读到旧值。两者的保险不是同一套。
9. **在协程里做阻塞调用。** 后果不是「慢一点」，而是**所有并发请求一起慢**——发现它的读数是并发 p95 一起抬，而不是单请求延迟。
10. **拿线程解 CPU 密集型。** GIL 之下多线程不提升吞吐（只在 I/O 释放 GIL 的窗口有效）；判据是「瓶颈在解释器还是在等 I/O」。
11. **把索引当成「加上就快」。** 联合索引的最左前缀、覆盖索引避免回表、区分度不够的列不值得建——三条里错一条，索引会变成负担（写入变慢）。
12. **隔离级别只背名字。** 要能说出「读已提交」与「可重复读」的怪象差异，以及它怎么换走并发（第 8.4 章那笔账）。
13. **把向量索引当数据库索引。** 前者是近似的（HNSW／IVF 用召回换速度），换参数就换召回——要有评测集兜底。
14. **死信队列当垃圾桶。** 它的用处是让「处理不了」有一个去处与一个计数；没有它，消息会阻塞分区。
15. **顺序问题答成队列问题。** 顺序只在同一分区（或同一 key）内成立；跨分区的全局有序在多数队列里要付很高的代价。
16. **RPC 只说「用 gRPC」。** 要能说出它与 REST 的两个取舍（契约强 ↔ 好调试、流式 ↔ 通用），以及四种调用类型各用在哪。
17. **每个调用不带 deadline。** 没有超时的调用会变成一场「慢的雪崩」；重试还要有上限与退避（6.3）。
18. **监控告警只讲资源指标。** 正确的起点是症状（用户看到的坏），资源指标是解释而非触发（8.5）。
19. **把「海量数据」理解成要懂大数据框架。** 你的岗位里它的形态是批处理、向量化入库与离线评测；追问几乎总落在「多久」与「多少钱」上。
20. **系统设计只准备一种题。** 题库 3 道撑不起来；要用 10.3 那套（澄清五问 → 范围表 → 请求线 → 四类失败）。
21. **反向索引那一张表背下来当答案。** 它是**补课清单**，不是考点清单：十八个零里每一个都对应本书一章的账，背词没用。
22. **把本书的章号当成面试答案的开头。** 「按书里第 5 篇的说法……」不是答案；章号只是你回去补课的路标。

## 面试视角

- **「你平时用 Python 还是 Java？」** 这是这场面试最先出现、也最容易被答窄的一句。答法照 10.5.1：先说你投的岗位要什么（Python／AI 栈），再主动说明你懂那份 Java 题库里的哪些部分（并发、队列、缓存、索引是共通的），最后举一个「同一个问题两种答案」的例子（比如 GIL 与线程池）。**主动划界比等着被问强。**
- **「消息重复消费怎么办？」** 照 10.5.6 答：消息可能重复、消费必须幂等；幂等键放消费者侧；再补一句死信与重试上限。这一句在两种岗位上完全相同，所以它是你在这场面试里最稳的一道题。
- **「缓存击穿和雪崩的区别？」** 照 10.5.4 答：一个是一个键、一个是一片键；顺手把穿透补上（没有的键），再用一句话收口——三种的解法不是同一种。
- **「为什么 Python 不加线程？」** 照 10.5.3 答：GIL 与三分法（I/O 用 async、CPU 用多进程、混合拆开），最后补一句混合负载最常见的坏形态（协程里的阻塞调用，读数是并发 p95 一起抬）。
- **「你怎么知道改了没有变差？」** 题库里一道都没有（评测 0 道），而面官几乎必问。答法照 7.1 与 10.3.6：离线集先量、越线就拦、灰度里看指标，并把「绿而没验」那种假绿点出来。
- **「你们服务上线怎么发？」** 容器只有 1 道，而这是必答项。答法照 8.1 与 8.2：镜像的层账、构建缓存、发布窗口与灰度，再补一条回滚的判据（回滚要在多少分钟内完成）。

## 本章小结

1. 题库换了体系不等于换了岗位：**换的是栈，不是问题**；逐板块判处置比逐题筛有用。
2. 处置有三个取值：**留**（问题本身一样）、**换视角**（思想一样、例子要换）、**弃**（岗位不问）。
3. **「弃」的依据是岗位口径，不是知识价值**：JVM 那 7 道占全库 4.2%，弃它不是删知识，是把时间挪走。
4. 「留」的判据是**去掉栈名还成立**——成立就留；不成立再看它是不是「换视角」。
5. 十二个板块里处置是留的有七个（并发、队列、缓存、数据库、RPC、监控告警、容器），换视角四个（语言核心、Spring、系统设计、海量数据），弃一个（JVM）。
6. 全库共 165 道、分 12 个板块，平均 3.28★，其中 4★ 及以上共 67 道（40.6%）。
7. 难度分布的主峰在 3★（79 道，47.9%）；**1★ 与 2★ 合计 13 道**，说明它几乎不考背书题。
8. 无标记 6 道：题库自己的标记率是 96.4%，漏标的恰好是最容易的那几道。
9. 三堆是：存储与消息 68 道、系统与稳定性 43 道、并发与异步 15 道；另有换视角 32 道、弃 7 道。
10. **题最多的那一堆不是最该先复习的**：并发那 15 道里 5 道在 4★ 以上（三堆里比例最高），且答错的代价最大。
11. 最大的板块是 MQ 消息队列（35 道），最小的两个是容器（1 道）与系统设计（3 道）——**最小的两块恰恰最需要外部补课**。
12. 平均难度最高的两个板块是海量数据（3.61★）与微服务／RPC（3.56★）：题少而深。
13. **GIL 决定三分法**：I/O 密集用 asyncio、CPU 密集用多进程、混合负载拆开。
14. **在协程里做阻塞调用**是混合负载最常见的坏形态：单请求延迟不变而并发 p95 一起抬。
15. JUC 的四个工具各有 Python 对应物：线程池→线程池／进程池、AQS→锁、volatile→「共享可变状态在哪」、ThreadLocal→`contextvars`。
16. 缓存三件的区别是一句话：**穿透是「没有」、击穿是「一个」、雪崩是「一片」**；三种解法不是同一种。
17. 缓存一致性不选边：两条路都有不一致窗口，处置是**承认窗口、说清多长、用过期与版本把它压小**。
18. **键缓存与语义缓存不是一回事**：判据、失效方式与错的代价都不同；后者要回答「凭什么判断这次命中是对的」。
19. 数据库那一板块按密度复（索引 7 道）而按岗位备（事务 1 道）：**索引的判据、工具、调优三层都要有一句话**。
20. 隔离级别那一句要与第 8.4 章的配额账连起来答：**级别越高，同一份配额支撑的并发越低**。
21. **向量索引是近似的**（HNSW／IVF 用召回换速度），所以「索引选择」在这里同时是一次召回取舍，要有评测集兜底。
22. MQ 三道关：**幂等**（消费侧）、**顺序**（同一分区或 key 内）、**死信**（给「处理不了」一个去处与一个读数）。
23. RPC 的换栈是「进程间怎么说话」：gRPC 与 REST 的取舍、四种调用类型、每个调用带 deadline 与退避。
24. 监控告警 12 道与 8.5 的三条接口一一对应：症状告警、错误预算、演练。
25. 海量数据的追问几乎总落在「多久」与「多少钱」上——那是 5.2 与 10.3.3 的账，不是大数据框架的知识。
26. 反向索引那一张表是**补课清单**：十八个题面里出现 0 次的词，各指本书一章；它与 10.4 的四个盲区合起来说明一件事——**题库给说法，书给做法**。
