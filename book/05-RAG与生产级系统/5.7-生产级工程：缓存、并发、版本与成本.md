# 5.7 生产级工程：缓存、并发、版本与成本

## 本章导读

前六章的东西全部是**一次性的**：给一个问题，拿一份答复，打印一组读数。

上线之后，同一个入口要面对的是**一直跑着**的那件事：同一句话被第二个人问一次、
十个请求同时到、用户不等第二个五秒、提示改了要作废谁的缓存、
一个月下来到底花了多少钱、半夜出了问题靠什么定位。这七件事在前六章的任何一个脚本里
都没有位置——它们不是「答得对不对」的问题，是**「跑得起来、跑得下去」**的问题。

本章把 5.1–5.6 那条管线装成一个**常驻的对象**，并给它加上四件在线才需要的东西：

| 件 | 它修的那条缺口 | 在哪 |
| --- | --- | --- |
| 三层缓存 | 同一句话第二次问还要把嵌入、检索、模型调用重算一遍 | `app/cache.py` |
| 并发与限流 | 没有上界，来多少接多少；同步调用把并发摁成串行 | `Limiter`、`app/serve.py` |
| 版本与成本 | 改一处不知道要作废什么；说不清一次提问花在哪 | `Versions`、`app/cost.py` |
| 观测与降级 | 出问题只能靠猜；上游抖一下整条请求就 500 | `app/observe.py`、`RetryPolicy` |

还有一件**本章刻意不做**的事：**不起 HTTP 服务**。不引 FastAPI、不引 uvicorn、
不开端口。理由不是省事——本树在离线环境下是可测的，而「起一个端口、发一个请求」
在本机不可复现（端口、依赖、容器）。所以本章把一次请求写成一个纯函数
`Service.handle()`，缓存、并发、降级、观测这四件事因此**都能进提交门跑真读数**；
起服务的那一半（ASGI 装配、`/metrics` 端点、容器化）在第 8 篇。这与 3.10 的分工同一条：
**能在门里跑的写进本树，跑不了的写进正文并标注。**

## 学习目标

读完本章，你应当能：

1. 说清**三层缓存为什么是三层**——不是「一个缓存切三份」，而是三层的失效面不同；
2. 写出缓存键的构造原则：**参数进键、版本进戳**，并解释为什么两者不能混；
3. 用一次实测说明**单飞省下的那一笔**（8 个并发同一问题：8 次嵌入 → 1 次）；
4. 说清 SSE 一帧的四个字段与**三条不变量**，并解释心跳为什么必须是注释行；
5. 面对「改一处要作废哪些缓存」时，能画出一张依赖矩阵而不是 `flush_all()`；
6. 把一次提问拆成**四笔可见的支出**，并区分「能算的容量」与「不能算的单价」；
7. 解释「降级必须写在返回值里」，以及为什么**降级结果不许进缓存**；
8. 用一句话说明本章的验收纪律：**任何为了变快而做的改动，先过 5.6 的门。**

## 5.7.1 离线读数与在线服务差在哪

先把缺口量出来。前六章交付的是一条这样的路径：

    问题 → 嵌入 → 两条路检索 → 融合 → 判档 → 生成 → 绑定引用 → 答复

它每一步都对，但每一步都是**为一次调用设计的**。把它连着跑两遍同一批 24 条评测集，
冷跑一遍、开缓存再跑两遍（第一遍填缓存、第二遍才是热跑），账是这样的：

```text $ python scripts/serve_reader.py --offline
层             命中     未命中    过期      命中率   说明
embedding     24      24     0   0.5000   只有「问题 → 向量」这一笔进请求路径
retrieval      0      24     0   0.0000   融合后的候选（片段 ＋ 改写后的 query）
answer        24      24     0   0.5000   整段答复（含质量档与降级标记）

① 冷跑（关缓存）    ：模型调用 19 ｜ 嵌入 48 ｜ 检索 72
② 开缓存的第一遍    ：模型调用 19 ｜ 嵌入 24 ｜ 检索 72（这一遍在填缓存）
③ 热跑（同一批再来）：模型调用 0 ｜ 嵌入 0 ｜ 检索 0
→ 缓存省下（①与③ 之差）：{'模型调用': 19, '嵌入': 48, '检索': 72}
```

三行数字里有**三件事值得停下来看**，而它们都不是「命中率 0.5 所以缓存还行」：

1. **热跑省下的账全部记在答案层**。第三遍的模型调用、嵌入、检索都是 0——
   不是它们「也命中了」，是**整个 `_full_path` 根本没被执行**：答案层的键一命中，
   一次请求在那一个函数里就结束了。所以「检索层命中率 0.0000」不是检索缓存没做好，
   而是**它在这三遍里没有第二次被查的机会**（答案层把它挡在前面了）；
2. **嵌入那 24 次命中发生在填缓存那一遍**，与热跑无关。这一笔是判档带来的：
   CRAG 的 `evaluate()` 要再走两条原始路，于是同一句话被第二次嵌入——
   而第二次命中了第一次刚存下的向量。**它是同一次请求内部的复用**，
   不是「两个用户问了同一句话」；
3. **`0.5000` 这个命中率的分母是三遍合起来的**（48 次查询 = 24 未命中 + 24 命中），
   它不是线上的分布。线上的分母取决于「多少比例的请求彼此重复」，
   而那是一个**业务量**，不是这段代码的性质。

第 3 条是 5.6 那条纪律的第二次落地：**先把分母写清，再读数字。**
一个把这张表读成「我们的缓存命中率是 50%」的人，会据此算出完全错误的成本模型。

可检测最小差异仍然是 `1/24 ≈ 4.2` 个点：命中率的改善小于它，
在本评测集上**看不出来**，也就不该被报成「提升」。

## 5.7.2 三层缓存：参数进键、版本进戳、TTL 管新鲜度

### 为什么是三层，不是「一个缓存切三份」

三层的划分依据只有一个：**失效面不同**。

```python
# app/cache.py —— 三层的依赖表就是本章的失效矩阵（节选）
LAYERS = ("embedding", "retrieval", "answer")

DEPENDS: dict[str, tuple[str, ...]] = {
    "embedding": ("model",),
    "retrieval": ("corpus", "index"),
    "answer": ("prompt", "corpus", "index"),
}
```

- **嵌入层**：键的载荷是**文字**（片或问题），只依赖**嵌入模型**。
  换语料、重切分都不影响「这段文字的向量」——它只跟文字与模型有关；
- **检索层**：载荷是问题 ＋ 检索参数，依赖**语料与索引**。
  片换了、索引换了，同一句话召回的就不同；
- **答案层**：载荷是问题 ＋ 控制位，依赖**提示、语料与索引**。

「改一处就把所有缓存清掉」是常见做法，也是**最浪费**的一种：它顺手丢掉了嵌入层里
真正可复用的那一半——重切分之后，大多数片的文字一字未变。

### 键里放参数，戳里放版本

两件事必须分开，否则一定会错：

- **同一进程内会变的调参**（`k`、`mode`、`depth`、要不要检索）→ 进**键的载荷**。
  它们是「这次查询的参数」，不是「这一版系统的身份」；
- **发布一次才变的东西**（提示正文、语料清单、索引参数、嵌入模型）→ 进**版本戳**。
  它们变了，旧值就**不能再算数**。

```python
# app/cache.py —— 键 ＝ 层 ＋ 载荷 ＋ 这一层依赖的版本
    raw = json.dumps({"layer": layer, "payload": payload,
                      "v": versions.depends_on(layer)},
                     ensure_ascii=False, sort_keys=True, separators=(",", ":"))
    return f"{layer}:{content_stamp(raw, size=16)}"
```

`sort_keys=True` 与 `separators` 那一行看着琐碎，其实是**正确性**：
字典序不固定的话，冷启动两次会算出两个键，命中率凭空掉一半，
而账面上看不出任何异常（它只是「没命中」）。

### TTL 管新鲜度，版本戳管正确性

两者走的是两条不同的路：

- **TTL** 回答「这东西还能用多久」：语料每月更新、答案里的口径会漂，过期就重算。
  它是**概率性的**；
- **版本戳**回答「这东西还算不算数」：提示改了、语料换了，旧值**一定**不对。
  它是**确定的**。

只用 TTL 会留下一个说不通的窗口：改了提示之后的头一个小时里，缓存照样命中旧答案。
只用版本戳则永远不清：一片文档下架了，没人去动版本戳，旧答案就一直留着。

T（TTL）这一侧有一个**照着 Redis 官方文档才对得上的陷阱**：
`EXPIRE` 的文档写明「timeout 只会被删除或覆盖键内容的命令清掉，包括 `DEL`、`SET`、
`GETSET`」。也就是说「先 `SET` 再 `EXPIRE`」的写法只要中间被打断，
这个键就变成**永久的**——而内存实现里读代码根本看不出来：

```python
# app/cache.py —— 写入与设期不可分
        if len(self._data) >= self.max_items and key not in self._data:
            self._evict()
        self._data[key] = Entry(key, value, self.clock() + ttl)
        self.stats.stores += 1
```

另外两处必须分开记的账：

```python
# app/cache.py —— 「看一眼」与「取一次」是两件事
    def peek(self, key: str):
        entry = self._data.get(key)
        return entry.value if entry is not None and entry.alive(self.clock()) else None
```

`peek()` 不记账，`get()` 记账。**这不是洁癖**：写读数时第一版让单飞的复查直接调了
`get()`，于是每层的查询数都多了一次、未命中数也多了一次——三层命中率算出来是
**0.3333**，而真实情况是 **0.5**。错的不是公式，是「什么算一次查询」。

`Stats` 里还单列了一个字段 `expired`：**过期与未命中是两件事**。
都当成未命中，就永远看不出 TTL 是不是设短了。

### 键只认字面相同

```python
# app/cache.py —— 只折空白与句末标点，不做同义归一
    folded = " ".join(text.split())
    return folded.rstrip("？?。.！!")
```

`normalize()` 折三件事：首尾空白、内部连续空白、尾部的句末标点。
它**不做同义归一**——那是 5.4 的活（改写）。理由是一条风险纪律：
一旦缓存层开始猜「这两句是不是一个意思」，它就会在猜错时**静默返回别人的答案**，
而这种错在账面上与命中长得一模一样。

### 单飞：缓存解决「算过了」，单飞解决「都没算过、同时来了」

这是缓存最容易被跳过的一层。冷启动或刚失效的那一瞬间，
一次热门查询会打出 N 次嵌入／N 次模型调用——**并发下最常见的形态不是重复查询，
而是同时未命中。**

```python
# app/cache.py —— 单飞：等待期间别人可能算好了
        lock = self._lock(key)
        with lock:
            if peek is not None:
                fresh = peek()
                if fresh is not None:
                    self.saved += 1
                    return fresh
            return fn()
```

两种做法的对照（8 个线程同时问同一个**冷**问题，数「嵌入真算了几次」）：

```text $ python scripts/serve_reader.py --offline
  没有单飞（对照组）：嵌入实际算了 8 次
  有单飞（本树）：嵌入实际算了 1 次
```

`peek` 那三步是必要的，少一步就有一种隐蔽的错：第二个请求排队拿到锁之后
**又算了一遍**——它手里的 `fn` 是在排队之前构造的，不会自己去看缓存。
这一笔被单飞挡下来的次数也进了账（`single_flight_saved`）：
**省下的调用要能数出来，否则「我们做了单飞」就无法验证。**

## 5.7.3 并发：上界、排队，与那条把并发摁成串行的写法

### 单飞不是「无限并发」

单飞只解决同一键的重复计算。不同键的请求照样同时涌进来，所以还需要一个**上界**。
本树的闸门是 `Limiter(limit=8, queue=32)`：8 个并发在跑、32 个可以排队，
再多的**拒绝**（并记进指标）。只有并发上限、没有排队上限，等于把压力从上游
转成内存——排队中的请求各自占着上下文，来得多就把进程拖垮。

**背压**这个词说的就是这一处：满了之后该等还是该拒，是一个必须写进配置的决定，
而不是「让它自己排队去吧」。拒绝也要记进指标，否则「限流生效了」在账面上看不见，
用户看到的只是一堆失败。

两个信号量是这件事的全部实现，四行里各有一笔账：

```python
# app/serve.py —— 排队满了就拒，而且拒也要记账
        if not self._sem.acquire(timeout=max(timeout, 1e-6)):
            self._slots.release()
            self.rejected += 1
            return False
```

`_sem` 管并发（8 个），`_slots` 管「并发 ＋ 排队」（40 个）；拿到后者没拿到前者，
就是「排上了但还轮不到」。两条路都把 `rejected` 加上一笔，
而 `max_active` 与 `overlapped` 两个数让「真的重叠过」可被断言——
这一条由 `test_限流会拒掉超出上界的请求` 钉住。拒绝的答复也要与兜底分开：
限流给的是 `REJECTED_TEXT`（「请求过多」），**它的处置是重试，与「资料里没有」无关**。

### 异步下最常见的一个性能缺陷

前六章的代码是同步的（嵌入、重排、检索都是普通函数）。把这些同步函数放在
`async` 端点里**直接 `await`**，事件循环会被它们摁住不放，并发退化成串行：

```text
8 个同步任务（各 50ms）：
  直接 await（阻塞事件循环）：   490.0 ms
  丢进线程（to_thread）      ：    60.7 ms（快 8.07 倍）
```

这是**结构量**：用 CPU 睡眠制造的等待，不是真实网络延迟。
要看的不是毫秒，是两个比值与「重叠了几层」——真实服务里这个差别还要大，
因为真正的时间花在网络往返上。

而「丢进线程」也有上界，而且是**默认就有的**：

```text $ python scripts/serve_reader.py --offline
默认线程池上限：min(32, CPU+4) ＝ 20（本机 CPU 16；实测 max_workers ＝ 20）
```

于是有一个必须写进文档的结论：**超过这个数的请求会排队，而它的失败模式不是报错，
是变慢。** 慢下来的请求会占着连接更久，于是队列更长——这是「雪崩」的字面起点。
知道自己有多少个线程，和知道自己有多少个并发，是同一件事的两半。

## 5.7.4 流式：一帧四个字段，三条不变量

用户不等第二个五秒。于是回答要在**生成的过程中**就往外发。
这一步改的不是 UI，是**接口的形状**：返回值从一个字符串变成一条有序事件流，
而事件流有它自己的契约——谁分配编号、断了怎么办、重连补什么、什么算「发完了」。

### 契约来自规范，不是来自某个库

字段只有四个（MDN 的 event stream format 一页写完）：

| 字段 | 作用 | 本树怎么用 |
| --- | --- | --- |
| `event` | 事件名，客户端按名字监听 | `sources` / `token` / `done` / `error` |
| `data` | 载荷；**多行要写成多行 `data:`**，客户端自动用换行拼回去 | JSON |
| `id` | 事件编号，浏览器把它存成 `Last-Event-ID` | 严格递增的整数（从 1 开始） |
| `retry` | 重连间隔（毫秒，**整数**） | 首帧给一次，之后不再重复 |

三条语法细节，任何一条弄错都会让客户端「静默少东西」：
一帧以空行结束（`\n\n`）；冒号开头的行是注释；`retry` 不是浮点数
（`1500.0` 会被整条忽略，而客户端依旧按默认间隔重连——与「没写」长得一样）。

```python
# app/stream.py —— 多行 data 逐行加前缀，而不是塞一个换行进去
    for line in frame.data.split("\n"):
        lines.append(f"data: {line}")
    return "\n".join(lines) + "\n\n"
```

### 心跳必须是注释行

本树把心跳写成 `HEARTBEAT = ": ping"`，并在代码里钉了一句最容易忽略的契约：

```python
# app/stream.py —— 心跳不碰 next_id
    def heartbeat(self) -> str:
        """心跳。**注意它不碰 `next_id`**——这是本章那条最容易被忽略的契约。"""
        return comment("ping")
```

把心跳做成一个真正的 `event: ping` 会怎样：它**推进编号**，
于是断线重连时客户端拿着 `Last-Event-ID=7`（其实是心跳），服务端从 8 开始补——
补的却是**正文的第 3 段**。顺序看着对、编号也对，但少了一段。

### 三条不变量，写成能报错的检查

```python
# app/stream.py —— 服务端自己解自己的流（节选）
    for prev, cur in zip(ids, ids[1:]):
        if cur <= prev:
            issues.append(f"编号没有严格递增：{prev} → {cur}")
    if len(set(ids)) != len(ids):
        issues.append("同一编号出现了多次（补发重复）")
    if not events or events[-1] != "done":
        issues.append("流没有以 done 结尾")
```

读数里，一条真回答被发成这样：

```text $ python scripts/serve_reader.py --offline
发布：来源 3 片 ｜ 正文 6 段 ｜ 心跳若干 ｜ 事件帧 8 个
三条不变量（编号严格递增 / 以 done 结尾 / 心跳不带编号）：全部通过

断在第 2 帧：补发 6 帧；拼接后正文段数 6（应等于 6）
不重不漏：True ｜ 补发前已有 1 段

  乱序（编号倒退）          → 编号没有严格递增：3 → 2
  重复（同一编号两次）        → 编号没有严格递增：2 → 2；同一编号出现了多次（补发重复）
  缺 done            → 流没有以 done 结尾
```

三条坏形态**各自被某一条规则抓到**，而且抓它们的不是人眼，是 `check()`。
这一处与 5.5 的「引用核对」是同一种做法：**被检查的一方不能自己证明自己。**

### 按号补发要靠服务端留一小段

`Last-Event-ID` 只是客户端报出来的「我收到几号」。要真的补齐，
服务端得**留着刚发过的那几帧**（本树留 64 帧）：

```python
# app/stream.py —— 补齐 last_id 之后的所有事件
    def replay(self, last_id: int) -> tuple[Frame, ...]:
        """补齐 `last_id` 之后的所有事件。**不重不漏**是它的全部判据。"""
        return tuple(f for f in self.frames if f.id > last_id)
```

留着不是「缓存优化」，是**可正确性的前提**：不留就只能从头发，
于是客户端拿到重复内容，而重复在拼接后的文本里表现为「同一句话说了两遍」——
它不像报错那么显眼。

最后一条设计上的取舍也要写明：**先发来源、再发正文**（用户看到「命中了哪几篇」，
比干等一个转圈可信得多），而它有一个代价——**来源一旦发出就收不回来**。
所以拒答判定必须发生在**发来源之前**，这正是 5.5 把判据放在生成之前那条设计
在流式下的延伸。

### 首字时长：流式下唯一用户可感的那个指标

流式把用户感知的指标从「总耗时」拆成了两个：**首字时长**（第一个 `token` 帧到达的时间）
与总时长。用户抱怨「慢」时，绝大多数时候抱怨的是前者。
本章**不报这个数的毫秒**，理由与 5.7.3 那 490.0ms 同一条：本树没有真实网络，
报出来的毫秒是结构量。能给形状：首字时长 ＝ 首帧之前的检索与判档 ＋ 模型吐第一个字的延迟，
所以 5.7.2 的缓存与 5.7.8 的重试预算**都直接影响它**——一个把首字拖到十秒的重试预算，
等于把流式的全部好处抵消掉（用户看不到任何东西的时间更长了）。

## 5.7.5 版本：改一处要作废哪几层

把依赖矩阵跑成读数，就是下面这张表（每层各放一条记录，报的是**清掉了几条**）：

```text
改动              嵌入    检索    答案   说明
换提示正文            0     0     1   只有答案层的值依赖提示
换语料              0     1     1   片换了，检索与答案都得重算；嵌入是「文字→向量」，与语料清单无关
换索引参数            0     1     1   索引换了，同一句话召回的就不同
换嵌入模型            1     0     0   向量换了，前面所有缓存都失去意义
```

```python
# app/cache.py —— 换版本时按依赖矩阵作废，而不是清空
        old, self.versions = self.versions, versions
        cleared: dict[str, int] = {}
        for layer in LAYERS:
            if old.depends_on(layer) == versions.depends_on(layer):
                cleared[layer] = 0
                continue
            cleared[layer] = self.tiers[layer].invalidate()
        return cleared
```

三处值得停一下：

- **换语料不清嵌入层**。这不是省事，而是事实：嵌入算的是「文字 → 向量」，
  与「语料清单里有哪几片」无关。重切分之后大多数片的文字一字未变，
  它们的向量可以原样复用；
- **换嵌入模型全清**。向量本身换了，后面所有基于向量的缓存都失去意义——
  这是四行里唯一「清掉非本层」的一行，也是唯一合理的越层作废；
- **`set_versions()` 返回每层清掉的条数**。作废动作必须留下账：
  否则「这次发布的影响面」只能靠猜。

### 版本戳要用内容算，不能用标签算

```
只改正文不改标签 → 键一样吗？**一样（旧答案被复用）**
用内容算戳        → 键一样吗？**不一样（正确失效）**
```

第一行是一次**真实事故的复述**：改的是提示正文，忘了改 `"v3"` 这样的标签，
于是「标签没变 → 戳没变 → 旧答案被复用」，而复查时两边都「看着对」。
可操作的判据只有一句：**能给内容算哈希的地方，就不要用人工维护的编号。**
这与 5.6 那条「这份数字是算出来的还是抄过来的」是同一个问题。

前面六章的顺序在这里也变成一条纪律：**提示、语料、索引三者本来就该一起进版本戳**。
5.5 的提示版本号、5.2 的切分参数、5.3 的索引参数，在离线时各自是实验变量，
上线后它们是**同一个东西的三个字段**。

### 一件本章不做的事：A/B 分流

接在版本戳后面很自然的下一个问题是「新提示先放给 5% 的人试试」。
本章**不做**，而理由不是省事：A/B 分流要先回答「按什么分桶」——
随机的话，同一个用户两次请求可能落在两个版本上，反馈混成一锅；
按用户哈希分桶才是可解释的做法。而它一旦上线，版本戳就不再是「一个」
（同一时刻有两个值），缓存键、成本账、观测维度全都要能带上「哪一版」。
这是**模型分流**那一层的活，属第 6 篇（6.4 的成本与分流）。
本章给出的是一条边界：**版本戳解决「这一版是谁」，分流解决「这两版同时在跑」——
后者是前者的下一步，不是它的替代。**

## 5.7.6 成本：一次提问的四笔账

前六章数过汉字（`lint` 的有效字）、数过词元（3.1 的词元账）、数过调用次数
（5.4／5.5 的「模型调用 24」）。本章加一层：把一次提问拆成**四笔可见的支出**。

```text $ python scripts/serve_reader.py --offline
冷跑（首次提问）：
    嵌入：1
    检索：3
    重排对数：0
    模型调用：1
    提示汉字：230
    输出汉字：134
热跑（同一句再问一次）：
    嵌入：0
    检索：0
    重排对数：0
    模型调用：0
    提示汉字：0
    输出汉字：0
```

**「检索 3」是这一节最值得看的一个数**：一次提问明明只检索一回，为什么记 3 笔？
因为 CRAG 的判档要再走两条原始路（要的是**分数**，而缓存里存的是**融合后的片**），
所以 `retrieve_calls += 2`。**判档不是免费的**——它换的是质量，付的是检索。
账目分得开（`test_判档不是免费的且账目分得开`），这个代价才看得见。

### 不折算成钱

本章**只报笔数与字数**，不折算货币。理由是 5.6 那条纪律的搬家：
**单价随时会变，而且带阶梯与缓存折扣**（各家对「缓存命中的输入词元」与
「新输入词元」不是一个价）。一个写死在正文里的「每次 0.003 元」三个月后就是错的。
**月成本表一条都不引**：它连测试语料规模与单价都没说，乘不出来。
读者拿自己那份价目表去乘即可。

### 容量：能算的与不能算的分开写

```text $ python scripts/serve_reader.py --offline
容量（DAU 1 万、人均 20 次、5 万文档 × 20 片 × 1024 维）：
    峰值 QPS：11.57
    向量存储 GB：4.096
    索引内存 GB：5.325
    日志 GB：12.288
    带宽 KB/s：578.7
```

四个数都是**纯算术**，与厂商无关：日查询量 → 峰值 QPS；
文档量 × 片数 × 维度 × 4 字节 → 向量存储；再乘索引膨胀系数（HNSW 约 1.3）→ 内存；
日查询量 × 日志大小 × 保留天数 → 日志盘。**不能算的**是单价、折扣与运维人力。

有两处默认值必须写进配置而不是藏在代码里：**峰值系数 5**（它不是业界惯例，
是一个要说明理由的参数——企业内部工具的实际峰谷比常在 3–10 之间）；
以及**向量按 4 字节算**（半精度能砍一半，但它会改变相似度排序，
那是 5.3 的边界之外，不能替读者做这个决定）。

最后一句提醒要写在数字旁边：**算出来的 5.3GB 不等于「买一台 8G 机器就够了」**——
还有模型权重、操作系统与峰值余量。

## 5.7.7 观测：日志、指标、追踪各管什么

3.9 已经建过一层（span 树、四类指标、按工具与角色分维度）。那一层量的是**一次运行**；
这一章要量的是**一直跑着的服务**，差别有三处。

### 日志要能被机器筛

3.9 的日志是给人读的句子；在线日志必须是「事件名 ＋ 键值对」——
想查「哪几个请求慢」时，`grep 慢` 是没有用的。本模块一行一个 JSON，
事件名在前（`rag_query_done`），字段跟在后面。还有一条约定：
**异常一律带 `error_type`**——只有 `error` 字符串的话，「超时」与「解析失败」在日志里
长得一样，而它们的处置完全不同。

### 指标的命名有官方规则，而「不许高基数标签」要写成代码

Prometheus 的指标与标签命名文档里有三条：累加计数用 `_total` 后缀、
单位用基本单位（秒而不是毫秒）并写进名字、**标签不能是用户 ID 这类无界取值**。
第三条在本树里落成了**会抛异常的代码**：

```python
# app/observe.py —— 标签白名单：加一个键就是一次决策
NAMESPACE = "zhizhou_rag"

ALLOWED_LABELS = frozenset({"status", "layer", "kind", "phase", "outcome"})
```

文档原话是「**每个键值组合都是一条新的时间序列**」。这条规矩写在文档里没人看，
写进代码就一定看得见：

```text
拒绝： zhizhou_rag_per_user_total 的标签 'user_id' 不在白名单里——
      高基数标签会把监控自己打挂（可用：['kind', 'layer', 'outcome', 'phase', 'status']）
```

代价是「按用户统计」在指标层做不了，而**这正是重点**——它本来就该在日志或追踪里做
（那里按条付费、可采样、能删）。把两者混起来的典型后果是：指标基数爆炸，
监控内存打满，而**最先挂掉的往往是监控本身**，于是故障时你看不到故障。

指标名与单位的三条规则在输出里是自证的：

```text
# TYPE zhizhou_rag_queries_total counter
zhizhou_rag_queries_total{outcome="degraded"} 1
zhizhou_rag_request_duration_seconds_count{outcome="ok"} 2
zhizhou_rag_request_duration_seconds_sum{outcome="ok"} 2.22
zhizhou_rag_request_duration_seconds_bucket{le="2.0",outcome="ok"} 2
```

`_total` 是计数、`_seconds` 是秒（不是毫秒）、直方图给的是 `_count`／`_sum`／
`_bucket` 三条线——**单位写进名字**这件事，在一个只有名字与数字的文本格式里
是唯一能防止「三个人各按各的单位读数」的办法。

而日志那一侧，一行 JSON 长这样：

```text
{"cached": false, "error_type": "TimeoutError", "event": "rag_query_done", "model_calls": 3, "outcome": "degraded", "trace_id": "t-7f3a", "ts": 1789547374.07}
```

「哪几个请求慢」于是变成一次筛选（`outcome == "degraded"` 或 `model_calls > 1`），
而不是一条条读句子；`error_type` 让「超时」与「解析失败」分开——
它们的处置完全不同，而在只有一句 `error` 字符串的日志里长得一模一样。

### 追踪把请求内部串起来

一次请求一个 `trace_id`，检索／重排／判档／生成各段各一行，
`sum(各段) ≈ 总耗时` 是一个可断言的不变量。
**OpenTelemetry 的 GenAI 语义约定**已经在 3.9 落地，
本章不重写那套字段，只把它接到在线服务上。

采样与分级沿用 3.9 的形状（全量 7 天／详细 1% ＋ 错误 100%／审计 180 天），
本章不重复它的阈值讨论。

## 5.7.8 降级：三档，且必须写在返回值里

「上游抖一下，整条请求就 500」是在线服务最常见的一种脆弱。本章的三档降级是：

| 档 | 触发 | 动作 | 用户看到 |
| --- | --- | --- | --- |
| 重试 | 模型调用抛异常 | 最多 3 次、指数退避、**带抖动**、总时长受预算约束 | 慢一点，答对 |
| 带警告继续 | 检索失败 | 当作「没有知识库」，走直答 | 答得出就答，`degraded` 里有记录 |
| 兜底文案 | 重试用尽 | 返回明确的服务不可用提示 | 知道该等一会儿再试 |

```python
# app/serve.py —— 有界重试的退避，必须带抖动
        base = min(self.backoff * (2 ** attempt), self.cap)
        return round(base * (0.5 + 0.5 * jitter()), 4)
```

```python
# app/serve.py —— 降级进返回值，不只进日志
            except Exception as exc:
                degraded.append(f"检索失败：{type(exc).__name__}")
                chunks = None                      # 当作「没有知识库」，走直答
                self._bump("degraded", kind="retrieve")
```

五处设计上的判断，每一条都能指向一个具体的失败：

1. **「有界」是硬要求**。没有上限的重试会把一次上游抖动放大成一场雪崩
   （每个请求都在重试，上游看到的流量是原来的三倍）。三个数都要有：次数、退避、
   以及**放弃时的动作**（这里是降级，不是把异常抛给用户）；
2. **必须加抖动**。不加的话所有请求同时重试，上游刚缓过来就被第二波打回去；
3. **预算检查在睡之前**。不然「重试 3 次 × 退避 4 秒」会让一次请求卡 12 秒，
   而连接早就断了；
4. **重试也是钱**。`cost.model_calls` 记的是**尝试次数**，不是成功次数。
   报「平均 1.0 次调用」而实际平均 1.3 次，是把成本算低了一档；
5. **降级必须出现在返回值里**（`Reply.degraded`）。只写日志的降级，
   调用方与读数脚本完全看不见它发生过。

### 兜底文案不是拒答

两句话必须分开，而且第 5.5 章已经给过其中一句：

- `NO_ANSWER`（5.5 的拒答）是**业务结论**：「资料里没有」——用户该去改问题；
- `FALLBACK_TEXT`（本章的兜底）是**运维状态**：「服务暂时不可用」——用户该等一会儿。

混成一句的后果是：用户去改问题，而这时候该做的是等一会儿再试。

### 降级结果不许进缓存

```python
# app/serve.py —— 降级结果不进缓存
            if use_cache:
                value, hit = self.cache.get_or_compute(
                    "answer", payload,
                    lambda: self._full_path(question, session, trace, cost),
                    store_if=lambda p: not p.degraded)     # **降级结果不进缓存**
```

一次上游故障换来的兜底回答，如果被当成正常结果缓存下来，故障恢复之后
用户还会继续吃旧的兜底文案——而且**看着像缓存命中**，没有任何报错。
这条由夹具守住（`降级结果不进缓存`：`stores ＝ 0`），
它与 5.5 那条「降级文案身上不能长引用」是同一族：**故障的痕迹不许被当成正常产物。**

## 5.7.9 性能与门：快不能抵错

本章给自己定了一条纪律，它是 5.6 那条「先问分辨率」的直接推论：

> **任何为了变快而做的改动，必须先在 5.6 的门里过关。**

所以 `Service` 同时留着两条路（`use_cache=True/False`），拿同一批 24 条评测集跑两遍，
逐条比：

```text
24 条里真的走了检索的：24 条
两条路径的候选逐条相同：24/24（缓存没有换掉候选）

同一分母（18 条需要召回的题）上的命中率：
  文档级（任意一片）：服务 1.0000 ｜ 直接调 1.0000
  片级（那一片）    ：服务 0.8333 ｜ 直接调 0.8333（未命中：E01, E07, E13）

答案命中：0.9444（17/18，分母是全部要求召回的题）
拒答四格（漏拒／误拒）：1／0（E17）
引用自称与绑定不符：19 条（对外答复已按绑定改写）｜降级过的请求：0 条
对外答复（绑定后）再查一遍：19 条，引用全部通过
```

**四项读数与 5.6 逐项相同**：文档级 1.0000、片级 0.8333、答案命中 0.9444、
四格 1／0。装上一层缓存、一层限流、一层观测之后，**系统还是那一个系统**。
这就是「快不能抵错」的可执行形式——不是一句口号，是一组必须相等的数字。

### 「引用自称与绑定不符 19 条」不是「引用质量 19/24」

这一行的名字改过一次，值得记为什么。它数的是**离线替身自己标的编号与代码算出的依据
不符**（5.5 的 `claimed` 那一路），而不是发出去的答复不合格——
对外答复用的是**绑定后的正文**：把发出去的 19 条再查一遍 `check_citations`，
**全部通过**。所以真正的读数是「让模型自证这条路有多不可靠」，
而它是 5.5 那条结论的第三个证据。

一个名字会改变一个数字的含义，这与 5.6 的「分母要写在表里」是同一件事：
**读数行的措辞也是口径。**

### 两处「改一个数、什么都不动」与一处「换一个开关、掉一半质量」

```text
判档时多看两片会怎样（judge_depth 5 对 3）：
  judge_depth=3 → 漏拒 1／误拒 0
  judge_depth=5 → 漏拒 1／误拒 0
```

判档深度取 3 还是 5，四格一格没动。**但「不动的参数」照样要写进配置**——
本树默认跟 `k` 走。它不动，是因为这批题（置信度两极，中间那档几乎没有落脚点）；
换一批题它就会动，而到那时没人记得它默认是几。

另一边是本章最重的一条实测：

```text
把 5.5 的「按需检索」接成默认值会怎样（control="offline"）：
  真的走了检索：9/24 条
  答案命中：0.3333（6/18）—— 对照总是检索的 0.9444
  拒答四格（漏拒／误拒）：0／3
```

省下 15/24 次检索是真的，**丢掉的一半质量也是真的**。原因可复算：
5.5 那套按需规则是**写在代码里的正则**，它不是模型，认不出
「发布说明有哪三个状态」这种没有显式关键词的问法——于是该检索的题被判成不检索，
答不出来就拒答（误拒从 0 涨到 3）。所以线上默认是 `control="always"`，
而 `offline` 只能是一个**实验开关**。**这一对数字必须一起看**：
只报「省了 62% 的检索调用」是一份误导性的月报。

## 5.7.10 知舟接线

### 加了什么

### 接口契约

对外的面只有一个入口与一个返回值：

```python
# app/serve.py —— handle 的四步顺序
    def handle(self, question: str, *, session_id: str = "",
               use_cache: bool = True) -> Reply:
        """一次请求。四件事按顺序发生：**限流 → 缓存 → 完整路径 → 观测**。"""
```

`Reply` 里有四个字段是本章新加的**在线语义**：`cached`（命中的层，按顺序）、
`degraded`（降级记录）、`outcome`（`ok` / `degraded` / `rejected`）、
`cost`（四笔账）。前六章的返回是「答复 ＋ 引用 ＋ 质量档」，
本章的返回多了一层：**这一次请求在服务里的处境。**

装配入口与 5.1 起一贯的形状一致：

```python
# app/serve.py —— 版本戳从内容算
        versions = Versions.from_content(prompt=prompt, corpus=corpus_text,
                                         index=index_text, model="hashed-embedder-v1")
```

它换来的是「不改 `retrieve.py` 一行」——正是 5.2–5.6 那些代码块与正文

2. **两条路径的候选逐条相同（24/24）**——缓存不许换掉系统给出的候选；
3. **热跑的模型调用、嵌入、检索都是 0**——省下的账要能指认到具体哪一笔；

## 常见坑

1. **把命中率当成业务指标**。本章那张表的分母是「三遍合起来的 48 次查询」，
   线上命中率取决于「多少比例的请求彼此重复」——那是业务量，不是代码性质；
2. **把「检索层 0.0000」读成「检索缓存没用」**。热跑时整个 `_full_path` 被答案层挡掉了，
   检索层根本没有第二次查询的机会；
3. **只设 TTL，不设版本戳**。改了提示之后的头一个小时里，缓存照样命中旧答案；
4. **`SET` 之后再 `EXPIRE`**。`EXPIRE` 的文档写明 TTL 会被 `SET` 这类命令清掉，
   中间被打断就变成永久键；
5. **版本戳用标签算**（`prompt="v3"`）。改了正文忘了改标签，旧答案被复用，
   而复查时两边都「看着对」；
6. **作废时一把清空**。嵌入层里大多数片的文字一字未变，全清等于白扔；
7. **不做单飞**。冷启动或刚失效的瞬间，一次热门查询打出 N 次嵌入／N 次模型调用；
8. **单飞里少了 `peek` 复查**。排队拿到锁的第二个请求会**又算一遍**；
9. **`peek()` 与 `get()` 混用**。复查用 `get()` 会把一次查询记成两次，命中率从 0.5 变成 0.3333；
10. **过期与未命中合记一个数**。合一之后就永远看不出 TTL 是否设短了；
11. **在 `async` 端点里直接 `await` 同步函数**。事件循环被摁住，并发退化成串行
    （本树实测 490.0ms 对 60.7ms）；
12. **以为线程池是无限的**。默认上限 `min(32, CPU+4)`，超过就排队；
    它的失败模式不是报错，是变慢；
13. **限流只设并发上限、不设排队上限**。压力从上游转成了内存；
14. **心跳写成真事件**。它推进 `Last-Event-ID`，断线重连时补的却是一段正文，
    顺序与编号都「看着对」；
15. **`retry` 写成浮点数**（`1500.0`）。规范规定非整数则整个字段被忽略——
    它不报错，它只是没生效；
16. **不做按号补发，续传就从头发**。客户端拿到重复内容，
    而重复表现为「同一句话说了两遍」，不像报错那么显眼；
17. **先发来源、后判拒答**。来源发出去就收不回来，用户已经看见那几片了；
18. **降级结果进了缓存**。故障恢复之后用户继续吃兜底文案，而且看着像缓存命中；
19. **降级只写日志、不写返回值**。调用方与读数脚本完全看不见它发生过；
20. **重试不设上限、不加抖动**。一次上游抖动被放大成雪崩；
21. **记账只记成功次数**。重试也是钱，`平均 1.0 次调用` 会把成本算低一档；
22. **把单价写进正文**。它带阶梯与缓存折扣，三个月后就是错的；
23. **用高基数标签做指标**（`user_id`）。指标基数爆炸，最先挂掉的往往是监控本身；
24. **日志写成给人读的句子**。想筛「哪几个请求慢」时，`grep 慢` 是没用的；
25. **忘了「算出来的内存 ≠ 买机器的规格」**。还有模型权重、操作系统与峰值余量。

## 面试视角

**问：缓存该按什么分层？**
答：按**失效面**，不是按数据大小或读写频率。嵌入层只依赖嵌入模型
（换语料不动它），检索层依赖语料与索引，答案层还依赖提示。
分层的直接好处是「改一处只作废该作废的」：换语料时那 4.096GB 的向量不用重算。
我手上有一张依赖矩阵的读数表可以对照。

**问：TTL 和版本戳有什么区别？**
答：TTL 管**新鲜度**（概率性：这东西还能用多久），版本戳管**正确性**
（确定性：这东西还算不算数）。只用 TTL 会留下「改了提示之后的一个小时里
还在命中旧答案」这个窗口；只用版本戳则永远不清。
而且戳必须**用内容算**——用 `"v3"` 这样的标签算，改了正文忘了改标签就会静默复用旧值。

**问：并发下最常见的性能缺陷是什么？**
答：在异步代码里直接 `await` 同步函数，事件循环被摁住，并发退化成串行。
本树同一批 8 个 50ms 的同步任务，直接 `await` 是 490.0ms，丢进线程是 60.7ms。
但「丢进线程」也有上界（默认 `min(32, CPU+4)`），超过就排队——
它的失败模式不是报错，是变慢。

**问：为什么需要单飞？**
答：缓存解决的是「算过了」，单飞解决的是「都没算过、同时来了」。
冷启动或刚失效的瞬间，8 个并发同一问题会打出 8 次嵌入；有单飞时是 1 次。
实现上有一处细节：等待者拿到锁之后要**复查一次缓存**，
否则它手里的计算闭包是在排队之前构造的，会又算一遍。

**问：SSE 的心跳为什么必须是注释行？**
答：因为 `id` 字段是客户端的 `Last-Event-ID` 游标。心跳要是真事件，
它就会推进编号，重连时服务端按那个编号补的却是一段正文——
顺序对、编号对，但少了一段。注释行（冒号开头）客户端直接忽略，不占编号。

**问：怎么做性能优化又不把质量搞坏？**
答：先立一条验收线。本章拿同一批 24 条评测集跑「开缓存」与「关缓存」两条路，
要求片级命中 0.8333、答案命中 0.9444、拒答四格 1／0 **逐项相同**——
装了几层缓存与限流之后，系统必须是同一个系统。
一个反例就在同一章里：把 5.5 的按需检索接成线上默认值，检索调用省了 62%，
而答案命中从 0.9444 掉到 0.3333。

## 本章小结

- 三层缓存的划分依据是**失效面**；**参数进键、版本进戳**；
  TTL 管新鲜度、版本戳管正确性，两件都要；
- 单飞补上缓存管不着的那个窗口（**都没算过、同时来了**）；
  8 个并发同一问题：8 次嵌入 → 1 次；
- 并发上界要成对设：**并发上限 ＋ 排队上限**，满了要拒并记账；
  线程池的默认上限是它的隐藏天花板；
- 流式的契约来自规范：四个字段、三条不变量；
  **心跳不带编号**，**按号补发不重不漏**，**先来源后正文且拒答在发来源之前**；
- 版本失效写成依赖矩阵（换语料不清嵌入层），**戳用内容算**；
- 成本只报笔数与字数，不折算钱；容量能算的与不能算的分开写；
- 观测三件各管一段：日志要能筛、指标不许高基数、追踪要能串起来；
- 降级三档，**必须写在返回值里**，且**降级结果不许进缓存**；
- 验收纪律一句话：**任何为了变快而做的改动，先在 5.6 的门里过关。**
