# 5.2 文档解析与切分策略

## 本章导读

上一章结尾留了一条难看的读数。问「知舟的发布说明必须包含哪几段？」：

```
发布规范#0  19.79   每一篇发布说明必须包含下列四段，缺一段即为不合格：      ← 25 字
发布规范#1   1.40   1. 变更摘要：… 2. 影响面：… 3. 回滚方式：… 4. 验证步骤…  ← 104 字
```

装着「回滚」的是 `#1`，可它排第 5——**文档召回了，片没到，而答案是半句。**
检索器没有错。错的是切分：按空行切，那句「引子」被单独切成了一片，
而提问的那半句话恰好与它逐字重合。**引子拿走了分数，内容被留在门外。**

这就是本章要修的缺口。它要回答三个问题，顺序不能换：

1. **读进来**：企业里的资料不是 Markdown，是 PDF、Word、PPT、扫描件、表格、邮件……
   怎么知道一个文件是什么、该交给谁读、读不出来时怎么办；
2. **洗干净**：抽取出来的文本带着页码、控制字符、全角符号、编码错误——
   哪些能洗掉，哪些洗不掉，洗不掉的该怎么办；
3. **切开**：这是全章的重头。四代切法各在「哪里落刀」上做一个选择，
   而本章会把它们**放在同一份语料、同一个检索器上**跑一遍，
   看那条「答案片排第 5」的读数会不会回到第 1——以及**换来了多少别的代价**。

四组读数（全部本机可复现，脚本见 `zhizhou-v5/scripts/split_reader.py`）：

| 组 | 问题 | 量到的数 |
| --- | --- | --- |
| ① 入口 | 扩展名与真实格式对不上时能判对吗 | 七个夹具全判对；**四种「读不出」分别被拦下**（加密／扫描件／超限／无引擎） |
| ② 切法 | 换一种切法能换来什么 | 答案片从**第 5 回到第 1**；但**四代切法在这一列上全是第 1** |
| ③ 重叠 | 重叠的代价是什么 | 入库量 **100.0% → 291.5%**；且后两片**整片都是前一片的尾巴** |
| ④ 清洗 | 五种噪声各被哪一步带走 | 四步管线各治一种；**替换字符谁都带不走** |

读完这一章，你应该能回答一个具体问题：**「我调了切分」这句话，怎么变成一组能被别人核对的数？**

## 学习目标

- 能说清**为什么格式检测要看魔数而不是扩展名**，并说出靠扩展名会栽在哪三种场合；
- 能列出八条解析路各自最容易丢的东西，并说清 **PDF 为什么要分三条路**（文本层／表格／扫描件）；
- 能说清四种「读不出」（加密、扫描件、超限、没有解析器）为什么要**分别报**，
  以及合并成一个异常会让谁去修错地方；
- 能按顺序说出清洗的四步与页码那一步，并解释**为什么 `U+FFFD` 谁都不该动它**；
- 能写出四代切法（定长／滑动／递归／结构感知）与父子片，并说清每一代**在哪里落刀**、
  代价是什么；
- 能解释**为什么「答案片排名」这一条读数不足以选切法**，以及要多量哪两条（坏表与入库量）；
- 能解释**「每一片都必须是原文的连续子串」**这条不变式为什么可机检、值得进测试。

## 前置知识

- **5.1 的四阶段与那条分界线**：本章从头到尾在**离线那一侧**（数据准备 ＋ 索引构建的前半段）。
  它的错误是批量的——切分策略错了，库里每一片都错；

  「异常要能说清下一步做什么」的直接应用；批量解析的并发沿用 1.7 的线程池边界；

  它的产物（片）是 5.3 要嵌入、5.4 要检索的东西。

## 5.2.1 先看清那条缺口是怎么来的

把 5.1 的 `split_paragraphs` 换成任何一种有尺寸上限的切法，答案片都会回到第 1——
可**为什么**是空行切法吃亏？把那份文档按空行摊开就清楚了：

| 片 | 内容 | 字数 | 与提问的字面重合 |
| --- | --- | ---: | --- |
| `发布规范#0` | 每一篇发布说明必须包含下列四段，缺一段即为不合格： | 25 | **极高**（提问原句几乎就是它） |
| `发布规范#1` | 1. 变更摘要：… 2. 影响面：… 3. 回滚方式：… 4. 验证步骤：… | 104 | 低（除了「包含」几乎对不上） |
| `发布规范#2` | 每篇发布说明正文不少于 120 字…只有「已发布」状态可以对外引用。 | 82 | 低 |

三片里，**只有第二片装着要答的东西，也只有第二片不重复提问的说法**。
而 5.1 的检索器是字符 2-gram ＋ BM25：`#0` 短、字字命中、`idf` 高，分数自然被它拿走。

这类失败有个共同形状：**「一句引子 ＋ 一串条目」被切在了引子与条目之间。**
它不是「检索不行」，也不是「模型不行」——**是切分把一句完整的话劈成了两片，
而提问那半句落在前一片上。**

> **一个必须提前说清的边界。** 「换一种切法这件事就没了」这句话本章**证明不了**。
> 本节的语料只有六份文档、共 1,718 字，四条问题里也只有一条踩到这个坑。
> 换一批文档、换一个检索器，谁排第几都会变——所以本章的读数**只用来发现和定位问题**，
> 不用来下判决。判决要等 5.6 的评测集。

## 5.2.2 第一道关：先判格式，再看内容

企业资料进到这一层时，第一个问题是「**这是什么文件**」。最省事的做法是看扩展名，
而扩展名有三种场合会骗人：

1. **用户改了名。** 把 PDF 存成 `报告.txt` 是合法操作，系统不会拦；
2. **上游没给后缀。** 对象存储里的键、邮件附件、接口直传的流都可能没有后缀；
3. **内容与后缀本来就不是一回事。** 一份 `.md` 里装 HTML 导出结果，太常见了。

所以这一层看**魔数**：每种标准格式的开头几个字节是固定签名，改不了。

```python
# app/split.py —— 魔数表：只看开头几个字节，不看文件名
MAGIC: tuple[tuple[bytes, str], ...] = (
    (b"%PDF-", "pdf"),
    (b"\x89PNG\r\n\x1a\n", "png"),
    (b"\xff\xd8\xff", "jpg"),
    (b"PK\x03\x04", "zip"),
)
```

`PK` 那一行是个例外，值得单独说：`.docx`／`.pptx`／`.xlsx` 都是 ZIP 容器，
**魔数只能告诉你是 ZIP，告诉不了你是哪一种**。要靠包内路径分：

```python
# app/split.py —— ZIP 容器里有三种我们要区分的 Office 格式
_ZIP_KIND: tuple[tuple[str, str], ...] = (
    ("word/document.xml", "docx"),
    ("ppt/presentation.xml", "pptx"),
    ("xl/workbook.xml", "xlsx"),
)
```

实测（`scripts/split_reader.py` 的 ① 组，夹具全是现造现删的）：

```
    报告.txt           1375B 后缀 .txt   头 8 字节 %PDF-1.7   → 判为 pdf
    页面.md             167B 后缀 .md    头 8 字节 <!DOCTYP   → 判为 html
    清单.csv             84B 后缀 .csv   头 8 字节 ········   → 判为 csv
    手册.docx         36921B 后缀 .docx  头 8 字节 PK······   → 判为 docx
    年报全集.txt        6.07MB 后缀 .txt   头 8 字节 ········   → 判为 txt
```

前两条就是「扩展名骗人」的两个方向：`报告.txt` 其实是 PDF，`页面.md` 其实是 HTML。
按扩展名路由，第一条会被当文本读出一屏乱码，第二条会把 `<script>` 一起读进索引。

那剩下的文本文件（`.md`／`.txt`／`.csv`）怎么办？它们没有魔数，所以判据换一层：
**先解码，再看内容特征，最后才看列数**。

```python
# app/split.py —— 文本文件之间靠内容特征分，不靠后缀
_TEXT_KIND: tuple[tuple[re.Pattern[str], str], ...] = (
    (re.compile(r"^\s*(<!DOCTYPE html|<html)", re.I), "html"),
    (re.compile(r"^#{1,6}\s", re.M), "md"),
)
```

CSV 单独有一条判据，而且它**故意写紧**：

```python
# app/split.py —— 像不像 CSV：至少两行、每行都含逗号、且列数一致
def _looks_like_csv(text: str) -> bool:
    lines = [ln for ln in text.splitlines() if ln.strip()]
    if len(lines) < 2:
        return False
    widths = {ln.count(",") for ln in lines}
    return len(widths) == 1 and widths.pop() >= 1
```

为什么不写成「有逗号就是 CSV」：中文正文里逗号满地都是，那样一份普通文档会被判成表格。
要的是「**这是一张表**」的证据，而列数一致才是证据。这条错法当场被夹具抓住过——
第一版用的正则是「一行里有一到两个逗号」，实测把一份散文判成了 CSV。

判出格式之后，路由是一件很薄的事：

```python
# app/split.py —— 格式 → 解析器。这张表是路由的全部
PARSERS: dict[str, Callable[[Path], Doc]] = {
    "md": parse_markdown,
    "txt": parse_text,
    "csv": parse_csv,
    "html": parse_html,
    "pdf": parse_pdf,
    "docx": parse_docx,
    "pptx": parse_pptx,
    "png": parse_image,
    "jpg": parse_image,
}
```

**加一种格式 ＝ 加一行**，而不是在 `load_document` 里加一个 `elif`。
这不是审美：`elif` 链里新加的分支最容易漏掉「它也属于可选依赖」这件事，
而表里的一行会逼你把它写成一个独立的解析函数。

## 5.2.3 八条解析路与它们各自最容易丢的东西

格式判对之后，每一条路都有自己的坑，而它们的坑**不是同一类**：

| 格式 | 用什么读 | 最容易丢的东西 |
| --- | --- | --- |
| PDF（文本层） | PyMuPDF（`fitz`） | 表格结构、分栏顺序、页眉页脚混进正文 |
| PDF（表格） | pdfplumber | 抽得到表，但**慢三倍**（同一份文本型 PDF：0.8s vs 2.3s） |
| PDF（扫描件） | PaddleOCR / Tesseract | 整页本来就没有文本层，**不 OCR 就是 0 字** |
| Word | python-docx | 样式里那层**标题层级**（丢了就没有结构可切） |
| PPT | python-pptx | 备注页里的讲解（正文框只有几个短语） |
| HTML | 标准库 `html.parser` | `<script>`／`<style>` 里的代码被当正文 |
| CSV／表格 | 标准库 `csv` | 表头与多行记录被拼成一长句 |
| 图片 | OCR（可选） | 本机没引擎时**整份资料静默消失**（最危险的一种） |

PDF 之所以要分三条路，是因为同一份 PDF 里三件东西的读法完全不同：
**文本层**用 `page.get_text()`，**表格**要 `pdfplumber` 的 `extract_tables()`，
**扫描件**则要先把页面渲染成图再 OCR。把它们合成「一个 PDF 解析器」，
结果一定是「某种 PDF 读出来是空的，而程序不报错」。

本章的 `parse_pdf` 只做第一条路，并且**明确拒绝**另两条：

```python
# app/split.py —— PDF：PyMuPDF 逐页抽文本（节选）
def parse_pdf(path: Path, *, passwords: tuple[str, ...] = ()) -> Doc:
    try:
        import fitz                       # noqa: PLC0415
    except ImportError as exc:
        raise Unsupported("pdf", "PyMuPDF 不在", "PyMuPDF") from exc
```

Word 那一条路有个容易漏的动作：**把样式换回标题层级**。
因为这一步做完，后面的切分逻辑就不必为 docx 写分支——它面对的永远是同一套 `#`。

```python
# app/split.py —— Word：用标题样式换出 `#` 层级（节选）
        style = (para.style.name or "").lower()
        if style.startswith("heading"):
            tail = style.split()[-1]
            level = int(tail) if tail.isdigit() else 1
            out.append("#" * min(level, 6) + " " + text)
```

HTML 那一条路只用标准库，理由在上一节已经写过：**这一层要能在什么都没装的环境里跑**。

```python
# app/split.py —— HTML 取文本：块级标签换行、丢掉脚本与样式（节选）
    _BLOCK = {"p", "div", "li", "tr", "h1", "h2", "h3", "h4", "h5", "h6", "pre", "table", "br"}
```

CSV 那一条路做的选择是「**一行一个记录**」：

```python
# app/split.py —— CSV：每一行变成一段 `列名：值`（节选）
        pairs = [f"{h}：{v}" for h, v in zip(head, cells) if v != ""]
```

为什么不是拼成一长行：一行一个记录，切分时才**可能按记录切开**。
拼成长行的话，定长切分一定会把某条记录拦腰切断——而表格类文档最怕的正是这个。

### 那张性能基准，与它缺的那半个口径

常见的那张「全格式解析性能对比基准」有九行，是这一节唯一能给读者量感的数
（PDF 文本型 0.8s／份、pdfplumber 2.3s／份、扫描件 28.5s／份、Word 0.3s／份、
PPT 0.5s／份、图片 OCR 2.1s／份、Markdown 0.1s／份）。我们**引用它的结论**——
「扫描件的代价比文本型高出两到三个数量级，所以别让所有 PDF 都走 OCR」——
但**不引用它的绝对数字**：它只说了「100MB 内存预算 ＋ 4 核 CPU」，
没说文档平均长度、是否含图、OCR 用的是哪个引擎与哪个模型。
一句话：**两个数要有可比性，先得有同一个口径。** 想在本机复现这张表，
至少要补上「每份文档多少页、多少字、扫描件的 DPI 是多少」三项。

## 5.2.4 读不出的四种，四种处置

「读不出来」不是一个状态，是四件不同的事。它们的处置完全不同，
所以在本章的实现里是**四个不同的异常／分支**：

| 情形 | 抛什么 | 下一步该做什么 |
| --- | --- | --- |
| 文件加密 | `Locked` | 去要密码，或者配一份常用密码表 |
| 扫描件（没有文本层） | `Unsupported`（说「需要 OCR 管道」） | **补一条 OCR 工序**，不是换解析器 |
| 超过大小上限 | `Unsupported`（说清多少 MB） | 先切分文件，或者走流式分批 |
| 没有解析器／没有引擎 | `Unsupported`（说清缺哪个库） | 装依赖，或者接受它不进索引（但要记在案上） |

实测四种全被拦下：

```
    ✔ 拦下 locked.pdf（加密件：试 4 个常用密码都打不开）→ Locked: locked.pdf 已加密，试了 4 个密码都打不开
    ✔ 拦下 扫描件.pdf（扫描件：整页没有文本层，要 OCR 管道）→ Unsupported: pdf：1 页全部没有文本层，是扫描件，需要 OCR 管道（需要 paddleocr 或 pytesseract）
    ✔ 拦下 截图.png（图片：本机没有 OCR 引擎）→ Unsupported: image：OCR 引擎不在（需要 pytesseract ＋ Pillow）
    ✔ 拦下 年报全集.txt（超过大小上限：不读，先说清多大）→ Unsupported: .txt：文件 6.1MB 超过上限 1MB
```

四个里有两个值得单独说。

**第一个是扫描件。** 它不是「解析失败」——PyMuPDF 完全打得开它，
只是逐页 `get_text()` 返回空字符串。所以判据不是异常，是**文本层密度**：

```python
# app/split.py —— 没有文本层 ≠ 解析失败
    if not pages:
        # **没有文本层 ≠ 解析失败。** 它是「这份文件需要 OCR 管道」——
        # 两件事的处置完全不同（换解析器 vs 补一条 OCR 工序），所以异常也要分开。
        raise Unsupported("pdf", f"{total_pages} 页全部没有文本层，是扫描件，需要 OCR 管道",
                          "paddleocr 或 pytesseract")
```

这一条如果写成「抽不到文本就返回空文档」，后果是**这份资料静默地没进索引**：
检索永远召不回它，而没有任何一处报错。这类错在 RAG 里最难查，
因为它的现象是「模型不知道这件事」，而不是「程序崩了」。

**第二个是加密件。** 它的处置是「试密码」，而试完之后要给的是同一个答案：

```python
# app/split.py —— 加密件：先试密码，再决定（节选）
    if doc.needs_pass:
        if not any(doc.authenticate(pw) for pw in passwords):
            doc.close()
            raise Locked(path, len(passwords))
```

`Locked` 与 `Unsupported` 分成两个异常，是因为它们的**读者不同**：
前者要人去要密码，后者要人去装库或者补工序。合成一个 `Exception`，
报错信息就只能写成「读不了」，而那等于没说。

### 容错不是吞异常

批量解析一定会遇到坏文件。三种处置手段——**重试、回退、跳过**——
各自适用不同的病因：重试治「偶发」（IO、超时），回退治「这个库读不了但那个能读」，
跳过治「这份文件本身就是坏的」。**三者都不该静默**：每次重试、回退、跳过
都要写一条结构化日志（文件路径、异常类型、重试次数、耗时），
否则「某类文件持续失败」这个系统性问题会被一条条孤立日志埋掉。

本章的 `load_directory` 只做最小的一件事：**读不了的当场抛，但不中断整批的语义由调用方决定**。

```python
# app/split.py —— 一个目录 → 一批 Doc（节选）
def load_directory(root: Path, *, passwords: tuple[str, ...] = ()) -> tuple[Doc, ...]:
```

**产物监控**是这一层容易被跳过的一步。一张六行的指标表把「该盯什么」说清楚了，
它的价值不在数字，而在**「哪几个数一异常就说明要动哪一步」**：

| 指标 | 异常阈值 | 对应动作 |
| --- | --- | --- |
| 每文档文本块数 | 长文档 < 3 | 检查拆分策略是否过粗 |
| 平均块字符数 | < 50 或 > 2000 | 调 `size` |
| OCR 置信度均值 | < 0.7 | 提图片 DPI，或换引擎 |
| 解析失败率 | > 5% | 排查失败文件的共性（格式／大小／加密） |
| 清洗噪音比 | > 30% | 检查清洗是否**过度**清除 |
| 嵌入空向量率 | > 1% | 检查嵌入模型是否加载正确 |

最后一行不属于本章（它要等 5.3），但它说明了这张表的位置：
**它是跨层的一张对照表，每一行都要回到各自那一层的旋钮上。**

## 5.2.5 清洗：五种噪声与一条不能换顺序的管线

抽取出来的文本没有一份是干净的。最常见的五种噪声，与它们各自该被哪一步带走：

| 噪声 | 长什么样 | 被谁带走 |
| --- | --- | --- |
| 控制字符 | `\x00`、`\x0b` | 第 1 步：按 Unicode 类别删 `Cc` |
| 页码行 | `第一页`、`3/120` | 单独一步（可关） |
| 全角符号 | `１．`、全角括号 | 第 2 步：NFKC 规范化 |
| 圈码／序号 | `①`、`⑵` | 第 2 步：NFKC |
| **编码错误残留** | `�`（`U+FFFD`） | **谁都带不走** |

四步的顺序**不能换**，每一步各治一种脏东西：

```python
# app/split.py —— 清洗四步，顺序不能换
    text = "".join(ch for ch in text if ch == "\n" or ch == "\t" or unicodedata.category(ch)[0] != "C")
    text = unicodedata.normalize("NFKC", text)
    text = text.replace("\u3000", " ").replace("\u00a0", " ")
    lines = [ln.rstrip() for ln in text.splitlines()]
```

- 第 1 步放在最前：控制字符里有 `\r` 这类会干扰后面按行处理的字符；
- 第 2 步（NFKC）放在换行处理之前：它会改变字符宽度，先做完再谈行长；
- 第 3 步治的是**全角空格与不换行空格**——它们在 `split()` 眼里不是空白；
- 第 4 步（按行 `rstrip` ＋ 压连续空行）放最后，因为前面几步都会新造出空行。

页码那一步为什么要单独一个开关、而且**中文数字也要认**：

```python
# app/split.py —— 一行只有页码的噪声。阿拉伯数字与中文数字都要认
_PAGE_NUMBER = re.compile(
    r"^\s*(?:第\s*)?[0-9一二三四五六七八九十百]{1,4}\s*(?:页|/\s*[0-9]{1,4})?\s*$")
```

第一版只写了 `\d`，实测 `第一页` 这种形式整行留着——而且**清洗完看起来已经干净了**，
这是最难发现的一类漏。反过来说，这个正则也会误删「一行只有一个 `1`」的小节号，
所以它是个**默认开、但要能关**的参数。法规与合同里那种编号小节号正好长这样。

### 那个谁都带不走的字符

`U+FFFD`（`�`）是替换字符：解码器在某个字节上失败时留下它的。
它是这一节最值钱的一条读数，因为它演示了**清洗的能力边界**：

```
清洗前后的质量报告（`scripts/split_reader.py` ④ 组）
               字符数       乱码比      平均行长
清洗前             79    0.0253       7.2
清洗后             67    0.0149      11.2
```

清洗后那份文本里，**那 1 个替换字符一个也没少**（变的只是分母）。
原因是它的 Unicode 类别是「符号」（`So`），与普通字一样合法，五条规则里没有一条碰得到它。

所以「乱码比高」的正确处置**不是清洗**，是**回去修编码，或者换一个解析器**。
把清洗当修复，会让一份错文本看起来像一份好文本——那比留着它更危险。
这正是上面那张监控表里「清洗噪音比 > 30%」那一行的意思：它要警报的不是「洗得不够」，
而是「**你在洗的东西可能本来就不该在这里**」。

有一个坑要顺手躲掉：**换行与制表符也是 `Cc` 类**。乱码比如果不把它们排掉，
每一份多行文本都会自带一个 5%–10% 的假乱码比，这个指标当场作废。

```python
# app/split.py —— `\n` 与 `\t` 也是 `Cc`，但它们不是乱码
    odd = sum(1 for ch in head
              if (ch not in "\n\t" and unicodedata.category(ch) == "Cc")
              or ch == "\ufffd" or "\ue000" <= ch <= "\uf8ff")
```

## 5.2.6 四代切法：在哪里落刀

切分只有一个问题要回答：**在哪里落刀。** 四代切法各自给了一个答案。

| 代 | 在哪里落刀 | 一句话的代价 |
| --- | --- | --- |
| 1 定长 | 每 `size` 个字 | 会在句子、表格、代码中间切，而且**切完看不出来** |
| 2 滑动 | 每 `size - overlap` 个字 | 交界处多存一遍：**入库量成倍涨**（见 5.2.7） |
| 3 递归 | 先按段落边界，仍超长才退到下一级 | 边界是**猜**的：分隔符表列不全就会退化到按字切 |
| 4 结构感知 | 先按标题分节，节内再递归 | 只对**有标题**的文档有效；没有标题就退化成第 3 代 |

```python
# app/split.py —— 四代切法：定长 / 滑动 / 递归 / 结构感知
def chunk_fixed(text: str, *, size: int = 300) -> tuple[str, ...]:
def chunk_sliding(text: str, *, size: int = 300, overlap: int = 60) -> tuple[str, ...]:
def chunk_recursive(text: str, *, size: int = 300, overlap: int = 60,
                    separators: tuple[str, ...] = SEPARATORS) -> tuple[str, ...]:
def chunk_sections(doc: Doc, *, size: int = 300, overlap: int = 60) -> tuple[Piece, ...]:
```

第 3 代有一个**中文特有的坑**：分隔符要给中文定一份。

```python
# app/split.py —— 递归切分的分隔符级联
SEPARATORS: tuple[str, ...] = ("\n\n", "\n", "。", "！", "？", "；", "，", "、", " ")
```

框架的默认分隔符是给英文准备的（`\n\n`、`\n`、` `），而中文段落里没有空格——
一路退下去就会退到「按字切」。所以中文的 `。！？；` 必须自己列进表里，
而且要**排在逗号与顿号之前**：句子边界比短语边界更值得优先落刀。

级联的实现有一个细节值得学一遍：**分隔符留在前一块的尾巴上**。

```python
# app/split.py —— 按分隔符切但把分隔符留在前一块的尾巴上
def _split_keep(text: str, sep: str) -> list[str]:
```

因为中文的 `。` 是句子的收尾，切掉的应该是它**后面**，不是它本身。
这一条看着像小事，但它直接关系到 5.2.9 那条不变式（片必须是原文的子串）。

第 4 代是本章的交付物，它做的唯一一件新事是**先看结构**：

```python
# app/split.py —— 按标题切节，返回标题路径（父 › 子）
def sections(doc: Doc) -> tuple[Section, ...]:
```

而 `Section` 把标题与正文分开放：

```python
# app/split.py —— 一节：标题路径 ＋ 正文。标题进 heading 而不进 text
@dataclass(frozen=True)
class Section:
```

标题为什么不能留在正文里，5.1 已经讲过一遍（会让「标题命中」被算成「正文命中」）。
这里补上第二个后果：**它同时让入库量降下来。** 本节的语料里，
标题行约占 14% 的字，它们不进索引——而那部分字本来就只会让召回率虚高。

### 父子片：不是第五代，是「入库两遍」

还有一代经常被和上面四代并列，但它其实是另一件事：**父子片**。

```python
# app/split.py —— 父子片：拿子片去检索，把小片换成它所属的父片再交给模型
def chunk_parent_child(doc: Doc, *, parent: int = 300, child: int = 100,
                       overlap: int = 20) -> tuple[tuple[Piece, ...], tuple[Piece, ...]]:
```

它治的是这一篇最根本的那对矛盾：**检索要小（准），生成要大（全）**。
做法是同一份文本存两遍——子片入库、参与检索；父片只存，命中子片后回查它。

实测（`接入清单` 一节 190 字）：

```
    父片 #0（190 字）← 子片 0（53 字）, 1（79 字）, 2（95 字）
    父片 #1（73 字）← 子片 0（73 字）
入库量对照：父片 263 字 ＋ 子片 303 字（原文 309 字）
```

入库量近似翻倍，这是它的账。**它不是「第五种切法」，所以不该放进同一张对照表里比分数**——
这一点在 5.2.8 那张表里也守着（表里只有四代与基线）。

### 特殊文档：一刀切会在哪里断

`RecursiveCharacterTextSplitter` 一把梭在四类文档上会断：

| 文档类型 | 推荐做法 | 特殊处理 |
| --- | --- | --- |
| 代码 | 语言感知的分隔符（按 `class`／`def` 边界） | 绝不在代码行中间截断 |
| 表格密集 | 表格感知：先把表换成占位符，切完再放回 | 保住表头与它下面的行 |
| 学术论文 | 按 Abstract／Intro／Method 分节 | 保留引用标记与公式 |
| 法规／合同 | 按条款编号切 | 保持条款完整 |
| FAQ | 一对问答算一片 | 问答不能被拆开 |

本章只实现其中一种（表格），而它可机检：

```python
# app/split.py —— 被切坏的表格：一片里有表格行、却没有表头分隔行
def broken_tables(pieces: tuple[Piece, ...]) -> tuple[str, ...]:
```

判据只认一种病：**一片从表格中间开始**。「表格语义有没有丢」不能机检，那要人看——
这就是那句一页纸长度的提醒「随机抽 20 个 chunk 人工确认无截断、无乱码、语义完整」的位置：
它是机检的补充，不是可以省的仪式。

两条原则在这里立住，后面几章都会用到：

1. **语义完整性 > 大小一致性。** 与其在代码中间强行截断，不如接受略大或略小的片；
2. **所有策略变更后都要抽样复看。** 切法一改，库里每一片都变了——
   而这件事在 5.1 那四组读数里是看不出来的（它们只看四条问题）。

## 5.2.7 参数的账：`chunk_size` 与 `overlap`

### `chunk_size` 定在多少

流传最广的那张六档对照表（128／256／512／800／1024／2048 tokens）里有一条结论：
「512 起步、通用推荐，精度与成本平衡最佳」。
这条建议**不能照抄**，两个原因：

一是那张表**没有口径**：它说「基于中文知识库的实测数据汇总」，
但没说知识库多大、问题从哪来、Precision@5 是怎么算的。没有口径的数不能作为结论。

二是**它和公开研究冲突**。2025 年的一篇多数据集分析
（[arXiv:2505.21700](https://arxiv.org/abs/2505.21700)）在多个嵌入模型上系统比较了定长切分，
结论是：

> 小片（**64–128 tokens**）在**事实型、答案短**的数据集上最好；
> 大片（**512–1024 tokens**）在需要**更宽上下文**的数据集上更好；
> 而且**不同嵌入模型对片长的敏感度不同**——有的模型吃到全局上下文才发挥得好，
> 有的模型在小片上的细粒度匹配更准。

这正好是本章两节读数的另一种说法：**「最优片长」不是文档的属性，是「语料 ＋ 提问方式 ＋ 嵌入模型」
三者的联合属性。** 所以本章的做法是：**不给默认值以外的建议，只给一个量它的方法**——
5.6 会把它做成评测集上的一次网格搜索。

### `overlap` 的账

重叠是「把交界处那句话在相邻两片里各留一份」。它一定有效，也一定有代价，
而代价可以精确地算出来：

```
size=300 overlap=0         8   214.8      1718    100.0%
size=300 overlap=30        9   200.6      1805    105.1%
size=300 overlap=60       11   175.7      1933    112.5%
size=300 overlap=120      13   175.9      2287    133.1%
size=300 overlap=240      32   156.5      5008    291.5%
```

入库量那一列就是账：**重叠是拿冗余换连续**。注意最后两档的涨幅**不是线性的**——
片数从 13 跳到 32，因为重叠把每片推短之后，被推短的那些片又各自触发了一次切分。
**参数之间的关系不是线性的，不能拿算术外推。**

再看一个更隐蔽的后果：取 `overlap=240` 的前 3 片，数每片有多少字是新的：

```
    发布规范#2（132 字）：前 132 字已在 发布规范#0 里出现过，**新字 0 个**
    发布规范#3（72 字）：前 72 字已在 发布规范#2 里出现过，**新字 0 个**
```

**后面的片整片都是前一片的尾巴。** 于是检索交回的「3 片」实际只有 1 片的信息量，
另外两片是它的截尾副本——而它们照旧占掉 3 个提示位。
这不是「重复入库」的小毛病，是**提示位置被吃掉了**。

`_pack` 的重叠是「回退前一片的尾巴」，所以只要 `overlap` 接近 `size`，
这个现象就一定会出现。它不是配置失误，是这一代数下去必然的结果。
`overlap >= size` 会让步长为 0——切片循环永远不前进，所以它必须在入口就被挡掉。

## 5.2.8 读数：五代切法的对照

现在把四代切法（加上 5.1 的空行切分做基线）放在**同一份语料、同一个检索器**上。
唯一的变量是切法——这是 4.3 那条纪律（先控制变量，再谈结论）在第 5 篇的第二次执行。

| 切法 | 片数 | 均长 | 均匀度 | 入库量 | 答案片排名 | 坏表 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `paragraph`（5.1 基线） | 15 | 98.1 | 0.673 | 1,471（85.6%） | **第 5** | 0 |
| `fixed`（定长 300） | 8 | 214.8 | 0.672 | 1,718（100.0%） | 第 1 | 0 |
| `sliding`（300／重叠 60） | 11 | 175.7 | 0.610 | 1,933（112.5%） | 第 1 | **1** |
| `recursive`（300／重叠 60） | 8 | 229.8 | 0.818 | 1,838（107.0%） | 第 1 | 0 |
| **`sections`（结构感知）** | 12 | 123.1 | 0.739 | **1,477（86.0%）** | 第 1 | **0** |

三段结论，一条比一条重要。

**第一段：基线的错被证实了，也确实被修掉了。** 空行切分把那句「引子 ＋ 四条目」
劈成两片（25 字与 104 字），答案片掉到第 5；换成任何一种有尺寸上限的切法，它都回到第 1。
两条回归门测试把这两个数钉在盘上：

```python
# tests/test_split.py —— 回归门
def test_回归门_空行切分把答案片放到第五() -> None:
def test_回归门_结构感知把答案片放回第一() -> None:
```

**第二段：「答案片排名」这一条读数是钝的。** 你看那一列——
`fixed`／`sliding`／`recursive`／`sections` 全是第 1，而它们四个并不一样。
一条读数只对一类病（句子被劈开）敏感，所以要再量两条：**被切坏的表格**与**入库量**。

**第三段：均匀度不能单独用来选切法。** 看它有多会骗人：

| 切法 | 均匀度 | 它其实把什么切坏了 |
| --- | ---: | --- |
| `fixed` 定长 300 | 0.672 | 在 120 字档实测切坏 2 片表格（这里是 300 字档才侥幸没切） |
| `sliding` 300／60 | 0.610 | 切坏 1 片（`接口约定#1` 从表格中间开始） |
| **`recursive`** | **0.818** | 没切坏，但它把**标题行**留在正文里（入库量 107.0% 的一部分） |
| `sections` | 0.739 | 没切坏；入库量最低 |

均匀度最高的两代各有一处吃亏：`fixed` 天生均匀而最不讲道理，`recursive` 均匀但留着标题。
**把三个数放在一起看，这一次对照才站住。** 而这一次里只有 `sections` 做到三件事：
表格没切坏、答案片在第 1、入库量最低。

**一句必须写下来的话**：这一次「`sections` 最好」只在**这一份语料**上成立。
六份文档都有标题、都很短、都按节写；换一批没有标题的文档，这一代退化成递归切分，
一点增益都没有。测试里为此专门留了一条断言：

```python
# tests/test_split.py —— 把结论限定在语料上，不是一句免责
def test_结构感知的这一代只在有结构的语料上成立() -> None:
```

## 5.2.9 那一族静默错误：片必须是原文的连续子串

这一节记一个**只有把不变式写出来才发现得了**的问题。修切分的那天，
`recursive` 那一代做出来是「看着对」的：片数合理、不超上限、答案片回到第 1。
但如果加一条断言——

> **每一片都必须是原文的连续子串。**

三处立刻就露出来了：

| 位置 | 那一行代码干了什么 | 现象 |
| --- | --- | --- |
| `_split_units` 开头 | `text = text.strip()` | 分隔符被吃掉，`"…方言；\n"` 与 `"2. …"` 拼成 `"…方言；2. …"`——**换行没了** |
| `_split_units` 的列表推导 | `if u.strip()` | `"\n\n"` 被拆成 `"\n"` ＋ `"\n"` 时两个都被丢掉——**表格最后一行与下面的标题粘成一行** |
| `_split_keep` 的返回 | `[p for p in out if p.strip()]` | 同族：拼回去比原文少字符 |

三处的形状完全一样：**在流水线的中间做了「顺手清理」，而那一层根本没有资格改内容。**
它们的读者与 5.1 那条真事故是同一族——渲染把片内的换行折掉、
回读却按行解析，于是多行片从第二行起静默丢掉。结论也一样：

> **跨层的格式契约只能写死在一处。** 要丢空白，只在收尾那一步丢（`_pack` 的末尾），
> 中间每一层的职责只有一个：让拼回去等于原文。

这条东西值得进测试，因为它**可机检**：

```python
# tests/test_split.py —— 这条不变式是拿真事故换来的
def test_每一片都是原文的连续子串() -> None:
```

为什么它可机检、而「切得好不好」不可机检：子串性是一个**结构性质**，
不需要任何标注；而「这一片语义完不完整」需要人看。**能从测试里守住的，就不要留给人工复核**——
人工复核的排期永远排在后面，而这一族的错不会自己报出来。

三条约定：

1. **`build_index` 返回第三个值 `pieces`。** 5.1 那个只返回两个（索引、文档）。
   这里多一个，因为本章的读数要看**片本身**（长度分布、表格完整性）——只看索引是量不出来的；

### 不能破坏什么

- **不能改 `corpus.split_paragraphs`**：它是 5.1 的基线，也是本章两条回归门的对照物。
  要换切法，就在 `app/split.py` 里加一代，不要在原来的函数上动手；
- **不能让「读不出」变成空文档**：扫描件、没有引擎的图片、超限文件都必须**抛异常**。
  兜底成空文档，等于把「这份资料没进来」藏起来——这是这一层最难查的一类错；
- **不能在中间件里清理内容**：任何一处 `strip()`／过滤都可能让片不再是原文的子串。
  收尾那一步才能丢空白；
- **不能把「标题进正文」当成优化**：它会让召回率虚高，也会让入库量看起来更漂亮。
  标题属于元数据；
- **不能把结论说成通用的**：「`sections` 最好」只在有标题的语料上成立，
  这句话在正文、测试与台账里各写了一遍。

## 常见坑

1. **按扩展名判格式。**「它就是 `.txt`」——用户改个名，程序就得读出一屏乱码。
   魔数不听文件名。反过来，**文本文件之间**也没有魔数，那要解码 ＋ 内容特征 ＋ 列数一致。
2. **「有逗号就是 CSV」。** 中文正文里逗号满地都是。判据要的是「**列数一致**」这个证据，
   不是「出现过逗号」这个现象。
3. **把 `.docx`／`.pptx`／`.xlsx` 当成三种不同魔数。** 它们同宗——都是 `PK`。
   只能靠包内路径分（`word/document.xml` 等）。
4. **把「扫描件」当「解析失败」。** PyMuPDF 完全打得开它，只是逐页抽出的文本是空的。
   判据是**文本层密度**，不是异常；处置是补 OCR 工序，不是换解析器。
5. **加密件与读不了的件共用一个异常。** 前者要密码，后者要装库——报错信息会变成没用的一句话。
6. **抽不到文本就返回空文档。** 这是这一层最贵的错：资料静默地没进索引，
   现象是「模型不知道这件事」，而不是「程序崩了」。
7. **OCR 走全量 PDF。** 扫描件每页 1–3 秒，文本型每页 0.05 秒，差两个数量级。
   先用快路径判文本层，只把扫描件丢进 OCR 队列。
8. **在流水线中间 `strip()`。** 表现是「候选文本在原文里搜不到」——引用回查直接失败。
   要丢空白，只在收尾那一步丢。
9. **过滤空白单元。** 与上一条同族：`"\n\n"` 被拆成两个 `"\n"`，两个都是空白，
   过滤掉就少一个换行。**空白是内容的一部分**，它决定片与片的边界。
10. **只按空白与标点切，不给中文列分隔符。** 框架默认分隔符是给英文准备的，
    在中文里没有空格可切，一路退到按字切。
11. **用「均匀度」选切法。** 定长切分天生均匀，而它恰恰最会把表格与代码拦腰切断。
    均匀度是块长的一致性，**不是语义的一致性**。
12. **拿一条读数下判决。** 「答案片排名」对「句子被劈开」敏感，对「表格被切坏」
    与「入库量涨了」完全无感。至少三条一起看。
13. **把重叠调大当成「更保险」。** 重叠 80% 时入库量涨到 291.5%，
    而后面的片整片是前一片的尾巴——提示位置被吃掉了。
    `overlap >= size` 更直接：步长为 0，循环不前进。
14. **以为清洗能修复乱码。** `U+FFFD` 的类别是「符号」，与普通字一样合法——
    五条规则里没有一条碰得到它。乱码比高要去修编码，不是去加清洗规则。
15. **页码行无条件删。** 法规、合同里的编号小节号正好是「一行一个数字」。
    它是默认开、但要能关的参数；中文数字也要认（不然 `第一页` 整行留着）。
16. **在语料上把旋钮调到全对，然后当成结论。** 本章的语料只有六份、1,718 字、
    四条问题里只有一条踩到切分的坑。**这一章所有的「谁更好」都只在这份语料上成立**，
    判决要等 5.6 的评测集——与 5.1 的「四条问题不是证据」是同一条纪律。
17. **切法改了却不重跑索引。** 离线侧的错是批量的：切法一改，库里每一片都变。
    5.1 的四条读数看不出这件事（它们只看四条问题），只有抽样复看才看得到。

## 面试视角

被问到「文档解析与切分」，**先说它决定的是什么**——

按这个顺序，一段能用的回答是四层：

1. **第一层：说清它的位置与量级。** 「切分是 RAG 离线的第一步，
   它**决定了召回的上限**：检索再准，也只能在你切出来的那些片里找。
   我在自己的语料上量到过一次：同一句话被切成两片，装着答案的那一片排第 5，
   于是答案少了半句——而文档本身是召回对的。」
2. **第二层：说清入口那一层的三个决定。** 「进来第一件事是判格式，
   我看**魔数不看扩展名**——实测把 PDF 存成 `.txt` 是合法的，
   而 `.docx`／`.pptx`／`.xlsx` 三个同宗，只能靠包内路径分。
   第二件事是**「读不出」要分四种报**：加密要密码、扫描件要补 OCR 工序、
   超限要先切文件、缺库要装依赖——合成一个异常就等于没说。
   第三件事是**抽不到文本不许返回空文档**：那会让资料静默地没进索引。」
3. **第三层：说清切法的四代与它们各自的代价。** 「定长最快但会在句子中间切；
   滑动带重叠但入库量成倍涨；递归按分隔符级联、中文的分隔符要自己列
   （默认那套是给英文准备的）；结构感知先按标题分节——
   我在同一份语料上量到它把答案片从第 5 拉回第 1，而且入库量最低
   （标题不进正文，省下约 14% 的字）。」
4. **第四层：说出这条路别没量什么，以及一条可机检的不变式。** 「我**没有**给
   `chunk_size` 一个『推荐值』：公开的多数据集分析（arXiv:2505.21700）显示
   64–128 的片在事实型问题上最好、512–1024 的片在需要宽上下文时更好，
   而且不同嵌入模型对片长的敏感度不同——所以最优片长是语料、问法与嵌入模型的联合属性，
   得在自己的评测集上搜。另外我加了一条断言：**每一片都必须是原文的连续子串**。
   它当场抓出三处静默丢字符的 bug，而且它可机检——能从测试里守住的，就不要留给人看。」

第四层是这一段里最值钱的部分：它同时展示了**你知道自己的读数有多硬**（只在这份语料上成立）、
**你知道下一步该量什么**（评测集上的网格搜索），以及**你把认知写成了机制**（子串断言进测试）。

常见的追问与答法：

- **「为什么不用 `RecursiveCharacterTextSplitter` 就完了？」**
  「它对英文够用，在中文上会退化成按字切（默认分隔符里没有 `。`）。而且它不管结构——
  我的语料里同一节的「引子 ＋ 四条目」会被它按空行切开，正是本章要修的那条缺口。」
- **「父子片和语义切分要用哪个？」** 「父子片不是一种切法，是**入库两遍**：
  子片检索、父片生成，代价是入库量近似翻倍。语义切分是另一件事——
  它按嵌入相似度找话题边界，好处是块内一致，代价是**每一句话都要调一次嵌入接口**。
  这两个都要在 5.6 的评测集上算收益，我没有在这份语料上量出它们的价值。」
- **「怎么知道切分改好了？」** 「三条一起看：答案片的排名、被切坏的表格数、入库量。
  只看第一条会骗人——我那份对照里四代切法在这一列上全是第 1。」

## 本章小结

- **本章修的缺口是上一章量出来的那条**：一句引子 ＋ 一串条目被切在中间，
  25 字的引子拿 19.79 分，装着答案的 104 字片只有 1.40 分、排第 5。
  **检索没错，错的是切分。**
- **入口那一层的核心是「不看扩展名看魔数」**，以及一条更重要的纪律：
  **「读不出」要分四种报**——加密要密码、扫描件要补 OCR 工序、超限要先切文件、
  缺库要装依赖。合并成一个异常，就等于没说。
- **抽不到文本不许返回空文档。** 扫描件不是「解析失败」，是「需要另一条工序」；
  用空文档兜底，等于把「这份资料没进来」藏起来，而这一类错的现象是
  「模型不知道这件事」而不是「程序崩了」。
- **清洗的四步顺序不能换**，而它有一个能力边界：`U+FFFD` 谁都带不走。
  所以「乱码比高」的正确处置是回去修编码，不是加清洗规则——
  **把清洗当修复，会让一份错文本看起来像一份好文本。**
- **四代切法各自的落刀点是**：每 `size` 字、每 `size - overlap` 字、
  按分隔符级联、按标题分节。中文的分隔符必须自己列，
  而且句子边界要排在逗号与顿号之前。
- **父子片不是第五代，是「入库两遍」**：子片检索、父片生成，
  治的是「检索要小、生成要大」这对矛盾，代价是入库量近似翻倍。
- **本章最重要的两条方法论**：一是**一条读数不能选切法**——
  「答案片排名」对「表格被切坏」与「入库量」完全无感，至少三条一起看；
  二是**均匀度会骗人**——定长切分天生均匀，而它恰恰最不讲道理。
- **片必须是原文的连续子串。** 这条不变式当场抓出三处静默丢字符的 bug
  （三处都是在流水线中间做了「顺手清理」）。它的价值在于**可机检**：
  能从测试里守住的，就不要留给人看。
- **所有「谁更好」的结论都只在这一份语料上成立**：六份文档、1,718 字、
  四条问题里只有一条踩到切分的坑。判决要等 5.6 的评测集。
- **这一次对照里只有 `sections` 同时做到三件事**：表格没切坏、答案片在第 1、入库量最低
  （86.0%，因为标题不进正文）。但它对**没有标题的文档**毫无增益——
  这个限制写进了正文、测试与台账各一遍。
