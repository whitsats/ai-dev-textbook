# 5.8 综合项目：企业级多格式知识库问答系统

## 本章导读

前七章每一章都修一处缺口，而每一章的入口都是**一次性的**：`why_rag.py` 跑四条问题、
`split_reader.py` 比切法、`vector_reader.py` 看排序、`retrieve_reader.py` 量融合、
`eval_run.py` 记读数、`serve_reader.py` 打六组账。它们是六台仪器，不是一台设备。

这一章把前七章装成**一台能验的设备**，并补上中间缺的那一段：

```text
一批真实文件（多格式）  →  入库报告  →  装好的检索器  →  常驻服务  →  一条命令的验收清单
        ↑ 本章新增这一段                                        ↑ 本章新增这一段
```

前七章的语料是 `corpus/` 里六个 `.md`，一行 `load_corpus()` 读完。真做项目时这一侧
有四件事要做，而且**每一件都能安静地错**：目录里哪些文件该进库、每个文件走哪条解析路、
这份文本值不值得进库、同一批文件重跑一次会怎样。四件事一件不做，症状都不是报错，
而是「检索里少了几片」「引用指向一段空文本」「改了文档而库里还是旧的」。

另一端同样缺一段：**没有任何一个脚本回答「这一版能不能上」**。
5.6 给了回归门，它拦的是「比上次差」；而发布前要回答的是另一组问题——
进来的文件对不对、格式齐不齐、扩库有没有伤到既有读数、对外发出去的引用有没有过核对。

| 件 | 它修的那条缺口 | 在哪 |
| --- | --- | --- |
| 入库（发现／解析／质量门／差量） | 「一批文件」到「一份可检索的库」之间没有任何一步是有记录的 | `app/ingest.py` |
| 多格式语料 | 语料只有 `.md`，而真实资料是 csv／html／txt／pdf 混着来 | `knowledge/` |
| 三套库并排对照 | 换切法之后「是好了还是差了」没有基准 | `scripts/acceptance.py` |
| 验收清单 | 「跑一遍看着对」不是验收；缺一个逐项打勾的东西 | `scripts/acceptance.py` |

三条设计决定写在最前面，理由是「不做的话会怎样」：

1. **入库是「全量报告 ＋ 差量重算」，不是追加。** 每次拿当前目录算一份完整报告，
   内容没变的文档直接复用上一次的片。**追加式入库的失败形态是静默的**：
   索引一直在长，而没有任何一处能回答「现在库里到底有什么」；
2. **内容哈希即身份。** 判「变了没有」看内容戳，不看修改时间：
   `touch` 一下不该触发重算，而**内容变了但时间没变**（回滚、`git checkout`）必须触发。
   报告整体的**语料戳**可以直接喂给 5.7 的 `Versions.corpus`——入库改了内容，缓存自动失效；
3. **验收 = 一条命令 ＋ 一份清单 ＋ 一个锚。** 锚是 5.6 记下的基线：本章的 A 组读数
   必须与它**逐项相同**，差一格就停下。没有锚的清单只是八个句子。

## 5.8.1 为什么要有这一章：七个零件与一次总装

先说清「综合项目」这四个字在本书里的意思：**它不是把前面做过的再跑一遍**，
而是把那些零件装成一台设备，并**补上零件之间缺的那两段**。装的过程中必然浮出
一些在前七章看不见的问题，本章至少有三个：

| 前七章的状态 | 装上之后浮出来的问题 |
| --- | --- |
| 语料是固定的六个 `.md`，`load_corpus()` 一行读完 | 目录里混着 `.xyz`、空文件、乱码日志时，谁进库、谁被拒、凭什么 |
| 切法是实验变量（5.2 在同一份语料上比五代） | 迁移到新切法**会不会伤到既有读数**，以及那个提升报不报得出来 |
| 每条读数各自的脚本都打印得很清楚 | 发布前要回答的是「这一版能不能上」，它不是任何一条读数 |

第三条尤其容易看漏：**读数与验收不是同一件事**。读数回答「它跑成什么样」，
验收回答「这一版能不能上」。前者可以有一条难看的好读数（比如召回 0.6），
后者必须是一组**逐项对得上**的勾。本章因此把验收清单做成会失败的代码：
一项不通过就非零退出——**一个从不失败的清单，与没有清单是一回事**
（这条纪律从 `check_runnable` 那次的「测试清单写死、18 条用例白写」一路传下来）。

## 5.8.2 从目录到知识库：入库的四个动作

入库这一侧的四个动作，各自的失败形态写在下面的表里。**它们共同的特点是都不报错**：

| 动作 | 安静错的形态 |
| --- | --- |
| **发现**：目录里有哪些该进库的文件 | 把 `.DS_Store`、编辑器临时文件、`笔记~` 一起收进来 |
| **解析**：每个文件走哪条解析路 | 读不了的当成空文档放过去，检索时空着、没人发现 |
| **质量门**：这份文本值不值得进库 | 一份乱码比 0.95 的日志进库，它会在某天冒成一条「引用」 |
| **差量**：同一批文件重跑一次会怎样 | 每次重算全部向量（省钱的反面），或者改过的文档还留着旧片 |

发现阶段的第一条纪律是**收进来的代价比漏掉的代价大**：
编辑器临时文件与系统文件进了库，它们会跟真文档抢名次——而它们永远不对。

```python
# app/ingest.py —— 发现阶段：跳过的清单写在代码里，不写在习惯里
SKIP_NAMES = frozenset({".DS_Store", "Thumbs.db"})
SKIP_SUFFIXES = (".tmp", ".bak", ".swp", "~")
```

```python
# app/ingest.py —— 目录 → 该考虑进库的文件（按路径排序，**顺序固定才可复现**）
def discover(root: Path) -> tuple[Path, ...]:
    out = []
    for p in sorted(root.rglob("*")):
        if not p.is_file():
            continue
        if p.name in SKIP_NAMES or p.name.endswith(SKIP_SUFFIXES):
            continue
        if any(part.startswith(".") for part in p.relative_to(root).parts):
            continue
        out.append(p)
    return tuple(out)
```

排序不是形式主义：报告要能**逐行比**（这一版与上一版、这一台机器与那一台），
顺序不固定的话，两份报告无法 diff。

第二个动作是解析，而它的规范写在**报告**里而不是日志里。理由很简单：
日志是给跑这一次的人看的，报告是给**决定要不要发这一版**的人看的。所以三种「读不了」
必须分得开：

| 档 | 含义 | 该做的动作 |
| --- | --- | --- |
| 缺解析器 | 格式认出来了，但没有对应的库 | 装库，或换一种导出格式 |
| 内容太少 | 解析成功，汉字数不足以被回答用上 | **源文件的问题**：一份空模板、一行配置 |
| 乱码超线 | 能解码，但乱码比过高 | 重新导出，或人工核对

混成一句「有文件读失败」，收到报告的人没法行动。本章报告里的那一行是这样的：

```text $ python scripts/acceptance.py --offline
knowledge/ 文件 6 ｜ 进库 3 ｜ 被拒 3 ｜ 片 5 ｜ 汉字 480 ｜ 戳 fcf0d3fe8441
    ✗ 乱码日志.txt        乱码超线：0.1480（上限 0.1）
    ✗ 扫描件.xyz         缺解析器：unknown（无可用库）
    ✗ 空文件.md          内容太少：0 汉字（下限 20）
```

`corpus/` 那一侧是另一行：**6 份文件全部进库，0 份被拒**——六份 `.md` 都是好的。
两行合起来：**12 份源文件 → 进库 9 份、被拒 3 份 ｜ 17 片 ｜ 1,317 汉字**。

注意那三个拒收原因**恰好覆盖三档**，这不是巧合：`knowledge/` 里那三份文件是
为此专门放进去的**坏样本**（一份乱码日志、一个 `.xyz`、一个空文件）。
它们与正常语料放在同一个目录里，于是「三档分得开」这件事在每一次验收里都被真跑一遍——
`tests/test_ingest.py` 里还有一条断言把它们钉住（`测试_真实知识的目录与逐行明细对得上`）。

## 5.8.3 格式按内容判，不按后缀

```python
# app/split.py —— 魔数表：**只看开头几个字节，不看文件名**
MAGIC: tuple[tuple[bytes, str], ...] = (
    (b"%PDF-", "pdf"),
    (b"\x89PNG\r\n\x1a\n", "png"),
    (b"\xff\xd8\xff", "jpg"),
    (b"PK\x03\x04", "zip"),
)
```

扩展名是给人看的，魔数是给解析器看的：前者可以被随手改名（把一份真 PDF 存成
`report.txt` 是合法的），后者不会——`%PDF-` 就是 `%PDF-`。ZIP 容器里还压着三种
Office 格式，靠**包内路径**分（`word/document.xml` → docx）；文本文件之间靠**内容特征**分：

```python
# app/split.py —— 文本文件之间靠内容特征分，不靠后缀。顺序有意义：先判最具体的
_TEXT_KIND: tuple[tuple[re.Pattern[str], str], ...] = (
    (re.compile(r"^\s*(<!DOCTYPE html|<html)", re.I), "html"),
    (re.compile(r"^#{1,6}\s", re.M), "md"),
)
```

这一条的实测在写测试的时候撞上了，值得单独记一笔：**把一份没有 `# ` 标题的正文
改名成 `.md`，它会被判成 `txt`**——因为它确实不是 Markdown（没有标题语法）。
第一版的测试夹具里 `说明.md` 的内容是纯段落，于是断言 `{"md", "csv"}` 失败、
实得 `{"txt", "csv"}`。**错的是我的期望，不是判据**：判据要守的是
「按内容判」，那我就不该用后缀去期望格式。

同一族里还有一条：CSV 的判定不能只看「有逗号」——中文正文里的顿号、列举句都有逗号。
所以它要求「**大多数非空行都是同列数的逗号分隔行**」，这条判据来自
Python `csv` 模块对「分隔符与引号」的定义方式，而不是从「看起来像表格」出发。

## 5.8.4 质量门：三档拒收，报告要能行动

两个阈值都是**选择**，所以都写在模块顶部、并写清它们的含义：

```python
# app/ingest.py —— 两个阈值都是选择，不是定律
MAX_GARBLED = 0.10

#: 一份文档少于这么多汉字就不进库。判据是「它能不能被回答用上」：
#: 十来个字的文件（`# 待办`、一行配置）在检索里只会变成噪声候选。
MIN_HANZI = 20
```

`MAX_GARBLED = 0.10` 指「前 1000 字里超过十分之一是控制字符／替换字符／私用区」：
正常导出的中文文档乱码比是 **0.0000**，而 OCR 失败或编码错乱的那一档通常在
**0.05–0.95** 之间。本章实测的那份乱码日志是 **0.1480**——它落在中间，
是那种「人眼一看就知道不对、程序不判就过去了」的文件。

质量门的实现只有六行，但它把三档的先后顺序也定死了：

```python
# app/ingest.py —— 质量门：内容太少与乱码超线是两件事，报告里也分两行
    q = quality(doc.text)
    hanzi = sum(1 for c in doc.text if "\u4e00" <= c <= "\u9fff")

    if hanzi < MIN_HANZI:
        return SourceRef(rel, doc_id, fmt, "rejected",
                         f"内容太少：{hanzi} 汉字（下限 {MIN_HANZI}）", 0, hanzi, stamp), None, ()
    if q["garbled"] > MAX_GARBLED:
        return SourceRef(rel, doc_id, fmt, "rejected",
                         f"乱码超线：{q['garbled']:.4f}（上限 {MAX_GARBLED}）",
                         0, hanzi, stamp), None, ()
```

**顺序有语义**：先数汉字、再判乱码。反过来的话，一份「全是控制字符、汉字数为 0」的文件
会被报成「乱码超线」，而它更该被报成「内容太少」——三档分开的意义就在这里，
顺序错了就等于档位混了。夹具里那条乱码样本为此专门写了三十个汉字：
只写控制字符的话，它会先被判成「内容太少」，**于是这条夹具守的是另一档**。
第一版就是那样写的，它「通过」了，但什么也没守。

## 5.8.5 内容哈希即身份：复用、差量与语料戳

先说清一个容易混的地方：**「没有重算」不等于「不在库里」**。
一份内容没变的文档仍然是库里的文档，变的只是重不重算。所以报告里
`decision` 只有两档（`kept` / `rejected`），而「重不重算」由另一个字段记：

```python
# app/ingest.py —— 一个源文件在报告里的一行。`decision` 只有两档：**kept / rejected**
    path: str            # 相对根目录的路径（报告里给人看）
    doc_id: str          # 入库后的文档名（引用里出现的那个）
    fmt: str             # 解析时判出来的格式（魔数判的，不是后缀）
    decision: str
    reason: str = ""
    pieces: int = 0
    hanzi: int = 0
    stamp: str = ""      # 内容哈希（前 12 位）
    reused: bool = False  # 内容未变，直接用了上一次的片
```

**为什么这一处要写这么细**：把「复用」当成第三档决策（`skipped`）的后果是——
它在差量里会显示成「被删了」。于是「今天删了三份文档」与「今天三份文档没变」
在报告上是同一行，而前者要发通告、后者什么都不用做。

语料戳由留下的内容算，不由「跑一次」算：

```python
# app/ingest.py —— 语料戳：**由留下的内容算出来**，不是「跑一次就变一个」
    @property
    def stamp(self) -> str:
        return content_stamp("|".join(sorted(f"{e.doc_id}:{e.stamp}" for e in self.kept)))
```

于是它天然有三条性质，每一条都有一条夹具守着：**改一份文档的内容 → 戳变**（缓存失效）；
**`touch` 一下 → 戳不变**（缓存留着）；**被拒的文件进来或出去 → 戳不变**（它们本来就没进库）。
第三条最值钱：它意味着**运维每天往目录里丢文件不会把缓存全打掉**——
打掉缓存的是「进了库的内容变了」，而不是「目录变过」。

差量是同一份报告的两版相减，五种结果都要能分开数：

```python
# app/ingest.py —— 与上一份报告比。**五种结果都要能分开数**
        old = {e.doc_id: e for e in (previous.kept if previous else ())}
        new = {e.doc_id: e for e in self.kept}
        added = sorted(k for k in new if k not in old)
        removed = sorted(k for k in old if k not in new)
        updated = sorted(k for k in new if k in old and old[k].stamp != new[k].stamp)
        unchanged = sorted(k for k in new if k in old and old[k].stamp == new[k].stamp)
        return {"added": added, "updated": updated, "removed": removed,
                "unchanged": unchanged, "rejected": sorted(e.path for e in self.rejected)}
```

`updated` 与 `added` 混在一起，就永远看不出「这次发布到底新加了几份、改了几份」。
而复用的那一段在 `ingest()` 的主循环里，只有四行：

```python
# app/ingest.py —— 内容戳没变的文档直接复用上一次的片，不重切、不重嵌
        if ref.decision == "kept" and ref.doc_id in old and old[ref.doc_id].stamp == ref.stamp \
                and old_chunks.get(ref.doc_id):
            entries.append(SourceRef(ref.path, ref.doc_id, ref.fmt, "kept", "", ref.pieces,
                                     ref.hanzi, ref.stamp, reused=True))
```

### 这一层的一个已知不足，写在这里而不是留给人去发现

**切分参数不进缓存键。** 本树按内容戳判重算，所以 `strategy`／`size` 变了、
内容没变时，它会**复用错的片**——上一版按段落切的片，会出现在这一版按结构切的库里。
真实系统里这一层要把切分参数一起进键（5.7 的 `DEPENDS` 已经给了形状）。
本章留的是一个可量的读数：**重跑一次要重算几份**。这条不足放在练习 1 里。

## 5.8.6 三套库并排：A 现状 / B 扩库 / C 迁移

验收的核心是一张表：**同一批 24 条评测集、同一个检索器（同一套零件），只换知识库**。
三套库的名字就是「改动量」的顺序：

| 组 | 是什么 | 片 |
| --- | --- | ---: |
| **A 现状** | `corpus/` ＋ 5.1 的段落切（**5.1–5.7 所有读数的锚**） | 15 |
| **B 扩库** | A ＋ `knowledge/` 的多格式新片 | 20 |
| **C 迁移** | `corpus/` 换成 5.2 的结构感知切 ＋ 多格式新片 | 17 |

判分口径**照抄 5.6**，一句都不新写——两份实现会漂，而这一层的漂移不会报错，
只会让「C 比 A 好」这个结论失去基准：

```python
# scripts/acceptance.py —— 一组片上的四项读数。**每一句都照抄 5.6 的 `run_offline()`**
    for c in cases:
        chunks = tuple(h.chunk for h in r.search(c.text, k=K, mode="bm25"))
        cites = tuple(h.cite() for h in r.search(c.text, k=K, mode="hybrid"))
        holder = span_cite(r.chunks, c.want)
        if c.needs_recall:
            spans.append(cites.index(holder) + 1 if holder in cites else 0)
            a = answer(model, c.text, chunks)
            bind(a.text, chunks)
            answers.append((c.want in a.text, True))
        if c.expect_retrieve:
            _h, _s, quality = evaluate(r, c.text, depth=K)
            cells.append((c.expect_refuse, must_refuse(chunks, quality.value) is not None))
```

跑出来是这样：

```text $ python scripts/acceptance.py --offline
知识库                    片        片级      答案命中    漏拒    误拒
A 现状（段落切）             15    0.8333    0.9444     1     0
B 扩库（＋多格式）            20    0.8333    0.9444     1     0
C 迁移（结构感知切）           17    0.8889    1.0000     1     0
```

三条结论，每一条都要说清它**凭什么**：

**一、A 组必须与 5.6 的基线逐项相同，差一格就停下。** 这不是「尽量」，
是一句断言——本书第一次运行这个脚本时就报过一次，因为 `fmt` 那一处缺陷
让清单先报了 ✖。断言写在一处专门的函数里，好让它自己也被夹具验：

```python
# scripts/acceptance.py —— A 组与 5.6 基线的差异。**空元组表示分毫不差**
    keys = (("片级", row["span"], BASELINE["span"]), ("答案命中", row["answer"], BASELINE["answer"]),
            ("漏拒", row["missed"], BASELINE["missed"]), ("误拒", row["over"], BASELINE["over"]))
    return tuple(f"{n} {got} ≠ {want}" for n, got, want in keys if got != want)
```

**二、扩库四项读数一格没动，而它并不是「没生效」。** 归因给了两个数：
**24 条里有 12 条的前三名出现过新片**，**逐条比对候选，13/24 条变了**。
也就是说——**过半的问题的候选集变了，而一条命中都没变**。
这正是「候选变了」与「读数变了」必须分开报的原因：如果只报后者，
这一组读起来像什么都没发生；只报前者，又会把它读成提升。
**真实结论是：新片挤进来的是排名靠后、本来就不装着答案的那些位置。**

按 5.6 定下的判据，这个组的差值（+0.0000）**在分辨率之下，不报**：
24 条用例的分辨率是 1/24 ≈ **0.0417**，任何小于它的「提升」都落在噪声里。
判断这件事的也是一个函数，两件都要有夹具：

```python
# scripts/acceptance.py —— 这一组的提升报不报得出来
def _reportable(a: dict, row: dict) -> bool:
    return max(abs(row["span"] - a["span"]), abs(row["answer"] - a["answer"])) > MIN_DETECTABLE
```

**三、迁移这一档的提升报得出来：+0.0556 > 0.0417。** 而且它不是「换了个数好看」：
答案命中从 **0.9444 涨到 1.0000**（那条一直没命中的用例终于命中了），
片级从 **0.8333 涨到 0.8889**，拒答四格一格没动（1／0）。
原因也可以复算：结构感知切把「一片被从中间腰斩」的形态修掉了——
5.1 那条「答案片排在第五」的缺口，本来就有一半出在切分上。

顺带一个对照：同一份 `corpus/`，**段落切 15 片、结构感知切 12 片**。
片少了三片，而读数更好——这一条**顺手否掉了「片越多越好」这个直觉**。
切的目的是让一片刚好装一个意思，不是让片更碎。

## 5.8.7 一条命令的验收：清单八项与它抓到的两条错

验收清单是一个表，八项，逐项判、逐项给明细：

| # | 条目 | 凭什么判 |
| ---: | --- | --- |
| 1 | 入库有报告，三档分得开 | `rejected ≥ 1` 且原因 ≥ 2 类 |
| 2 | 多格式真的进来了（不是只有 `.md`） | 进库文档的格式 ≥ 3 种 |
| 3 | 语料戳由内容算，两库各一个 | 长度 12、且两库的戳不同 |
| 4 | A 组与 5.6 的基线逐项相同 | `_gap(a)` 为空 |
| 5 | 扩库不伤既有读数 | B 的答案命中 ≥ A |
| 6 | 迁移这一档有读数、且方向说得清 | C 的片级 ≥ A |
| 7 | 端到端有答复、引用由代码核对通过 | 每一条发出去的答复 `check_citations` 为空 |
| 8 | 四笔账记得下来 | 每条请求的账能打出来 |

```python
# scripts/acceptance.py —— 一条命令的验收（节选：第 1、2、7 项的判据）
        ("入库有报告，三档分得开",
         k["files"] > 0 and k["rejected"] >= 1 and len(rep["knowledge"].by_reason()) >= 2,
         f"{k['kept']} 份进库／{k['rejected']} 份被拒："
         f"{json.dumps(rep['knowledge'].by_reason(), ensure_ascii=False)}"),
        ("多格式真的进来了（不是只有 .md）",
         len({e.fmt for e in rep["knowledge"].kept}) >= 3,
         "解析出的格式：" + "、".join(sorted({e.fmt for e in rep["knowledge"].kept}))),
        ("端到端有答复、引用由代码核对通过", all(r["delivered_ok"] for r in e2e["replies"]),
         f"{len(e2e['replies'])} 条问题的答复全部通过核对（其中 "
         f"{e2e['misnumbered']} 条的模型自称与绑定不符）"),
```

八项全过，再加上十条夹具自检（`夹具自检：10/10 通过`）。而**清单不是装饰**：
它在第一次运行里就抓到了两条错，两条都值得写下来。

### 它抓到的第一条错：进库的行没有格式

第 2 项判的是「进来的格式 ≥ 3 种」，输出是「解析出的格式：」——**空的**。
去查 `app/ingest.py`，原因很清楚：`_one()` 里给**被拒**的行带上了格式
（异常里本来就有 `exc.fmt`），而给**进库**的行传了空串：

```text
✖ 多格式真的进来了（不是只有 .md）　解析出的格式：
```

这条缺陷的意义不在它多难，而在**它有多安静**：库里明明进来了 csv、html、txt 三种，
检索、报价、引用全都正常，`lint` 与回归门全绿——**只有报告答不上来
「这一版进来了哪几种格式」**，因为它把那个字段扔了。修法是在判完格式之后
把它一路带上（并对复用的行也带），`tests/test_ingest.py` 里加了
一条叫「进库的行也带格式」的断言把它钉住。

### 它抓到的第二条错：清单自己把两件事混成了一个布尔

第 7 项第一次跑也是 ✖，而**两条答复其实完全合格**。原因在我写的判据里：
我读的是 `reply.citations_ok`，而那个布尔是 `not bound.issues and not check_citations(...)`
——它同时包含**「离线替身自己标的编号对不对」**。实测两条请求都是
「模型自称与绑定不符（绑定层改过了）」，于是这个布尔为假，清单就报了 ✖。

**这是同一族错误的第三次露面**：5.7 审阅时抓过一次（把「引用自称与绑定不符 19 条」
读成「引用质量 19/24」），本章第一版又犯了一遍，而且这次犯在**验收清单自己身上**。
修法是把两把尺子分开：

```python
# scripts/acceptance.py —— 验收的是「发出去的那一份」
        delivered = check_citations(reply.text, reply.chunks) if reply.chunks else ()
```

读数因此变成两个数：**发出去的两份全部通过核对**，而**两条的模型自称与绑定不符**。
前者是质量结论，后者是「这一版的替身有多不听话」——**两个数必须分开报**，
合成一个布尔就必然在某一天把合格的答复判成不合格。夹具自检里加了一条
专门守它的用例（`引用看的是发出去的那一份`）。

## 5.8.8 端到端：从问题到引用

验收的第 7 项不是「读一段读数」，是**真发一次请求**：在 C 库上走完整的
`Service.handle()`（检索 → 判档 → 生成 → 绑定）。两条问题的读数：

```text
问：夜间值守是谁？
  引用：knowledge.值班表#1、调用预算#1、接入清单#0
  质量档 ambiguous ｜ 拒答 False ｜ 答复 328 字
  引用核对（对发出去的那一份）：通过　自称与绑定不符（绑定层改过）
  四笔账：{'嵌入': 1, '检索': 3, '重排对数': 0, '模型调用': 1, '提示汉字': 243, '输出汉字': 156}

问：发布说明必须包含哪几段？
  引用：发布规范#0、发布规范#1、接口约定#0
  质量档 correct ｜ 拒答 False ｜ 答复 375 字
  引用核对（对发出去的那一份）：通过　自称与绑定不符（绑定层改过）
  四笔账：{'嵌入': 1, '检索': 3, '重排对数': 0, '模型调用': 1, '提示汉字': 319, '输出汉字': 226}
```

四处细节值得逐个说：

**引用里出现了 `knowledge.值班表#1`。** 那是本章新进来的 CSV 的第二片——
多格式语料不只是「进了库」，它**真的出现在了发出去的引用里**。
根名前缀（`knowledge.`）的用处也在这里：读者一眼能看出这份资料来自哪个目录。

**「检索 3 笔」仍然是三笔**（融合 1 ＋ 判档 2），与 5.7 记的那笔账一致。
**账里没有一笔是「新语料特有的」**——这正是「同一个检索器只换库」的意思。

**质量档 `ambiguous` 不奇怪，也不要过度解读。** 离线判档器是字面判据的替身，
面对 CSV 切出来的那一句「值班表」它给的是「部分支撑」（ambiguous）。
5.6 已经写明这类读数**只能与自己比**：它是确定性的替身，口径与真机不同。

**端到端用的是 C 库，而片数与 §5.8.6 那张表的 C 组是同一个数（17）**——
这一条是「片数可复述」这项清单条目的意义：读数与请求若用的不是同一份片，
那张对照表就只是另一份语料的读数。

## 5.8.9 一个不做的决定：为什么不擅自迁移

读数说 C 比 A 好（答案命中 1.0000 对 0.9444，超过分辨率；四格不变）。
那为什么不把线上那条路直接迁到 C？

**因为换切法等于换系统。** A 组是 5.1–5.7 **全部读数**的锚：片级 0.8333、
答案命中 0.9444、拒答四格 1／0、以及那一整章「热跑省下的账」——它们全都是在
段落切的语料上量出来的。迁到 C 之后：

1. 那七章的正文数字**全部作废**（它们是不可复现的了，而本书的纪律是每个数都能复算）；
2. 5.6 的基线要**重取**，5.7 的服务读数要**重跑**，而重取基线本身是一次
   「把门放宽」的动作——它必须由人来做，而且要有记录；
3. 四格表要重扫（判档器的行为会随片边界变），阈值扫描的结论也可能动。

**这些是发布动作，不是重构。** 本章的交付因此不是「迁完了」，而是把这次迁移
变成**一条命令 ＋ 两组读数 ＋ 一份差异清单**：跑 `python scripts/acceptance.py --offline`，
决策者手里就有 A／B／C 三行数与逐条差异（`迁移改了 22/24 条`）。
同一件事在代码里也有边界：C 组那套切法**只存在于验收脚本**（`_sections_of_corpus()`），
线上默认路径（`build_retriever()`）一行都没动——**「没动」是刻意的，不是忘了。**

### 接口契约

入库这一侧对外的面只有两个：一个函数与一份报告。

```python
# app/ingest.py —— 一个文件 → 一份 `Doc`。三步：**大小 → 格式 → 路由**。
def ingest(root: Path, *, prefix: str = "", strategy: str = "sections", size: int = 300,
           overlap: int = 60, previous: IngestReport | None = None) -> IngestReport:
```

`IngestReport` 上有三样东西是本章的新语义：`entries`（逐行的处置）、
`stamp`（语料戳，可直接喂 5.7 的 `Versions.corpus`）、`diff(previous)`（五种结果）。
注意 `prefix` 是调用方给的：本章的库里带 `knowledge.` 这样的根名前缀，
而**前缀写进 `Doc` 而不只写在报告行里**——片是从 `doc` 切出来的，引用标识取自 `piece.doc_id`。
只改报告的话，引用里看不到前缀，而且「按 `doc_id` 取回上一次的片」会永远匹配不上

### 不能破坏什么

1. **A 组的四个数与 5.6 的基线逐项相同**——本章的锚，差一格就 `assert` 停下；
2. **扩库不许伤既有读数**（B 的四项 ≥ A 的四项）；这一条是**方向**断言，
   不是数值断言——语料会变，方向不该变；
3. **端到端发出去的答复必须通过 `check_citations`**，而「自称与绑定不符」
   只作为另一个数报出来；
4. **语料戳的三条性质**（改内容变／`touch` 不变／被拒进出不变）——它们是缓存正确性的前提；
5. **夹具自检 10/10**：三档拒收、复用、戳、基线断言的两个方向、分辨率判据的两个方向、
   两把尺子分开。

## 常见坑

1. **把「目录里的文件」当成「库里的文档」**。中间还差发现、解析与质量门三步，
   任何一步没有记录，库里就会有一些没人知道来源的片；
2. **读不了的文件只记日志**。跑这一次的人看得见，决定要不要发这一版的人看不见；
3. **把三种「读不了」合成一句**。「有文件读失败」没法行动，三档分开才有动作；
4. **按后缀判格式**。把真 PDF 存成 `.txt` 是合法的，把一份纯段落改名成 `.md` 也是——
   实测它会被判成 `txt`（判据没错，期望错了）；
5. **先判乱码、后数汉字**。全是控制字符的文件会被报成「乱码超线」，而它更该是「内容太少」；
6. **质量门的阈值不写出来**。20 汉字、0.10 乱码比都是选择，写在心里的阈值无法被审计；
7. **没有标题的正文当 Markdown 收**。它进了库也只能按纯文本切；
8. **入库用追加**。索引一直在长，而没有任何一处能回答「现在库里到底有什么」；
9. **把「复用」当成第三种决策**。它在差量里会显示成「被删了」，于是没变的文档与删掉的文档同一行；
10. **用修改时间判「变了没有」**。`touch` 触发全量重算，`git checkout` 回滚却不触发；
11. **语料戳由「跑一次」算**（时间戳、随机数）。它一变，5.7 的三层缓存全失效；
12. **语料戳把被拒的文件算进去**。于是每天丢一个坏文件进目录，缓存天天被打掉；
13. **切分参数不进缓存键**（本树已知不足）。改了切法而内容没变，会复用上一版的片；
14. **拿「片更多」当质量指标**。同一份语料：段落切 15 片、结构切 12 片，而后者的读数更好；
15. **只在同一套库上比读数**。换库对照必须**同一批题、同一个检索器**，只换库；
16. **另写一份判分实现**。两份实现会漂，而这一层的漂移不报错，只让结论失去基准；
17. **不求 A 组等于基线**。锚一松，「C 比 A 好」这句话就没有基准了；
18. **报小于分辨率的提升**。24 条用例的分辨率是 0.0417，+0.0000 与 +0.02 都是噪声；
19. **把「候选变了」当成「读数变了」**。扩库改了 13/24 条的候选，而四项读数一格没动；
20. **把 `citations_ok` 当成「答复合格」**。它里面还夹着「模型自称的编号对不对」——
    同一族错误在本书已经露过三次面；
21. **验收清单不会失败**。一个从不报 ✖ 的清单，与没有清单是一回事；
22. **验收脚本只在自己这一章跑**。它要进提交门（`check_runnable` 的离线入口清单），
    否则「这一版能不能上」这句话没有第二次机会说出口；
23. **擅自迁移线上切法**。换切法作废前面全部章节的读数，那是发布动作——
    要有记录、要重取基线、要人来点那一刀。

## 面试视角

**问：做 RAG 时「语料入库」这一步你觉得最容易出什么问题？**
答：最容易出的不是检索质量，是**记录**。一份文件读不了、一份文件内容太少、
一份乱码进了库——这三件事都不会让程序报错，只会让库里少几片或者多一条莫名其妙的引用。
所以我做的第一件事是把入库写成一份**全量报告**：每一份文件一行、三档拒收分得开、
含一个由内容算出来的语料戳。报告还有一个副作用：它是「现在库里到底有什么」的唯一答案，
而这一句话决定了发布能不能被复核。

**问：怎么判断一份文档「变了」？**
答：看内容哈希，不看修改时间。三条性质都得成立：改内容则变、`touch` 不变、
被拒的文件进出不变。第三条最容易被漏掉，但它决定了运维每天往目录里丢文件
会不会把缓存全打掉。

**问：切分策略该按什么选？**
答：按读数选，而不是按「片多片少」。我在同一份语料上比过：段落切 15 片、结构感知切 12 片，
后者的片级命中与答案命中都比前者高（+0.0556，在 24 条用例上超过了 0.0417 的分辨率）。
片更少而读数更好——**切的目的是让一片刚好装一个意思，不是让片更碎**。

**问：验收一个 RAG 版本，你会看哪几件事？**
答：我有一张八项的清单，核心是四类：进来的文件对不对（三档拒收、格式齐不齐）、
扩库有没有伤到既有读数（方向断言）、迁移这一档的差值够不够大（超过 1/n 的分辨率）、
以及**发出去的那一份**引用有没有通过代码核对。最后一条要特别说清：
「模型自称的编号对不对」与「发出去的答复对不对」是两个数，合并成一个布尔
必然会在某一天把合格的答复判成不合格。

**问：换切法之前你会做什么准备？**
答：先承认它是**换系统**，不是重构。要作废的读数、要重取的基线、要重扫的阈值表，
列出来给做决定的人看；然后把决策需要的账准备好——同一批题、同一个检索器，
三套库并排（现状／扩库／迁移），再给逐条差异。我的脚本把这件事做成了一条命令，
所以「要不要迁」这个决定不依赖任何人的印象。

## 本章小结

- 入库是「**全量报告 ＋ 差量重算**」，不是追加；报告是「现在库里有什么」的唯一答案；
- 发现阶段的跳过清单、质量门的两个阈值都**写在代码里**，并说清理由；
- 三种「读不了」分三档（缺解析器／内容太少／乱码超线），**顺序有语义**；
- **格式按内容判**：魔数管二进制、内容特征管文本，后缀只是给人看的；
- **内容哈希即身份**：改内容变、`touch` 不变、被拒进出不变；语料戳可直接喂 5.7 的版本戳；
- 「复用」是布尔、不是第三种决策；差量五档（新增／更新／删除／未变／被拒）都要能分开数；
- 对照必须**同一批题、同一个检索器、只换库**；判分口径照抄 5.6，不另写一份实现；
- A 组必须与基线**逐项相同**（锚），扩库不许伤既有读数（方向），
  迁移的提升必须**超过 1/n 的分辨率**才报；
- 验收 = **一条命令 ＋ 八项清单 ＋ 10 条夹具**；一项不通过就非零退出；
- 本章最值钱的两条读数：**候选变了 13/24 条而读数一格没动**（扩库）、
  **答案命中 0.9444 → 1.0000**（迁移，超过分辨率）；
- 换切法等于换系统：本章把它变成「一条命令 ＋ 两组读数 ＋ 一份差异清单」，**不擅自迁**。
