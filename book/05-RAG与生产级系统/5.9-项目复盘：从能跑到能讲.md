# 5.9 项目复盘：从能跑到能讲

## 本章导读

前八章每修一条缺口就留下一次读数，而**那些读数现在躺在八个脚本、一份基线文件与一份台账里**。
换一个人接手，他要回答的第一个问题不是「它准不准」，而是「它由哪些件组成、
每个件当初为什么这么定」。本章交付的不是新读数，而是**回答这两个问题的两份文档，和一条让文档自己对账的命令**：

```text
八章的零件                  →  架构文档（两张图 ＋ 节点到模块的对照表）
十几次「与预设相反」的读数  →  六条决策记录（背景／决定／被否掉的选项／失效线）
两份手写的文档              →  一条对账命令（模块双向点名、ADR 字段、读数引用、行数标注、自描述条数）
```

先说清「复盘」在本书里的意思，因为它与「总结」不是一件事：

| | 总结 | 复盘 |
| --- | --- | --- |
| 写的是 | 结果（做了什么、得到了什么数） | **当时还有哪些选项、为什么没选** |
| 读者 | 想知道进度的人 | 想改这一版的人 |
| 失效方式 | 过期（数字变了就作废） | 失真（写成回忆，被后来的读数悄悄推翻） |
| 本树的产物 | 各章的读数与小结 | `docs/architecture.md` ＋ `docs/decisions/` ＋ `scripts/recap.py` |

所以这一章有两个不常见的做法，都写在前面：

1. **文档是被核对的，不是被信任的。** 两份文档一共 26 个模块引用、6 条决策记录、30 条读数引用、
   8 处行数标注、3 处条数标注，全部由 `scripts/recap.py` 逐条核对，漂了就非零退出——**手写的第二份清单必须自己对账**
   （`STYLE` 8.8 第 7 条）。它已经进了提交门；
2. **说不清的那部分要写出来。** 本树**没有**真实并发用户、没有多租户，
   这两件事写在架构文档的「已知不足」里，而不是留给人去发现。**没做过的，不能写成结论。**

与第 3.10 节的分界也要说清，否则两章会互相踩：3.10 讲的是**一个 Agent 怎么从零长出来**，
交付的是装配与验收脚本；本章讲的是**一个知识库为什么长成这个样子**，
它的原料是前八章十几次「与预设相反」的读数，交付的是决策记录。
前者回答「它怎么跑起来」，后者回答「它为什么这么定」。

## 学习目标

读完本章，你应当能：

1. 区分「总结」与「复盘」，并说出复盘里最容易省掉、也最值钱的两栏；
2. 解释为什么架构图画**两张**（离线入库与在线问答）而不是一张，并说出「节点必须能指到模块」这条纪律；
3. 写出一条决策记录的六个字段，并说清「背景」为什么必须是**当时手上的那个数**（而不是现在的数）；
4. 从一组读数里判断哪一个改变了**边界**、哪一个只改变了**失败的姿势**，并据此决定要不要写成一条记录；
5. 给每条记录写出**可判定的**失效线（不是「视情况而定」），并接到 5.6 的门与 5.7 的作废矩阵上；
6. 说清「文档自己对账」能查的五件事与查不到的那一件（函数名这一级）；
7. 用「问题 → 一次实测 → 一个决定 → 一个代价」把一次改动讲成四句话，并带上三个必须说的数；
8. 面对「为什么不用向量库」「这个数怎么量的」这类追问，给出**有代价**的回答。

## 5.9.1 「跑通了」和「讲得清」是两件事

先给一个具体的场景，它是本章每一节都在解的题：

> 有人问你：「你这个知识库，为什么不是向量数据库 ＋ 大模型直接拼起来？」
> 你能答出「我们试过、代价是这样」；还是只能答「我这个能跑」？

能跑与讲得清之间差三种「说不清」，三种都不是技术问题，都只能靠**当时留下一份记录**来解：

| 说不清 | 平时的表现 | 解它的东西 |
| --- | --- | --- |
| 说不清它由哪些件组成 | 只记得「有个入库、有个检索」，说不清谁调谁 | 架构图 ＋ 节点到模块的对照表 |
| 说不清某个选择为什么这么定 | 「当时就试了试」「这样比较好」，说不出被否掉的那条 | 决策记录（含被否掉的选项） |
| 说不清哪些数是重的 | 报一堆数，但说不出哪个变了会让系统行为变化 | 读数的**极性**与分辨率（5.6 那两张门） |

第三种最容易被当成「严谨」而不去解：报了很多读数，看起来已经讲清了。
**但一个没有极性、也没有分辨率的数不是读数，是噪声**——5.6.9 的扁平表与两个方向、
5.6.8 的 `1/n`，正是为这件事准备的。本章只是把那些数**搬进决策记录里**，
让每一个数都挂在一个决定上。

装成设备之后浮出来的问题，前八章一条都看不见，下面三条本章各处理一条：

| 前八章的状态 | 装起来之后浮出来的问题 |
| --- | --- |
| 每章一台仪器（八个脚本、九组读数） | 它们之间的**关系**没有任何一张图说清 |
| 有两处「与预设相反」的读数（5.4 的融合边界、5.8 的扩库对照） | 那些读数现在只写在正文里，改代码的人不读正文 |
| 八章的结论散在八章 | 哪些结论**互相依赖**、改一处要动哪几章，没有一处记着 |

最后一条是发布时最痛的：5.8.9 讲「不擅自迁移」，而它真正的理由不是「迁移不好」，
是「迁移会作废七章的读数」——**这条依赖关系必须写在文档里，否则下一个人会重算一遍才发现**。

## 5.9.2 架构图：一张图回答三个问题

画架构图最容易犯的错是**画愿望**：图上写「向量检索服务」「缓存层」「可观测平台」，
而树里没有对应的文件。避免它的办法不是画得更认真，而是换一条纪律：

> **每个节点都必须能指到一个真实模块。指不到，就别画进图里。**

这条纪律有代价：图会变得不那么「完整」（少了那些「显然应该有」的层）。
它的收益在接手的人身上——**图上的每一格他都能打开看**。

三个问题，一张图各回答一个：

| 问题 | 图上的位置 |
| --- | --- |
| 请求从哪进 | 在线问答那张图的入口节点（`Service.handle()`） |
| 数据从哪来 | 离线入库那张图左边的目录，以及它右侧落盘的三样东西 |
| 每一步留下什么产物 | 每个节点的产物标注，以及对照表的最后一列 |

**为什么是两张，不是一张？** 因为离线入库与在线问答不是同一条时间线上的两段：

- 入库是**一次运行**：可以重跑、产物落盘（片、索引、戳）；
- 问答是**每次请求重走一遍**：产物只存在这一次的答复里（答复 ＋ 引用 ＋ 账）。

画成一张会得到一个好看而骗人的图——它让人以为入库也在请求路径上，
于是「重跑一次入库」看起来像一次可以随时做的操作，而它实际上会改变语料戳、
进而作废 5.7 的整层缓存。**图上省掉的那条边界，会在运维时用故障的形式补回来。**

### 两个容易画错的地方

都不是排版问题，都是没想清关系：

- **两个 `build_index()`**。`app/split.py` 的 `build_index()` 收文档、出片（切分那一侧）；
  `app/corpus.py` 的 `build_index()` 收语料、出 `NgramIndex`（索引那一侧）。
  名字撞车而职责不同——图上因此不写裸的 `build_index()`，而是把**产物**写出来。
  **函数名撞车时，用产物认人。**
- **两路索引是并列的，不是串联的**。片同时喂给向量索引与字面索引，
  在线侧**两路并集**才进融合。画成串联，读者会以为字面路是向量路的兜底——
  那不是本树的设计（见下面第一条记录的「决定」与「被否掉的选项」）。

### 图外的那三个模块

架构文档里刻意留了一张「图外」表，装着 `app/metrics.py`、`app/questions.py`
与本章的 `scripts/recap.py`：

```text
图外（不在请求路径上，因为它们不是「系统在跑」的一部分，而是「事后的一次运行」）
  app/metrics.py     判据与指标      评测与验收时
  app/questions.py   5.1 的 Q1–Q4    各章的阅读器脚本
  scripts/recap.py   文档对账        改完文档时
```

把它们塞进请求路径的图，会得到一个「看着更完整、实际更假」的结果：
读数不参与回答，验收更不是请求的一部分。

## 5.9.3 一条决策记录必须有的六个字段

六字段的**形状**借自一份公开的模板（原始出处见「延伸阅读」），但本章改了两处。
先说六栏与它们各自防的失效：

| 字段 | 防的失效 |
| --- | --- |
| 编号与标题 | 记录之间互相引用时不会指错（`ADR-0002` 这种编号是**唯一的锚**） |
| 状态 | 「已决定」与「待定」被当成一回事——后者仍需有人拍板 |
| 背景（**当时手上的那个数**） | 决定变成凭感觉：说不出当时看到的是什么 |
| 决定 | 只写了「为什么」，没写「所以做什么」 |
| **被否掉的选项及否掉的理由** | 后来者把已经否过的路再走一遍 |
| **失效线（什么条件下该推翻它）** | 一条决定被当成永久真理，而在它的前提早就不成立之后 |

第三栏与第六栏是最容易被省掉的，也正是最值钱的：**没有它们，记录只剩结论，
而结论是最容易被误用的东西。** 本章的写法是：

```markdown
# ADR-0002 回归门与验收的主判据只收片级，不收文档级

- **状态**：已决定
- **背景（当时手上的那个数）**：四个配置的文档级命中率逐个相同（`recall.bm25=1.0`、
  `recall.vector=1.0`、`recall.hybrid=1.0`、`recall.rewrite=1.0`）——它已经饱和，没有分辨率
- **决定**：门建在片级判据上；文档级只留作粗筛
- **被否掉的选项及否掉的理由**：用文档级命中率当回归门——四个配置全 1.0000，
  任何改动都是「没有退步」；调小 `k` 制造分辨率——那是改题，不是改门
- **失效线（什么条件下该推翻它）**：语料规模扩大后文档级不再饱和时两者同时看；
  题数变化（`cases` 不再是 24）时 0.0417 这个数作废
```

两处改动都值得单独说：

1. **「理由」被收窄成「背景（当时手上的那个数）」**。理由是散文，背景是**读数**——
   而读数能进对账（下面 5.9.6 会讲它怎么被核）。写「因为文档级判据不够灵敏」
   是没法被核的；写 `recall.bm25=1.0` 能被核，而且**它会被后来的读数推翻**——
   那正是我们想要的属性；
2. **「后果」被换成「失效线」**。原因是「后果」这句话写起来太容易变成免责声明
   （「维护成本会上升」），而失效线是一条**可判定的条件**：
   「片数超过 50,000」「题数不再是 24」「文档级不再饱和」。**判定不了的条件等于没写。**

还有一条纪律：**决定里不许出现「优化」「提升」这类没有对象的词**。
每条决定都要能回答「改的是哪个边界」，或者「改的是哪种失败的姿势」——
这两条也是判断「要不要为它写一条记录」的判据（下一节）。

## 5.9.4 把八章的读数提炼成决策记录

先给判据，否则会写成一张「技术选型清单」：

> **一条记录要么改了边界，要么改了失败的姿势。两样都没改的，是配置不是决定。**

按这条判据过一遍前八章的读数，六条留了下来。下表每一行的「读数」都能在
`experiments/eval_baseline.json` 里指到（那张文件由 `eval_run.py --write-baseline` 写出）：

| 读数（当时手上的那个数） | 支持或推翻了什么 | 落进哪条记录 |
| --- | --- | --- |
| 片级：字面路 `span.bm25=0.8333`、向量路 `span.vector=0.7222`、并集 `span.hybrid=0.8333` | 并集**没有**抬图片级，但向量路在改写题上是唯一出路——保留两路，不引外部向量库 | `ADR-0001` |
| 文档级四路全 `1.0`，片级才分得开 | 门不能建在饱和的读数上 | `ADR-0002` |
| 拒答四格 `3／1／0` ＋ 阈值扫描 `sweep.windows_with_zero=0` | 拒答不是调阈值能解决的，要可判定的判据 | `ADR-0003` |
| 答案命中 `answer_hit=0.9444` 而支撑档位只有 `support=0.8686` | 段级引用看不出哪一句无依据 → 按句绑定 | `ADR-0004` |
| 现状片级 `span.hybrid=0.8333`，分辨率 1/24 ≈ 0.0417，迁移差值 +0.0556 | 刚过分辨率的提升换掉七章读数——要人拍板 | `ADR-0005` |
| 提示词成本 `cost.prompt_chars=6452`、题数 `cases=24` | 账按「笔」记，且单位用汉字而不是货币 | `ADR-0006` |

（第三行那条记录里的两个数也在这里：拒答四格是 `refusal.plain.right_refuse=3`、
`refusal.plain.missed=1`、`refusal.plain.over=0`。）

两条对这张表的读法，比表本身重要：

- **不能把「用了什么」写成决定。** 反面例子：「本树用倒数排名融合」——
  融合这件事在 5.4.4 的两条边界读数里其实是**被压缩过**的那一项
  （并集没有抬图片级读数，它改的是名次而不是命中）。把它写成一条「决定」，
  等于把被否掉的那个选项重新扶正。**写记录时要问：这一栏里写的，
  是当时的决定，还是我现在的偏好？**
- **每条记录都要能指到一次实测。** 指不到实测的「决定」不是决定，是偏好；
  偏好可以有，但它是正文里的一句话，不是一条记录。

## 5.9.5 给每条记录写一条失效线

失效线有三类，前八章的读数各自对应一类：

| 哪一类变了 | 已经量到的例子 | 触发之后要重跑什么 |
| --- | --- | --- |
| 语料规模变了 | 片从 25 涨到 5 万、文档级判据不再饱和 | 重取基线（5.6.10）＋重扫阈值表（5.6.7） |
| 换了嵌入或生成模型 | 提示词规模、支撑档位、按句切分都不再可比 | 重算支撑档位（5.5.8）＋重算成本（5.7.6） |
| 线上分布与评测集不同 | 24 条题覆盖不了真实问题的长尾 | 先扩题集再谈门（5.6.3），否则门守的是旧分布 |

写失效线时有三个坑，都是这一轮自己踩出来的：

1. **写成「视情况而定」**。判定不了的条件等于没写——它会让后来者以为有人看着这件事；
2. **写成「以后再说」**。那是待办，不是失效线；失效线要能回答「到什么程度就该重来」；
3. **只写「模型换了要重跑」而不写重跑哪条命令**。命令写不出来，说明这条失效线还没想清楚
   ——本章的做法是把它接到具体的小节上（5.6.10 的重取基线、5.7.5 的作废矩阵）。

最后是一条**诚实**：本树有两条没验证过的东西，它们没有被写成任何一条记录的失效线，
而是并排写进了架构文档的「已知不足」：

- **真实并发用户**：`Service` 有并发闸门与排队上限，但所有读数都在单进程里跑出来，
  真实流量下的排队分布、超时分布、缓存命中率**一条都没量过**；
- **多租户**：语料前缀（`knowledge.`）能区分来源，但两套库不能各带各的权限一起住。

**没验证过的事，写进「未验证」；不要写成结论，也不要写成失效线**——
失效线的前提是「这个决定在什么条件下不成立」，而它们连「成立」都还没验过。

## 5.9.6 让文档自己对账

文档是**手写的第二份清单**：它抄的是树的结构与读数的取值。
这类清单的失效方式在本书出现过两次（`LEDGER` 的逐节表、本章的术语日志），
共同点是——**它看着像被核过**。所以本章给它接了一条会响的路：

```bash
cd zhizhou-v5
python scripts/recap.py --check      # 五条对账：模块双向点名、ADR 六字段、读数引用、行数标注、自描述条数
python scripts/recap.py --self-test  # 28 条夹具（含「删一个模块名就红」「改一行就红」）
python tests/test_recap.py           # 6 条用例（其中四条用第二种实现互相对照）
```

五条各自对应一种**不会报错**的漂移：

1. **文档点名了不存在的模块**——读者照着找，找不到（读文档的人不会来问你）；
2. **树里长了新模块而文档没点名**——图从「现状」退化成一个不标日期的快照；
3. **记录里引用的读数与实跑不符**——那条「当时手上的数」变成回忆；
4. **标的行数与盘上不符**——「这个文件三百多行」这类断言最像真的，因此最难被发现：
   它不改任何行为，只让文档慢慢变成一张过期的照片；
5. **写下的夹具条数、用例条数与实得不同**——它们只在**改脚本**时才该变，
   而改脚本的人往往不觉得「文档里那个数」跟自己有关。

第 3 条是这一章最不一样的地方：它让**读数引用也进了对账**。取数是两级——
先查证据文件打平后的点号键（`span.hybrid`），再按点号逐级走原始结构（`cases`）。
两级的写法在这一段代码里：

```python
# scripts/recap.py —— 在证据文件里取一个读数。**「没找到」与「值为 0」必须分得开**
def lookup(evidence: dict, key: str):
    flat = evidence.get("flat") or {}
    if key in flat:
        return flat[key]
    node = evidence.get("raw") or {}
    for part in key.split("."):
        if not isinstance(node, dict) or part not in node:
            return None
        node = node[part]
    return node if isinstance(node, (int, float)) and not isinstance(node, bool) else None
```

### 它对账的五件事，与它查不到的那一件

```text $ python scripts/recap.py --offline
  模块：文档点名 26 个路径（其中 app 模块 20 个）｜ 树里 20 个
  ADR：6 条（编号 0001–0006）｜ 读数引用 30 条，逐条与 eval_baseline.json 比
  行数：8 处「N 行」标注（8 份文件），逐处与盘上的行数比
  自描述：3 处条数标注（其中夹具 28 条是本脚本实有），逐处与实得比
文档对账：五条全过 ｜ 离线自检通过
```

**它查不到函数名这一级。** 图上写 `ingest.discover()`，而树里把那个函数改了名，
这一关不会响（它只核模块）。这条边界写在脚本的文档字符串里，也写在架构文档里——
**一处已知边界要主动写出来，否则它迟早被当成「这里查过、没问题」。**

### 演示：漂了会红

把架构文档里的 `app/embed.py` 改成一个不存在的名字（模拟一次改名而没同步文档），
再跑同一条命令：

```text
  模块：文档点名 26 个路径（其中 app 模块 20 个）｜ 树里 20 个
  ADR：6 条（编号 0001–0006）｜ 读数引用 30 条，逐条与 eval_baseline.json 比
  行数：8 处「N 行」标注（8 份文件），逐处与盘上的行数比
  自描述：3 处条数标注（其中夹具 28 条是本脚本实有），逐处与实得比
  ✖ docs/architecture.md 点名了 app/embed_renamed.py，而树里没有这个文件
  ✖ app/embed.py 在树里，但没有一份文档点名它——图画的是旧快照

文档对账不通过：2 处
```

两行报错正好是那两条方向：**点错了**与**漏点了**。它们在输出里长得不一样，
修法也不一样——前者去改文档，后者去补文档。**一个只说「不一致」的对账，
拿到报错之后还得自己判断该改哪边。**

### 再演示一次：改一行也红

第四条盯的是另一种漂移，它比模块名更难发现——**因为一个数字看起来永远是「真的」**。
架构文档的最后一节列着本章交付物的行数，把 `scripts/recap.py` 那一格的 557 改成 556
（模拟「改了文件而忘了改这一格」），再跑同一条命令：

```text
  ✖ docs/architecture.md 说 scripts/recap.py 有 556 行，盘上是 557 行——把新数抄进去；别删这个标注：删了就等于把这一栏退回没人核的状态

文档对账不通过：1 处
```

这条报错里有三处刻意的地方：**带上真实行数**（否则拿到报错还得自己去 `wc -l`，
而人一旦要自己再算一次，下次就会选择把这一栏删掉）；**修法写在报错里**
（「把新数抄进去」是一句可以直接照做的事）；**末尾那句「别删这个标注」也是合同的一部分**
——删掉比改错更坏：改错还有人被提醒，删掉是**把这一格退回没人核的状态**，
而表面上它看起来像「这篇文档不再声称任何行数」，安静得多。

一条纪律从这三处浮出来：**给一个数接上会响的路，比把这个数写得更准重要**。
同一批行数第一次出现在 5.9.10 那张表里时，写的是 152 与 245，
而盘上是 138 与 260——四个数里没有一个有路可走（三关都不核它），
直到它们被搬进架构文档的「谁几行」并接上这一条。

### 一个约定：阿拉伯数字是断言，汉字是引用

第五条对账收的是**文档写自己的那两个数**（夹具几条、用例几条）。
这类数字有一个别处没有的坑：**检查自己也会被引用**。我写这一节时顺手引了一句历史——
「抓到一处八条夹具（而脚本当时已有 10 条）」——而对账脚本一视同仁地把它当成断言，
当场报红。**修法不是把历史数字改得好看，而是给它一个看得见的出口**：

> **阿拉伯数字就是断言；要引用一个旧数字，写成汉字（八条夹具）。**

这条约定与前面几条是同一件事：**约定要看得见形状，否则「哪些数字该被核」就只能靠猜**。
报了红之后能一眼看出「这是引用、不是断言」，比每次都要去读检查的源码便宜得多。

### 怎么进的门

`scripts/recap.py --offline` 是提交门的八个离线入口之一（`tools/check_runnable.py` 的
第 5 篇清单）。它进门的理由与 5.8 的验收脚本一样：**一个只在自己这一章里跑过的检查，
等于没有第二次机会**。同时抬高的还有这一篇的三条下限（章 9／模块 20／测试 12）——
**树的规模在长，下限不跟着长，就退化成「只守住一章」。**
抬的时候还抓到一处：章数那条下限**自己停在上一章的值**（8），而 9 ≥ 8，
输出里一个字都不会变——**一条比真值低的下限，只在扫描整个坏掉时才响**。

## 5.9.7 讲法：把「与预设相反」讲成亮点

讲项目最容易讲成流水账，因为流水账不需要取舍。而**与预设相反的读数**恰恰是
最值钱的材料：它证明你真的量过，而不只是把教程跑了一遍。本章接着 3.10 的骨架，
只加一条纪律：

> **结果（Result）那一栏必须带一个反例。没有反例的结果，听起来像抄的。**

四个句子讲一次改动，每个句子对应一个能追问的点：

```text
问题：文档级判据看不出四个检索配置的差别（全是 1.0000）
一次实测：换成片级之后才分开——字面路 0.8333、向量路 0.7222，并集还是 0.8333
一个决定：门建在片级上；并集保留，但它不是「因为更好」而是「因为它在改写题上是唯一出路」
一个代价：多一次成对打分，候选深度要跟着调，而且片级读数比文档级更脆（语料一变就动）
```

三个必须带上的数（缺一个，追问就会落到你答不出的地方）：

| 数 | 为什么必须带 |
| --- | --- |
| **分辨率**（`1/24 ≈ 0.0417`） | 不带它，「提升了 0.02」听起来像个成果 |
| **代价**（多一笔什么、多多少延迟或成本） | 不带它，决定听起来是免费的——而免费的决定不需要拍板 |
| **失效线**（什么条件下该推翻它） | 不带它，对方会以为你把一次实验当成了定律 |

还有一句**不背稿的兜底话**，它救过本章两次：

> 「这个数我是这么量的：跑 `python scripts/recap.py --check`，
> 它读的是 `experiments/eval_baseline.json`，那份文件由评测脚本写出。」

它的作用不是炫耀，而是把「记不清」变成「可复核」——**当对方发现自己能自己去核，
追问的方向就从「你是不是编的」变成「这个量法对不对」**，后者才是你想聊的。

## 5.9.8 追问防御：检索侧十二问

与 3.10 那套按**侧**分工：3.10 防的是 Agent 侧的追问（循环、工具、预算、审批），
本节防的是检索与在线侧的追问。十二问分四类，每类三问，每条都给**有代价**的答法。

**第一类：为什么不用某个现成的东西**

1. 「为什么不用向量数据库？」——语料是 25 片这个量级，索引自持；代价是**自己写索引**，
   而它换来的是每个数都能离线复算。失效线写在第一条记录里：超过 5 万片就重评；
2. 「为什么不用现成的评测框架？」——用了它的**口径**（5.6.1 的四项指标），
   但没引它的库：这一树每个数都要能在不装任何东西的机器上算出来；
3. 「为什么不用托管的重排模型？」——5.4.6 量过：成对打分是自己实现的，
   而它的分数**不可校准**（只用来排序），这一点托管模型也一样。代价是精度换成本，
   这个交换写在第 5.4.6 节那张前后对照表里。

**第二类：这个数是怎么量的**

4. 「0.8333 是从哪来的？」——24 条评测集、`k=3`、片级判据；
   分母写在 5.6.2（**分母不写清，指标就不能比**）；
5. 「1/24 为什么算分辨率？」——5.6.8：题数定了，能分辨的最小差值就定了，
   它**不随容差下降**；
6. 「文档级 1.0000 是真的吗？」——是真的，也正因此它没用：六份文档、`k=3` 时它已经饱和。
   **一个满分读数首先要问「它还能不能动」。**

**第三类：失败的姿势是什么**

7. 「检索不到怎么办？」——三条路径各自的行为写在 5.1.4：不检索／检索到资料／检索不到，
   而「检索不到」那一档要么拒答、要么指出最接近的片；
8. 「模型编了怎么办？」——按句绑定 ＋ `check_citations()`，两把尺子分开报（5.8.8）；
9. 「缓存脏了怎么办？」——参数进键、版本进戳、TTL 兜底（5.7.2），
   而语料戳由进了库的内容算出（5.8.5）——**改一份文档，只有它的片重算**。

**第四类：上线还要补什么**

10. 「并发上去了会怎样？」——并发闸门与排队上限有（5.7.3），但真实流量**没量过**——
    这一点写在架构文档的「已知不足」里，不装作量过；
11. 「多租户怎么加？」——当前用前缀区分来源，权限层没有；要加就得先重定索引键；
12. 「成本怎么估？」——按**笔**记（检索、判档、生成），单位用提示词汉字数（`cost.prompt_chars=6452`），
    不用货币单位——**一个会变的单位不能当口径。**

十二问的共同点：**每条答法都要落到一个数、一条命令或一处「没量过」上。**
答不出来的地方，说「没量过，量它要做什么」比编一个数安全得多。

### 接口契约

对外的面只有两个：**文档的写法**与**对账命令的退出码**。

```bash

python scripts/recap.py --check      # 五条全过 → 0；任一条不过 → 1，并逐条打印
python scripts/recap.py --offline    # 同 --check（提交门的入口名），末尾打印收尾标记
python scripts/recap.py --self-test  # 28 条夹具
```

文档那一侧的契约是五条本文档自己遵守的规矩：模块路径写在反引号里、
读数引用写成 `键=值`（放在反引号里）、每条记录六个字段逐字用那五个小标题、
**文件后面标了 `N 行` 的行数要跟盘上一致**（这一条同时规定了形状：
标注写成 `` `路径` `` 后面跟一个「N 行」，写在同一个行里）、
**「N 条夹具」「N 条用例」要与实得相等，且引用旧数字要写成汉字**
——**约定要看得见形状，否则「哪些数字该被核」就只能靠猜**。
**契约写在正文里，检查写在脚本里**——两边都改，才叫契约。

### 怎么验

`文档对账：五条全过 ｜ 离线自检通过`（漂了会打印 `文档对账不通过：N 处` 并返回非零）。

### 不能破坏什么

1. **`docs/` 里点名的模块必须存在，且树里每个 `app/` 模块都被点名**——两个方向都要成立，
   只查一个方向会漏掉「新模块没进文档」这一半；
2. **`app/` 模块数不许悄悄变少**：对账脚本报的是「树里 20 个」，
   少一个就会同时触发「文档点名了不存在的模块」，两处都会响；
3. **读数引用必须与 `experiments/eval_baseline.json` 逐条相等**——
   基线一变，记录里的数就得跟着改，改不动就说明那条记录该重写；
4. **六字段逐字齐全**：省掉「被否掉的选项」或「失效线」都会让这一关变红；
5. **标了「N 行」的文件必须真的有那么多行**，报错里要带真实行数：
   这一条的修法是**把新数抄进去，不是把标注删掉**（删掉等于退回没人核的状态）；
   同一条也对「一处都没解析到」报错——解析一退化，输出会变成「全部通过」；
6. **写下的夹具条数与用例条数要与实得相等**；报错里要给出「引用旧数字写成汉字」这个出口，
   否则写历史的人只剩两个选择：把旧数字改得好看，或者把检查关掉；
7. **夹具 28/28**：其中必须有「删一个模块名就红」「改一行就红」「夹具少写一条就红」
   与「读数写成 0.8334 就红」——一条只会在顺利时沉默的检查，是没被验过的检查。

## 常见坑

1. **把复盘写成总结**。总结写结果，复盘写「当时还有哪些选项」——后者的读者是改这一版的人；
2. **把架构图画成愿望**。图上写了树里没有的层，接手的人第一件事就是怀疑整张图；
3. **用一张图讲两件事**。入库与问答的时间线不同（一次运行 vs 每次请求），合在一张会误导运维；
4. **节点指不到模块**。图好看而每格都打不开，等于给读者一张海报；
5. **省掉「被否掉的选项」**。后来者会把同一条路再走一遍，而代价你已经付过一次；
6. **省掉「失效线」**。决定被当成永久真理，而它的前提早就变了；
7. **失效线写成「视情况而定」**。可判定的才叫条件，判不了的叫感想；
8. **背景里的数写成现在的数**。「当时的数」与「现在的数」不一样，混起来那条记录就无法复核；
9. **把「用了什么」写成决定**。本树的融合是**被压缩过**的那一项，
   写成决定等于把被否掉的选项重新扶正；
10. **决定里出现「优化」「提升」**。没有对象的动词，读者无法判断改的是哪个边界；
11. **手写的第二份清单不对账**。本树的逐节表、术语日志与本篇文档三次踩中同一形态——
    它们都「看着像被核过」；
12. **只查一个方向**。「文档点了不存在的模块」与「树里有模块没被点名」是两种漂移，
    报错信息也得分开，否则拿到报错还得自己判断该改哪边；
13. **对账只覆盖「有没有」**，不覆盖「对不对」（函数名这一级）。
    这条边界要写出来，否则它迟早被当成「这里查过」；
14. **把没验证过的事写成结论**。真实并发与多租户这两条，本树写进「未验证」，
    而不是写成失效线。

## 面试视角

**问：一个项目做完，你会留下什么文档？**
答：两份，而且都要能被机器核对。一份是架构图，纪律是**每个节点都能指到一个真实模块**
——指不到就不画；还有一张「图外」表，专门装那些不在请求路径上的东西（指标、题集、
对账脚本），因为把它们画进请求路径会让图更完整也更假。另一份是决策记录，
每条六栏，其中两栏最容易被省：**被否掉的选项**与**失效线**。
只有结论的记录会被误用，而结论是最容易被误用的东西。

**问：怎么保证文档不会过期？**
答：给它接一条会响的路。我的对账脚本查五件事：文档点名的模块存不存在、
树里每个模块有没有被点名、每条记录引用的读数能不能在**实跑写出的证据文件**里找到且相等、
标了「N 行」的文件是不是真的有那么多行、写下的夹具与用例条数是不是与实得相等
（改一行就红、少写一条夹具也红，而修法是把新数抄进去、不是删掉标注）。

**问：文档里的数字怎么区分「断言」与「引用」？**
答：用形状区分——**阿拉伯数字就是断言，引用一个旧数字写成汉字**。
这不是讲究，是那一条检查咬到我自己之后才补上的：我在正文里引了一句「八条夹具」的历史，
而脚本不知道那是在引用，当场报红。给它一个出口，比让写历史的人去改旧数字便宜。
漂了就非零退出，而它已经进了提交门。它查不到函数名这一级——这条边界我写在文档里，
因为不写出来，它迟早被当成「这里查过」。

**问：你怎么描述一次「与预设相反」的结果？**
答：四句话：问题、一次实测、一个决定、一个代价。比如文档级判据看不出四个配置的差别
（全是 1.0000），换成片级才分开（0.8333 对 0.7222），于是门建在片级上，
代价是多一次成对打分、而且片级读数更脆。**带上分辨率**（1/24 ≈ 0.0417），
否则「提升 0.02」听起来像成果；带上代价，否则决定听起来免费。

**问：为什么你的库里没有向量数据库？**
答：因为语料是 25 片这个量级，自己写索引换来的是**每个数都能离线复算**。
这不是「自研更好」——那条记录里写着失效线：超过 5 万片、需要按权限过滤、
或延迟要求进到毫秒级，就该重评。我不喜欢「我们觉得不需要」这种答法：
它既没量过，也没说清什么条件下会变。

**问：这套东西上线还缺什么？**
答：缺两样，我没量过：真实并发下的排队与缓存命中分布，以及多租户的权限层。
它们写在我的架构文档「已知不足」里，而不是写成结论——**没做过的，不能写成结论。**

## 本章小结

- 复盘不是总结：总结写结果，复盘写**当时还有哪些选项、为什么没选**；
- 架构图的纪律是**每个节点都能指到真实模块**；入库与问答画**两张**，因为时间线不同；
- **图外要有表**：指标、题集、对账脚本不在请求路径上，塞进去只会让图更假；
- 一条记录六个字段，最值钱的两栏是**被否掉的选项**与**失效线**；
- 「背景」收窄成**当时手上的那个数**（能被复核），「后果」换成**可判定的失效线**；
- 判据：**一条记录要么改了边界，要么改了失败的姿势**——两样都没改的是配置；
- 失效线三类：语料规模变了、换了模型、线上分布与评测集不同——每条都要接到具体命令；
- **手写的第二份清单必须自己对账**：模块双向点名、六字段齐全、读数引用对实跑证据、
  **行数标注对盘上实际行数、夹具/用例条数对实得**；报错要带真实值，
  修法是抄新数而不是删标注；引用旧数字要写成汉字（约定要看得见形状）；
- 对账的边界要主动写出来（函数名这一级查不到）；**没验证过的事写进「未验证」，不写成结论**；
- 讲法：「问题 → 一次实测 → 一个决定 → 一个代价」，R 必须带反例，
  三个数必带（分辨率／代价／失效线）；
- 追问防御按侧分工：本节十二问防检索与在线侧，3.10 那套防 Agent 侧；
- 篇收尾三件事（反向核对、术语扫描、交叉引用复核）都做过一遍，本篇 `⬜` 归零。

## 练习

- **基础**：**写一条注定会红的记录**。故意把背景里的一个读数写成错的（比如 `span.hybrid=0.8334`），
  跑对账，记下它报的那一行；再把键名拼错一次，比较两行报错的区别。
  **两行必须长得不一样**，否则你就分不清「数错了」与「键没了」。

- **基础**：**把追问防御过一遍嘴巴**。找一个人（或一个模型）扮演追问者，只问本节十二问里的四问，
  要求每条回答都带上一个数、一条命令或一句「没量过」。

- **进阶**：**给本树再加一条记录**。从 5.1–5.8 里找一条**改了失败姿势**的读数（提示：5.2.9 那一族静默错误、
  5.7.8 的三档降级），按六字段写出来，并让 `recap.py --check` 保持全过。
  写完后回答：你这条记录的被否掉的选项是什么？

- **进阶**：**给架构文档补第三张图**。把「一次发布要动哪几样」画成第三张图（入库 → 重取基线 →
  重扫阈值 → 更新正文数字），并说明它为什么不与现有两张合并。

- **挑战**：**把对账扩到函数名这一级**。用 `ast` 解析 `app/*.py`，把图上写的 `ingest.discover()`
  这类限定名也核一遍，并给出一条「改了函数名就红」的夹具。
  想清楚：为什么这一级比模块级更难做对？（提示：重命名是重构的常态。）

- **挑战**：**压测那两条「未验证」**。给 `Service.handle()` 写一个并发脚本，
  量出排队分布与超时分布，再决定它们是进「已知不足」还是进一条记录。
  提示：量出来的东西**可能推翻**某条现有记录——这正是失效线的用法。

- **挑战**：**替你自己的项目写三条记录**。每条六栏齐全，其中至少一条是「不做某个东西」的决定；
  然后逐条问：如果明天有个更快的模型出现，这条记录要不要改？改哪一栏？
