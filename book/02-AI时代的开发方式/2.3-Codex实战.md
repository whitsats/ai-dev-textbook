# 2.3 Codex 实战：云端与本地的工作流

> **本章导读**：2.2 用 Claude Code 走完了一条闭环：选入口 → 只读熟悉 → 写工单 → 控权限 →
> 走 R-P-I-V-R-D → 隔离改动 → 交付。这一章换一个工具，讲的**不是另一套闭环**，而是同一套闭环
> 在另一组默认姿态下的样子。
>
> 两个工具的能力高度重叠，都会读项目、改文件、跑命令。真正的差别不在「谁更聪明」，而在三件事：
> **它默认允许自己做什么（沙箱）、什么时候必须停下来问你（审批）、以及它在哪台机器上跑（本地还是云端）。**
> 这三件事决定了同一个任务在两个工具上的安全缺口完全不同。
>
> 所以本章不重讲闭环（闭环与工单模板见 2.2.4、2.2.5），只写 Codex 侧独有或写法不同的部分：
> 两层安全控制怎么写、联网为什么默认关着、域名规则怎么读、把它放进脚本会发生什么、
> 代码审查为什么改不动你的工作区、云端的两阶段运行模型，以及一个任务该放本地还是放云端。

## 学习目标

- [ ] 用「我想让它看到什么、改什么、在哪里跑」三个问题选对入口（IDE / CLI / 应用 / 云端）
- [ ] 说清沙箱与审批各决定什么，并写出一份可解释的默认组合，而不是抄一份别人的配置
- [ ] 让写权限扩展到第二个目录，而不必打开完整访问
- [ ] 配出一份「开网但不放开」的域名规则，并解释 `*.` 与 `**.` 的差别、为什么 `deny` 压 `allow`
- [ ] 说清 `network_proxy` 为什么不能自己给你网络，以及它**管不到**哪几类流量
- [ ] 用 `codex exec` 把一次只读分析放进脚本，并让输出可被下游消费（JSONL 与结构化输出）

- [ ] 把一份云端产出的 diff 拉回本地，并在它打不上时安全地退回去
- [ ] 对同一个任务做出「本地还是云端」的决定，并写出理由

## 2.3.1 它是什么：同一个形状，不同的默认姿态

官方对 Codex CLI 的定义很短：**在本地终端里运行的编程代理，可以在你选定的目录中读取、修改和运行代码**；
IDE 扩展则与代码并排工作，也可以把较长的任务**委派给云端**。

把它和聊天窗口并排，差别和 2.2 讲的一样，是「给任务」和「给代码片段」的差别：

| | 聊天机器人 | Codex |
| --- | --- | --- |
| 你给什么 | 一个问题 | 一个任务 |
| 它做什么 | 输出建议 | 读项目 → 定计划 → 改文件 → 跑检查 → 汇报 diff |
| 上下文从哪来 | 你粘贴的 | 它自己去项目里找 |
| 谁运行代码 | 你 | 它（在你划定的边界内） |
| 谁验收 | 你 | 先跑一遍，**但结论仍然是你下** |

### 最容易用错的定位

最危险的定位是「反正它会写，全交给它」。原因和 2.1 那条判据一致：
**它不知道你没有写出来的业务规则、历史包袱、线上约束与合规要求。**
你没有说的约束，它不会替你遵守。

经验法则只有一句：

> 💡 **提示**：**越容易回滚、越容易自动验证、影响面越小的任务，越适合交给它；
> 越不可逆、权限越高、越依赖业务判断的任务，越应该由你主导。**

| 适合直接交 | 不适合直接交 |
| --- | --- |
| 读陌生项目、生成项目导读 | 改生产数据库结构 |
| 解释函数、模块与调用链 | 执行不可逆的删除命令 |
| 定位有明确报错的 bug | 自动部署到正式环境 |
| 在明确范围内加一个小功能 | 处理未脱敏的隐私数据 |
| 给已有逻辑补单元测试 | 读取、复制或提交密钥 |
| 重命名、迁移、格式统一等机械改动 | 在不了解算法的前提下改科研模型核心逻辑 |
| 写 PR 风格的代码审查意见 | 在没有测试的前提下重构整个项目 |
| 查 lint / 类型 / 构建失败的原因 | 自动合并 PR |

### 入口：四个面，一个问题

Codex 有四个入口，能力来自同一套代理，差别在「它能看到什么、在哪运行」：

| 入口 | 它能看到 | 它在哪里运行 | 适合 |
| --- | --- | --- | --- |
| IDE 扩展 | 当前打开的文件、选中的代码 | 你的机器 | 边写边问、前端与 UI 任务；也可把长任务转给云端 |
| CLI | 终端与整个工作目录 | 你的机器 | 跑命令、读日志、写脚本、脚本化调用 |
| 应用（桌面） | 项目目录与多个仓库 | 你的机器 | 长时间盯着一个任务、看 diff 面板 |
| 云端 | 已推送的仓库 | OpenAI 管理的隔离容器 | 后台长任务、并行、先审 diff 再开 PR |

选入口不用背表，问一句话：

> **我希望它看到什么、改什么、在哪里运行？**
> 想让它看当前文件和选中代码 → IDE；想让它跑命令、读日志 → CLI；
> 想在后台跑长任务、产出可审查的改动 → 云端；想接外部系统（issue、文档、数据库）→ 先考虑 MCP，但只接必要的工具。

新手的三条推荐顺序（按你主要做什么）：

```text
写 Python / 科研代码 / 脚本      → IDE 扩展 → CLI → 云端
做前端 / 网页 / App 页面         → IDE 扩展 → 应用 → 云端
做 GitHub 项目 / 团队协作 / 长任务 → 应用或云端 → IDE → CLI
```

### 十二条纪律里与本章相关的几条

这份工具的使用纪律里，有一半是通用的（先只读、先计划、要验证、小步提交、不要在主干上大改、交付要能接手），
这些在 2.2 已经讲过，不再重复。与本章直接相关的只有四条，后面各节逐个展开：

1. **不要随手打开完整访问，也不要用 `--yolo`**（2.3.2）
2. **外网、密钥、数据库、生产环境默认拒绝或严格限制**（2.3.3）
3. **长任务可以先想清楚它在哪跑**（2.3.8、2.3.9）
4. **产出要可解释、可复现、可验证、可回滚**（2.3.7、2.3.11）

### 安装与服务端前置

官方给了三条安装途径，选一条即可（不需要同时装）：

```bash

# ② npm（需要 Node.js 18+）

npm install -g @openai/codex

# ③ Homebrew（macOS）

# 装完先确认：codex --version            # 能打印版本即安装成功
```

第一次运行 `codex` 时选登录方式；不登录则只能在已配置 API key 的场景下使用。

> ⚠️ **注意**：不要用「第三方供应商切换工具」来配服务端。那类图形工具会绕开官方的登录与授权链路，
> 出问题时你既拿不到官方日志，也不知道自己的密钥被写到了哪里。
> 自定义供应商要走官方配置文件（第 2.5 节会讲配置的层次与落地位置）。

## 2.3.2 两层安全控制：沙箱定边界，审批定停顿时机

官方把这两个概念分开说，而且强调它们是**不同的控制、要一起用**：

- **沙箱模式（sandbox mode）**：命令在技术上**能做什么**——能写哪里、能不能联网。
- **审批策略（approval policy）**：它**什么时候必须停下来问你**——比如要离开沙箱、要用网络、要跑可信集合之外的命令。

这个分工值得画成一张表，因为大多数「我明明设了限制怎么还是出事了」都来自把两者混为一谈：

| | 沙箱决定 | 审批决定 |
| --- | --- | --- |
| 回答的问题 | 技术上碰得到什么 | 何时必须停下来问 |
| 生效方式 | 由操作系统强制（不是由模型自觉） | 由客户端在执行前拦一次 |
| 边界内 | 命令直接跑，不打扰你 | 不触发询问 |
| 越界时 | 命令本身会失败 | 弹出询问，由你决定放不放 |
| 谁兜底 | 操作系统 | 你（或自动复核代理） |

> ⚠️ **最容易误判的一点**：审批是**客户端在它执行前拦一次**，不是模型在生成时自我约束。
> 所以写在提示词里的「不要联网」不是安全边界，它只是请求。真正的边界是沙箱与审批。

### 三种沙箱模式

| 模式 | 它意味着什么 | 什么时候用 |
| --- | --- | --- |
| `read-only` | 能看文件；改文件或跑命令都要先经审批 | 只读分析、看代码、做计划 |
| `workspace-write` | 能读、能在工作区内改、能跑常规本地命令；联网默认关 | **本地日常工作的默认低摩擦档** |
| `danger-full-access` | 没有文件系统与网络边界 | 只在已经外部隔离好的环境里用 |

### 审批策略：`on-request`、`never`，以及一个已经退役的值

| 策略 | 行为 |
| --- | --- |
| `on-request` | 默认在沙箱内自己干，越界时才问 |
| `never` | 不再弹审批 |
| `untrusted` | **已停用**：Codex 与 ChatGPT Work 都不再支持这个可选值 |

> ⚠️ **如果你是从旧教程抄的配置**：把 `approval_policy = "untrusted"` 留在用户级或项目级配置里，
> **可能让客户端直接起不来**。官方给的迁移写法是——想去掉它、保留交互式只读：

```toml
sandbox_mode = "read-only"
approval_policy = "on-request"
```

> 想保留「命令必须逐条批准」的严格行为，则是**不写** `approval_policy`，
> 改在用户级 `~/.codex/config.toml` 里给项目打信任标记：

```toml
[projects."/path/to/project"]
trust_level = "untrusted"   # 命令须审批；同时禁用该项目的本地配置
```

### 常见组合：一份可以照着选的表

| 意图 | 命令或配置 | 效果 |
| --- | --- | --- |
| 自动（预设） | 不加参数，或 `--sandbox workspace-write --ask-for-approval on-request` | 工作区内读、改、跑都不用问；出工作区改文件或要联网时才问 |
| 只读浏览 | `--sandbox read-only --ask-for-approval on-request` | 只读沙箱内可以读和跑；越界动作可能要审批 |
| 只读非交互（CI） | `--sandbox read-only --ask-for-approval never` | 只读沙箱内活动，从不询问 |
| 自动复核 | `--sandbox workspace-write --ask-for-approval on-request -c approvals_reviewer=auto_review` | 边界同「自动」，但符合条件的审批交给复核代理 |
| 完整访问 | `--dangerously-bypass-approvals-and-sandbox`（别名 `--yolo`） | **无沙箱、无审批，不建议** |

一句话记住两个组合的差别：**「完整访问」= `danger-full-access` 加 `never`；
「低风险本地自动化」= `workspace-write` 加 `on-request`。** 后者才是你想要的日常档。

### 自动复核：把「问谁」也变成一个选择

审批是交互的时候，还有一个独立设置决定**谁来审**：

```toml
approval_policy = "on-request"
approvals_reviewer = "auto_review"    # 可选 user（默认）
```

理解它有三条要点：

1. **它只审「本来就需要审批的动作」**——沙箱内的常规操作直接跑，不额外过一遍复核。
2. 复核策略关注四类风险：**数据外泄、凭据探测、持续削弱安全设置、破坏性操作**。
   低与中风险在策略允许时可放行，**严重风险一律拒绝**，高风险要求足够的用户授权且没有命中的拒绝规则。
3. 它**失败时是关闭的（fail closed）**：构建提示、复核会话、解析失败都会拒绝执行；
   超时单独报出，但那一次动作同样不跑。

> 💡 **提示**：自动复核**不改变沙箱边界**，它只是边界上的一类审批接收者。
> 别把它理解成「有它就可以放宽沙箱」——它审的是越界请求，越界的定义没变。

企业还可以用托管配置替换复核策略里与本租户相关的那一节；本地 `[auto_review].policy` 也支持，但托管配置优先。

### 工作区不等于「你的项目文件夹」

三条容易踩空的事实：

1. **工作区包含当前目录，也包含临时目录（如 `/tmp`）**。用 `/status` 可以看到它当前认为工作区包含哪些目录。
   所以「我只授权了项目目录」这句话不成立——临时目录也在范围内。
2. **可写根里仍有受保护路径**：默认 `workspace-write` 下，
   `<可写根>/.git`、`<可写根>/.agents`、`<可写根>/.codex` 都是只读的，而且**递归**（目录下所有内容都只读）。
   `.git` 是文件（指向别处的 `gitdir:` 指针文件）时，解析出来的真实目录同样受保护。
3. **沙箱作用于子进程，不只是内置的文件操作**。它跑 `git`、包管理器、测试运行器时，
   **这些子进程继承同一套边界**。想「只让某个命令出去」，做不到；边界是给整棵进程树的。

### 权限不够时的正确加法

需要让它在第二个目录里也能写，不要直接跳 `danger-full-access`：

```bash
codex --add-dir ../shared-lib          # 优先用这个把可写范围加一个目录
```

配置层面则是显式的可写根：

```toml
sandbox_mode = "workspace-write"

[sandbox_workspace_write]
writable_roots = ["../shared-lib"]
```

如果只是某几个命令前缀需要例外，官方推荐的是**规则（rules）**：让某类命令前缀可以被允许、必须询问或被禁止，
而不是把整个信任边界放宽。这比一次性扩权可控得多，第 2.5 节会讲规则文件的写法。

### 平台前置：沙箱不是处处开箱即用

| 平台 | 沙箱实现 | 前置 |
| --- | --- | --- |
| macOS | Seatbelt，开箱可用 | 无 |
| Linux | `bwrap` + `seccomp` | 需要 `bubblewrap`（`bwrap` 在 `PATH` 里） |
| WSL2 | 走 Linux 实现 | 同上（Ubuntu 24.04 可能还需加载 `bwrap` 的 AppArmor 配置） |
| 原生 Windows | 原生 Windows 沙箱（PowerShell 下） | 在 `config.toml` 的 `[windows]` 段选 `sandbox = "unelevated"` 或 `"elevated"` |

几个必须知道的历史与边界：

- **WSL1 自 Codex 0.115 起不再支持**：Linux 沙箱改用 `bwrap`，而 WSL1 不具备所需能力。
- Linux 上如果找不到 `bwrap`，Codex 会退回内置的辅助程序，但它需要**非特权用户命名空间**可用；
  `bwrap` 缺失或命名空间创建失败时，启动会给出警告。
- 在 Docker 这类容器化环境里跑 Linux，沙箱可能不工作——具体限制见官方平台文档。
- 在 IDE 扩展里可以用一个设置（`chatgpt.runCodexInWindowsSubsystemForLinux`）让它在有 WSL2 时一律跑在 WSL2 里，
  这样命令、审批与文件访问都按 Linux 沙箱语义走，比原生 Windows 路径更接近文档描述。

### 先自检，再信任

不用等出事才发现沙箱没生效，官方给了三条自检命令：

```bash
codex sandbox macos   [--permissions-profile <名>] [--log-denials] <命令...>   # 别名 codex debug
codex sandbox linux   [--permissions-profile <名>] <命令...>
codex sandbox windows [--permissions-profile <名>] <命令...>
codex execpolicy check --rules ~/.codex/rules/*.rules --pretty   # 发规则前先看它判成什么
codex doctor                                                     # 安装/配置/登录状态/运行时体检
```

> 💡 **提示**：`codex sandbox <平台> <命令>` 是把一条命令放到**和 Codex 内部一致**的策略下跑。
> 想验证「我在这个目录里到底能不能写」，这是最直接的实验方式，比读文档快。
> 本章下述用法均按官方文档描述，未在本机实跑（本机没有 Codex CLI）。

### 为什么不该用 `--yolo`

`--dangerously-bypass-approvals-and-sandbox` 会**同时**去掉沙箱与审批。官方只建议在
「外部已经强化隔离」的环境里使用（比如一次性的沙箱虚拟机、隔离的 CI runner）。
`--yolo` 对 Codex 的语义等于「不用问我，按你觉得对的来」——而它在你的个人电脑、科研目录、
含凭据的机器、公司代码库上，都是在拿真实环境做实验。

顺带说清一个反直觉的连带效应：**`--yolo` 会改变网页搜索的默认模式**。
默认情况下网页搜索走的是缓存结果（OpenAI 维护的索引），而不是实时抓取网页，
这样能减少「网页内容里藏着指令」的提示注入面；而在 `--yolo` 或其他完整访问设置下，
网页搜索默认变成**实时结果**。这条设计意图很清楚：**权限越宽，外部不可信内容的入口也越宽。**

## 2.3.3 联网：默认关着，开了也要按域名管

### 默认是没有网络的

对应用、CLI、IDE 的 `workspace-write` 模式：**网络默认关闭**，需要你显式打开：

```toml
[sandbox_workspace_write]
network_access = true
```

为什么默认关？因为它同时挡掉一串风险：提示注入（网页/issue/README 里写的命令）、恶意依赖、
源码与密钥外泄、许可证风险、来路不明的数据。对应的操作纪律是：

1. 默认为关；
2. 只有确实要装依赖、查官方文档时才开；
3. **能白名单就不要全开放**；
4. 不直接执行网页、issue、README 里的命令；
5. 不让它把密钥贴进命令行或日志。

### `network_proxy` 是「约束」，不是「开关」

官方这句话必须逐字读：**这个功能改变的是「已开启的网络如何被强制」，它本身不会给你网络。**

```toml
[features.network_proxy]
enabled = true
domains = { "api.openai.com" = "allow", "example.com" = "deny" }
```

两种状态是**与**的关系，四种组合里只有一种真的被域名规则约束：

| 命令联网 | `network_proxy` | 结果 |
| --- | --- | --- |
| 关 | 开 | 网络仍然是关的，代理什么都不做 |
| 开 | 关 | 网络开着，**直连，域名规则完全不生效** |
| 开 | 开 | 网络开着，出站被域名规则约束 |
| 关 | 关 | 网络仍然是关的 |

> ⚠️ **这是本章最值钱的一条**：只写域名规则、忘了开 `network_proxy`，你得到的是**完全不受约束的直连**。
> 你以为自己做了白名单，实际是给自己发了一张全通证。
> 管理员侧的 `experimental_network` 要求是另一套东西，它能在没有这个功能开关的情况下配置并启动沙箱网络，
> 但同样**不会**在沙箱把网关着的时候把网打开。

### 域名规则的语义：逐条对表

官方把规则说得很短，短到容易记错：

- **精确主机只匹配自己**（`api.openai.com` 不匹配 `v2.api.openai.com`）；
- `*.example.com` 匹配子域（如 `api.example.com`），**不匹配 `example.com`**；
- `**.example.com` 匹配 **apex 本身与所有子域**；
- 全局 `*` 允许任何未被拒绝的公开主机，官方建议把它当作「放开网络」看待；
- **`deny` 永远赢过 `allow`**，而且全局 `*` 只对 `allow` 合法。

为了确认这些规则读起来不自相矛盾，我把它们写成一个几十行的匹配器，逐条对表：

```python
"""按官方文档写下的域名规则，逐条核对每个具体判定（Python 3.10，仅标准库）。"""
import ipaddress, socket

ALLOW, DENY = "allow", "deny"

def match(rule: str, host: str) -> bool:
    if rule == host:                       # 精确主机：只匹配自己
        return True
    if rule.startswith("**."):
        base = rule[3:]
        return host == base or host.endswith("." + base)   # 含 apex
    if rule.startswith("*."):
        return host.endswith("." + rule[2:])               # 不含 apex
    return False

def decide(rules, host):
    """rules: [(模式, 判定)]；白名单优先，deny 压 allow。"""
    deny  = [p for p, v in rules if v == DENY  and match(p, host)]
    allow = [p for p, v in rules if v == ALLOW and match(p, host)]
    if deny:  return "deny", deny
    if allow: return "allow", allow
    return "block（白名单优先：没有命中的 allow 规则即拒）", []

RULES = [("*.example.com", ALLOW), ("**.corp.example", ALLOW),
         ("api.openai.com", ALLOW), ("evil.example.com", DENY)]
for h in ["example.com", "api.example.com", "a.api.example.com",
          "corp.example", "git.corp.example", "api.openai.com",
          "evil.example.com", "other.org"]:
    print(h, "->", decide(RULES, h)[0])
```

实跑输出：

```text
example.com         -> block（白名单优先：没有命中的 allow 规则即拒）
api.example.com     -> allow
a.api.example.com   -> allow          ← 文档只写死了「不含 apex」，多级子域未明确
corp.example        -> allow          ← **. 覆盖 apex
git.corp.example    -> allow
api.openai.com      -> allow
evil.example.com    -> deny
other.org           -> block
```

两条要注意的地方：

1. **「白名单优先」不是你写出来的，是默认值**：`domains` 不配置时行为就是白名单——
   在你没有加任何 `allow` 规则之前，**没有任何外部目标被允许**。
2. **多级子域是文档没说死的地方**。文档只给了「`*.example.com` 匹配 `api.example.com`、不匹配 `example.com`」。
   上表按「后缀匹配」实现，于是 `a.api.example.com` 也命中了。
   这类没写死的语义，请以你自己的实测为准——不要照抄别人的规则表去赌。

### 本地地址与私有网：默认被挡住，而且通配不算例外

默认 `allow_local_binding = false` 时，**回环、链路本地、私有网目的地一律被挡**：

| 情形 | 怎么放行 |
| --- | --- |
| 某一个本地目标（如本地数据库） | 加一条**精确**的本地 IP 字面量或 `localhost` 的 `allow` 规则 |
| 确实要放宽本地/私有网 | 显式设 `allow_local_binding = true` |
| 想用通配规则蒙过去 | **不行**——通配规则不算显式的本地例外 |
| 域名解析结果是本地/私有 IP | **仍然被挡**，即使它命中了 `allow` 名单 |

还有一道尽力而为的防解析重绑定检查：**解析失败或超时一律挡**，解析到非公网地址的一律挡。
官方也明说了它降低风险但消除不了（要彻底消除得在传输层把解析结果钉住），
所以真要防恶意 DNS，还得在网络层做出口控制。

这条规则在本机实测时出了个很有意思的结果。我把两个名字送去解析：

```text
localhost                          -> ['127.0.0.1', '::1']   -> 非公网 -> block
this-name-should-not-exist.invalid -> ['198.18.0.146']      -> 非公网 -> block
```

**一个根本不存在的域名，居然解析到了一个地址**——因为这台机器上有拦截式 DNS/代理，
把不存在的名字也解析到了 `198.18.0.0/15`（保留的基准测试网段，`is_private` 为真）。
于是「解析结果非公网就阻断」这条规则在这台机器上会把**所有**域名都挡掉。

> 💡 **提示**：如果你的机器上开了透明代理或 fake-ip 模式的代理，遇到「Codex 什么网站都连不上」时，
> 先看解析结果：**域名都解析到 `198.18.x.x` 一类的地址，就是这条保护在误伤**。
> 这不说明规则错了，说明它比你想象的更严格——**它按解析结果判，不按域名判**。

### 两项会主动放宽边界的危险设置

| 设置 | 放宽了什么 |
| --- | --- |
| `dangerously_allow_non_loopback_proxy = true` | 代理监听可能暴露到回环之外 |
| `dangerously_allow_all_unix_sockets = true` | 绕过 Unix socket 白名单 |

名字里的 `dangerously_` 不是修辞。第二条有一处细心的设计：即使你请求了非回环绑定，
Unix socket 代理开启时**监听仍然只留在回环**，避免沙箱网络变成通往本机守护进程的远程桥梁。

### 命令网络代理管不到什么（最容易高估的地方）

官方专门列了一段：这个代理过滤的是**本地命令沙箱里跑起来的脚本、程序与子进程**。
它**不**过滤：

- 网页搜索工具
- 应用 / 连接器（connector）的工具调用
- MCP 服务器连接
- 浏览器与 Computer Use 的活动
- **云端任务**
- 客户端与模型、认证之间的请求

这些面各有自己的服务连接、功能开关、工作区策略或环境控制。
浏览器的工具会另外检查托管网络拒绝项与独占允许名单，但那是另一道机制。

> ⚠️ **结论**：把命令域名规则当成本机 AI 的全部出口管控，是**错的**。
> 你会在「命令连不出去」上得到很强的约束感，却在 MCP、浏览器、云端这几条路上完全没有约束。
> 真要收口，得把这些面各自单独设。

### 网页搜索的三种模式

```toml
web_search = "cached"     # 默认：走 OpenAI 维护的搜索索引，降低实时内容的注入暴露
# web_search = "live"     # 同 --search：允许实时浏览
# web_search = "disabled" # 关掉这个工具
```

即使走索引模式，官方也提醒：**搜索结果仍然要当不可信内容看待**。提示注入可以让代理去抓取并执行网页里的指令。

## 2.3.4 本地第一次上手：先确认它现在是什么模式

2.2.3 的那套只读熟悉法（Git 快照 → 只读分析 → 分清事实与推测 → 生成规则文件草稿 → 从小任务开始）
在 Codex 上完全适用，不重复。这里只补 Codex 侧**必须先做、但顺序和直觉相反**的一步。

### 第 0 步不是「设成只读」，而是「看它现在是什么」

官方给的默认推荐是按目录判定的：

- **在版本控制下的目录 → Auto（工作区可写 + `on-request` 审批）**
- **不在版本控制下的目录 → 只读**

而且还有一个前置条件：**在你显式信任这个工作目录之前，它可能先以只读启动**
（通过引导提示或 `/permissions` 切换）。

所以「第一次进项目默认是只读」这句话**是错的**——只要目录在 Git 里，它开局就是可写的自动模式。
正确做法是把状态先看清楚：

```bash
codex            # 启动后先别给任务
/permissions     # 打开权限档选择器，看清楚当前的沙箱模式与审批策略
/status          # 看它当前认为「工作区」包含哪些目录
```

> 💡 **提示**：**只读是一种要显式选择的姿态，不是开局状态。**
> 想做只读分析，就明确用 `--sandbox read-only --ask-for-approval on-request` 启动，
> 或者用 `/permissions` 切过去——**不要指望默认值帮你只读**。

### 安全起步的两条命令

```bash
codex --sandbox read-only --ask-for-approval on-request     # 第一次进陌生项目：只读分析
codex --sandbox workspace-write --ask-for-approval on-request  # 确认任务后再放开写
```

### 后面四步照 2.2.3 做

| 步骤 | 做法 | 产出 |
| --- | --- | --- |
| 只读分析 | 明确「不改文件、不装依赖、不联网」，让它回答项目导读八问 | 项目导读（每条结论标文件路径） |
| 分清事实与推测 | 要求逐条标注「从文件里读到的」与「我的推测」 | 事实 / 推测 / 待确认三列表 |
| 生成规则文件草稿 | 让它先展示草稿，**不要直接写入** | `AGENTS.md` 草稿（人工核对后再落地） |
| 低风险第一改 | 错误提示 + 范围 + 验证三件套 | 一个能跑通的改动 + 验证输出 |

「低风险第一改」的工单写法与 2.2.5 的七要素模板一致，规模小到可以一眼验收：

```text
任务：把 src/utils/date.ts 里 parseDate 的报错信息改得更具体。

范围：
- 只允许修改 src/utils/date.ts
- 允许新增 tests/date.test.ts
- 禁止修改：接口签名、其他文件、任何配置

验收：
1. 传入 "2026-13-01" 时，错误信息包含「月份」二字
2. npm test 全部通过
3. 输出未通过项（若有）
```

### 在编辑器里用：三种自主程度与五个动作

上面走的是终端。如果你日常在编辑器里，Codex 扩展的用法可以压成两件事。

**三种自主程度**（界面名称会随版本微调；官方列的是 Chat、Agent、Agent (Full Access)）：

| 场景 | 选择 | 说明 |
| --- | --- | --- |
| 新手、只想问 | Chat（只读） | 只回答、不动文件 |
| 日常开发 | Agent + 审批 | 默认组合；越界动作会停下来问（2.3.2 那两层在编辑器里同样生效） |
| 高风险项目 | 只读 + 手工执行 | 让它给你命令与说明，你自己跑 |

**五个动作**：解释选中代码、只改当前文件、用 `@文件` 精确补上下文、审计划后执行、对 diff 逐行反馈——
与 2.2.2 的「IDE 五个动作」同源，**提示词直接抄那一节的五段即可**。
Codex 侧还多一条在这份材料里最常用的动作：**把报错和相关文件一起交给它**，让它先判层、再动手。

```text
当前错误：
【粘贴报错】
相关代码在：
@src/api/article.ts
@src/api/http.ts
请先阅读这两个文件，判断错误发生在：参数传递 / 请求封装 / 服务端返回 / 类型定义 / 状态更新，
中的哪一层。
不要修改，先给证据链。
```

截图类前端任务照 2.2.2 的「五轮」做（视觉分析 → 组件与结构 → 限定范围 → 三档宽度验收 → 逐条反馈），
第 1 轮的视觉分析提示词也在那里——**先要分析、不要它直接改**，是这条流程里唯一不能省的一步。

## 2.3.5 规则文件：草稿在这里生成，写法在 2.5

规则文件（`AGENTS.md`）在这一章只做三件事，**完整写法归第 2.5 节**：

1. 用 `/init` 生成**草稿**，而不是让它直接落地；
2. 官方要求人工补充，不允许照抄生成结果——**生成物里可能有猜的**，
   而规则文件一旦写错，后面每次任务都会照着错的来；
3. 记住位置是分层的，并且**离当前目录更近的优先**。

最后一条的实际含义：你可以有用户级、仓库根级、子目录级三层规则，
在子目录里工作时，更近的那份优先。所以「大仓库里某个子包有自己的约定」不需要额外机制，
给它一个更近的文件就行。

## 2.3.6 CLI 实操：把它放进脚本与管道

### 启动与常用开关

```bash
codex                              # 交互式 TUI
codex -C /path/to/repo             # 指定工作目录（--cd）
codex --image shot.png             # 带一张图（截图类任务）
codex --search                     # 本次允许实时网页搜索
codex --ask-for-approval never      # 或 -a never：不再弹审批（沙箱仍生效）
codex --sandbox read-only --ask-for-approval on-request
codex --profile readonly-quiet      # 用命名的配置档案启动
codex -c 'sandbox_workspace_write.network_access=true'   # 单次覆盖配置项
codex resume --last                 # 继续最近一次会话
codex fork --last                   # 从最近一次会话分叉出新会话
```

`-c key=value` 的覆盖**只对这一次调用生效**，也优先于配置文件。这条规则在排查
「我明明改了配置怎么没生效」时非常有用：先在命令行显式覆盖一次，确认行为符合预期，再落进配置。

### 值得记住的斜杠命令与交互动作

| 命令 | 作用 |
| --- | --- |
| `/permissions` | 切换权限档，并查看当前沙箱与可写根 |
| `/status` | 查看工作区包含哪些目录 |
| `/review` | 打开审查预设（见 2.3.7） |
| `/plan` | 先出计划再执行 |
| `/init` | 生成规则文件草稿 |
| `/mcp` | 管理 MCP 连接 |
| `/copy` | 复制最近一次完成的输出 |

> ℹ️ **可用集合因界面而异**：上表里 `/permissions`、`/review`、`/status`、`/copy`、`/exit`
> 是 CLI 侧文档明确列出的；`/plan`、`/init`、`/mcp`、`/goal` 与应用内输入框的斜杠命令一致。
> 不同版本的可用命令会有出入，**以当场按 `/` 弹出的列表为准**，不要照背这张表。

交互上的几个动作，比命令更省时间：

- 输入 `@` 在工作区搜索文件并把路径加入提示词；
- 它工作时按 <kbd>Tab</kbd> 把后续提示**排队**到下一轮，按 <kbd>Enter</kbd> 把新指令**注入当前轮**；
- 空的输入框里连按两次 <kbd>Esc</kbd>，可以**改上一条消息并从那里分叉**；
- 行首加 `!` 直接跑一条本地命令——**在当前审批与沙箱设置下跑**（不是「绕过它跑」）。

### `codex exec`：非交互模式

它默认跑在**只读沙箱**里，这是有意的：脚本化场景最容易在没有人工确认的情况下跑飞。

```bash
codex exec "总结这个仓库的结构，并列出最危险的 5 个区域"
codex exec --sandbox workspace-write "修复 README 里失效的命令示例"
codex exec "生成最近 10 个提交的发布说明" | tee release-notes.md
codex exec --ephemeral "先粗看一遍这个仓库，给下一步建议"     # 不留下会话文件
```

三条设计细节值得记住：

1. **进度走 stderr，只有最终回答走 stdout。** 所以可以直接把最终结果管到下一个工具，
   不用在海量日志里切分。
2. **stdin 与提示词可以一起给**：管道内容会被当作额外上下文，参数里的那句话是指令。
3. **它要求在一个 Git 仓库里运行**（防止破坏性改动），确认安全时可以用 `--skip-git-repo-check` 覆盖。

### 让输出可被下游消费

人类看的输出适合人，不适合 jq。两种机器可读的方式：

```bash
codex exec --json "总结仓库结构" | jq
```

`--json` 会把 stdout 变成 JSON Lines 事件流，事件类型包括 `thread.started`、`turn.started`、
`turn.completed`、`turn.failed`、`item.*` 与 `error`；条目类型覆盖代理消息、推理、命令执行、
文件改动、MCP 工具调用、网页搜索与计划更新：

```jsonl
{"type":"thread.started","thread_id":"0199a213-81c0-7800-8aa1-bbab2a035a53"}
{"type":"turn.started"}
{"type":"item.started","item":{"id":"item_1","type":"command_execution","command":"bash -lc ls","status":"in_progress"}}
{"type":"item.completed","item":{"id":"item_3","type":"agent_message","text":"仓库包含 docs、sdk、examples 三个目录。"}}
{"type":"turn.completed","usage":{"input_tokens":24763,"cached_input_tokens":24448,"output_tokens":122,"reasoning_output_tokens":0}}
```

需要**固定字段**给下游用（任务摘要、风险报告、发布元数据），就上 `--output-schema`：

```json
{
  "type": "object",
  "properties": {
    "project_name":        { "type": "string" },
    "programming_languages": { "type": "array", "items": { "type": "string" } }
  },
  "required": ["project_name", "programming_languages"],
  "additionalProperties": false
}
```

```bash
codex exec "Extract project metadata" --output-schema ./schema.json -o ./project-metadata.json
```

`-o/--output-last-message` 把最终回答写进文件（同时也打印到 stdout），
`--ephemeral` 不留会话文件，`codex exec resume --last` 可以接着上一轮跑——
两段式流水线（先分析、再按分析结果动手）就靠它。

### 在 CI 里怎么放密钥

这是最容易被写错的一处。官方给的规则很硬：

- **不要把 `OPENAI_API_KEY` 或 `CODEX_API_KEY` 设成 job 级环境变量**，
  尤其是在会检出或运行仓库代码的 job 里——构建脚本、测试、依赖的生命周期钩子、
  任何一个被投毒的动作都能读到它。
- GitHub Actions 用官方的 Codex Action，它安装 Codex、起一个 Responses API 代理、按可配置的安全策略运行，
  目的是**减少密钥暴露面**；PR 相关流程用一个只读权限的 job 产出 patch 工件，
  再由另一个拿到写权限、但**拿不到 API key** 的 job 去应用并开 PR。
- 其他自动化环境里，`CODEX_API_KEY` **只给需要它的那一次调用**，并确保同一进程环境里没有不可信代码：

```bash
CODEX_API_KEY=<api-key> codex exec --json "triage 未处理的 bug 报告"
```

- `~/.codex/auth.json` 要当密码对待（里面有访问令牌）：不要提交，不要贴进 issue，不要发到聊天里。
- 能不用长期凭据就不用：若运行时本身有短时工作负载令牌，用联合身份（workload identity federation）代替存密钥。

### 什么时候不适合脚本化

`codex exec` 的定位是「不需要人介入的流水线」。反过来，**需要频繁确认的高风险任务不该塞进 `exec`**：
你会为了让它跑完而把沙箱调宽，而定宽之后照样没人看它的输出。
这类任务应该在交互模式里一条条批，或者在云端跑完 diff 再人工审（2.3.8）。

## 2.3.7 代码审查：一个不改工作区的审稿人

`/review` 的 CLI 里有三种范围，加一种自定义：

| 范围 | 它审什么 |
| --- | --- |
| 对照基线分支 | 找到 merge base，审你这条分支的差异 |
| 未提交的改动 | **已暂存 + 未暂存 + 未跟踪**的文件都在内 |
| 某一次提交 | 那一次提交的确切改动集 |
| 自定义指令 | 按你给的关注点审 |

三条关键性质：

1. **它不改你的工作区**，只报告按优先级排好的、可执行的问题清单。
   这是一条很强的前提——审查可以随时做，不担心它边审边改。
2. 如果**你让它顺手修**，那就回到普通的沙箱与审批设置：它一旦动手，就受和平时一样的约束。
3. 它需要一个 Git 仓库（不在仓库里，`/review` 可能根本不出现）；可以让审查用另一个模型（`review_model`）。

非交互的版本叫 `codex review`，**三个目标互斥，只能选一个**：

```bash
codex review --uncommitted
codex review --base main
codex review --commit <sha> --title "修复分页边界"
```

`--title` 只能配 `--commit`；也可以不给目标，直接把关注点当提示词传进去。

### 审查意见四分类

这一点与 2.2.4 的 V 阶段同源，重新列一遍是因为「审查输出」最容易被写成一堆散文：

| 类别 | 含义 | 你的动作 |
| --- | --- | --- |
| 阻塞 | 会导致错误结果或安全问题 | 必须修，修完重审 |
| 高风险 | 现在能跑，但边界条件下会坏 | 要么修，要么写清为什么接受 |
| 建议优化 | 可读性、结构、命名 | 排期，不进这次提交 |
| 测试缺口 | 没有被覆盖的路径 | 转成工单，补测试 |

> ⚠️ **定位要摆正**：审查是**找问题**，不是**验收**。
> 一份没有阻塞项的审查报告，只说明「在它的视野里没发现问题」，
> 不说明功能满足需求、也不说明验收标准达成了。验收永远由可执行的判据说话（1.14）。

## 2.3.8 云端：隔离容器与两阶段运行

### 为什么用云端

| 理由 | 具体含义 |
| --- | --- |
| 并行 | 长任务各占一个环境，不占你的机器，同时推进几件事 |
| 可复现的环境 | 依赖、工具、变量、setup 步骤写进环境配置，谁跑都一样 |
| 先审再合 | 先看摘要与 diff，再决定要不要开 PR |
| 离开工位也能推进 | 从网页或终端提交与查看 |

### 两阶段运行模型：这是云端最需要记住的一件事

```text
setup 阶段 ──▶ agent 阶段
  可联网          默认离线
  可用 secrets      secrets 已被移除
```

官方说明的要点，逐条对照：

1. 云端任务在 **OpenAI 管理的隔离容器**里跑，接触不到你的主机与无关数据；
2. 任务会**检出指定仓库的分支或提交**，跑 setup 脚本、应用网络规则，然后在隔离环境里执行；
3. **setup 阶段可以联网安装指定依赖；agent 阶段默认离线**，除非你为该环境显式开启联网；
4. **为云端环境配置的密钥只在 setup 阶段可用，进入 agent 阶段之前会被移除**。

第 4 条最容易被误读成「云端很安全，密钥放进去没事」。正确的理解是：

> **隔离与权限机制是真的，但你的原则仍然是「最小权限、最少数据、最少联网」。**
> 密钥在 agent 阶段不可见，恰恰说明 agent 阶段的代码**不可能用到它**——
> 如果你的构建或测试需要密钥，那个需求要在 setup 阶段里解决，而不是把密钥一路带下去。

### 从哪里把任务交出去

云端任务可以从这些地方发起：**网页、GitHub、GitLab、Linear、Slack**。
从终端也可以：

```bash
codex cloud            # 交互式选择
codex cloud exec       # 直接提交一个任务
codex cloud list       # 列出最近的云端任务（--json 给自动化用）
```

云端环境里跑出来的改动，可以用 `codex apply` 应用到本地仓库：
它把最近一次云端会话的 diff 打到你本地，打印被改动的文件，
**并且 `git apply` 失败时（比如冲突）以非零退出码结束**。

### 云端联网是另一套控制

别把本地的域名规则套到云端上：云端有它自己的开关——要么完整联网，要么给一份域名允许名单，
入口在 agent internet access 那套设置里。两套机制是分开的，改一处不会影响另一处。

## 2.3.9 本地还是云端：一张决策表

| 判据 | 选本地 | 选云端 |
| --- | --- | --- |
| 数据 | 含未脱敏数据、私有文件、本地数据库 | 公开仓库、明确任务，不需要本地私有数据 |
| 环境 | 需要 GPU、本地服务、GUI、实时日志、频繁手工调试 | 环境可以用脚本重建；不需要本地硬件 |
| 节奏 | 要反复打断、改方向、看实时输出 | 后台长任务、并行处理多个 issue |
| 交付 | 你要自己看每一步 | 先审 diff 再开 PR |
| 隔离 | 你能严格控制网络与文件范围 | 希望实验在隔离容器里做，不碰本机 |

相应的代价也说清楚：

- **本地**：快、上下文近、能用本地环境；风险是**权限给大了会影响本机**（2.3.2 那两层就是为此存在的）。
- **云端**：隔离、可并行、适合后台与 PR 流程；局限是**看不到你本机未上传的文件**，
  不适合依赖本地硬件或 GUI 的调试，而且**环境没配好时最常见的表现是「它就是跑不起来」**。

> 💡 **提示**：多数真实工作不是二选一，而是**分工**——本地做拆解与决策，云端做能并行的实现，
> 拉回本地验收。2.3.11 就是这个分工的一个完整例子。

## 2.3.10 一个任务，两个工具：怎么选、怎么切

两个工具的能力面几乎重合，所以「选哪个」这个问题的答案往往不是选一个，
而是**看清楚各自的默认姿态，然后把任务放到缺口更小的那一边**。

| 维度 | Claude Code（见 2.2） | Codex |
| --- | --- | --- |
| 默认姿态 | 个人订阅内置起始是自动模式；企业/API key 场景每次问 | 按目录判定：Git 目录默认 Auto，非 Git 目录只读 |
| 权限模型 | 权限模式 + 规则三档（`deny` → `ask` → `allow`） | 沙箱模式 + 审批策略 + 规则；**OS 强制**沙箱边界 |
| 网络 | 沙箱提供网络隔离，平台有限制（原生 Windows 不支持） | 默认关；开了还要 `network_proxy` + 域名规则；平台各有实现 |
| 审查 | 由对话驱动的自审 | 独立的 `/review`，**明确不改工作区**，可非交互 `codex review` |
| 云端 | 有托管环境 | 两阶段模型（setup 可联网、agent 离线，密钥不出 setup） |
| 脚本化 | 有非交互入口 | `codex exec`：默认只读、stdout/stderr 分离、JSONL、`--output-schema` |
| 配置落点 | 规则文件与设置 | `config.toml` + `AGENTS.md` |

选型的经验法则：

- **要「审查但不许动手」** → Codex 的 `/review` 更省事（性质上就不改工作区）。
- **要「脚本里跑一次只读分析」** → `codex exec`（默认只读，还带 JSONL 与结构化输出）。
- **要「明确的 OS 级边界，还要能自己试」** → Codex 的沙箱 + `codex sandbox` 自检。
- **要「权限规则细到命令前缀」** → Claude Code 的三档规则更直接。
- **两边都别急着重配**：先用默认档跑一次低风险任务，看它的默认姿态，
  再决定要不要加限制——**先观察，再收紧**比反过来安全。

最重要的一条不是选哪个工具，而是：

> **同一套闭环 + 各自的默认姿态。**
> 闭环（阅读 → 计划 → 实现 → 验证 → 审查 → 交付）不因工具而变；
> 变的是「它默认能做什么」，而这一层必须你自己去看、去设。

## 2.3.11 综合示例：本地拆解、云端并行、拉回验收

这一节把前几节接起来。任务仍然来自知舟博客 API（1.15），但**刻意选一个不会与 2.2.11 重叠的形态**：
2.2.11 演示的是本地走完一条 R-P-I-V-R-D；这里演示的是**分工**——本地拆解，云端并行两件互不冲突的活，
再拉回本地验收。

### 背景与任务

知舟的评论模块有两件小事要修，它们互不冲突，适合并行：

- **A**：楼层号的并发问题没有回归测试——现在只有一条「顺序创建」的测试，一旦有人把并发计数改回内存变量，测试不会失败。
- **B**：README 的接口清单已经和真实路由不一致（多了一个已删除的接口，少了一个新增的）。

为什么这样切：**A 与 B 改的文件不重叠**，并行不会互相覆盖；两件事都可以用自动判据验收，
不需要业务判断。这两条正是 2.3.9 里「适合云端」的条件。

### 第一步：本地只读拆解（不写代码）

```bash
codex --sandbox read-only --ask-for-approval on-request
```

```text
只读分析，请不要修改任何文件、不要安装依赖、不要联网。

目标：为下面两件事划出改动范围，并说明依据。
A. 给评论楼层号的并发安全性补回归测试
B. 让 README 的接口清单与真实路由一致

请回答：
1. A 涉及哪些文件（测试文件与它依赖的模块），并发安全目前由哪段逻辑保证？
   把关键引用的文件路径与行号列出来。
2. B 请逐个对比 README 的接口清单与 app/routers/ 下注册的路由，
   给出「README 有但代码没有」和「代码有但 README 没有」两张表。
3. 这两件事的文件范围有没有重叠？
4. 哪些结论是你从文件里读到的，哪些是推测？分开列。
```

产出预期是三样东西：A 的文件清单、B 的两张差异表、以及一份「事实 / 推测 / 待确认」三列表。
**如果它在第 3 问上给出「没有重叠」，那正是可以并行的依据**——这个结论必须来自文件，不能来自感觉。

### 第二步：写成两条云端任务

云端环境需要一次性的环境配置（依赖、工具、变量），之后每条任务都在这套环境里跑。
两条任务分别提交，环境相同、改动范围不重叠：

```text
任务 A（测试）：
- 背景：评论楼层号在并发创建时可能重复，目前只有顺序创建的测试。
- 范围：只允许修改 tests/ 下的测试文件；禁止修改 app/ 下的实现代码。
- 要求：新增的测试必须能在「把楼层计数改回内存变量」时失败，
        并在正文里说明你是怎么验证这一点的。
- 验收：pytest 全绿；新测试单独跑一次；给出失败复现的说明。

任务 B（文档）：
- 背景：README 的接口清单与 app/routers/ 下真实注册的路由不一致。
- 范围：只允许修改 README.md；禁止修改任何代码。
- 要求：按「已在代码中注册」为准修订清单，逐条给出你据以判断的路由注册位置。
- 验收：清单与路由逐项对齐；不改动其他段落。
```

两条任务都要在提示词里写清「**不要顺便重构**」——这正是 2.2.10 那类翻车的首要成因。

> ⚠️ **云端的边界要提前想到**：agent 阶段默认离线。任务 A 如果需要一个 setup 阶段没装上的包，
> 它**在 agent 阶段装不了**，会以「跑不起来」告终。所以环境的 setup 步骤必须覆盖测试所需依赖，
> 这件事要在提交任务之前确认，而不是等它失败。

### 第三步：审 diff（不急着合）

拿到云端结果后按固定顺序看，不要只看摘要：

| 检查项 | 看什么 | 不合格的样子 |
| --- | --- | --- |
| 范围 | 改动文件是否落在任务允许的范围内 | 顺手改了实现代码 / 改了别的文档 |
| 测试有效性 | 新测试是否真的能失败 | 断言写成「调用不报错」；或改了既有测试来让它过 |
| 证据 | 是否给出了实际执行过的命令与输出 | 只有「测试通过」四个字 |
| 未验证项 | 有没有如实列出没验证的部分 | 全部「通过」却没说环境 |
| 回滚 | 这次改动的回滚方式 | 说不出来 |

### 第四步：把云端 diff 拉回本地

两条任务都过了审，用 `codex apply` 把改动应用到本地仓库。此时**本地可能已经有你自己的改动**，
所以要先理解「打不上」时到底发生了什么。下面这套行为在 git 2.54 上逐条实测得到：

| 命令 | 本地有冲突改动时的行为 |
| --- | --- |
| `git apply --check <补丁>` | 只试不打，退出码 1，工作区不变 |
| `git apply <补丁>` | **原子**：退出码 1，**所有文件都不动**（实测其中能打上的那个文件也没被改） |
| `git apply --3way <补丁>` | **不原子**：退出码同样是 1，但**能干净打上的文件已经落盘，而且写进了索引**，只有冲突的那份留下冲突标记 |

实测的关键片段：

```text
# 普通 apply：一个文件能打、一个冲突
退出码=1
f1.txt 第2行=b          ← 未被改动
f2.txt 第2行=Y-local    ← 我自己的改动仍在

# --3way：同一份补丁
退出码=1
f1.txt 第2行=B-cloud    ← 已经改了！
f2.txt 含冲突标记=1
索引里的 f1=B-cloud      ← 索引也被改了
```

> ⚠️ **这是脚本化里最危险的一类信号**：`--3way` 的退出码 **1** 通常会被脚本理解成「什么都没发生，可以重试」，
> 但它可能已经改了工作区与索引。`codex apply` 的文档只说「`git apply` 失败时非零退出」，
> **并没有说这不是部分应用**。所以：要么用普通 `git apply` 的原子语义，要么在 `--3way` 之后**先看 `git status` 再决定**。

还有两个连带的操作事实：

1. **工作区有未暂存改动时，`--3way` 直接拒绝**：报 `error: <文件>: does not match index` 并退出 1。
   它需要索引里的内容做三方合并——所以要么先 `git add` 自己的改动，要么就接受「它会这样失败」。
2. **撤销一次 `--3way` 不能只用 `git checkout -- <文件>`**：
   那个命令从**索引**恢复，而索引已经被这次 apply 改过了。实测：

```text
git checkout -- f1.txt       → f1 仍然是 B-cloud（因为索引里也是 B-cloud）
git checkout HEAD -- f1.txt  → f1 回到 b        ← 要显式指定 HEAD
```

完整的撤销（撤掉云端改动、保留我自己的改动）：

```bash
git checkout HEAD -- <干净打上的文件>     # 显式从 HEAD 恢复，而不是从索引
git checkout --ours <冲突的文件> && git add <冲突的文件>
git reset                                 # 取消暂存，回到「只有我自己的改动」的状态
```

> 💡 **提示**：**别把「失败」和「没改动」当成同一件事。** 这条在 2.2.6 讲权限时出现过一次，
> 在这里又出现了一次——只不过主角从权限规则换成了补丁应用。
> 判据是一样的：**结束后必须看状态，而不是看退出码。**

### 第五步：本地验收后才交付

```bash
pytest -q                              # 测试全绿
ruff check . && mypy app               # lint 与类型检查
git diff --stat                        # 改动范围与任务一致
curl -s localhost:8000/openapi.json | python -m json.tool | head   # 路由清单与 README 对齐
```

全部通过后再开 PR，PR 描述里写清三件事：**改了什么、怎么验证的、怎么回滚**。
这一步和 2.2.11 的 D 阶段是同一件事，不重复展开。

> ⚠️ **本节示例的执行边界**：本机没有 Codex CLI，也没有云端账号，
> 所以两条云端任务的**运行结果未实跑**，写的是提交方式与审查清单；
> 第四步里 `git apply` / `--3way` 的三种行为、索引被改写、以及 `HEAD` 与索引两种恢复来源的差别，
> 均在本机 git 2.54.0 上**逐条实跑**，输出即上文所示。

## 常见坑

| 现象 | 真实原因 | 修法 |
| --- | --- | --- |
| 客户端启动就报错 / 起不来 | 配置里留着已停用的 `approval_policy = "untrusted"` | 删掉它，或按 2.3.2 换成 `sandbox_mode = "read-only"` + `on-request`，或改 `trust_level` |
| 写了域名规则，网络依然全通 | 只开了域名规则，没开 `network_proxy`（两者是「与」的关系） | 同时开 `features.network_proxy` 与 `sandbox_workspace_write.network_access` |
| 开了 `network_proxy`，网络还是不通 | 只开代理不会给你网络 | 先开命令网络，再用代理去约束它 |
| `*.example.com` 不匹配 `example.com`，以为规则写错了 | `*.` 本来就不含 apex | 要连 apex 一起覆盖就用 `**.example.com` |
| 想让本地数据库联调，加了通配规则还是被挡 | 通配规则**不算**本地例外；解析到私有地址的也会被挡 | 加精确的 IP 字面量或 `localhost` 规则；确实要放宽再开 `allow_local_binding` |
| 以为命令域名规则管住了全部出口 | 它只管沙箱里跑起来的命令与子进程 | 网页搜索、MCP、浏览器、云端任务、模型请求各有自己的控制 |
| 以为「只授权了项目目录」 | 工作区还包含临时目录（如 `/tmp`） | 用 `/status` 看它到底把哪些目录算作工作区 |
| 让它在工作区里改 `.git` 下的东西，改不动 | `.git`、`.agents`、`.codex` 在可写根里也是只读，且递归 | 这不是故障，是保护；要操作 Git 元数据就自己做 |
| 以为沙箱只管内置文件工具 | 子进程继承同一套边界 | 排查「这条命令为什么出不去」时，把整棵进程树都算上 |
| 非 Git 目录里也指望它自动可写 | 非版本控制目录的推荐默认是**只读** | 先 `git init`，或显式用 `--sandbox workspace-write` |
| 第一次进项目就以为它只读 | Git 目录下默认是 Auto（可写） | 想只读就显式选，别靠默认 |
| CI 里 `OPENAI_API_KEY` 设成 job 级变量 | 同 job 里任何被投毒的步骤都能读到 | 只给需要它的那一次调用；GitHub Actions 用官方 Action |
| 脚本里用 `--full-auto` | 已弃用（会打印警告） | 改成显式 `--sandbox workspace-write` |
| 为了省事用 `--yolo` | 同时去掉沙箱与审批；还会让网页搜索默认变实时 | 需要写权限就加可写根或规则，不要整体放开 |
| `codex apply` 非零退出后直接重试 | `--3way` 下非零可能已经改了工作区与索引 | 先 `git status`，按 2.3.11 的方式撤销干净再重试 |
| 把 `/review` 的「没有阻塞项」当验收通过 | 审查只找问题，不验需求 | 验收看可执行判据（测试、lint、类型、接口对齐） |

## 面试视角

聊到「你怎么用 AI 写代码」时，能讲清下面五点的人，和只讲「我用了什么工具」的人，
不在一个层次上：

1. **两层控制的区别**：「沙箱定技术上能做边界，审批定何时必须停下来问」。
   再补一句「审批由客户端在动作前拦一次，不是模型自觉」——这句一出口，面试官就知道你不是被工具带着走的。
2. **默认姿态因场景而异**：「Git 目录默认是可写的自动模式，非 Git 目录才是只读」；
   「所以想做只读分析要显式选，不能靠默认」。这类细节说明你真的用过、并且核过文档。
3. **联网的正确关法**：「默认关网络，开了还要靠代理按域名约束」，
   以及「域名规则与网络开关是『与』的关系，只配域名规则等于直连」。
   再能说出「命令代理管不到搜索、MCP、浏览器与云端」，就是另一个层级的答案。
4. **云端的安全模型**：「两阶段——setup 可以联网装依赖，agent 默认离线，密钥只在 setup 可见」。
   然后给出你自己的原则：**正是因为 agent 阶段看不到密钥，所以需要密钥的步骤必须放在 setup**，
   而不是把密钥一路带下去。
5. **失败不等于没发生**：「`git apply` 是原子的，`--3way` 不是；
   非零退出码下工作区和索引可能已经变了，所以看状态而不是看退出码」。
   这条能把「会用工具」和「能在流水线里用工具」区分开。

## 本章小结

1. Codex 与 2.2 的工具能力重合，差别在**默认姿态**：沙箱能碰什么、审批何时停、跑在本地还是云端。
2. **沙箱定技术边界，审批定停顿时机**；边界由操作系统强制，审批只是拦一次，写在提示词里的「不要」不是边界。
3. 三种沙箱模式（`read-only` / `workspace-write` / `danger-full-access`）；
   低风险本地自动化的正确组合是 `workspace-write` + `on-request`；
   `untrusted` 已停用，留在旧配置里可能让客户端起不来。
4. 自动复核只审「本来就需要审批的动作」，**失败时关闭**；它不改变沙箱边界。
5. 工作区不只有你的项目目录（还含临时目录）；`.git`、`.agents`、`.codex` 在可写根里也是只读且递归；
   沙箱作用于**子进程**。
6. **网络默认关**；`network_proxy` 只约束已开启的网络，域名规则与网络开关是「与」的关系；
   白名单优先、`*.` 不含 apex、`**.` 含 apex、`deny` 永远压 `allow`。
7. 本地与私有网默认被挡，**通配不算例外**，解析到非公网地址也挡（所以拦截式 DNS 会让全部域名连不出去）。
8. 命令域名代理**管不到**网页搜索、MCP、浏览器、云端任务与模型请求——收口要分别设。
9. `codex exec` 默认只读、进度走 stderr、最终结果走 stdout；`--json` 给 JSONL，`--output-schema` 给固定字段；
   CI 里绝不把密钥设成 job 级环境变量。
10. `/review` 三种范围（基线分支 / 未提交 / 某次提交），**不改工作区**；非交互版 `codex review` 三目标互斥。
11. 云端两阶段：**setup 可联网、agent 默认离线、密钥只在 setup 可用**；`codex apply` 把云端 diff 拉回本地。
12. **`git apply` 原子、`--3way` 不原子**；非零退出码可能已经改了工作区与索引，撤销要显式从 `HEAD` 恢复。

## 练习

- **基础**：在你自己的项目上跑一次「先看模式，再做只读分析」：
  `/permissions` 与 `/status` 各看一次，说清它当前的工作区包含哪些目录；
  然后用只读档让它产出项目导读与「事实 / 推测」两列。
  要求：导读里每条结论都能指到具体文件。
- **进阶**：为你常访问的三个域名写一份域名规则（`allow` 两条、`deny` 一条），
  并回答：为什么只开 `network_proxy` 不够？把你的规则按 2.3.3 的匹配器实现一遍，
  找出至少一个「我以为会命中、其实不会」的域名。
- **挑战**：做一次 2.3.11 的分工实验，拿一个真实需求：
  本地只读拆解 → 云端并行两条任务 → 审 diff → 拉回本地验收。
  要求：写下每一切分的**依据**（为什么这件事能并行、为什么它适合上云），
  并构造一次**故意失败的 `git apply`**，用「看状态而不是看退出码」的方式把它收拾干净。
