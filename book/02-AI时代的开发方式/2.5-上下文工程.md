# 2.5 上下文工程：规则文件、技能、钩子与 MCP

## 本章导读

2.2 与 2.3 讲的是**怎么把任务交给代理**，2.4 讲的是**在编辑器里怎么用它**。
这一章往下走一层，讲一件每次开工都会遇到的事：**每个会话都从零开始**，
而你要它记住的项目事实、要它每次都做的检查、要它够得到的外部系统，分别该放在哪里。

「上下文工程」这个词说的就是这件事——不是把话说得更漂亮，而是决定**什么东西此刻应该在场**。
本章把机制分成三层，判据只有两条：**多久需要一次**（决定要不要常驻，直接吃上下文预算），
**要不要每次都无损执行**（决定它能靠自愿遵循还是得由工具强制执行）。

三层之外还有一件事：把外部系统接进来（MCP）。接得越多不等于越强，
它带来的是**更大的权限面**，所以顺序比数量重要。

一句话先放在这：**规则文件是「希望」，权限与钩子是「保证」。** 把「不要执行某操作」
写在规则文件里，拦不住任何东西——这不是态度问题，是机制问题。

## 2.5.1 会话从零开始：能带过去的三类东西

官方文档在记忆页的第一句就写死了这件事：

> Each Claude Code session begins with a fresh context window.

每个会话都从一个**新的上下文窗口**开始。这一句是所有规则的出发点：模型不会「记得」你昨天说过什么，
它只看到这一轮被放进窗口里的东西。所以问题从来不是「怎么写提示词」，而是**什么东西此刻在场**。

这件事还有更硬的一面——**上下文会爆**。把项目结构、历史决策、所有文档、
所有命令一次性塞进去，结果不是「它知道得更多」，而是它记不住真正要紧的那几条。

于是有三个不同性质的问题，对应三类机制：

| 层 | 机制 | 什么时候在场 | 谁保证它生效 |
| --- | --- | --- | --- |
| 一、常驻上下文 | 规则文件（`CLAUDE.md` / `AGENTS.md` / 路径规则） | 每次会话开始时加载 | **模型自愿遵循**，工具不检查 |
| 二、按需加载 | 技能（Skill）、MCP 工具描述、参考资料 | 用到时才进上下文 | 模型判断相关性，或你手动调用 |
| 三、强制执行 | 权限规则、钩子、沙箱 | 每次匹配到事件时 | **工具本身执行**，模型说什么都不影响 |

这三层不是三个产品，而是**同一个问题的三种解法**：第一类解决「它一开始就该知道」，
第二类解决「它用的时候才需要知道」，第三类解决「不管它怎么想，这件事必须发生」。
分不清这三层，最常见的后果是把强制要求写成第一层——然后奇怪为什么它「不听话」。

### 官方给的时间表：什么时候该加什么

官方 `Extend Claude Code` 一页给了一张「按信号添加」的表，它是本章的骨架，
因为**它把顺序也给了**——这些机制不是一开始全都配上，而是各自有一个可识别的触发点：

| 触发信号 | 该加的东西 |
| --- | --- |
| 同一个约定或命令它**错第二次** | 写进 `CLAUDE.md` |
| 你反复输入**同一段开场提示** | 存成一个可调用的技能 |
| 你把**同一份多步骤流程**第三次贴进对话 | 把它固化成技能 |
| 你反复从**它看不见的浏览器/系统**里复制数据 | 把那个系统接成 MCP 服务器 |
| 它为了找一个符号定义**读了很多文件** | 装上该语言的代码智能插件 |
| 一个**支线任务**把会话刷满你根本不会再看回来 | 交给子代理（第 2.6 章） |
| 你希望某件事**每次自动发生、不必问** | 写一个钩子 |
| **第二个仓库**需要同样的配置 | 打包成插件 |

读这张表和读一条规则是一样的：**先看信号，再看机制**。信号出现之前就配齐，
得到的是没人维护的配置文件——它们会在半年后变成互相矛盾的一堆规则，
而没人知道哪条还有用。

### 两条判据

把上表压成两个问句，遇到任何一条「它应该……」的需求都能用：

1. **要多久用一次？** 每次都要 → 常驻上下文（规则文件）；偶尔用 → 按需加载（技能）。
   这一条决定的是**上下文预算**：常驻的每一行都在每个会话里占位置，按需的不占。
2. **要不要每次都无损执行？** 要 → 第三层（权限或钩子）。
   这一条决定的是**执行力**：第一、二层的规则是「模型读了并选择遵守」，
   只有权限与钩子由工具执行。

第 2 条经常被跳过，但结论很直接：**需要无条件阻断一个操作时，要用 `PreToolUse` 钩子或权限规则**——
因为规则文件是**上下文**，而不是强制配置。
本章后面每一节都会回到这条线。

## 2.5.2 规则文件（一）：`CLAUDE.md`

### 什么时候该写进去

官方给的四个信号，覆盖了日常九成以上的场景：

1. 它**第二次**犯同一个错误；
2. 代码审查发现它**本应知道**的项目事实；
3. 你把**上一轮说过的同一句纠正**又说了一遍；
4. **新同事**也需要这段背景才能上手。

第 4 条是最容易被低估的判据：它把「我个人的偏好」和「项目的共识」分开了。
前者放用户级，后者放项目级——而项目级是要提交进版本库、给全组看的。

反过来，有四类内容**不该**写进 `CLAUDE.md`，它们的去向值得逐条照抄：

| 不该写 | 该去哪 |
| --- | --- |
| 很长的执行流程（多步骤操作） | 技能 |
| 只适用于某一类文件/目录的约束 | 路径规则（`.claude/rules/`） |
| 需要**强制阻断**的要求 | 权限规则或钩子 |
| 每次都不同的临时需求 | 当前任务的提示词 |

判据可以简化成一句话：**`CLAUDE.md` 只放「每个会话都成立的事实与约定」**。
一条内容只要不是每次都需要，就不该占用常驻预算。

### 放哪里：四种位置与加载顺序

官方表格按**从宽到窄**列出了四种作用域（因此项目级的内容会出现在用户级之后）：

| 作用域 | 位置 | 用途 |
| --- | --- | --- |
| 管理策略 | macOS `/Library/Application Support/ClaudeCode/CLAUDE.md`；Linux 与 WSL `/etc/claude-code/CLAUDE.md`；Windows `C:\Program Files\ClaudeCode\CLAUDE.md` | 公司规范、安全与合规要求 |
| 用户 | `~/.claude/CLAUDE.md` | 个人偏好，跨所有项目 |
| 项目 | `./CLAUDE.md` 或 `./.claude/CLAUDE.md` | 团队共享（进版本库） |
| 本地 | `./CLAUDE.local.md` | 个人在本项目的偏好（进 `.gitignore`） |

容易记错的是层级：常见说法是「管理级 / 用户级 / 项目级 / 子目录级」四级，
但官方这里还有一个个人层 **`CLAUDE.local.md`**；
而「子目录」不是第四级作用域，是**另一种加载时机**：

- **工作目录及其所有上级目录**里的 `CLAUDE.md` / `CLAUDE.local.md` 在**启动时**加载；
- **工作目录之下**的子目录里的同名文件**按需加载**——只有当它真的读到那个目录的文件时才进上下文。

而且它们**是拼接进上下文，不是彼此覆盖**。顺序是**从文件系统根目录往下到工作目录**，
所以「离你启动的位置更近」的指令读得更晚、效果上更具体；同一目录里 `CLAUDE.local.md`
排在 `CLAUDE.md` 之后——你的个人备注是那一层最后被读到的东西。

这一步的含义要说透：**没有「项目级覆盖用户级」这种机制，只有先后与内容是否冲突**。
两条互相矛盾的规则同时在窗口里，模型可能任选一条执行。官方把这句写进了最佳实践：
**定期回头清理互相冲突或过期的规则**。

### 写多大：官方给了数字

这是本章最该记住的一个数字：

> **Size**: target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence.

**每份建议 200 行以内。** 注意它说的不是「加载不进来」——再长也会全部加载，
而是**遵循度下降**：规则越多，每条被认真执行的把握越小。这与「上下文会爆」是同一件事的两面。

两条相关机制：

- **导入（import）**：`CLAUDE.md` 里可以写 `@path/to/file` 把别的文件拉进来，
  但**被导入的文件仍然在启动时全量进上下文**——所以导入是**为了组织，不是为了省预算**。
  相对路径按「包含它的那个文件」解析，最多递归四层；代码块与行内代码里的 `@` 不算导入，
  写 `` `@README` ``（带反引号）只表示提到这个路径。
- **HTML 注释会被剥掉**：`<!-- 维护者备注 -->` 这类块级注释在注入上下文前被移除，
  所以在里面写给人看的备注**不额外花上下文**。这是一个很实用的技巧：
  把「为什么这么规定」留在文件里，把 token 省下来。代码块里的注释不受影响。

### 一份文件装不下：根目录只做地图

200 行是给**根目录那一份**定的，不是给项目的规则总量定的。超出这个范围的内容有一个固定分法：

- 根目录的规则文件**只做地图**：项目是什么、目录怎么分工、命令是什么、细节去哪找；
- **详细内容放 `docs/`**（`docs/architecture.md`、`docs/api-conventions.md` 之类），按主题分文件；
- 让 Agent **按需读取**：它在规则文件里看到路径，真需要时会自己去读；
- **每份文档必须有一个明确用途**——否则它不知道该读哪一份，「按需读取」就退化成「随机挑一份」。

这条分法与「技能 vs 规则」是同一个判据的两个应用：**常驻的只放每次都要的事实，
其余的一切都要有「什么时候会被读到」的答案。**

### 改完为什么不生效

一个非常具体、也非常容易被当成 bug 的行为：**`CLAUDE.md` 在会话开始时读一次**，
你在会话中途改文件，**当前会话里不生效**。官方在 prompt caching 页专门解释了这一点
（这也是为什么改完之后要新开一个会话，或者用 `/context` 确认内容有没有进去）。

核对是否加载，官方给了两个办法：

```bash
# 在会话里看当前上下文构成，Memory files 一栏列出已加载的规则文件
/context

# 让 Claude 总结它读到的本项目指令（侧面确认加载与顺序）
> 列出你本次会话加载到的指令来源与顺序
```

### 一个可用的通用模板

下面这份是按官方「写什么」的边界整理的模板。**注意它有多短**——
不是因为它简单，而是因为 200 行是硬约束，而这份模板只用了 40 行左右：
剩下的一半空间应该留给这个项目**独有**的、它猜不到的事实。

```markdown
# 项目说明

## 项目目标
这是一个【项目类型】项目，核心用途是【一句话】。

## 目录约定
- `src/`：业务源码；`tests/`：测试；`docs/`：文档
- `config/`：配置；`data/`：数据目录，**原始数据只读**
- `outputs/`：生成结果，可写入

## 常用命令
- 安装依赖：`【填写】`
- 本地启动：`【填写】`
- 单元测试：`【填写】`
- lint / 类型检查：`【填写】`
- 构建：`【填写】`

## 开发规则
1. 先搜索是否已有类似实现，再新增代码。
2. 不新增依赖，除非先说明必要性、替代方案与风险。
3. 不做与任务无关的重构。
4. 改 API 前必须检查调用方与测试。
5. 新逻辑必须优先补相关测试。

## 禁止事项
1. 不提交密钥、令牌、口令或真实用户数据。
2. 不修改生产配置。
3. 不删除或大规模移动文件，除非任务明确授权。
4. 不通过修改测试来掩盖业务缺陷。
5. 不直接执行 `git push`、`merge`、`rebase`、`reset --hard`，除非明确批准。

## 完成标准
1. 说明改动文件及原因；
2. 运行相关测试、lint 与类型检查；
3. 标出**未验证**项；
4. 说明兼容性、风险与回滚方式。
```

这份模板里有两条值得单独指出，因为它们把「愿望」翻译成了**可核对**的东西：

- 「标出未验证项」——它防的是最常见的一种虚报：把「没跑」说成「应该没问题」。
  可核对的表述是「`npm test` 未运行」而非「测试已覆盖」。
- 「说明兼容性、风险与回滚方式」——它让一次改动在**没有测试覆盖**的地方也有验收路径。

### 科研项目的额外三条

科研项目的模板与通用版相比，多的是**可比性**约束（因为改一处就可能让历史结论作废）：

```markdown
## 可复现性规则（科研项目）
1. `data/raw/` 只读；所有中间数据写入 `outputs/`，不覆盖历史结果。
2. 不得修改模型结构、损失函数、数据划分、评价指标，除非任务明确要求。
3. 不得更改随机种子策略，除非任务明确要求。
4. 不得为了让代码跑通而跳过样本或计算步骤。
5. 任何可能影响论文结论的改动，先停下来说明，不等确认不动手。
6. 先跑小样本 smoke test，再跑正式配置；记录命令、配置、参数与结果路径。
```

### 自动记忆：它自己写的那部分

另一套机制是**自动记忆（Auto memory）**——由 Claude 自己记下你给过的纠正与偏好。
两者的分工官方给了一张表：

| | `CLAUDE.md` | 自动记忆 |
| --- | --- | --- |
| 谁写 | 你 | Claude |
| 内容 | 指令与规则 | 学到的经验与模式 |
| 范围 | 项目 / 用户 / 组织 | 按仓库，**跨工作树共享** |
| 每次加载多少 | 全量 | **前 200 行或 25KB** |
| 适合放 | 编码规范、工作流、项目架构 | 你的偏好、你给过的纠正、它推不出来的项目背景 |

两条使用要点：自动记忆**不是硬规则**，它帮助你跨会话记住偏好，但不能替代约束；
而它的加载有上限（前 200 行或 25KB），所以别把它当成「无限容量的笔记」。
要看它到底记了什么，去会话里问它，或直接读对应文件——**看得见才敢依赖**。

## 2.5.3 规则文件（二）：`AGENTS.md`——同样的事，机制不同

第 2.3.5 节已经说过：Codex 侧的规则文件叫 `AGENTS.md`，草稿用 `/init` 生成。
这一节补上写法与机制，因为它和 `CLAUDE.md` 有一条**关键差别**，不知道这条差别会踩坑。

### 指令链是「拼」出来的，而且每次运行只拼一次

官方文档描述得很具体：Codex 在**启动时（TUI 里通常是每次启动会话）构建一次指令链**，
发现顺序是：

1. **全局作用域**：`~/.codex`（或 `CODEX_HOME` 指定的目录）下，优先 `AGENTS.override.md`，
   否则 `AGENTS.md`，**只取第一个非空文件**；
2. **项目作用域**：从项目根目录（通常是 Git 根）**逐层往下走到当前工作目录**，
   每一层取一份（`AGENTS.override.md` → `AGENTS.md` → 配置里的后备文件名）；
3. **合并顺序**：把各层文件**从上往下拼接**，用空行相连；
   **越靠近当前目录的规则出现在越后面**，因此效果上覆盖前面的。

三条推论，每一条都有实际影响：

- **`AGENTS.override.md` 是一个「临时顶掉」的开关**：需要短期改口径时不必删原文件，
  改完把 override 删掉即可恢复。
- **指令链只在每次运行开始时构建一次**：和 `CLAUDE.md` 一样，**改完要重启 Codex 才生效**。
- **有上限，到顶就停**：合并后的内容达到 `project_doc_max_bytes`（**默认 32 KiB**）后，
  Codex **不再继续添加后面的文件**——注意不是「截断最后一份」，而是后面的文件干脆不进来。
  所以超限时要么把上限调大，要么把指令拆到更靠近的嵌套目录里。

后备文件名也值得知道：仓库里已经有 `TEAM_GUIDE.md` 之类约定时，
可以在配置里加进 `project_doc_fallback_filenames`，让 Codex 把它当指令文件读；
**不在名单里的文件名不会被发现**——改了名字却不改配置，指令会静默失效。

```toml
# ~/.codex/config.toml
project_doc_fallback_filenames = ["TEAM_GUIDE.md", ".agents.md"]
project_doc_max_bytes = 65536
```

### 两份文件的对照

| | `CLAUDE.md` | `AGENTS.md` |
| --- | --- | --- |
| 谁读 | Claude Code | Codex（以及其它遵循该约定的工具） |
| 作用域与顺序 | 管理 / 用户 / 项目 / 本地四级；上级目录启动时加载，子目录按需 | 全局 → 仓库根 → 逐层往下到当前目录；每层一份 |
| 合并方式 | **拼接**，根在上、当前在下 | **拼接**，根在前、当前在后（效果同为「近者更具体」） |
| 生效时机 | 会话开始时读一次 | **每次运行构建一次**指令链 |
| 显式上限 | 建议 200 行（超出降低遵循度） | 默认 32 KiB（**超出则后续文件不加载**） |
| 局部覆盖 | `CLAUDE.local.md`（个人层） | `AGENTS.override.md`（可临时顶掉） |

两条读表结论：**顺序机制几乎一样（都是拼接、都是「近者更具体」），差别在「哪一层能顶掉哪一层」**——
`CLAUDE.local.md` 是**追加**的个人层，而 `AGENTS.override.md` 是**替换**同目录的那一份。

### 一份可用的 `AGENTS.md`

结构与 `CLAUDE.md` 模板同构（官方对「该写什么」的要求几乎一致：
仓库布局、目录职责、运行方式、构建/测试/lint 命令、工程约定、PR 要求、禁止事项、
完成标准）。差别在写法风格，而所有写法都收在同一句上：**短、准、能执行**。

```markdown
# AGENTS.md

## 项目目标
这是一个【项目类型】项目，核心用途是【一句话说明】。

## 目录约定
- `src/`：业务源码；`tests/`：测试代码；`docs/`：项目文档
- `scripts/`：开发与维护脚本；`config/`：配置
- `data/`：数据目录；**不要修改原始数据**

## 常用命令
- 安装依赖：`【填写】`
- 本地启动：`【填写】`
- 单元测试：`【填写】`
- lint / 类型检查：`【填写】`

## 开发规则
1. 优先复用现有组件、工具与模式。
2. 不新增依赖，除非先说明必要性、替代方案与影响。
3. 不做与任务无关的重构。
4. 改 API 时必须检查调用方和测试。

## 禁止事项
1. 不提交密钥、令牌或真实用户数据。
2. 不直接修改生产配置。
3. 不删除文件或大规模移动文件，除非明确授权。
4. 不更改数据库结构，除非任务明确要求。
5. 不绕过失败的测试，也不降低测试门槛。

## 完成标准
1. 说明改动文件与原因；
2. 运行相关测试、lint 与类型检查；
3. 标出未验证项目；
4. 评估兼容性与回滚方式。
```

科研与数据处理项目的额外段落（三段模板合并、去掉了重复项）：

```markdown
## 可复现性规则（科研代码）
1. 不得更改随机种子策略、数据划分与评价指标，除非任务明确要求。
2. 任何可能影响实验结论的修改，必须先停下来说明。
3. 运行实验前先确认配置文件；结果记录命令、git commit、配置与依赖版本。
4. 每改动一处，先回答五句并写进提交信息：是否改变了算法逻辑、是否影响随机性、
   是否改动了数据、用的是哪个配置、哪些结论仍需人工验证。

## 数据处理规则（数据管线）
1. 原始文件只读；所有输出写入 `outputs/`，不得覆盖源文件。
2. 列名、缺失值、单位、时间格式变化时，必须记录映射规则。
3. 清洗前后的行数、列数与缺失率必须输出。
4. 删除、去重、填补等操作必须留审计日志。
5. 处理失败时不允许静默跳过，必须写明失败文件与原因。
```

最后一段还有一个官方独有的用法：`AGENTS.md` 里可以写一个 `## Code Review Rules` 段落，
给 GitHub 上的 Codex 代码审查提供判据。**放在最靠近被审代码的那一份里**——
仓库级检查放根目录，服务专属的放嵌套文件，这与「近者更具体」是同一条原则。

### 两个工具怎么共用一份说明

这是本章最实用的一条：**Claude Code 读的是 `CLAUDE.md`，不是 `AGENTS.md`。**
所以仓库里已经有了 `AGENTS.md`（给 Codex 用）时，不要让两份文件各写一遍——
官方给的做法是**在 `CLAUDE.md` 里导入它**：

```markdown
@AGENTS.md
## Claude Code
`src/billing/` 下的改动走计划模式。
```

这样两个工具读的是同一份项目说明，而 Claude 独有的部分（上面那两行）追加在后面。
官方也允许符号链接（`ln -s AGENTS.md CLAUDE.md`），但**Windows 上建符号链接需要管理员权限
或开发者模式**，所以跨平台更稳的做法是导入。

同一条线上还有两个命令值得记住：`/init` 会读取 Cursor 与 Copilot 的规则文件
（`.cursor/rules/`、`.cursorrules`、`.github/copilot-instructions.md`）并把相关内容并进生成的
`CLAUDE.md`；`/import` 则可以把另一个工具的配置（`AGENTS.md`、MCP 服务器、命令、技能等）
迁移过来。**先用 `/init` 读一遍现有规则，比从空白手写省事，也更不容易漏。**

> ⚠️ **导入的安全性**：项目级规则文件里若导入**工作目录之外**的文件（例如 `@~/.claude/xxx.md`），
> 官方会弹一次确认框列出这些文件——因为那是别人提交进仓库的路径。你个人的用户级文件
> （`~/.claude/CLAUDE.md`、`~/.claude/rules/`）属于你自己写的东西，不会弹。
> 这也说明一件事：**规则文件是会被共享执行的输入，审查它和审查代码一样要紧**。

## 2.5.4 规则文件（三）：按路径与按命令分片

`CLAUDE.md` 的问题是「全量常驻」。文件多了、项目大了之后，就需要**分片**：
让一部分指令只在真正相关时进上下文。两种分片方式各管一头。

### 按路径分片：`.claude/rules/`

官方推荐的做法是把指令拆进项目里的 `.claude/rules/` 目录，**一个文件一个主题**，
文件名能读懂（例如 `testing.md`、`api-design.md`）。规则文件还能**绑定到具体路径**：
在 YAML frontmatter 里声明 `paths`（标准 glob 写法），于是它**只在 Claude 处理匹配文件时加载**。

```markdown
---
paths: ["src/api/**/*.ts", "src/api/**/*.tsx"]
---

## API 层约定
- 处理函数放在 `src/api/handlers/`，一个 handler 一个文件。
- 所有返回值统一为 `{ data, error }`，错误码用 `ApiError` 子类。
- 新增端点必须同时补一条集成测试。
```

这里的取舍很清楚：**常驻的规则每一次会话都在花预算，路径规则只在相关时才花。**
所以「只适用于某一类文件」的约束基本都该走这里，而不是写进 `CLAUDE.md`。

官方在同一个页面里给了一条容易看漏、但很关键的对照：

> Rules load into context every session or when matching files are opened.
> **For task-specific instructions that don't need to be in context all the time, use skills instead.**

也就是说，路径规则仍然是**「会自己进上下文」的那一类**（每次会话，或在匹配文件被打开时），
真正做到「用到才加载」的是技能。判断方法是问一句：**这条指令是「约束」还是「流程」？**
约束（命名、目录、返回值形状）适合规则；流程（检查清单、多步骤操作）适合技能。

> 一处社区反馈值得知道：有使用者报告过 `.claude/rules/` **子目录**里带 `paths` 的规则
> 没有被自动加载（issue #16853）。官方文档没有对子目录布局做额外说明，
> 所以稳妥的写法是把带 `paths` 的规则**直接放在 `.claude/rules/` 顶层**，
> 并用下面这条命令确认真加载了（`InstructionsLoaded` 事件是官方提供的观测点）。

```bash
# 会话里查看已加载的规则文件
/context

# 规则到底有没有在「读匹配文件时」加载：用钩子观测，不靠猜
# （settings.json 里配 InstructionsLoaded，命令写进脚本；写法见 2.5.6 与官方 hooks 参考）
```

### 按命令分片：Codex 的命令规则

Codex 侧的「分片」不是按文件，而是**按命令**。这一层前面没有出现过，
但它是「哪些命令能在沙箱外跑」的判定依据，写代理配置时会直接用到。

规则文件是 `.rules`，语法是 **Starlark**（像 Python，但为安全执行而设计），
放在**某个生效配置层**旁边的 `rules/` 目录里，例如 `~/.codex/rules/default.rules`。
项目级的 `<repo>/.codex/rules/` 只有在项目的 `.codex/` 层**被信任**时才会加载。
规则本身是 `prefix_rule(...)` 调用：

```python
# 允许 `gh pr view` 在沙箱外执行，但每次都要问一下
prefix_rule(
    pattern=["gh", "pr", "view"],          # 命令前缀（按参数列表逐段比对）
    decision="prompt",                     # allow / prompt / forbidden
    justification="查看 PR 允许，但需要审批",
    match=[                                # 自带单元测试：应当匹配的例子
        "gh pr view 7888",
        "gh pr view 7888 --json title,body",
    ],
    not_match=["gh pr --repo openai/codex view 7888"],   # 应当不匹配的例子
)
```

四个要点，每一个都能在别处踩坑：

1. **决策只有三种，且最严的赢**：`forbidden` > `prompt` > `allow`。多条规则命中时取最严的一条，
   所以「多写几条允许规则」不会绕过一条禁止规则。
2. **项目级规则要「信任」才生效**。这一点和 2.3 的沙箱与审批是同一套思路：
   **能改行为的东西必须先取得信任**。
3. **`match` / `not_match` 是写进规则里的自测**：加载时校验，写错了当场报出来——
   这比「上线后发现规则没生效」便宜得多。命令行的 `codex execpolicy check`
   可以在不启动会话的情况下验证一条命令会命中哪些规则、最终决策是什么：

   ```bash
   codex execpolicy check --pretty \
     --rules ~/.codex/rules/default.rules \
     -- gh pr view 7888 --json title,body
   ```
4. **复合命令有两种命运，这决定了一条规则能不能兜住它**。像
   `["bash", "-lc", "git add . && rm -rf /"]` 这种把多条命令塞进一个字符串的调用，
   Codex 的处理是：

   | 脚本形态 | 处理方式 |
   | --- | --- |
   | **线性链条**：只有普通词，用 `&&` `\|\|` `;` `\|` 连接（无变量、无通配、无重定向） | 解析后**拆成单条命令**，逐条比对规则，取最严结果 |
   | 含重定向、`$(...)`、环境变量赋值、通配符、控制流 | **不拆**，整段当作一个 `["bash","-lc","<脚本>"]` 调用比对 |

   第二行是关键：不拆的时候，规则是对**整段脚本**生效的，一条「允许 `git add`」的规则
   自然不会命中它。而第一行给了安全性——官方举的例子正是
   「即使你允许了 `pattern=["git","add"]`，`git add . && rm -rf /` 也不会被自动放行，
   因为 `rm -rf /` 那一段被单独评估」。**这就是「为什么白名单式写法容易出事」的机制性回答。**

把两种分片放在一起看：

| | `.claude/rules/` | Codex `.rules` |
| --- | --- | --- |
| 分片依据 | 文件路径（glob） | 命令前缀（参数列表） |
| 解决什么 | 哪些文件相关的指令此时才需要 | 哪些命令能在沙箱外执行 |
| 何时生效 | 会话开始或打开匹配文件时加载进上下文 | 每次要跑命令时做判定 |
| 是否由模型执行 | 否，进上下文后由模型遵守 | **否，由工具判定**（这一点让它属于第三层） |

最后一行是最容易混淆的地方：**路径规则属于第一、二层（上下文），命令规则属于第三层（强制执行）。**
名字里都有「规则」，但一个影响「模型知道什么」，另一个决定「工具允不允许」。

## 2.5.5 技能（Skill）：把反复粘贴的流程沉淀下来

### 触发信号与它省下了什么

官方给的技能触发信号有两条，都很具体：

- 你**反复把同一段指令、清单或多步骤流程**贴进对话；
- `CLAUDE.md` 里的某一段**已经长成了一个流程**，不再是一条事实。

第二条尤其值得注意：它把「规则文件写不下」这件事变成了**升级信号**——
不是让你把 `CLAUDE.md` 写得更长，而是把那一段搬去技能。

省下的是上下文：**`CLAUDE.md` 每次会话全量加载，技能的正文只在被用到时才加载。**
所以技能是本章第二层的代表：用长参考资料、长清单、长流程时，
把它放技能里，「几乎不花上下文，直到你需要它」。

### 一个技能长什么样

技能是**一个目录**，核心是 `SKILL.md`：YAML frontmatter + 正文。
frontmatter 里的 `description` 决定它**什么时候会被自动加载**（模型按描述判断相关性），
你也能直接用 `/名字` 手动调用。目录名就是命令名。

```markdown
---
description: 审查当前分支相对 main 的改动，聚焦缺陷、边界、安全、性能与测试缺口。当用户要求审查改动、准备提交或要一份 PR 说明时使用。
---

## 当前改动
!`git diff main...HEAD`
!`git log --oneline main..HEAD`

## 审查步骤
1. 先读上面的 diff，再读受影响的测试；缺测试的地方要单独列出来。
2. **先说明这次改动想达成什么**，再点出其中与这个目标无关的改动（范围漂移比 bug 更难被发现）。
3. 按「阻塞 / 高风险 / 建议 / 测试缺口」四类归档，不要混在一起。
4. 每条问题必须附**文件路径与证据**（行号或复现命令）；没有证据的判断标为待确认。
5. 不修改代码，除非用户明确要求。
6. 输出最后给一段「我认为最可能出事的一处」以及它的验证方式。
```

两个细节值得单独说：

- `!`git diff main...HEAD`` 是**动态上下文注入**：Claude Code 在执行技能前先跑这条命令，
  把**输出**填进这一行。所以模型看到的是真实的当前 diff，而不是它猜的。
  这解决了一个常见问题——「让它审查改动，它却凭记忆或凭打开的文件猜改了什么」。
- **`description` 要写清「什么时候用」和「什么时候不用」**。它既是给人看的，
  也是给模型做自动匹配用的：写「审查改动」是关键词，写「当用户要求审查、准备提交、
  要 PR 说明时使用」才是触发条件。

技能目录里还可以放其它文件——脚本、参考资料、模板——按需读取：

```text
.claude/skills/pr-review/
├── SKILL.md          # 必需：说明 + 触发条件
├── scripts/          # 可选：可执行脚本
├── references/       # 可选：长参考资料
└── assets/           # 可选：模板等资源
```

存放位置有两类：**个人级 `~/.claude/skills/<名字>/SKILL.md`**（跨所有项目可用），
**项目级 `.claude/skills/<名字>/SKILL.md`**（进版本库、全组共享）。

还有一条**名字上的变化**必须知道：**自定义命令已经并入技能**。
`.claude/commands/deploy.md` 与 `.claude/skills/deploy/SKILL.md` 现在产生同一个 `/deploy`，
行为一致，老文件继续可用；技能多出来的能力是「支持文件目录」「用 frontmatter 控制谁能调用」
「模型可以在相关时自动加载」。所以**新写的流程一律用技能**，命令只是历史写法。

另外，Claude Code 自带一批**内置技能**（`/run`、`/verify`、`/code-review`、`/debug` 等）。
它们大多按需自动触发，少数（例如 `/verify`）**只在你手动调用时运行**——
把耗时的检查交给你决定何时花预算。

### Codex 侧的技能：同一标准，不同的位置与预算

Codex 的技能建立在同一个开放标准上（Agent Skills），`SKILL.md` 同样要求 `name` 与 `description`。
差别在**从哪些位置加载**与**列表怎么计费**：

| 作用域 | 位置 | 用途 |
| --- | --- | --- |
| REPO | `$CWD/.agents/skills` | 只与当前工作目录相关的技能 |
| REPO | `$CWD/../.agents/skills`、`$REPO_ROOT/.agents/skills` | 共享区域的技能 / 全仓库技能 |
| USER | `$HOME/.agents/skills` | 个人跨仓库的技能 |
| ADMIN | `/etc/codex/skills` | 机器或容器级的默认技能 |
| SYSTEM | 随 Codex 附带 | 官方技能（如 `skill-creator`） |

注意路径是 `.agents/skills`（不是 `.codex/skills`），仓库级扫描是从当前目录**向上到仓库根**逐层找；
同名技能**不会合并**，两个都会出现在选择器里——所以别在不同层放同名技能。
Codex 也支持符号链接的技能目录。

然后是那个很有教学价值的**预算数字**：

> In Codex, the initial list also includes each skill's file path.
> To avoid crowding out the rest of the prompt, this list uses at most **2% of the model's context window,
> or 8,000 characters when the context window is unknown**. If many skills are installed,
> Codex **shortens skill descriptions first**. For large skill sets, Codex may omit some skills
> from the initial list and show a warning.

三句话读出三件事：

1. **初始只装「名字 + 描述」**，正文等你（或它）选中才读——这就是它说的 progressive disclosure；
2. 列表有**硬预算**（上下文的 2%，未知时 8,000 字符），所以**技能不是越多越好**，
   装到超量时**先被牺牲的是描述**；
3. 描述被截短意味着**自动匹配会变差**——技能装了却不再被自动触发，
   而且「省略一部分并给警告」是唯一的提示。所以写描述时要**把触发词放在最前面**，
   官方也建议按这个顺序写。

### 写好一个技能的四条

官方文档与实践给出的取舍其实一致，合并成四条：

1. **一个技能只解决一类问题**，不要做「万能技能」——描述写不准确，自动匹配就会失灵。
2. **输入与输出要说清**：读什么（diff、日志、报告路径）、产出什么格式（清单、Markdown、补丁）。
3. **先把流程人工跑稳，再封装**。技能是流程的固化，不是流程的设计工具。
4. **需要外部状态就注入，不要靠模型猜**：能用 `!`命令`` 拉进来的（diff、`git status`、
   测试输出）就拉进来，这比「请你自己去看」可靠得多。

## 2.5.6 钩子（Hook）：必须发生的事，别指望「记得」

### 三种节奏

官方把钩子事件按**触发节奏**分了三类，这个框架比逐个记事件名有用得多：

| 节奏 | 事件 | 典型用途 |
| --- | --- | --- |
| **每会话** | `SessionStart`、`SessionEnd` | 环境准备、收尾归档 |
| **每轮** | `UserPromptSubmit`、`Stop`、`StopFailure` | 提交提示时补上下文；结束前检查测试是否跑过 |
| **每次工具调用** | `PreToolUse`、`PostToolUse`（以及失败与批处理事件） | 改完就格式化、拦住敏感文件读写 |

实际项目中，钩子能解决的问题收在五类里——超出这五类的需求，先用原则 1 问一句
「声明式的权限规则能不能表达」：

1. **改完自动跑格式化 / lint / 类型检查**（`PostToolUse`）；
2. **拦住敏感文件的读写**（`PreToolUse`，与权限规则同层，但能做更细的判断）；
3. **留审计日志**：谁在什么时候改了什么（`PostToolUse` 追加写日志）；
4. **提交或推送前的确认**：检查测试跑过、检查分支名（`PreToolUse`）；
5. **会话的开场与收尾**：准备环境变量、归档产物（`SessionStart` / `SessionEnd`）。

在此之外还有一批「独立事件」，其中几个和本章直接相关：

- **`InstructionsLoaded`**：`CLAUDE.md` 或 `.claude/rules/*.md` **被加载进上下文时**触发，
  会话开始时触发，之后**按需加载时也会触发**。这是你验证「规则到底有没有加载」的官方观测点。
- **`FileChanged`**：被监视的文件在磁盘上变化时触发（`matcher` 指定文件名）。
- **`PreCompact` / `PostCompact`**：压缩上下文前后触发——长会话里很有用。
- **`ConfigChange`**、**`PermissionDenied`**、**`SubagentStart` / `SubagentStop`** 等。

钩子处理器的类型也不止 shell：官方列出的有**shell 命令、HTTP 端点、MCP 工具调用、
LLM 提示、子代理**。所以「钩子」不等于「写个脚本」，但在教学与工程实践里，
**优先用最简单的形态**——这一点写进了下面的设计原则。

事件全表与每个事件的输入输出模式以官方 `hooks` 参考为准；本章只给判断方法。
契约（stdin 收 JSON、stdout 回 JSON、退出码含义）已在 **2.2.6** 讲过，此处不再重复。

### 该不该做：五条设计原则

下面五条原则值得原样保留，因为它们防的正是「钩子越写越多、最后没人敢动」：

1. **能用权限规则解决的，不要写钩子。** 权限声明式、由工具执行、看得懂；
   钩子是代码，会坏、要维护。
2. **能用简单 shell 检查解决的，不要先用 LLM 钩子。** 能用一条命令判断的，
   就没必要花一次模型调用、还引入不确定性。
3. **钩子必须快、稳定、可观测**。它挂在每次工具调用前后，慢一点就是全流程变慢。
4. **失败要给出人可读的错误**：钩子失败时最糟的结果是「静默不生效」。
5. **安全阻断宁可明确失败，不要静默忽略。**

第 1 条是本章反复出现的那条线的另一面：**先把强制要求交给第三层里最省的一端**
（声明式的权限），再考虑代码。

### 一条必须记住的边界

**权限与规则由工具执行，不由模型执行。** 所以：

- `CLAUDE.md` 里写「不要执行 `git push`」→ 这是**上下文**，模型大概率遵守，
  但它是一句建议，不是一道闸门；
- `settings.json` 里写 `permissions.deny` → 这是**工具**在执行，跟模型怎么想无关；
- `PreToolUse` 钩子返回拒绝 → 同样由工具执行，而且能做权限规则表达不了的判断。

第 2.2.6 节已经给出过这条结论。放在本章的意义是：**它决定了「愿望」和「保证」分别该住在哪一层**——
规则文件里写「不要」，实际得到的是「希望它不要」。

配权限时有一个好用的分层，它按**「这一级最坏能坏到什么程度」**分，而不是按工具名分：

| 级别 | 允许什么 | 不允许什么 |
| --- | --- | --- |
| 只读 | 读文件、搜索代码 | 改文件、执行命令 |
| 本地修改 | 改工作区文件、跑测试与 lint | 联网、读密钥、动生产配置 |
| 受控外部访问 | 联网、调外部 API、写远端 | 未逐条列明或未审批的任何调用 |

它比「按名单放行」好用的原因是：**新增一个工具时，你只需要判断它属于哪一级**，
而不必先猜它会被怎么用。

### 一个最小可用的钩子

目标：**改完文件自动跑格式化，并在提交前拦下 `.env`**。前者用 `PostToolUse`，后者用权限规则
（按原则 1，能声明式解决的就不写脚本）：

```json
{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)"
    ]
  },
  "hooks": {
    "PostToolUse": [
      {
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/format.sh"
          }
        ]
      }
    ]
  }
}
```

配套脚本保持「只在必要时做事、失败要说人话」：

```bash
#!/usr/bin/env bash
# .claude/hooks/format.sh —— 改完文件后自动格式化，只处理 Python 文件
set -euo pipefail

# 钩子从 stdin 收 JSON，用 jq 取出被改的文件路径（契约见 2.2.6）
file=$(jq -r '.tool_input.file_path // empty')

# 不是 Python 文件就什么都不做：钩子要快，不给自己加活
case "$file" in
  *.py) ;;
  *) exit 0 ;;
esac

if ! command -v ruff >/dev/null 2>&1; then
  echo "格式化被跳过：找不到 ruff（请在项目里安装，或改这条钩子）" >&2
  exit 0        # 明确说明「没做」，而不是假装成功
fi

ruff format "$file" && ruff check --fix "$file"
```

这段脚本里有三条通用的写法，比它做了什么更重要：

- **先判断「是不是该我管」**（`case "$file"`），不相关就直接退出——钩子挂在热路径上；
- **依赖缺失时给出人可读的说明**，并明确退出（这里退 0，因为格式化失败不该阻断整个编辑流程；
  如果这条检查是安全相关的，就应该按第 5 条原则让它**明确失败**）；
- **用环境变量拿项目根**（`$CLAUDE_PROJECT_DIR`），不要假设当前工作目录。

## 2.5.7 MCP：把外部系统接进来

### 什么时候该接

官方给的信号比「工具很酷」可靠得多：

> Connect a server when you find yourself **copying data into chat** from another tool,
> like an issue tracker or a monitoring dashboard.

**当你开始反复把别处的数据复制进对话时**，才考虑接。而接之前先排序，
下面的三阶段顺序可以直接用：

| 阶段 | 接什么 | 例子 |
| --- | --- | --- |
| 一 | **只读** | 文档库、Issue 跟踪、监控、设计规范 |
| 二 | 有限写入 | 建 Issue、开草稿 PR |
| 三 | 高风险写入 | 数据库写入、云资源、部署——**尽量不接，或强制审批** |

接入前的 8 个问题（每题都在问「代价」而不是「能力」）：

1. 它真的能减少重复手工操作吗？
2. 它需要读权限还是**写权限**？
3. 是否涉及生产数据或隐私数据？
4. 有没有干净的测试环境？
5. 能不能限制到单个项目或目录？
6. 有审计日志吗？
7. 有限流与撤销方式吗？
8. **工具输出里可能含提示注入文本吗？**

第 8 题是 MCP 特有的：能取外部内容的服务器，等于把**别人的文本**喂给一个能执行命令的模型。
官方在 MCP 页上专门放了这条警告，所以「接之前先确认你信任这个服务器」不是客套话。

### 怎么接：三种传输与两个配置文件

```bash
# 远程 HTTP（推荐）：适用于云端服务
claude mcp add --transport http notion https://mcp.notion.com/mcp

# 需要鉴权时加请求头
claude mcp add --transport http secure-api https://api.example.com/mcp \
  --header "Authorization: Bearer 【令牌】"

# 本地 stdio：需要直接访问系统或跑自己的脚本时
claude mcp add my-tools -- python /path/to/server.py
```

三种传输的现状要记准：**HTTP 是推荐的远程传输**（MCP 规范里叫 `streamable-http`，
`type: "streamable-http"` 与 `type: "http"` 等价）；**SSE 已弃用**，
但仍有服务只暴露 SSE 端点，此时用同一条 `--transport http` 命令即可，
Claude Code 会先试 HTTP、失败再切 SSE；**stdio 是本地进程**，
官方会往它的环境里注入 `CLAUDE_PROJECT_DIR` 指向项目根，脚本可以直接用。

配置文件按作用域分两处，这是团队协作时最实际的一条：

- **项目级 `.mcp.json`**（放项目根、进版本库）：全组共用的服务器。
  密钥不要写进文件，用环境变量引用：`{"env": {"TOKEN": "${NOTION_TOKEN}"}}`。
- **个人级 `~/.claude.json`**：只有你自己需要的服务器（`claude mcp add --scope user` 写到这里）。

> ⚠️ **一个会静默跳过的坑**：在 `.mcp.json` 里写了 `url` 却忘了 `type`，
> 会被当作 **stdio** 服务器解析——于是它根本不加载。官方现在会明确报错：
> `MCP server "<name>" has a "url" but no "type"; add "type": "http" ...`。
> 早于 v2.1.202 的版本报的是另一句更难看懂的话（`command: expected string, received undefined`）。
> 遇到「配置写了却没生效」，先查这个字段。

### 上下文成本：接得多不等于占得多

这里有个与我们直觉相反的事实：**MCP 工具的 schema 默认是延迟加载的**
（官方对 `.mcp.json` 的说明：会话开始时连接服务器，但**工具 schema 默认推迟，按需通过工具搜索加载**）。
所以「接了十个服务器，上下文就被塞满」不必然发生——真正占预算的是**被实际加载进来的工具**。

但这不改变两条实践结论：

- **工具少而精**：要防的误区是「工具越多越强」，
  因为选择成本与误用概率都随工具数量上升；
- **先只读再写入**：因为写权限一旦给出去，代价是**副作用**，不是 token。

Codex 侧的 MCP 是同样的形状（协议相同、也建议先接一两个真正消除手工循环的工具），
差别在配置写在 `config.toml` 里、以及云端任务还有额外的联网控制（见 2.3.2 与 2.3.3）。

## 2.5.8 定时与事件触发：让重复的检查自己跑

最后一层自动化不是挂在会话上，而是挂在**时钟或外部事件**上。
两支官方文档在这件事上的判据高度一致：**适合「发现问题、生成报告、提交候选改动」，
不适合跳过人工审核直接影响正式系统。**

适合的与不适合的（这两行可以直接照抄）：

| 适合 | 不适合 |
| --- | --- |
| 每周汇总：上周新增代码里测试覆盖不足的模块，生成 Markdown 报告，**不改代码** | 每天自动修掉所有 lint 问题并**直接提交到 main** |
| 每天读最近 24 小时失败的 CI，按失败类型归类，列出可能原因与负责人 | 定时任务直接改生产配置或跑数据迁移 |

四条落地要点：

1. **先生成、再审查**：让定时任务的产物是「报告」或「候选改动」，人看过才合并。
2. **先手动把提示词跑通再排期**：官方明确建议先在普通对话里测一遍，
   并**看前几次运行结果**再调整提示词、工具与频率。
3. **可用面比想象中窄**：Codex 侧，**CLI 与 IDE 扩展没有定时任务的管理界面**，
   要在 web 或桌面应用里创建与管理（CLI 可以用来先把提示词或技能准备好）；
   **事件触发**（Gmail / Slack / GitHub）只在 web 与移动端可用。桌面应用里的定时任务
   可以跑在**项目目录或隔离的工作树**里——这正好接上 2.2.8 的隔离思路。
4. **与钩子分工**：钩子响应的是「会话里发生的事」；定时任务响应的是「时间到了」或
   「外部系统发生了变化」。两者都不该用来替代人的验收。

## 2.5.9 三层对照：一条需求该住在哪里

把全章收成一张表。用的时候先问「要不要每次都生效」，再问「多久用一次」：

| 需求的样子 | 该去的层 | 机制 | 为什么不是别的 |
| --- | --- | --- | --- |
| 「每个会话都该知道的项目事实与约定」 | 一、常驻 | `CLAUDE.md`（≤200 行） | 它是事实，不是流程 |
| 「只适用于某些文件的约定」 | 一、按需常驻 | `.claude/rules/*.md` + `paths` | 常驻会白占预算 |
| 「同一件事它错了两次」 | 一、常驻 | 追加进规则文件 | 这是升级信号，不是重说一遍 |
| 「一套多步骤流程 / 长清单」 | 二、按需 | 技能（`SKILL.md`） | 正文只在用到时加载 |
| 「一份反复要用的参考资料」 | 二、按需 | 技能的 `references/` | 同上 |
| 「外部系统的数据与动作」 | 二、按需 | MCP 服务器 | 它是连接，不是指令 |
| 「不管模型怎么想，这件事必须发生」 | 三、强制 | 权限规则（声明式优先） | 由工具执行 |
| 「需要编程判断的拦截 / 自动动作」 | 三、强制 | 钩子 | 权限规则表达不了 |
| 「哪些命令能在沙箱外跑」 | 三、强制 | Codex 命令规则 | 由工具判定，最严者赢 |
| 「定期检查并生成报告」 | 三、自动 | 定时任务 / 事件触发 | 不挂在会话上，产物仍需人审 |

三条升级路径可以直接背下来：

1. **错第二次 → 规则文件**（官方触发表的第一行）；
2. **重复粘贴 → 技能**；
3. **「必须每次都发生」→ 权限或钩子**；**「数据在别人家」→ MCP**。

配置顺序别倒过来。官方触发表的排列是有道理的：**先规则文件，再技能，再钩子，
最后才是插件打包**——因为前面每一步都会让你更清楚「到底哪些东西值得固化」。
反过来先配一堆再回头删，成本高得多，而且删不干净（旧的规则会继续在每次会话里占位置）。

## 2.5.10 综合示例：给知舟配一套最小配置

目标：给 1.15 的知舟博客 API 配一套**能用、能验证、不过度**的配置。约束有三条：

- 只加**官方有明确写法**的机制，不发明配置；
- 每一项都要有**验证它生效**的命令；
- 能声明式解决的不用脚本，能用技能的不用常驻规则。

### 文件树

```text
zhizhou/
├── CLAUDE.md                     # 项目事实与约定（常驻）
├── AGENTS.md                     # 同一份说明，给 Codex 读
├── .claude/
│   ├── settings.json             # 权限 + 钩子（强制层）
│   ├── rules/
│   │   └── api.md                # 只对 src/api/ 生效的约定
│   ├── skills/
│   │   └── pr-review/SKILL.md    # 提交前自审流程
│   └── hooks/format.sh           # 改完自动格式化
└── .mcp.json                     # 只读的文档服务器（示例）
```

### `CLAUDE.md`（常驻层）

```markdown
# 知舟博客 API

## 常用命令
- 启动：`uvicorn app.main:app --reload`
- 测试：`pytest -q`
- lint / 类型：`ruff check . && mypy app`

## 目录约定
- `app/api/`：路由；`app/services/`：业务；`app/repositories/`：数据访问
- `app/models/`：ORM 模型；`app/schemas/`：Pydantic 模型
- `tests/`：测试；**测试与实现一一对应**

## 开发规则
1. 三层顺序：路由只做参数校验与装配，业务在 `services/`，数据访问在 `repositories/`。
2. 所有对外响应必须是 Pydantic 模型（不允许返回裸 dict）。
3. 新增或修改接口，必须同时补一条对应测试。
4. 不新增依赖，除非先说明必要性、替代方案与风险。

## 禁止事项
1. 不提交 `.env`、密钥或真实用户数据。
2. 不改数据库结构，除非任务明确要求（迁移脚本要单独提交）。
3. 不直接执行 `git push`、`rebase`、`reset --hard`。

## 完成标准
1. 列出改动文件与原因；2. `pytest -q` 与 lint 的实际输出；3. 标出未验证项。
```

### `.claude/rules/api.md`（只对 API 目录生效）

```markdown
---
paths: ["app/api/**/*.py"]
---

## API 层约定
- 一个路由文件对应一个资源；处理函数不超过 30 行。
- 依赖注入一律走 `Depends`，不要在函数体里手工构造会话。
- 分页参数统一为 `page`（从 1 开始）与 `size`（最大 100）。
```

### 一个技能（提交前自审）

### 逐条验收

配置最容易变成「写了但没生效」。下面每条都是**能自己跑出结论**的：

```bash
# 1) 规则文件真的加载了吗（Memory files 一栏应列出 CLAUDE.md）
/context

# 2) 改完 CLAUDE.md 是否要新会话：改一行，再 /context 看内容有没有变
/context

# 3) 技能能不能被手动调用（以及描述是否让模型在相关时自动选它）
/pr-review

# 4) 权限规则是否拦住了 .env：请它读 .env，应被拒绝而不是「读不到」
> 读取 .env 的前三行

# 5) 钩子是否真的跑了：故意制造一个格式错误，看它有没有被自动修好
printf 'x=1\n' > app/_probe.py     # 改完后看 ruff 是否已格式化 / 报告缺失

# 6) MCP 是否连上、工具是否可用
/mcp
```

两点如实说明：**第 1–2、4–5 条依赖本机装了 Claude Code**，
本章写作环境里没有这个 CLI，所以这些命令写的是「官方的核对方式」而不是本机实测输出；
**第 3 条的自审技能用的是动态注入**（`!`git diff HEAD``），
它的效果取决于那两条命令能跑通——这也是为什么技能里要写命令而不是「请自己去看改动」。

## 常见坑

1. **把「不要」写进规则文件，当成闸门用。** 规则文件是上下文而不是强制配置
   （官方原话），真正拦得住的是权限规则与 `PreToolUse` 钩子。
2. **把长流程塞进 `CLAUDE.md`。** 它每次会话全量加载，还会**降低对其它规则的遵循度**。
   流程该去技能，路径约束该去 `.claude/rules/`。
3. **改完规则文件就在当前会话里验证。** 它在会话开始时读一次，
   所以「改了没生效」不是 bug，是新会话之前都不会生效。
4. **忘了 `AGENTS.md` 与 `CLAUDE.md` 是两份文件。** Claude Code 读后者，
   所以要么导入 `@AGENTS.md`，要么两份各写一遍（后者一定会漂）。
5. **在 `.mcp.json` 里写 `url` 却漏 `type`。** 会被当成 stdio 服务器解析而**静默跳过**，
   新版会打印明确错误，旧版的报错很难看懂。
6. **一次接五个 MCP 服务器。** 顺序是只读 → 有限写入 → 高风险尽量不接；
   「能取外部内容」的服务器还带来提示注入面。
7. **把 Codex 的命令规则当成上下文规则。** 它由工具判定、最严者赢，
   而且**拆不拆复合命令**取决于脚本形态——白名单式写法在这里会出事。
8. **给技能写一句模糊的描述。** 描述是自动匹配的唯一依据；技能多了还会被**先截断描述**
   （初始列表有 2% / 8,000 字符的预算），于是「装了却不触发」。
9. **钩子越写越多。** 能权限解决的别写钩子；能一条 shell 判断的别上 LLM 钩子；
   钩子挂在热路径上，慢和静默失败都会放大。
10. **把规则文件的加载顺序当成覆盖关系。** 它们是**拼接**的，冲突的两条会同时在场，
    模型可能任选一条——所以定期回查有没有互相矛盾的规则。

## 面试视角

1. **「同样是写规则，为什么有的能拦住、有的拦不住？」**
   考察点：区分上下文与强制执行。答题要点：规则文件进上下文、由模型遵循；
   权限规则与钩子由工具执行；`CLAUDE.md` 的「不要」只是建议，闸门要写在 `settings.json`
   或 `PreToolUse` 钩子里。能举出一个具体例子（不提交 `.env`）就够。
2. **「让你给一个团队配 AI 编程环境，你会按什么顺序加东西？」**
   考察点：是否有成本意识与顺序意识。答题要点：按官方触发表来
   （错两次 → 规则文件；重复粘贴 → 技能；必须发生 → 钩子；数据在别处 → MCP；
   第二个仓库 → 插件），并说明为什么不能一次配齐（规则会互相矛盾、没人维护）。
3. **「同样一份审查流程，你会放 `CLAUDE.md` 还是技能？」**
   考察点：上下文预算。答题要点：它是流程不是事实、正文只在用到时加载、
   `CLAUDE.md` 有 200 行的建议上限且越多越不灵；放技能还能打包脚本与参考资料。
4. **「为什么允许了 `git add`，`git add . && rm -rf /` 还是会被拦？」**
   考察点：知不知道工具怎么对待复合命令。答题要点：线性链条会被拆成单条命令逐条判定、
   取最严结果；含重定向/变量/通配时不拆，整段当一个调用比对。
5. **「接了三个 MCP 服务器之后上下文会不会爆？」**
   考察点：是否知道工具 schema 是延迟加载的。答题要点：默认按需加载；
   真正的问题是权限面与选择成本，所以先只读、再有限写入，高风险尽量不接。

## 本章小结

1. **每次会话都从新的上下文窗口开始**，所以关键问题不是「怎么说得更好」，
   而是「什么东西此刻在场」。三层机制：常驻上下文、按需加载、强制执行。
2. **两条判据**：多久用一次决定它吃不吃常驻预算；要不要每次都生效决定它靠遵循还是靠执行。
3. **规则文件的边界由官方数字界定**：每份建议 200 行以内（超出会降低遵循度），
   导入的文件仍然在启动时全量加载；HTML 注释会被剥掉，是留给维护者的免费备注。
4. **改完规则文件当前会话不生效**——它在会话开始时读一次；用 `/context` 核对。
5. **`AGENTS.md` 与 `CLAUDE.md` 机制同形、细节不同**：都是拼接式、都是「近者更具体」，
   但 `AGENTS.md` 有 `project_doc_max_bytes`（默认 32 KiB，**超出则后续文件不加载**）
   与 `AGENTS.override.md`（替换而非追加）；Claude Code 只读 `CLAUDE.md`，
   所以要共用一份说明就用 `@AGENTS.md` 导入（Windows 上别用符号链接）。
6. **分片有两种**：`.claude/rules/` 按路径，只在相关时加载；
   Codex `.rules` 按命令，由工具判定、**最严者赢**，且复合命令拆不拆取决于脚本形态。
7. **技能是「用到才加载」的代表**：`SKILL.md` + 支持文件，`description` 决定自动匹配；
   自定义命令已并入技能；Codex 的初始技能列表有 2% / 8,000 字符的预算，
   超量时先截短描述——所以技能不是越多越好。
8. **钩子按三种节奏触发**（每会话 / 每轮 / 每次工具调用），
   设计原则是先权限、再简单脚本、最后才考虑复杂形态；失败必须可见。
9. **MCP 的判据是「你是不是在反复复制数据」**，顺序是只读 → 有限写入 → 高风险尽量不接；
   工具描述默认延迟加载，接得多不一定占上下文，但一定扩大权限面。
10. **定时任务适合发现问题和生成报告**，不适合跳过人工审核直接影响正式系统。

## 练习

- **基础**：给一个你熟悉的项目写一份 `CLAUDE.md`，控制在 200 行内，
  并逐条标注 ①这条属于「事实」还是「流程」②如果是流程，它应该去技能还是规则。
- **基础**：把一份你反复粘贴的提示词改写成 `SKILL.md`，
  要求 `description` 里同时写出「什么时候用」与「什么时候不用」。
- **进阶**：写一条 Codex `prefix_rule`，为「允许 `pytest` 在沙箱外跑但每次都要确认」，
  并用 `match` / `not_match` 各写两个例子；然后说明为什么
   `pytest -q && rm -rf build` 这条命令的判定与前者不同。
- **进阶**：为你的项目配一个 `PostToolUse` 钩子（改完自动格式化），
  要求它在「不是目标文件类型」和「工具没装」两种情况下都**明确说明自己没做**。
- **挑战**：按 2.5.10 的六条验收，给一个真实项目配出最小的一套（规则文件 + 一个技能 +
  一个钩子 + 一个只读 MCP），并把每条的验证结果记下来（包括失败的那几条）。

**材料在这里说错、或缺了三处（均已按官方文档改写）**：

   而且**每次运行只构建一次**、合并后有 `project_doc_max_bytes`（默认 32 KiB）的硬上限——
   到顶之后**后续文件不再加入**，不是截断最后一份。
3. **「自定义命令」这一类已经不存在了**。素材把自定义命令与技能并列为两种东西，
   官方写明**自定义命令已并入技能**（`.claude/commands/x.md` 与 `.claude/skills/x/SKILL.md`
   产生同一个 `/x`），并且技能是那条开放标准（Agent Skills）的实现；
   同一条线在 Codex 侧也发生过（自定义提示词标记为「已弃用，改用技能」）。

另外补上三块素材没有、但官方已经给出的机制：**`.claude/rules/` 的 `paths` 分片写法**、
**Codex 的命令规则（`.rules` / `prefix_rule` / 复合命令的拆分条件）**、
以及**Claude Code 与 Codex 共用一份项目说明的 `@AGENTS.md` 导入法**。
