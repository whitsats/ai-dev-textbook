# 2.4 AI 编辑器与 Vibe Coding 全栈开发

> **本章导读**：2.2 和 2.3 讲的是**在终端里**跑的代理：能读项目、改文件、跑命令，
> 适合「一个任务、一段改动、一次验收」。这一章换到**编辑器里**，讲另一种用法：
> 改动更小、反馈更快、你始终在看着代码——补全、选中即问、侧栏对话、长任务。
>
> 顺着这个用法，很容易滑进一种更激进的模式：**不逐行读，只看结果对不对**。
> 这就是 Vibe Coding。它在原型上很好用，在交付上代价明确——而代价是可以量化的。
> 所以本章分两半：前一半讲清楚编辑器类工具的能力面与 Vibe Coding 的证据链，
> 后一半做一件具体的事——**用 AI 编辑器把知舟的前端从零做到可交付**，
> 并把每一步的验收从「看一眼」变成「跑一条命令」。
>
> 关键在最后半句。**AI 生成代码的成本不在写，在验**；谁把验证做得可执行，谁就能安全地用更激进的生成方式。

## 2.4.1 编辑器类工具在 AI 编程版图里的位置

把这一章的主角先定义清楚，免得与 2.2、2.3 混淆：**编辑器类工具是把同一个模型接到「你正在写的那一行」上的用法**。
它不是一个新物种，而是同一个能力在三个不同的介入点上的三种形态：

| 形态 | 介入点 | 你的角色 | 典型动作 |
| --- | --- | --- | --- |
| 补全式 | 光标处 | 写着，它接着写 | 续写这一行、补齐这个分支 |
| 会话式 | 选中的代码或整个文件 | 你问，它答或改 | 「这段在干什么」「按这个方式改」 |
| 代理式（长任务） | 整个工作区 | 你定目标，它自己规划 | 「按规格把这个功能做完」 |

三种形态共享同一套底座：**一个工作区（它能看到的文件范围）+ 若干上下文入口（引用、选区、当前文件）+
一个持续生效的规则文件 + 一个可回滚的版本控制**。第 2.5 节讲规则文件的写法，
这里只讲它们怎么协作。

### 它和终端代理不是替代关系

同一件事在编辑器里做和在 CLI 里做，差别不在「哪个更强」，而在两个半径：

| | 改动半径 | 上下文半径 | 适合 |
| --- | --- | --- | --- |
| 编辑器类工具 | 小（几行到几个文件） | 你能看见的那部分（含你的意图） | 边写边调、改文案与样式、补一个分支、看懂一段代码 |
| 终端 / 云端代理（2.2、2.3） | 大（跨模块、整条链路） | 项目级（它自己去搜） | 加一个完整功能、批量重构、跑测试与命令、并行长任务 |

判据可以压成一句话：

> 💡 **提示**：**改动半径小、你要即时反馈 → 编辑器；改动半径大、要跑命令或要隔离 → 终端或云端。**
> 反过来用会很难受：在 CLI 里改一行样式，你要写一段工单；
> 在编辑器里让会话式 AI「把整个认证模块重构掉」，等于在没有验收点的情况下赌一把。

### 编辑器类工具的三个共同弱点

它们强在「你看着」，弱的地方也全在这里：

1. **上下文是「你以为它看到了」**：你打开了八个文件，它未必都用上；你没指的那份配置它可能根本没读。
2. **补全的失败是无声的**：它给的那段代码语法正确、逻辑错误，你顺手按了 Tab。
3. **会话的失败是渐进的**：一轮轮改下去，最初的约束会被冲淡（这就是 2.1 讲的上下文腐烂）。

三条弱点的对策是同一条：**把关键约束外化**——写进契约、写进规则文件、写成测试。
放在你脑子里或对话框里的约束，都会在第三轮消失。

## 2.4.2 四个常用面：各自适合什么、怎么失败

### 补全：最快，也最容易让你接受自己没读过的代码

补全的能力已经不止「续写一行」。以官方文档描述的行为为例，它能够：

- 一次修改多行；
- 自动补上遗漏的 import；
- 在相关代码之间给出联动修改；
- 接受之后**预测你的下一个编辑位置并跳过去**；
- 在另一个文件需要同步修改时，给出跨文件的建议。

它的价值是减少机械动作，失败方式却很具体：**你按 Tab 的速度会超过你阅读的速度**。
判断标准不是「这段代码对不对」，而是**「我能不能解释它为什么这么写」**——
解释不了就不该按下去。这一条与 2.1 的「你能验证多少，决定你能用多少」是同一件事。

补全还带来一个隐蔽的副作用：**它会延续你已有的错误模式**。
代码里如果有一处没处理错误，它倾向于照着这个风格继续写。所以「先修一遍坏味道，再让它接着写」比反过来划算。

### 内联对话：针对选中的那一块问

选中一段代码直接问，比在侧栏里描述「我指的是哪一段」准确得多。它适合三类问题：

| 想做的事 | 问法 |
| --- | --- |
| 看懂 | 「这段在做什么？输入输出是什么？有哪些边界情况？」 |
| 改进 | 「按当前项目风格重写这段，不要改接口」 |
| 补测试 | 「给这段写单测，覆盖空值、超长输入与并发调用」 |

关键纪律是**框住改动范围**：「不要改变函数签名」「不要动其他文件」这两句要养成条件反射。
在编辑器里，一次「顺手优化」的连带改动比在 CLI 里更难发现，因为它就发生在你眼皮底下，
而你正在看别的地方。

### 侧栏对话：只问不改

问「这个报错什么意思」「这个字段在哪里赋值」「这两套实现哪个更好」——
这类问题不该让 AI 动代码。**把「理解」和「修改」分成两个动作**，
是编辑器里最省事的一条纪律：理解阶段的产出应该是解释与清单，而不是 diff。

### 长任务：先出规格，再动手

一些 AI 编辑器把长任务做成独立的模式：不是「你说一句它改一次」，
而是**先产出一份技术设计与任务拆解，确认后再执行，中间可以停下来检查**。
这类模式适合跨模块、需要多步的任务（这也是 2.2.4 里 P 阶段在编辑器里的对应物）。

它的失败方式只有一个字：**大**。一次改太多、跨太多文件，
你就会面对一个「没读完就已经写完」的 diff。所以用它的时候，
把任务拆到「能在一次审查里读完」的粒度，再交给它。

## 2.4.3 上下文怎么给：引用、符号与规则文件

编辑器类工具的上下文不是一个开关，而是一组入口。把它们按「确定性」排一下，用起来就不会乱：

| 入口 | 确定性 | 什么时候用 |
| --- | --- | --- |
| 选中的代码 | 最高（就是这几行） | 内联对话、局部改写 |
| `@` 引用具体文件 | 高（你点名的） | 「按 `api/comment.ts` 的写法改这个」 |
| 当前打开的文件 | 中（你打开了一堆） | 常规会话 |
| 符号 / 大纲导航 | 高（结构视角） | 快速定位类、方法、组件与函数 |
| 整个工作区检索 | 低（它自己判断相关性） | 长任务、跨模块改动 |

一个实用技巧是**多根工作区**：把后端目录与前端目录放进同一个窗口，
前后端一起读、一起改，还能开两个终端（一个跑后端、一个跑前端）。
全栈开发里，「前端改了字段、后端没跟着改」这类问题，大多是因为两个项目从来没在同一个上下文里出现过。

### 规则文件：各家都在同一件事上收敛了

不同编辑器的规则文件形态不同，但结构惊人地一致——**分作用域 + 离当前文件越近越优先**：

| 产品 | 形态 | 作用域 |
| --- | --- | --- |
| Cursor | `.cursor/rules` 下的 `.mdc` 文件；另有用户级、团队级与 `AGENTS.md` | 项目 / 用户 / 团队 |
| GitHub Copilot | `.github/copilot-instructions.md`（仓库级）、`.github/instructions/NAME.instructions.md`（路径级）、`AGENTS.md` | 仓库 / 路径 / 就近 |
| Codex（2.3） | `AGENTS.md` | 就近优先 |

`.mdc` 的四种生效方式很值得记，因为它解释了「为什么我写了规则它却不遵守」：

| alwaysApply | globs | description | 生效方式 |
| --- | --- | --- | --- |
| `true` | — | — | 每次会话都带上 |
| `false` | 有 | — | 匹配的文件进入上下文时自动带上 |
| `false` | 无 | 有 | **由模型按描述判断是否相关**，它觉得不相关就不会带 |
| `false` | 无 | 无 | 只有你手动 `@` 提及时才带上 |

第三行是「规则没生效」最常见的原因：你把它当成了硬约束，它其实是一句**建议**。

### 官方对「写什么」给的边界，比自己猜有用

官方文档明确列了几类**不该写进规则文件**的内容，理由都很实在：

| 不要写 | 改用 |
| --- | --- |
| 整套代码风格指南 | 格式化与 lint 工具（规则文件管不住缩进） |
| 每个命令的用法 | 它本来就知道 npm、git、pytest 这些常见工具 |
| 极少用到的边缘情形 | 只写反复出现的模式 |
| 复制一份代码当范例 | 指向那个文件（复制会过期） |

反过来，值得写的是**它已经犯过两次以上的错**——「发现问题→补一条规则」这个循环，
比一开始写一份二十条的清单有效得多。官方的建议就是这句：**从简开始，重复出现再补**。

这条边界正好能用来处理一类常见材料：一份十几节的团队开发规范文档。
它里面通常只有一小部分是规则文件该管的，其余各有归属：

| 规范里的内容 | 该去哪 |
| --- | --- |
| 命名、缩进、注释格式、import 顺序 | 格式化 / lint 配置（机器执行，不靠模型自觉） |
| 目录结构、分层职责 | 规则文件（它决定「新代码放哪」） |
| 「生成物不许手改」「迁移必须可回滚」 | 规则文件 + 提交钩子 |
| 「所有 Git 操作必须走某个工具」 | 权限或钩子——这类硬约束不该靠提示词 |

最后一行的判断标准值得记住：**能由机器拦住的，就不要写成请求**。
这与 2.2.6 的结论是同一条。

> 📌 规则文件的完整写法、Skills、Hooks 与 MCP 的连接方式见**第 2.5 节**，本章不展开。

## 2.4.4 Vibe Coding 的准确定义

这个词被用得很松，先把它钉住。它的来源是清楚的：

> 2025 年 2 月，计算机科学家 Andrej Karpathy 提出这一说法，描述一种
> **完全顺着感觉走、把指数级能力接进来、忘掉代码还存在**的编程方式。

随后它被词典收录（2025 年 3 月进入 Merriam-Webster 的「俚语与流行语」，
并被 Collins 选为 2025 年度词）。词条给出的定义比口号严谨：

> **由 AI 辅助的软件开发：开发者用自然语言向大模型描述需求，模型自动生成源码；
> 其中可能包含「不彻底审查产出、而是靠结果与后续提示来引导修改」的做法。**

定义里有两点值得注意：

1. **它不否定生成**——「用自然语言描述需求、让模型生成」这件事本身没问题，2.2/2.3 都是这么干的。
2. **它描述的是验证姿态**——关键在「接受产出而不彻底审查」。所以它与「AI 辅助编程」的差别
   **不在生成方式，而在你事后做了什么**。

这正好解释了为什么「Vibe Coding」这四个字在专业语境里褒贬分明：
倡导者看的是前半句（门槛降低了），批评者看的是后半句（审查被省掉了）。
两拨人说的其实是同一个定义的两半。

采纳面确实很广。词条记录了几个可核查的数字与例子：

| 证据 | 内容 |
| --- | --- |
| Y Combinator（2025 年 3 月） | 其 2025 冬季批次中约 **25%** 的初创公司，代码库有 **95%** 由 AI 生成 |
| 《华尔街日报》（2025 年 7 月） | 职业软件工程师开始在商业场景中采用这一方式 |
| Linus Torvalds（2026 年 1 月） | 为一个业余项目用 AI 编辑器写了可视化工具，并在 README 里说明该工具「基本上是 Vibe Coding 出来的」 |
| Andrew Ng（2025 年 6 月） | 公开反对这个词，认为它会让人误以为软件工程师「就是顺着感觉来」 |

最后一条值得单独领会：**反对的不是工具，而是这个词隐含的姿态**。
在本书的语境里，结论很直白——**Vibe Coding 是一种在明确边界内可用的加速手段，不是一种交付方式**。
边界在哪，看下一节。

## 2.4.5 代价的证据链：功能在变好，安全没有跟着变好

这一节全是可核查的数据，不用感觉说话。

| 证据 | 结论 |
| --- | --- |
| Veracode（2026 年 3 月更新，测试 200+ 个模型） | **语法正确率已超 95%，而安全通过率仍在 55% 上下**——与两年前几乎相同；也就是说 **45% 的生成任务引入了已知漏洞**。模型规模大小几乎没有影响 |
| CodeRabbit（2025 年 12 月，470 个开源 PR） | 由生成式 AI 共同署名的 PR，**每个 PR 的问题数 10.83 vs 6.45（约 1.7 倍）**；安全类最高 **2.74 倍**；逻辑与正确性问题多 **75%**；错误处理缺口近 **2 倍** |
| Lovable（2025 年 5 月报道） | 抽检 1,645 个由该平台生成的 Web 应用，**170 个**存在「任何人都能访问其中个人信息」的问题 |
| GitClear（2025 年，分析 2.11 亿行变更） | 重构占变更行的比例从 2021 年的 25% 降到 2025 年的不到 10%；**重复代码块约增四倍**；复制粘贴首次超过移动代码 |
| METR（2025 年 7 月，随机对照实验） | 有经验的开发者在 AI 辅助下完成 246 个任务，整体**慢 19%**——而他们自认为快了 24% |
| SaaStr 创始人（2025 年 7 月） | Replit 的 AI 代理在明确要求「不要改动」的情况下删除了数据库 |
| rsync（2026 年 5–6 月） | 版本更新后有用户发现增量备份异常，追溯发现自 3.4.1 起有大量 AI 参与提交，引发关于「AI 生成代码进入关键开源基础设施」的争论，维护者本人不得不出面说明 |

前四行各有一手报告可查（链接见本章「延伸阅读」）；这是必要的区分：
**一手报告有方法说明与可核对的原始数据，二手转述只有结论**。前者你可以自己判断它测得准不准，后者只能选择信不信。

这些数字要连起来读，才能看出三条互不相同的问题：

**① 生成能力与安全能力脱钩。** 功能变好是肉眼可见的，安全没有——所以**「它能跑」不再是质量信号**。
这一条直接解释了为什么「看着能跑就接受」在专业场景里不成立。

**② 量上去以后，问题从「错」变成「难以发现」。** 重复代码翻四倍、重构比例掉一半，
意味着系统在变大而结构在退化。单个 bug 可以修，退化的结构会持续收利息。

**③ 成本从写转移到了验。** METR 那个 19% 特别值得记住：**当事人感觉快了 24%，实际慢了 19%**。
这不是「工具没用」，而是说**感受到的速度与真实的速度是两件事**——
你能验证多少，才真正决定了你省下了多少。

> ⚠️ **对这一章而言，最重要的推论是最后这条**：
> 如果验证是新的瓶颈，那么**把验证做成可执行的**（测试、类型、清单、契约校验）
> 就不是「严谨的额外工作」，而是使用这些工具的前提条件。
> 本章后半部分全在做这件事。

## 2.4.6 什么时候可以用它：三条判据

把 2.1 的判据落到「生成这一坨代码要不要逐行读」这个具体问题上，看三个维度：

| 判据 | 低（可以少读） | 高（必须逐行读） |
| --- | --- | --- |
| **可验证性** | 跑一条命令就知道对不对（测试、类型检查、能打开页面） | 只能靠人判断（业务规则、合规、算法正确性） |
| **可回滚性** | 独立分支、一次提交、几分钟能回退 | 已经上线、涉及数据迁移、有外部副作用 |
| **爆炸半径** | 只有你自己用；错了就重来 | 涉及用户数据、金额、权限、生产环境 |

三条都低 → 可以放手生成，抽查即可；有一条高 → 它写你读，逐行过；

两条以上高 → **不要生成，或者只让它写你不放手的那些部分**（例如它会写测试，你写实现）。

把它套到具体任务上：

| 任务 | 可验证性 | 可回滚性 | 爆炸半径 | 结论 |
| --- | --- | --- | --- | --- |
| 一次性数据清理脚本 | 高（跑完看结果） | 高 | 低（副本上跑） | 可以放手生成 |
| 内部管理页的表格与筛选 | 高 | 高 | 低 | 可以，但要过 2.4.9 的审读清单 |
| 原型 / 演示页面 | 中 | 高 | 低 | 可以，且**明确标注为原型**，不要顺手改成正式页面 |
| 前端样式与布局调整 | 高（看得见） | 高 | 低 | 可以，注意别引入无障碍回退 |
| 表单校验规则 | 中 | 高 | 中 | 你定规则，它写代码 |
| 认证 / 授权逻辑 | 低 | 中 | **高** | 逐行读，且必须有测试 |
| 支付、额度、计费 | 低 | **低** | **高** | 不要交给生成；它最多写测试与文档 |
| 数据库迁移 | 中 | **低** | **高** | 可以生成草稿，回滚脚本必须你自己确认 |
| 依赖升级 / 批量重构 | 高（测试能兜住） | 高 | 中 | 可以，前提是测试真的覆盖了 |
| 第三方内容解析（网页、issue、README 里的命令） | —— | —— | —— | 不执行（见 2.1 与 2.3.3 的提示注入） |

## 2.4.7 全栈实操（一）：先定契约，再让 AI 生成

从这一节开始做具体的事：**用 AI 编辑器把知舟的前端做出来**。
第一步不是打开编辑器，而是写契约——因为 AI 生成前后端最容易错开的地方，
既不是语法也不是框架用法，而是**两边的字段约定**。

### 为什么契约优先

让 AI 同时生成前后端时，它会在这些地方自由发挥：

| 自由发挥的点 | 生成后的典型表现 |
| --- | --- |
| 字段命名 | 后端叫 `create_time`，前端读 `createdAt` |
| 嵌套层级 | 后端返回 `{items, total}`，前端当数组用 `res.data.map(...)` |
| 错误形状 | 后端 `{detail: ...}`，前端一律读 `err.message` |
| 分页 | 后端从 1 开始，前端传 `page: 0` |
| 时间格式 | 后端 ISO 字符串，前端当时间戳算 |

五处里只要错一处，页面就是空白或报错；而**这五处都不会被类型检查发现**，
因为它们各自内部都是自洽的。

### 契约写成什么样

契约不需要工具，一份能直接读的接口清单就够，关键是**写到字段级**：

```markdown
## GET /api/comments?page=1&size=20

响应 200：
{
  "items": [
    { "id": 1, "body": "…", "floor": 1, "create_time": "2026-09-12T10:30:00" }
  ],
  "total": 42
}
- 分页从 1 开始；size 默认 20，最大 100
- create_time 是 ISO 8601 字符串，前端自行格式化
- 无数据时 items 为 []，不是 null

错误：
- 404 { "detail": "文章不存在" }
- 422 { "detail": [ … ] }   # 参数校验失败，结构由框架决定
```

三条纪律：

1. **字段名以实际返回为准**，不从设计稿推。最省事的做法是先把接口 `curl` 一遍，把真实响应贴进契约。
2. **把「不是 null」这类边界写出来**。AI 默认会写出 `items.length` 这种代码，遇到 `null` 就崩。
3. **错误形状也要写**。否则前端永远只有一条 `catch (e) { console.log(e) }`。

### 让 AI 按契约生成：一份可用的工单

```text
任务：为知舟前端生成帖子评论区的数据层与列表视图。

上下文：
- 契约见 docs/api-contract.md 的 GET /api/comments 一节
- 参照已有写法：src/api/comment.ts（分页函数）、src/views/HomeView.vue（视图结构）
- 技术栈：Vue 3 + TypeScript + Vite，组合式 API，`@` 是 src 别名

范围：
- 允许新增：src/api/comment.ts、src/views/CommentList.vue
- 允许修改：src/router/index.ts（只加一条路由）
- 禁止修改：任何后端代码；不要新增依赖；不要改已有组件

约束：
- 请求基地址从环境变量读，不要写死
- 所有请求必须有错误分支，并在界面上显示可读的错误
- 列表渲染必须有稳定的 :key

验收：
1. npm run build 通过（含类型检查）
2. 把后端关掉，页面显示错误提示而不是白屏
3. 字段名与契约逐字段一致
```

这份工单的四段（上下文 / 范围 / 约束 / 验收）与 2.2.5 的七要素是同一套东西，
只是用词更短——**编辑器里的小任务不需要完整七段，但这四样一个都不能少**。

### 基地址与工作区

前端有一类错误在本地永远不出现：**把地址写死**。
正确的做法是从环境变量读，并且用它来切换开发与生产：

```ts
// src/api/http.ts
const baseURL = import.meta.env.VITE_API_BASE ?? '/api'
export const http = axios.create({ baseURL, timeout: 10_000 })
```

两条与它配套的事实（前端构建工具 Vite 的官方文档写得很明确）：

- **只有 `VITE_` 前缀的变量会被打进前端代码**，其余变量不会出现在客户端；
- 反过来说，**`VITE_*` 里的值等于公开**——它们会在构建时被静态替换进产物。
  **不要把密钥放进 `VITE_` 变量**，那条路没有秘密可言。

`.env.local` 这类本地文件不入库（官方建议把 `*.local` 写进 `.gitignore`），
所以「我本地能跑、别人拉下来跑不了」通常是这个问题，而不是依赖没装。

最后把后端与前端放进**同一个窗口的两个根**：契约文件、前端的 `src/`、后端的路由都在一个上下文里，
AI 才可能发现「前端在读一个后端不存在的字段」。这一步是免费的，但多数人没做。

## 2.4.8 全栈实操（二）：跨域、代理与联调

前端做完了，打开页面——空白，控制台一行红字。
这是 AI 生成全栈最经典的第一个失败，而它的机制值得完整讲一遍。

### 为什么会有跨域

浏览器要求：**页面所在源与请求目标源必须一致**，否则要服务器明确“允许”。
源由三样东西组成：**协议 + 主机 + 端口**，三者任何一个不同就是不同源。
所以 `http://localhost:5173`（前端开发服务器）与 `http://localhost:8000`（后端）
**是两个源**——端口不同就够了。

跨域请求分两类：

- **简单请求**：方法限 `GET` / `HEAD` / `POST`，请求头限几个安全头，
  `Content-Type` 只能是表单类或 `text/plain`。浏览器直接发，但**响应要被读取仍需要服务器点头**。
- **需要预检的请求**：其余情况（比如 `PUT`、`DELETE`，或 `Content-Type: application/json`），
  浏览器**先发一个 `OPTIONS` 请求**去问「我要这样发，你允许吗」，得到允许后才发真正的请求。

### 把这一步跑出来看

用一个真实的 FastAPI 应用（带与不带 CORS 中间件）分别起步，再用带 `Origin` 头的请求去打它，
结果如下（FastAPI 0.136.3 / Starlette 1.6.0）：

```text
──── CORS_MODE=none（没加中间件） ────
① 预检请求（浏览器在发 POST 之前自动发的那次 OPTIONS）
   OPTIONS /api/comments               405  ACAO=None  ACAC=None
② 实际请求（带 Origin 头，模拟 fetch）
   GET /api/comments                   200  ACAO=None  ACAC=None
③ 不带 Origin 的请求（curl / 服务端脚本）
   GET /api/comments                   200  ACAO=None
```

三条结论逐一读：

1. **预检拿到的是 405**，因为应用里压根没有 `OPTIONS` 路由。浏览器看到这个（或看到没有许可头），
   就直接不发真正的请求，控制台报跨域错误。
2. **带 `Origin` 的 GET 是 200**，但**没有 `Access-Control-Allow-Origin`（ACAO）**——
   服务端的处理完全正常，只是浏览器**不允许页面读取这个响应**。
3. **不带 `Origin` 的请求没有任何限制**。这解释了那个最常见的困惑：
   **「我用 curl / Postman 能通，浏览器为什么不行？」**——因为拦人的是浏览器，不是服务器。

> ⚠️ **记住这两句**：**服务端返回 200，不代表浏览器能拿到数据**；
> **预检失败时 JavaScript 里拿不到原因**（浏览器出于安全考虑只告诉你「出错了」，
> 细节只在控制台）。所以联调必须看**浏览器**的控制台，不能只看服务端日志。

### 加了 CORS 中间件之后

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5173"],   # 开发期前端的源
    allow_methods=["*"],
    allow_headers=["*"],
)
```

实测四种配置的差别：

| 配置 | 预检 | 普通请求（带 Origin） | 说明 |
| --- | --- | --- | --- |
| 不加中间件 | 405，无 ACAO | 200，无 ACAO | 浏览器一律拦 |
| `allow_origins=["http://localhost:5173"]` | 200，ACAO=该源 | 200，ACAO=该源 | 只有这一个源被放行 |
| `allow_origins=["*"]` | 200，ACAO=`*` | 200，ACAO=`*` | 任何源都能读 |
| `allow_origins=["*"]` + `allow_credentials=True` | 200，**ACAO=请求来源**，ACAC=`true` | 同上 | **任何源都能带凭证访问** |

最后一行是本节最需要留意的一处。浏览器的规矩是：
**带凭证的请求不允许用 `*` 回应，服务器必须回一个具体的源**。
于是框架的做法变成**把请求里的 `Origin` 原样反射回去**。
逐条实测的结果是——包括 `https://evil.example` 在内，**每个源都拿到了「放行」**：

```text
── allow_origins=['http://localhost:5173'] + allow_credentials=True ──
  Origin=http://localhost:5174      服务端 200  ACAO=http://localhost:5174      放行
  Origin=http://127.0.0.1:5173      服务端 200  ACAO=http://127.0.0.1:5173      放行
  Origin=https://evil.example       服务端 200  ACAO=https://evil.example       放行
```

一段来自「网上抄的配置片段」里的 `allow_origins=["*"]` 加上一个 `allow_credentials=True`，
**实际效果是对全网开放带凭证请求**。这类配置在代码审查里极难被发现，
因为它长得很像「我先放开一下，回头收一收」。

### 白名单的两个近邻陷阱

即使认真写白名单，下面两个也常被漏掉。实测（`allow_origins=["http://localhost:5173"]`）：

```text
  Origin=http://localhost:5173      服务端 200  ACAO=http://localhost:5173      放行
  Origin=http://localhost:5174      服务端 200  ACAO=None                       浏览器会拦
  Origin=http://127.0.0.1:5173      服务端 200  ACAO=None                       浏览器会拦
  Origin=https://evil.example       服务端 200  ACAO=None                       浏览器会拦
```

- **端口差一个就是不同源**：`5173` 放行，`5174`（Vite 端口被占用时它会自动换端口）不放行。
  所以「昨天还好好的」经常是因为前端换了端口。
- **`localhost` 与 `127.0.0.1` 是两个源**：字符串不同就是不同源，白名单不会自动等价。

### 正确的做法：开发用代理，生产用同源

不要在代码里到处放开 CORS。两条更稳的路：

**① 开发期：让开发服务器代理过去**（前端仍然请求自己的源，由开发服务器转发给后端）：

```ts
// vite.config.ts
export default defineConfig({
  server: {
    proxy: {
      '/api': { target: 'http://127.0.0.1:8000', changeOrigin: true },
    },
  },
})
```

这样前端代码里写 `/api`，开发与生产的行为一致，**跨域在开发期就不再是问题**。

**② 生产期：同源部署**（前端静态文件由后端一起提供，或用反向代理把两者放在同一个源下）。
回到 1.15 的知舟：后端本来就挂载了静态目录，前端构建产物直接交给它，
**源一致，CORS 配置可以一条都不需要**。

只有当「前端与后端必须异地部署」时才保留白名单，并且：

- 白名单写**完整的源**（协议 + 主机 + 端口），一个字都不能差；
- **不要用 `*`**，尤其不能与 `allow_credentials=True` 同用；
- 把 `allow_origins` 收进配置，不要散落在代码里。

## 2.4.9 全栈实操（三）：把「看一眼」变成可执行断言

生成出来的前端代码，「看着对」的比例是最高的：语法正确、命名合理、结构像样。
所以需要一层**能跑的审读**。它的定位要说清楚：

| 层次 | 管什么 | 谁执行 |
| --- | --- | --- |
| 格式化 / lint | 风格、明显错误、未使用变量 | 工具链（已配好，不该靠规则文件） |
| 类型检查 | 类型不一致、字段拼错 | `vue-tsc`（构建时自动跑） |
| **审读清单** | **语义与安全上的常见反模式** | 本章这个脚本 |

清单只补第三层的空缺，不替代前两层。

### 清单与理由

| 检查项 | 为什么危险 |
| --- | --- |
| `v-for` 没有 `:key` | 列表更新时复用错节点，出现「删了 A 显示成 B」 |
| `v-html` | 直接把 HTML 插进页面，是 XSS 的入口；除非内容可信且已净化 |
| 源码里写死 `http(s)://localhost` | 上线即断，而且它永远不会在本地暴露 |
| 凭据存进 `localStorage` | 任何一处 XSS 都能把它读走；比 HttpOnly Cookie 弱得多 |
| 请求没有错误分支 | 后端一挂就是白屏，用户与你都不知道发生了什么 |
| `@ts-ignore` / `eslint-disable` | 把问题藏起来；AI 特别容易用它来「让报错消失」 |
| 残留 `console.log` | 日志里泄露业务数据与令牌的风险 |
| 未使用的 import | 白拉一个依赖（实测里那行是 `lodash`），体积与供应链风险都增加 |

### 先看用来对账的三份文件

```python
"""AI 生成前端的可执行审读清单（Python 标准库，粗略但可跑）。"""
import pathlib, re

# (名称, 正则, 扫哪一份文本, 附加判定)
#   code = 剥掉注释后的代码，避免被注释里的字眼骗
#   raw  = 原样的那一行，因为有些问题本身就长在注释里（@ts-ignore 之类）
RULES = [
    ("v-for 没有 :key",      r"<[a-zA-Z-]+[^>]*\bv-for\b[^>]*>", "code", lambda m: ":key" not in m.group(0)),
    ("v-html（XSS 面）",     r"\bv-html\s*=",                    "code", lambda m: True),
    ("写死的后端地址",        r"https?://(localhost|127\.0\.0\.1)[:\d]*", "code", lambda m: True),
    ("调试残留 console.log", r"\bconsole\.(log|debug)\s*\(",      "code", lambda m: True),
    ("把问题藏起来",          r"@ts-ignore|@ts-nocheck|eslint-disable", "raw", lambda m: True),
    ("凭据存进 localStorage", r"localStorage\.(get|set)Item\(\s*['\"](token|jwt|api_?key)", "code", lambda m: True),
]

# 行注释与 HTML 注释；`://` 不算注释（否则 http://localhost 会被连地址一起剥掉）
STRIP = re.compile(r"(?<!:)//.*$|<!--.*?-->")

def check(path: pathlib.Path):
    hits, text = [], path.read_text(encoding="utf-8")
    raw = text.splitlines()
    code = [STRIP.sub("", l) for l in raw]          # 同一行留两份：原样、剥注释
    for i, (r, c) in enumerate(zip(raw, code), 1):
        for name, pat, scope, pred in RULES:
            for m in re.finditer(pat, r if scope == "raw" else c):
                if pred(m):
                    hits.append((i, name, r.strip()))
        if re.search(r"\b(axios|fetch)\b", c) and re.search(r"\b(await|return)\b", c):
            window = "\n".join(code[max(0, i - 5):i + 4])
            if not re.search(r"\b(try|catch)\b", window):
                hits.append((i, "请求没有错误分支", r.strip()))
    for i, c in enumerate(code, 1):
        m = re.match(r"\s*import\s+(?:(\w+)|(?:type\s+)?\{\s*([^}]+)\s*\})", c)
        if not m:
            continue
        names = [m.group(1)] if m.group(1) else [n.strip().split(" as ")[-1] for n in m.group(2).split(",")]
        body = "\n".join(code[:i - 1] + code[i:])   # 排除 import 自己那一行，否则每条都算「用过了」
        for n in [x for x in names if x]:
            if not re.search(rf"\b{re.escape(n)}\b", body):
                hits.append((i, f"未使用的 import：{n}", raw[i - 1].strip()))
    return sorted(hits)

if __name__ == "__main__":
    total = 0
    for p in sorted(pathlib.Path("src").rglob("*.*")):
        hits = check(p)
        total += len(hits)
        print(f"{p.as_posix()} —— {len(hits)} 处")
        for ln, name, src in hits:
            print(f"  L{ln} {name} | {src}")
    print(f"合计 {total} 处")
```

注意中间那一行：**同一个目录里那份写得规矩的组件，命中 0 处**。
这是必要的证据——一个从不沉默的检查，与「一切正常」在输出上没有区别；
所以**每加一条规则，都要拿一个反例与一个正例各跑一次**（与第 8.5 节的硬要求同源）。

### 这个清单自己也出错，而且错法的层次很有教育意义

上面那段脚本不是一次写成的。三个版本跑在同一组文件上，结果如下：

| 版本 | comment.ts | CommentList.vue | 出了什么问题 |
| --- | ---: | ---: | --- |
| v1 不剥注释 | 4 处 | 3 处 | 漏掉 L7 那行 `axios` |
| v2 把 `//` 之后一律剥掉 | 4 处 | 2 处 | 修好了 L7，却漏掉 L3 与 L5 |
| v3 同一行留两份 + 排除 import 自身行 | 5 处 | 5 处 | —— |

**v1 的错法：被自己的注释骗。** `comment.ts` 第 6 行写着「先这样，没加 catch」，
而 v1 用关键词 `catch` 判断「这个请求有没有错误分支」——
于是第 7 行那行没有人兜底的 `axios.get` 被认定成「已有错误分支」，**漏报**。

**v2 的修法引入了三个新的漏报。** 「把注释剥掉」看着无懈可击，实测却杀掉三条规则：

```text
剥掉注释后，这一行变成：        const BASE = 'http:'
  → 「写死的后端地址」的匹配式是 https?://…，永远匹配不到
一起被剥掉的还有 // @ts-ignore
  → 而「把问题藏起来」这条规则要找的恰好就是注释本身
未使用的 import 一条也没报出来
  → 因为每个名字都能在自己的 import 行里匹配到自己
```

这三处错得都很安静：不报错、不少条目、输出格式完全正常。
**修掉一个假阴性，很容易造出新的假阴性**，所以改完必须把全部规则重跑一遍，
而不是只看刚才漏掉的那一条。

**v3 的两处修法**：同一行留两份文本（`raw` 与 `code`），每条规则自己声明扫哪一份——
需要防注释污染的查 `code`，本身就长在注释里的查 `raw`；
判断未使用的 import 时，把 import 那一行从搜索范围里去掉。
剥注释的匹配式也从 `//.*$` 收紧为 `(?<!:)//.*$`：**`://` 不是注释**。

三层教训：

1. **搜索式检查会被文本本身骗**：注释、字符串、文档里的示例都会污染判断；
2. **假阴性比假阳性更危险**：假阳性你会去关掉规则，假阴性你以为已经查过了；
3. **验证清单的办法是故意写坏，而且每组规则都要写坏**：先写一个「应该被抓」的文件，
   再看它抓不抓得到——v2 里那三条规则之所以死掉，正是因为没做这一步。

> 💡 **提示**：这份清单的正确用法不是「跑完就放心」，而是
> **把它当成一次提问的清单**——每一处命中都值得回看那行代码，
> 判断是「误报」还是「真该改」。它给的是检查点，不是结论。

## 2.4.10 全栈实操（四）：构建与验收清单

### 先看脚手架给了什么

用 `create-vue` 起一个空项目（实测版本 3.23.0，命令与选项来自它自己的 `--help`）：

```bash
npm create vue@latest zhizhou-web -- --ts --router --pinia
cd zhizhou-web && npm install
```

产出的 `package.json` 脚本是这样的（实测）：

```json
{
  "dev": "vite",
  "build": "run-p type-check \"build-only {@}\" --",
  "preview": "vite preview",
  "build-only": "vite build",
  "type-check": "vue-tsc --build"
}
```

**这里有两条直接可用的验收事实**：

1. `npm run build` **已经包含类型检查**（它并行跑了 `type-check` 与 `build-only`）。
   所以「构建通过」这句话本身就有信息量——它不等于「页面能打开」，但至少字段拼错会被拦住。
2. `npm run preview` 用来预览**构建产物**，而不是开发服务器。
   联调结束后至少跑一次它，因为开发模式与产物模式的行为差异（环境变量、路由回退）只在产物上暴露。

### 环境变量与模式

| 事实 | 含义 |
| --- | --- |
| 只有 `VITE_` 前缀的变量会进前端代码 | 其余变量在客户端是 `undefined` |
| 值是**字符串** | `VITE_PAGE_SIZE=20` 读出来是 `"20"`，算术前要转换 |
| 变量在**构建时静态替换** | 改完 `.env` 要重启开发服务器 |
| `.env.local` 不入库 | 把 `*.local` 加进 `.gitignore` |
| 生产 / 预发可以用不同模式 | `vite build --mode staging` 会读 `.env.staging` |
| `VITE_*` **等于公开** | 密钥不要放这里；要隐藏就该由后端持有 |

### 交付前的四条验收

| 验收 | 命令 | 通过标准 |
| --- | --- | --- |
| 构建 + 类型 | `npm run build` | 无报错；`dist/` 生成 |
| 产物可跑 | `npm run preview` 后打开页面 | 首屏出数据；路由刷新不 404 |
| 接口联调 | 关闭后端再打开页面 | 显示错误提示，而不是白屏 |
| 产物卫生 | 在 `dist/` 里搜写死的地址与密钥 | 搜不到 `localhost`、`token=` 之类 |

第四条的思路是把本章前面所有「应该不会吧」变成一次检索：

```bash
grep -rn "localhost\|127.0.0.1" dist/ ; echo "命中数=$?"
grep -rn "sk-\|api[_-]key\|password" dist/ ; echo "命中数=$?"
```

两条命令的**期望结果都是「没有命中」**。这类检查的价值在于：
它拦的是「开发时对、上线就错」的那一类问题，而这类问题在本地永远不会自己冒出来。

> 📌 与对话式界面相关的部分（流式输出、SSE、AI SDK）**不在本章**——它属于**第 8.3 节**。
> 本章的边界就是「一个能交付的常规前端」。

## 2.4.11 综合示例：知舟前端从 0 到可交付

把前面几节串成一条流程。每一步都写清**AI 参与多少**与**你怎么验**。

| 步 | 做什么 | AI 参与 | 验收（可执行） |
| --- | --- | --- | --- |
| 1 | 写接口契约 | 让它把实际响应整理成契约，你核对字段名 | 契约里的字段能对上 `curl` 的真实响应 |
| 2 | 起骨架 | **不用 AI 生成骨架**，用官方脚手架 | `npm run build` 通过 |
| 3 | 生成数据层与视图 | 按 2.4.7 的四段工单让它写 | 2.4.9 的清单 0 处命中；类型检查通过 |
| 4 | 联调 | 它解释报错，你判断是配置还是代码 | 关后端显示错误提示；开后端出数据 |
| 5 | 构建与产物检查 | 它写检查命令 | 2.4.10 的四条全部有输出 |
| 6 | 交接 | 让它写变更说明 | 说明里含「改了什么 / 怎么验 / 怎么回滚」 |

第 2 步值得单独说一句：**骨架不要交给 AI 生成**。
脚手架的目录结构、依赖版本、构建脚本是后面所有验收命令的基础，
它出错的表现是「一切看起来都正常，但检查全都不生效」——
这正是 2.4.6 里「可验证性」那一栏最怕的形态。

第 6 步的变更说明模板（沿用 2.2 的 D 阶段）：

```text
改了什么：
- 新增 src/api/comment.ts（按契约的分页请求）
- 新增 src/views/CommentList.vue（列表 + 错误提示 + 加载状态）
- src/router/index.ts 加一条路由

怎么验的：
- npm run build 通过（含 vue-tsc 类型检查）
- 关掉后端：页面显示「加载失败，请稍后重试」，不是白屏
- 审读清单：0 处命中
- dist/ 里检索不到 localhost 与 token

怎么回滚：
- 单次提交，git revert 即可；无数据库与配置改动
```

回滚方式这一栏在编辑器场景里尤其不能省：**AI 生成的前端改动通常散落在多个文件**，
只有先做了提交，`revert` 才能一次性收回。

## 常见坑

| 现象 | 真实原因 | 修法 |
| --- | --- | --- |
| 编辑器里改了但页面没变 | 改的是开发服务器没监听的文件，或环境变量改了没重启 | 重启开发服务器；确认改的是 `src/` 下被引用的文件 |
| `curl` 能通、浏览器报跨域 | 跨域是**浏览器**的限制，服务器侧本来就没有问题 | 看浏览器控制台；加 CORS 白名单或用开发代理（2.4.8） |
| 加了 CORS 中间件还是不通 | 白名单里的源与实际源不完全一致（端口、`localhost` 与 `127.0.0.1`） | 用浏览器里实际的 `Origin` 值逐字对照 |
| 预检直接 405 | 应用没有 `OPTIONS` 路由，中间件没生效或顺序不对 | 确认 CORS 中间件已挂载；在预检请求上直接看响应头 |
| 「我先用 `*` 放开一下」 | 若同时开了凭证，等于**对所有源开放带凭证请求** | 写具体源；生产用同源部署 |
| 前端读不到数据但接口返回 200 | 响应字段与契约不一致（嵌套层级、命名） | 把真实响应贴进契约，逐字段对齐 |
| `import.meta.env` 里读不到某个变量 | 没有 `VITE_` 前缀，或改了 `.env` 没重启 | 加前缀；重启开发服务器；记住值是字符串 |
| 上线后接口全断 | 源码里写死了 `http://localhost:8000` | 用环境变量；构建后检索 `dist/` |
| 列表删除后显示错乱 | `v-for` 少了 `:key`，或用了数组下标当 key | 用稳定的业务 id 当 key |
| 页面出现来历不明的排版与脚本 | 用了 `v-html` | 尽量用插值；必须用时先净化 |
| 类型报错被「修好」了但问题还在 | AI 加了 `@ts-ignore` / `eslint-disable` | 当作阻塞项处理；在规则文件里禁止 |
| 依赖突然多了几个 | 补全自动补 import 时拉进了新包 | 提交前看 `package.json` 的 diff |
| 白屏且无提示 | 请求没有错误分支，异常被吞掉 | 统一错误处理：拦截器 + 组件级错误态 |
| 「构建通过」但预览是旧页面 | 看的是开发服务器，不是 `npm run preview` | 交付前至少跑一次产物预览 |
| 审读清单 0 处命中就放心了 | 清单是搜索式检查，会被注释与字符串骗；剥注释过粗还会让规则永不出声（2.4.9 两个版本各错一处） | 把它当检查点清单，逐条回看；新加规则时正例反例各跑一次 |

## 面试视角

「你怎么用 AI 写代码」这个问题，答得好不好，差别在于**你有没有一套自己的验收方式**。
下面五点是能直接说出口的：

1. **说清工具的边界**：「编辑器的补全适合小改动，跨模块的任务我放给终端代理做，
   因为前者的上下文半径就是我眼睛能看到的范围。」——这一句同时证明你用过多类工具、而不是只用过一个。
2. **给 Vibe Coding 一个准确的定义**：「它的定义核心是**接受产出而不彻底审查**，
   所以它描述的是验证姿态，不是生成方式。」能说出这一点，和「就是让 AI 写代码」不在一个层次。
3. **举出量化证据**：「METR 的随机对照实验里，有经验的开发者用 AI 反而慢了 19%，
   但他们自认为快了 24%。」——能报出「感受与实测相反」这件事，说明你关注验证而不是爽感。
4. **说出跨域的真实机制**：「服务端 200 不等于浏览器能拿到数据；
   带凭证时服务器不能回 `*`，必须回具体源，所以框架会反射请求源——
   一旦写成 `*` + 允许凭证，等于对所有站点开放带凭证请求。」这是极高频的岗位实战考点。
5. **把验收讲成命令**：「交付前我跑四条：构建含类型检查、产物预览、关掉后端看错误提示、
   在 `dist/` 里搜写死的地址与密钥。」——**能不能把话说到命令这一级**，是「用过」和「会交付」的分界。

## 本章小结

1. 编辑器类工具是同一个模型接在「你正在写的那一行」上：补全式、会话式、代理式三种形态共用一个底座。
2. 选择判据：**改动半径小、要即时反馈 → 编辑器；改动半径大、要跑命令或要隔离 → 终端或云端**。
3. 编辑器类工具的三个弱点都是「你看着」带来的：上下文是你以为的、补全失败无声、会话约束会漂。
   对策只有一条：**把关键约束外化**。
4. Vibe Coding 的差别在**验证姿态**（接受产出而不彻底审查），不在生成方式；采纳面很广，争议也在此。
5. 量化证据三条：**生成能力与安全能力脱钩**、**问题从「错」变成「难以发现」**、**成本从写转移到验**；
   METR 的 19% 说明感受与实测可以相反。
6. 放手生成的三条判据：**可验证性 × 可回滚性 × 爆炸半径**；两条以上高就不要交给生成。
7. 全栈生成的第一保障是**契约优先**：字段名、嵌套、错误形状、分页、时间格式写到字段级。
8. 跨域是浏览器行为：**服务端 200 不代表前端能拿到数据**；白名单差一个端口或差 `localhost`/`127.0.0.1` 就不放行；
   `*` 加凭证等于全网开放；生产优先**同源部署**，开发用**代理**。
9. 前端审读要**可执行**，且必须验证它「会响、也不乱响」——实测里那份规矩的组件命中 0 处才是有效证据；
   而检查本身也会出错：被注释骗（漏报）、剥注释过粗（规则永不出声），两者都只能靠正例反例各跑一次发现。
10. 交付四条验收：构建（含类型）、产物预览、后端不可用时的表现、产物里搜不到写死的地址与密钥。

## 练习

- **基础**：给一个你自己的前后端任务写一份接口契约（写到字段级，含错误形状与分页约定），
  然后按 2.4.7 的四段工单让 AI 生成前端数据层。
  要求：契约里的每个字段都能在真实响应里找到；生成后逐字段核对一次。
- **进阶**：复现 2.4.8 的四种 CORS 配置，用浏览器（不是 curl）验证行为，
  并解释为什么「带凭证 + `*`」时框架要反射请求源。
  要求：写下你自己的排查顺序，至少包含「先看预检」「逐字对照 `Origin`」两步。
- **挑战**：把 2.4.9 的审读清单扩到 10 条规则（自选 3 条），
  并**为每条规则各写一个正例与一个反例**跑一遍。
  要求：必须找出至少一条你自己的规则被文本骗过的情况（注释、字符串或文档示例），
  并说明你是怎么发现它的——**一条从不沉默的检查与「一切正常」在输出上没有区别**。
