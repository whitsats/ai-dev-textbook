# 2.6 AI Harness：把 AI 编程接入工程流水线

> **本章导读**：2.2 讲「怎么把任务交给代理」，2.3 讲「云端与本地两种跑法」，
> 2.4 讲「在编辑器里怎么用它」，2.5 讲「什么东西此刻该在场」。四章讲的都是**零件**。
> 这一章是第 2 篇的收口：把这些零件接成一条流水线，让 AI 写出来的东西
> **必须经过验证才算完成**。
>
> 2.1 把这件事概括成一句话——「从会问 AI，到给 AI 搭工作台」。本章就是把那张工作台
> 具体化：它由哪几个位置组成、每个位置放什么、谁说了算、失败之后留下什么。
>
> 全章只有一个中心判据，值得先写在这里：
>
> **让 AI 写代码不是难点，让 AI 写出来的代码被可靠验证，才是难点。**
>
> 围绕它可以拆成三问：**产物有没有外部验收？失败能不能回滚？过程能不能复盘？**
> 三问里只要有一问答不上，那套东西就还停在「聊天窗口」的层次——
> 即使它用上了最贵的模型。本章的很多结论听上去像工程常识，
> 但每一条都对应一个具体的失败：模型说「完成」而测试是红的、改了不该改的测试、
> 补丁跑不通却没还原、出问题后不知道它到底做了什么。

## 2.6.1 六个位置：一条流水线的形状

先看形状。一个完整的 Harness 可以画成这样：

```text
用户请求
   │
   ▼
任务规格构建     Task Spec Builder
   │
   ▼
上下文选择       Context Selector ──── 项目文档 / 数据库 / 记忆
   │
   ▼
Agent 运行时     Agent Runtime
   ├── 工具路由       Tool Router ──── 工具 / MCP / API
   ├── 权限闸门       Permission Gate
   ├── 状态存储       State Store
   └── trace 记录器   Trace Logger
   │
   ▼
验证层           Verification Layer ── 测试 / 评测 / 规则 / 人工评审
   │
   ▼
产物：补丁 / PR / 报告 / 动作
```

每一层都有明确职责，少一层就会出现一类特定的失败：

| 层 | 做什么 | 少了它会怎样 |
| --- | --- | --- |
| 任务规格构建 | 把自然语言换成明确任务 | 需求一路漂，做到最后不知道要做什么 |
| 上下文选择 | 挑相关上下文 | 把整库塞进上下文，早期约束被挤掉 |
| 工具路由 | 管理工具调用 | 工具太多、选错工具、副作用失控 |
| 权限闸门 | 控制风险 | 在没有任何围栏的环境里改生产数据 |
| 状态存储 | 保存进度 | 上下文一压缩就只能从头再来 |
| trace 记录器 | 记录过程 | 出了问题没人知道它做过什么 |
| 验证层 | 判断是否完成 | 模型说「完成」就是完成 |

这张图的用法不是「照着搭一遍」，而是**排查**：当一次协作结果不对劲，
先在图里找缺失的那一层，而不是换一个更贵的模型。

### 判据：一次模型调用不是 Harness

有一条一句话的判据，来自这套方法自己的定义：

| 形态 | 特征 | 属于 |
| --- | --- | --- |
| 调一次模型 API 拿一段文本 | 无工具、无状态、无验证、无权限、无 trace | 模型调用 |
| 多轮对话里改代码 | 有上下文，但验证靠人看、过程靠人记 | 对话式编程 |
| 有工具、有状态、有验证、有权限、有 trace | 不通过验证就不算完成，失败会自动回滚 | Harness |

差别不在「用了多少个 AI 功能」，而在**完成这件事由谁判定**。
对话式编程里，判定权在人的眼睛；Harness 里，判定权在一条命令的退出码。
这也是第 2.1 节的五阶段成熟度落到工程上的样子——
阶段越高，判定权越是从人手里移交给可复现的机制。

## 2.6.2 任务规格：把感觉变成合同

### 五个字段

任务规格不是「做个功能」。它至少要写清五件事：

```markdown
# Task Spec

## Goal
实现订单折扣计算。

## Non-goals
- 不做优惠券系统。
- 不接入支付。
- 不修改数据库结构。

## Inputs
- items：商品列表
- user_type：normal 或 vip

## Rules
- 满 100 减 10；
- VIP 在满减后额外 95 折；
- 金额使用 Decimal；
- 返回保留两位小数；
- 负数价格必须报错。

## Done When
- pytest 全部通过；
- 新增边界测试；
- 不引入 float；
- 输出变更说明。
```

这份规格很朴素，但它做了一件关键的事：**把「感觉」变成「合同」**。

### 为什么 Non-goals 与 Done When 最不该省

五个字段里，`Goal` 谁都会写，`Non-goals` 与 `Done When` 常年被省掉。而它们恰好是
把「漂移」和「自信地完成」按住的两个字段。

- **`Non-goals` 对付的是「顺手多做」**。代理很擅长「既然改到这里了，就把旁边也顺手改一下」，
  而每一次顺手都在扩大评审面。写下「不做优惠券系统」，等于提前划出爆炸半径。
- **`Done When` 对付的是「我觉得完成了」**。它必须是**外部可判定**的：
  一条命令、一个断言、一次构建。写成「代码质量要好」等于没写。

### 开工前的六个问题

同一件事还有一份更短的检查表，适合放进任务描述的开头：

| 字段 | 回答什么 | 反例 |
| --- | --- | --- |
| Goal | 我要做什么 | 「优化一下」 |
| Why | 为什么做 | 缺了它，方案会挑最省事的那条 |
| Scope | 这次包括什么 | 「相关的都改改」 |
| Non-goals | 这次不包括什么 | （通常直接省略） |
| Constraints | 有什么技术、业务、安全限制 | 「随便，你看着办」 |
| Done When | 怎样才算完成 | 「能跑就行」 |
| Verification | 用什么命令或方法验证 | （通常直接省略） |

注意最后一行：**验证方式与完成标准是两个字段**。前者是命令，后者是判断。
把它们分开写，好处是当命令换了（从 pytest 换成 unittest、从本地换成 CI），
完成标准不用改。

### 把模糊需求改写成可验收任务

下面是同一个需求的两种写法，差别全在可验收性上：

| 模糊说法 | 可验收写法 |
| --- | --- |
| 把金额改成 Decimal | `src/cart.py` 里不出现 `float(`；`1.005` 这种半进位能算成 `1.01` |
| 让接口更稳一点 | 参数校验失败返回 422；补一个「负数价格」的用例 |
| 清理一下日志 | 日志里不出现 `password`、`token` 明文；保留 `request_id` |
| 优化这个查询 | 加上索引；在 `tests/test_articles.py` 里断言查询次数不高于 3 |
| 补一下测试 | `tests/` 下覆盖正常值、边界值、非法输入三类，缺一类不算完成 |

右列的共同点是：**每一行都能变成一条命令或一个断言**。写不出右列，
通常说明需求本身还没想清楚——这时让它先动笔，只会把「没想清楚」放大成「改不完」。

### 不会写代码的人能做的那一半

任务规格里有一半完全不需要编程能力。举一个真实场景：你说「帮我做一个 CRM 系统」，
几十分钟后就拿到了几个页面。问题是**「看起来像 CRM」不等于「是 CRM」**。
真正需要先确认的是这些：

- 客户字段有哪些；
- 谁可以看客户；
- 销售阶段怎么流转；
- 数据怎么导入导出；
- 权限怎么做；
- 删除客户是否可恢复；
- 操作日志怎么留；
- 移动端要不要适配；
- 报表口径是什么；
- 哪些功能第一版不做。

这份清单一条代码都没有，但它决定了后面所有代码的形状。所以哪怕不写代码，
也可以这样开口，而不是直接要成品：

```text
你先不要写代码。请先帮我整理一份产品规格，包含：

1. 用户角色
2. 核心流程
3. 数据字段
4. 页面列表
5. 第一版做什么
6. 第一版不做什么
7. 验收标准
8. 风险和疑问

等我确认后，再开始生成代码。
```

「等我确认后再开始」这一句是重点：它把一个不可控的生成过程，
变成了两段可控的交付。

### 长任务的终点也要可检查

任务规格解决的是「这一次做什么」。当任务跨越多轮会话时，还得回答「什么时候算到头」。
Goal mode 的用法就是给长任务一个**可检查的终点**。

| 坏目标 | 好目标 |
| --- | --- |
| 把项目改好 | 将本项目从 JavaScript 迁移为 TypeScript |
| —— | 验收标准：① strict 模式编译通过；② 不出现显式 `any`；③ 全部测试通过；④ 不改变现有接口行为 |

差别在于：坏目标只能靠感觉结束，好目标可以在任何时刻被一条命令检验。
这四行验收标准的写法值得照抄——**每一条都是可执行的，没有一条是形容词**。

## 2.6.3 项目记忆：重要事实写进仓库

### 对话会结束，文件会留下

有一条事实决定了这一节的必要性：**代理的对话会结束，上下文会被压缩，记忆会丢；
但仓库里的文件会留下来。** 所以重要事实应该沉淀成文件，而不是留在聊天里：

```text
docs/
├── architecture.md              模块边界
├── testing.md                   测试命令与策略
├── known-issues.md              已知问题
├── tech-debt.md                 技术债
└── decisions/
    ├── 0001-use-decimal-for-money.md
    └── 0002-discount-order.md
```

这就像给代理留路标：下一次它进来，不用从头问一遍。
第 2.5 节讲过这些文件**该放在哪一层**（常驻、按需、强制），这一节讲的是
**放什么内容**——它们不是零散的笔记，而是一套知识系统。

### 从「提示词文件」到「仓库知识系统」

团队一开始用代理，常见的做法是写一个巨大的 `AGENTS.md` 或 `CLAUDE.md`，
把项目背景、架构说明、编码规范、API 说明、数据库说明、测试命令、部署步骤、
常见坑、产品规划、历史债务，甚至团队偏好全塞进去。

这样做前期有用，但很快会变成垃圾堆。更好的做法只有一句话：**入口短，知识分层**。

```text
AGENTS.md
docs/
├── architecture.md
├── testing.md
├── coding-style.md
├── product/
│   ├── pricing.md
│   └── checkout.md
├── decisions/
│   ├── 0001-money-decimal.md
│   └── 0002-api-versioning.md
└── runbooks/
    └── incident-api-error-rate.md
```

`AGENTS.md` 只做地图，例如：

```markdown
# AGENTS.md

## Start Here
Read this file first. It is a map, not the full manual.

## Architecture
See docs/architecture.md.

## Pricing Rules
See docs/product/pricing.md.

## Testing
See docs/testing.md.

## Decisions
Before changing money calculation, read:
- docs/decisions/0001-money-decimal.md

## Done Criteria
- tests pass
- lint passes
- docs updated if behavior changed
- PR summary includes verification result
```

这种结构的好处不止「省上下文」：

| 好处 | 为什么 |
| --- | --- |
| 上下文更省 | 每次加载的是一张地图，不是一本手册 |
| 文档更容易维护 | 改价格规则只动 `docs/product/pricing.md` |
| 代理更容易按需读取 | 它知道该去哪找，而不是从一大段里猜 |
| 规则可以被测试 | 「不引入 float」能写成一条检查 |
| 过期内容更容易发现 | 小文件过期一眼可见，大文件里的三行没人注意 |
| 团队成员也能看懂 | 同一套结构对人同样有效 |

### 一份值得抄的决策记录

`docs/decisions/` 里的文件是这套系统的关键。它们的价值在**「为什么」**，
而不在「是什么」——「是什么」读代码就有，「为什么」只存在于当时的人脑子里。
最短的写法只要三行：

```markdown
# 0001 金额一律使用 Decimal

日期：2026-05-12

## 背景
`cart.py` 用 float 累加金额，1.005 这类半进位在二进制浮点下会向下取整。

## 决定
金额计算与存储一律用 `Decimal`，四舍五入统一 `ROUND_HALF_UP`。

## 后果
- 价格入参改用字符串；
- 数据库列改为 `NUMERIC(10, 2)`；
- 所有进出金额的接口都要有边界用例。
```

最后那个「后果」小节最容易被省，也最有用：它把一条决定变成了**后续任务的约束**。
代理读到它，就会知道「改价格入口要顺手加边界用例」不是某个人的偏好，
而是这条决定的一部分。

**与第 2.5 节的分工**：那里回答「这条信息该住在哪一层」，
这里回答「知识该怎么组织、写成什么形状」。两张表可以并起来用——
先用 2.5 的判据决定载体，再用本节的三段式决定内容。

## 2.6.4 状态管理：长任务的进度文件

### 进度文件与项目记忆的区别

上一节的文件回答「这个项目一直是怎么做的」，本节的回答「**这件事现在做到哪了**」。
长任务不能只靠对话记录，因为对话会被压缩、会被截断、会被新话题挤掉。
所以要让代理写一个计划文件：

```markdown
# exec-plans/2026-05-pricing-refactor.md

## Goal
重构 pricing 模块，统一 Decimal 金额计算。

## Milestones
- [x] 梳理现有价格入口
- [x] 增加边界测试
- [ ] 替换 float 计算
- [ ] 跑全量测试
- [ ] 更新文档

## Current Status
已发现 cart.py 和 discount.py 中存在 float 计算。

## Risks
- 订单导出 CSV 可能依赖旧格式。
```

注意它的写法：**步骤是带勾选框的、状态是一句话、风险单独一节**。
这样即使上下文被压缩，代理也能回到这个文件继续工作——它不需要回忆，只需要读。

### 四个字段各自对付什么

| 字段 | 对付的问题 | 写坏的后果 |
| --- | --- | --- |
| Goal | 中途跑偏 | 做到最后发现方向错了 |
| Milestones | 不知道还剩多少 | 每次都从头梳理一遍 |
| Current Status | 上下文被压缩后失忆 | 重复已完成的工作，或漏掉已发现的问题 |
| Risks | 只盯着主路径 | 收尾时才发现有依赖被改动 |

`Risks` 一栏值得单独说：它的作用不是「记录风险」，而是**让下一轮知道该先看哪里**。
上面那条「订单导出 CSV 可能依赖旧格式」，就是下一次开工的第一个检查项。

### 计划模式：先出方案，再动代码

进度文件是「事中」的载体，「事前」的那一半是计划。计划模式适合新功能、大重构、
跨前后端、需求模糊，或者你只想先看方案。

但计划不是「列几个步骤」。一份好的计划必须能回答六个问题：

- 为什么改这里？
- 改哪些文件？
- **不改哪些文件？**
- 风险是什么？
- 如何验证？
- 如何回滚？

第三行是个很好的观察点：普通计划只列「要动的文件」，好的计划会明确**不动的文件**。
这和任务规格里的 `Non-goals` 是同一个思路——把边界说出来，才能事后判断有没有越界。
后面三个问题（验证、回滚）则是本章后半段的主题：
一份说不出怎么验证、怎么回滚的计划，不管多详细都不算计划。

### 任务进行中的三句约束

进度文件是它自己写的，但「什么时候写、写完先干什么」得由你定。
把下面这段话当成开工模板，它把三个时间点都提前安排好了：

```text
先读取 AGENTS.md 和 docs/testing.md。
然后制定计划。
计划确认后再改代码。
每完成一个 milestone 跑一次测试。
如果测试失败，先解释失败原因，再修复。
```

三句对应三件事：**先给上下文、先计划再动手、每个阶段结束就跑一次验证**。
最后一行的顺序很关键——**先解释再修**，而不是直接改。
解释这个动作会让「猜」暴露出来（常见于它一次改三处然后碰巧跑通），
读者也更容易判断它到底懂不懂。

### 什么时候需要进度文件

不是每个任务都要。判据是两条，满足任意一条就该有：

1. **跨会话**：这一件事不可能在一次会话里做完；
2. **多步骤且步骤之间有依赖**：做完 A 才知道 B 该怎么做。

反过来，单文件小改、一个小函数的解释、一次问答，都不需要——
写进度文件本身也是开销，而这个开销只在「会失忆」的场景里才划得来。

## 2.6.5 验证机制：能机器判定的完成标准

### 验证手段不止一种

需要说明的是，「跑测试」只是验证的一小块。以下手段在不同场景里各自不可替代：

| 手段 | 抓什么 | 什么时候必须有 |
| --- | --- | --- |
| 单元测试 | 函数级行为 | 有明确输入输出的逻辑 |
| 集成测试 | 组件之间 | 跨模块、跨服务 |
| lint | 风格与可疑写法 | 每次都跑 |
| 类型检查 | 契约不匹配 | 有类型系统的项目 |
| 构建 | 是否能产出 | 有编译/打包步骤 |
| 快照测试 | 输出形态变化 | 渲染结果、生成文件 |
| 黄金文件 | 与基准逐字比对 | 解析器、编译器、报表 |
| API 契约测试 | 接口与文档是否一致 | 对外接口 |
| 迁移 dry-run | 数据库变更是否可执行 | 有 schema 变更 |
| 回归测试 | 修过的问题是否复发 | 每次修 bug |

这张表的用法是**对照检查**：一次改动如果只跑了一种验证，就要问「还有哪一行没覆盖」。

### 失败信息本身就是产品

对代理来说，最有价值的反馈不是「你写得不错」，而是这样一段：

```text
FAILED tests/test_discount.py::test_vip_discount
Expected Decimal("85.50"), got Decimal("90.25")
```

它好在三点：**哪条用例、期望什么、实际什么**。有了这三样，代理能基于它继续修；
少任何一样，它就只能猜，猜的方式通常是「改测试来迎合实现」——
这正是常见的翻车现场之一（见 2.2 与 2.3 的翻车现场小节）。

反过来说，如果你给它的失败信息是一句「测试没过」，那它做对的可能性会大幅下降。
所以**让失败信息可读，是搭 Harness 的一部分，不是额外的体贴**。

### 完成标准要机器化

把完成标准从形容词换成命令，是这一层最直接的动作：

| 不要写 | 要写成 |
| --- | --- |
| 代码质量要好 | `python -m pytest -q` |
| 风格要统一 | `npm run lint` |
| 类型要对 | `npm run typecheck` |
| 能构建 | `npm run build` |

一句话总结：**能机器判断的，就不要靠感觉判断。**

### 一个测试名字给了虚假的安全感

下面这条实测结论值得单独拿出来，因为它是「阶段 3 误区」的实证：

在金额场景里写一条叫「不引入浮点精度问题」的测试，它**抓不住浮点的问题**。

```python
# 这条用例在 float 版本上也会通过
items = [{"price": "0.10", "qty": 3}, {"price": "0.20", "qty": 1}]
assert calculate_total(items) == Decimal("0.50")
```

原因很朴素：`0.1 * 3 + 0.2` 的浮点结果是 `0.5000000000000001`，
再经 `round(x, 2)` 又回到 `0.5`，而 `Decimal("0.5") == Decimal("0.50")` 为真。
换句话说，**这条用例从写下的那一刻起就没有在验证它名字里说的事**。

换一条真正能抓的用例（半进位）：

```python
items = [{"price": "1.005", "qty": 1}]
assert calculate_total(items) == Decimal("1.01")
```

| 版本 | `1.005` 的结果 | 这条用例 |
| --- | --- | --- |
| 浮点累加 + `round` | `Decimal('1.0')` | 失败（这正是我们要的） |
| `Decimal` + `ROUND_HALF_UP` | `Decimal('1.01')` | 通过 |

所以「通过一次测试」的含金量，取决于**那条测试到底在验证什么**。
一条全绿的套件如果全是这类无效用例，它带来的只是放心，不是保证。

2.6.8 的用例里把它改名为 `test_small_amounts_add_up_exactly`，并另加了一条真能抓住浮点的
`test_rounding_is_half_up`。改名本身就是结论：**名字只能承诺它真正验证的事**。

## 2.6.6 可观测性：每一步都要能复盘

### 失败不可怕，不知道为什么失败才可怕

代理失败不可怕。可怕的是失败以后你不知道它为什么失败。
所以 Harness 要记录的是**一次任务的过程**，而不是散落的日志行：

```json
{
  "task_id": "pricing-discount-001",
  "started_at": "2026-05-28T10:00:00Z",
  "steps": [
    {"type": "read_file", "path": "src/cart.py"},
    {"type": "write_file", "path": "src/cart.py"},
    {"type": "run_tests", "command": "pytest", "exit_code": 1,
     "summary": "test_vip_discount failed"},
    {"type": "write_file", "path": "src/cart.py"},
    {"type": "run_tests", "command": "pytest", "exit_code": 0}
  ],
  "final_status": "passed"
}
```

### trace 与日志的差别

两者都是「记录」，差别在于看的人要回答的问题不同：

| | 日志 | trace |
| --- | --- | --- |
| 回答的问题 | 系统现在在做什么 | **这一次任务为什么是这个结果** |
| 单位 | 时间戳 + 事件 | 任务 + 步骤序列 |
| 结尾 | 通常没有 | 有一个 `final_status` |
| 典型用途 | 报警、排查线上问题 | 复盘、评测、建立信任 |

关键在最后两行：**trace 有一个明确的结尾状态**。
没有结尾的日志只能靠时间范围去猜，而猜不出「它到底是过了还是回了」。

### 该记什么，不该记什么

四类该记：**工具调用的类型与参数、执行的命令与退出码、结果摘要、结束状态**。
四类不该记：**密钥与凭据、个人身份信息、完整的请求体/响应体、与任务无关的闲聊**。

第三类容易被忽略：把完整上下文记下来，看起来对排障有利，实际上是把 trace 变成
一个新的泄露面。正确做法是记**摘要与引用**（哪个文件、哪一行、哪条命令），
而不是把所有内容复制进去。这与第 1.14 节的日志脱敏是同一条规矩。

### 审计是给小团队准备的

有一条容易被当成「大公司才需要」的要求：如果代理能改代码、查数据、发消息、
开 PR、触发部署，那就必须能审计。

审计的判据不是组织结构，而是**权限**：只要它做了不可逆的动作，就必须留得下记录。
反过来，小团队更依赖这件事——大公司有流程和人盯着，小团队只有 trace。

## 2.6.7 人类接管点：哪些必须停

### 该自动的自动，该停的停

很多人把 AI 代理想成「完全自动」。但真实工程里，高级不是完全自动，
而是**该自动的自动，该停的停**：

| 动作 | 处理 |
| --- | --- |
| 改测试 | 自动 |
| 跑 lint | 自动 |
| 格式化代码 | 自动 |
| 修改核心支付逻辑 | 需要 review |
| 删除数据 | 必须拒绝 |
| 改 CI/CD 权限 | 必须审批 |
| 访问生产密钥 | 不允许 |

这张表的价值在于它**不需要你从零想**。真实项目照着改两行就能用，
而自己拍脑袋的结果通常是「全都自动」或「全都人来」——前者危险，后者等于没搭。

### 判据：不可逆 × 爆炸半径

表里的六条看起来是经验，其实可以归到两个维度上：

- **不可逆**：删数据、改权限、触发部署——做错了没法撤销；
- **爆炸半径**：改核心支付逻辑、改公共接口——影响的不止一处。

两个维度只要有一个是「大」，就该设停机点。反过来，可逆且半径小的动作
（改测试、跑 lint、格式化）自动掉，不占人的注意力。

这也解释了为什么「改测试」列在自动那一栏却很危险：
修改测试本身可逆，但**如果它改的是测试而不是实现**，就等于把验证层拆掉了。
所以正确做法不是禁止它改测试，而是**在评审时把「测试文件的改动」与
「实现文件的改动」分开看**（具体检查项见 2.6.9）。

### 把停机点写下来

停机点不能只是「心里有数」，要落到配置里。最常见的一种写法：

```text
如果改动涉及 src/payment/ 或 migrations/ ：
- Agent 可以提出 patch；
- Agent 可以跑测试；
- Agent 不允许自动合并；
- 必须由 human reviewer 审查。
```

注意它同时给了**允许**与**不允许**（可以提 patch、可以跑测试，但不许合并）。
只写「不许自动合并」是不够的——它还得知道被允许做什么，否则会退化成什么都不敢做，
或者什么都敢做。

### 与权限分层的关系

第 2.5 节给过一套权限分层（只读 / 本地修改 / 受控外部访问），
本节讲的是**这一层里停在哪一步**：同一层权限下，不同动作的停机点不同。
两件事可以叠加：先用分层决定「它能碰到什么」，再用停机点决定「碰到之后谁按下确认」。

一层重要的现实：**规则文件里的「不要」拦不住任何东西**（第 2.5 节的结论）。
所以停机点必须落在工具能执行的地方——权限规则、CI 门禁、受保护分支，
而不是 `CLAUDE.md` 里的一行字。

## 2.6.8 最小可验证 Harness：实跑一遍

前面几节都是规则。这一节把它们缩成一个能跑的例子，它的写法很特别：
**不依赖真实模型**。

为什么不用真模型跑？因为这一段要示范的是「怎么验收」，而不是「模型多能干」。
真模型的输出每次不同，没法当作基准；用一个固定的「代理提案」代替，
则每个结论都能重跑出来。这不是偷懒，而是在挑**可验证**的那个变量：
**不是谁写了代码重要，而是代码必须经过验证才算完成。**

### 项目结构

```text
mini-harness-demo/
├── src/
│   └── cart.py            有缺陷的业务代码
├── tests/
│   └── test_cart.py       验收用例
├── agent_harness.py       限制、验证、回滚、trace
└── trace.json             运行后生成
```

### 一个真实存在的缺陷

`src/cart.py` 能跑、也能算出大致对的结果，但它在两个地方是错的：

```python
from decimal import Decimal


def calculate_total(items, user_type="normal"):
    """items: [{"price": "60.00", "qty": 2}]
    rules:
    - subtotal >= 100: minus 10
    - vip user: 5% off after threshold discount
    - return Decimal with 2 decimal places
    """
    total = 0.0

    for item in items:
        total += float(item["price"]) * item["qty"]

    if total >= 100:
        total -= 10

    if user_type == "vip":
        total = total * 0.95

    return Decimal(str(round(total, 2)))
```

两处错：**金额用了 `float`**（半进位会向下跑），**负数价格没被拒绝**。
注意它们都没让程序报错——这正是「能跑不等于对」。

### 验收用例

下面这份用例描述了这个模块**应该**具备的行为：

```python
import unittest
from decimal import Decimal

from src.cart import calculate_total


class CartTest(unittest.TestCase):
    def test_normal_user_threshold_discount(self):
        items = [{"price": "60.00", "qty": 2}]
        self.assertEqual(calculate_total(items), Decimal("110.00"))

    def test_vip_discount_after_threshold_discount(self):
        items = [{"price": "60.00", "qty": 2}]
        self.assertEqual(calculate_total(items, user_type="vip"), Decimal("104.50"))

    def test_small_amounts_add_up_exactly(self):
        items = [{"price": "0.10", "qty": 3}, {"price": "0.20", "qty": 1}]
        self.assertEqual(calculate_total(items), Decimal("0.50"))

    def test_rounding_is_half_up(self):
        items = [{"price": "1.005", "qty": 1}]
        self.assertEqual(calculate_total(items), Decimal("1.01"))

    def test_negative_price_rejected(self):
        items = [{"price": "-1.00", "qty": 1}]
        with self.assertRaises(ValueError):
            calculate_total(items)


if __name__ == "__main__":
    unittest.main()
```

> **为什么用标准库的 `unittest` 而不是 pytest？** 因为这个例子的意义在于
> **零依赖、在任何人的机器上都能立刻跑出下面这些输出**。pytest 写法更简洁，
> 但这条流水线的每个环节都要可复现，所以这里选标准库——库换成 pytest，
> 只需要改一处运行命令，其余结构不变。
>
> 这也带来一个真实差异：pytest 的失败行是 `FAILED tests/...::用例名`，
> unittest 是 `FAIL: 用例名 (类名.用例名)`。上一节引的那段 `FAILED …::…` 是
> pytest 的格式（本章环境未装 pytest，只作示例展示）；本节看到的是 unittest 的真实输出。

### 真实基线：两条用例是红的

不改任何东西，直接跑：

```console
$ python -m unittest discover -s tests

----------------------------------------------------------------------

  File ".../tests/test_cart.py", line 26, in test_negative_price_rejected
    with self.assertRaises(ValueError):
```

三件事值得注意：

1. **开头是 `F.F..`**：五个用例里第 1、3 个失败、第 2、4、5 个通过。
   前面那条「不引入浮点精度问题」的用例就是通过的那一批——它没抓住任何东西。
2. **失败信息本身就是修复指令**：`ValueError not raised` 与
   `Decimal('1.0') != Decimal('1.01')`，两句都直接指向要改什么。
3. **退出码非零**：这是把「完成」交给外部判定的前提。

### 这 134 行的 Harness

```python
import json
import shutil
import subprocess
import sys
from datetime import datetime, timezone
from pathlib import Path

ROOT = Path(__file__).parent
TARGET_FILE = ROOT / "src" / "cart.py"
TRACE_FILE = ROOT / "trace.json"

PATCH_PROPOSAL = '''from decimal import Decimal, ROUND_HALF_UP


def money(value):
    return Decimal(str(value)).quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)


def calculate_total(items, user_type="normal"):
    """items: [{"price": "60.00", "qty": 2}]"""
    total = Decimal("0.00")

    for item in items:
        price = Decimal(str(item["price"]))
        qty = int(item["qty"])
        if price < 0:
            raise ValueError("price must not be negative")
        if qty < 0:
            raise ValueError("qty must not be negative")
        total += price * qty

    if total >= Decimal("100.00"):
        total -= Decimal("10.00")

    if user_type == "vip":
        total = total * Decimal("0.95")

    return money(total)
'''

# 故意写坏的补丁：95 折写成 9 折。用来跑「失败要回滚」那条路径。
BROKEN_PATCH = PATCH_PROPOSAL.replace('Decimal("0.95")', 'Decimal("0.9")')

TEST_CMD = "python -m unittest discover -s tests -q"


class Harness:
    """最小 Harness：限权写、跑验证、失败回滚、全程记 trace。"""

    ALLOWED_WRITES = {TARGET_FILE}

    def __init__(self, task):
        self.trace = {
            "task": task,
            "started_at": datetime.now(timezone.utc).isoformat(timespec="seconds"),
            "steps": [],
        }

    def log(self, step_type, **kwargs):
        record = {"type": step_type, **kwargs}
        self.trace["steps"].append(record)
        print(json.dumps(record, ensure_ascii=False))

    def run(self, command):
        self.log("run_command", command=command)
        result = subprocess.run(
            command, cwd=ROOT, shell=True, text=True,
            stdout=subprocess.PIPE, stderr=subprocess.STDOUT,
        )
        self.log("command_result", exit_code=result.returncode,
                 output_tail=result.stdout[-260:].strip())
        return result.returncode == 0

    def read_file(self, path):
        self.log("read_file", path=path.relative_to(ROOT).as_posix())
        return path.read_text(encoding="utf-8")

    def write_file(self, path, content):
        if path.resolve() not in {p.resolve() for p in self.ALLOWED_WRITES}:
            self.log("permission_denied", path=path.relative_to(ROOT).as_posix())
            raise PermissionError(f"not allowed to write {path}")
        self.log("write_file", path=path.relative_to(ROOT).as_posix())
        path.write_text(content, encoding="utf-8")

    def check_no_float_for_money(self):
        """确定性检查：规则明确，不靠模型判断。"""
        for token in ("float(",):
            if token in TARGET_FILE.read_text(encoding="utf-8"):
                self.log("check_failed", token=token)
                raise AssertionError(f"forbidden token found: {token}")
        self.log("check_passed", rule="money code uses no float()")

    def save_trace(self, status):
        self.trace["finished_at"] = datetime.now(timezone.utc).isoformat(timespec="seconds")
        self.trace["final_status"] = status
        TRACE_FILE.write_text(
            json.dumps(self.trace, ensure_ascii=False, indent=2), encoding="utf-8")

    def execute(self, patch):
        backup = TARGET_FILE.with_suffix(".py.bak")
        shutil.copyfile(TARGET_FILE, backup)
        try:
            self.read_file(TARGET_FILE)

            try:  # 越权写入：测试文件不在白名单里
                self.write_file(ROOT / "tests" / "test_cart.py", "# 改测试来迎合实现\n")
            except PermissionError:
                pass

            if self.run(TEST_CMD):
                self.log("baseline", message="tests already pass, nothing to do")
                self.save_trace("already_passed")
                return

            self.write_file(TARGET_FILE, patch)

            if not self.run(TEST_CMD):  # 补丁没让测试通过，回滚
                shutil.copyfile(backup, TARGET_FILE)
                self.log("rollback", reason="tests failed after patch")
                self.save_trace("failed_and_rolled_back")
                return

            self.check_no_float_for_money()
            self.log("done", message="patch accepted because tests passed")
            self.save_trace("passed")
        finally:
            if backup.exists():
                backup.unlink()


if __name__ == "__main__":
    which = sys.argv[1] if len(sys.argv) > 1 else "normal"
    patch = {"normal": PATCH_PROPOSAL, "rollback": BROKEN_PATCH}[which]
    Harness(f"pricing: reject negative price without float ({which})").execute(patch)
```

三个设计点值得留意，它们对应的是第一节里那三层：

- `ALLOWED_WRITES` 是一个**白名单集合**，而不是判断「等于某个文件」。
  看起来一样，但白名单能随需求长大，而写死的比较每次都要改代码结构。
- `write_file` 被拒绝时**先记 trace 再抛异常**。顺序反了的话，
  越权尝试会从记录里消失——而那正是最需要留痕的一类事件。
- 备份是在 `try` 之前做的，删除在 `finally` 里。这样无论从哪条路径退出，
  备份文件都不会留下来（否则第二次运行会把它当成新的「原始文件」）。

### 实跑一：正常路径

```console
$ python agent_harness.py normal
{"type": "read_file", "path": "src/cart.py"}
{"type": "permission_denied", "path": "tests/test_cart.py"}
{"type": "run_command", "command": "python -m unittest discover -s tests -q"}
{"type": "command_result", "exit_code": 1, "output_tail": "22, in test_rounding_is_half_up\n    self.assertEqual(calculate_total(items), Decimal(\"1.01\"))\nAssertionError: Decimal('1.0') != Decimal('1.01')\n\n----------------------------------------------------------------------\nRan 5 tests in 0.001s\n\nFAILED (failures=2)"}
{"type": "write_file", "path": "src/cart.py"}
{"type": "run_command", "command": "python -m unittest discover -s tests -q"}
{"type": "command_result", "exit_code": 0, "output_tail": "----------------------------------------------------------------------\nRan 5 tests in 0.000s\n\nOK"}
{"type": "check_passed", "rule": "money code uses no float()"}
{"type": "done", "message": "patch accepted because tests passed"}
```

有一行值得停下来看：**`permission_denied`**。那段代码里故意做了一次越权尝试
（把测试文件改成一句注释，也就是「改测试来迎合实现」），
而它被写权限白名单挡住了——**代理没有能力把自己的验收标准改宽**。
这条限制是整个例子能成立的前提。

### 实跑一生成的 trace

```json
{
  "task": "pricing: reject negative price without float (normal)",
  "started_at": "2026-09-13T07:33:48+00:00",
  "steps": [
    {"type": "read_file", "path": "src/cart.py"},
    {"type": "permission_denied", "path": "tests/test_cart.py"},
    {"type": "run_command", "command": "python -m unittest discover -s tests -q"},
    {"type": "command_result", "exit_code": 1, "output_tail": "..."},
    {"type": "write_file", "path": "src/cart.py"},
    {"type": "run_command", "command": "python -m unittest discover -s tests -q"},
    {"type": "command_result", "exit_code": 0, "output_tail": "..."},
    {"type": "check_passed", "rule": "money code uses no float()"},
    {"type": "done", "message": "patch accepted because tests passed"}
  ],
  "finished_at": "2026-09-13T07:33:48+00:00",
  "final_status": "passed"
}
```

九步。它回答的正是「复盘」需要的问题：读了哪个文件、碰了哪里、跑了什么命令、
每步退出码是多少、凭什么接受这个补丁。

> **一个实现细节**：时间用的是 `datetime.now(timezone.utc)` 而不是
> `datetime.utcnow()`。后者返回的是**没有时区信息的** naive datetime，
> 在新版 Python 上已标记为弃用，而且写出来的时间戳不带 `+00:00`，
> 多个机器合并 trace 时会分不清时区。

### 实跑二：失败要回滚

把补丁改坏（`Decimal("0.95")` 写成 `Decimal("0.9")`，相当于把 VIP 折扣打成 9 折）：

```console
$ python agent_harness.py rollback
{"type": "read_file", "path": "src/cart.py"}
{"type": "permission_denied", "path": "tests/test_cart.py"}
{"type": "run_command", "command": "python -m unittest discover -s tests -q"}
{"type": "command_result", "exit_code": 1, "output_tail": "22, in test_rounding_is_half_up\n...\nFAILED (failures=2)"}
{"type": "write_file", "path": "src/cart.py"}
{"type": "run_command", "command": "python -m unittest discover -s tests -q"}
{"type": "command_result", "exit_code": 1, "output_tail": "_discount\n    self.assertEqual(calculate_total(items, user_type=\"vip\"), Decimal(\"104.50\"))\nAssertionError: Decimal('99.00') != Decimal('104.50')\n\n----------------------------------------------------------------------\nRan 5 tests in 0.001s\n\nFAILED (failures=1)"}
{"type": "rollback", "reason": "tests failed after patch"}
```

注意两次跑的失败数不一样：基线是 `failures=2`，打完坏补丁是 `failures=1`。
因为坏补丁确实修好了负数与舍入两项，只是把 VIP 折扣算错了——
**这正是测试套件的价值：它不关心你修好了几项，只看是不是全绿。**

回滚不能只说「我回滚了」。下面是本次运行的校验：

```console
$ md5sum src/cart.py > before.md5
$ python agent_harness.py rollback          # 上面那次
$ md5sum -c before.md5
src/cart.py: OK
$ python -c "import json; print(json.load(open('trace.json'))['final_status'])"
failed_and_rolled_back
```

`OK` 是重点：文件回到了补丁之前的内容，而不是「差不多」。
仅靠 `shutil.copyfile` 而不验证，很容易在备份时机上出错。

### 实跑三：确定性检查的两个方向

那一条「金额代码里不出现 `float(`」的检查不属于测试，它是一条**确定性检查**：
规则明确，不由模型判断。两个方向都得验证，否则无法区分「规则生效了」与
「这条规则从来没响过」：

```console
# 方向一：对有缺陷的代码必须报错
$ python -c "import agent_harness as h; h.Harness('x').check_no_float_for_money()"
{"type": "check_failed", "token": "float("}
AssertionError: forbidden token found: float(

# 方向二：对修复后的代码必须沉默
$ python agent_harness.py normal            # 上面实跑一里的路径
{"type": "check_passed", "rule": "money code uses no float()"}
```

这一步看起来像多余，但它抓住的是一类很常见的假绿灯：
规则写错了（比如正则写成了永远不会命中的形式），于是它**永远不响**，
而每个人都以为它在看着。**新增一条检查时必须补一个「它应该报错」的用例**，
这与写测试是同一件事。

### 这个例子体现了什么

22 行业务代码 + 31 行用例 + 134 行 Harness，已经有 Harness 的核心味道：

| # | 特点 | 靠什么实现 |
| --- | --- | --- |
| 1 | 代理不能随便改任何文件 | 写入白名单，越权尝试被挡下并留痕 |
| 2 | 修改不能靠嘴说完成 | 必须跑测试，看退出码 |
| 3 | 失败要回滚 | 备份 + 还原 + `md5` 校验 |
| 4 | 全过程有 trace | 每步记类型、参数、退出码、结束状态 |
| 5 | 完成标准是外部验证 | `final_status` 由结果决定，不由模型自信决定 |

### 它的边界也要说清

这个例子故意省掉了真实 Harness 里最难的部分：

- **补丁是写死的**。真实场景里，补丁来自模型，而模型可能提出各种形状的改动；
- **只有一条确定性检查**。真实项目里还有 lint、类型检查、构建、契约测试；
- **只有本地一关**。真实团队里它后面还有 CI、分支保护、人工评审（下一节）；
- **没有评测集**。单次任务过了不代表同类任务都能过（2.6.11）。

把它当成骨架而不是成品：骨架贵在**每个环节都可以被替换**——
把「写死的补丁」换成模型输出，其余四层完全不用动。

## 2.6.9 接入工程流水线：CI 门禁、PR 与审批

本地 Harness 只是第一关。上一节的 `final_status: passed` 只说明「在这台机器上过了」，
而团队要的是「**任何人都不能绕过**」。这一节把同一个思路搬到仓库里。

### 一条不可绕过的路径

推荐的做法只有一条：**不要让代理直接改主分支**。

```text
每个任务一个分支 → 代理提交 diff → CI 跑 → 人工 review → 合并
```

配套的 PR 模板五段：

```markdown
## What changed?

## Why?

## Verification
- [ ] Tests passed
- [ ] Lint passed
- [ ] Typecheck passed
- [ ] Manual check completed

## Risk
Low / Medium / High

## Rollback
How to rollback this change?
```

第二段 `Why?` 与最后两段是重点。`Why?` 留下的是需求上下文（否则三个月后没人敢动这段代码）；
`Risk` 与 `Rollback` 把「出事的时候怎么收场」提前写好——两者都是**为人准备**的，
但代理写它们的时候也不得不把自己那份不确定性交出来。

### 把验证脚本化

模板里那句 `bash scripts/verify.sh` 应该真有一个文件在后面：

```bash
#!/usr/bin/env bash
set -euo pipefail

echo "Running tests..."
python -m unittest discover -s tests -q

echo "Checking money code has no float()..."
if grep -rn "float(" src/ ; then
  echo "FAIL: float() is not allowed in money code" >&2
  exit 1
fi

echo "Verification passed."
```

它的好处是**本地与 CI 跑的是同一条命令**。如果本地跑一套、CI 跑另一套，
那就一定会出现「本地过了、CI 挂了」——而排查它们的差异比修 bug 更费时间。

在未修复的代码上，它停在第一步：

```console
$ bash scripts/verify.sh
Running tests...
...
Ran 5 tests in 0.001s

FAILED (failures=2)
$ echo $?
1
```

修复之后：

```console
$ bash scripts/verify.sh
Running tests...
Checking money code has no float()...
Verification passed.
$ echo $?
0
```

### CI 门禁：让「不许合并」变成机制

把这条脚本接进 CI，也就是仓库里一个工作流文件：

```yaml
name: pricing-check

on:
  pull_request:
    paths:
      - "src/**"
      - "tests/**"

jobs:
  verify:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - run: bash scripts/verify.sh
```

在仓库设置里把它设为**必需状态检查**，效果就是：**代理可以开 PR，但 CI 不通过就不能合并。**
这一句话是整章的落点——它把「不通过就不算完成」从一段代码里的 `if`，
变成了一道谁都绕不过的闸门。

### 四个坑：看着非常合理的工作流会卡住合并

上面那个工作流里藏着一个很熟悉的写法与实际后果的差距，官方文档里有一张专门的表：

| 情况 | 官方给出的结果 | 怎么避 |
| --- | --- | --- |
| 工作流被 **path 过滤**跳过（只改了 `docs/`） | 关联检查**一直停在 Pending**，合并被拦住 | 不要把可被跳过的**工作流**设为必需；把条件写在 **job 内部** |
| 某个 **job 被条件跳过** | 该 job 报告 **Success** | 可以放心用 job 级条件（但它不再是「没跑」的语义） |
| 某条检查**依赖一个失败的 job** | 依赖项被跳过，**可能不拦合并** | 用 `always()` 配合 `needs` |
| 用了 **merge queue** 却只监听 `pull_request` | 入队后检查不触发，合并失败 | 触发器加上 `merge_group` 事件 |

第一行直接冲击了上面那个工作流：它写了 `paths: ["src/**", "tests/**"]`，
那么一个只改文档的 PR **根本不会触发它**。如果它又是必需检查，
这个 PR 就会永远卡在「等待状态被上报」。而更隐蔽的是第二行：
**「跳过」与「没跑」是两种语义**——同一个仓库里，job 被条件跳过算通过，
工作流被路径过滤掉却算没发生。这两条规则不是常识能推出来的，
写了必需检查之后必须拿一个「不触发」的 PR 试一次。

这里还有一个与工作流无关但同样会卡住合并的坑：**job 名在多个工作流里重名**。
官方文档把它写成了注意事项——重名会让状态检查的结果语义不明，
从而阻塞合并。所以起名时要带上场景前缀（`pricing-check / verify`），而不是清一色的 `test`。

### 用第三方工具校验工作流会踩到的一个小坑

工作流是 YAML，于是很多人会用现成的 YAML 解析器去校验它。这一步会撞到一个老问题：

```console
$ python -c "import yaml; print(list(yaml.safe_load(open('.github/workflows/pricing-check.yml')).keys()))"
['name', True, 'jobs']
```

`on` 变成了布尔值 `True`。原因是 YAML 1.1 把 `on`/`off`/`yes`/`no` 当作布尔字面量，
而这份文档的作者写的是工作流关键字。后果是：按 `d["on"]` 取触发器的校验脚本会直接 `KeyError`。
看到这种报错，先怀疑解析器，而不是先去改工作流。

### 谁都可以写这个工作流：两家的差异

CI 门禁可以只跑自己的脚本，也可以让代理直接进来干活。两家工具的定位差别很大：

| | Claude Code GitHub Actions | Codex |
| --- | --- | --- |
| 入口 | 在 Issue / PR 评论里 `@claude`，或给工作流一个 `prompt` | 在 PR 评论里 `@codex review` |
| 能做什么 | Issue 转 PR、修 bug、跑定时任务、审查 PR | 审查 PR（默认只报 P0/P1）、`@codex fix the P1 issue` 让它动手 |
| 权限模型 | 装 GitHub App，授权 **Contents / Issues / Pull requests 读写**；装它需要仓库管理员权限 | 需要先配好云端接入，并要有仓库 push 或 admin 权限去开开关 |
| 配置存哪 | 仓库里的工作流文件 + 仓库 secret | 主要在服务设置面板，不在仓库里 |
| 自定义规则 | 读规则文件 | 读 `AGENTS.md` 里的 `## Code Review Rules` 段落 |

两边各有一条很容易忽略的事实：

- **Claude Code 侧是两种模式**：不给 `prompt` 时是**交互模式**（等你 @ 它），
  给了 `prompt` 就是**自动化模式**（不等你开口）。两种模式都会先检查**「谁可以触发」**，
  不满足就整次运行失败。所以「接了机器人」不等于「谁都能指挥它干活」。
- **装 App 授的不是三个权限，是一整套**。官方文档写明了这件事：App 的权限集是全部功能共用的，
  如果你只需要 `Contents / Issues / Pull requests`，得自己建一个自订 App；
  而自订 App 只覆盖 Action 这一块，另一些功能仍然要官方 App。
  这件事影响的不只是「能不能用」，而是**安全评审时你得说清它到底改了哪些开关**。

Codex 那侧有一条值得抄到自己的 `AGENTS.md` 里的写法：把审查规则写在**离代码最近的那个**
`AGENTS.md` 里（仓库根的写通用规则，服务目录里的写该服务的规则），并用 `###` 分组：

```markdown
## Code Review Rules

### Experiment cohorts
- Do not filter treatment comparisons on post-exposure behavior, including conversion or retention.
- Safe path: build cohorts from assignment or exposure; report conversion as an outcome.
```

两条写法上的经验：**先说该报什么，再说安全的做法**（只写「不要」会让它把预期行为也报出来）；
以及**机械检查留给 CI**——格式、lint 这类事由确定性工具做，不要写进审查规则里去烧模型。
还有一句必须记住：**审查规则不能取代测试、分支保护与必需的审批**。

### 安全清单

如果把机器人接进了仓库，下面七条建议逐条都值得做成默认值：

1. 只装到指定仓库，不要全组织开放；
2. 不要把生产密钥放进 Actions；
3. 对自动修复设置人工 review；
4. 不让机器人直接合并 `main`；
5. 工作流里限制触发分支、触发人、可执行命令；
6. 把规则文件、权限规则、钩子与 CI **同时**纳入代码评审；
7. 定期审计机器人创建的 PR 与它被授予的作用域。

第六条容易被忽略：规则文件与钩子也是代码，而且它们直接影响代理的行为。
只评审业务代码、不评审规则文件，等于留了一扇没人看的门。

### 并行分析与大任务：什么时候值得

当审查面变大时，还有一层工具：子代理。它适合「**只读、可并行、边界清楚**」的分析任务：

```text
请用 3 个只读子任务并行分析：
任务 A：检查前端页面到 API 调用链；
任务 B：检查后端接口、参数校验与错误处理；
任务 C：检查测试覆盖与缺口。
每个子任务必须输出：
1. 涉及文件；2. 关键发现；3. 证据；4. 风险；5. 建议。
最后由主任务汇总成一个修复计划。
先不要修改代码。
```

它也有一张「不该用」的清单，比该用的那张更重要：**一个函数的解释、单文件小改、
边界不清的任务、彼此强依赖的子任务、没有验收方式的任务**，都不适合拆——
拆完只会得到三份互相矛盾的结论，还得自己合并。

再大一档是动态工作流：代理由自己写一段编排脚本，在后台协调大量子代理，
适合代码库级安全审计、数百文件的 API 迁移、大型单仓库依赖盘点。
用之前必须写清六件事，否则规模越大越危险：

| 必须写清 | 例子 |
| --- | --- |
| 目标 | 可量化的结果 |
| 范围 | 目录 / 模块 / 文件数 |
| 禁止 | 不可触碰的内容 |
| 验证 | 测试、构建、审查标准 |
| 输出 | 报告、PR、迁移清单、失败项 |
| 停机条件 | 何时必须停下来等人决定 |

最后一行是新增的，也是最重要的一条：大规模任务必须自带**刹车**。

### 审查时先看什么

当 PR 真的摆在面前，检查顺序建议是固定的（这也是代理最容易蒙混的地方）：

1. **先看 diff，不看总结**——总结可以写得比代码好很多；
2. **看测试文件的改动**：新增了几条、删了几条，有没有把断言改宽；
3. **看是否改了不该改的文件**（配置文件、锁文件、部署脚本）；
4. **看是否新增了不必要的依赖**；
5. **看边界用例**：空输入、负数、极大值、并发；
6. **看有没有留下说明**（为什么要这样改）。

第 2 条对应的是最常见的一类蒙混：**为了让他自己通过而修改测试**。
在本章的例子里，这件事被写入白名单直接堵住了——但在真实项目里，
代理通常**有**写测试的权限（它必须能补测试），所以只能靠在评审时把
「测试的改动」与「实现的改动」分开看。

## 2.6.10 评价一个 Harness：成熟度、五类代理与五个误区

### 一张成熟度对照表

判断一个团队走到哪一步，看它的日常长什么样就够了：

| 阶段 | 日常长什么样 | 判定权在谁手里 |
| --- | --- | --- |
| 懵懂期 | 复制 AI 代码到项目里 | 人眼 |
| 起步期 | 让代理读文档、写代码 | 人眼 |
| 稳定期 | 代理跑测试、开 PR、留 trace、按规则工作 | 退出码 + 人 |
| 系统期 | 改 Harness 而不是改提示词；有评测集与失败案例库 | 机制 |

第三行是分水岭：**从「代理写得快不快」变成「它写的东西能不能被机器验收」。**
这不是态度问题，而是可验证性的问题——第一、二阶段里，
一个写得又快又好的同事和一个看起来很靠谱的代理，从外部根本区分不出来。

### 五类典型代理：同一套 Harness，不同的验收标准

搭 Harness 不是给代码生成专用。只要一个 AI 应用需要「多步执行、调用工具、
依赖外部状态、需要验证结果」，就需要它。五类常见形态的差别在**验收标准**：

| 形态 | 输入 | 提供给它的能力 | 完成标准 |
| --- | --- | --- | --- |
| 代码修复 | 一个线上报错 | 读日志、搜代码、改文件、跑测试、出 diff、开 PR | 新增复现测试；修复后测试通过；输出根因分析 |
| PR 审查 | 一个 PR | `git diff`、变更文件、代码规范、安全清单、历史决策、评论 API | 只评论具体文件与行；不输出泛泛建议；高风险问题说明影响与修法；不阻塞低风险风格问题 |
| 数据分析 | 一个分析问题 | 只读数据仓库、数据字典、指标口径、notebook、图表、结果校验、敏感字段脱敏 | SQL 可复现；指标口径引用明确；图表有数据来源；结论与证据对应；不泄露个人隐私 |
| 运维排障 | 一个告警 | 日志、指标、链路追踪、发布历史、应急预案、回滚工具、权限审批 | 找出时间线；关联最近变更；给出可能根因；提供低风险缓解建议；**回滚必须人工确认** |
| 文档维护 | 一次接口变更 | OpenAPI 规范、代码扫描、文档目录、markdownlint、预览构建 | 文档与接口一致；示例能运行；链接不失效；PR 描述说明变更范围 |

四列里最值钱的是最后一列。它示范了怎么把「做得好」写成可判定的句子：
「只评论具体文件与行」排除了报一堆泛泛建议，「回滚必须人工确认」直接嵌入了停机点，
「不泄露个人隐私」把一条合规要求变成了验收项。

### 五个误区

| 误区 | 为什么错 | 正确做法 |
| --- | --- | --- |
| 提示词越长越好 | 太长会稀释重点 | 入口短、文档分层、规则明确、按需读取 |
| 工具越多越强 | 选择成本上升，低风险任务可能变成高风险操作 | 工具要少、稳、可组合 |
| 过一次测试就放心 | 测试只能证明你测过的地方没问题 | 边界、回归、人工评审、灰度、监控、回滚 |
| 代理会自动理解团队品味 | 架构偏好、命名习惯、抽象边界、错误处理方式不会从代码里自动浮现 | 写下来，并用 lint、测试或评审清单固定住 |
| 只适合大公司 | 小团队没有那么多人力去 review | 加一个规则文件与一条验证命令就已经比纯 Vibe Coding 稳 |

其中第三个误区在本章 2.6.5 里被实测了一次——**一条叫「不引入浮点精度问题」的
用例在浮点版本上照样通过**。它是这个误区最具体的形状：
红色好认，绿色难辨。

第四个误区给出了一个很好的工作方式：**团队品味要能被 lint 或测试固定**。
一句写在评审清单里的「金币用整数存」，时间一长会被人忘掉；
一条 `grep` 能报警的规则不会。两条路径的分界线是：**能不能被机器否认**。

## 2.6.11 团队落地：四步与评测闭环

### 分四步走，不要一上来搞平台

| 步骤 | 做什么 | 关键动作 |
| --- | --- | --- |
| 一、补最小项目上下文 | 让代理不迷路 | 加 `AGENTS.md` + `docs/architecture.md` + `docs/testing.md`，先保持短 |
| 二、把完成标准机器化 | 让「完成」可判定 | 把「代码质量要好」换成 `pytest` / `lint` / `typecheck` / `build` |
| 三、变更统一走 PR | 让过程可审计 | 每任务一分支 → diff → CI → 人 review → 合并 |
| 四、记录失败并改进 Harness | 让系统变好 | 每次出错先问「是哪里没设计好」 |

这个顺序不能换：跳过第一步，规则的堆积无处可放；跳过第二步，
后面的 CI 没有任何内容可跑；跳过第四步，同一个错会一直犯。

### 失败归因八问

第四步的具体做法是一张问句表。每次代理出错，先别骂模型，
而是拿这八个问题对着看，每个问题都指向 Harness 的一个具体位置：

| 问自己 | 改哪里 |
| --- | --- |
| 是任务没写清楚？ | 任务规格（2.6.2） |
| 是上下文缺了？ | 项目记忆与知识分层（2.6.3） |
| 是工具太多？ | 工具路由与白名单（2.6.1、2.6.8） |
| 是没有测试？ | 验证机制（2.6.5） |
| 是权限太大？ | 权限闸门与停机点（2.6.7） |
| 是日志太乱？ | trace 与可观测性（2.6.6） |
| 是完成标准不明确？ | 完成标准机器化（2.6.5） |
| 是旧文档误导了它？ | 知识系统的维护（2.6.3） |

然后把经验沉淀到具体位置：规则文件、测试文件、新测试、
新的 lint 规则、新的审批规则、新的应急预案、新的评测用例。
**沉淀到具体文件，而不是沉溠到「以后注意」**——这是第四步与「复盘会」的差别。

### 小团队可以直接抄的目录

```text
my-project/
├── AGENTS.md
├── docs/
│   ├── architecture.md
│   ├── testing.md
│   ├── coding-style.md
│   └── decisions/
│       └── 0001-key-decision.md
├── scripts/
│   └── verify.sh
└── .github/
    └── pull_request_template.md
```

配套的 `scripts/verify.sh` 就是上一节那份；`docs/testing.md` 里至少要写清三件事：

```markdown
# Testing

## Unit Tests
Run: python -m pytest -q

## Required Coverage
For business logic changes, include:
- normal case
- boundary case
- invalid input
- regression case if fixing a bug

## Completion Rule
A task is not done until tests pass.
```

最后一句是全章的浓缩：**「测试通过之前，任务不算完成。」**
它没有提到 AI 一个字，但它是本章剩下的所有机制的理由。

### 评测：从「感觉变好了」到「知道变好了」

当团队开始大量使用代理，会碰到一个新问题：**我们怎么知道它越来越好了，
还是只是感觉越来越好了？** 这就该引入评测用例：

```yaml
id: pricing-negative-price
task: Fix cart pricing to reject negative prices.
repo_state: fixture/pricing_bug
expected:
  tests:
    - tests/test_cart.py::test_negative_price_rejected
  forbidden_patterns:
    - "float("
  required_files_changed:
    - "src/cart.py"
```

这份用例与单元测试的差别在**验收对象**：单元测试验收代码，它验收**Harness 自己**。

| 字段 | 作用 |
| --- | --- |
| `id` / `task` | 用例标识与任务描述 |
| `repo_state` | 从哪个固定状态开始（回归的前提） |
| `expected.tests` | 必须变绿的用例 |
| `expected.forbidden_patterns` | 禁止引入的写法 |
| `expected.required_files_changed` | 必须改到哪些文件（防止只改测试蒙混） |

后两个字段是关键：它们把「怎么算做对了」写成了**可机器判定的约束**。
每次改规则文件、改提示词、改工具、换模型，都跑一批评测，
看成功率、耗时、词元、失败类型有没有变化。

失败类型要记下来，因为它直接指向该改哪里：

```json
{
  "case_id": "pricing-negative-price",
  "result": "failed",
  "failure_type": "missing_test",
  "notes": "Agent fixed implementation but did not add regression test."
}
```

看到 `missing_test` 这种失败，能做的事很具体：
在规则文件里加「修 bug 必须先写失败测试」；在验证脚本里检查测试文件是否被变更；
在 PR 模板里强制填写回归测试；在输出要求里让它列出新增测试。
**这就是 Harness 的自我改进：把一次失败变成一个不会再发生的约束。**

### 这件事和「传统软件工程」的关系

有一个很危险的叙事：「AI 编程会把传统软件工程淘汰掉」。现实恰好相反：
**传统工程里那些好习惯，在代理时代会变得更重要。**
清晰的模块边界、自动化测试、类型系统、CI/CD、代码评审、文档、决策记录、
可观测性、权限控制、灰度发布、回滚机制——这些东西以前是为了帮人类协作，
现在多了一个作用：**帮代理正确工作**。

一个没有测试、没有文档、没有边界、没有 CI 的项目，人维护起来已经困难；
让代理维护，只会更乱。代理不会把混乱变成秩序，它会**准确地放大你给定的环境**。

### 工程师的角色变了，责任没变

在 Vibe Coding 阶段，工程师像个「指挥员」：写这个、改那里、报错了修一下。
到了搭 Harness 的阶段，关心的问题变了：

- 需求如何表达成规格；
- 项目知识如何组织；
- 代理能用哪些工具；
- 哪些操作需要审批；
- 怎样验证完成；
- 怎样记录过程；
- 怎样评估质量；
- 怎样让失败经验沉淀到系统里。

也就是说：**工程师不一定逐行写代码，但要对系统结果负责。**
后面几篇（尤其是第 7 篇「AI 应用工程化」）会把评测、监控、安全这些环节展开。

### 往后看：四个会变的东西

| 变化 | 含义 |
| --- | --- |
| 写代码继续变便宜 | 样板、测试补齐、文档更新会大量交给代理；难的是判断该做什么、风险在哪里 |
| 仓库变得更「代理可读」 | 好仓库不仅要人看得懂，还要代理看得懂：清晰文档、机器可执行验证、明确模块边界 |
| CI/CD 成为代理的工作场所 | Issue 分类、PR 审查、CI 失败修复、发布说明、故障响应都会有人机协作的形态 |
| Harness 成为核心资产 | 模型会换、框架会过时，但任务模板、测试体系、trace 数据、评测集、权限模型会积下来 |

最后一行是这一章最想留下的一个判断：**你加的东西会过时，你沉淀的东西不会。**

## 2.6.12 本章验收：给知舟接一条最小流水线

把本章的东西落到全书那条主线上。目标不是「一次配齐」，而是
**每一步都能被独立验证**。

### 文件树

```text
zhizhou-api/
├── AGENTS.md                          项目地图（2.6.3）
├── docs/
│   ├── architecture.md                模块边界
│   ├── testing.md                     测试命令与完成规则
│   └── decisions/
│       └── 0001-money-decimal.md      与金额/时间相关的关键决定
├── scripts/
│   └── verify.sh                      本地与 CI 共用的验证命令
├── .github/
│   ├── workflows/ci.yml               必需状态检查
│   └── pull_request_template.md       PR 五段模板
└── exec-plans/
    └── 2026-09-article-pagination.md  当前长任务的进度（2.6.4）
```

### 四个文件的最小内容

`AGENTS.md`（地图，不是手册）：

```markdown
# AGENTS.md

## Start Here
先读这一行：本文档是地图，不是完整手册。

## 架构
见 docs/architecture.md。

## 测试与完成标准
见 docs/testing.md。改行为必须补用例。

## 决定
改金额或时间存储前，先读 docs/decisions/。

## 常用命令
- 验证：bash scripts/verify.sh
- 本地服务：uvicorn app.main:app --reload

## 完成标准
- bash scripts/verify.sh 通过
- 行为变更时文档已更新
- PR 描述里带验证结果
```

`docs/testing.md` 里的完成规则就是那句：**`bash scripts/verify.sh` 不过，任务不算完成。**

`exec-plans/2026-09-article-pagination.md` 四字段：`Goal` / `Milestones`（带勾选框）/ `Current Status` / `Risks`。

`.github/pull_request_template.md` 五段：`What changed` / `Why` / `Verification`（勾选框）/ `Risk` / `Rollback`。

### 六条验收

每一条都是一个可执行动作，做完把结果记下来（包括失败的那几条）：

| # | 验收什么 | 怎么验 |
| --- | --- | --- |
| 1 | 规则确实被读到 | 新会话里让它总结本项目指令，对不上说明没加载 |
| 2 | 完成标准真的能让任务停下来 | 故意引入一个不引入的写法（如金额用 `float`），看验证是否变红 |
| 3 | 验证命令只有一份 | 本地与 CI 日志里出现的是同一条命令 |
| 4 | 必需检查真的拦得住 | 开一个故意不过 CI 的 PR，确认按钮是灰的 |
| 5 | 不触发的工作流不会卡住合并 | 开一个只改文档的 PR，确认它不会被「Pending」挂住（这是 2.6.9 第一个坑） |
| 6 | trace 真的能复盘 | 拿一次真实运行，只看 trace 能否回答「读了什么、改了什么、为什么接受」 |

第 4 与第 5 条必须**真的开一次 PR**。这两件事的共同点是：
它们在仓库设置里，不在代码里——而**仓库设置的部分最难被代码评审覆盖**，
只能靠实际做一遍来确认。

### 把这六个问题带回你的项目

本章的所有机制，可以缩成六个能长期用的问题。任何一个 AI 应用上线前，
拿它们逐个对一遍：

| # | 问题 | 对应本章 |
| --- | --- | --- |
| 1 | 这个应用的**输入契约**是什么？ | 用户能说任何话，但系统不能接受含糊目标直接执行（2.6.2） |
| 2 | 它能用哪些**工具**？ | 每个工具都要有名称、描述、输入/输出 schema、权限、风险级别、是否需审批（2.6.1） |
| 3 | 它的**状态**放哪里？ | 短期状态可以在对话里，长期状态要落到数据库、文件或 trace 存储（2.6.4） |
| 4 | 它怎么**判断完成**？ | 不能只靠模型说完成，要有可验证标准（2.6.5） |
| 5 | 它怎么**失败**？ | 工具失败、权限不足、上下文不足、测试失败、外部超时、目标冲突、安全拒绝——每种都要有明确输出，而不是一句「抱歉我失败了」（2.6.6） |
| 6 | 它怎么被**审计**？ | 能改代码、查数据、发消息、开 PR、触发部署，就必须能审计（2.6.6） |

第六个问题最容易被当成「以后再说」。而它实际上是前面五个问题的保险——
没有它，前五个即使做对了，出了问题你也只能靠猜。

### 从这一章往后

第 2 篇到这里结束。回头看一下这条线：

```text
2.1 为什么要搭工作台（思维模型 / 能力边界 / 风险）
2.2 第一个工具（Claude Code）          ┐
2.3 第二个工具（Codex）                 │ 零件
```

但有个习惯已经在第 2 篇里形成了：**每引入一个能力，先问它的验收方式是什么。**
这个习惯在第 7 篇（评测、监控、安全）会被展开成完整的工程体系。

## 常见坑

1. **让代理改自己的验收标准。** 最危险的一类蒙混是「为了让测试变绿而改测试」。
   本章的例子用写入白名单直接堵死；真实项目里代理必须能补测试，
   所以只能靠在评审时把测试改动与实现改动分开看。
2. **完成任务靠模型说完成。** 只要完成标准里还有形容词（「质量要好」），
   判定权就回到了感觉上。换成命令与退出码。
3. **写了进度文件却不同步。** 勾选框停在两周前，比没有更糟：
   它会误导下一轮先去做已经做完的事。
4. **分支保护设了必需检查，却忘了 path 过滤。** 工作流直接被跳过时，
   检查会永远停在 Pending，一个只改文档的 PR 就卡死了。
5. **靠 job 条件来控制「跑不跑」。** job 被跳过报的是 Success，
   而工作流被过滤掉是「没发生」——两种语义完全不同。
6. **用 `always()` 之外的办法处理依赖关系。** 依赖一个失败 job 的检查可能不拦合并，
   必需检查要用 `always()` 配合 `needs`。
7. **多个工作流里用同一个 job 名。** 官方文档写明它会让状态检查结果语义不明而阻塞合并；
   加前缀。
8. **trace 记了不该记的。** 把完整请求体或密钥写进 trace，等于新增一个泄露面；
   记摘要与引用。
9. **回滚只说「已回滚」。** 备份时机错一次就会把「改了一半」当原文件。
   回滚后用校验（哈希、用例）确认，而不是相信代码路径。
10. **一次性把工具都接上。** 工具越多选择成本越高，低风险任务可能被做成高风险操作；
    先少而精，需要时再加。

## 面试视角

1. **「让你给团队搭一套 AI 编程流程，你怎么保证代理写的东西可信？」**
   考察点：是否知道「完成」必须外部判定。答题要点：任务规格（Goal / Non-goals / Done When）
   → 验证机制（测试 + 确定性检查）→ 限权写 → 失败回滚 → trace → CI 必需检查。
   能说出「它不能改自己的测试」这种具体约束就到位了。
2. **「为什么要把 CI 设成必需检查，而不是在提示词里要求它跑测试？」**
   考察点：上下文与强制执行的区别（与 2.5 的连接）。答题要点：写在规则文件里的要求
   由模型遵循，可以被忽略；必需状态检查由平台执行，绕不过。两者是互补而非替代。
3. **「一条测试全绿的 PR，你会重点看什么？」**
   考察点：是否知道测试可以被写宽。答题要点：先看 diff 不看总结；
   看测试文件的增删与断言是否被改宽；看是否改了不该改的文件；看是否新增了不必要的依赖。
4. **「长任务跑一半上下文被压缩了怎么办？」**
   考察点：是否有状态外置的习惯。答题要点：进度文件（Goal / Milestones / Current Status / Risks），
   以及计划里的「不改哪些文件 / 怎么验证 / 怎么回滚」三问。
5. **「单次任务过了不代表以后都能过，怎么评测一套 Harness？」**
   考察点：是否知道评测集的验收对象是 Harness 而不是业务代码。答题要点：
   eval case 的 `repo_state` / `expected.tests` / `forbidden_patterns` / `required_files_changed`，
   以及用失败类型（如 `missing_test`）反向修补约束。

## 本章小结

1. **Harness 的判据不是「用了多少 AI 功能」，而是「完成由谁判定」。**
   三问：产物有没有外部验收？失败能不能回滚？过程能不能复盘？
2. **六个位置：任务规格、上下文选择、工具路由、权限闸门、状态存储、trace、验证层。**
   少一层就会出现一类特定失败，排查时先找缺的那一层。
3. **任务规格五个字段里最不能省的是 `Non-goals` 与 `Done When`**：
   前者划爆炸半径，后者把完成交给外部判定。
4. **项目记忆回答「一直是怎么做的」，进度文件回答「现在做到哪了」。**
   前者是分层知识系统（入口短、知识分层，关键决定写清背景 / 决定 / 后果），
   后者四个字段（Goal / Milestones / Current Status / Risks）。
5. **验证手段有十种**（单元 / 集成 / lint / 类型 / 构建 / 快照 / 黄金文件 / 契约 /
   迁移 dry-run / 回归）；失败信息本身就是产品，「哪条用例、期望什么、实际什么」三样缺一不可。
6. **一条名字很好但验证不了一件事的测试是负资产**：实测中「不引入浮点精度问题」
   这条用例在浮点实现上照样通过；换成半进位（`1.005 → 1.01`）才真能抓住它。
7. **trace 与日志的差别在于有没有结尾状态**：`final_status` 把「到底过没过」变成可查询的事实。
   该记工具调用、命令与退出码、结果摘要、结束状态；不该记密钥与个人隐私。
8. **停机点的判据是「不可逆 × 爆炸半径」**，而且要写成允许与不允许两半；
   它必须落在工具能执行的地方，不能只写在规则文件里。
9. **最小可验证 Harness 的五个特征可以全部实跑**：限权写、靠退出码判定、
   失败回滚并校验、全程 trace、完成标准外部化；把写死的补丁换成模型输出，其余四层不用动。
10. **接进流水线靠三条：一条验证命令、一条 CI 必需检查、一个停机点。**
   GitHub 上四个坑要提前知道：被 path 过滤跳过的工作流会卡住合并、
   条件跳过的 job 算通过、依赖失败 job 的检查可能不拦、用 merge queue 必须加 `merge_group`。
11. **工程习惯在代理时代变得更重要，而不是过时。** 代理不会把混乱变成秩序，
   它会准确地放大你给定的环境；所以评测集与失败案例库是真正的资产。

## 练习

- **基础**：把一个你手头的模糊需求（「优化一下」「改得好一点」）改写成任务规格，
  要求五个字段齐全，并且 `Done When` 里的每一条都能写成一条命令或一个断言。
- **基础**：给你的项目写一份 `docs/testing.md`，必须包含「完成规则」一句话，
  并列出业务逻辑变更时必须覆盖的四类用例（正常 / 边界 / 非法输入 / 回归）。
- **进阶**：把本章的最小 Harness 改成"限权写 + 两档验证"：除了跑测试，
  再加一条确定性检查（例如「迁移文件里不许出现 `DROP TABLE`」）。
  要求两个方向都验：对违规代码它必须报错，对含规代码它必须沉默。
- **进阶**：给一个仓库配好 CI 必需检查，然后故意开两个 PR：
  一个 CI 会挂的、一个只改 `docs/` 的。用它们分别验证「拦得住」与「不卡住」，
  并记录下你踩到的坑。
- **综合**：为你的项目写三个 eval case（一个正常任务、一个需要修 bug 的任务、
  一个应该被拒绝的任务），跑一遍并写下失败类型；
  然后将其中至少一条反向修补成一个新约束（规则文件 / 校验脚本 / PR 模板）。
