# 8.2 CI/CD 与发布：自动化测试、构建与灰度发布

## 本章导读

8.1 问的是「打出来的那个东西有多重」；这一章问的是**「有没有人去打它」**。这一层的问题与 8.1 一样，答案在你机器的外面——只不过这次外面的东西换成了**另一个时刻、另一个人的身份、另一条分支上的那份代码**。它比镜像更难自查，因为它的每一条默认值都**不会在本地留下痕迹**：你本地 `pytest` 全绿，而流水线可能根本没被触发；你以为「没跑」等于「没过」，而官方口径给「没跑」准备了**两个相反的结论**。

**这一章的第一句话可能反直觉**：**一次提交会起两个 run，而「这一格没跑」有时算通过。**`push` 与 `pull_request` 都成立时，同一份提交跑两遍——两份账单、同一次检查。而更要紧的是三句官方原话：**被跳过的 job 会报 Success，即使它是必需检查也不阻止合并**；**因路径过滤、分支过滤或提交信息被跳过的，检查会停在 Pending，要求它的 PR 被挡住**；**必需检查的合格状态只有 `successful`／`skipped`／`neutral` 三种**。三句话合起来，本章的主轴就定了：**「没跑」不是一个结论，它是两个相反的结论**，而这两种写法在配置文件里只差一个词。与 6、7 篇一样，本章**不连 GitHub、不要密钥、不跑 runner**：六组读数全是模型与算术算出来的。

## 8.2.1 触发与过滤：一类改动有没有门，由过滤器决定

流水线的第一道关口不是测试，是**触发器**。`on:` 决定这个工作流响应哪些事件，`paths:` / `paths-ignore:` 决定**哪些改动根本不进流水线**。后者的性质值得单说一句：它**不是「跳过一次检查」，而是「这一类改动从此没有再被检查过」**——而这件事不会出现在任何输出里。

```text $ python scripts/ci_reader.py --offline
=== 一、触发与过滤：十一次提交 × 四种过滤器 ===
写法                              进流水线    漏掉    漏掉里最贵的那一条
不写过滤器                        11          0       —
白名单·窄（只 app/ 与依赖）       3           7       chore: 顺手改一下门自己
黑名单·宽（只挡文档）             10          0       —
白名单·宽（把该管的都列上）       9           1       chore: 新增一个部署目录

**窄白名单漏掉 7 条（十一次里漏七次）**，而它漏掉的第一条就是「chore: 顺手改一下门自己」——
改 `ci.yml` 那一次不进流水线，于是「门」这个东西从此没有人检查
**两种「宽」写法今天各只漏 1 条与 0 条，而这两个数不是同一件事**：
黑名单漏 0 条是「今天不痛」（新目录默认被检查），宽白名单漏 1 条是因为**名单是枚举——枚举永远漏一个**
（新目录不进名单就不被检查，而没人会记得上来加一行）
十一次提交里，**只有改文档那一次是真的不该跑**（本该进流水线的有 10 条）
=== 一次提交起几个 run ===
同仓分支                  2 个 run：push ＋ pull_request 各一个 run
fork 的 PR                1 个 run：只有 pull_request（push 发生在 fork 里）
提交信息带 [skip ci]      0 个 run：[skip ci]：两个事件都不起（检查停在 Pending）

**同一份提交跑两遍**（`push` 与 `pull_request`）——两份账单、同一次检查；而 fork 的 PR 只有一份
**`[skip ci]` 不是「少跑一次」，是「这一格没有结论」**：它停在 Pending，而要求它的 PR 被挡住
```

那五行数字各有各的读法：

**① 窄白名单漏掉了七条，而漏掉的第一条恰好是「改门自己」。**`paths: [app/**, requirements*.txt]` 是很多人第一版会写的东西——它挡住了 `Dockerfile`、`tests/`、`web/`、`scripts/`，也挡住了 `.github/workflows/ci.yml`。最后这条不是「少检查一次」：**那一份文件正是决定「谁会被检查」的文件**。于是从此以后，任何人改这个门都不会被这个门检查。这是本章最典型的「不报错」：流水线全绿，因为它根本没跑。

**② 两种「宽」写法今天都不漏，而它们的「不漏」不是同一件事。**黑名单（`paths-ignore`）是**默认放行**：新目录默认被检查，今天一条不漏——它的风险在**未来**（某天有人往被忽略的目录里放了一个决定行为的配置文件）。白名单是**默认拒绝**：它的不漏要**靠人记得上来加一行**，而读数里它就漏了那一条新增的目录。所以真正的结论不是「哪种写法更好」，而是：**过滤器是默认值的一种，而默认值永远站在「不做检查」那一边**——你写的每一个模式，都是在为「从此不用管这一类改动」签字。

**③ 十一次提交里只有一条真的不该跑**（改文档那次）。这一条是本节里**唯一由人断言的数**（`SHOULD_RUN ＝ 10`），其余全是从模型里算出来的。把它单列出来是有意的：**「该不该跑」这句话没有机器口径**——任何过滤器都是在拿「漏检的风险」换「账单」，而这一笔交易只有人能做。

接着是「一次提交起几个 run」：

**同一份提交会起两个 run。**`push` 与 `pull_request` 在同一仓库的分支上**都成立**，所以两个事件各起一个 run：同一份代码、同一次检查、两份额单。这不是配置错误，是两件事确实都在发生（一次是「这条分支被推了」，一次是「这个 PR 的头变了」）。而 fork 来的 PR 只有一个：那个 `push` 发生在**对方的仓库**里，用的是对方那份配置——**你这边看不到它，它也不在你这边计费**。

**`[skip ci]` 不是「少跑一次」，是「这一格没有结论」。**它是官方给的五个固定字符串之一（`[skip ci]`／`[ci skip]`／`[no ci]`／`[skip actions`]／`[actions skip]`，另有 `skip-checks:true` 的预告行写法），写在提交信息里就让 `push` 与 `pull_request` 都不起流水线。而官方在同一页上写清了后果：**因提交信息被跳过的，与它相关的检查会停在 Pending**——于是「本地已经跑过了」这句善意的话，在这里等于**让这个 PR 卡住**。它只对 `push` 与 `pull_request` 生效（`pull_request_target` 不受影响），这一条记在 8.2.4 的危险面上。

> 💡 **提示**：本节每个读数都来自 `zhizhou-v8/scripts/ci_reader.py --offline`（`app/trigger.py` 是它的模型）。它**不连 GitHub、不要密钥**：触发与过滤是按**官方语法**建模的（事件与过滤器就是那几个字符串），run 数由 `runs_for()` 算出来。所以它能量的是**这些过滤器的性质**，量不了真实仓库的事件风暴——真实项目里还会叠加 `schedule`、`workflow_dispatch`、`merge_group` 等等。

## 8.2.2 job 图与并发：`needs` 决定关键路径，槽位只能填满它

`needs` 写的是「谁等谁」。不写就是**谁都不等谁**——于是所有 job 同时起，墙钟最短，而**门是假的**：`e2e` 会跑在 `unit` 之前，那个绿与这一版代码无关。

```text $ python scripts/ci_reader.py --offline
=== 二、job 图与并发：`needs` 决定关键路径，槽位只能填满它 ===
图                              关键路径                1 槽  2 槽  4 槽  顺序违背
扁平（谁都不 needs 谁）         （无依赖）              32    17    12    5
一条链（每步都等上一步）        lint → … → deploy    32    32    32    0
正确的图（lint 与 unit 并行）   unit → e2e → deploy   32    21    21    1

**最快的图是最差的门**：扁平图 12 分钟跑完，而它有 5 处顺序违背——`e2e` 跑在 `unit` 之前，那个绿与这一版代码无关
**正确的图 21 分钟，而从 2 个槽加到 4 个槽一分钟不省**（关键路径就是 21）
——一条链无论给多少槽都是 32 分钟：槽位只能填满关键路径，填不满它就只能排队
=== `matrix`：格数就是账单（每格 4 分钟）===
六格全跑                              6 格    可计费 24 分    墙钟 12 分
exclude 掉两格                        4 格    可计费 16 分    墙钟 8 分
其中第一格红掉（fail-fast）           4 格    可计费 2 分     墙钟 1 分  取消 3 格

**最后一行是这一节最容易被忽略的账**：`fail-fast` 在第 1 分钟取消了另外三格——
省下 14 分钟，代价是**那三格从来没有结论**（报的是 `cancelled`）
```

第一张表里每一列都在说一件不同的事：

**① 最快的图是最差的门。**扁平图 12 分钟跑完（四个槽全开），而它有**五处顺序违背**——`MUST_PRECEDE` 那五对关系（lint→unit、unit→integration、unit→e2e、integration→deploy、e2e→deploy）一对都没被表达。正确的那张图 21 分钟，只留了一处**无害**的违背（`lint` 与 `unit` 互不依赖，谁先谁后都对）。**加门是要花时间的**：21 与 12 的差就是「顺序」这个词的价格。

**② 槽位只能填满关键路径。**正确的图从 1 个槽到 2 个槽省掉 11 分钟（32 → 21），而从 2 个槽加到 4 个槽**一分钟都不省**——因为关键路径就是 21 分钟，剩下的 job 都卡在它后面。一条链更极端：无论给多少槽都是 32 分钟。所以「加并发」不是线性省时间，它是一个**上限**：你只能把「等待」压到关键路径那么长，压不过去。真要高并发之前先问一句：**我的关键路径是哪条**。

**③ `matrix` 把格数变成账单。**六个格就是六个 job：可计费 24 分钟、墙钟 12 分钟（2 个槽）。`exclude` 掉「前端 × 两个旧版本」那两格之后是四格（16 分钟），而这一刀省的是**没有意义的组合**——前端不需要在三个 Python 版本上各跑一遍。

**④ `fail-fast` 取消掉的格，既不是失败也不是通过。**读数里第一格在第 1 分钟红掉，`fail-fast`（默认开）当场取消另外三格：省下 14 分钟，报出来的是一个 `failure` 加三个 `cancelled`。而官方给必需检查列的合格状态只有三种（`successful`／`skipped`／`neutral`）——`cancelled` 不在其中。**那三格从来没有给出过结论**，而它们在 PR 页面上看起来像是「跑过了」。

最后是 `concurrency`。它的三个字段里最要紧的是 `group`（哪些运行互斥）与 `cancel-in-progress`（互斥时取消谁）：

```text $ python scripts/ci_reader.py --offline
=== `concurrency`：取消谁（连推三次、每次 21 分钟）===
cancel-in-progress: true（group 带 ref）      可计费 27 分      取消 2  结论文：最后一次
不写 cancel-in-progress（同一个 group 排队）  可计费 63 分      取消 0  结论文：最后一次（前两次的结论已经过期）
group 写宽了（只写 ci，不带 ref）             可计费 27 分      取消 2  结论文：最后一次

**省下两次全量（63 → 27 分钟）**，而代价是前两次的检查报 `cancelled`；
排队那一行把三个 run 都跑完（前两个测的是已经不在的代码），而它连「省」都没有——
**取消省的是账单，排队省的是「哪一次的结论算数」**
第三行（group 写宽了）**账单与第一行完全一样，性质却完全不同**：**在 main 上的一次运行会把 PR 的运行取消掉**
```

**取消省的是账单，排队省的是「哪一次的结论算数」。**取消那一行把三次连推的 63 分钟压到 27 分钟（前两次各跑到第 3 分钟就被后面那次顶掉），代价是前两次的检查报 `cancelled`；排队那一行把三个 run 都跑完——而前两个测的是**已经不在的代码**，它们的绿没有任何意义。而第三行是这一节最该记住的一个坑：**`group` 的键写宽了，账单与正常取消一模一样，性质却完全不同**——只写 `ci` 而不带 `github.ref` 时，**在 `main` 上的一次运行会把 PR 的运行取消掉**：两次互不相干的推送互相踩，而你去查的时候只会看到「PR 的检查被取消了」。

> ⚠️ **注意**：这几个旋钮的顺序是有讲究的：先写对 `needs`（把门立起来），再看关键路径（决定槽位值不值），最后才谈 `matrix` 与 `concurrency`（省账单）。反过来做，你会得到一个很快、很便宜、而**什么都没验过**的流水线。

## 8.2.3 缓存与产物：命中哪一条、靠哪条规则、以及「拿得到」的判据

缓存与产物是流水线里最容易混成一件事的两样东西：它们的输入都是文件、都有名字、都会过期，而官方给它们的规矩**完全不同**。先看缓存——这一节的每个数都来自官方那套查找顺序：

```text $ python scripts/ci_reader.py --offline
=== 三、缓存：命中哪一条、靠哪条规则命中的 ===
行  分支       key             命中            作用域    规则                      cache-hit
A   feat/rag   pip-3.12-cccc   pip-3.12-cccc   feat/rag  精确匹配 key @feat/rag    ✔
B   feat/rag   pip-3.12-dddd   pip-3.12-cccc   feat/rag  restore-key：pip-3.12- @feat/rag✘
C   main       pip-3.11        pip-3.11-aaaa   main      key 的部分匹配 @main      ✘
D   main       pip-3.12-e500   pip-3.12-bbbb   main      restore-key：pip- @main   ✘
E   feat/rag   pip-3.11-aaaa   pip-3.11-aaaa   main      精确匹配 key @main        ✘
F   main       pip-3.12-cccc   （没有）        —        全都试过，没有            ✘

**六行里只有 1 行 `cache-hit` 为真，而有 5 行真的恢复到了文件**
B：**恢复了旧依赖的缓存**，而官方那个布尔值是 false——拿它当「缓存生效了吗」会得出相反结论
C：`key` 自己的部分匹配**先于 `restore-keys`**（试了 2 步，写的那条 restore-key 根本没轮到）
E：**跨分支共享是单向的**——feat/rag 看得到 main，而反向看不到（F 行：`main` 找不到只建在 `feat/rag` 上的那条）
```

六行里有五行**真的恢复了文件**，而只有一行 `cache-hit` 为真。这就是这一节的第一条纪律：

**① 「命中」与「恢复了东西」不是一回事。**官方口径：`cache-hit` 只在 **exact** 匹配时为真；而 `restore-keys` 的前缀命中会**真的把文件恢复出来**（B 行）。所以拿 `cache-hit` 当「缓存有没有生效」的判据，会得到一个相反的结论：B 行明明恢复了 185 MB 的依赖目录（而且这正是 `restore-keys` 的用法：先恢复旧依赖、再让 `pip install` 补齐新增的那几个），而那个布尔值说「没有命中」。

**② 搜索顺序比「写了什么」更要紧。**官方顺序是：当前分支上 `key` 精确 → 当前分支上 `key` 的部分匹配 → `restore-keys`（按写的顺序，各按前缀找）→ **默认分支上把这几步再来一遍**。C 行就是这条顺序的现场：`key ＝ pip-3.11` 时，它在**第 2 步**就以「部分匹配」命中了同分支上较旧的那一份，于是写下的 `restore-keys` 一次都没被用上。D 行则演示了并列时的规则：同一前缀下有多份时，取**创建时间最新**的那一份。

**③ 作用域是单向的，而且它不吃「同一条线」上的假设。**E 行：在 `feat/rag` 上找只建在 `main` 上的缓存 → 命中（当前分支试完就去默认分支）；F 行：在 `main` 上找只建在 `feat/rag` 上的 → **找不到**。官方口径里这句话是「不能恢复子分支或兄弟分支创建的缓存」。所以「我在分支上跑过一次热的构建，合并回主线应该也热」是一个**没有依据的期待**——恰恰相反，主线看不见你那条分支上的那份。另有一条常被忽略的口径：PR 触发时创建的缓存**属于那个合并引用**，只有这个 PR 的重跑能恢复它。

**④ 缓存不可改，所以静态 key 的缓存是一份不再更新的缓存。**官方原话是「你不能改变已有缓存的内容，只能用一个新 key 建一份」。于是：

```text $ python scripts/ci_reader.py --offline
=== 缓存不可改：静态 key 与动态 key ===
  静态 key 第 1 次保存   180,000 KB   ✔ 存下去
  静态 key 第 2 次保存   260,000 KB   ✘ @main 上已经有 pip-cache：内容不可改，只能换一个 key
  静态 key 第 3 次保存   310,000 KB   ✘ @main 上已经有 pip-cache：内容不可改，只能换一个 key
  动态 key 第 1 次保存   180,000 KB   ✔ 存下去
  动态 key 第 2 次保存   260,000 KB   ✔ 存下去

**静态 key 的缓存是一份不再更新的缓存，而它看起来一直命中**：缓存里留的还是 180,000 KB 那一份
动态 key 两次都存下去，代价是两份都占空间（旧的不会被覆盖掉）
```

**静态 key（不含指纹）的缓存，从第一次写下那一刻起就冻住了**：依赖升了三次、`key` 没变，于是后两次保存**被跳过**（不报错，日志里也就是一句说明），而它看起来一直「命中」——命中一份三周前的依赖目录。反过来，把依赖指纹写进 `key` 的写法**每次都存下去**（旧的不会被覆盖掉，各占一份空间）。这一条与 8.1.2 的第三行是同一个机制的两副面孔：`RUN pip install` 那一层不会自己过期，而它的缓存也不会自己更新——**两个「不会」叠在一起，就是你上线了一个旧版本的包的那条路**。

接着是清理的两条规则，它们的**触发条件不同**，所以不能互相替代：

```text $ python scripts/ci_reader.py --offline
=== 清理：7 天没访问，与 10 GB 上限 ===
初始 7 条里活着 5 条；被「7 天没访问」那条规则清掉的是 `pip-3.9-aaaa`（40 天没访问，168 MB）、`wheel-ubuntu-aaaa`（25 天没访问，90 MB）
——这件事**不出现在任何输出里**，它只让下一次构建慢一点
MONOREPO：10 条共 11,059 MB，上限 10,240 MB（10 GiB），而**每一条都在 7 天内被访问过**
  清掉 `gradle`、`cargo-registry` → 剩 10,137 MB
**超限时起作用的是「最后访问从旧到新」**，而不是 7 天那一条——两条规则的触发条件不同
```

**「7 天没访问」那条规则是静默的**：它把两条过期缓存清掉了（258 MB），而这件事不出现在任何输出里——你只会发现某天的构建慢了几分钟。**「超出上限」那条规则是算出来的**：大仓库里十条缓存共 11,059 MB，上限 10 GiB（10,240 MB），于是最久没被访问的两条被清掉——注意这个仓库里**每一条都在 7 天内被访问过**，所以起作用的是「按最后访问从旧往新」这一条，而不是 7 天那一条。两条规则一起管着同一件事：**缓存不是存储，是「最近用过的东西」的近似**。

最后是产物。它与缓存的分界值得背下来：**缓存是跨 run 复用的输入，产物是一次 run 的输出**。

```text $ python scripts/ci_reader.py --offline
=== 产物：`needs` 是「拿得到」的判据 ===
`needs: lint` 来取 test 的产物        ✘ 没有 `needs: test`——它不会等那个 job 跑完，也就取不到
`needs: lint, test` 来取             ✔ 3 个文件下到 ./test-report/
同名重传                              ✘ `test-report` 已经存在：产物不可变，要换一个名字
改一个字节之后下载                     ⚠ 1 个文件与上传时不一样，而这只记成一句警告（run 仍然是绿的）

**四行里两行是「失败」，一行是「警告」**：产物不可变会让第二次上传**真的失败**；
而摘要不符**只报警告**——「产出物被换过」这件事在流水线里不是失败
```

**① `needs` 是「拿得到」的判据，不是顺序偏好。**官方口径：依赖别的 job 产物的 job，必须等那个 job **成功**完成。没写 `needs` 时，产物不是「晚一点到」——是**取不到**，而失败信息说的是「找不到这个产物」，不是「那个 job 还没跑完」。

**② 产物也是不可变的（v4 起）。**同名重传**真的失败**。官方文档里那个「在 job 之间传数据」的例子之所以要给第二个 job 上传一个**新名字**（`homework_pre` → `homework_final`），原因就在这里：v4 里没有「覆盖」这个动作。

**③ 而摘要校验只报警告。**上传时会返回一个 SHA256 摘要，下载时自动比对——不一致时**只在日志里显示一句警告，run 仍然是绿的**。这是这一节最值得记的一条：**「产出物被换过」这件事在流水线里不是失败**。它与 8.1 的「层账与可见账」是同一类纪律——**你需要的不是「有没有校验」，而是「校验不通过时它挡住什么」**。缓存那边也有同构的一条：官方说缓存**内容不签名、也不校验**，低信任触发器（`pull_request_target`、`issue_comment`、`workflow_run`）在默认分支作用域只有**读**权，而它想写时**保存失败、step 与 job 都不失败**（日志里一句 warning）。

> ⚠️ **注意**：官方对缓存还有一句直白的话：**能读缓存的人可以打开一个 PR 读到它**。而缓存里的东西会被后面的流程**执行**（解包出来的文件可能被直接跑起来）——所以「别把密钥写进缓存」不是洁癖，它是一条和 8.1.6 的密钥三档同源的纪律。

## 8.2.4 权限与密钥：一个被投毒的三方 action 能做什么

从这一节起，「谁在跑」这件事从代码层升到了**身份层**。流水线里跑着的每一行代码——包括你不认识的三方 action——权限面与 `GITHUB_TOKEN` 一样大。于是这一节的问题可以问得很具体：**如果今天有一个 action 被投毒，它在这个配置下能干什么**。

```text $ python scripts/ci_reader.py --offline
=== 四、权限面：一个被投毒的三方 action 能做什么 ===
写法                                          改代码  改 workflow   推镜像  读密钥  换云凭证
不写 permissions:（宽松默认）                 ✔      ✔            ✔      ✔      —
不写 permissions:（受控默认）                 —      —            —      ✔      —
permissions: {}                               —      —            —      ✔      —
contents: read ＋ 部署 job 的 id-token: write —      —            —      ✔      ✔
pull_request_target ＋ checkout PR 的头       ✔      ✔            —      ✔      —

**「改 workflow」这一格要单列**：有写权限的下一次运行会拿到更多权限——提权链的入口就在这一格
**受控默认与 `permissions: {}` 的差别**在「只能读代码」与「什么都不能做」之间，而两行里真正救命的是**没有任何一行能推镜像**
**最后一行是唯一「三样同时在手」的一格**：不受信任的代码 ＋ 写 token ＋ 密钥
```

**① 默认值永远站在权限更大的那一边。**什么都不写时，官方给的默认可以是**受控（只读代码）**，也可以是**宽松（读写）**——安全文档把「设成只读」写成了一条建议，这本身就说明默认值不能靠猜。而宽松默认那一行的两格值得单列：**能改代码**与**能改 workflow**。后者的分量在于它不是一次读写，而是一条提权链——**改一次 workflow，下一次运行就能拿到更多权限**（包括把仓库里的密钥读出来）。所以「最小权限」在这里的具体动作是：**把 `GITHUB_TOKEN` 的默认设成只读，再在真正需要的那个 job 上提权**（表里第四行）。

**② `pull_request_target` 是唯一「三样同时在手」的形状。**它跑在 **base 上下文**里：有写 token、有密钥，而它最常见的用法又恰恰是「去 checkout 那个 PR 的头」。官方把这一条写得很硬：这些触发器**必须不显式 checkout 不受信任的代码**。读数里最后那一行就是这个组合的现场——不受信任的代码 ＋ 写 token ＋ 密钥，三样同时在手。而它在配置里长得完全正常：一行 `on: pull_request_target` 加一行 `actions/checkout`。

**③ 「配了密钥」与「这一步拿得到密钥」是两件事。**

```text $ python scripts/ci_reader.py --offline
=== 密钥在哪种事件下可见 ===
push 到本仓           看得见      正常
同仓分支的 PR         看得见      正常
fork 来的 PR          空字符串    401／403，而原因看起来像服务端的问题
pull_request_target   看得见      正常
Dependabot 触发       空字符串    401／403，而原因看起来像服务端的问题

**「配了密钥」与「这一步拿得到密钥」是两件事**，而失败现场指向的是服务端（401／403）
```

官方口径：**除 `GITHUB_TOKEN` 外，fork 触发的工作流拿不到密钥**（Dependabot 事件同理）。而更值得记的是它的**表现方式**：表达式取不到密钥时，返回值是**空字符串**——不是「这个变量不存在」，而是「它是个空值」。于是那一行 `curl -H "Authorization: Bearer $TOKEN"` 会带着空值跑，然后失败在一个看起来与服务端有关的地方（401／403）。**你没配密钥时的现象，与密钥配错了的现象，长得一样。**

**④ OIDC 换掉的是「长期凭证」这件事本身。**

```text $ python scripts/ci_reader.py --offline
=== 长期密钥与 OIDC ===
长期密钥（存进仓库 secret）   存 2 份         有效期 90 天    人（到期前记得换，忘了也不报错）泄漏窗口 最多 90 天
OIDC 换的短期令牌             存 0 份         有效期 300 秒   没有人：每一个 job 自己换一次 泄漏窗口 一次 job（之后它自己过期）

**官方示例里那个 JWT：`exp − iat ＝ 300` 秒**——而它的代价是要按 job 声明 `id-token: write`
```

两栏的差不在「更安全一点」，而在**存几份、活多久、谁负责换**：长期密钥在云厂商与你仓库各存一份、活 90 天、轮换靠人（而忘了换不会报错，只会在某天突然开始 401）；OIDC 一份都不存，官方示例里那个 JWT 的 `exp − iat` 是 **300 秒**，它由每一个 job 自己换一次。它的使用代价只有一个、而且是必要的：**要按 job 声明 `id-token: write`**——那正是「最小权限」这条纪律的形态。

**⑤ 三方 action 的钉法，与第 6 组的镜像钉法是同一件事。**

```text $ python scripts/ci_reader.py --offline
=== 三方 action 的钉法 ===
uses: actions/checkout@v4                   标签可以被移动、也可以被删除——你审过的那一版由别人保管
uses: actions/checkout@8f4b7f8…（40 位 SHA）官方口径：钉到完整 SHA 是目前唯一把 action 当作不可变版本的方式

**与第六组的「镜像钉法」是同一件事**：可变的引用等于把「你审过的那一版」交给别人保管
```

官方口径：**钉到完整 SHA 是目前唯一把 action 当作不可变版本的方式**；挂标签「即使你信任作者也有风险，因为标签可以被移动、也可以被删除」。这与 8.2.6 里「部署清单写 `:latest` 还是 `@sha256:…`」是同一个道理的另一个现场：**可变的引用等于把「你审过的那一版」交给别人保管**。

## 8.2.5 门禁与必需检查：同样是「没跑」，两个相反的结论

这一节是本章最短、也最锋利的一节。它只用两句官方口径，就把「门禁」这件事拆成了七种形状：

```text $ python scripts/ci_reader.py --offline
=== 五、门禁与必需检查：七种形状，报出什么、放不放行 ===
形状                                      报出              看起来    结论
job 跑完并通过                            success           绿        放行
job 级 `if:` 不成立                       success           绿        放行
`continue-on-error: true` 的那一步红了    success           绿        放行
workflow 级 `paths` 过滤挡住              （没有 check run）Pending   挡
提交信息带 `[skip ci]`                    （没有 check run）Pending   挡
矩阵里被 `fail-fast` 取消的兄弟           cancelled         已取消    挡
被 `concurrency` 取消掉的旧 run           cancelled         已取消    挡

真绿 1 ｜ 绿而没验 2 ｜ 停在 Pending（挡） 2 ｜ 跑了却被取消（挡） 2
**同样是「没跑」，写在 `if:` 上把门拆掉（报 Success，即使它是必需检查也不挡合并），写在 `paths:` 上把门焊死（检查停在 Pending，要求它的 PR 被挡）**
——而这两行在配置里的差别只有一个词；七种形状里**真的验过的只有一行**
```

**① 七种形状里，真的验过东西的只有一行。**其余六行各自用不同的方式「没有验」：两种**绿而没验**（`if:` 跳过的 job 报 Success；`continue-on-error` 的那一步红了而外面是绿的）、两种**停在 Pending**（`paths` 过滤与 `[skip ci]`，它们连 check run 都没有）、两种**跑了却被取消**（`fail-fast` 的兄弟、被 `concurrency` 顶掉的旧 run）。

**② 两种「没跑」的后果完全相反。**这是本节的主结论，而它恰好是两句话对着一句话：

| 写在哪儿 | 报出来什么 | 合并 | 机制 |
| --- | --- | --- | --- |
| `jobs.<id>.if:` | **Success** | **放行** | 官方：被跳过的 job 报 Success，**即使它是必需检查也不阻止合并** |
| `on.<event>.paths:` ／ `[skip ci]` | 没有 check run（Pending） | **挡住** | 官方：因路径过滤／分支过滤／提交信息被跳过时，检查停在 Pending，要求它的 PR 被挡 |

**把门拆掉的那一行，和把门焊死的那一行，在配置里只差一个词。**于是「不相关的改动不要跑流水线」这句正确的意图，落成 `paths:` 就是把所有人都堵在门外（包括只改了一份文档的人），落成 `if:` 才是它想说的意思。两条可照用的推论：**必需的检查不能写在带 `paths:` 过滤的工作流里**；**要让某一格「不跑但算过」，就得用 job 级 `if:`**。

**③ `cancelled` 不在合格的三状态里。**官方给必需检查列的合格状态只有 `successful`／`skipped`／`neutral`。所以被 `fail-fast` 取消的矩阵兄弟、被 `concurrency` 顶掉的旧 run，都**不是通过**——而它们在 PR 页面上的样子（「已取消」）非常容易被读成「跑过了、没事」。这一条把它接回了 8.2.2：**取消省的账单是从「结论」里挪出来的**，代价必须在别处认领（重跑一次）。

> 💡 **提示**：本节刻意**不**把「必需检查一个都没配」算进那七行——那是「还没立门」，不是「门有缝」。这两者的处理方式不同：前者要加配置，后者要改**写法**。而写法这一类恰恰更容易被忽略，因为它留下的是一路绿灯。

## 8.2.6 发布与灰度：判据的形态决定金丝雀救不救得了人

最后一节把前五节收在「上线那一刻」。它有三个各自能单独出错的部件，而每一个的默认值都站在**「快」**那一边。

```text $ python scripts/ci_reader.py --offline
=== 六、发布与灰度：钉法、审批、金丝雀 ===
钉法                    回滚回到同一份字节  静默改动能改到几处  改动留在哪里
浮动标签 `latest`       ✘                  1 处                不留在任何地方
版本标签 `v1.2.3`       ✘                  1 处                一次 `docker push`（同一个标签覆盖推）
内容摘要 `@sha256:…`   ✔                  0 处                清单里那串字符（＝一次可审的提交）

**只有摘要能回答「八小时后回滚回到的是不是同一份字节」**——而它也是回滚的前提

审批：自动 0 秒；必需审阅人的环境 240 秒／次（一天 6 次 ＝ 24 分钟等待）
它买到的是「一次发布有一个名字（以及那一格的密钥在批准前拿不到）」；
而**待批准的 run 仍然占着 `concurrency` 组**——后面推的那一次会被排队或取消

金丝雀三档 × 两门判据（全量 1,000 rps、坏版本错误率 3%）：
档位    该档 rps  判据一：攒够 40 个错误  判据一放过的坏请求  判据二：一窗的坏请求
5%      50        26.7s                   1,333               90
25%     250       5.3s                    1,333               450
100%    1,000     1.3s                    1,333               1,800

**判据一（固定样本数）下三档放过的坏请求完全一样**（40 ÷ 3% ＝ 1,333）：
「攒够 N 个错误」与档位无关——**小档位只是把判红拖长，而拖长的这段时间照样在错**
**判据二（固定窗口）下 5% 档就是真的少错 20 倍**（90 vs 1,800）
所以「金丝雀救不救人」不取决于阶梯，取决于判据的形态

回滚：4 分钟等人 ＋ 90 秒生效 ＝ 330 秒
  在 100% 档下回滚期间受影响 330,000 请求，是判红时放过的坏请求（1,333）的 **247.6 倍**
  在 5% 档下同一个回滚只影响 16,500 请求
**回滚比判红贵两个数量级**——而「钉摘要」正是让回滚能做到「一键回到那一份」的前提
```

**① 钉法：八小时之后回滚，回到的是不是同一份字节。**

三种写法里只有内容摘要能回答那个问题。`latest` 每发布一次就动一次；版本标签**也可以被覆盖推**（一次 `docker push` 就把它挪了——而这次挪动**不留在你的仓库里**，所以没有人能在评审里看到它）；只有 `@sha256:…` 是内容寻址的，**它只可能指一份**——要换必须去改清单里那串字符，而那是一次可审的提交。所以「钉摘要」不是洁癖，它是**「一键回到那一份」这个能力的前提**——下一行的回滚账是它的价格。

**② 审批：它买到的不是「更安全」，是「一次发布有一个名字」。**

官方口径：环境密钥在审阅人批准**之前**那一格拿不到——所以审批确实改变权限面。但把它当成安全机制就高估了：它拦不住有意作恶的人，它拦的是**没人看着就上线**这件事。代价是明码标价的 240 秒／次。而它有一个不会出现在任何输出里的连带后果，正好接回 8.2.2：**待批准的 run 仍然占着 `concurrency` 组**——于是你等审批的这几分钟里，后面推的那一次会被排队、甚至被取消。

**③ 灰度的判据：这一节最反直觉的一处。**

放量阶梯（5% → 25% → 100%）本身不救人，**救人或不救人的是「判红」这门判据的形态**：

- **判据是固定样本数**（攒够 40 个错误就判红）时，三档放过的坏请求**完全一样**（1,333）。这不是巧合，是算术：**「攒够 N 个错误」所需的请求数 ＝ N ÷ 真实错误率**，与流量无关。小档位唯一改变的是**判红要多久**（26.7 秒 vs 1.3 秒）——而拖长的这段时间里它照样在错。**用固定样本数当判据时，金丝雀一分钱也省不下来。**
- **判据是固定时间窗**（一个窗口里的真实错误率超阈值）时，小档位就是真的少错：同样的 60 秒里，5% 档放过 90 个坏请求，100% 档放过 1,800 个——**20 倍，正好是档位之比**。这才是「金丝雀」这个词通常想表达的意思。

**④ 而回滚比判红贵两个数量级。**回滚由两段构成：等一个人点（240 秒）与生效（90 秒），而这两段里的流量都是**当前档位的全量**。在 100% 档下，330 秒意味着 330,000 个受影响请求——是判红时放过的坏请求（1,333）的 **247.6 倍**；同一个回滚放在 5% 档下只影响 16,500 个。**所以「回滚多快」比「多快判红」更值钱**——而它由两件事决定：要不要人点，以及**镜像钉没钉摘要**（8.2.6 的第一条）。四节连起来看，这一章的因果链是闭合的：**钉法决定回滚能不能精确，判据决定金丝雀有没有用，两者都不做的话，「灰度发布」只是一句口号。**

**实跑**：以上两条命令与全部用例（172 条，8.3 落地后是 224 条，8.4 落地后是 273 条）都是实跑。**口径**：本树**不连 GitHub、不要密钥、不跑 runner、不装 Docker**——触发与过滤是按官方语法**建模**的（`app/trigger.py` 里的事件与过滤器就是那几个字符串），`needs` 的墙钟是**脚本化的分钟数**（`app/graph.py` 的 `Job.minutes`），缓存的查找顺序是按官方那套顺序**逐条落成尝试记录**的（`caching.restore()` 返回的 `tries` 就是那几步），金丝雀与回滚是纯算术（`app/release.py` 的四个常数）。所以它验证的是**这些机制的性质**，**不构成一次真实的流水线验收**：它量不了真实 runner 的调度与排队、真实仓库的缓存命中率、真实发布里用户的分布。本章引到的官方口径有九处：依赖缓存参考（查找顺序、不可改、作用域、7 天与 10 GiB、低信任触发器的只读与「保存失败但不报错」、缓存不签名）、存储与共享数据（产物的 `needs`、v4 不可变、摘要校验只警告）、控制 job 执行的条件（**被跳过的 job 报 Success**）、跳过工作流运行（**停在 Pending**、五个跳过字符串、`pull_request_target` 不受影响）、分支保护（**合格状态三种**）、安全使用参考（写权限即可读密钥、`pull_request_target`／`workflow_run` 的危险面、钉到完整 SHA）、在 GitHub Actions 里使用密钥（**fork 不传密钥**、取不到时是空字符串）、OIDC（短期令牌、示例里的 `exp − iat`）、受保护分支的必需检查。其余全是本章自己的算术，能手算复核。

### 不能破坏什么

- **不许把「没跑」写成一个结论**：`gate.SHAPES` 的四组分类是这一章的地基（绿而没验 ／ 停在 Pending ／ 被取消）。要合并它们，先给出一个能同时说出「放行」与「挡住」的说法；
- **不许把 `cancelled` 算成成功**：官方列的合格状态只有三种，`gate.Shape.blocks` 就是这条断言的落点；
- **不许只报 `cache_hit`**：`caching.restore()` 的三个字段（`matched`／`rule`／`cache_hit`）必须一起出现在读数里——只报最后一个，B 行就变成了「没有命中」；
- **不许让 `paths` 与 `paths_ignore` 同时生效**：`Workflow.__post_init__` 会直接抛错，这是有意的（官方语法也只认其中一个）；
- **不许把 `matrix` 的格数与墙钟混为一谈**：`matrix_table()` 的 `billable` 与 `wall` 是两列，合成一个就等于把 8.2.2 那一节删掉；
- **不许给「该不该跑」写一个机器判据**：`trigger.SHOULD_RUN` 是**人断言**的那一列。哪天它变成算出来的，这一节的结论就没人负责了；
- **不许把金丝雀的阶梯当成结论**：`release.canary_table()` 的两门判据是并列的两列——只留一列，这一节就退化成「小步放量总是更好」；
- **离线入口不许读 `.env`、不许联网、不许调 GitHub API**：这是「离线当门、真机报数」（3.9 定，3.10 起成为整章验收）在本篇的形态；
- **不改前五棵树**：v3／v4／v5／v6／v7 照旧可装可跑。

## 常见坑

1. **用 `paths:` 做「不相关的改动不要跑」**。它把不相关的 PR 也挡在门外（停在 Pending），正确写法是 job 级 `if:`（8.2.5）。
2. **给必需检查配 `paths:` 过滤**。检查从此停在 Pending，而 PR 卡住的原因看起来像「流水线没跑」——它确实没跑（8.2.5）。
3. **把 `[skip ci]` 当成省时间**。它让检查停在 Pending，于是那个 PR 反而合不了（8.2.1）。
4. **以为「没跑就等于没过」**。job 级跳过报的是 **Success**，而且不挡合并——这是相反的那一半（8.2.5）。
5. **窄白名单漏掉了 `.github/**`**。于是改门的人被关在门外，而流水线全绿（8.2.1）。
6. **以为一次提交只起一个 run**。同仓分支上 `push` 与 `pull_request` 各一个（8.2.1）。
7. **不写 `needs` 图**。最快的那张图（12 分钟）同时是最差的图：`e2e` 跑在 `unit` 之前（8.2.2）。
8. **以为加并发一定省时间**。槽位只能填满关键路径；一条链给多少槽都是 32 分钟（8.2.2）。
9. **把 `fail-fast` 取消的格当成通过**。报的是 `cancelled`，而它不在合格的三状态里（8.2.2、8.2.5）。
10. **`concurrency` 的 `group` 不带 `github.ref`**。于是 `main` 上的运行会把 PR 的运行取消掉（8.2.2）。
11. **拿 `cache-hit` 当「缓存生效了吗」**。`restore-keys` 的前缀命中会真的恢复文件，而它是 `false`（8.2.3）。
12. **以为 `restore-keys` 一定会被用到**。`key` 自己的部分匹配**先于**它（8.2.3）。
13. **以为分支上的热缓存合并回主线也热**。作用域是单向的：默认分支看不到子分支建的缓存（8.2.3）。
14. **用静态 `key`（不含指纹）**。缓存从第一次写下就冻住了，而它看起来一直命中（8.2.3）。
15. **以为缓存会自己更新**。与 8.1.2 的 `RUN` 不自动失效叠在一起，就是你上线旧依赖的那条路（8.2.3）。
16. **把缓存当存储**。7 天没访问会被静默清掉；超限时按最后访问从旧往新清（8.2.3）。
17. **跨 job 取产物不写 `needs`**。失败信息说的是「找不到产物」，不是「那个 job 还没跑完」（8.2.3）。
18. **给产物起同名再传一次**。v4 起产物不可变，同名重传**真的失败**（8.2.3）。
19. **以为产物校验会挡住什么**。摘要不一致只记一句警告，run 仍然是绿的（8.2.3）。
20. **不写 `permissions:`**。默认值可能给你一个能改 workflow 的 token——那就是一条提权链的入口（8.2.4）。
21. **在 fork 的 PR 上期待密钥**。密钥不传给 runner，而取不到时的值是**空字符串**：失败现场指向服务端（8.2.4）。
22. **把 `pull_request_target` 用来跑 PR 的代码**。写 token ＋ 密钥 ＋ 不受信任的代码，三样同时在手（8.2.4）。
23. **把长期云凭证复制进仓库 secret**。它存两份、活 90 天、轮换靠人；OIDC 的那一份只活一次 job（8.2.4）。
24. **三方 action 挂标签。**标签可以被移动、也可以被删除——钉完整 SHA 是唯一不可变的形式（8.2.4、8.2.6）。
25. **部署清单写 `:latest`**。八小时之后你回滚的不是同一份字节（8.2.6）。
26. **把版本标签当成不可变**。同一个标签可以被覆盖推，而这次挪动不留在你的仓库里（8.2.6）。
27. **用固定样本数当灰度判据**。小档位只是把判红拖长，放过的坏请求一样多（8.2.6）。
28. **只算「多快判红」，不算「多快回滚」**。回滚 330 秒在 100% 档下是 33 万个请求，比判红贵 247 倍（8.2.6）。
29. **在等审批的时候继续推**。待批准的 run 仍然占着 `concurrency` 组，后面那次会被顶掉（8.2.6、8.2.2）。

## 面试视角

1. **「你们的 CI 每次要跑多久？」**——不要只报墙钟。报三样：**关键路径**、**并行槽位**、以及**这个图有几处顺序违背**。能说出「扁平图最快而它不算门」是加分项（8.2.2）。
2. **「怎么让流水线省钱？」**——四个各带一句代价的答案：路径过滤（但别拿它挡必需检查）、`matrix` 的 `exclude`（省没有意义的格）、`concurrency` 的取消（省账单，代价是前几次没有结论）、缓存（含指纹的 key，别用静态 key）。**能说出「四者的省法不同」比说出四个名字重要**（8.2.1–8.2.3）。
3. **「为什么 PR 的检查一直是 Pending？」**——这一问几乎必被追问。答：因路径过滤、分支过滤或提交信息被跳过时，检查停在 Pending，而要求它的 PR 会被挡住；对比着说另一句（job 级 `if:` 跳过会报 Success 且不挡合并）（8.2.5）。
4. **「密钥怎么管？」**——三句：**按 job 的最小权限**（`permissions:` 与 `id-token: write`）、**fork 的 PR 拿不到**（而表现是空字符串，失败指向服务端）、**能用 OIDC 就别存长期凭证**（它一份不存、活 300 秒、没人需要轮换）（8.2.4）。
5. **「怎么做灰度发布？」**——先问一句「你的判据是固定样本数还是固定窗口」。是前者，金丝雀救不了你；是后者，5% 档就是真的少错 20 倍。补一句「回滚比判红贵两个数量级」，并说出钉摘要是回滚的前提（8.2.6）。
6. **「本地跑通就够了吗？」**——不够，而且这一篇的五章都在回答这件事：镜像、流水线、前端交互、多租户、线上运维，**每一件的答案都在你的机器外面**（8.1）。

## 本章小结

- **流水线的第一道关口是触发器**：`on:` 决定响应哪些事件，`paths:` / `paths-ignore:` 决定哪些改动**根本不进流水线**——而后者不是「跳过一次检查」，是「这一类改动从此没有再被检查过」（8.2.1）。
- **两种过滤器的性格相反**：白名单**默认拒绝**（漏掉的是名单之外的现在，包括「改门自己」），黑名单**默认放行**（漏掉的是没人想到要挡的未来）。过滤器是默认值的一种，而默认值站在「不做检查」那一边（8.2.1）。
- **同一份提交会起两个 run**（`push` 与 `pull_request`）；fork 的 PR 只有一个。`[skip ci]` 让 run 归零，而**检查停在 Pending**（8.2.1）。
- **`needs` 决定关键路径，槽位只能填满它**：最快的图（扁平、12 分钟）是最差的门（五处顺序违背）；正确的图 21 分钟，从 2 个槽加到 4 个槽**一分钟不省**（8.2.2）。
- **`matrix` 的格数就是账单**；`fail-fast` 取消掉的兄弟报 `cancelled`——**既不是失败，也不是通过**（8.2.2、8.2.5）。
- **`concurrency` 取消省的是账单，排队省的是「哪一次的结论算数」**；`group` 键不带 `github.ref` 时，跨分支会互相取消（8.2.2）。
- **`cache-hit` 只在 exact 匹配时为真**，而 `restore-keys` 的前缀命中**会真的恢复文件**——「恢复了东西」与「命中」是两件事（8.2.3）。
- **官方查找顺序里，`key` 自己的部分匹配先于 `restore-keys`**；作用域是**单向**的（当前分支 ＋ 默认分支，反向不可见）（8.2.3）。
- **缓存不可改**：静态 key 的缓存从第一次写下就冻住了，而它看起来一直命中。两条清理规则的触发条件不同（7 天没访问 vs 超出上限）（8.2.3）。
- **产物与缓存的分界**：`needs` 是「拿得到」的判据；产物 v4 起不可变（同名重传真的失败）；**而摘要不一致只记一句警告**（8.2.3）。
- **权限的默认值站在更大的那一边**：不写 `permissions:` 可能给你一个能改 workflow 的 token，而「改 workflow」就是提权链的入口；正确做法是默认只读＋按 job 提权（8.2.4）。
- **fork 的 PR 拿不到密钥，而表现是空字符串**——「配了密钥」与「这一步拿得到密钥」是两件事（8.2.4）。
- **OIDC 换掉的是「长期凭证」这件事本身**：存 0 份、活 300 秒、没人需要轮换（8.2.4）。
- **「没跑」有两个相反的结论**：job 级 `if:` 跳过 → 报 **Success** 且**放行**；`paths:` 过滤或 `[skip ci]` → **停在 Pending** 且**挡住**。两行在配置里只差一个词（8.2.5）。
- **`cancelled` 不在合格的三状态里**（`successful`／`skipped`／`neutral`）——被取消的格从没给出过结论（8.2.5）。
- **发布的第一步是钉法**：只有内容摘要能回答「八小时后回滚回到的是不是同一份字节」（8.2.6）。
- **审批买到的不是更安全，是「一次发布有一个名字」**；而待批准的 run 仍然占着并发组（8.2.6）。
- **金丝雀救不救人取决于判据的形态**：固定样本数下三档放过的坏请求完全一样（1,333）；固定窗口下 5% 档真的少错 20 倍（8.2.6）。
- **回滚比判红贵 247.6 倍**（330,000 对 1,333 个请求）——所以「回滚多快」比「多快判红」更值钱，而钉摘要是它的前提（8.2.6）。

### 这一篇的五章各守住交付链上的一格

| 章 | 它守的环节 | 没有它会怎样 |
| --- | --- | --- |
| 8.1 | **交付物**：镜像与层账、构建缓存、编排、容器的权限面 | 本地一键全绿，而运到另一台机器上才知道 |
| **8.2** | **交付流程**：触发与过滤、job 图、缓存与产物、流水线权限面、门禁、发布与灰度 | 交付靠手，每一次都不可复现；而「没跑」会被读成「过了」 |
| 8.3 | 前端流式交互：SSE 与对话式 UI | 后端能用，而用户看不到过程 |
| 8.4 | 多租户、配额与计费 | 第二个用户进来时，隔离与账都说不清 |
| 8.5 | 线上运维：SLO、告警、故障演练与容量规划 | 出了事只能等人打电话 |

- **基础**：把 `app/trigger.py` 的 `FILTERS` 里那条第 4 项（宽白名单）补上 `ops/**`，重跑第一组读数。**要求**：说明 `ran` 与 `missed` 各自变成多少，并回答「这一行是补在过滤器里对，还是补在别处对」。
- **基础**：给 `app/graph.py` 加第四个图：`integration` 与 `e2e` 都等 `unit`，而 `lint` 等 `unit`（即把 lint 挪到最后）。**要求**：算出它的关键路径与三个槽位下的墙钟，并解释为什么顺序违背数从 1 变成了 0 而墙钟反而变长了。
