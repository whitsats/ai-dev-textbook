# 8.1 容器化部署：Docker、镜像瘦身与 Compose

## 本章导读

前面七篇 52 章里，知舟的每一层都能在**你这台机器上**被验一次：「跑起来了没有」——循环转没转、检索召没召回、账单对不对得上、门红没红。而这一篇要回答的是另一个问题：**怎么把它交出去。**交付这一层的特别之处在于，它的问题**在本地一键全绿的时候仍然是未知的**——镜像有多重、改一行要重打多久、`docker compose up` 之后应用第一次请求会不会失败、这个容器跑起来之后能做什么。它们的共同点是：答案在一台机器的**外面**（另一台机器、另一个文件系统、另一个时刻）。8.1 是这一篇的第一章，给后面四章立地基：**交付物本身**。

**这一章的第一句话可能反直觉**：**镜像的大小不是你删完文件之后看到的那个大小。**层是只加的，所以在后面一层里删掉前面加进来的东西，只是又加了一层把它遮住——看得见的那一份小了，而镜像一点没小。本章有三样东西各自都要能单独说话：**层账**（每一行一层，相加就是镜像）、**可见账**（最终看得见多少）、**浪费账**（交付了却没人能用上）。同一件事在编排那一侧还有一个对应：`depends_on` 保证的是**顺序**，不是**能用**。与第 6、7 篇一样，本章**不装 Docker、不联网**：六组读数全是剧本算出来的。

## 8.1.1 交付物是一个镜像，而它是一叠只加的层

「把它交出去」这件事的物理形态是一个**镜像**。它由一叠**层**组成，而官方对层说了两句最要紧的话：每一层是**一组文件系统变化**（增、删、改），而每一层**一旦创建就不可变**。

第二句的后果不是「不能改」，是**改的方式只有一种**：再叠一层。于是在后面一层里 `rm` 掉前面加进来的文件，只是给那些文件盖了一张「看不见」的条子——**它们在联合文件系统里不见了，在镜像里还在**。这就是本章开头那句话的可算形式：

```text $ python scripts/deploy_reader.py --offline
=== 一、层账：朴素版那份 Dockerfile 的每一层（基础镜像 python:3.12 1.02 GB）===
 # 指令                                                             这一层   白障
 1 COPY . /app                                               53,042KB    0
 2 RUN pip install -r requirements.txt                      272,000KB    0
 3 RUN apt-get update && apt-get install -y build-essent…   250,000KB    0
 4 RUN rm -rf /root/.cache/pip /var/lib/apt/lists /app/.…         3KB    3
 5 USER app                                                       0KB    0
 6 CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", …         0KB    0
…
层账（每一行相加）：  575,045 KB  ＋ 基础镜像 1,020,000 KB  ＝ 1.60 GB
可见账（最终看得见的）：  468,042 KB  ＋ 基础镜像 1,020,000 KB  ＝ 1.49 GB
**浪费账 = 层账 − 可见账 = 107,003 KB（107 MB）**——交付了、却没人能用上
而白障本身只占 3 KB（ 3 个条目）：
**`rm` 那一层的大小约等于 0，而它遮住的那 107 MB 仍然在盘上**——这就是「删了不变小」的可算形式
```

那六行指令里有几个位置值得逐个看一眼：

- **第 1 行 53,042 KB**：`COPY . /app` 把上下文里**七项**全放进来了——夹着版本历史（26 MB）、测试（1.8 MB）、一份离线语料（9 MB）和一个本地虚拟环境（15 MB）；
- **第 2、3 行 272,000 与 250,000 KB**：装依赖留下的 pip 缓存（62 MB），以及编译工具链与包索引（250 MB）。**工具链只有装依赖那一刻需要，之后全程用不到**；
- **第 4 行 3 KB**：`rm -rf` 那一层。它删掉的三样东西加起来 107,000 KB，而它自己**只占 3 KB**——因为 `rm` 只是加了一层的「白障」。

于是三个数必须一起报：**层账 1.60 GB**（每一行相加，再加基础镜像）、**可见账 1.49 GB**（最终还看得见多少）、**浪费账 107 MB**（二者的差）。只看最后一个数会得到一个错觉：**「我已经删过了」**。真实的说法是：**你删的那一份只影响可见账，而镜像算的是层账。**

> 💡 **提示**：本章每个读数都来自 `zhizhou-v8/scripts/deploy_reader.py --offline`。它**不装 Docker、不联网**：镜像的大小与层数是**文件系统剧本**算出来的（`app/image.py` 里就是那几行「加了什么、删了什么」），构建耗时是**脚本化的每层秒数**。所以它能量的是这些机制的**性质**（层是不是只加的、顺序是不是真的那么贵），**量不了真实镜像的体积与真实机器的构建速度**——这一条写在「不能破坏什么」里。

## 8.1.2 构建缓存：位置决定代价

同一个改动，代价可以差 36 倍——而差的那一部分不在改动本身，在**它在文件里的位置**。官方把这件事讲成了三句话，三句都可以直接变成一条判据：

| 官方口径 | 它意味着什么 |
| --- | --- |
| 一旦某层失效，**它之后的所有层都要重跑**（即使它们本来会打出一样的结果） | 「把变化频繁的往后放」不是风格，是唯一有效的优化 |
| `COPY`/`ADD` 按**文件元数据**算校验和，而 **mtime 不算** | 「碰一下文件」与「改一个字」是两回事 |
| `RUN` 那一层**不会自动失效** | 「上游有没有新版本」不在它的输入里 |

```text $ python scripts/deploy_reader.py --offline
=== 二、构建缓存：同一个改动，写在依赖之前还是之后 ===
改动                                  乱序（COPY . .）             顺序（依赖先、源码后）
改一行源码                                  3 层/ 147s                 1 层/   4s
改依赖清单                                  3 层/ 147s                 3 层/  54s
只碰一下时间戳（内容没变）                          0 层/   0s                 0 层/   0s
什么都没改，隔 90 天再构建一次                      0 层/   0s                 0 层/   0s
把装依赖那一行的文本改一下                          2 层/ 143s                 2 层/  52s
…
**改一行源码：147s → 4s（36 倍）**——改的是同一个字节，位置不同，重打的层数 3 → 1
而**改依赖清单两边一样贵**（147s 与 54s）：它在两种顺序里都在最前面，位置救不了它——这就是「少改依赖」这句话的由来
**只碰一下时间戳：0 层**（官方：mtime 不参与缓存校验和）——「刚才编译过」与「刚才看过一眼」在缓存眼里是两件事
**什么都没改、隔 90 天再构建：0 层**——官方原话：`RUN` 那一层不会自动失效，「上游有没有新版本」不在它的输入里，所以要「永远最新」得给一个显式动作
**改指令文本那一行：从那一层起全部重跑**（143s）——它不是「改了内容」，是「改了这一层的输入」，而它之后全是下游
```

五行的读法各不相同：

**① 改一行源码：147s → 4s。**两种写法的**改动完全一样**（`app/main.py` 里一个字节），重打的层数 3 → 1。差别只有一处：`COPY . /app` 放在装依赖**之前**，于是它一失效，装依赖（48s）与装工具链（95s）全成了下游。而把源码那一层挪到最后，前面两层照样命中。

**② 改依赖清单：两边一样贵（147s 与 54s）。**这是这张表里最值得记住的一行：**位置只能救「放在后面的东西」。**依赖清单在两种顺序里都在最前面（它必须在，装依赖要用它），所以「少改依赖」不是一句习惯建议，它是唯一一条出路——而 8.2 会把它变成一条 CI 纪律：**依赖变更必须单独一次提交**。

**③ 只碰一下时间戳：0 层。**官方明说 mtime 不参与校验和。所以「刚才编译过」与「刚才看过一眼」在这件事上是两回事——你 `touch` 一个文件不会让任何人重打一层。

**④ 什么都没改、隔 90 天再构建：0 层。**这是本章最容易被当成 bug 的一行：`RUN apt-get update && apt-get install -y …`（或 `pip install`）**不会自己去仓库看一眼有没有新版本**。它在缓存眼里永远是命中的，直到它的输入变了。想让它重跑，只有三个显式动作：前面某一层变一变、`--no-cache`（或 `--no-cache-filter` 只失效指定那一段）、或者让它**依赖一个会变的输入**（例如把依赖锁文件的校验和当参数）。

**⑤ 改一行指令的文本：从那一层起全部重跑。**它不属于「内容变了」——它是「这一层的输入变了」，而后面的层全是它的下游。

> ⚠️ **注意**：第 ④ 行与 8.2 的 CI 有一条共同的后果：**「我昨天构建过一次」不等于「它是最新的」**。生产镜像的构建要么带 `--pull`（基础镜像重新取），要么带一个显式的时间/版本输入——否则你会推上去一个包版本很旧的镜像，而它看起来完全正常。

## 8.1.3 瘦身四招：各减多少、代价是什么

四件常见的事各能减掉一部分体积。**它们必须与基线单独比，不能相加**——原因在最后一行：

```text $ python scripts/deploy_reader.py --offline
=== 三、瘦身四招的账（基线 1.60 GB，四招**各与基线单独比、不叠加**）===
招                                                               镜像         省     省%       浪费账
…
四招里最省的是**换基础镜像**（它一次带走 890 MB），最贵的是**多阶段**（它要求你把构建过程拆成两段）；而**只有两招能把「浪费账」归零**：
合并 `RUN`（那两笔开销根本没有产生）与多阶段（没被带走的东西不在最终镜像里）
**四招一起：1.60 GB → 341 MB（省 1.25 GB，78.6%）**——而它不等于四行相加（那些数字动的是同一个数的不同部分）
```

为什么不能相加：四招动的是**同一个数**（层账）的不同部分，两两之间会互相吃掉。最典型的一对是「合并 `RUN`」与「多阶段」——合并 `RUN` 省下的那 92 MB 里，有 62 MB 是 pip 缓存，而多阶段**本来就会把缓存留在 builder 里**。一张把四招加起来等于最终值的表，是一张**每一项都不可信**的表。

四招各自的**代价**，比它们省下的字节更值得记：

- **合并 `RUN`**（`--no-cache-dir`、索引随装随删）：代价是**缓存粒度变粗**——所有依赖变成一层，改一个包就要重装全部。它与 8.1.2 那张表的第一行是**同一个取舍的两端**；
- **`.dockerignore`**：代价最小的一招，也是唯一一招性质不同的——**它减掉的东西从来没有进过镜像**（见 8.1.4）；
- **多阶段构建**：代价是**构建过程要拆成两段**，中间产物要从 `--from` 里点名带走（`COPY --from=build …`）。它是唯一一招能让浪费账归零的（没被带走的东西不在最终镜像里）；
- **换基础镜像**：省得最多（890 MB），而它是唯一一招**会带走能力**的——slim 镜像里没有编译器，所以本项目把它与多阶段配套用：builder 里补上工具链，最终阶段只留产物。

**四招一起**：1.60 GB → 341 MB（78.6%）。这是本章交付的那份 Dockerfile 的量级，而它验证了那条纪律：**优化体积的每一招都要问「它的代价落在谁头上」**——落在构建时间上（合并 `RUN`）、落在构建脚本复杂度上（多阶段）、还是落在运行期能不能编译（slim）。

> 💡 **提示**：别把「浪费账归零」当成目标。**合并 `RUN` 让那两笔开销根本没产生；多阶段让没带走的东西不在最终镜像里**——两者的机制不同，而它们在同一份 Dockerfile 里是可以并存的（本项目就是这么用的）。

## 8.1.4 上下文与传输：什么东西离开了这台机器

构建上下文是**发给构建器的那些文件**。官方那句「指定本地目录时**所有子目录都被包含**」很短，后果很长：**你在项目根目录下 `docker build .` 的那一刻，这个目录里的一切都会离开这台机器**——包括那几样从来没打算进镜像的东西。

```text $ python scripts/deploy_reader.py --offline
=== 四、上下文与传输（上下文里一共 7 项、53,042 KB）===
没有 `.dockerignore`： 53,042 KB 全部发给构建器（7 项）
有 `.dockerignore`： 10,242 KB（4 项）——被挡下来 42,800 KB
  /app/.git       版本历史（含历史提交里的每一份旧 `.env`）
  /app/.venv      本地虚拟环境（目标平台不对，而且它本来会被重建）
  /app/tests      测试代码（不必进运行镜像）
**「没有进最终镜像」与「没有离开这台机器」是两件事**：`.git` 从来不会进镜像，但它会进构建器的缓存
…
改一行源码之后重新推送：5 层里 **1 层变了**（1,300 KB），不是整份 341 MB
  变了的那一层：COPY --from=build /app/app /app/app
  拉一次：全量 13.7s → 只更新那一层 0.05s（按 25 MB/s 算）
——**层是内容寻址的**：前面某层失效（要重跑）不等于它的内容变了（重跑出来一样，指纹就一样，也就不会被重发）
所以「优化缓存」与「层复用」救的是两件事：**前者救构建，后者救传输**
```

第一组数的读法：**「没有进最终镜像」与「没有离开这台机器」是两件事**。`.git` 从来不会出现在镜像里——它不在 `COPY` 的名单上。但它**会**被发给构建器（远端构建器就是另一台机器），并留在那台机器的构建缓存里。一份曾经提交过的 `.env` 就算今天删了，它仍然躺在 `.git` 的历史里；而 `.dockerignore` 是让它在**发出去之前**就被移掉的那一步。

```python

    sent = sum(kb for _, kb in kept)
    total = sum(kb for _, kb in CONTEXT)
    return {
        "total_kb": total,
        "sent_kb": sent,
        "blocked_kb": total - sent,
```

第二组数说的是**传输**：改一行源码之后重新推送，五层里**只有一层变了**（1,300 KB），而不是整份 341 MB。机制是**层是内容寻址的**——层按内容取指纹，两份镜像共有 99% 的层时，推拉只走那一层不同的。

这里有一个容易混淆的地方，值得单独说一句：**「前面某层失效」与「它的内容变了」是两件事**。8.1.2 里 `COPY . /app` 失效会让后面三层都**重跑**（花掉 147 秒），但重跑出来的内容如果和上次一样，指纹就一样，**也就不会被重发**。所以优化缓存与层复用救的是两件事：**前者救构建，后者救传输**。把这两个数混在一起报，会得到一个自相矛盾的结论（「镜像没大多少，所以构建应该也快」）。

## 8.1.5 Compose：起得来 ≠ 起得对

编排这一层只有一句话要记，而它是官方原话：**Compose 在启动时不等到容器「就绪」，只等到它在跑。**

这句话把「依赖」拆成了两件事：容器**在跑**（进程起来了）与它**能用**（自己的初始化做完了，端口上真的有人应答）。中间那段时间里，应用的第一次请求会失败——而**这段差有多长，取决于数据库的初始化**，不取决于你的代码。

```text $ python scripts/deploy_reader.py --offline
=== 五、编排：`depends_on` 的四种等法（数据库第 2s 在跑、第 12s 能应答；应用每 3s 重试一次）===
写法                                                  应用起于   失败      第一次成功
不写 `depends_on`（两个一起起）                                0s    4        12s
`depends_on: db`（默认 `service_started`）                2s    4        14s
`condition: service_healthy`                         15s    0        15s
`condition: service_completed_successfully`（等迁移跑完）     14s    0        14s
…
**不写 `depends_on` 反而最早成（12s）**——因为它把 4 次失败当成正常；写默认的 `service_started` 只保证**容器在跑**，于是应用第 2s 起来、第 14s 才成（比不写还晚 2 秒）
`service_healthy` 等到**第一次报健康**（第 15s，即第 3 个探针），应用第 15s 起来、**失败 0 次**
`service_completed_successfully` 等的是**迁移跑到退出码 0**（第 14s）——它等的不是同一次等待的变体，是另一条链
```

第一张表里最反直觉的一行是第二个：**不写 `depends_on` 反而最早成（12s vs 14s）。**原因不是它更好，而是它**把 4 次失败当成了正常**（应用自带重试）。写默认的 `service_started` 只是把应用的启动往后推了 2 秒——推到「容器在跑」那一刻，而那一刻数据库还不能应答，于是失败次数一次没少，成的时间还晚了 2 秒。

`service_healthy` 与 `service_completed_successfully` 买到的是**零失败**，而它们的机制不同：

- `service_healthy` 等的是 `healthcheck` **第一次报健康**（读数里是第 15 秒，即第 3 个探针）——它等的是「这个服务能用了吗」；
- `service_completed_successfully` 等的是**另一个服务**（建表与建索引的迁移任务）**跑到退出码 0**。它不是同一次等待的变体：应用真正需要的是「表建好了」，而**迁移跑得完这件事本身已经蕴含了数据库可用**（它连的就是那个库）。

而「哪一种更好」这个问题的答案取决于一个前提——**发起方要不要自己扛住那段时间**：

```text $ python scripts/deploy_reader.py --offline
前提换一个，结论就换一个——**应用自己没有重试的时候**：
  不写 `depends_on`（两个一起起）                                0s    1失败  **起不来**
  `depends_on: db`（默认 `service_started`）                2s    1失败  **起不来**
  `condition: service_healthy`                         15s    0失败  15s
  `condition: service_completed_successfully`（等迁移跑完）     14s    0失败  14s
**四种等法的差别不在「快不快」，在「成不成」**：应用不重试时，只有后两种能起来——而它们之所以能起来，是因为它们等的东西**恰好蕴含了「依赖可以用」**（健康检查过、迁移跑完）
```

**四种等法的差别不在「快不快」，在「成不成」。**应用自己不重试时（很多脚手架就是这样：启动时连一次，连不上就退出），只有后两种能起来。所以依赖声明的正确问法不是「它会不会更快」，而是**「如果依赖不在，这一方自己扛不扛得住」**——扛得住，依赖声明只是省几次失败；扛不住，依赖声明就是它唯一的活路。

最后是 `healthcheck` 的四个参数，它们管的是两个不同的时刻：

```text $ python scripts/deploy_reader.py --offline
`healthcheck` 的四个参数（判健康与判不健康是两个时刻）：
 interval retries start_period     判健康   探针      判不健康
…
——`retries` 越大，启动期越不容易误判，而**真出事的时候也就越晚知道**：第一行要 25s 才判不健康，第二行 10s
```

`interval` 与 `start_period` 决定**判健康**要多久（也就是依赖声明要等多久），而 `retries` 与 `start_period` 决定**判不健康**要多久。读数的最后一行是这条取舍的现场：`retries` 越大，启动期越不容易被误判成不健康，而**真出事的时候也就越晚知道**——第一行要 25 秒才判不健康，第二行 10 秒。这是一条**没有免费选项**的取舍，所以取值要写进注释，而不是留给直觉。

## 8.1.6 运行期的最小权限：谁在跑、能写哪里、密钥留在哪几处

前三节讲的是「打出来的东西有多大、有多快」；这一节讲**它跑起来之后能做什么**。三件事，各有一个不会报错的默认值。

**① 不写 `USER`，就是 root 在跑。**官方把它当成一条最佳实践写在 Dockerfile 那一页（「给应用建一个用户，别用 root 跑」）——反过来说，**默认值永远站在权限更大的那一边**。root 的代价不是「它会作恶」，而是**它作恶的时候没法挡**：容器里被打穿的那一段代码，权限面与进程本身一样大。

**② 根文件系统默认可写。**应用真正需要写的其实只有少数几处，而默认它**到处都能写**：

```text $ python scripts/deploy_reader.py --offline
=== 六、运行期权限面：谁在跑、能写哪里、密钥留在哪几处 ===
姿态                                                          可写     显式声明  root
…
三处写入需求：`/tmp`（uvicorn 与多进程启动）与 `/app/.cache`（库的缓存）**是硬的**，`/app/logs` **可以不要**（日志也能只往标准输出走）
前两行都能写、都通——**它们的区别不在「通不通」，在「那一行以谁的身份在写」**（root 写进去的东西，没有任何一层能拦住它写别的地方）
第三行（只读根文件系统、什么都不挂）**三处全写不进去**；第四行把两处真正需要的挂出来之后就够启动了——**只读根文件系统买到的是「它写过哪里」从「没人知道」变成一份清单**
```

前两行一共 3/3 通——**它们的区别不在「通不通」，在「那一行以谁的身份在写」**。只读根文件系统买到的东西因此不是「省了什么」，而是**「它写过哪里」从「没人知道」变成一份清单**：第三行三处全写不进去，第四行把两处真正需要的挂出来之后就够启动了。注意挂出来的是**两处**而需求是三处——`/app/logs` 那处**可以不写**（日志也能只往标准输出走），这正是这份清单的价值：它逼你把「必需」与「顺手」分开。

**③ 密钥不进层。**三种递法各留在了不同的地方，而这一组读数要分的是「**谁看得见**」：

```text $ python scripts/deploy_reader.py --offline
密钥的递法                                           配置    层里    缓存    看见的人
`ENV API_KEY=…`                                  ✔     ✔     ✔       3
`ARG` ＋ `RUN echo $API_KEY > /tmp/k`             —     ✔     ✔       2
`RUN --mount=type=secret,id=key`                 —     —     —       0
```

`ENV` 三处全中：**任何人 pull 下来 `docker inspect` 就能读到**，而后来把那一行删掉，已经构建出来的那一版仍然带着它。`ARG` 少一处（镜像配置里没有），**但值参与缓存校验、并被 `RUN` 写进文件的那一份留在层里**。只有 `--mount=type=secret` 三处都不留——而它的机制值得说清：**它不是一个「更安全的写法」，它是「这件事根本不发生」**（挂在构建容器里的一次临时文件，只在那条指令执行期间存在；官方原话是 secret 的内容**不参与构建缓存的校验**）。

> ⚠️ **注意**：这三档不是「推荐程度」的三级，而是三种**机制**。第三档唯一的使用代价是它要求 BuildKit（现代 Docker 与 CI 默认就是），而它换来的是「**密钥从来没有成为镜像的一部分**」这句话能被机器验证。

### 不能破坏什么

- **不许把浪费账藏起来**：`wasted_kb` 是要报出来的数，不是「优化掉就好」的东西。想改这条，先把「可见账」那一栏补上；
- **不许让四招相加**：`slimming_table()` 的每一行都是**与基线单独比**的。哪一天有人写出一张「四招相加等于最终值」的表，这张表的每一行就都不可信了；
- **不许把「容器在跑」写成「服务可用」**：`Service` 的 `start_s` 与 `ready_s` 是两个字段，合成一个就等于把 8.1.5 整节删掉；
- **不许把 mtime 塞进缓存校验**：`cache_run` 的三个入参里没有「时间」，这是有意的（官方口径）。要加时间，先加一条夹具证明它不改变结果；
- **密钥那一栏不许少报**：`SECRET_RUNGS` 的三个布尔值是「它留在了哪里」的断言。第三档之所以特殊，正是因为三个值同时为假；
- **离线入口不许读 `.env`、不许多 Docker、不联网**：这是「离线当门、真机报数」（3.10 起）在本篇的形态；
- **不改前五棵树**：v3／v4／v5／v6／v7 照旧可装可跑。

## 常见坑

1. **以为 `rm` 能让镜像变小**。它只让**可见账**变小；层账一分不少（读数里 3 KB 的那一层遮住了 107 MB）（8.1.1）。
2. **只看「删完之后」的大小**。三个数必须一起报：层账、可见账、浪费账。少报一个，另一个就会变成一句听起来对的话（8.1.1）。
3. **把 `COPY . .` 放在最前面**。它让后面每一层都成了它的下游：改一行源码重打 3 层／147s，而不是 1 层／4s（8.1.2）。
4. **以为「改了文件」才失效**。指令**文本**改了也会从那一层起全部重跑——失效的判据是「这一层的输入变了」（8.1.2）。
5. **以为 `touch` 会让缓存失效**。官方明说 mtime 不参与校验和（8.1.2）。
6. **以为重新构建会带上新版本**。`RUN` 那一层不会自动失效——「隔 90 天再构建」的读数是 0 层重跑（8.1.2）。
7. **把四招的节省加在一起**。它们动的是同一个数的不同部分，两两互相吃掉（8.1.3）。
8. **为了合并 `RUN` 把依赖和源码合成一层**。合并 `RUN` 的代价是**缓存粒度变粗**——它是一笔清楚的时间换空间的交易，不是白拿（8.1.3）。
9. **用 slim 当构建阶段**。它省得最多，也唯一会带走能力（没有编译器）：builder 里要补工具链，最终阶段才留产物（8.1.3）。
10. **以为 `.git` 不会离开这台机器**。它不会进镜像，但它**会进构建上下文**，也就会进远端构建器的缓存（8.1.4）。
11. **把「要重跑」与「要重发」当成一件事**：前者看输入，后者看内容。重跑出来一样的那一层不会被重发（8.1.4）。
12. **用「镜像没大多少」推断「构建也应该不慢」**。两笔账的主语不同：一个看层的内容，一个看层的输入（8.1.4）。
13. **把 `depends_on` 当成「等它准备好」**。默认的 `service_started` 只保证**容器在跑**（8.1.5）。
14. **以为 `service_started` 至少能少失败几次**。读数里它一次没少，还把成功时刻推后了 2 秒（8.1.5）。
15. **拿「不写 `depends_on` 最早成」当结论**。那 12 秒里**有 4 次失败**，而它只在应用自带重试时成立（8.1.5）。
16. **`healthcheck` 只写 `interval`**。`retries` 与 `start_period` 决定的是**判不健康**那一头——它们决定「真出事的时候要多久才知道」（8.1.5）。
17. **不写 `USER`**。默认是 root；而 root 的代价是「它作恶的时候没法挡」，不是「它会作恶」（8.1.6）。
18. **只读根文件系统一把开下去**。启动会失败在三处写入上——正确做法是先把「必需」与「顺手」分开，再挂出必需的那几处（8.1.6）。
19. **把密钥写进 `ENV`**。它留在镜像配置里，任何人 pull 下来就能读，而删掉那一行对已构建的版本无效（8.1.6）。
20. **把 `ARG` 当成比 `ENV` 安全的替代**。它少一处，但值参与缓存校验、并被写进层——真正干净的是 `--mount=type=secret`（8.1.6）。
21. **把「我本地跑通了」当成「交付验收完了」**。这一篇的六件事**每一件都发生在你的机器外面**；本地能验的只有 1.1 那一层（8.1.7）。
22. **在 CI 里用 `--no-cache` 解决一切**。它确实让那一层重跑，代价是每次都重装全部依赖——正确做法是让**它依赖一个会变的输入**（8.1.2、8.2）。

## 面试视角

1. **「你们镜像多大？为什么这么大？」**——不要只报一个数，报三个：层账、可见账、浪费账。然后**从最大的那一项往下说**（本项目是基础镜像 1.02 GB，换 slim 一次省 890 MB）。这一问真正想看的是你知不知道**层是只加的**。
2. **「改一行代码要重新构建多久？」**——答之前先反问一句「改的是哪一个文件」：源码 4 秒、依赖 147 秒（同一个项目的两种顺序、同一个改动量级）。**「位置决定代价」**这句话能说出来，说明你真的调过缓存。
3. **「镜像怎么瘦身？」**——四招各说一句，并各带一句代价：`--no-cache-dir`（缓存粒度变粗）、`.dockerignore`（减的是根本没进来的东西）、多阶段（构建要拆两段）、slim 基础镜像（带走编译器）。**能说出「四招不能相加」是加分项。**
4. **「`depends_on` 写了为什么还是起不来？」**——因为默认的 `service_started` 只保证容器在跑。答出四种等法各等到哪一刻，并说一句「差别不在快不快，在发起方扛不扛得住」。
5. **「容器安全你们做了什么？」**——三件：非 root（不写 `USER` 就是 root）、只读根文件系统（买到的是「写过哪里」有一份清单）、密钥不进层（`ENV`/`ARG` 都不行，`--mount=type=secret` 才是不留痕的那一档）。
6. **「本地跑通就够了吗？」**——不够，而且这一问几乎必追问。这一篇的六件事——镜像、构建缓存、发布、前端交互、多租户、线上运维——**每一件的答案都在你的机器外面**。

## 本章小结

- **交付物是一个镜像，而它是一叠只加的层**：每一行产生一层，层一旦创建就不可变；删掉的东西只影响**可见账**（8.1.1）。
- 三个数必须一起报：**层账**（每行相加 ＋ 基础镜像）、**可见账**（最终看得见多少）、**浪费账**（交付了却没人能用上，本项目 107 MB）（8.1.1）。
- **构建缓存的三条判据**：逐行比对且**失效后其后全部重跑**；`COPY`/`ADD` 按文件元数据算、**mtime 不算**；`RUN` 那一层**不会自动失效**（8.1.2）。
- **「改一行」的代价由位置决定**：同一行源码，放在依赖之后是 4 秒，放在依赖之前是 147 秒；而**改依赖清单两种顺序一样贵**——位置只能救「放在后面的东西」（8.1.2）。
- **瘦身四招各与基线单独比，不能相加**（它们动的是同一个数的不同部分）。只有两招能让浪费账归零：合并 `RUN`（那两笔开销根本没产生）与多阶段（没带走的不在最终镜像里）（8.1.3）。
- **「没有进最终镜像」与「没有离开这台机器」是两件事**：`.git` 属于后者；`.dockerignore` 是唯一在**发出去之前**动手的一招（8.1.4）。
- **层是内容寻址的**：改一处源码只重发一层（1,300 KB，而不是 341 MB）。「优化缓存」救构建，「层复用」救传输（8.1.4）。
- **`depends_on` 保证顺序，不保证能用**：四种等法（不写／`service_started`／`service_healthy`／`service_completed_successfully`）的差别不在快不快，在**发起方扛不扛得住**（8.1.5）。
- **「起得来」与「起得对」的分界是一次反转**：应用自带重试时，不写 `depends_on` 最早成（12s，代价是 4 次失败）；应用不重试时，只有后两种能起来（8.1.5）。
- **运行期的三个默认值都站在权限大的那一边**：不写 `USER` 就是 root、根文件系统默认可写、密钥默认可以写进 `ENV`（8.1.6）。
- **只读根文件系统买到的是清单，不是体积**：三处写入需求里两处是硬的、一处可以不写——这就是「必需」与「顺手」的分别（8.1.6）。
- **密钥三档是三种机制，不是三个推荐等级**：`ENV` 三处全中、`ARG` 少一处但写进了层、`--mount=type=secret` 三处都不留（8.1.6）。
