# 8.4 多租户、配额与计费

> **本章导读**：8.1 把东西打出来、8.2 让它能被打出来、8.3 让用户在等的时候看得见东西；这一章回答的是最后一个问题——**这块场地要租给几个人用，而每个人用了多少、这笔账算谁的**。前三章的读数都只有一个「用户」：镜像大小、流水线墙钟、首字时长。这一章的第一件事是**把「用户」拆成两层**：认出来的那个人（认证）与他属于谁（租户）；第二件事是把「用」这个字拆成四种量（并发／速率／词元／成本）；第三件事是把同一笔调用在**三个时刻**各说一遍账（预扣、结算、对账）。

> **这一章的第一句话最容易写错**：**「我们做了多租户」不是一个结论，它是一组默认值。** 隔离不是一道门，而是一个默认值——你不选，它就等于「谁都看得到」（8.4.2 那四个落点里最靠前的那一个，漏数就是 3 格里的 3 格）。同样容易写错的是「账单对不上」：它常常不是有人算错，而是**两边的口径不同**（账单按百词元进整、日志按词元记，一个月的差是 5.8%，而对齐口径之后这个差是 0）。本章与第 6、7 篇和 8.1–8.3 一样**不连数据库、不调模型、不跑网关**：隔离是按官方默认值建模的、用量是一份写死的调用表、限流与账是纯算术。

## 8.4.1 三种隔离姿势：判据是「谁能看到谁的什么」

「多租户」这三个字没有技术内容，它只是把一个问题提出来：**这块场地上住着几个人，而他们各自能看到什么。** 三种常见回答，每一种都在回答三件事：隔离强度、运营代价、以及**跨租户统计**。

```text $ python scripts/quota_reader.py --offline
=== 一、三种隔离姿势：判据是「谁能看到谁的什么」===
姿势                              隔离强度                          运营代价                      什么时候合算
行级 `tenant_id`（共享表、共享库）**够用**：漏一处 `where` 就漏一次数据——强度等于「最近一次检查」**最低**：一张表、一份迁移、一次扩容租户数量大而每个租户的数据小；且你**愿意**把「每处查询都带租户」做成一道门
schema-per-tenant（一租户一 schema）**强**：连接串里带 schema，忘了写 `where` 也只在本租户内漏**中**：迁移要逐 schema 跑一遍（租户一多，一次上线几十条 DDL）租户数量中等（几十到几百），且**法规／合同要求「数据分开」**这句话能被指出来
库级（一租户一库／一实例）        **最强**：想跨租户访问就得先跨实例——**它不再是代码问题****最高**：备份、迁移、监控、成本都乘以租户数租户数量少（个位数到几十），且每个租户**愿意为「独占」付钱**
```

第一栏与第二栏的关系是这一节的判据：**强度与代价同向**——行级租户最低成本、最容易漏；库级租户最强、最贵。所以「隔离强度」不是越高越好，而是一次买卖：库级租户买到的是一句话——**想跨租户访问，就得先跨实例**——而这句话的价钱是备份、迁移、监控、成本全部乘以租户数。行业里同一件事常常两边都做：**控制面用库级、数据面用行级**，原因是那句买卖话在两边的价值不同——控制面里一个租户的配置泄漏是事故，数据面里同样的泄漏只是数据；反过来，控制面租户少（几十个）、数据面租户多（几万个），同一句买卖在两边根本不一个价。

第三栏最容易被跳过，而它是唯一会**反过来**推动选择的一栏：**行级租户最方便做统计**（`group by tenant_id` 一句就出来了），库级租户「要么建数仓、要么不统计」。这不是技术缺点，是产品后果——「平台运营能不能一眼看到全局」这件事在选型会上常常没人提，直到某天有人要一份「这个月谁在涨」。

同一件事在向量库里有**四级版本**（数据组织是 Database → Collection → Partition 三层，除了前三层还有第四种：把租户做成 **partition key**）。四级各自有天花板，而**只有 partition key 的天花板不是「数量上限」**，而是「不支持批量写入」：

```text $ python scripts/quota_reader.py --offline
**同一件事在向量库里有四级版本**（数据组织是 Database → Collection → Partition）：
向量库的策略                                  好处                      它的天花板
库级（一租户一 Database）                     隔离最强、检索性能最好    **不活跃的租户白占资源**——租户越多，浪费越大
集合级 · 一集合装所有租户（按字段过滤）       最简单：一次迁移、一处维护**租户一多就撞性能**：过滤是查询之后的事，列表还在长
集合级 · 一租户一集合                         隔离与性能都更好          **受集合数上限**：租户数超过它就上不去
分区级 · 一租户一分区                         隔离与性能的折中          **受分区数上限**：分区比集合便宜，但仍然有顶
分区级 · partition key                        **最可扩展**：集合数固定，租户靠键分散**不支持批量写入**——这条路把「导入」换成了「逐条」

四级策略里**只有 partition key 的天花板不是「数量上限」**，而是「不支持批量写入」：
**它把成本从「存储怎么切」搬到了「数据怎么进」**——这条最容易在架构会上被漏掉。
  ·     8 个租户、批量导入不要 → 库级（一租户一 Database）（少数大户：隔离最强，而运营代价乘上租户数仍然划算）
  ·    60 个租户、批量导入不要 → 集合级 · 一租户一集合（租户不多：隔离换来的是「一次误查只影响一个租户」）
  ·  5000 个租户、批量导入不要 → 分区级 · partition key（租户数超过集合／分区上限，只剩按键分这一条）
  ·  5000 个租户、批量导入要 → 集合级 · 一集合装所有租户（按字段过滤）（要批量导入而租户数又大：partition key 的「不支持批量写入」先把这条路否掉）
```

这行读数值得单说：**它把成本从「存储怎么切」搬到了「数据怎么进」。**「租户多到不能一租户一分区」是容量问题，加了机器就能糊过去；而「不支持批量写入」是流程问题——你的导入脚本要从批量改成逐条，而这件事在压测里看不出来（压测用的是一份小样本）。所以选型会上那个问题不是「租户会多到多少」，而是**「租户会多到多少，并且我们还要不要批量导入」**——两个问题一起问，才有那三条判定。

## 8.4.2 `tenant_id` 落在哪一层：三个探针，四种漏法

姿势选完，落地时第一个问题不是「怎么写」，而是「**谁在说话**」。认证回答的是「你是谁」，租户回答的是「你属于谁」——**后者是从前者查出来的一个属性**，而它必须每一处都用同一个来源。这句话的代价在两处：一是**每处都自己查一遍**（于是某处查漏了、某处查错了、某处查出来的是上一次缓存的），二是**在缓存与后台任务里没有「谁在说话」**（那里没有请求上下文，租户得由调用方显式带进来）。

`tenant_id` 有四种落点，它们按「忘掉它会怎样」排序。三个探针各问一个问题：正常访问、**忘了带**、**带别人的**：

```text $ python scripts/quota_reader.py --offline
=== 二、tenant_id 落在哪一层：三个探针，四种漏法 ===
落点                            探针                  看到什么                      这一格靠什么成立
应用层自己写 `where`            看到                  **看到全部**                  什么事都没发生——代码里没有那一行
应用层自己写 `where`            忘了带                **看到全部**                  漏法就在这里：**漏掉的是「一行」，后果是「一整库」**
应用层自己写 `where`            带别人的              **看到对方的数据**            同样没人拦——`where` 写了，只是写的是别人的值
ORM／仓储层的全局过滤           看到                  看到                          全局过滤在查询构造那一层注入（比如一个默认条件）
ORM／仓储层的全局过滤           忘了带                **看到全部**                  **只有当这一条路走的是 ORM**；裸 SQL 一次就够
ORM／仓储层的全局过滤           带别人的              **看到对方的数据**            过滤注入的是「当前租户」，而查询里写的是别人——先写的赢不了后写的
数据库行策略（RLS）             看到                  看到                          策略 `USING (tenant_id = current_tenant())` 放行本租户那一行
数据库行策略（RLS）             忘了带                **看到本租户的行**            **这是它值钱的地方：漏的是「不带条件」，而策略兜住了**
数据库行策略（RLS）             带别人的              **一行都看不到**              策略把它筛掉了——注意是**空**，不是报错：它是可用的，只是没数据
存储层分区／集合                看到                  看到                          分区键与查询里的租户一致
存储层分区／集合                忘了带                **看到全部（或什么都不返回）**取决于默认：不指定分区即全扫（漏），或强制指定（空）
存储层分区／集合                带别人的              **看到对方的数据**            它只认分区键，不认调用者是谁——**认人不是它的事**

**逐层的漏数**（漏 ＝ 多看到了别人的数据；空与看不到都不算）：
落点                            漏了几格    漏在哪几格
应用层自己写 `where`            3 / 3       看到、忘了带、带别人的
ORM／仓储层的全局过滤           2 / 3       忘了带、带别人的
数据库行策略（RLS）             0 / 3       一个都不漏
存储层分区／集合                2 / 3       忘了带、带别人的

四种落点各自能漏 **3／2／0／2** 格，而**它们漏的方式完全不同**：
  · 应用层：漏的是「那一行 `where`」——**代码里没有它，现场什么都没有**；
  · ORM 层：漏的是「走了一条不经 ORM 的路」——裸 SQL、后台任务、迁移脚本；
  · 行策略：**一个都不漏**，代价是它把「忘了带」变成了「看到本租户的行」、把「带别人的」变成了**空**（可用的，只是没数据）；
  · 存储层：写错了是空、写漏了是漏——**两类完全不同的故障落在同一个参数上**。

**行策略不是「更严的 where」，它是另一个方向**：`where` 漏的是**多看到**，
行策略兜住的是**少带条件**；而它自己的漏法在别处——**表属主默认绕过**：
应用若连的是建表那个账号，策略等于写了一行注释。
```

这张表里最值得看的是**四种落点漏得完全不一样**（3／2／0／2 格），而它们漏的**方式**不同：

- **应用层漏的是「那一行 `where`」**——代码里没有它，现场也什么都没有：日志、监控、错误率全部正常。这是四种里最隐蔽的一种，也是最常见的一种（一个临时加的统计接口就够）。
- **ORM／仓储层漏的是「走了一条不经它的路」**——裸 SQL、后台任务、迁移脚本。它把「每处都写」换成了「一处设定」，代价是**这个约定需要另一条规矩守着**（「不许绕过它」），而那条规矩通常写在文档里、没写在门里。
- **行策略一个都不漏**，而它换来的两种结果不一样：对「忘了带」它给**本租户的行**（等于是兜住了漏），对「带别人的」它给**空**（可用，只是没数据）。所以它是四种里唯一把「漏」换成「错」的——**而「错」是一种更贵的故障**：它长得像一个正常的空结果。
- **存储层把两类故障藏在同一个参数里**：写错了是空（少看到）、写漏了是漏（多看到）。它与行策略的差别在于**它不认调用者是谁**——分区键只认那个键，认人不是它的事。

行策略还有一处必须一起说，否则「我们开了 RLS」这句话会变成一句听起来对的话：**它的默认方向是拒绝**（表上开启了行策略、而这一张表没有任何策略时，没有任何行可见、也不可修改），但它默认**绕过表属主**——除非显式 `FORCE ROW LEVEL SECURITY`；超级用户与带 `BYPASSRLS` 的角色同样绕过；而 `TRUNCATE`、`REFERENCES` 这类整表操作**本来就不受行安全约束**。于是一个很常见的现场是：策略写得很全，而应用连的账号是**建表那个账号**——策略等于一行注释，且它一声不响。

还有一处形状值得记：行策略是**逐表**的（每张表一套策略，缺失即拒绝），所以「列了 20 张表、第 21 张忘了」的后果是**拒绝**（一次可用性事故），而不是泄漏；而应用层的 `where` 恰好相反——忘了写是**泄漏**。两种漏法一个往安全那侧倒、一个往可用那侧倒，**这就是为什么「哪一层」比「写不写」更值得先决定**。

## 8.4.3 配额按什么量：同一批调用，四个答案

「用了多少」这句话有五种量法，而它们的答案可以差两个数量级。下面这一批是租户 A 在 3.5 秒里发出的 12 条调用（长短混合、三条命中缓存），四档上限给的是同一个租户：

```text $ python scripts/quota_reader.py --offline
=== 三、同一批 12 条调用，按四种量各算一遍 ===
量                    这一批用掉        占该档上限  还能再来几条
并发                  7                 87.5%       1 条
请求速率              4                 80.0%       3 条
词元                  11163             55.8%       9 条
成本                  $0.090510         36.2%       21 条

**同一份余量，四个答案**：并发只剩 1 条、速率 3 条、词元 9 条、成本 21 条（四档的取值见 `quota.CAPS`）。
而这一批的用量是：并发峰值 **7**、速率峰值 **4**、词元 **11,163**、成本 **$0.090510**。
```

**四档读的是同一份余量，而它们说「还能再来几条」时说出了 1／3／9／21 四个数。** 差从哪里来？四条量各自的单位不同：并发数「同时在进行中的人」，速率数「每秒几条」，词元数「一共消耗多少」，成本是这四种里唯一**与账单同名**的量。它们不是同一个数的近似——**它们是四台不同的闸机**，而一个租户撞上哪一台，取决于他的用法：一个把长回答排满的租户先撞并发，一个把短问题刷满的租户先撞速率。

换一个角度能看得更清楚：**把两条长回答（6.0 秒与 7.5 秒）压到 2 秒，四个量里只有一个会动。**

```text $ python scripts/quota_reader.py --offline
**四条里只有并发那一档被「时长」影响**——把两条长回答（c02 的 6.0 秒、c06 的 7.5 秒）压到 2 秒，四个量这样变：
量                    原样          压短后        变了没
并发                  7             6             **变了**
请求速率              4             4             一个数没变
```

**词元与时长无关**——同样一段回答，问得快不会让它变便宜。这一格解释了一个很常见的误判：把「回答慢」当成「贵」。慢是并发那一档的事（长回答占着 worker），贵是词元与成本那一档的事；把两件事合成一个数（比如按「会话时长」计费），就会得到一个两边都不准的数。

四种量各自抓住什么、漏掉什么，是这一节的正文：

```text $ python scripts/quota_reader.py --offline
四种量各自抓住什么、漏掉什么（这是这一组的正文）：
量                    它抓住                                  它漏掉
请求数 / 秒           脚本刷接口——**官方那条被绕开的示例里，攻击者正是靠它漏过去的**一次请求里的贵操作；批处理；重试
                      超限怎么答                              429 ＋ `Retry-After`（这一档最常拒人，而它拒得最便宜）
```

## 8.4.4 三种限流算法与超限之后的三句话

量的选择定了之后，接下来是「怎么数」。同一串到达时刻（10 条，**跨过第 10 秒那条窗口边界**）、同一个额度（每 10 秒 5 条），三种算法给出三种答案：

```text $ python scripts/quota_reader.py --offline
=== 四、三种算法，同一串到达（每 10 秒限 5 条）===
到达时刻（秒）            固定窗口    滑动窗口    令牌桶
第 1 条  t=9.60           放行        放行        放行
第 2 条  t=9.70           放行        放行        放行
第 3 条  t=9.80           放行        放行        放行
第 4 条  t=9.90           放行        放行        放行
第 5 条  t=9.95           放行        放行        放行
第 6 条  t=10.10          放行        **拒**      **拒**
第 7 条  t=10.20          放行        **拒**      **拒**
第 8 条  t=10.30          放行        **拒**      **拒**
第 9 条  t=10.40          放行        **拒**      **拒**
第 10 条  t=10.50         放行        **拒**      **拒**
  · 固定窗口：放行 10 / 10 条
  · 滑动窗口：放行 5 / 10 条
  · 令牌桶：放行 5 / 10 条
```

第一行是这一组的全部内容：**固定窗口把 10 条全放行了**——因为前 5 条落在 0–10 秒那个窗口、后 5 条落在 10–20 秒那个窗口，**每一条都在自己的窗口里合规**。这正是「窗口边界」那个经典缺口：0.9 秒里放行了 2 倍额度，而曲线图上每一秒都不超。滑动窗口每次都回头看 10 秒，于是后 5 条全被拒（前 10 秒里已经有 5 条）；令牌桶在这一串到达上与滑动窗口答案相同，而它的差别在别处——**它允许「攒着用」**（空闲一会儿就攒下几个令牌），于是空闲之后的一次突发能穿过去。所以三选一的判据不是「谁更准」，而是**你要不要允许攒着用**：不允许就选滑动窗口，允许就选令牌桶（它的桶容量就是「最多能攒多少」）。

算法之外还有一层分工，它决定了「限谁」：

```text $ python scripts/quota_reader.py --offline

用户          分／时（与人的手速同窗）它拦住「一个人写了个脚本」——**这一类占线上超限的绝大多数**一个人可以有多个 key（前端、脚本、CI），所以它拦不住有意的滥用
```

三层配额**顺序不能反**：租户那一层是合同上写的数（也是 8.4.6 对账要对上的那一栏），它太粗——一个用户刷爆会让整个租户一起被限；用户那一层拦的是「一个人写了个脚本」（线上超限的绝大多数）；key 那一层最先触顶，也最该最先触顶（它拦的是「一个坏掉的循环」）。反过来，只做 key 这一层是不够的：key 会被共享，而共享的 key 让「谁在滥用」变成一个查不出来的问题。

超限之后能说的三句话，各自有各自的代价：

```text $ python scripts/quota_reader.py --offline

答复                      它诚实在哪                              它的代价
429 ＋ `Retry-After`      最诚实的一句：**现在不行，N 秒后再来**（单位是秒）它要调用方**会重试**；不会重试的客户端把它当成一次失败（于是丢了一次真实需求）
排队（把请求挂在队列里）  对并发这一档最合适：**说得出「等多久」**，也不用调用方改代码队列本身要占内存与 worker；**队列没有上限时它就是 8.3 那个背压事故**

```

「没有免费的那一种」是这一节的判据：429 要调用方会重试；排队要占内存与 worker（**队列没有上限时它就是 8.3 那个背压事故**）；降级要有一条能降级的路径，而那条路径的成本通常在模型选型那一章、不在这里。三句话里最诚实的是第一句，最好用的是第二句——**并发这一档特别适合排队**，因为它说得出「等多久」（一条调用平均多久，队列里几条，乘一下就是），而速率那一档说出的 `Retry-After` 只能按平均用量的倒数估。

还有一件比算法更重要的分工：**限流器与负载卸载是两件事。** 限流器按**用户**决策（「如果你能接受用户改变请求节奏，限流器就合适」），负载卸载按**系统整体状态**决策（事故中保住核心请求）。官方那篇里两种都给了具体形态：按请求数的限流器（最要紧的一个，且**测试模式与生产模式用同一条限流**）、**按并发数的限流器**（「同一时刻最多 20 条在进行中」，用来治 CPU 密集型端点的资源争抢，「把它调得比按请求数的那一个更常拒绝是完全合理的」）、以及两种卸载器（给关键方法预留一个比例、按 worker 利用率分级卸载，而**来回放量要慢，否则会 flapping**）。这一节与它们的关系是：**前者是产品策略，后者是事故预案**——配额表里写的是前者，而值班手册里写的是后者。

## 8.4.5 预扣与结算：那笔账在结算前是欠着的

一笔调用的钱要在**三个时刻**各说一遍：调用之前（预扣）、调用之后（结算）、月底（对账）。先看单价从哪来——只有前两段是抄来的，后两段是 6.1 记下的乘法关系算出来的：

```text $ python scripts/quota_reader.py --offline
四段单价（**只有前两段是抄来的**，后两段按 6.1 记下的乘法关系算出来）：
  · `input`：$2.00 ／百万词元
  · `output`：$10.00 ／百万词元
  · `cache_write`：$2.50 ／百万词元
  · `cache_read`：$0.20 ／百万词元
  · 批量通道：**0.5×**（它作用在整单上）
```

**「不重抄」在这里不是洁癖**：抄四个价就有四次抄错的机会，而抄错了这四个数之间**没有任何关系会响**（它们都只是一个数）。而 1.25×／0.10× 这两条关系是「供应商自己写下的乘法关系」，把它们当不变量之后，表里只剩两个数要核。

三笔结算给出这一节的主结论：

```text $ python scripts/quota_reader.py --offline
=== 五、预扣与结算：预扣 $0.012000（按 1,000 进 ＋ 1,000 出估），三笔调用 ===
调用            预扣        实际        差额        这一笔的现场
c1 正常         $0.012000   $0.004200   +0.007800   实际比预扣小——**这是常态**
c2 想多了       $0.012000   $0.017400   -0.005400   输入越过了估算、输出越过了上限——**预扣不够，结算时是欠着的**
c3 上游 500     $0.012000   $0.001800   +0.010200   一个字也没给用户；**而输入那一段上游已经处理过了**

三笔里退了 **$0.018000**、补收 **$0.005400**——而**预扣额三笔完全相同**，差别全在实际那一列上。
预扣按「估算输入 ＋ 最大输出」收，所以正常的调用都是**退**；**只有越过了估算上限的那一笔是欠着的**——这不是 bug，是「按上限估」的必然结果。
第三条最值得单说：上游 500、用户一个字也没拿到，而**输入那一段上游已经处理过了**。
这类账一个月 37 笔时是 **$0.177600**——
它**不会出现在用量账单里**（账单按「送达」计），只会出现在成本里；
所以「用量对了」和「成本对了」是两个不同的结论。
```

**预扣额三笔完全相同，而三笔的差额符号不同。** 预扣按「估算输入 ＋ 最大输出」收，所以正常的调用都是**退**；只有**越过估算上限的那一笔是欠着的**。这不是 bug，是「按上限估」的必然结果——把它当成 bug 去修（比如把预扣调到与实际相等），换来的就是另一类事故：预扣不够而结算失败（用户余额明明够，却因为一笔调用超了预收而被拒）。

第三笔是这一节最值得记的一类：**上游 500、用户一个字也没拿到，而输入那一段上游已经处理过了。** 这类账的特征是**账单按「送达」计、成本按「已生成」计**——两个口径的差就是这一笔，而它不会出现在用量账单里。所以「用量对了」与「成本对了」是两个不同的结论，必须一起报；这也是为什么它要单独做成一行读数（一个月 30 家量级的调用就能让这笔钱变成一条明显的成本线）。

## 8.4.6 账单与日志：同一个月的两种口径

月底对账时，手上有两个数：日志（我们逐笔记的）与账单（上游开的）。同一个月的 1,000 笔调用，两个数并不相等：

```text $ python scripts/quota_reader.py --offline
=== 六、账单与日志：同一个月的两种口径（1000 笔调用）===
口径                                    合计            它记的是什么
日志（精确到词元）                      $10.104051      每一笔按实际词元算——**它是我们这边唯一能逐条复算的数**
账单（按 100 词元进整）                 $10.688620      开票口径：词元先进整再乘单价——**每一笔都被抬高一点点**

两边的差是 **$0.584569**（占日志 5.8%），而**把日志也进整到同一粒度，差是 $0.000000**——
这就是对账的第一步：**先把口径对齐，剩下的差才是需要解释的东西**。
```

差是 5.8%，而**对齐口径之后是 0**——账单按百词元进整（先把它进整到粒度，再乘单价），日志按精确词元记。这就是对账的第一步：**不是去查谁算错，而是先把两边的口径摆出来**。这一步值钱的地方在于它把「差异」变成了两种可能：口径差（改口径就归零）与真差异（那才需要解释）。

对齐之后仍然可能与成本对不上，因为差异还有两处，而它们的性质又不一样：

```text $ python scripts/quota_reader.py --offline

进整粒度：账单按百词元、日志按词元          +$0.584569（占日志 5.8%） **口径对齐就归零**（把日志也进整到同一粒度，差 $0.000000）——对账要比的是同一口径下的两个数，而不是两个数看起来应该一样
上游已算完、我们没收到                      +$0.177600（37 笔）       它**不该**出现在用量账单里：账单按送达计、成本按已生成计——两个数一起看才对得上，只核一个会一直差这一笔
某个旗舰型号的缓存读（官方 0.025×，而全局按 0.10× 算）−$0.270000（30 笔）      把例外抄进单价表（6.1 那一条就是这么写的）：**「按全局倍数算」在八个模型里错一个，而那一个恰好是缓存用量最大的那种**
```

三处差异里**只有一处是钱，另两处是口径**：第一处改口径就归零；第二处（上游已算完、我们没收到）不该出现在用量账单里；第三处是**把例外当通例**——缓存读普遍是输入的 0.10×，而官方给某个型号单独写了 0.025× 的例外（6.1 抄下来的那一条）。把例外按通例算，一个月少收 0.27 美元：**小到没人发现，所以它必须写成单价表上的一行**，而不是留在某个人的记忆里。

这一节最后要收一句总账：**配额、账单、隔离三者共用同一份用量。** 配额在**调用之前**说话（让不让进），账单在**调用之后**说话（花了多少），而隔离决定**这份用量能不能按租户切开**——切不开的用量，账单就只能按人算、不能按租户算。所以 8.4.1 那一节选的不只是「谁能看到什么」，还是**对账能不能按合同上那一栏做**。

**契约**（这一章的模块替谁说话、对谁负责）：

1. `tenant.ISOLATION_MODES` 的四问是**选型判据**：强度、代价、跨租户统计、什么时候合算——四栏缺一栏都会让「越强越好」变成默认结论；
2. `tenant.WHERE_LAYERS` 与 `tenant.ANSWERS` 靠**层名逐字相认**（两张表名字漂一个字，`leak_table()` 会安静地少算一层，夹具专门盯着这一条）；
3. `tenant.Probe.is_leak` 的判据是「多看到了别人的数据」——**空与看不到都不算漏**（两类故障分开报）；
4. `tenant.vector_choice(tenants, bulk)` 的两个输入都是**产品决定**（租户数量级与「要不要批量导入」），不是技术参数；
5. `quota.usage(calls)` 返回四个数，而**四个数来自同一份现场**——任何一处只报其中一个，都要在这里找回来；
6. `quota.CAPS` 的四档是**同一个租户**的上限（可比较性由这一条保证：换成四档不同的口径，「谁先触顶」就没意义了）；
7. `quota.peak_concurrency` 数的是**重叠**（一条 7.5 秒的长回答会横跨七条短调用），而 `quota.peak_rate` 数的是**到达**——两个函数不许合并；
8. `quota.shorten()` 是这一章最干净的一组对照：**它只改时长，而词元与成本一个数都不变**；
9. 三种限流算法共用一组 `ARRIVALS` 参数（每 10 秒 5 条）——**换参数就不是同一个对照**；
10. `quota.REPLIES` 的三句话各自带**代价**：这一栏不许空着（「没有免费的那一种」是这一节的判据）；
11. `billing.PRICE` 里只有 `input`／`output` 是抄的，`cache_write`／`cache_read` **由乘法关系算出**（夹具直接断言这两条等式）；
12. `billing.reserve()` 按**上限估**（估算输入 ＋ 最大输出）——预扣不许「尽量准」，它必须是上界；
13. `billing.bill_call()` 的进整粒度是**开票口径**，不是舍入误差（正文与读数里都要说清这一点，否则下一次有人会把它当 bug 修掉）；
14. `billing.month_calls()` 用固定种子（84）——**这一个月能被重算**，这是「读数要么能复算」那条纪律在随机数上的形态；
15. 一行纪律：**四个模块都不 import 前三段**（`tenant` / `quota` / `billing` 之间只有 `quota` 借了 `billing.PRICE` 来算成本那一档——那一处依赖写在 `usage()` 里）。

**不能破坏什么**（这一章的三块模块一旦跨界，下面这些就会静默变错）：

1. **不许把「认证」与「租户」合成一步**：认出来的是人，租户是查出来的属性——合成一步之后，缓存与后台任务里就没有租户了；
2. **不许把 `is_leak` 放宽成「结果不对就算漏」**：空是另一类故障，它有自己的值班话术（「查不到东西」而不是「看到了别人的东西」）；
3. **不许给行策略加「兜底通配策略」**：默认拒绝是它的价值所在（加一条 `USING (true)` 就把它变回应用层）；
4. **不许把四档上限改成不同口径**（比如并发按分钟、成本按天）——那样「谁先触顶」这个问题就没有答案了；
5. **不许把 `peak_rate` 写成「平均速率」**：峰值与均值在配额这件事上不是同一个数（突发正是它要拦的东西）；
6. **不许把三句答复里的「代价」栏删掉**：删掉之后它变成一句推荐语，而三种都各有各的代价；
7. **不许把 `Retry-After` 写成毫秒**：官方口径是秒（MDN 那个例子里是 `Retry-After: 3600`）；
8. **不许把预扣调成「尽量准」**（见契约 12）：它是上界，宁可多收后退；
9. **不许把进整粒度当成 bug 修掉**（见契约 13）：它是开票口径，而它是对账里能被解释的一件事；
10. **不许把「上游已算完、我们没收到」那一行从差异表里删掉**：它是账单里唯一一处「账单上没有、而你必须付」的钱。

**与别的章的边界**：这一章不重讲报价表（6.1）、不重讲上游的错误分档与退避（6.3）、不重讲背压的队列形态（8.3）、不重讲权限与密钥（8.2）。它讲的是四件事：**谁能看到什么**（隔离）、**能用多少**（配额）、**花了多少**（成本与结算）、**两个数怎么才能对上**（对账）。

## 常见坑

1. **把「我们做了多租户」当成一个结论**——它是一组默认值：隔离、配额、计费三件各有各的默认值，而默认值都是「最省事的那一个」。
2. **在每一处自己查租户**——四处查四次，就有四次机会查漏、查错、或查到上一次缓存的；租户必须有一个来源。
3. **在缓存里存一个租户**——缓存键里不带租户，就等于把第一个租户的数据发给了第二个。
4. **以为行策略「开了就安全」**——要问的是应用连的**哪个账号**（表属主默认绕过）。
5. **把「查不到东西」当成「没有问题」**——行策略与分区键写错时给的是空，而空看起来最像正常。
6. **在迁移脚本里绕过 ORM**——迁移脚本也在访问数据，而它通常没有请求上下文。
7. **按请求数限流，然后被一个批处理接口绕过去**——一次 HTTP 请求里装 999 个操作，按请求数它只是 1。
8. **把「慢」当成「贵」**——慢是并发那一档的事，贵是词元那一档的事；按会话时长计费会把两边都算错。
9. **用固定窗口**——边界处能放行两倍的量，而曲线图上完全正常。
10. **以为令牌桶更准**——它多出来的能力是「允许攒着用」，那是产品决定，不是精度。
11. **三层只做了一层**——只做 key 拦不住有意的滥用（key 会被共享）；只做租户会让一个用户把整个租户拖下水。
12. **给队列不设上限**——那不是一个「宽容」的设置，它是 8.3 那个内存事故换了个地方发生。
13. **`Retry-After` 写成毫秒**——官方单位是秒；写错的后果是客户端要么等 3600 秒、要么立刻重试。
14. **预扣「按实际估」**——预扣必须是上界：它管的是「最贵的那一次会不会透支」，不是「通常花多少」。
15. **把结算失败当成支付失败**——两件事：前者是一次调用超了预收，后者是余额不够；混在一起的报错会让人查错地方。
16. **把上游已计费的那一段当成「没发生」**——它不在用量里，但在成本里；只核用量会一直差这一笔。
17. **把账单与日志的差当成 bug**——先对口径（粒度、送达／已生成、例外），剩下的才是真差异。
18. **把例外按通例算**——缓存读那个 0.025× 的例外少收的钱小到没人发现，所以它必须写在表上。
19. **把「跨租户统计」放到最后想**——它是会反过来推动隔离选型的那一栏（8.4.1）。
20. **以为配额是技术参数**——四档上限是合同、是定价、是销售承诺；技术只是实现它。
21. **在配额表里写「无限」**——写「无限」的那一格通常只是没人算过；而缺任一条上限即脆弱是官方判据。
22. **只报用量不报成本**——「用量对了」与「成本对了」是两个结论（差在按送达计与按已生成计那一处）。

## 面试视角

1. **问**：「你们怎么做多租户隔离的？」**答**：先说判据（谁能看到谁的什么），再说三种姿势各自买到什么、付出什么，最后说**在哪一层落**——并在同一句话里说出那一层的漏法（应用层漏一行 `where`、行策略漏「连的是属主账号」、存储层漏「不带分区键即全扫」）。**加分点**：主动提「跨租户统计」这一栏会反过来推动选型。
2. **问**：「行级安全能替代应用层的租户过滤吗？」**答**：不能互相替代，它们兜的是不同的探针——行策略兜住「忘了带条件」，而它自己默认绕过表属主；应用层兜住「带了别人的」这件事的应用语义（比如「回答里能不能引用别人的文档」）。**加分点**：说出默认拒绝与 `FORCE ROW LEVEL SECURITY`。
3. **问**：「限流按什么限？」**答**：按**会被怎么滥用**来选：刷接口按请求数、长回答按并发、长文本按词元、合同按成本；并说清「按请求数」被批处理绕开的那一个示例。**加分点**：说出限流器与负载卸载的分工（前者按用户、后者按系统整体状态）。
4. **问**：「用户超限了你们怎么答？」**答**：三句话各有代价——429 ＋ `Retry-After`（最诚实，但要调用方会重试）、排队（说得出等多久，但要设上限）、降级（产品上最容易被接受，但要有一条能降级的路径）。**加分点**：说出并发这一档特别适合排队。
5. **问**：「账单和用量对不上，你怎么查？」**答**：第一步是**对齐口径**（粒度、按送达还是按已生成、例外那一档），对齐之后剩下的差才需要解释。**加分点**：说出「上游已算完、我们没收到」这一类只出现在成本里。

## 本章小结

1. **隔离不是一道门，是一个默认值**：不选它，它就等于「谁都看得到」。
2. 三种姿势的**强度与代价同向**——选它不是选安全上限，是选一句买卖话（跨租户访问必须跨实例）值多少钱。
3. **跨租户统计是唯一会反过来推动选型的那一栏**（行级最方便、库级要么建数仓要么不统计）。
4. 向量库四级隔离的天花板各不同，而**只有 partition key 的天花板不是数量**（不支持批量写入）。
5. **认证认人、租户认归属**——租户是从人身上查出来的属性，必须有唯一来源。
6. `tenant_id` 有四个落点，四种漏法：应用层漏一行、ORM 漏一条路、行策略换成「空」、存储层把两类故障藏在一个参数里。
7. 行策略的价值是**默认拒绝**；它的代价是**逐表**，它的漏法是**表属主默认绕过**。
8. 「多看到」与「没看到」是两类故障——**它们的检查与值班话术都不同**。
9. 配额有五种量法，而**它们是四台不同的闸机**：并发／速率／词元／成本各拦一种用法。
10. 同一份余量、四个答案（1／3／9／21）——**只报其中一个就是一句听起来对的话**。
11. **词元与时长无关**：慢不等于贵，快也不等于便宜。
12. 固定窗口在**边界**处放行近两倍的量，而图上完全正常；滑动窗口回头看；令牌桶多出来的是「允许攒着用」。
13. 三层配额顺序是**租户 → 用户 → key**；超限的三句话各有代价，没有免费的那一种。
14. **限流器是产品策略，负载卸载是事故预案**；测试模式与生产模式应当同一条限流。
15. 一笔调用的账有三个时刻：**预扣、结算、对账**。
16. 预扣是**上界**，所以正常调用都是退；越过上限的那一笔在结算前是**欠着的**。
17. **账单按送达计、成本按已生成计**——那一段差不会出现在用量里。
18. **账单不是日志的抄本，是另一种口径**；对账第一步永远是对齐口径。
19. 对不上的三处差异里只有一处是钱，另两处是口径；而**最小的一处最危险**（小到没人发现）。
20. 配额、账单、隔离共用同一份用量——**切不开的用量，账单只能按人算**。

## 练习

1. 把 `tenant.ANSWERS` 改成「行策略也给应用层兜底」（三条 `where` 各加一句 `OR tenant_id IS NULL`），跑夹具，说出它为什么会在 `leak_table()` 上变红——然后说出这条改动在真实系统里对应什么做法。
2. 给 `quota.CALLS` 加两条「同一秒到达的短问题」，重算四个量，说明**哪一档先触顶变了、为什么**。
3. 把 `quota.LIMIT` 从 5 改成 3、`Q.WINDOW` 保持 10，重跑三种限流算法；**固定窗口还能放行几条**？用它写一句「固定窗口比真实额度宽容多少」。
4. 把 `billing.GRAIN` 从 100 改成 1_000，重算 `month_totals()`：差变成多少？再说出「上游换粒度」这件事在合同里该写在哪一句旁边。
5. 给 `billing.discrepancies()` 加第四处差异：「按美元结算与按人民币结算的汇率差」，并把「怎么才算对上」那一栏写完（提示：汇率是一个**时刻**，所以对账要固定用哪一天）。
