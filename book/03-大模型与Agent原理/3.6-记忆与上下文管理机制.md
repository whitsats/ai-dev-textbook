# 3.6 记忆与上下文管理机制

## 本章导读

前五章里，每一次模型调用都是**从零开始**的：你不传历史，它就不知道刚才说过什么。
所谓「记忆」，从头到尾都是你这一侧的工作——把该带的带回去，把不该带的留在库里。
一句话贯穿全章：**记忆不是真相，是索引**；你送进模型的从来不是历史，而是历史的一个投影，
而投影一定是有损的。学完本章，你能算出这次投影省了多少、丢了什么，
能设计三张表把会话与偏好分开存，能让新会话在**历史为空**的情况下接上旧偏好，
并说清什么该进库、什么该过期、什么必须能被删掉。

## 3.6.1 为什么需要记忆：无状态模型的三个症状

先把一件事说直白：**模型没有记忆，也没有会话**。HTTP 端点是无状态的，模型更彻底——
它连「上一次请求」这个概念都没有。你调它十次，它不会因为前九次而改变第十次的行为；
它改变的只有一个途径：**你在这一次的输入里写了什么**。

于是「让 Agent 记住」这件事，落到工程上只有两句话：

```text
写：把值得留下的东西存到你自己的库里
读：下一次调用前，把该带的那一部分装回输入
```

没有记忆的 Agent 会表现得像三种病，症状不同、处方也不同：

| 症状 | 用户看到的样子 | 真实原因 | 处方 |
| --- | --- | --- | --- |
| **失忆** | 每轮都要重新问「文章 id 是多少」 | 历史没被带回请求 | 短期记忆（会话历史） |
| **失约** | 昨天说「发布先给我看草稿」，今天照旧直接发 | 偏好没跨会话留存 | 长期记忆（键值偏好） |
| **失焦** | 会话一长，它开始答非所问、忘掉开头定的规矩 | 上下文太长，注意力被稀释 | 装配策略（清理 / 笔记 / 压缩） |

三种病对应本章的三块内容，顺序也是本章的顺序。**它们不能互相替代**：
把历史拉长不会让偏好跨会话留存，把偏好存起来也不解决上下文过长。

一个必须澄清的误解：**「记忆」不是让模型学会什么**。你没有在训练它。
你写的每一行存储代码，最后都变成某次请求输入里的一段文本——模型在那一次读到它，
然后（在那一刻）按它行动。这正是为什么「记忆里存了什么」是可以用文本检查的，
也是为什么第 3.6.6 节要花一整节讨论写入的三个闸。

> **实测（本章的第一笔账）**：把同一份 24 条的历史分别按「全量」「清理工具结果」「清理＋笔记」
> 装配，用本地编码器数词元，最终上下文是 766 / 524 / 327，累计计费输入是 12,192 / 7,715 / 2,079。
> 三种装配的**任务信息完全一样**——差别只在送进去多少。见 3.6.4。

## 3.6.2 短期与长期：各自存什么、活多久

记忆要分两类，不是分类癖，而是因为**两类东西的失效方式不一样**：
会话历史是「这一段对话说过什么」，它天然有边界（这次会话结束就没了）；
偏好是「这个人长期如此」，它跨会话、按人存、值很短、覆盖而不追加。

| 维度 | 短期记忆（会话） | 长期记忆（偏好与事实） |
| --- | --- | --- |
| 内容 | 每条消息的正文、顺序、工具往返的配对 | 一句话级的偏好或稳定事实 |
| 归属 | 会话 | 用户（跨会话） |
| 生命周期 | 会话活跃期；过期靠归档策略 | **显式 TTL**（本章默认 180 天） |
| 写入时机 | 每一轮都写（追加） | 只在用户说了偏好时写（覆盖） |
| 召回方式 | 按会话按序取，再做装配 | 按用户取全部（几十条），拼进系统提示 |
| 数量增长 | 与对话轮数线性增长 | 与偏好种类数有关，**不随会话数增长** |
| 失败的样子 | 装不下、请求非法 | 记错、记旧、删不掉 |

三条边界要在这里定死，后面几节都靠它们：

1. **会话表必须存正文**。只存摘要指纹的表看起来更安全（脱敏），但它装不出下一次上下文——
   你手里只有一串哈希。3.5 的 `agent_message` 就是这么设计的，本章的迁移把它补回来，
   同时把「能删、有保留期、能按用户清空」作为它的**条件**（第 3.6.8 节）。
2. **长期记忆的键名空间由代码拥有**。模型或规则只能往既定的格子里写（`pref.publish`、
   `pref.tone`……），不能自己发明键——否则记忆表会变成一张随笔墙。
3. **两类记忆不混存**。把偏好塞进会话历史，它就会随会话消失；把历史塞进偏好表，
   它会随会话数无限增长，且每一条都要在每次请求里重发。

表结构就是这个结论的直接翻译。三张表，每张只回答一个问题：

```python
# app/models/agent.py —— 会话与消息两张表（节选；3.6 给它们补上正文，并加了长期记忆表）
class AgentSession(Base):
    __tablename__ = "agent_session"
    id: Mapped[int] = mapped_column(primary_key=True)
    user_id: Mapped[int] = mapped_column(ForeignKey("user.id"), index=True)
    title: Mapped[str] = mapped_column(String(64))
    created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), default=utcnow)
    state: Mapped[str] = mapped_column(String(16), default="active")   # 沿用第 1 篇的「位」风格


class AgentMessage(Base):
    """一次会话里的一条消息。**正文在这里**（3.5 的版本只有指纹，装配不出上下文）。"""

    __tablename__ = "agent_message"
    id: Mapped[int] = mapped_column(primary_key=True)
    session_id: Mapped[int] = mapped_column(ForeignKey("agent_session.id"), index=True)
    role: Mapped[str] = mapped_column(String(16))             # user / assistant / tool
    content: Mapped[str] = mapped_column(Text, default="")
    content_digest: Mapped[str] = mapped_column(String(64))   # 留着：追踪与去重仍按指纹比对
```

第三张表（`agent_memory`）的三个字段是刻意的，缺一个都会出问题：`key` 唯一（同键覆盖，
记忆才不会无限长）、`source` 记下它来自哪一次会话（召回时可追溯）、`expires_at` 允许为空
但**写入方必须显式回答「它能活多久」**。完整定义见 `zhizhou-v3/app/models/agent.py`。

**改表要说清是「加需求」还是「改错」。** 本章的迁移是后者：3.5 那张只存指纹的表不是
「信息更少的安全版本」，它是一个**装不出上下文**的记忆表。给已有表加列要按三步走，
少一步就会在不同的数据库上翻车：

```python
# migrations/versions/0002_agent_memory.py —— 三步加列（节选）
def upgrade() -> None:
    # 第 1 步：加可空列
    op.add_column("agent_message", sa.Column("content", sa.Text(), nullable=True))
    op.add_column("agent_message", sa.Column("tool_call_id", sa.String(64), nullable=True))
    op.add_column("agent_message", sa.Column("created_at", sa.DateTime(timezone=True),
                                             nullable=True))

    # 第 2 步：回填。正文回填不了（老行只有指纹），但时间戳可以按插入顺序给个近似值；
    #          tool_call_id 回填成空串，好让第 3 步在 Postgres 上能把它收紧成 NOT NULL。
    op.execute("UPDATE agent_message SET content = '' WHERE content IS NULL")
    op.execute("UPDATE agent_message SET tool_call_id = '' WHERE tool_call_id IS NULL")
    op.execute("UPDATE agent_message SET created_at = CURRENT_TIMESTAMP WHERE created_at IS NULL")

    # 第 3 步：SQLite 上的收紧留空（见文件头）。Postgres 上就写成：
    #   op.alter_column("agent_message", "content", nullable=False)
    op.create_index("ix_agent_message_session_created", "agent_message",
                    ["session_id", "created_at"])
```

## 3.6.3 上下文窗口溢出的两种症状

上下文装不下的时候，很多人以为问题是「超了上限」。真正的第一个坑在别处：
**你从中间截断历史，会把一段工具往返切成两半。**

服务商对消息序列的形状有要求：每条 `tool` 消息必须是**前面某条 `assistant` 声明过的调用的回应**。
你只保留最近 8 条，历史的第一条很可能就是一条 `tool`——它的声明已经被截掉了。这样的请求发出去，
拿到的是一句 400：

```text
messages with role 'tool' must be a response to a preceding message with tool_calls
```

一样的问题出现在尾巴上：历史停在「assistant 宣布调用、结果还没回来」这一刻（流被中断、
重试边界、或者你正好在这一步截断），留着它，请求同样非法。**校验的是声明与结果配对，
不只是「有没有 tool 消息」。**

于是装配之前必须先合法化。这一步是纯函数，也是最容易漏掉的一步：

```python
# app/agent/memory.py —— 合法化：把装不成合法请求的消息去掉（节选）
def sanitize(messages: Sequence[Message]) -> tuple[list[Message], int]:
    out, dropped = [], 0
    pending: set[str] = set()
    for m in messages:
        if m.role == "assistant":
            pending |= {c.id for c in m.tool_calls}
            out.append(m)
        elif m.is_tool():
            if m.tool_call_id and m.tool_call_id in pending:
                pending.discard(m.tool_call_id)
                out.append(m)
            else:
                dropped += 1                       # 没有对应的调用：丢掉，别把请求弄非法
        elif m.role == "note":
            out.append(Message("user", m.content))
        else:
            out.append(m)
    return out, dropped
```

**实测**（`python -m app.agent.memory`，本地估算）：

- 只留最近 8 条 → 窗口第一条就是 `tool`；装配后第一条变成 `assistant`，丢掉 **11** 条；
- 历史停在「宣布调用」这一步 → 装配后最后一条变成 `user`，丢掉 **1** 条；
- 一段只有结果、没有声明的历史 → 装配后 **0** 条。它就是服务商报 400 的那种请求。

第二种症状更隐蔽，也是本章最重要的一个观念：**装得下，不等于用得上。**
官方在上下文工程那篇里给了它一个名字——**上下文腐烂（context rot）**：上下文里的词元越多，
模型从那一段里准确召回信息的能力**越低**。所以「我上下文还有 100K 空间」不是「我可以随便塞」，
而是「我正在为每一条词元付边际递减的钱」。

两句必须同时记住的话：

1. **装不下**是工程问题：截断、非法请求、丢事实；
2. **装得下但不可用**是效果问题：不是报错，而是开始答偏，而且**没有任何异常会告诉你**。

第二种症状只能靠装配策略解决，而策略的代价必须能算出来——这就是下一节。

## 3.6.4 三套手法的代价对照：清理、笔记、压缩

三套手法常常被混着说。官方在上下文工程那篇里把它们按**作用域**分得很清楚，这个分法比背名字有用：

| 手法 | 作用域 | 动什么 | 不动什么 |
| --- | --- | --- | --- |
| **清理工具结果** | 子轨迹（sub-transcript） | 只替换工具结果的内容块 | 用户消息、助手推理、**调用的记录本身** |
| **压缩** | 整条轨迹（whole-transcript） | 把用户/助手/工具往返/压缩块全部压成摘要 | — |
| **结构化笔记** | 移到窗口之外 | 把值得留的写进外部存储，需要时再取回 | 窗口里已经有的内容 |

这个分法解释了两件实践里最容易做错的事：

- **清理为什么是三种里风险最低的**：工具结果是**可重新获取**的（文件能再读、接口能再请求），
  而且**调用的记录被保留**——模型仍然知道自己调过什么，只是拿不到当时的原始载荷。
  对应到本章实现，就是「只换正文，声明与 id 原地不动」。
- **压缩为什么必须配一张清单**：它是整条轨迹的操作，一旦压过头，丢掉的是**当时看不出重要**的东西。
  官方给的保留清单是：架构决策、未解决的问题、关键事实；丢掉的是冗余内容。
  它还明确说了一句每个工程师都该抄在墙上的话：**有损，且是故意的**（lossy by design）。

把这三套手法在同一份历史上量一遍，账是这样的（`zhizhou-v3/experiments/memory_cost.py`，
本地编码器 `o200k_base`，24 条历史，其中 6 条工具结果，任务依赖 6 条事实）：

```text
策略            最终上下文  累计计费输入  峰值      事实存活  丢了哪几条
A 全量          766         12,192        766       6/6       —
B 清理工具结果  524         7,715         524       4/6       宽限窗口；token_version
C 清理＋笔记    327         2,079         327       3/6       宽限窗口；token_version；幂等键 run-7f3a

相对 A 全量（最终 766／峰值 766）：
  B 清理工具结果：最终 524（-32%）；峰值 524（-32%）
  C 清理＋笔记：最终 327（-57%）；峰值 327（-57%）
```

**这张表里真正该看的是最后一列。** 省下的词元与保住的事实是**反向**的：
B 省 32% 丢两条，C 省 57% 丢三条——而且 C 多丢的那条（幂等键）掉得最冤：
它不在工具结果里，在被逐行截断的**笔记第 50 字之后**。

所以结论不是「C 不好」，而是更硬的一句：

> **装配时的压缩不解决「事实会丢」，它只是把丢掉的时机往后挪。**
> 真正解决它的是**写入时就把事实落到长期记忆**（第 3.6.6 节）——
> 让重要的东西不依赖「装配时还能不能看见」。

三个手法的实现都只改装配那一步，三行代码就能切换——这是它们能被对照的前提：

```python
# experiments/memory_cost.py —— 三套手法只改「送进模型之前的那一段」（节选）
def assembled(policy: str):
    if policy == "A 全量":
        return TURNS
    if policy == "B 清理工具结果":
        return clean_tool_results(TURNS)
    return note_tail(clean_tool_results(TURNS))
```

**真机上再量一遍。** 上面那份 24 条历史是造的，换成一次真的会话（对真实服务商跑三轮问答，
库里 14 条消息、4 条工具结果）之后，同一套代码给出的是这些数：

```text
装配账 full →   2510 词元｜省下   0%｜装进去 14 条｜工具结果换摘要 0 条｜丢弃消息 0 条
装配账 clean→    641 词元｜省下  74%｜装进去 14 条｜工具结果换摘要 2 条｜丢弃消息 0 条
装配账 note →    367 词元｜省下  85%｜装进去  6 条｜工具结果换摘要 2 条｜丢弃消息 9 条
```

真会话里 clean 的效果比造的样本更大（-74% vs -32%），原因不神秘：**真工具结果更长**
（读一篇正文就是两千字符），所以「可重新获取的载荷」占的比例更高。
这正好是清理最适用的一类工作负载——官方那句「你的工作负载的工具使用形态，才是配置的依据」
说的就是这件事。

## 3.6.5 压缩：该保留什么、丢了什么

笔记有两种生成方式，它们的区别不在「谁更聪明」，而在**可复现性**：

| 方式 | 可复现 | 代价 | 什么时候用 |
| --- | --- | --- | --- |
| 逐行截断 | **是**（同一输入永远同一输出） | 丢信息最狠（第 50 字之后全没了） | 默认；出问题时能二分定位 |
| 模型摘要 | 否（换一次采样就换一份笔记） | 一次模型调用 + 不可复现 | 历史很长、必须压到很小时 |

本章的实现同时保留两条路，默认走可复现的那条：

```python
# app/agent/memory.py —— 笔记：summary 为空则逐行截断，否则用模型给的版本（节选）
def note_tail(history: Sequence[Message], keep_recent_turns: int = KEEP_TURNS,
              note_chars: int = NOTE_CHARS, summary: str = "") -> tuple[list[Message], int]:
    if len(history) <= keep_recent_turns:
        return list(history), 0
    head, tail = history[:-keep_recent_turns], list(history[-keep_recent_turns:])
    if summary.strip():
        body = summary.strip()
    else:
        lines = [f"- [{m.role}] {m.content[:note_chars]}" for m in head if not m.is_tool()]
        if not lines:
            return tail, len(head)
        body = "\n".join(lines)
    return [Message("note", f"{NOTE_HEAD}\n{body}")] + tail, len(head)
```

三个工程细节，都是踩过才知道的：

1. **笔记不是合法角色**。模型 API 只认 user / assistant / tool，`note` 是我们发明的。
   装配时折成 `user` 消息，并在文字里写明「这不是新指令，只作背景」——
   否则模型会把笔记里的一句话当成新命令执行。
2. **压缩本身也要记账**。它花的是**现在**的词元，买的是**后面每一轮**的空间；
   峰值口径才看得见它的收益（峰值 = 装配后的那一段，也就是最大的一次请求）。
3. **压缩会失败**。输出被 `max_tokens` 截断时，你拿到的不是「一段短笔记」而是「一段断掉的笔记」，
   而它会被当成正常内容发出去。所以压缩路径必须有回退：**失败就退回逐行截断**，
   宁可多花词元，不要送一段坏摘要进上下文。

还有一条最容易忽略的：**不要只压对话、留下原始工具结果**。上面那个实验里，
C 比 B 省 25 个百分点，但多丢的那条事实来自笔记——如果笔记只保留「说过的」而丢掉「做过的」，
那么「做过的」那一半就没人替你记了。这就是为什么第 3.6.6 节的长期记忆里，
除了用户偏好还有一条 `task.last`：任务痕迹活得短，但它存在。

## 3.6.6 长期记忆的写入：什么时候存、存什么、存多少

长期记忆真正的难点不是召回，而是**写入**。写给多了，记忆表变成噪音；写少了，跨会话还是失约。
三个闸要同时存在，缺一个都会出问题：

| 闸 | 问题 | 本章的做法 |
| --- | --- | --- |
| **抽取** | 从哪一句里抽？ | 只从**用户这一轮的话**里抽，且必须带线索词（「以后」「记住」「别」……） |
| **归并** | 同一件事说了三次怎么办？ | 键名归一 + 同键**覆盖**（`uq_agent_memory_user_key`），不追加 |
| **生命周期** | 它能活多久？ | 写入时**必须**给出 TTL；偏好 180 天，任务痕迹 2 天 |

**抽取为什么不用模型。** 这是本章最值得抄走的一个判断：提示注入污染长期记忆最短的路径，
就是让模型「转述」一句恶意偏好——攻击者不需要攻破你的库，只需要让模型多说一句话。
而在客户端用规则抽取，既能被单测覆盖，也不需要额外一次调用。
代价是**漏抽**：规则看不懂复杂表达。这个代价是划算的，因为记忆是「宁可漏，不要瞎存」：

```python
# app/agent/memory.py —— 抽取：只看用户说的话，且必须带线索词（节选）
@dataclass
class MemoryWriter:
    max_value: int = MAX_VALUE
    max_items: int = MAX_PER_TURN
    ttl_days: int = 180
    attribution_days: int = 2

    def topic_of(self, text: str) -> str | None:
        for key, words in TOPICS:
            if any(w in text for w in words):
                return key
        return None
```

「存多少」也有硬上限，而且三个上限各有理由：**值截到 200 字符**（记忆是索引，不是档案；
长内容属于原文，需要时去取）、**一轮最多 2 条**（一次说十句偏好的用户不存在，
而规则抽出来的十条里有九条是噪音）、**键名来自固定表**（`TOPICS`）。
三个上限一起，保证记忆表的行数与「偏好种类数」同阶，而不是与「会话数 × 轮数」同阶。
这是它能被整个塞进系统提示的前提。

**任务痕迹活得更短**，因为它的性质不同：`task.last` 描述的是一次具体经过（「把 42 号文章发布上线
（等待人工确认）」），2 天之后它就该消失。把两类东西分开的收益是可预期的：
偏好稳定、痕迹短暂，**一次覆盖不会污染另一类**。

## 3.6.7 检索式记忆与向量库的接缝

到这里为止，长期记忆都是「按用户全取回来」。这能撑多久？取决于**条数**：几十条偏好、
每条 200 字符，全塞进系统提示也就是几千词元——比一条工具结果还便宜。
所以本章的答案是：**能全取回来的时候，不要建索引。**

需要换形状的信号有三个，出现任何一个就说明该上检索：

- 记忆条数进入**几千条**量级（用户资料、跨项目事实、企业知识）；
- 记忆里存的是**长文本**（会议纪要、上一次的方案全文），而不是一句话；
- 召回的判据是**语义相关**而非「属于这个人」（「上次讨论过的那类并发问题」）。

这时形状变成：**写入时同时建索引，召回时按语义取 Top-K，把结果当不可信输入拼进上下文**。
但请注意与第 5 篇（RAG）的分界，这条线很容易糊：

| | 本章的键值记忆 | 第 5 篇的检索式记忆 |
| --- | --- | --- |
| 存什么 | 一句话级偏好与事实 | 长文档、切片 |
| 键 | 固定的键名（代码拥有） | 向量 |
| 召回 | 按用户全取 | 相似度 Top-K |
| 更新 | **同键覆盖** | 重新切片与重建索引 |
| 删 | 按键删一行 | 按文档删多行，且要清索引 |
| 失败的样子 | 记错、记旧 | 召回了错的片段、答得头头是道但没依据 |

反模式要单独点出来：**把整段会话原样塞进向量库当记忆**。它有三个必然的后果——
同一件事被反复存成多条（无法覆盖）、越存越像（检索出来的片段彼此重复）、
以及用户说「删掉它」时你找不到该删哪一条。会话历史归会话表，偏好归记忆表，
长文档归第 5 篇的知识库：**三者的更新语义不同，就不该共用一张表。**

## 3.6.8 正确性：过期、冲突与遗忘

记忆会错，而且错的方式很安静。三类问题各要一条对应的机制：

**过期**。TTL 是写入方的责任，不是读取方的宽容。**过期不等于删除**：过期的行留在库里，
只是召回时不返回——它仍然可审计（「上个月它以为用户要什么」），也仍然能被用户手动删掉。
把过期做成物理删除，你会在某次线上事故里再也查不到「当时它为什么这么做」。

**冲突**。同一个键的新旧值冲突，规则是**新值覆盖旧值**；而当记忆与本次对话冲突时，
口径写进系统提示本身：**与本次对话冲突时，以本次为准**。
提示里这句话是必须的——没有它，模型会在「它记得的」和「你刚说的」之间随机选择。

时间比较还有一个具体的坑，值得单独记：

```python
# app/agent/memory.py —— 时间归一化：两种库取回来的时区不一样（节选）
def aware(dt: datetime) -> datetime:
    """把时间统一成带时区的。

    不是强迫症：SQLite 存的是不带时区的字符串，取回来 `tzinfo` 是 `None`，
    和 `datetime.now(timezone.utc)` 一比就抛 `TypeError`。真实库（Postgres）取回来是带时区的。
    **同一个模块要在两种库上跑，就先归一化，再比较。**
    """
    return dt.replace(tzinfo=timezone.utc) if dt.tzinfo is None else dt
```

**遗忘**。用户能看见的记忆必须能被用户删掉——这是「可脱敏」能说出口的前提，
也是第 3.8 节数据保留策略的地基。本章实现到一个键的删除（`forget`），
按用户整表清空与导出留在第 3.8 节。**没有删除权的记忆不是记忆，是负债。**

最后一条：**记忆进提示的位置**。它属于系统提示的前缀（`system` 之后、任务之前），
有两个好处——它是稳定前缀（第 3.1 节的前缀缓存能命中），且与「本轮任务」层次分明。
记忆为空时不要输出空标题：一句话的空模板也会占词元，且在每一轮里重复付费。

```python
# app/services/agent_service.py —— 带记忆的一轮：先装配，再调模型，再回写（节选）
        policy_name = policy or self.memory_policy
        sid = self.open_session(task[:40]) if session_id is None else session_id

        snapshot = self.sessions.history(sid)                   # ①
        assembly = assemble(snapshot, policy=policy_name)
        self.sessions.append(sid, Message("user", task))        # ②

        remembered = self.sessions.recall(self.user_id)          # ③
        history = to_openai(assembly.messages)
        result = self.chat(task, allow_write=allow_write, history=history,
                           max_steps=max_steps, max_tokens=max_tokens, max_seconds=max_seconds,
                           conversation_id=str(sid))

        for m in self._trace_messages(result):                   # ④
            self.sessions.append(sid, m)
        written = self.writer.from_turn(task, session_id=sid)
        for item in written:
            self.sessions.remember(self.user_id, item)
        self.sessions.remember(self.user_id,
                               self.writer.from_task(task, result.reason, session_id=sid))
```

四步各自的理由，都能独立说清：①取**快照**（装配用的是「本轮以前」的历史，否则本轮提问会被算两遍）；
②**写前落库**（用户说过的话先落地，模型那条路炸了也不丢）；③召回长期记忆并拼进系统提示；
④跑完**一次性回写**轨迹与答案（半截轨迹落库会装出非法请求），再抽偏好。

工具往返的落库形状直接决定「能不能重放」，所以它单独成函数：

```python
# app/services/agent_service.py —— 轨迹 → 可回放的消息（节选）
    @staticmethod
    def _trace_messages(r: LoopResult) -> list[Message]:
        """轨迹 → 可回放的消息。**工具往返必须成对**：声明一条、结果一条，id 相同。

        只存结果的写法看起来更干净，但下一次会话装不出合法请求——服务商要求
        `tool` 消息紧跟在声明了同一个 id 的 `assistant` 消息之后。
        """
        out: list[Message] = []
        for e in r.trace.entries:
            if e.final or not e.action:
                continue
            cid = f"call_{e.n}"
            out.append(Message("assistant", e.thought or "", e.tokens,
                               tool_calls=(ToolCall(cid, e.action, e.arg or "{}"),)))
            out.append(Message("tool", e.observation or "", tool_call_id=cid))
        if r.answer:
            out.append(Message("assistant", r.answer))
        return out
```

这里要盯住的不是词元数，而是**第 4 行与最后两行**：新会话的历史是 **0 条**——
它不知道上一个会话里说过任何一句话——但 `pref.publish` 被召回到了，
于是它的回答变成了「必须先提供草稿才能发布」。**跨会话续跑靠的不是上下文更长，而是记忆更准。**

### 不能破坏什么

- **不改第 1 篇的表**：`user` / `article` / `comment` / `favorite` 一字不改；
  本章新增三张表，并只在迁移基线里补一张被引用的 `user`（理由见下）。
- **装配是纯函数**：`assemble` / `sanitize` / `to_openai` 都不写库、不发请求，
  所以它们能在测试里被穷举（半截历史、孤儿结果、空历史、超上限），也能被单独复算。
- **存储可替换**：`session_chat` 只认识 `MemoryStore` 协议；
  换真库（`SqlMemoryStore`）不改装配层一行。3.10 会把默认实现换掉。
- **密钥与库地址不进代码**：数据库地址只从 `APP_DB` 读，迁移文件里没有连接串。
- **删除权不能少**：任何时候都要能删掉一条记忆（`DELETE /memory/{key}`）；
  整表清空与保留期策略属于 3.8，但接口在这里就留好了。
- **看记忆不需要模型凭据**：`GET /session/{id}`、`GET /session/{id}/context`、`DELETE /memory/{key}`
  走一条**不依赖模型配置**的依赖——否则在没配密钥的开发机上，「会话存了些什么」会以一个 500 回答你，
  而那与模型毫无关系。只有 `POST /session/chat` 真的需要凭据。
  （这一条是写完端点后用 `TestClient` 在无密钥环境下逐个打出来的，不是设计出来的。）
- **外键目标必须存在**：`agent_session.user_id` 与 `agent_memory.user_id` 指向 `user` 表。
  SQLite 默认不强制外键，**它不存在也照样建表成功**；Postgres 会当场报
  `relation "user" does not exist`。所以基线迁移把 `user` 一起建出来——
  **只在 SQLite 上跑过的迁移不算跑过。**

## 常见坑

1. **只存指纹不存正文**。3.5 的 `agent_message` 就是这么设计的，理由是脱敏。
   结果是记忆装不出来——你手里只有哈希。**脱敏的正确做法是「能删、有保留期、按用户隔离」，
   不是「不存」。**
2. **把工具结果和它的声明分开存**。下一次会话装不出合法请求，服务商回 400
   （`tool` 消息必须紧跟声明了同一个 id 的 `assistant` 消息）。
   官方那篇也点明了：清理要**保留调用的记录**，只替换载荷。
3. **从中间截断历史就发出去**。窗口第一条是 `tool`、或者最后一条 assistant 宣布了没有结果的调用，
   两种半截都会让整个请求作废——**重试也一样**。
4. **`note` 当成合法角色发出去**。服务商只认 user / assistant / tool；
   要折成 `user` 并在文字里写明「不是新指令」。
5. **降幅算错**。拿「截断后的窗口」和「原始全量」比，把截断的效果算成清理的功劳，
   得出的降幅是假的。基线要取**同一窗口下的全量装配**（`Assembly.baseline_tokens` 就是这么定义的）。
6. **压缩不记账**。压缩花的是当前的词元，收益在后面每一轮里——只按「最终上下文」算，
   你会得出「压缩很贵」的错误结论；峰值口径才看得见它。
7. **用模型抽取长期记忆**。提示注入污染记忆的最短路径就是让模型转述一句恶意偏好；
   规则抽取能单测，模型抽取不能。
8. **记忆无限追加**。同键覆盖是记忆表能撑住的唯一原因；只追加的表最后会长成一张事实库，
   每次请求都要重发一遍。
9. **时区不归一就比大小**。SQLite 取回来是 naive，Postgres 取回来是 aware，
   混着比直接抛 `TypeError`——同一个模块要在两种库上跑，就先归一化。
10. **过期做成物理删除**。你会在事故复盘时最需要它的那一刻发现它没了。
11. **只写不预习**（写入路径没有测试）。记忆是**跨会话**才生效的，
    单会话测试永远发现不了「键名归一没生效」这类问题——那要两个会话才能暴露。
12. **把「查不到会话」当成「这段会话还没说话」**。`history()` 返回空数组看起来无害，
    但它把一个拼错的 id 变成了一段安静的空历史（端点声称的 404 永远不会发生）。
    两者必须分开：**空历史是合法的首轮，不存在的会话是 bug**（与第 1 篇「区分空结果与失败」同源）。

## 面试视角

本章在面试里被问到的形态通常是「Agent 怎么做记忆」。答得好不好，区别在**你有没有把三类问题分开**：

- **问「记忆怎么实现」**：先说两类（短期会话历史 / 长期偏好），再说装配三策略
  （清理工具结果 / 压缩 / 结构化笔记），最后给出它们的**作用域**
  （子轨迹 / 整条轨迹 / 窗口之外）——这个分法是官方的口径，比背名字更抗压。
- **问「上下文太长怎么办」**：先区分两种症状（装不下 / 装得下但不可用），
  再给出你**量过的数**（哪一份历史、省了多少、丢了什么）。说出「清理工具结果最安全，
  因为结果可重新获取且调用记录保留」这一句，基本可以停在这里。
- **问「怎么保证记忆不丢」**：反转一下——**装配时的压缩不解决丢失，写入时才解决**。
  然后给出你的三个闸（抽取 / 归并 / 生命周期）与上限（值多长、一轮几条、键名谁定）。
- **问「记忆和 RAG 有什么区别」**：键值 vs 向量（固定的键名 vs 相似度），
  更新语义（同键覆盖 vs 重建索引），删除成本（一行 vs 一批加索引）——
  最后给一句分界：**能全取回来的时候，不要建索引。**
- **问「记忆会不会被投毒」**：从写入路径答（只从用户的话抽、模型不参与），
  再说出代价（漏抽）与补偿（任务痕迹 + 用户可删）。

## 本章小结

1. 模型无状态：**记忆 = 写库 + 装配**，「带回去」而不是「教会它」。
2. 记忆分两类，因为失效方式不同：会话历史（短期、追加、按会话）与偏好（长期、覆盖、按用户）。
3. 会话表**必须存正文**。脱敏的正确做法是能删、有保留期、按用户隔离。
4. 上下文溢出有两种症状：装不下（截断切坏工具往返 → 400）与装得下但不可用（上下文腐烂）。
5. 三套手法按作用域分开：清理（子轨迹，保留调用记录）、压缩（整条轨迹，有损且故意）、
   结构化笔记（窗口之外）。
6. 装配前必须**合法化**：孤儿工具结果、半截声明都要去掉，否则请求整次作废。
7. 账有四笔：基线、装进去多少、省下多少、**丢掉了什么**。降幅要用同一窗口的基线算。
8. 长期记忆靠三个闸：抽取（只用用户的话 + 线索词）、归并（同键覆盖）、生命周期（显式 TTL）。
9. 过期不是删除；冲突以本次对话为准；**用户必须能删**。
10. 跨会话续跑的验证点是「新会话历史为 0，但回答用上了旧偏好」——
    这正是本章真机跑通的那一条。

## 练习

- **基础**：给 `MemoryWriter.TOPICS` 加一个话题（例如「长度」`pref.length` 与线索词「以后」「记住」），
  并为它补两条用例：一条能抽出来、一条因为缺线索词而**不该**被抽出来。
  然后回答：新增这个话题会不会让偏好多到影响系统提示的每轮开销？
- **进阶**：把 `note_chars` 从 50 调到 12 再调到 200，用 `experiments/memory_cost.py`
  的三份答案各跑一次，画出「省下的词元」与「事实存活率」两条曲线，
  找出你这台机器上代价与信息的拐点，并解释为什么这个拐点不能直接搬到别的任务上。
- **挑战**：实现 `compress` 的**可校验版本**：让模型压缩时按固定清单输出
  （架构决策 / 未解问题 / 关键事实 / 涉及的文件），压缩完再让一个纯函数检查这四栏是否齐全，
  不齐就退回逐行截断；然后用同一份历史跑十次，统计「多少次退回」与「退回时少花了多少词元」。
  结论要能回答：**不可复现的那一步，该怎么被验证。**
