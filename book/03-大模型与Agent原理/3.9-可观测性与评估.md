# 3.9 可观测性与评估

## 本章导读

前八章把知舟从「一次模型调用」长成了「有规划、有工具、有记忆、会分工、带护栏的代理」。
它们每一章都在回答「它能不能做这件事」，没有一章回答**「它做得怎么样、比上次好了还是差了」**。

这正是本章要补的两件事，而它们共用同一批数据：

- **可观测性**回答「刚才那次为什么是这样」——从一个已经发生的运行里推断内部状态，
  包括你没预想过要问的那些问题；
- **评估**回答「改了之后是变好还是变坏」——把「好不好」变成一批固定的题、
  可重复的跑法，和一个能拦住退步的门。

这两件事在 Agent 上比在普通服务上更难，原因很具体：**同一次输入不保证同一条轨迹**。
第 3.3 节给过那条实测：同一句提问跑四次，出来两条不同的轨迹（一条读正文，一条直接检索）。
一次成功不是通过，一次失败也不一定是退步——所以本章下半部分有一半篇幅在讲**试验与统计**，
而不是在讲「怎么写一个测试」。

本章的交付物是知舟的第九段增量：`app/agent/trace.py`（span 树与四类指标）、
`tests/agent/eval_cases.jsonl`（6 条用例、15 次试验的评测集）、
`experiments/eval_run.py`（跑法与回归门）与 `GET /api/v1/agent/metrics`（只读指标端点）。
它们的验收标准写在 [`PROJECT.md`](PROJECT.md)：**一次改动能报出指标变化，
且 CI 拦得住回归。**

## 学习目标

读完本章，你应该能够：

1. 说清可观测性与「多打日志」的分界，以及三支柱各自回答哪一类问题；
2. 把四类黄金信号（延迟 / 流量 / 错误 / 饱和度）映射到 Agent 的具体读数上；
3. 按 OpenTelemetry 的 GenAI 语义约定记录 span：命名、属性、一次逻辑操作一棵 span、
   内容捕获默认关闭；
4. 写出「成功率 / 平均步数 / 每任务成本 / 失败分布」四类指标，并知道为什么
   失败分布必须是**有限档**；
5. 设计一份能当门用的评测集：判产出与终态、不判路径，能力题与回归题分开；
6. 用 pass@k 与 pass^k 区分「一次能做」与「每次都做得到」，并知道什么规模的题量
   才够看出差别；
7. 让指标与评测接进提交路径，**漏跑一次都提交不了**。

## 3.9.1 可观测性：能回答没预想过的问题

先划一条界。**测试回答的是你已经想到的问题**：你写下断言，跑一遍，绿了。
**可观测性回答的是你没想到的问题**：用户说「昨晚有一单特别慢」，而你没有一条以「这单为什么慢」
为名的测试——你只能从已经记录下来的东西里把它推出来。

工程上有一条判据：**故障时能回答的问题，必须在这个系统正常运行时就已经记下了。**
没记下的东西，事后补不出来。所以可观测性的建设时机永远在故障之前，
而它的产出不是「更多的日志」，是**一组能被独立查询的信号**。

业界把信号分成三类，常说的三支柱：

| 支柱 | 形状 | 回答什么 | 代价 |
| --- | --- | --- | --- |
| 指标（Metrics） | 数字，按时间聚合 | **多少 / 多快 / 多贵**：「过去一小时成功率 93%，p95 延迟 2.7 秒」 | 极低，可长期保存 |
| 日志（Logs） | 离散事件，带字段 | **这一件发生了什么**：「这次调用返回了 429，重试 2 次后成功」 | 中等，会膨胀 |
| 追踪（Traces） | 一次请求的完整路径 | **它走到了哪里、卡在哪一步**：「读了正文 → 查了标签 → 写草稿被拒」 | 较高，通常要采样 |

三者不是三选一：指标告诉你**有事发生了**，追踪告诉你**哪一步**，日志告诉你**为什么**。
只做指标，你知道成功率掉了却查不出原因；只做日志，你能查到原因却不知道掉得有多严重、
从哪一刻开始。所以本章的交付物也正好是三样都落在同一份数据上。

还有一对分类要记住，它们对应两种完全不同的做法：

- **黑盒监控**：只看外部可观察的行为——请求进、响应出、耗时多少、状态码是什么。
  它不关心内部结构，因此**换实现不影响它**；
- **白盒监控**：观察系统内部的状态——队列长度、连接池占用、预算剩余、缓存命中率。
  它能看到症状的来源，但会和实现绑在一起。

Agent 的可观测性天然是白盒偏多的：**「模型想了什么」这个字段在系统外部根本不存在**，
要观测它就必须在循环内部留钩子。这也是本章的实现选择（`on_call` / `on_tool` 两个回调）
而不是「在外面包一层 HTTP 中间件」的原因：中间件拿得到「这次请求 8 秒」，
拿不到「这 8 秒里有 5 次模型调用、其中第 3 次要求了工具」。

最后一个分野是**观测与审计的区别**，两者容易混：审计回答「谁在什么时候做了什么决定，
依据是什么」（第 3.8 节），它的字段是定好的、为了追责与合规；观测回答「系统现在处于什么状态」，
它的字段会随着你新想到的问题而增加。审计记录**不能用来做指标**
（那是另一个系统的写入路径），而观测数据**不能替审计**（它的保留期通常短得多）。

## 3.9.2 四类黄金信号在 Agent 上长什么样

Google SRE 那本书里给了四类黄金信号，它们对任何请求—响应系统都成立。搬到 Agent 上，
每一个都要重新问一次「它的分子分母是什么」：

| 黄金信号 | 传统服务里的样子 | Agent 上的样子 | 本章的读数在哪 |
| --- | --- | --- | --- |
| 延迟（Latency） | 请求耗时，分成功与失败两组 | 一次**任务**的墙钟（不是一次模型调用的耗时） | `latency_ms.p50 / p95` |
| 流量（Traffic） | QPS、并发连接数 | 单位时间的任务数、**模型调用次数**、工具调用次数 | `runs`、`calls`、`by_tool` |
| 错误（Errors） | 5xx 率、超时率 | **失败分布**（哪一档失败），而不只是一个错误率 | `failure_distribution` |
| 饱和度（Saturation） | CPU、内存、队列水位 | **预算**：步数、词元、墙钟三条上限用掉了多少 | `steps.avg / max`、`tokens` |

三处 Agent 特有的坑，都在上表里藏着：

**延迟要分成功与失败两组看。** 把失败的请求混进延迟分位，会得到一张自相矛盾的表——
**失败往往是「快」的**（模型调用直接报错、连接断开、被护栏拒绝），于是失败率一升，
延迟分位反而「变好」。第 3.9.4 节那张真机表里就是这个形状：p50 被一批中断的试验拉到接近 0。

**流量在 Agent 上不等于任务数。** 一个任务可能调 1 次模型，也可能调 12 次。
按任务数扩容会严重低估负载，真正的乘数是「平均步数 × 每次请求的词元」。
这也是为什么本章的指标里有 `calls.total` 与 `steps.avg` 这两个看似重复的数：前者是成本，
后者是延迟。

**饱和度在 Agent 上是「预算」，而预算用满不是错误。** CPU 打满是坏事，
步数用满是**设计好的收口**：第 3.3 节的五类终止条件里，「预算耗尽 → 收口」是正常工作方式之一，
它交付的是一个打折的答案，不是一次失败。所以本章把它单独归成一档（`预算收口`），
而不是扔进错误率里——把「按预算收口」算成错误，会让一个正常的系统看起来一直在出错。

### GenAI 的四件新东西

上面那四条是通用的。GenAI 的应用还额外带来四样东西，它们在传统 APM 里**根本没有对应的位置**：

1. **模型调用**：它是一次跨进程的、非幂等的、按次计费的调用，而它的耗时波动可以从
   0.3 秒到 20 秒（第 3.9.7 节的真机表里 p95 是 26.9 秒）；
2. **工具执行**：它是应用自己的函数，但它的**参数由模型给出**——所以「工具失败」
   既可能是代码错，也可能是模型把参数编错了；
3. **词元用量**：它是唯一的计费单位，而且**输入与输出是两个价**；
4. **内容捕获**：提示、模型输出、工具参数与结果都是「内容」，
   它们既是最有诊断价值的字段，也是最容易带出敏感数据的字段。

行业内把这些字段的统一口径交给了 OpenTelemetry 的 **GenAI 语义约定**：
属性统一用 `gen_ai.*` 前缀，操作名用一组枚举值，span 的命名与层级都有规定。
本章的所有字段名都取自它，因此换一个后端（第 7 篇 7.4 节的选择）不需要改业务代码。

一处必须写清的现状：**这套语义约定的状态是 Development**，不是 Stable。
字段会有增删，升级前要看一遍变更说明——这和第 1 篇里那些 Stable 的规范不是一回事。
把它们当「稳定接口」写死在一堆地方，是这一节最容易犯的错。

## 3.9.3 追踪：一次逻辑操作一棵 span

三个词先定义清楚，它们在日常对话里经常被混用：

- **span**：一个操作的记录，有名字、开始与结束时间、一组属性、一个状态；
- **trace**：一棵 span 树，共享同一个 `trace_id`——它对应**一次任务**；
- **context**：把「当前 span 是谁」传递给下一层的机制。它决定了子 span 挂在谁下面。

知舟的形状很扁，只有两层：根 span 是 `invoke_agent`，它下面平铺着若干
`chat` 与 `execute_tool`。真实的分布式系统会更深（HTTP 请求 → 服务 → 数据库查询），
但层级本身不是目的，**「哪几个操作属于同一次任务」才是**。

```python
# app/agent/trace.py —— 一次运行的根 span：它要盖住整个任务，不只是那几次调用（节选）
class Run:
    """一棵 span 树。根 span 是 `invoke_agent`，子 span 挂在同一层（本项目的操作没有嵌套）。"""

    def __init__(self, tracer: Tracer, task: str, *, conversation_id: str = "",
                 run_id: str = "", agent_name: str = "知舟") -> None:
        self._tracer = tracer
        self.task = task
        self.spans: list[Span] = []
        trace_id = tracer.new_id("trace")
        root_attrs = {"gen_ai.operation.name": INVOKE_AGENT,
                      "gen_ai.agent.name": agent_name,
                      "zhizhou.run_id": run_id,
                      "zhizhou.task.digest": digest(task),
                      "zhizhou.task.chars": len(task)}
        if conversation_id:
            # 会话 id 进属性：这样「同一会话跨几次运行」在追踪里是连得上的（官方同名属性）
            root_attrs["gen_ai.conversation.id"] = conversation_id
```

三个命名口径值得单独记下来，因为它们都不是自创的：

- **span 名**是 `{操作名} {模型}`，例如 `chat agnes-2.5-flash`。工具 span 用
  `execute_tool {工具名}`，例如 `execute_tool read_article`。这样在追踪界面上按名字聚合，
  得到的就是「哪个模型、哪个工具慢」；
- **操作名**取自官方枚举：`invoke_agent`、`chat`、`execute_tool`。**不自己造名字**——
  自造的名字在换后端时不会有人给你翻译；
- **会话 id 用官方的 `gen_ai.conversation.id`**：它把「同一会话的几次运行」串起来，
  而第 3.6 节的记忆层正是按会话组织的。官方还特别写了一条：拿不到会话标识时
  **不要**用 trace id 或内容哈希凑一个——假 id 会让「同一会话」的分析全部失真。

### 一次逻辑操作一棵 span，重试不另起一棵

这条是官方原文里最容易被违反的一句（`span SHOULD cover the duration of the logical
operation with all retries`）。它的含义用一张表说最清楚：

| 做法 | 「重试了 3 次才成功」在图上长什么样 | 后果 |
| --- | --- | --- |
| 一次逻辑调用一棵 span（正确） | 一个 span，属性里带 `attempts=3` | 与实际计费、与「这一次为什么慢」都对得上 |
| 每次重试各起一棵 span（错误） | 三个 span，两个失败一个成功 | 「调用次数」凭空变三倍，失败率也被抬高 |

代码里的落点只有一行——重试次数是**属性**，不是新的 span：

```python
# app/agent/trace.py —— 一次模型调用：重试次数进属性，不进 span 数量（节选）
    def record_model_call(self, run: Run, *, model: str, duration_ms: float, tokens: int = 0,
                          in_tokens: int = 0, out_tokens: int = 0, attempts: int = 1,
                          tools: tuple[str, ...] = (), agent_name: str = "知舟",
                          content: str = "", wrap_up: bool = False) -> Span:
        """一次模型调用。`attempts` 是**这一棵 span 里的重试次数**，不是新 span。"""
        attrs = {"gen_ai.operation.name": CHAT, "gen_ai.provider.name": self.provider,
                 "gen_ai.request.model": model, "gen_ai.agent.name": agent_name,
                 "gen_ai.usage.input_tokens": in_tokens,
                 "gen_ai.usage.output_tokens": out_tokens,
                 "zhizhou.attempts": attempts}
        if tools:
            attrs["gen_ai.response.finish_reasons"] = ["tool_calls"]
            attrs["zhizhou.tools.requested"] = list(tools)
        else:
            attrs["gen_ai.response.finish_reasons"] = ["stop"]
```

另外三条属性口径也一并落在这里：

- **`gen_ai.usage.input_tokens` / `output_tokens` 分开记**。只记总量就没法算钱——
  两者单价不同，而且输入里有一大块是每轮重发的历史（第 3.9.4 节）；
- **`gen_ai.response.finish_reasons`** 记「为什么停下来」：`["tool_calls"]` 表示还要调工具，
  `["stop"]` 表示给出了答案。它是判断「这次到底做完没有」的官方字段；
- **`error.type` 是低基数枚举**，不是错误原文（原文会带路径、带用户输入，基数无穷）。
  官方要求「形状相同的错误用同一个值」，理由是告警与分组都靠它。

还有一条本章自己加的属性：`zhizhou.wrap_up=True` 标出「收口那一次」。
它不是官方字段（所以带项目前缀，避免与将来官方新增的名字撞车），
因为**预算被用满的证据在官方口径里没有位置**，而它恰恰是「这一次为什么只给了打折的答案」
的直接原因。

### 采样：什么时候可以不全记

追踪的代价是存储：一次任务一棵树、一棵树十几个 span，一天几万次任务就是几百万条。
业界的做法是采样，两类策略的取舍完全不同：

- **头部采样**：请求进来时就按比例决定「这一次记不记」。它的优点是便宜（不记就什么都不做），
  缺点是你**记不到最想看的那一类**——失败的、慢的、异常的都只占少数，按比例抽多半抽不到；
- **尾部采样**：先把整棵树记在内存里，跑完之后按条件决定留不留（留下所有失败的、
  所有超过 3 秒的、以及 1% 的正常样本）。它贵在缓冲，但保住了「异常必留」这条性质。

这里有一个反直觉的结论值得写下来：**「全采」在成本上等价于「不记」**。
当你把所有东西都记下来之后，读的人会被淹没——真正的问题（那 0.5% 的慢请求）
在一堆正常样本里根本找不出来，于是没人去看。这就是本章的取舍：**本地不采样
（几百次运行还没到量级），但指标里留住了「异常必留」的能力**——
`failure_distribution` 与延迟分位都是全量算的，只有明细的 span 树才是有界的。

```python
# app/agent/trace.py —— 有界的账本：只留最近 200 次，进程活久了内存不能只涨不落（节选）
class Tracer:
    """记录器 ＋ 指标源。**有界**：只留最近 `max_runs` 次，否则进程活久了内存只涨不落。"""

    def __init__(self, *, capture_content: bool = False,
                 clock: Callable[[], float] = time.perf_counter,
                 max_runs: int = 200, provider: str = "openai",
                 price: Price | None = None) -> None:
        self.capture_content = capture_content
        self.clock = clock
        self.provider = provider
        self.price = price
        self.runs: deque[RunRecord] = deque(maxlen=max_runs)
        self._n = 0
```

`deque(maxlen=...)` 这一行承担了「有界」的全部责任：新的一次进来，最老的一次自动挤出。
它同时解释了 `/metrics` 上那个 `window` 参数——**看的是「最近多少次运行」，
不是「从进程启动至今」**，因为后者在跑了几天的进程上根本存不下。

## 3.9.4 指标：分位、直方图与每任务成本

指标最容易做错的地方是**只记平均值**。平均值会把两件完全不同的事压成同一个数：
「每次任务都花 2 秒」与「95 次花 0.1 秒、5 次花 40 秒」。而这两种情况的修法完全不同——
前者是系统性慢，后者是有长尾。所以延迟必须给分位：

```python
# app/agent/trace.py —— 分位数：延迟必须给分位，均值会被长尾藏住（节选）
def percentile(values: list[float], p: float) -> float:
    """线性插值分位。**延迟必须给分位，不给均值**：均值会被长尾藏住（3.9.4）。"""
    if not values:
        return 0.0
    xs = sorted(values)
    if len(xs) == 1:
        return xs[0]
    k = (len(xs) - 1) * p
    lo = int(k)
    hi = min(lo + 1, len(xs) - 1)
    return xs[lo] + (xs[hi] - xs[lo]) * (k - lo)
```

这里有个细节值得说：**样本很少时分位数没有意义**。15 次试验算 p95，等于在两个样本之间插值——
它报得出一个数，但那个数不承载统计意义。生产上的惯用做法是「样本少时报最大与最小值，
样本够多（几百以上）才报 p95 / p99」。本章保留 p50 / p95 两列，是因为它们在同一份表里
连起来看仍然有诊断价值，而不是因为它们在这点样本量上「统计显著」。

### 四类指标一次算完

指标的形状要先定下来，再谈怎么算。本章收敛成四类主指标 ＋ 两组切分：

```python
# app/agent/trace.py —— 四类指标：成功率、步数、成本、失败分布（节选）
        "tokens": {"avg": round(sum(r.tokens for r in records) / n, 1),
                   "input": in_tokens, "output": out_tokens,
                   # 输入占比是**最该看的一个数**：每轮把历史重发一次，输入会随步数平方增长。
                   # 服务商没分开报时为 None——**“没这个数”与“这个数是 0”是两件事**。
                   "input_share": round(in_tokens / (in_tokens + out_tokens), 4)
                   if (in_tokens + out_tokens) else None},
        "latency_ms": {"p50": round(percentile([r.duration_ms for r in records], 0.5), 1),
                       "p95": round(percentile([r.duration_ms for r in records], 0.95), 1)},
        "failure_distribution": dict(Counter(r.kind for r in records)),
        "by_tool": _by_tool(records),
        "by_role": _by_role(records),
    }
    if price is not None:
        out["cost"] = {"currency": price.currency,
                       "per_task": round(price.of(in_tokens, out_tokens) / n, 6),
                       "total": round(price.of(in_tokens, out_tokens), 6)}
    else:
        out["cost"] = None                     # 没配单价就只报词元，**不要编一个价**
    return out
```

四个数字各有各的读法：

**成功率**是唯一一个「一眼就该有数」的指标，但它单独看会误导——它把「模型做错了」
与「网络断了」混成一个数。真机上这一点立刻现形：15 次试验里 9 次是连接断开，
成功率读作 40%，而完成的那 6 次全部通过。只看 40% 会把结论写成「这个模型不行」，
**真实的结论是「这个服务商今天不稳定，而模型 6/6 通过」**。所以成功率必须与失败分布一起读。

**平均步数**是「效率」与「预算设计是否合理」的交叉点：它突然上升，通常是提示变了；
突然下降到 1，通常是**没调工具就回答了**（第 3.3 节的「直接答」，看着快，其实没查证据）。

**每任务成本**由两个数相乘得到，而**输入与输出必须分开算**：

```python
# app/agent/trace.py —— 单价：输入与输出是两笔钱，而且输入的重复付费才是大头（节选）
@dataclass(frozen=True)
class Price:
    """单价（每百万词元）。**输入与输出分开**——它们是两笔钱，而且输入的重复付费才是大头。"""

    input_per_mtok: float
    output_per_mtok: float
    currency: str = "元"

    @staticmethod
    def from_env(getenv: Callable[[str, str], str]) -> Price | None:
        """从环境变量读；两个都没配就是「没有单价」，此时只报词元、不报钱。"""
        raw = (getenv("LLM_PRICE_IN", ""), getenv("LLM_PRICE_OUT", ""))
        if not any(v.strip() for v in raw):
            return None
        try:
            return Price(float(raw[0] or 0), float(raw[1] or 0),
                         getenv("LLM_PRICE_CURRENCY", "元"))
        except ValueError:                      # 配错了不要炸整个服务：只当没有单价
            return None

    def of(self, in_tokens: int, out_tokens: int) -> float:
        return (in_tokens * self.input_per_mtok + out_tokens * self.output_per_mtok) / 1_000_000
```

三个细节都是刻意的：

- **没配单价就报 `None`，不报 0**。0 是一个数字，它会被加起来、被平均、被画在图上，
  而它什么都不是——「这个数是 0」与「没有这个数」必须能分开；
- **配置错不抛异常**（`except ValueError` 那一行）：指标是旁路，它不该把主流程打挂。
  单价配错了就降级成「没有单价」；
- **输入的重复付费才是大头**。真机那次读数是 `输入占比 0.9655`——**96.6% 的词元是输入**。
  原因在第 3.1 节就说过：每一轮都要把历史重发一次，所以步数一多，输入随步数增长。
  这也是把 `input` 与 `output` 分开报的直接理由：只报总量，你看不到「钱花在重发上」。

**失败分布**必须是**有限档**，这是本章花过最多心思的一个字段：

```python
# app/agent/trace.py —— 失败分布：档位按「下一步该改什么」分，不按原话分（节选）
# 失败分布的口径：**它必须是有限档**。把终止原因的原话当键，会得到一个每次都不同的
# 直方图（原话里带步数和工具名），那样读完什么也看不出来。六档是按「下一步该改什么」分的：
# 改预算、改提示、补工具、查服务商、查网络——它们的修法完全不同，所以不能合成一句「失败 3 次」。
#
# 最后一档是**真机跑出来的**：9 次试验因「连接断开」中断，全被归进「模型失败」——
# 而模型的错与服务商的错修法相反（前者改提示，后者加重试）。没有这一档时，一张
# 90% 是网络抖动的失败分布看起来像「这个模型不行」。
KINDS = ("成功", "预算收口", "卡死", "工具不可用", "模型失败", "运行中断")


def classify(reason: str) -> str:
    """把一次运行的终止原因收进有限档。**外部中断不能记成「模型失败」**。"""
    if reason.startswith("运行中断"):
        return "运行中断"
    if reason.startswith("模型给出最终答案"):
        return "成功"
    if any(k in reason for k in ("预算耗尽", "步数上限", "墙钟超时")):
        return "预算收口"
    if any(k in reason for k in ("卡死", "无新事实")):
        return "卡死"
    if "不存在" in reason:
        return "工具不可用"
    return "模型失败"
```

这段代码的注释里那件事值得展开：本章的工具第一次跑真机评测时，9 次试验因连接断开中断，
而它们**全部被归进了「模型失败」**。数字一个没错（9 次中断都记上了），但结论完全错了——
一张 60% 是网络抖动的失败分布，看起来像「这个模型不行」。加上 `运行中断` 这一档之后，
同一次运行读作 `{'成功': 6, '运行中断': 9}`，结论立刻变成「模型 6/6 通过，服务商今天不稳」。

**这就是「有限档要按修法分」的实际含义**：档位的划分依据不是「原因长什么样」，
而是「看到这一档的人接下来该改什么」。改预算、改提示、补工具、查服务商、查网络——
五件事完全不同的修法，不能合成一句「失败 3 次」。

### 分维度：按工具与按角色

总数看不出「哪里该改」。所以指标再切两刀：

```python
# app/agent/trace.py —— 按工具切：失败率高的那个就是最该改的一个（节选）
def _by_tool(records: list[RunRecord]) -> dict:
    """每个工具：调用次数、失败次数、平均耗时。**失败率高的那个就是最该改的一个。**"""
    acc: dict[str, dict] = {}
    for r in records:
        for s in r.spans_of(EXECUTE_TOOL):
            name = s.attributes.get("gen_ai.tool.name", "?")
            row = acc.setdefault(name, {"calls": 0, "failed": 0, "ms": []})
            row["calls"] += 1
            row["failed"] += 1 if s.status == "error" else 0
            row["ms"].append(s.duration_ms)
    return {k: {"calls": v["calls"], "failed": v["failed"],
                "avg_ms": round(sum(v["ms"]) / len(v["ms"]), 1) if v["ms"] else 0.0}
            for k, v in sorted(acc.items())}
```

本章离线的读数是：

```text
工具：create_draft 5 次（失败 0）｜get_tags 4 次（失败 0）｜publish_article 2 次（失败 2）
      ｜read_article 13 次（失败 0）｜search_article 2 次（失败 0）
```

`publish_article` 失败 2 次是**正确行为**：那两条用例测的正是「发布必须被拦下」，
所以在工具这一维里它是「失败」，在用例那一维它是「通过」。这一对读法要能同时说清，
否则很容易把「按设计拒绝」当成缺陷去修——**这就是为什么 `tool_no_run` 与「工具执行失败」
必须是两个判分器**（第 3.9.6 节）。

按角色切的理由不同：`by_role` 数的是每个角色的**模型调用次数**，
多 Agent 路径上它才非空。第 3.7 节讲过「哪个角色在花钱」这个问题的价值——
同一个目标，检索者调 1 次、写作者调 4 次，那预算该调的是写作者的交接单，
而不是总预算。**按工具切是为了改工具，按角色切是为了改分工**，两种修法不同，所以不能合并成一个维度。

## 3.9.5 日志与内容捕获：默认不记正文

指标告诉你「有事」，追踪告诉你「哪一步」，日志告诉你「为什么」，而三者之间最容易出事的是
**内容**——提示、模型输出、工具参数与结果。它们诊断价值最高，泄露风险也最高。

官方的立场写得很明确：语义约定里那几个内容类属性（`gen_ai.input.messages`、
`gen_ai.output.messages`、`gen_ai.system_instructions`、`gen_ai.tool.definitions`、
`gen_ai.prompt.variable`）标的是 **`Opt-In`**，而且**逐条都带敏感数据警告**
（原文用 `MUST`/`MAY` 级别的措辞要求它们默认不出现在遥测里）。
所以正确的默认值是「关」，打开要显式配置：

```python
# app/agent/trace.py —— 内容捕获默认关闭：不记正文，只记指纹与长度（节选）
        if self.capture_content:
            attrs["gen_ai.output.messages"] = content
        else:
            attrs["zhizhou.content.digest"] = digest(content)
            attrs["zhizhou.content.chars"] = len(content)
```

代替正文的是两样东西，它们各自解决一类问题：

- **指纹（`digest`）**：内容哈希的前 12 位。它能回答「这两次的内容是不是同一份」，
  **不能**反推出内容——这正是「可比对、不可还原」的取舍；
- **长度（`chars`）**：内容有多长。诊断「是不是上下文被截断了」「工具是不是返回了空」
  靠的是它，而不是正文。

开关的来源也在 `Opt-In` 的位置上：`LLM_CAPTURE_CONTENT=1`（环境变量），
不是代码里的常量——第 3.8 节的脱敏是同一条边界，两处都不该由程序员一句「先打开调试」决定。

### 结构化日志的字段口径

日志最容易退化成「一句人话」：`打印出来看得懂，但查不了`。所以字段要有规范，
而且规范要**和追踪共用同一套名字**：

| 场景 | 必须有的字段 | 说明 |
| --- | --- | --- |
| 模型调用 | `trace_id`、`span_id`、`model`、`attempts`、`in/out tokens`、`duration_ms`、`finish_reasons` | 与 span 属性同名同义，避免「同一件事两个叫法」 |
| 工具执行 | `trace_id`、`tool`、`ok`、`error.type`、`duration_ms`、参数指纹 | 参数只留指纹（除非显式打开内容捕获） |
| 终止 | `trace_id`、`termination`（原话）、`result`（有限档）、`steps`、`budget` | 原话与档位都要：前者给人看，后者给机器聚合 |
| 拒绝 / 确认 | 第 3.8 节的审计四件（谁 / 想做什么 / 判定 / 依据） | 审计与观测**分成两条写入路径**，不互相顶替 |

三条实践口径：

1. **一条日志一个事件**，不要把 6 件事拼成一行用分隔符分开——那等于自己发明一个格式；
2. **级别要能动态调**：`DEBUG` 用来打开内容捕获级别的细节，正常运行只留 `INFO` 以上。
   级别写死会让人养成「反正什么都打」的习惯；
3. **不要打两次同一件事**：追踪里已经有的字段，日志里再打一遍就会在两个地方各错一次。
   本章的做法是——**明细进 span 属性，日志只记那些没有 span 承载的事件**（进程启动、配置变更、
   预算耗尽时的收口决策）。

最后一条与第 3.8 节的边界要重申：**脱敏在内容捕获这条路上是前置条件，不是可选项**。
真要把正文记下来，先过分通道脱敏（密钥、令牌、邮箱、手机号、私有 URL），
再考虑保留期——「先存下来再脱敏」在合规上是不成立的。

## 3.9.6 评估：判产出、判终态，不判路径

指标是**被动**的：它记录已经发生的事。评估是**主动**的：它制造事件，只为了比较。
这也是本章下半部分的全部篇幅所在——Agent 的评估比普通服务难，因为
**行为在两次运行之间会变**（第 3.3 节那条「同一句提问跑四次两条轨迹」）。

先把术语定下来，它们不是同义词，混用会让讨论失焦：

| 术语 | 含义 | 知舟上的对应 |
| --- | --- | --- |
| task（任务 / 用例） | 一道有明确输入与成功标准的题 | `eval_cases.jsonl` 里的一行 |
| trial（试验） | 同一道题跑一次 | 一条用例的 `trials` 次之一 |
| grader（判分器） | 给某个方面打分的逻辑，一道题可有多个 | `tool_run` / `outcome_draft_status` 等 |
| transcript（轨迹） | 一次试验的完整记录（含工具调用与推理） | 那棵 span 树 |
| outcome（终态） | 试验结束时**环境里的状态** | 草稿在库里的 `status` |
| harness（跑法） | 端到端跑评测的基础设施 | `experiments/eval_run.py` |
| suite（套件） | 一组有共同目标的题 | `capability` / `regression` 两个套件 |

三类判分器的强弱点，选择顺序按「能用确定性就别用模型」：

| 类型 | 长处 | 短板 | 知舟用在哪 |
| --- | --- | --- | --- |
| 代码判分 | 快、便宜、客观、可复现、好调试 | 对「合法的变体」脆弱，缺细微判断 | 工具是否跑过、库里的状态、步数与词元上限 |
| 模型判分 | 灵活、能处理开放式输出 | 不确定、要人来校准、更贵 | 本章**不用**（第 4–5 篇的 RAG 评估会用） |
| 人工判分 | 金标准，用来校准模型判分 | 慢、贵、要专家 | 抽样复核判分器本身 |

### 判产出，不判路径

本章最容易做错的一条，是**把「应该走哪几步」写成判分器**。官方明确说过这种写法太脆：
Agent 经常找到设计者没想到的合法路线，按路径判会把这些一律判错。这道教训在本章的
评测集里就有一次真实记录——「读出文章标签」这道题的第一版判分器要求调用 `get_tags`，
而真机上模型**从 `search_article` 的结果里就拿到了标签**，于是它「失败」了：

```python
# tests/agent/eval_cases.jsonl —— 不要求调 get_tags：真机第一轮它从检索结果里就拿到了标签
{"id": "stuck-third-trial", "suite": "capability", "why": "三条试验里有两条会做完、第三条卡住：**pass@k 与 pass^k 在这里分道扬镳**。不要求调 get_tags——真机第一轮它从 search_article 的结果里就拿到了标签，而我们当时判的是路径", "task": "读 42 号文章的正文，并告诉我它的标签。", "trials": 3, "budget": {"max_steps": 6, "max_tokens": 8000}, "graders": [{"name": "读了正文", "type": "tool_run", "tool": "read_article"}, {"name": "答出了标签内容", "type": "final_contains", "any": ["安全"]}, {"name": "正常收口", "type": "termination", "expect": "成功"}], "scripts": [[{"action": "read_article", "arg": {"article_id": 42}}, {"action": "get_tags", "arg": {}}, {"final": "标签是：安全、后端、JWT、部署。"}], [{"action": "read_article", "arg": {"article_id": 42}}], [{"action": "read_article", "arg": {"article_id": 42}}, {"action": "get_tags", "arg": {}}, {"final": "标签有：安全、后端、JWT、部署。"}]]}
```

改法不是「放宽标准」，而是**把标准放在产出上**：要求「答出了标签内容」，
不要求「用哪个工具拿到它」。同一秒的另一个例子是反向题——「知舟上有没有讲
Kubernetes 调度的文章」这类问题，正确答案是「没有」。只测正向题会让代理对什么都答「有」，
所以套件里必须有**该说没有的那一类**。

### 判终态，不判那句话

比「判路径」更隐蔽的一种错：**信模型自己说做了什么**。「已发布上线」这五个字
在轨迹里出现，不证明库里那条草稿真的变成了 `published`。官方把两者的区别命名为
transcript 与 outcome，并明确说——**分数要算在终态上**：

```python
# experiments/eval_run.py —— 判环境终态：模型说了什么不算数，库里的状态才算（节选）
        elif kind == "outcome_draft_status":
            # 环境终态：**模型说了什么不算数**，库里那条草稿的状态才算（outcome > transcript）
            got = (store.get("draft") or {}).get("status", "（没有草稿）")
            if "expect_not" in g:
                add(g["name"], got != g["expect_not"], f"库里状态 {got}（不应为 {g['expect_not']}）")
            else:
                add(g["name"], got == g["expect"], f"库里状态 {got}（期望 {g['expect']}）")
```

还有一个必须分开的组合，它同时是观测与评估的关键：

```python
# experiments/eval_run.py —— 「没执行」与「没尝试」是两件事（节选）
        elif kind == "tool_no_run":
            # 「没有真的执行」与「没有尝试过」是两件事：被权限拦下的一次是**尝试过**，
            # 它该记在账上（3.9.5 的那张表就是靠这一列分开的）。
            ran = [t for t in g["tools"] if any(s.status == "ok" for s in tool_spans(record, t))]
            add(g["name"], not ran, f"真正执行过的：{ran or '无'}")
```

`tool_no_run` 判的是「**真的执行过**没有」，`tool_no_attempt` 判的是「**尝试过**没有」。
第 3.8 节的注入用例需要前者：模型尝试发布但被白名单拦下，是**护栏生效**的证据，
不能因为「没发布成功」就给「没有尝试」的满分——那样一条完全没被触发过的用例
与一条被拦下的用例会得到同样的分数。

### 能力评估与回归评估要分开

两类套件的目标相反，混在一起就两头不讨好：

| | 能力评估（capability） | 回归评估（regression） |
| --- | --- | --- |
| 问的问题 | 「它能做到什么」 | 「它还能做到原来那些吗」 |
| 期望的通过率 | **低**（起点低才有爬坡空间） | **接近 100%** |
| 变差意味着 | 正常（还在爬） | 有人改坏了东西，必须停下 |
| 知舟上 | `qa-refresh-token`、`no-such-topic`、`stuck-third-trial` | `draft-then-stop`、`summary-three-tools`、`injection-cannot-publish` |

两者之间还有一条**毕业机制**：一条能力题跑久了稳定通过，就该转进回归套件——
它测的问题从「我们能不能做到」变成「我们还能不能稳定做到」。知舟的
`injection-cannot-publish` 就是这种题：第 3.8 节第一次跑它是探索（护栏到底拦不拦得住），
现在它是一条回归题（每次改动都不许把它跑坏）。

## 3.9.7 单次成功不能当通过：试验与统计

这一节是本章最不像「编程」的一节，也是 Agent 评估与普通测试最大的分界。

### 一次成功不是通过

第 3.3 节那条实测（同一句提问四次、两条轨迹）的直接推论是：
**「跑一次通过」不能写进验收标准**。两个指标分别刻画这件事的两面：

| 指标 | 含义 | 上升时 | 适合 |
| --- | --- | --- | --- |
| pass@k | k 次里**至少一次**成功 | 随 k 增大而**升高** | 「一次做出来就行」的工具型任务 |
| pass^k | k 次里**全部**成功 | 随 k 增大而**降低** | 面向用户、要求每次稳的任务 |

两者在 k=1 时相等，k 一大就朝相反方向走：k=10 时前者趋近 100%，后者趋近 0%。
直觉上最清楚的一个算式是官方给的例子：单次成功率 75%、跑 3 次，
三次全过的概率是 0.75³ ≈ 42%。

知舟的评测集在离线跑里同时算这两个数，于是出现了一行只属于这一节的现象：

```text
用例                          套件            试验    通过    首次    至少一次    全过     平均步数     词元/次
stuck-third-trial           capability     3     2     ✓       ✓     ✗     2.67     24.0  ←
```

`stuck-third-trial` 的三条试验里两条做完、第三条卡住（剧本用完就重复最后一个动作，
这正是在测卡死）。**「至少一次」是 ✓，「全过」是 ✗**——一次成功与每次都成功在这里
被分开了，而这种用例才是真实的：能做完但偶尔卡住的代理，比从来做不完的代理更常见，
也更容易被一次「跑通了」的验收漏掉。

### 评测的统计：五条能直接用的建议

试验次数一多，第二个问题就来了：一次 3% 的提升，是改进还是抖动？
官方给的五条建议，逐条都有可以落地的动作：

| # | 建议 | 作用 | 在知舟上怎么用 |
| --- | --- | --- | --- |
| 1 | 报标准误（SEM）与 95% 置信区间 | 让「这个分数有多少不确定」可见 | 题量够时给通过率 ± 1.96×SEM |
| 2 | **聚类标准误** | 同一篇 / 同一话题的题不是独立样本，忽略它会把标准误低估 | 同一文章的题聚类后报，实测聚类标准误可以是朴素值的**3 倍以上** |
| 3 | 题目内多采样降方差 | 同一题多跑几次取均值，比多出几道题更划算 | 就是 `trials` 存在的第二个理由 |
| 4 | **配对差比较** | 基线里的位置会把「难度」这一项抵掉，等于白得一次降方差 | 与基线比同一批用例，而不是比两个总数 |
| 5 | 功效分析 | 先问「要看出 3% 的差别需要多少题」，再决定题量 | 题太少时**别下结论**，也不要靠加跑凑显著 |

第 4 条正是本章的回归门用「逐条用例的通过数」而不是「总成功率」比较的原因：

```python
# experiments/eval_run.py —— 与基线比：任何一条用例的通过数下降都算退步（节选）
def regression_gate(current: dict, baseline: dict) -> list[str]:
    """与基线比：**任何一条用例的通过数下降、或整体成功率下降超容差，都算退步。**

    只比「通过数」不比耗时与词元：后两者会随服务商与机器抖，把它们也当门会让门变成噪声源
    （第 8.5 节那条「乱响的检查最终会被绕过」）。
    """
    problems: list[str] = []
    if baseline.get("mode") != current.get("mode"):
        return [f"基线是 {baseline.get('mode')} 模式，当前是 {current.get('mode')}——"
                "真机跑不当门，基线只收离线那一份"]
    old = {c["id"]: c for c in baseline.get("cases", [])}
    new = {c["id"]: c for c in current["cases"]}
    for cid, row in old.items():
        if cid not in new:
            problems.append(f"{cid}：基线里有、现在没有了（用例被删掉不算改进）")
        elif new[cid]["passed"] < row["passed"]:
            problems.append(f"{cid}：通过数 {row['passed']}/{row['trials']} → "
                            f"{new[cid]['passed']}/{new[cid]['trials']}")
    drop = baseline["totals"]["success_rate"] - current["totals"]["success_rate"]
    if drop > TOLERANCE:
        problems.append(f"整体成功率 {baseline['totals']['success_rate']:.1%} → "
                        f"{current['totals']['success_rate']:.1%}（跌了 {drop:.1%}）")
    return problems
```

三处细节都是被真实问题逼出来的：

- **删掉用例不算改进**（`cid not in new` 那一支）。不然「删掉过不去的那条」就成了最快的通过方式；
- **真机读数不与离线基线比**（第一段 `return`）。真机的通过率会抖，拿它当门等于把门变成噪声源；
- **只比通过数，不比耗时与词元**。后两者在真机上受服务商与机器影响，把它们当门的结果是
  「门天天响」——而一个乱响的检查最终会被绕过（第 8.5 节那条）。

### 一条被外部原因打断的试验要进账

限流、超时、断连是评测里最常见的失败，而它们**不是被测对象的表现**。处理方式如果写错，
会得到一个荒谬的结果：**基础设施抖动把成功率抬上去**。

原因很直接：一条中断的试验什么都没做，于是它会「轻松通过」所有「不该做 X」的判分器
（没写草稿、没发布、没乱调工具——因为什么都没发生）。所以中断的试验**不进判分器**，
直接记一次不通过：

```python
# experiments/eval_run.py —— 中断的试验必须进账，而且原因要单独成档（节选）
def aborted(case: dict, n: int, exc: Exception,
            elapsed_ms: float = 0.0) -> tuple[tr.RunRecord, dict]:
    """一次试验被外部原因打断（限流、超时、断连）：**它必须进账，不能把整场评测带走**。

    两件事不能混：`评分不过` 与 `根本没跑完`。一个中断的试验会“轻松通过”所有
    「不该做 X」的判分器（因为什么都没发生）——照常打分的话，基础设施抖动会把成功率**抬上去**。
    所以中断的试验不进判分器，直接记一次不通过，并把原因写进失败分布的**「运行中断」档**
    ——与「模型失败」分开：真机上这两档的修法相反（一个加重试，一个改提示）。
    （官方 Step 4：共享基础设施造成的相关失败会让试验不再独立。）
    """
    tracer = tr.Tracer()
    run = tracer.start_trace(case["task"], run_id=f"{case['id']}#{n}(中断)")
    kind = getattr(exc, "kind", type(exc).__name__)
    # 时长要传**真实的已耗**：默认 0 会让 9 次中断把延迟 p50 拉到 0.0ms——
    # 一张「p50 0.0ms」的延迟表看不出任何东西，而它其实是「一半样本没有时长」。
    record = tracer.finish(run, reason=f"运行中断：{kind}", steps=0, calls=0, tokens=0,
                           duration_ms=elapsed_ms, error_type=str(kind))
    return record, {}
```

这里的 `elapsed_ms` 是本章第二次跑真机时补上的：第一版的默认时长是 0，
于是 9 次中断把延迟 p50 拉到 `0.0ms`——**一张「p50 是 0 毫秒」的延迟表看起来像「系统飞快」**，
实际含义是「一半样本没有时长」。数字都在，读法完全反了。

官方对这件事的说法是「共享基础设施造成的相关失败会让试验不再独立」：
如果 9 条试验同时因为同一个原因失败，这 9 个样本不携带 9 份独立信息，
于是**它们不该被当成 9 次「模型表现差」**。这是功效分析那一条在实践里的样子。

### 题从哪来、多少条起步

起步规模上，官方给的经验值是**20–50 条来自真实失败的题**就够开始，
而不是等到有几百条。理由是早期每次改动的影响都很大，小样本也看得出来。
题从哪来也有顺序：先拿你现在**手动在测**的那些，再去 bug 追踪与支持队列里找真实失败。
知舟的 6 条题就是按这个顺序来的——`draft-then-stop` 来自第 3.8 节「用户说直接发布」那类诉求，
`stuck-third-trial` 来自第 3.3 节「同一句提问两条轨迹」那次观察。

题面质量有三条硬要求，任何一条不满足都会让分数变得不可解释：

1. **两个专家独立看会得出同一个通过判定**。含糊的题面会变成指标里的噪声；
2. **每题都要有不通过的可能**（有明确的对立面）。只有正向题的套件会导致
   「对什么都答有」的代理拿到高分；
3. **每题都要有一个参考解**——一份能通过全部判分器的已知解。它证明这道题可解、
   判分器配置正确。官方的经验是：**多次试验全 0% 通过，先怀疑题，而不是先怀疑模型。**

最后一条落在实现上是一个断言：评测集加载时逐条检查「有判分器、有剧本」：

```python
# experiments/eval_run.py —— 题面质量的两条硬要求在加载时就检查（节选）
def load_cases() -> list[dict]:
    rows = [json.loads(line) for line in CASES.read_text(encoding="utf-8").splitlines() if line.strip()]
    # 题面质量的两条硬要求（官方 Step 2）：每题都要有一个确定性的剧本，
    # 否则离线跑不起来；每题都要有判分器，否则它只是一个「跑得动」的演示。
    for case in rows:
        assert case.get("graders"), f"{case['id']} 没有判分器"
        assert len(case.get("scripts", [])) and case["trials"] > 0, f"{case['id']} 缺少剧本"
    return rows
```

### 离线当门，真机报数

最后一个结构性的决定：**同一条评测集有两种跑法，只有一种能当门**。

| | `--offline` | `--real` |
| --- | --- | --- |
| 「模型」是什么 | 背好剧本的函数 | 真实服务商 |
| 工具 / 循环 / 注册表 / 追踪器 / 判分器 | **全都是真的** | 全都是真的 |
| 证明什么 | **评测这套机器是准的** | 被测对象此刻的表现 |
| 能不能当门 | **能**（确定性、秒级、不要密钥） | **不能**（读数会抖、要网、要钱） |

这不是「离线是简化的假跑」，而是**把变量分开**：离线的剧本让「评测机器本身」变成确定性的，
于是任何变化都只能来自被测的那部分。离线跑不出模型的能力上限，但它能证明
「判分器写对了、回归门真的会响」——后者才是一个门该有的性质。

```python
# experiments/eval_run.py —— 剧本驱动：工具、循环、追踪器、判分器都是真的，只有「模型」是剧本（节选）
def scripted(steps: list[dict], wrap_text: str = "（按已有信息收口）"):
    """把「模型」换成背好剧本的函数。剧本用完就重复最后一个动作——**这正是在测卡死**。"""
    def policy(task, trace, wrap_up=False):
        if wrap_up:
            return {"thought": wrap_text, "final": True, "tokens": 8, "final_text": wrap_text}
        n = len([e for e in trace.entries if not e.final])
        step = steps[min(n, len(steps) - 1)]
        if "final" in step:
            return {"thought": step["final"], "final": True, "tokens": 8,
                    "final_text": step["final"]}
        return {"thought": f"{step['action']}", "action": step["action"],
                "arg": json.dumps(step.get("arg", {}), ensure_ascii=False), "tokens": 8}
    return policy
```

## 3.9.8 读法与告警：分数到顶之后

### 读 transcript：数字掉了要能说出为什么

分数只告诉你「掉了 3%」，说不出「掉在哪」。所以每条用例失败时都要留下**哪个判分器没过**：

```text
    ✗ stuck-third-trial 第 2 次｜无新事实 → 收口｜没过的判分器：答出了标签内容、正常收口
```

这一行就是本章的读 transcript 的入口：它指向「那一次」，顺着 `trace_id` 能找到那棵树，
树上有每一步的动作与参数。**没有这一行，分数就只是一个数字**；
而有了它，改一次提示之后的涨跌能立刻归因到具体判分器。官方的说法是「失败要有细节」，
理由是：分不清「模型变差了」与「判分器写坏了」的评测，不能用来指导改动。

### 评估饱和：分数到顶之后

一条能力题跑到接近满分，它就不再指路了——**它只能防退步，不能告诉你下一步该做什么**。
这是评估的第三个阶段（探索 → 爬坡 → 饱和），对应的动作是：

- 饱和的题**转进回归套件**（毕业机制），继续拦住退步；
- 能力侧换更难的题——把「要求更严」而不是「要求更多」；
- 或者提高标准：同样一道题从「答对标签」升级成「答对标签并给出依据」。

知舟当前的 6 条题正处于探索阶段（离线成功率 93.3%），离饱和还远；
但 `stuck-third-trial` 的「至少一次 ✓ / 全过 ✗」已经提前演示了饱和期的形状。

### 告警：响得太勤就会被绕过

指标有了，最后一个问题是「谁在看」。告警设计上有三条来自实践的口径：

1. **多级阈值，而不是一条线**。一条线只有两种情况（响 / 不响），而现实里
   「有点慢」「很慢」「完全不可用」是三件不同的事，对应三种不同的应对
   （先看着 / 查一下 / 叫人起来）。分级的价值在于它让**不响**也是一种信息；
2. **告警要能回答「该做什么」**。`成功率下降` 不是告警，`成功率下降且失败集中在工具不可用`
   才是一条可执行的告警——它直接指向「工具或服务商」这一档；
3. **降噪，否则告警会被忽略**。一直响的告警最终会被加白名单，而加白名单之后就再也没人看了。
   这与本章回归门「只比通过数、不比耗时」是同一条原则：**宁可少报，不可乱报**。

一条只有 Agent 才有的告警值得单独列出来：**输入占比异常升高**。
它不响的时候代表「历史重发正常」，一旦从 96% 掉到 60%（说明有改动让历史没带上，
第 3.6 节的装配出了问题），或者升到 99%（说明上下文在膨胀），
两者都比单纯的成功率下降更早暴露问题。

## 3.9.9 知舟接线

本章把「可观测性与评估」这一段落到可运行树里，交付四样：一个核心模块（`trace.py`）、
一份评测集（`tests/agent/eval_cases.jsonl`）、一个跑法与回归门（`experiments/eval_run.py`）、
一个只读端点（`GET /api/v1/agent/metrics`），外加一组测试。
这一节按 [`PROJECT.md`](PROJECT.md) 的四问写。
**实跑与拼接验证的标注**：span 树、四类指标、分维度、评测集与回归门、自检夹具、
六个端点的路由全部**离线跑通**（不需要密钥，也不需要数据库）；
`experiments/eval_run.py --real` 的 15 次试验与 `demo.py` 的指标自检是真机跑；
导出到 OTLP、接后端、采样策略**没有实现**（第 7 篇 7.2 节与 7.4 节的地盘）。

### 加了什么

往知舟里加了**一层「事后可查」的账**：每次任务开一棵 span 树（`invoke_agent` →
`chat` / `execute_tool`），每次模型调用与工具执行往里挂一个 span，
跑完把这一次收进一个有界的账本；账本能按四类指标聚合，并支持按工具与按角色两个维度切分。
评测侧加了**一套能当门用的跑法**：6 条用例、15 次试验，判分器判产出与终态，
离线读数是确定性的、与基线逐条比对，真机读数只报不动门。

它是 v3 的**第九段增量**，复用第 3.5 节的注册表、第 3.6 节的会话与记忆、
第 3.7 节的编排与角色名、第 3.8 节的脱敏边界，**不新增任何外部依赖**
（纯标准库：`hashlib`、`time`、`collections`、`dataclasses`）。

**端点**：新增 `GET /api/v1/agent/metrics?window=50`（返回 `Result` 外壳，
`data` 就是 `summarize()` 的那份字典）。它挂在**不需要模型凭据**的那条依赖上：

```python
# app/api/agent.py —— 只读指标端点：看账不该要求密钥（节选）
@router.get("/metrics", response_model=Result)
def metrics(window: int = Query(default=50, ge=1, le=200),
            svc: AgentService = Depends(get_memory_service)) -> Result:
    """四类指标：成功率 / 平均步数 / 每任务词元 / 失败分布（再给延迟分位与分维度）。

    它挂在**不需要模型凭据**那条依赖上：看账不该要求密钥，否则没配模型的开发机上
    「刚才那几次到底跑成什么样」会以一个 500 回答你（3.6 踩过同一个坑）。
    参数 `window` 是看最近多少次运行——取有界的滑动窗口，而不是「从进程启动至今」。
    """
    return Result.success(svc.metrics(window=window))
```

**不新增**任何写端点，也**不改**任何既有端点的请求与响应形状：
`chat` 与 `session_chat` 的返回值多了两个字段（`record`、`trace_id`），
其余形状一行不变——观测是旁路，它不该改变业务接口。

### 不能破坏什么

- **不改业务路径的形状**：本期改动只加钩子（`on_call` / `on_tool`）与一个只读端点。
  `loop.py` 的终止判定、`registry.py` 的工具契约、前面各章的响应形状一行不改；
- **指标是旁路，不许把主流程打挂**：`Price.from_env` 遇到配错的单价必须降级成「没有单价」，
  而不是抛异常。旁路一抛异常，观测行为就成了故障源；
- **内容捕获默认关闭**，且只有 `LLM_CAPTURE_CONTENT=1` 一条开关。
  任何「为了调试先默认打开」的改动都算破坏（第 3.8 节的脱敏是同一条边界）；
- **一次逻辑操作一棵 span**：重试进 `attempts` 属性，不许另起 span。
  破坏它的后果不是少一个字段，是调用次数与失败率同时失真；
- **失败分布必须有限档**：新增档位要同时给出「这一档该改什么」。
  把终止原话当键会让直方图每次都不同——那样它读起来什么都不是；
- **真机读数不进基线**：`regression_gate` 第一段就是这条的守门。删掉它，
  门会在服务商抖动时天天响，然后被人加白名单；
- **告警阈值不写进代码常量**：阈值是运行时的判断（多级、可降噪），
  写进代码等于把「谁该被叫醒」固化进版本控制；
- **审计与观测分成两条写入路径**：不要把第 3.8 节的审计记录当指标源，
  它们的保留期与字段口径完全不同。

## 常见坑

1. **用日志代替追踪**。日志能回答「发生了什么」，回答不了「它走到了哪一步」——
   在图上少一层父子关系，「这次为什么慢」就要靠人拼时间戳。三支柱不是三选一。
2. **只记平均值**。均值会把「都慢」与「长尾慢」压成同一个数，而这两种情况的修法完全不同。
   延迟必须给分位。
3. **样本很少就报 p95 / p99**。15 个样本算 p99 是在两个点之间插值，它报得出数，
   但不承载统计意义——样本少时报最大最小值。
4. **把失败也混进延迟分位**。失败通常更快，于是失败率一升、延迟看着「变好」。
5. **把「按预算收口」算成失败**。它是设计好的终止方式，交付的是打折的答案，不是错误。
   扔进错误率会让正常系统看起来一直出错。
6. **重试另起一棵 span**。「重试了 3 次」会在图上长成「调用了 3 次」，
   调用次数与失败率同时失真，而按次计费的账单不会。
7. **把内容（提示 / 输出 / 工具参数）默认记下来**。它们是敏感数据，
   官方口径是逐项 `Opt-In`；默认打开等于把用户的输入直接写进遥测管道。
8. **用 `error.type` 装错误原文**。原文带路径、带用户输入、基数无穷，
   分组与告警都会失效——它是低基数枚举。
9. **失败分布用终止原因的原话当键**。原话里带步数与工具名，直方图每次都不同，
   于是「失败最多的是哪一类」永远答不出来。
10. **中断的试验照常打分**。一条什么都没做的试验会「轻松通过」所有「不该做 X」的判分器，
    基础设施抖动于是把成功率**抬上去**。中断必须记成不通过，且单独成档。
11. **按路径判分**。要求固定动作序列，会把模型找到的合法路线一律判错
    （「读标签」那道题的第一版就是这么坏的）。
12. **信模型说的「已发布」**。判分要看环境终态：库里那条记录的状态才算。
13. **把「没执行」与「没尝试」合成一个判分器**。被护栏拦下的尝试是护栏生效的证据，
    不能和「压根没试」得同一个分。
14. **只测正向题**。只测「该搜的时候搜了吗」，会得到一个对什么都搜的代理；
    套件里必须有该说「没有」的那一类。
15. **拿单次通过当验收**。Agent 的输出会抖；「至少一次」与「每次都过」是两个指标。
16. **题太少就下结论**。3% 的差别在 15 次试验里看不出来；
    先算「要多少题才看得出」，再决定题量——也不要靠加跑到显著。
17. **拿真机读数当回归门**。它会抖、要网、要钱；基线只收离线那一份确定性读数。
18. **删掉过不去的用例**。这是最快的「通过」方式，所以回归门要专门挡它。
19. **把追踪器的实例建在请求里**。`/metrics` 只会看到最后一次运行，
    而指标的意义全在「很多次」上。
20. **把语义约定当稳定接口**。GenAI 语义约定的状态是 Development，字段会变；
    升级前要看变更说明。

## 面试视角

- **问「你怎么知道你的 Agent 变好了还是变坏了」**：先分**指标**与**评估**（被动记录 / 主动比较），
  再说评估的结构（task / trial / grader / transcript / outcome / harness），
  最后落在两个数字上：**pass@k 与 pass^k**——「一次能做」和「每次都做得到」是两件事。
- **问「怎么设计一个 Agent 的评测」**：20–50 条来自真实失败的题起步；判分器优先用确定性代码；
  **判产出与环境终态，不判路径**；能力题与回归题分开；每题都要有参考解；
  多次试验取比例而不是单次通过。
- **问「你的评测为什么可信」**：报不确定度——标准误与置信区间；
  同一篇 / 同一话题的题要**聚类标准误**（实测可大到朴素值的 3 倍以上）；
  与基线比**配对差**；题量按功效分析定，题太少就不下结论。
- **问「多 Agent 或长任务怎么观测」**：按 OpenTelemetry 的 GenAI 语义约定记录
  （`invoke_agent` / `chat` / `execute_tool`，`gen_ai.*` 属性），
  一次逻辑操作一棵 span（重试进属性）、内容默认不记、指标按工具与角色两个维度切。
  再补一句「语义约定的状态还是 Development」。
- **问「线上怎么发现 Agent 出了问题」**：四类黄金信号在 Agent 上的映射——
  延迟看分位、流量看调用次数、错误看**失败分布**、饱和度看预算；
  再加一条 Agent 特有的：**输入占比异常**（历史重发是否正常）。
- **问「告警怎么设计」**：多级阈值、可执行（告警里带着失败档位）、降噪。
  一句「响个不停的检查最终会被加白名单」比任何指标都说明你做过线上。
- **问「你的回归门拦什么」**：逐条用例的通过数下降、用例被删掉、离线与真机混比；
  不拦耗时与词元（那会让门变成噪声源）。

## 本章小结

1. **测试回答你想到的问题，可观测性回答你没想到的问题**；前者的建设时机是写代码时，
   后者的建设时机是故障之前——没记下的东西事后补不出来。
2. 三支柱分工：**指标**说有事发生、**追踪**说哪一步、**日志**说为什么。
   Agent 天然偏白盒（「模型想了什么」在系统外部不存在）。
3. 四类黄金信号在 Agent 上的映射：延迟看**任务**的墙钟分位、流量看**模型调用次数**、
   错误看**失败分布**、饱和度看**预算**。失败混进延迟分位会让延迟「越坏越好」。
4. 记录按 OpenTelemetry 的 GenAI 语义约定：span 名 `{操作} {模型}`、
   操作名取自官方枚举、会话 id 用 `gen_ai.conversation.id`；
   **一次逻辑操作一棵 span，重试进属性**；**内容捕获逐项 `Opt-In`、默认关闭**；
   这套约定当前是 Development。
5. 指标四件：成功率、平均步数、每任务成本、失败分布。
   **失败分布必须是有限档，按「下一步该改什么」分**——真机上「网络中断」被记成
   「模型失败」时，数字一个没少，结论完全反了。
6. 成本要**输入与输出分开**算：真机实测输入占比 96.6%，
   钱主要花在「每轮重发历史」上。没配单价就报 `None`，不报 0。
7. 评估的判分顺序：能用确定性代码就别用模型；**判产出不判路径**（固定动作序列会误杀合法路线）；
   **判环境终态不判那句话**（「已发布」不算，库里的状态算）；
   「没执行」与「没尝试」必须是两个判分器。
8. 能力题起点低、回归题接近全绿；稳定通过的能力题**毕业**成回归题。
9. **单次成功不能当通过**：pass@k 随 k 上升、pass^k 随 k 下降，
   k=1 时相等——3 次试验、单次 75% 的成功率，三次全过只有约 42%。
10. 统计五条：报 SEM 与置信区间、聚类标准误、题目内多采样、配对差、功效分析。
    题太少就不下结论，也不要靠加跑到显著。
11. **中断的试验必须进账且单独成档**：它什么都不做，会「轻松通过」所有「不该做 X」的判分器，
    从而把成功率抬上去；它的时长要记真实已耗，否则延迟分位会被拉到 0。
12. 离线当门、真机报数：离线证明「评测机器是准的」，真机读的是被测对象此刻的表现。
    真机读数不进基线。
13. 回归门只比通过数、不比耗时与词元；并专门挡住「删掉用例」这条捷径。
14. 分数到顶就**饱和**：饱和的题转回归防退步，能力侧换更难的题。
    告警要分级、可执行、降噪——**响得太勤的检查最终会被绕过**。
15. 观测是旁路：不改业务路径的形状、不许把主流程打挂、内容默认不记。

## 练习

- **基础**：给评测集加两条用例——一条 `capability`（测一次真正的多步任务，
  比如「把 42 号文章的摘要与标签存成草稿，并说明为什么选这两个标签」）、
  一条 `regression`（测「不许把文章 43 的内容读到」这类越权）。
  要求：每条至少三个判分器，其中必须有一个判**环境终态**；跑
  `experiments/eval_run.py --offline --write-baseline` 更新基线，
  再跑 `--check` 确认门是绿的。回答一个问题：**新加的两条用例，`trials` 各设几次？
  理由是什么？**
- **进阶**：把 `KINDS` 里的 `运行中断` 暂时去掉，重跑
  `experiments/eval_run.py --real`（或在离线里注入一个会抛异常的实验跑法），
  记录失败分布的变化；然后恢复它，改为把 `预算收口` 也合进 `模型失败`。
  两次改动各回答一个问题：**哪一档去掉之后，「下一步该改什么」变得不可回答？
  哪一档合进去之后，一个正常系统看起来像一直在出错？**
- **挑战**：给本章的指标加一条**告警**（不改循环、不改端点形状）：
  当最近 N 次运行的「输入占比」超过 98% 或低于 60% 时给出可执行的提示
  （分别指向「上下文膨胀」与「历史没带上」两种可能）。
  要求：1）阈值来自配置而不是代码常量；2）同一状态在滑动窗口内只报一次（降噪）；
  3）写一条测试证明它**在该报的时候报、在正常波动时不报**——后者更重要。

**不用的理由**：LSTM、自回归残差、根因排序与故障传播链路推断是**算法与 SRE 侧**的题目——
要数据、要基线模型、要拓扑。本章讲的是「一次 Agent 运行好不好、好多少」，
把它们拉进来会写成一个模型训练小节。**漂移与退化那三题归本章**（它是评估侧的判断），
而「怎么用统计模型检测」不归。所以本章的**判据来自官方文档**
（OpenTelemetry 的 GenAI 语义约定、Anthropic 的评测与统计方法、Google SRE 书的监控一章），
**数字全部来自本机跑**（离线 15 次试验的四类指标、六条读数与门的自检、真机 15 次试验），
实现由本章重写。题库不作结论依据，只作**考点索引**（面试视角一节）。
