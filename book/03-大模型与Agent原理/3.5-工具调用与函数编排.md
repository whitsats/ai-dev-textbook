## 3.5.1 一次工具调用的往返

先看动作的完整路径。用户问道：

```text
帮我找一篇讲 JWT 刷新令牌的文章，读一遍，然后说清它给了几种做法。
```

模型不会去查数据库，也不会去读文件。它做的是**提出一个调用**：

```json
{"type": "tool_use", "id": "toolu_01A09q90qw90lq917835lq9", "name": "search_article",
 "input": {"q": "刷新令牌"}}
```

接下来的三件事都由你的代码做：执行 `search_article("刷新令牌")`，把结果包成一条 `tool_result`，
把它连同 `tool_use_id` 发回模型。模型看到结果之后再决定下一步——再调一次工具，或者给出回答。
这个往返就是 3.3 那个循环的每一次迭代。

三件事分开看，责任很清楚：

| 环节 | 谁做 | 产出 |
| --- | --- | --- |
| 决定调什么、参数给多少 | 模型 | 一个 `tool_use` 块：`id` / `name` / `input` |
| 真的去执行 | 你的代码 | 一段字符串、一段 JSON，或者一个错误 |
| 记账（词元、耗时、成功失败） | 你的代码 | 追踪记录，第 3.9 节要用 |

**这个分工有一条最重要的推论：模型给的是「意图」，不是「事实」。** `input` 里的每个值都还没有发生过——
`{"q": "刷新令牌"}` 只是一个待执行的请求，它可能是模型猜的、记错的，甚至是别人塞进去的。
官方文档在工具定义那一页把这一点写得很直白：模型会根据请求猜出你没给的值
（比如用户没说城市时，它可能替你把 `location` 填成纽约）。所以参数必须当成**用户输入**来对待，而不是当成程序内部调用。

两套主流 API 的形状相同、名字不同，看代码时不要被名字带偏：

| 概念 | Claude | OpenAI |
| --- | --- | --- |
| 工具定义字段 | `name` / `description` / `input_schema` | `function.name` / `function.description` / `function.parameters` |
| 模型的调用意图 | 响应里的 `tool_use` 块，`stop_reason: "tool_use"` | `message.tool_calls[]` |
| 你回的结果 | `user` 消息里的 `tool_result` 块，按 `tool_use_id` 配对 | `role: "tool"` 的消息，按 `tool_call_id` 配对 |
| 强制调用 | `tool_choice`：`auto` / `any` / `tool` / `none` | `tool_choice`：`auto` / `required` / 指定函数 |

两者都是「意图 → 你自己执行 → 结果回填」。记住这个形状，具体字段查文档就行。

## 3.5.2 工具定义的三个字段

一个自定义工具由三个字段构成，官方对这三点都有明确要求：

| 字段 | 内容 | 官方限制 |
| --- | --- | --- |
| `name` | 工具名 | 匹配正则 `^[a-zA-Z0-9_-]{1,128}$`；跨服务时加前缀（如 `github_list_prs`） |
| `description` | 纯文本说明：做什么、什么时候用、怎么表现 | 官方称它是**工具表现里最重要的因素**，建议每个工具至少 3–4 句 |
| `input_schema` | 参数的 JSON Schema | `type` / `properties` / `required` / `enum` 等标准关键字 |

第三个字段是整章最容易出错的地方，因为它同时被**两方**使用：模型照着它生成参数，你的代码照着它校验参数。
这就带来一个必须守住的性质——**同一份 schema 只能有一处定义**。说明书写着 `article_id` 必填、
实现里却有默认值，这种漂移在真实项目里极为常见，而它的症状是「模型永远不传这个参数，代码却总能跑通」，
于是没人发现说明书是错的。

```python
# 一份工具定义：schema 与实现相邻，改一处就必须改另一处
SEARCH_ARTICLE = {
    "name": "search_article",
    "description": (
        "按关键词检索知舟的历史文章，返回文章 id、标题与标签。适用于「有没有讲过 X 的文章」"
        "这类按主题找文章的问题；查询词给关键词而不是整句话。要正文请拿到 id 后调 read_article。"
        "一条都没命中时返回空列表而不是报错。"
    ),
    "input_schema": {
        "type": "object",
        "properties": {"q": {"type": "string", "description": "检索关键词"}},
        "required": ["q"],
        "additionalProperties": False,      # 关掉多余字段，这是严格模式的前提
    },
}
```

`additionalProperties: False` 不是风格偏好，它是**严格工具调用的两个前提之一**。官方对严格模式的要求是
「所有字段都列进 `required`，且 `additionalProperties` 为 `false`」——两条都满足，模型给出的参数才会与你声明的
schema 逐字一致，而不是「大致一致」。Anthropic 与 OpenAI 都提供这个开关（Claude 侧写在工具定义上，
OpenAI 侧写在 function 对象上）。

严格模式的收益很实在：官方文档写明，参数非法（比如缺必填）时模型会自己纠正并重试 **2–3 次**才放弃；
开了严格模式，这类错误在生成阶段就不出现。代价是**所有参数都变成必填**——如果某个参数你真的希望可选，
就得在 schema 里给它一个明确的取值空间（用 `enum` 或 `anyOf` 表达「要么给，要么给 null」），
而不是靠省略 `required` 来表达。

> ⚠️ **陷阱**：`required` 与实现的默认值不能同时存在。schema 说必填、代码有默认值，等于把校验交给一个
> 永远不会触发的分支；反过来 schema 说可选、代码却直接索引该键，则会在参数缺失时崩在工具内部——
> 而工具内部抛出的异常最容易变成整个请求 500（第 3.5.7 节）。

## 3.5.3 描述是唯一的说明书

模型看不到你的代码，它看到的只有 `description`。官方把这一条排在所有建议之首，并给了具体的写法要求：
**做的什么事、什么时候用、什么时候不该用、每个参数是什么意思、有什么限制**。
这四条里最容易漏的是第三条——「什么时候不该用」。工具之间的混淆几乎都发生在这里：`search_article` 与
`read_article` 都涉及文章，模型怎么知道该用哪个？只有当描述里显式写了「只知道主题时用前者，已经知道 id 时用后者」，
它才有依据。

同一段描述写两版，差别一眼可见：

```text
❌ 一句话：按标签检索文章。

✅ 四条齐全：
按标签检索知舟的文章，返回标题、id 与发布时间。适用于「讲过 X 的文章有哪些」这类按主题归类的
问题；标签是单值字符串而不是关键词列表，且必须与库里已有的标签完全一致——不确定时先用 get_tags
列出可用标签。按 id 精确读取请用 read_article，不要用本工具。
```

写描述时有三条可以照做的规则：

1. **写「何时不用」，并点名隔壁工具。** 消歧的责任在使用方的文档里，不在使用方的智商里。
2. **把返回值写进去。** 模型需要知道这一次调用能拿到什么，才能判断下一步要不要再调一次。
   写成「只返回 id、标题与摘要，不含正文」就足够，比让模型自己试一次便宜得多。
3. **描述里不要写会变的东西。** 具体日期、当前的条数、「本季度」这类表述会随版本漂移，
   而更致命的是它会**打断前缀缓存**（第 3.1.6 节）：工具定义在可缓存前缀里，只要它逐字不变，
   每轮都命中缓存；一旦描述里嵌了时间戳，整段前缀每次都要重算。

描述写完还要过一次版本管理：它是提示的一种，改动会影响行为，所以第 3.2.10 节的「提示是配置，不是常量」
同样适用——把工具描述纳入版本与回归集，改它之前先跑一遍评测用例。

## 3.5.4 工具集：少而厚

一个工具写好了，接下来是「给几个」。直觉是「能力越全越好」，官方的建议恰好相反：
**把相关操作合并成更少的工具**。它举的例子很具体：与其为每个动作各造一个工具
（`create_pr` / `review_pr` / `merge_pr`），不如做成一个带 `action` 参数的工具——
「更少、更强的工具减少选择歧义，也让工具面更好导航」。

这条建议值得信，因为它同时省了两种东西。用一个真实分词器量一遍：

```python
"""工具定义的价格：数量与描述长度各值多少。用真实分词器数。"""
import json

import tiktoken

enc = tiktoken.get_encoding("o200k_base")
n = lambda s: len(enc.encode(s))                                    # noqa: E731

TASK = "帮我找一篇讲 JWT 刷新令牌的文章，读一遍，然后说清它给了几种做法。"


def T(name: str, desc: str, props: dict, required: list[str]) -> dict:
    return {"name": name, "description": desc,
            "input_schema": {"type": "object", "properties": props, "required": required}}


BRIEF = "按关键词检索知舟的文章。"
DETAIL = ("按关键词检索知舟的历史文章，返回标题、id 与发布时间。适用于需要按主题找文章的场景，"
          "例如用户问「有没有讲过 X 的文章」；不适合按 id 精确读取（用 read_article），"
          "也不适合列出全部文章（用 articles 的 mode=recent）。查询词用中文，支持短语，"
          "结果按相关度倒序、最多 20 条。一条都没命中时返回空列表而不是报错，"
          "你应该据此换词再试或换工具。")

SEARCH_B = T("search_article", BRIEF, {"q": {"type": "string", "description": "检索词"}}, ["q"])
SEARCH_D = T("search_article", DETAIL, {"q": {"type": "string", "description": "检索词"}}, ["q"])
READ_B = T("read_article", "读一篇文章的正文。", {"article_id": {"type": "integer"}}, ["article_id"])
READ_D = T("read_article", "读一篇文章的完整正文。适用于已经知道 id、要看内容细节的场景；"
                           "只返回标题与摘要时不要用它，用 search_article。正文超过 2,000 字会被截断。",
           {"article_id": {"type": "integer", "description": "文章 id，正整数"}}, ["article_id"])
BRIEF6 = [SEARCH_B, READ_B,
          T("search_by_tag", "按标签检索文章。", {"tag": {"type": "string"}}, ["tag"]),
          T("list_articles", "列出文章。", {}, []),
          T("recent_articles", "列出最近发布的文章。", {}, []),
          T("count_articles", "统计文章数。", {}, [])]
DETAIL6 = [SEARCH_D, READ_D,
           T("search_by_tag", "按标签检索知舟的文章，返回标题、id 与发布时间。适用于「讲过 X 的文章有哪些」"
                              "这类按主题归类的问题；标签是单值字符串而不是关键词列表，"
                              "且必须与库里已有的标签完全一致。", {"tag": {"type": "string"}}, ["tag"]),
           T("list_articles", "列出知舟的文章，按发布时间倒序，最多 50 条，只返回 id、标题与摘要，不含正文。"
                              "用于「最近写了什么」这类浏览需求；要正文请再用 read_article 按 id 读。", {}, []),
           T("recent_articles", "列出最近发布的知舟文章，最多 20 条，只返回 id、标题与发布时间，不含正文。"
                                "与 list_articles 的区别是它只按时间取最新的几篇，不接受分页参数。", {}, []),
           T("count_articles", "返回知舟的文章总数，一个整数，不含任何正文或标题。用于「一共写了多少篇」"
                               "这类计数问题；不要用它来列举文章。", {}, [])]
ARTICLES = T("articles", "按条件列出知舟的文章：可按标签、按发布时间、或只要总数。",
             {"mode": {"type": "string", "enum": ["by_tag", "recent", "count"]},
              "tag": {"type": "string"}}, ["mode"])
THREE = [SEARCH_D, READ_D, ARTICLES]


def cost(tools: list[dict]) -> int:
    return n(json.dumps(tools, ensure_ascii=False)) if tools else 0


print(f"任务提示本体：{n(TASK)} 词元\n")
print(f"{'配置':<24}{'工具数':>6}{'词元/轮':>9}{'20 轮':>9}")
for label, tools in [("无工具", []), ("2 个，一句话描述", [SEARCH_B, READ_B]),
                     ("2 个，详细描述", [SEARCH_D, READ_D]),
                     ("6 个，一句话描述", BRIEF6), ("6 个，详细描述", DETAIL6),
                     ("3 个，合并后仍详细", THREE)]:
    per = cost(tools)
    print(f"{label:<24}{len(tools):>6}{per:>9}{per * 20:>9}")

six, three = cost(DETAIL6), cost(THREE)
print(f"\n六变三：{six} → {three} 词元/轮（−{six - three}，20 轮 −{(six - three) * 20}），描述一个字没少")
print(f"一句话变详细：{cost([SEARCH_B])} → {cost([SEARCH_D])} 词元（+{cost([SEARCH_D]) - cost([SEARCH_B])}）")
```

输出：

```text
任务提示本体：29 词元

配置                         工具数     词元/轮     20 轮
无工具                          0        0        0
2 个，一句话描述                    2      112     2240
2 个，详细描述                     2      268     5360
6 个，一句话描述                    6      269     5380
6 个，详细描述                     6      594    11880
3 个，合并后仍详细                   3      354     7080

六变三：594 → 354 词元/轮（−240，20 轮 −4800），描述一个字没少
一句话变详细：61 → 166 词元（+105）
```

四行结论，每一行都能当决策依据：

- **工具定义比任务本身贵得多。** 提问 29 词元，六个详述工具 **594 词元**——说明书是问题的 20 倍。
  3.1.5 引的官方实测「工具定义特别贵」在这里有了知舟自己的数字。
- **「6 个一句话」与「2 个详细」差不多贵**（269 对 268）。这是个很实用的等式：
  把描述砍成一句话，省下的钱刚好等于「多写四个工具」的代价——也就是说，
  **靠省略描述来省钱，换来的只有更差的选择**。
- **合并才是那个真正便宜的杠杆。** 六个细工具变三个，594 → 354 词元（−40%），20 轮省 4,800 词元，
  而描述一个字都没短。
- **描述本身很便宜。** 从一句话到四条齐全，+105 词元/轮。相对它带来的选择正确率，
  这是全书性价比最高的一笔开销。

工具集还有两个不能忘的性质。

**它是权限面。** 模型能做什么，等于你给了它哪些工具。所以工具集要按**最小权限**设计：
发布上线这类不可逆动作，要么不给模型，要么给一个必须经过人工确认的包装（第 3.8 节展开）。
「读文章」与「发文章」分成两个工具，不只是为了描述清楚，也是为了能给它们**不同的授权档**。

**它随用户走。** 工具集不是一个全局常量，它是「这个用户在这个会话里被允许做的事」。
第 3.5.10 节的做法是按会话构造注册表：同一个 `build(user_id)`，换个人就是另一套工具集。

> 💡 **提示**：工具数量还有一个上限之外的问题——**工具太多时选择本身就变难**。
> 官方的应对是「工具搜索」：把不常用的工具延迟加载，用到时才进上下文。
> 这与 2.5 的「渐进式披露」是同一个思路。但你不需要一开始就上这套机制：
> 先按「合并相关操作」把数量压下来，压不动了再考虑按需加载。

## 3.5.5 参数：模型给的是建议，不是可信输入

参数从模型到工具要过四道关，顺序不能换：

| 关卡 | 问题 | 例子 |
| --- | --- | --- |
| ① schema 校验 | 形状对不对 | `article_id` 是 `"42"` 还是 `42` |
| ② 业务校验 | 值合不合理 | id 不存在、正文超长、标签库里没有 |
| ③ 授权 | 这个用户能不能碰它 | 43 号文章属于别人 |
| ④ 幂等 | 重跑会不会写两遍 | 同一份草稿被创建两次 |

前三道都不该写在工具实现里。**工具的职责是干活，不是过滤坏输入**——把它塞进实现，就等于让每个新增工具
都要重复写一遍同样的检查，而漏掉的那一个不会报错，只会在某天写错数据。用一批真实会出现的坏调用量一下：

```python
"""参数校验拦下什么，拦不住什么。12 个候选调用：4 个合法 + 8 类坏法。"""
import json
from dataclasses import dataclass

SCHEMAS = {
    "search_article": {"required": ["q"], "props": {"q": ("string", None)}},
    "read_article": {"required": ["article_id"],
                     "props": {"article_id": ("integer", (1, None))}},
    "articles": {"required": ["mode"],
                 "props": {"mode": ("enum", ["by_tag", "recent", "count"]),
                           "tag": ("string", None)}},
}


@dataclass(frozen=True)
class Problem:
    kind: str
    detail: str

    def message(self) -> str:
        return f"{self.kind}：{self.detail}"


def validate(name: str, args: dict) -> list[Problem]:
    schema = SCHEMAS.get(name)
    if schema is None:
        return [Problem("未知工具", f"没有注册名为 {name} 的工具")]
    out = [Problem("缺必填", f"{k} 未提供") for k in schema["required"] if k not in args]
    for key, value in args.items():
        rule = schema["props"].get(key)
        if rule is None:
            out.append(Problem("多出字段", f"{key} 不在 schema 里"))
            continue
        kind, (rng, _) = rule[0], (rule[1], None)
        if kind == "string" and not isinstance(value, str):
            out.append(Problem("类型错", f"{key} 应为 string，实为 {type(value).__name__}"))
        elif kind == "integer" and (isinstance(value, bool) or not isinstance(value, int)):
            out.append(Problem("类型错", f"{key} 应为 integer，实为 {type(value).__name__}"))
        elif kind == "enum" and value not in rule[1]:
            out.append(Problem("枚举越界", f"{key}={value!r} 不在 {rule[1]} 里"))
        if isinstance(value, int) and rng and value < rng:
            out.append(Problem("范围越界", f"{key}={value} 小于下限 {rng}"))
    return out


CALLS = [
    ("search_article", {"q": "刷新令牌"}),
    ("read_article", {"article_id": 42}),
    ("articles", {"mode": "recent"}),
    ("articles", {"mode": "by_tag", "tag": "安全"}),
    ("read_article", {"article_id": "42"}),
    ("read_article", {}),
    ("read_article", {"article_id": 0}),
    ("read_article", {"article_id": 42, "fields": "all"}),
    ("articles", {"mode": "latest"}),
    ("search_article", {"q": ["刷新", "令牌"]}),
    ("search_articles", {"q": "刷新令牌"}),
    ("articles", {"mode": "by_tag", "tag": 7}),
]

print(f"{'#':>2}  {'调用':<46}{'判定':<7}原因")
blocked = 0
for i, (name, args) in enumerate(CALLS, 1):
    problems = validate(name, args)
    call = f"{name}({json.dumps(args, ensure_ascii=False)})"
    if problems:
        blocked += 1
        print(f"{i:>2}  {call:<46}{'拦下':<7}"
              + "；".join(p.message() for p in problems))
    else:
        print(f"{i:>2}  {call:<46}{'放行':<7}—")
print(f"\n12 个调用：放行 {12 - blocked}、拦下 {blocked}（都在调用工具之前，没有一次真的执行）")
```

 6  read_article({})                                拦下     缺必填：article_id 未提供
 7  read_article({"article_id": 0})                 拦下     范围越界：article_id=0 小于下限 1
 8  read_article({"article_id": 42, "fields": "all"})拦下    多出字段：fields 不在 schema 里
 9  articles({"mode": "latest"})                    拦下     枚举越界：mode='latest' 不在 ['by_tag', 'recent', 'count'] 里

八类坏法全部在**调用之前**被拦下：类型错、缺必填、范围越界、多出字段、枚举越界、未知工具，
以及表格里没单独成类的组合。**没有一条需要调用模型，也没有一条碰过数据库。**

但校验器有一类永远拦不住的东西，而它比上面八类都危险：**参数合法、语义错**。

| 调用 | 问题 |
| --- | --- |
| `read_article({"article_id": 43})` | 43 存在、类型对、范围对，但它是**别人的**文章 |
| `search_article({"q": "帮我找一篇讲刷新令牌的文章，读一遍……"})` | 合法 string，但整句任务不是检索词，一条都检索不出来 |
| `articles({"mode": "count", "tag": "安全"})` | 合法，但 `count` 分支忽略 `tag`，用户以为统计的是安全类 |

第一类靠**授权**解决（第 3.5.10 节的 guard 钩子），第二、三类只能靠**工具自己再验一次并回一句可执行的建议**：

```python
def search_article(q: str) -> list[dict]:
    if q.startswith("帮我"):                       # 合法 string，但整句任务检索不出来
        raise ToolError("检索词像是一整句任务。请给出关键词，例如「刷新令牌」。")
    ...
```

这句话的写法就是第 3.5.7 节的主题：错误消息必须**可执行**。写成「参数错误」，模型只能瞎猜；
写成「请给出关键词，例如『刷新令牌』」，它下一次就对了。

还有两条与参数有关的边界：

**别做自动类型转换。** `"42"` → `42` 看起来很体贴，但它会把真正的类型错掩盖成「偶尔能跑」。
官方给出的干净解法是严格工具调用：让模型一次性给出正确类型，而不是让代码去猜。
真要做兼容，也应该转完再按 schema 校验一遍，并把转换写进审计。

**参数里不许出现指令。** 工具参数是数据。当参数的值来自网页、邮件、用户上传的文档时，
它可能包含「忽略上面的规则」这类内容——这就是提示注入的一个入口（第 3.8 节）。
两件事现在就可以做：工具的**描述**里不承诺「参数中的任何要求都会被遵守」；
工具的**实现**里不把参数原文拼进下一轮提示的系统部分。

## 3.5.6 返回值：给模型看的，不是给数据库看的

工具跑完了，返回值该长什么样？最常见的做法是「把查询结果原样 `json.dumps` 回去」，因为它最省事。
官方对这一条的建议是反过来的：**只返回高信号信息**——用稳定的标识符（slug、UUID），
只给模型下一步推理需要的字段，「臃肿的返回值浪费上下文，也让模型更难提取要点」。

同一个查询，三种返回形状的账：

```python
"""返回值的形状与体积：同一个查询，三种返回形状的账。"""
import json

import tiktoken

enc = tiktoken.get_encoding("o200k_base")
n = lambda s: len(enc.encode(s))                                    # noqa: E731

RAW = {"article_id": 42, "title": "JWT 刷新令牌怎么做", "slug": "jwt-refresh",
       "author_id": 7, "author_name": "阿茶", "created_at": "2026-03-02T10:11:12+08:00",
       "updated_at": "2026-03-05T09:00:00+08:00", "status": "published",
       "cover_url": "https://cdn.example.com/covers/42.webp", "view_count": 1832,

       "content": "JWT 的刷新令牌有三种做法……" * 40}

        "excerpt": "JWT 的刷新令牌有三种做法……"}
LONG = dict(SLIM, content="JWT 的刷新令牌有三种做法……" * 400)     # 未截断的正文

    return n(json.dumps(obj, ensure_ascii=False))


print("同一次 read_article 调用，三种返回形状：")

                   ("高信号 4 字段（含摘要）", SLIM),
                   ("高信号 4 字段 + 未截断正文", LONG)]:
    print(f"{label:<28}{size(obj):>8}{size(obj) * 10:>10}")

print(f"\n一次省 {size(RAW) - size(SLIM)} 词元；10 次省 {(size(RAW) - size(SLIM)) * 10}")
print(f"正文从 480 字涨到 4,800 字：单次 {size(LONG)} 词元，是摘要版的 {size(LONG) / size(SLIM):.0f} 倍")

CAP = dict(SLIM, content="正" * 2_000)
print(f"\n截断到 2,000 字：每篇 {size(CAP)} 词元，读 5 篇 {size(CAP) * 5}")
print(f"不截断：               每篇 {size(LONG)} 词元，读 5 篇 {size(LONG) * 5}")

```

```text

```

三行数字对应三条规则：

1. **只给下一步需要的字段。** 原样 14 字段（588 词元）里至少一半是模型永远不会用的：
   封面图 URL、点赞数、评论数、两个时间戳。裁成高信号 4 字段是 **49 词元**，只有原来的 8%，
   而模型要做的事（判断这篇讲不讲刷新令牌、要不要读全文）一个字段都没少。
2. **给稳定标识符。** `article_id` 与 `slug` 是模型能拿去做下一步的钥匙；
   自增主键之外的内部引用（比如行号、内存地址）没有意义。这条也是官方明说的。
3. **给体积设上限，并在截断处说清楚。** 未截断的 4,800 字正文是摘要版的 **91 倍**——
   一次 `read_article` 就能把预算吃掉一半。上限值本身可以商量（知舟取 2,000 字），
   但**截断之后必须告诉模型发生了什么**：

```text
刷新令牌要解决的问题是：访问令牌必须短期有效……（已截断，原文 3104 字）
```

为什么必须告诉它：如果截断是静默的，模型会以为文章就读到这里，于是给出一个基于前半篇的结论，
而它有理由相信自己已经读完了。加一句「原文 X 字」之后，它至少知道有两种选择——
再调一次取后半段，或者去找另一篇更短的。**静默截断是「看起来成功」的一种**，
与第 3.5.7 节的「返回空字符串」同源。

返回值还有一条比体积更重要的性质：**它也是不可信输入**。工具结果里可能有网页正文、邮件内容、
第三方 API 的字段，而这些都是攻击者可能影响到的位置。官方在这一条上给的措辞很直接：
「把这类内容当作不可信——能影响它的攻击者可能在里面嵌入指令，试图改变模型的行为（间接注入）」；
并给出具体做法：**把不可信内容留在工具结果块里**，不要搬进系统提示或普通的用户文本块。
知舟的做法与之同构：`read_article` 返回的正文只出现在 `tool_result` 里，不进系统提示、不进前缀。

## 3.5.7 失败：分类、可执行消息与可恢复性

工具的失败不是异常，是**一种正常返回值**。官方给了明确的机制：在 `tool_result` 里带上
`is_error: true` 与错误内容，模型会把它纳入后续推理。同时官方给了写错误消息的标准——
**写可执行的错误**：「不要用『failed』这种笼统的说法，说清出了什么错、以及模型接下来该试什么，
例如『限流已触发，60 秒后重试』」。

三种错误返回方式，用同一个极小模型跑三条轨迹，差别很清楚：

```python
"""失败怎么说给模型听：三种返回，三条轨迹。"""
TOOLS = ["search_article", "read_article", "articles"]


def fake_model(step: int, last: dict | None) -> dict | None:
    """极简模型：看到可重试的错就换下一个工具；看到空结果就以为成功。"""
    if last is None:
        return {"tool": "search_article", "args": {"q": "刷新令牌"}}
    if last.get("retry") and step < len(TOOLS):
        return {"tool": TOOLS[step], "args": {"q": "刷新令牌"}}
    return None


def run(kind: str, failing: str = "search_article") -> list[tuple[str, str]]:
    log: list[tuple[str, str]] = []
    step, last = 0, None
    while True:
        call = fake_model(step, last)
        if call is None:
            return log + [("收口", "模型给出最终回答")]
        name = call["tool"]
        if name == failing:
            if kind == "raise":
                raise RuntimeError("工具异常冒到循环外：这一轮请求整体 500")
            if kind == "empty":
                return log + [(name, '返回 ""'), ("收口", "模型把空结果当成答案，直接作答")]
            log.append((name, "is_error=true：搜索服务未响应，可换 read_article 按 id 取，或稍后重试"))
            last = {"retry": True}
        else:
            log.append((name, "正常返回：命中 3 条"))
            last = {}
        step += 1
        if step > len(TOOLS) + 1:
            return log + [("放弃", "没有进展，触发步数上限")]


for kind, label in [("raise", "① 抛异常：异常冒到循环外"),
                    ("empty", "② 返回空字符串：看着像成功"),
                    ("is_error", "③ is_error=true ＋ 说清怎么补救")]:
    print(f"\n{label}")
    try:
        for i, (who, what) in enumerate(run(kind), 1):
            print(f"   {i}. {who:<16}{what}")
    except RuntimeError as exc:
        print(f"   ✗ 循环在这里断掉：{exc}")
```

输出：

```text
① 抛异常：异常冒到循环外
   ✗ 循环在这里断掉：工具异常冒到循环外：这一轮请求整体 500

② 返回空字符串：看着像成功
   1. search_article  返回 ""
   2. 收口              模型把空结果当成答案，直接作答

③ is_error=true ＋ 说清怎么补救
   1. search_article  is_error=true：搜索服务未响应，可换 read_article 按 id 取，或稍后重试
   2. read_article    正常返回：命中 3 条
   3. 收口              模型给出最终回答
```

三条轨迹的分野值得逐条说：

- **抛异常最糟，而且它最容易发生。** 工具内部没接住的异常会冒到循环外，把一次本可以自愈的失败
 变成整个请求 500。修法不是「多写 `try`」，而是**在注册表这一层统一收口**：
  工具只允许抛出一种自己的错误类型，注册表把它转成 `ToolResult(ok=False, ...)`，
  其他异常则按「工具实现有 bug」记录并同样转成失败结果。
- **返回空字符串是一种假成功。** 它不报错，模型于是把「没找到」当成「没有相关文章」——
  这是 3.3 讲过的「无新事实」在工具层的版本。空结果要么算失败，要么必须在返回值里显式区分：
  返回 `[]` 并说明「0 条命中，可换关键词」，而不是返回 `""`。
- **`is_error` 把失败变成下一步。** 模型看到「可换 read_article 按 id 取」之后真的换了工具，
  第三次就收口了。这就是「可执行错误」的价值：一句建议省掉一整轮试探。

错误消息要可执行，意味着它得包含三样东西：**出了什么错**（原因）、**能不能再试**（可恢复性）、
**下一步可以做什么**（建议）。第二样要同时出现在两个地方：给模型看的文字里，
以及给你的循环看的结构化字段里——因为**是否重试是编排层的决定，不是模型的决定**：

| 失败 | 可重试 | 循环该怎么做 |
| --- | --- | --- |
| 网络超时、连接被重置、限流 429 | 是 | 指数退避重试，设次数上限（第 3.2 节的分类直接复用） |
| 服务端 5xx、依赖不可用 | 是 | 重试；连续失败则降级到备用工具或告知用户 |
| 参数错、枚举越界、类型错 | 否 | 不要重试；把错误原文回给模型让它改参数 |
| 授权失败、越权、缺少确认 | 否 | 不重试，且**不要**把「怎么绕过」写进错误消息 |
| 工具实现抛出的未知异常 | 不确定 | 当作不可重试，同时记一条要人工看的日志 |

最后一行是本书加的：未知异常**不该**被当成可重试。重试一个因为代码 bug 而失败的操作，
只会把同一个 bug 跑三遍。

格式上还有两条硬要求，都来自官方文档，写错了会被 API 直接拒掉（400）：

1. **每条 `tool_use` 都要有一条配对的 `tool_result`。** 如果你出于某种原因没有执行它
   （比如批次里前一个失败了就停下），**仍然要回一条结果**，标上 `is_error: true` 与一句说明，
   例如「未执行：前一个写操作失败」。
2. **结果块必须紧跟对应的调用块。** 中间不能插入别的消息；在同一轮的所有结果里，
   `tool_result` 块要排在内容数组的**最前面**，文本放在其后。

## 3.5.8 并行与顺序：一次响应里的多个调用

模型一次响应里可以给出**多个**调用。官方对此的表述是：这很常见，而且**执行顺序由你决定**——
「你可以并发跑（`asyncio.gather`），也可以按出现顺序串行，或者任意组合」。
并行的收益是墙钟，而能不能并行有两条判据：

```python
"""一个响应里多个调用：什么时候能并行。"""
COST = {"search_article": 0.8, "read_article": 0.6, "articles": 0.4,
        "create_draft": 0.5, "update_article": 0.5}
SIDE_EFFECT = {"create_draft", "update_article", "delete_article"}


def sync_time(calls: list[tuple[str, dict]]) -> float:
    return round(sum(COST[name] for name, _ in calls), 1)


def parallel_time(calls: list[tuple[str, dict]]) -> float:
    return round(max(COST[name] for name, _ in calls), 1)


def can_batch(calls: list[tuple[str, dict]]) -> tuple[bool, str]:
    """并行的两个前提：全都无副作用；没有谁的参数依赖别人的结果。"""
    for name, args in calls:
        if name in SIDE_EFFECT:
            return False, f"{name} 有副作用"
        if any(str(v).startswith("$") for v in args.values()):
            return False, "参数引用了别的调用的结果"
    return True, "全是独立只读"


CASES = [
    ("三个独立只读", [("search_article", {"q": "刷新令牌"}),
                       ("articles", {"mode": "recent"}),
                       ("articles", {"mode": "count"})]),
    ("两个写操作", [("create_draft", {"article_id": 42}),
                    ("update_article", {"article_id": 42})]),
    ("一个写、一个读它刚建的草稿", [("create_draft", {"article_id": 42}),
                                    ("read_article", {"article_id": "$draft.id"})]),
]

print(f"{'情形':<28}{'判定':<9}{'顺序':>7}{'并行':>7}  依据")
for label, calls in CASES:
    ok, why = can_batch(calls)
    print(f"{label:<28}{'可并行' if ok else '必须顺序':<9}"
          f"{sync_time(calls):>6.1f}s{(parallel_time(calls) if ok else sync_time(calls)):>6.1f}s  {why}")

head = CASES[0][1]
print(f"\n三个只读：顺序 {sync_time(head)}s → 并行 {parallel_time(head)}s，"
      f"省 {sync_time(head) - parallel_time(head)}s")
print("但并行的前提是「每个调用都拿到了结果」——少回一条，下一轮请求会被 API 直接拒掉。")
```

输出：

```text
情形                          判定            顺序     并行  依据
三个独立只读                      可并行          1.6s   0.8s  全是独立只读
两个写操作                       必须顺序         1.0s   1.0s  create_draft 有副作用
一个写、一个读它刚建的草稿               必须顺序         1.1s   1.1s  create_draft 有副作用

三个只读：顺序 1.6s → 并行 0.8s，省 0.8s
但并行的前提是「每个调用都拿到了结果」——少回一条，下一轮请求会被 API 直接拒掉。
```

两条判据是**都满足**才并行：

- **没有副作用。** 两个写操作并行跑不是优化，是竞态：`update` 可能比 `create` 先落库。
  官方对需要顺序的工具（比如电脑操作类工具集）给的规则更严：**按出现顺序串行跑，遇到第一个失败就停**。
- **参数不依赖别人的结果。** 参数里出现 `$draft.id` 这种引用，就说明这一步在等上一步——
  它必须顺序，与有没有副作用无关。

还有一个只在并行时才会踩的格式坑，官方专门列在了「排查」一节：**把多条结果拆成多条 `user` 消息**。
正确的做法是**所有 `tool_result` 放在同一条 `user` 消息里**。这不是风格问题——官方解释得很清楚，
错误的格式会「教」模型不再并行：它会学到并行没用，于是退回一次一个。

反过来，要**关掉**并行也有开关：Claude 侧是 `tool_choice` 里的 `disable_parallel_tool_use`，
OpenAI 侧是 `parallel_tool_calls`（设为 `false` 即「恰好零或一次调用」）。
什么时候该关：工具之间有隐含顺序、写操作占多数、或者你还没做好一致性处理的时候。
**并行省下的墙钟，换不回一次写错的数据。**

## 3.5.9 编排：链、扇出、分支与终止

到这里，单个调用已经完整了。把多个调用串起来就是**编排**——也是本章标题的后半截。
先划清与 3.4 的边界：**3.4 决定「做什么」，本节决定「怎么调」**。计划里写「检索→核对→起草」，
这是 3.4 的事；而「这三步各用哪个工具、能不能并行、失败了退到哪儿」，是本节的事。

四种形状覆盖了绝大多数场景：

| 形状 | 结构 | 何时用 | 失败时怎么办 |
| --- | --- | --- | --- |
| 链式 | A → B → C，一步的输出是下一步的输入 | 步骤有严格依赖 | 从失败那一步重试；前面的结果还能用（第 3.4 节的分层计划） |
| 扇出–聚合 | A → (B1 ‖ B2 ‖ B3) → 合并 | 子任务独立、可并行 | 单个失败只重跑那一个；聚合时标注缺哪一路 |
| 条件分支 | 看 A 的结果决定走 B 还是 C | 分支条件能程序化判断 | 判断逻辑写在代码里，不要写在提示里 |
| 循环 | 重复调直到终止条件成立 | 需要多轮探索 | 三条终止口径必须都在（第 3.3 节） |

四者可以叠加，但叠加时会遇到一个用一次就够的教训：**编排的复杂度应该加在代码里，不要加在工具的粒度上**。
把「检索 + 核对 + 起草」做成三个工具再由提示告诉模型「必须按这个顺序调」，远不如做成一个链式的函数
——因为顺序是确定的事，确定的事就该由代码保证，而不是靠模型记得住。

编排还有两个只能在编排层解决的问题。

**第一是幂等性。** 重试是编排的常态动作，所以每个工具都要能回答「重跑一次会怎样」：

| 工具类型 | 例子 | 重跑的安全性 |
| --- | --- | --- |
| 纯读 | `search_article` / `read_article` | 安全，随便重试 |
| 可撤销写 | `create_draft` | 需要幂等键：同一键只写一次 |
| 不可逆写 | `publish_article` / 转账 / 发邮件 | **不能靠重试解决**；要么幂等键 + 状态检查，要么人工确认 |

第三行是编排里最容易出事的地方。一个已经成功的「发布」如果因为超时被判为失败并重跑，
用户可能会看到两次发布。所以对不可逆操作的编排规则是：**先查状态，再决定动作**——
重试前先问「它是不是已经完成了」，而不是直接把请求再发一遍。

**第二是「谁来汇总」。** 扇出之后必然要聚合，而聚合点是最容易被写坏的地方：
把三路结果拼成一段文本交给模型，和把三路结果结构化地放进一条消息，效果与账单都不同。
知舟的做法是把聚合写在工具侧：`articles(mode=count)` 返回一个整数，而不是让模型自己去数一个列表——
**能让代码算的，不要交给模型算**，这条在成本与正确率上都成立。

最后是一条反向的经验：**能用一个工具做完的，不要拆成三步**。
每多一次往返就多一次模型调用（第 3.3 节的账：固定前缀每轮都要重发），
而中间多出来的每个「中间结论」都是一个新的出错点。编排的价值在于**必要的**顺序与并行，
不在于把简单事情拆开显得完整。

```python
# app/agent/tools/registry.py —— 注册表：定义、校验、授权、幂等、裁剪
"""知舟的工具注册表：一处定义、一处校验、一处调用。

三个约束都落在同一个文件里，因为它们是同一件事的三面：
  · 给模型看的 schema 与实现必须同源，否则说明书写着必填、代码却有默认值；
  · 参数在调用工具**之前**校验，工具的职责是干活，不是过滤坏输入；
  · 写操作必须带幂等键——重试与并行是常态，重跑不能变成重复写入。
"""
from __future__ import annotations

import json
from collections.abc import Callable
from dataclasses import dataclass, field
from typing import Any

READONLY, WRITE = "readonly", "write"
MAX_RESULT_CHARS = 2_000        # 单条工具结果的体积上限（第 3.5.6 节）


@dataclass(frozen=True)
class Problem:
    """参数问题：kind 用来分类报账，detail 用来回给模型（第 3.5.7 节）。"""

    kind: str
    detail: str

    def message(self) -> str:
        return f"{self.kind}：{self.detail}"


@dataclass
class ToolResult:
    ok: bool
    data: Any = None
    error: str = ""
    retryable: bool = False

    def payload(self) -> str:
        """回给模型的那一段文本：成功给数据，失败给可执行的建议，绝不截断成空。"""
        body = self.error if not self.ok else json.dumps(self.data, ensure_ascii=False)
        if len(body) > MAX_RESULT_CHARS:
            body = body[:MAX_RESULT_CHARS] + f"……（已截断，原文 {len(body)} 字）"
        return body


class ToolError(Exception):
    """工具自己抛的错。retryable 为真表示「可以再试」，否则「别试了，换方法」。"""

    def __init__(self, message: str, *, retryable: bool = False) -> None:
        super().__init__(message)
        self.message, self.retryable = message, retryable


@dataclass
class Tool:
    name: str
    description: str
    schema: dict
    access: str
    handler: Callable[..., Any]
    guard: Callable[..., None] | None = None      # 授权：只读参数，绝不碰数据

    def spec(self) -> dict:
        """给模型看的定义（规范形）。additionalProperties=False 与 required 齐全，才开得了严格模式。"""
        return {"name": self.name, "description": self.description,
                "input_schema": {**self.schema, "additionalProperties": False}}


@dataclass
class Registry:
    tools: dict[str, Tool] = field(default_factory=dict)
    executed: list[str] = field(default_factory=list)   # 记账：每次真的执行了什么
    audit: list[str] = field(default_factory=list)      # 被拒的调用也要留痕（第 3.8 节）
    _seen: dict[str, ToolResult] = field(default_factory=dict)

    def add(self, tool: Tool) -> Tool:
        if tool.name in self.tools:
            raise ValueError(f"工具名重复：{tool.name}")
        self.tools[tool.name] = tool
        return tool

    def specs(self) -> list[dict]:
        return [t.spec() for t in self.tools.values()]

    def validate(self, name: str, args: dict) -> list[Problem]:
        t = self.tools.get(name)
        if t is None:
            return [Problem("未知工具", f"没有注册名为 {name} 的工具")]
        props, required = t.schema.get("properties", {}), t.schema.get("required", [])
        out = [Problem("缺必填", f"{k} 未提供") for k in required if k not in args]
        for k, v in args.items():
            rule = props.get(k)
            if rule is None:
                out.append(Problem("多出字段", f"{k} 不在 schema 里"))
            else:
                out += _check(k, v, rule)
        return out

    def call(self, name: str, args: dict, *, idem: str | None = None,
             allow_write: bool = False) -> ToolResult:
        """唯一入口。顺序固定：校验 → 授权 → 权限档 → 幂等 → 执行。"""
        t = self.tools.get(name)
        if probs := self.validate(name, args):
            result = ToolResult(False, error="；".join(p.message() for p in probs))
        elif t.guard is not None and (denied := _run_guard(t.guard, args)) is not None:
            result = ToolResult(False, error=denied)
        elif t.access == WRITE and not allow_write:
            result = ToolResult(False, error=f"权限不足：{name} 是写操作，本轮未获授权")
        elif t.access == WRITE and not idem:
            result = ToolResult(False, error=f"缺少幂等键：重复调用 {name} 会写入两次")
        elif t.access == WRITE and idem in self._seen:
            return self._seen[idem]                     # 重跑返回第一次的结果，不重复写
        else:
            self.executed.append(name)
            try:
                result = ToolResult(True, data=t.handler(**args))
            except ToolError as exc:
                result = ToolResult(False, error=exc.message, retryable=exc.retryable)
        if not result.ok:
            self.audit.append(f"{name}({json.dumps(args, ensure_ascii=False)}) → {result.error}")
        elif t.access == WRITE and idem:
            self._seen[idem] = result
        return result


def _run_guard(guard: Callable[..., None], args: dict) -> str | None:
    """授权钩子：通过返回 None，拒绝返回一句可执行的说明。它只能看参数。"""
    try:
        guard(**args)
    except ToolError as exc:
        return exc.message
    return None


def _check(key: str, value: Any, rule: dict) -> list[Problem]:
    kind = rule.get("type")
    if kind == "string" and not isinstance(value, str):
        return [Problem("类型错", f"{key} 应为 string，实为 {type(value).__name__}")]
    if kind == "integer" and (isinstance(value, bool) or not isinstance(value, int)):
        return [Problem("类型错", f"{key} 应为 integer，实为 {type(value).__name__}")]
    if "minimum" in rule and isinstance(value, int) and value < rule["minimum"]:
        return [Problem("范围越界", f"{key}={value} 小于下限 {rule['minimum']}")]
    if "enum" in rule and value not in rule["enum"]:
        return [Problem("枚举越界", f"{key}={value!r} 不在 {rule['enum']} 里")]
    return []
```

"""把知舟自己的能力变成 6 个工具：4 个只读、2 个写。

"""

from app.agent.tools.registry import READONLY, WRITE, Registry, Tool, ToolError

    "代价是两个标签页同时刷新时，后到的那个拿着已作废的令牌，会被判成盗用；"
    "工程上常给旧令牌留一个很短的宽限窗口。",
    "做法二，黑名单：刷新令牌长期有效，退出或检测到异常时把它的 jti 写进 Redis，"
    "TTL 设为令牌剩余寿命即可。代价是每次刷新多一次查询，黑名单一丢数据撤销就失效。",
    "做法三，版本号：用户表上存 token_version，签发时写进声明，校验时比对；"
    "改密码或强制下线就把版本号加一，该用户所有旧令牌立刻失效。"
    "代价是做不到只踢单台设备。",
    "三种做法可以叠用：滑动过期覆盖常态，版本号覆盖一键下线，"
    "黑名单只留给需要精确到单枚令牌的场景。",
    "边界一：刷新端点必须校验 aud/typ，不能接受访问令牌来换新令牌，"
    "否则等于把短期凭证升级成长期凭证。",
    "边界二：刷新令牌只走 HTTPS，不要放在 URL 里；浏览器端优先 HttpOnly Cookie。",
    "边界三：日志里不要打印令牌本体，只打印 jti 与用户 id。",
]
BODY_OF = {42: "\n\n".join(_SECTIONS * 6)}   # 约 3 千字：读回来会被 2,000 字符的上限截断（3.5.6）


def _own(article_id: int, user_id: int) -> None:
    """授权钩子：只读参数与作者表，不碰正文。schema 管得了类型，管不了「这是谁的文章」。"""
    if article_id not in OWNER_OF:
        raise ToolError(f"文章 {article_id} 不存在。可先用 articles(mode=recent) 取 id。")
    if OWNER_OF[article_id] != user_id:
        raise ToolError(f"文章 {article_id} 不属于你，无权读写。")


def build(user_id: int, store: dict | None = None) -> Registry:
    """按会话构造注册表：工具集就是权限面，所以它随用户走。"""
    store = store if store is not None else {}

    def search_article(q: str) -> list[dict]:
        if q.startswith("帮我"):                       # 合法 string，但整句任务检索不出来
            raise ToolError("检索词像是一整句任务。请给出关键词，例如「刷新令牌」。")
        # **结果必须随查询词变化**。第一版不问查什么都返回同一篇，于是「换个说法的第二次检索」
        # 在观察层看就是「没有新事实」——循环当场判卡死，而卡住的是夹具不是模型。
        # 3.9 的评测集第一次真机跑就是 0/3，查下来的原因在这里。
        words = [w for w in re.split(r"[\s，,。、；;]+", q) if w]
        hits = [{"article_id": 42, "title": "JWT 刷新令牌怎么做", "tags": ["安全", "后端"]}]
        return [h for h in hits
                if any(w in h["title"] or w in "".join(h["tags"]) for w in words)]

    def read_article(article_id: int) -> dict:
        return {"article_id": article_id, "title": "JWT 刷新令牌怎么做",
                "body": BODY_OF.get(article_id, "正文")}

    def articles(mode: str, tag: str | None = None) -> list[dict] | int:
        if mode == "count":
            return 128
        rows = [{"article_id": 42, "title": "JWT 刷新令牌怎么做", "tags": ["安全", "后端"]}]
        return [r for r in rows if tag in r["tags"]] if mode == "by_tag" else rows

    def get_tags() -> list[str]:
        return ["安全", "后端", "JWT", "部署"]

    def create_draft(article_id: int, body: str) -> dict:
        store["draft"] = {"article_id": article_id, "body": body, "status": "draft"}
        return dict(store["draft"])

    def publish_article(article_id: int) -> dict:
        if "draft" not in store:
            raise ToolError("还没有草稿可发布。先调 create_draft，发布是不可逆操作。")
        store["draft"]["status"] = "published"
        return dict(store["draft"])

    r = Registry()
    r.add(Tool(
        "search_article",
        "按关键词检索知舟的历史文章，返回文章 id、标题与标签。适用于「有没有讲过 X 的文章」"
        "这类按主题找文章的问题；查询词给关键词而不是整句话。要正文请拿到 id 后调 read_article。"
        "一条都没命中时返回空列表而不是报错。",
        {"type": "object", "properties": {"q": {"type": "string", "description": "检索关键词"}},
         "required": ["q"]}, READONLY, search_article))
    r.add(Tool(
        "read_article",
        "按 id 读一篇知舟文章的正文；正文超过 2,000 字会被截断并注明原文长度。适用于已经知道 id、"
        "要看内容细节的场景；只知道主题时先用 search_article 拿 id。",
        {"type": "object", "properties": {"article_id": {"type": "integer", "minimum": 1,
                                                         "description": "文章 id，正整数"}},
         "required": ["article_id"]}, READONLY, read_article,
        guard=lambda article_id: _own(article_id, user_id)))
    r.add(Tool(
        "articles",
        "按条件列出知舟的文章：mode=by_tag 按标签列（需给 tag）、mode=recent 按发布时间倒序取最新 20 条、"
        "mode=count 只返回总数。用于浏览与计数；要正文请再用 read_article。",
        {"type": "object", "properties": {"mode": {"type": "string",
                                                   "enum": ["by_tag", "recent", "count"]},
                                          "tag": {"type": "string", "description": "标签，by_tag 时必填"}},
         "required": ["mode"]}, READONLY, articles))
    r.add(Tool(
        "get_tags",

五段输出里有四件事值得指出来：

- **参数与授权在同一个入口拦下，而工具一次都没被执行。** 越权读（43 号是别人的）、范围越界（0）、
  类型错（`"42"`）、枚举越界（`latest`）四条全部停在 `Registry.call` 里，
  `reg.executed` 是空的——这就是「工具的职责是干活」的机器可查形式。
- **写操作有两道闸，缺一不可。** 没有授权档时拒，有授权但没幂等键时也拒；
  带同一个幂等键跑两次，`create_draft` 只被执行了 **1** 次。这里的键是**循环生成的**，
  不是模型给的（第 3.5.5 节的边界）——模型可以不给键，但你不能不生成。
- **体积上限是“回给模型的量”，不是“查出来的量”。** 原文 3,104 字符裁到 2,017，
  且裁完仍能告诉模型原文多长。
- **被拒的调用进了审计。** 这六行在第 3.8 节会变成「越权尝试的频率」这种指标，
  而它们之所以存在，只是因为 `call` 在拒绝时也记了一笔。

### 不能破坏什么

- **不新增端点、不改既有表**：工具集是循环内部的替换，`/agent/chat` 的请求与响应一字不动；
  自查：跑 3.3 的循环测试与 1.14 的测试套，全绿才算数。
- **工具集不越过用户的权限面**：`_own` 在**取数据之前**判越权，所以“别人文章存在但你看不到”这件事
  不会以“文章不存在”的形式漏给模型；同理，写操作默认不授权（`allow_write=False`）。
- **幂等键只由循环生成**：它不出现在任何工具的 schema 里。一旦把键交给模型，
  重试时它可能给出不同的键，于是“重跑只写一次”这道闸就形同虚设。
- **审计里不落正文**：`audit` 只记工具名、参数与错误原因；参数中的 `body` 要截断成 `…` 长度后记，
  不记原文（与 3.4 的追踪口径一致，脱敏规则在第 3.8 节）。
- **返回值体积上限只有一处**：`MAX_RESULT_CHARS` 只在 `registry.py` 定义，工具自己不截断——
  否则每个新增工具都得记得带一次上限，漏掉的那个不会报错，只会把预算吃掉。

## 常见坑

1. **把工具描述写成「给人看的文档」。**
   现象：功能列得很全，模型却在明显不该用的时候调它，或者该用的时候不用。
   原因：描述里只有「这个工具能干什么」，没有「什么时候该想起它、什么时候不要」。
   修法：每一段描述都回答两个问题——**何时用**（典型问题长什么样）、**何时不用**（该找谁）。
   3.5.3 的对照实验里，只改描述不改 schema，工具选择的正确率就动了。
2. **用 schema 表达业务约束。**
   现象：把「只能操作自己的文章」写进参数说明，甚至想用 `enum` 把当前用户的文章 id 列进去。
   原因：把「格式约束」与「归属约束」当成了一类东西。schema 是给模型看的说明书，不是访问控制。
   修法：类型与范围放 schema，**归属放执行前的授权钩子**——它只能看参数与用户身份，
   拿不到正文也就漏不了正文（3.5.5）。
3. **一个工具干太多事。**
   现象：出现 `update_article(field, value)` 这种签名，很快字段之间出现互斥组合，模型开始给错。
   原因：把「省一个工具定义」当成了优化，代价是每次调用都多一层歧义。
   修法：动作用**参数**而不是新工具，但仅限同一种验收方式的动作；验收方式不同就拆开（3.5.4）。
4. **工具结果原样回吐。**
   现象：一次查询把几十 KB 的 JSON 塞进上下文，之后每一轮都在为它重复付费，还更容易撞上截断。
   原因：把「查出来的量」当成了「该回给模型的量」。
   修法：上限一刀切在注册表里（`MAX_RESULT_CHARS`），并且返回**形状稳定**的字段子集（3.5.6）。
5. **失败消息写成「操作失败，请重试」。**
   现象：模型原样重试，把预算烧在同一个错误上。
   原因：错误消息是写给**日志**的，不是写给**下一步决策**的。
   修法：按 3.5.7 的三分类落：缺参数（补参数）／越界（换值）／权限（停下并告知用户），
   每条都带一句可执行的建议；不可重试的失败要明确说「别试了」。
6. **把幂等键交给模型提供。**
   现象：重试时两次写入，或者模型每次都造一个新键，于是「重跑只写一次」这道闸形同虚设。
   原因：把控制面（谁负责去重）与数据面（参数）混在了一起。
   修法：幂等键由循环生成，且不出现在任何工具的 schema 里（3.5.5 的边界）。

## 面试视角

**问：工具调用和函数调用是一回事吗？**

答：机制上同源——都是把「可调用的东西」以声明形式给模型，模型回一个结构化的调用请求，
由你的代码执行。区别在**约定的层级**：函数调用是服务商提供的一次往返（约束、并行、
严格模式都写在 API 里）；工具调用是更上层的通称，包含跨服务器的发现与授权（MCP 那一层）。
面试里更值得说的不是名词，而是**三个必须自己实现的部分**：参数校验、归属判定、幂等。
API 只能替你保证「格式像」，保证不了「该不该做」。

**问：一次响应里模型给了三个工具调用，你怎么处理？**

答：分三步。①**校验与授权逐个先过**，任何一个不过就地变成一条失败结果，不去执行；
②**互不依赖的并行、有依赖的串行**——三个都是只读且无共享状态就可以并发，
只要有一个是写、或依赖另一个的输出，就必须串行；③**词元账只记一次**：三个调用出自同一次
响应，所以「模型调用」是 1 而不是 3，步数才是 3。最后这条最容易被记账记错。

**问：工具越多越好吗？**

答：不是。工具定义每一轮都在付（3.5.2 量过：两个工具定义 ≈126 词元，占一句提问的 5 倍），
而且工具越多，模型的选择空间越大、选错的机会越多。
判据是**验收方式**：同一种验收方式 → 用参数（`mode`）而不是新工具；
不同的验收方式 → 拆成独立的工具。「少而厚」是有代价的——厚意味着描述长，
所以描述要写「何时用/何时不用」，而不是把功能清单堆长。

**问：工具返回错误时，应该抛异常还是返回错误对象？**

答：返回**错误对象**，并且分成可重试与不可重试两类。异常会把控制流从「模型的下一步」
拉回「你的调用栈」，而这些错误本来就是要交给模型看的输入。
但异常不该被吞掉：它要在注册表这一层被翻译成一条带分类与建议的结果
（`ToolResult(ok=False, error=..., retryable=...))`，而不是变成一句「未知错误」。

## 本章小结

1. 一次工具调用的往返是五步：定义 → 模型决策 → 参数校验 → 执行 → 回填；
   五步各有一个归属，混在一起就没法单独测。
2. 工具定义只有三个字段：名字、描述、参数 schema。**描述是唯一的说明书**——
   它决定模型在不该用的时候会不会用。
3. 工具集要「少而厚」：按验收方式分组，动作用参数而不是新工具；
   工具定义每一轮都在付费，这一点在 3.1 的账里已经量过。
4. 参数是建议，不是可信输入：类型与范围靠 schema 拦，**归属靠执行前的授权钩子拦**，
   业务约束靠工具自己再验一次并回一句可执行的建议。
5. 返回值是给模型看的：形状稳定、字段子集明确、体积有上限，
   而且上限只在注册表一处定义。
6. 失败要分类：可重试（超时/限流/服务端）／不可重试（参数/结构）／需要人工（发布、越权）；
   错误消息是给模型的下一步指令，不是给日志的。
7. 一次响应里可以有多个调用：**互不依赖的并行、有依赖的串行**，
   而且它们出自同一次响应——模型调用算 1 次，步数算多次。
8. 工具多了以后，复杂度从「怎么调」转到「怎么编排」：链、扇出、分支、终止，
   而编排的每一种形态都对应一种终止条件（回到 3.3 的运行时）。

## 练习

- **基础**：给注册表加一个新工具 `list_drafts()`（只读，返回当前用户的草稿列表），

**三处按官方口径改写的地方**：

1. **「工具定义越详细越好」改成「描述只说何时用」**。旧素材建议把每个参数的意义、取值范围、
   示例都写进描述；实测（3.5.3 的对照）表明，描述变长带来的选择正确率提升会很快饱和，
   而它每一轮都在付费。正确做法是：**何时用/何时不用**写进描述，取值范围交给 schema。
2. **「参数校验用 pydantic 一次搞定」改成「三层各管一段」**。schema 管类型与范围、
   授权钩子管归属、工具自己管业务约束——一层全包会让「越权」与「参数错」返回同一个错误，
   而这两件事对模型的意义完全不同（一个该停下告知用户，一个该改参数重试）。
3. **并行调用的记账**。旧素材把一次响应里的多个调用一律记成多次「模型调用」；
   真实实现里它们出自同一次响应，**模型调用是 1 次、步数是多次**。
   这不是口径之争：按旧口径算，一次三调的批量任务会被记成三倍成本，
   而成本表正是 3.9 用来判断回归的地方。
