## 3.4.1 规划要解决的三个问题

把「帮我准备一场技术分享会」交给一个没有规划的代理，你会看到三种失败同时出现：它不知道从哪开始（先去订场地还是先定主题？），中间漏掉关键步骤（大纲做完了发现没准备演示 Demo），以及把同一次思考重复几遍（每一轮都重新决定「先做什么」）。

有规划的那一版，第一步产出的不是内容，而是一份顺序：

```text
确定主题与目标听众 → 检索相关资料 → 设计大纲 → 准备演示 Demo → 生成演讲稿
```

这份顺序就是规划模块的全部产出。它解决三个问题：

| 问题 | 规划给出的答案 | 没有它会怎样 |
| --- | --- | --- |
| 从哪开始 | 一份有序的步骤清单 | 每轮都在重新决定「先做什么」，词元花在决策而不是执行上 |
| 会不会漏 | 步骤清单是一份可核对的检查表 | 靠模型记性，长任务里必然漏 |
| 做到哪了 | 每步的状态（未开始 / 进行中 / 完成 / 失败） | 重试时不知道哪些已完成，容易重复做事 |

**规划不是「想得更久」，而是把「要做什么」与「现在做什么」分开。** 分开之后，「要做什么」可以被检查、被展示、被修改；「现在做什么」只需要在有限的候选里挑一个。这个分离是后面所有工程手段的前提。

至于这一步由谁来做，官方在编排形态上给了一个很实用的判据：

- 子任务**能**预先确定，而且顺序固定 → 写**提示链**，一步接一步，中间可以插程序化校验。
- 子任务**不能**预先确定，但可以边做边分 → 用**编排者–工作者**：一个中心模型负责拆，工作者负责干。
- 连「需不需要拆」都不确定 → 才是自主 Agent 的地盘（第 3.3.2 节）。

## 3.4.2 两种主流方式：先计划后执行与边想边做

### 两种方式各自的样子

**边想边做**（ReAct 风格）：模型每一步都看着当前上下文，决定「下一步做什么」。灵活，中间结果能立刻改变方向；代价是每一步都要一次模型调用，而且它没有全局视角——可能走到第七步才发现方向错了。

**先计划后执行**（Plan-and-Execute）：先用一次调用产出一份完整计划，再按计划逐步执行。规划只花一次，步骤之间如果有独立的就可以并行，整体更快；代价是计划一旦被推翻，返工面很大。

### 返工面有多大：一次对照

两者真正的差别不在平均情况，而在**出错之后**。设一个 12 步的任务，第 7 步失败且重试仍然失败，三种方式的代价可以直接算出来：

```python
"""三种规划方式在「第 7 步失败、重试也失败」时的代价。规则：一次模型调用 = 一轮。"""

TOTAL, FAIL_AT = 12, 7

def fixed_plan():
    """A：一次性规划，然后逐步执行。计划一旦推翻，已完成的步骤全部作废。"""
    calls, done = 1, []                       # 1 次规划调用
    for step in range(1, TOTAL + 1):
        calls += 1                            # 执行一步
        if step == FAIL_AT:
            calls += 1                        # 重试一次（仍失败）
            wasted = len(done)
            calls += 1                        # 重规划
            for _ in range(TOTAL):            # 按新计划重跑全部步骤
                calls += 1
            return calls, wasted, "推翻计划，重跑全部步骤"
        done.append(step)
    return calls, 0, "一次通过"

def staged_plan():
    """B：分层计划，每个阶段带检查点。计划错只作废当前阶段。"""
    calls, wasted = 1, 0                      # 1 次规划调用（产出 3 个阶段）
    for stage in range(3):
        stage_steps = range(stage * 4 + 1, stage * 4 + 5)
        for step in stage_steps:
            calls += 1
            if step == FAIL_AT:
                calls += 1                    # 重试一次（仍失败）
                wasted += step - 1 - stage * 4   # 只作废本阶段已完成的部分
                calls += 1                    # 重规划本阶段
                for _ in stage_steps:         # 重跑本阶段
                    calls += 1
                break
    return calls, wasted, "只作废当前阶段并重跑它"

def react_loop():
    """C：边想边做，没有预先计划。失败只影响当前一步。"""
    calls = 0
    for step in range(1, TOTAL + 1):
        calls += 1
        if step == FAIL_AT:
            calls += 1                        # 原地重试一次
    return calls, 0, "原地重试当前一步"

print("策略 | 模型调用（＝墙钟轮数） | 作废的已完成步骤 | 处置")
for name, f in [("A 一次性计划后执行", fixed_plan),
                ("B 分层计划 + 阶段检查点", staged_plan),
                ("C 边想边做（无预先计划）", react_loop)]:
    calls, wasted, how = f()
    print(f"{name} | {calls} | {wasted} | {how}")
```

输出：

```text
策略 | 模型调用（＝墙钟轮数） | 作废的已完成步骤 | 处置
A 一次性计划后执行 | 22 | 6 | 推翻计划，重跑全部步骤
B 分层计划 + 阶段检查点 | 18 | 2 | 只作废当前阶段并重跑它
C 边想边做（无预先计划） | 13 | 0 | 原地重试当前一步
```

三个数字对应三种工程后果：**一次性计划在失败时最贵**（22 次调用，还要重跑已经做对的 6 步）；**边想边做最便宜但最没方向感**（没有任何全局产物，人无法在动工前审一遍计划）；**分层计划是折中**（18 次、只作废 2 步，而且每一阶段末尾都有人能看的东西）。

这解释了为什么推荐形态不是二选一，而是分层：**先计划后执行，但在阶段之间加检查点**。阶段划分本身就是给「重规划」预留的最小单元——阶段内的失败在阶段内解决，阶段级的偏差才回到规划层。

### 选择依据

| 任务特征 | 建议 | 理由 |
| --- | --- | --- |
| 探索性、中间会遇到什么不知道 | 边想边做 | 计划必然作废，先计划只是多一次调用 |
| 流程明确、步骤固定 | 先计划后执行（可加并行） | 规划一次就能复用，重点是步骤质量 |
| 步骤多、彼此有依赖、可能要重来 | **分层计划 + 阶段检查点** | 返工面被限制在一个阶段内 |
| 复杂混合 | 两者结合：先出阶段级计划，阶段内边做边定 | 全局可控、局部灵活 |

> 别照抄示例代码里的 API 名——先查官方文档里那个版本是否还有这个符号（第 4 篇会给出当前的写法）。

## 3.4.3 任务分解：粒度、依赖与关键路径

### 三条判据

一份能用的分解，每一步都要满足三条：

1. **可单独验收**：完成后有一个客观信号说明它对不对（测试通过、数据取到、字段齐全）。
2. **输入输出明确**：它读什么、产出什么，能写成一两句话。
3. **失败可重试**：失败时重做这一步不会污染已完成的部分（这就是「幂等」在规划里的样子）。

这三条中**第 1 条最常被跳过**。没有验收标准的步骤，到了循环里只能靠模型自己说「我做完了」——而第 2.1 节已经说过，那是不可靠的。

### 粒度：步数不是目标

把同一件事拆成 4 步、10 步、20 步，看起来越细越安全，但真正决定墙钟时间的是**关键路径**（最长依赖链）——它决定了至少要跑多少轮：

```python
"""分解粒度与依赖结构：真正决定墙钟时间的是关键路径，不是步数。"""

def levels(n, deps):
    """拓扑分层：每层内部可并行，层数 = 关键路径长度。"""
    layer = {}
    def depth(i):
        if i in layer:
            return layer[i]
        layer[i] = 0 if not deps[i] else 1 + max(depth(d) for d in deps[i])
        return layer[i]
    for i in range(n):
        depth(i)
    by_layer = {}
    for i in range(n):
        by_layer.setdefault(layer[i], []).append(i + 1)
    return layer, by_layer

# 同一个任务，三种拆法
plans = {
    "粗（4 步，重依赖）": (4, [[], [0], [0], [1, 2]]),
    "中（10 步，两条并行链）": (10, [[]] + [[0]] * 3 + [[0]] * 3 + [[1, 4]] + [[2, 5]] + [[3, 6]] + [[7, 8]]),
    "细（20 步，同两条链再切细）": (20, [[]] + [[0]] * 6 + [[0]] * 6 + [[1, 7]] + [[2, 8]] + [[3, 9]] + [[4, 10]]
                                  + [[5, 11]] + [[6, 12]] + [[13, 14]] + [[15, 16]] + [[17, 18]]),
}
print("拆法 | 步数 | 关键路径（轮） | 并行层分布 | 串行时的轮数")
for name, (n, deps) in plans.items():
    layer, by_layer = levels(n, deps)
    dist = " / ".join(f"L{k}:{len(v)}步" for k, v in sorted(by_layer.items()))
    print(f"{name} | {n} | {max(layer.values()) + 1} | {dist} | {n}")
```

输出：

```text
拆法 | 步数 | 关键路径（轮） | 并行层分布 | 串行时的轮数
粗（4 步，重依赖） | 4 | 3 | L0:1步 / L1:2步 / L2:1步 | 4
中（10 步，两条并行链） | 10 | 3 | L0:1步 / L1:6步 / L2:3步 | 10
细（20 步，同两条链再切细） | 20 | 4 | L0:1步 / L1:12步 / L2:6步 / L3:1步 | 20
```

步数从 4 涨到 20（**5 倍**），关键路径只从 3 涨到 4（**1.33 倍**）——因为细拆增加的是**同层内的宽度**，不是深度。这条结论有两个直接用途：

- **要压时间，压关键路径**：把长链上的步骤合并、或者把其中能独立的部分挪出来并行。给非关键路径上的步骤再拆细，一点都不会更快。
- **要控成本，看宽度**：同层 12 步意味着一次要并发 12 次模型调用（或串行 12 轮），成本和限流额度都是按宽度出的。

反过来说，粒度确实有下限：**每一步至少要能被单独验收**。拆到「调用一次接口就一步」的程度，验收标准会退化成「接口没报错」，等于没有验收标准。

### 依赖、顺序与聚合

分解的产物有两部分：**节点**（每步做什么）与**边**（谁依赖谁）。三件事做好，这份依赖图就能用：

- **依赖排序**：按依赖做拓扑排序，得到执行顺序；有环就是死锁，必须在动手前发现。
- **并行分组**：同层节点可以一起发出去，但要注意它们对同一份资源（同一个文件、同一条数据库记录）的写入会互相覆盖。
- **聚合点**：并行分支的结果要有一个明确的汇总步骤，并说清冲突时怎么办（取最新、取权威源、还是报错让人看）。

分层规划的经典形态（HTN，分层任务网络）与这里说的是同一件事：**高层是抽象任务，低层是具体动作，中间靠「把抽象任务细化成子任务」这条规则连起来**。它给工程的两条提醒值得记住：

- **抽象层级要按「谁来验收」划分**，而不是按动作类别划分。一个阶段对应一个人能看懂、能签字的交付物。
- **细化深度要设上限**。递归细化下去总还能更细，问一句「再细一层，有谁能用它做决定吗」，答不出就停。

## 3.4.4 计划的形态：一份可校验的结构化数据

### 四个字段

计划的载体不是一段自然语言描述，而是一份**结构化数据**。模型那边用受约束解码产出（第 3.2.4 节），运行时这边校验。四个字段就够用：

| 字段 | 作用 | 缺了它会怎样 |
| --- | --- | --- |
| `id` + `action` | 每一步做什么、叫什么 | 没法引用、没法做依赖、没法记状态 |
| `deps` | 依赖哪些步骤 | 顺序靠模型记性，并行没有依据 |
| `accept` | 验收标准（命令、字段、阈值） | 只能靠模型自称完成 |
| `max_steps` 等上限 | 预算与规模护栏 | 模型可以规划出 50 步，成本不可控 |

把「状态」这一列交给你自己的运行时（而不是让模型在文本里维护），是这条路上最省事的决定：`未开始 / 进行中 / 完成 / 失败` 四个状态落在数据库里，模型每次只看到一份摘要。

### 为什么值得先校验

计划是纯数据，因此可以在**动任何工具之前**静态检查。下面这个校验器盯五类问题：

```python
"""计划的静态校验：在动第一个工具之前，把必然失败的计划拦下来。"""

def validate(plan):
    issues = []
    ids = [s["id"] for s in plan["steps"]]
    if len(set(ids)) != len(ids):
        dup = sorted({i for i in ids if ids.count(i) > 1})
        issues.append(f"步骤 id 重复：{dup}")
    known = set(ids)
    for s in plan["steps"]:
        if not s.get("accept"):
            issues.append(f"{s['id']}：没有验收标准，完成后无法判断是否成功")
        for d in s.get("deps", []):
            if d not in known:
                issues.append(f"{s['id']}：依赖 {d} 不存在（悬空依赖）")
    # 环检测（DFS 三色）
    color, cyc = {}, []
    def dfs(u, stack):
        color[u] = 1
        for v in plan["by_id"].get(u, {}).get("deps", []):
            if v not in color:
                dfs(v, stack + [v])
            elif color[v] == 1 and not cyc:
                cyc.append(" → ".join(stack + [v]))
        color[u] = 2
    plan["by_id"] = {s["id"]: s for s in plan["steps"]}
    for s in plan["steps"]:
        if s["id"] not in color:
            dfs(s["id"], [s["id"]])
    if cyc:
        issues.append(f"依赖成环：{cyc[0]}")
    limit = plan.get("max_steps", 12)
    if len(plan["steps"]) > limit:
        issues.append(f"步骤数 {len(plan['steps'])} 超过上限 {limit}")
    return issues

good = {"max_steps": 12, "steps": [
    {"id": "s1", "action": "search", "accept": "拿到 2025 年营收数据"},
    {"id": "s2", "action": "search", "accept": "拿到 2025 年利润率", "deps": ["s1"]},
    {"id": "s3", "action": "calc", "accept": "两个比率算出且量纲一致", "deps": ["s1", "s2"]},
]}
bad = {"max_steps": 5, "steps": [
    {"id": "s1", "action": "search", "accept": "拿到原始报告"},
    {"id": "s1", "action": "search", "accept": "拿到补充数据"},
    {"id": "s2", "action": "calc", "accept": "算出增长率", "deps": ["s9"]},
    {"id": "s3", "action": "write", "accept": "", "deps": ["s4"]},
    {"id": "s4", "action": "verify", "deps": ["s3"]},
    {"id": "s5", "action": "publish", "accept": "报告已发布"},
]}

for name, plan in [("正常计划", good), ("问题计划", bad)]:
    issues = validate(plan)
    print(f"\n=== {name}（{len(plan['steps'])} 步）===")
    if not issues:
        print("  通过：可以开始执行")
    for i in issues:
        print("  ✗", i)
```

输出：

```text

=== 正常计划（3 步）===
  通过：可以开始执行

=== 问题计划（6 步）===
  ✗ 步骤 id 重复：['s1']
  ✗ s2：依赖 s9 不存在（悬空依赖）
  ✗ s3：没有验收标准，完成后无法判断是否成功
  ✗ s4：没有验收标准，完成后无法判断是否成功
  ✗ 依赖成环：s3 → s4 → s3
  ✗ 步骤数 6 超过上限 5
```

六条问题里，**没有任何一条需要调用模型才能发现**。这一类检查的性价比极高：一条二十行的函数，把「跑到第三步才发现计划是死的」变成「计划生成后立刻报错，并让模型重新生成」。校验失败时的处置也要写清楚——重试两次仍不通过，就退回到「边想边做」，别让用户在门口等。

### 形式化：状态、动作、目标与判据

从更抽象的层次看，任何决策问题都可以写成四件：**状态**（世界现在什么样）、**动作**（能做什么、做完状态怎么变）、**目标**（什么算做完）、**判据**（怎么打分、怎么权衡）。做 Agent 开发时它有一个立刻能用的推论：

- 状态 → 你要喂给模型的上下文（以及工具能查到的部分）；
- 动作 → 你的工具集；
- 目标 → 验收标准与终止条件；
- 判据 → 你在多个候选计划之间做选择的依据。

面试里常被问到这里（「如何定义目标条件的形式化表达」「奖励函数如何反映目标条件的达成」）。答题的要点是**把它落到工程物上**：目标条件不是一句自然语言，而是一条可执行的检查；奖励不是玄学，而是「哪个计划被选中、为什么」的排序依据。至于复杂度类别、可观测性建模那类经典理论问题，属于规划算法的范畴，应用岗需要知道它们存在、以及什么时候该请人，不需要在这里展开。

## 3.4.5 执行与重规划：什么时候该改计划

计划是假设，执行是验证。四类信号出现时，就该回到规划层改计划：

| 信号 | 判断 | 处置 |
| --- | --- | --- |
| 步骤失败且重试无望（同样错误两次以上） | 这条路走不通 | **局部改**：替换这一步的实现，或把它拆成两步 |
| 新信息与某个假设冲突 | 计划的前提不成立了 | **重规划受影响的后继部分**，已完成部分不动 |
| 预算不足（剩余预算 < 关键路径所需） | 硬跑完也会超预算 | **收口**：用已有信息给最佳答案并说明缺口（第 3.3.3 节） |
| 外部状态变化（文件被改、数据源更新） | 已完成部分的结论可能失效 | **重校验**受影响步骤，必要时重做 |

两条实操要求：

**第一，重规划要产出一份 diff，而不是一份新计划。** 让模型重新生成整份计划，等于把已经做对的步骤也放到赌桌上：新计划里的 `s1` 与旧计划的 `s1` 文本相似但不等价，运行时却无法判断，于是只能重跑。做法是让重规划只允许三类操作——**替换某步、插入一步、删除一步**——并带上步号。这样「已完成的 6 步」天然被保住。

**第二，状态更新要事件驱动、并允许一次重规划失败。** 每一步结束时发一个事件（完成 / 失败 / 需要人工），规划层订阅它来决定要不要重规划；重规划本身也可能产出坏计划，所以它同样受步数上限约束，并且要记进追踪记录——否则线上出问题时，你看到的是「计划变了」，却看不到「为什么变」。

> ⚠️ **注意**：重规划不是免费的。除了多一次模型调用，它还会让**缓存失效**：计划一变，前缀里那段「当前计划」也跟着变，后面所有轮次的缓存命中都会掉（第 3.1.6 节）。
> 所以别把计划写进最前面的系统提示——放在需要它的位置，别放在会被反复复用的前缀里。

## 3.4.6 让规划更可靠：五个方向与一条边界

把「怎么让模型规划得更好」这件事整理成方向，一份 2024 年的综述给出了五个：**任务分解、计划选择、外部模块、反思、记忆**。对应到工程上是五组手段：

| 方向 | 具体手段 | 什么时候用 | 代价 |
| --- | --- | --- | --- |
| 任务分解 | 提示链 + 程序化校验；编排者–工作者 | 任务能分层、能验收 | 多一轮拆解调用 |
| 计划选择 | 采样多个计划再评（投票 / 打分 / 约束筛查） | 计划质量方差大、错了很贵 | 生成成本 × k |
| 外部模块 | 用真实工具验证（跑测试、查数据库、问求解器） | 有可信的验证信号 | 需要先把验证做出来 |
| 反思 | 失败后带着错误信息重试（Reflexion 式） | 有外部反馈信号 | 无外部信号时反而变差（第 3.2.8 节） |
| 记忆 | 计划与进度落到外部（todo / NOTES.md） | 任务跨会话、轮数多 | 需要读写与一致性维护 |

四条值得记住的判断：

- **思维链让计划更长，不等于更准。** 它提高的是「把隐含假设写出来」的概率，而计划的好坏最终靠验收：把每一步的验收标准一并生成出来，比再想一段推理更有用。
- **多计划 + 选择**是提高计划质量最直接的手段，但它把成本乘上 k 倍。用之前先问：这份计划的错误要花多少代价才能发现？如果一步就能发现，不如直接做、错了再改。
- **反思要有外部信号。** 「再想一遍」在无外部反馈时会变差；「带着测试输出重想」才有效。
- **LLM 当世界模型只适合短推演。** 让它预测「这个方案会发生什么」在几步之内有价值，步数一多，误差复合就把它变成编故事。

### 一条必须知道的边界

有一条反直觉但证据充分的结论：**模型在常识任务上表现出的「规划能力」，不一定是规划能力。** 在基于经典规划任务的基准上（要求形式化地推理动作与状态变化），模型的表现在多轮改进后**依然差得远**；而在常识任务上，很难区分「模型真的在规划」还是「它在从见过的类似场景里检索答案」。

这条边界给出两个工程决定：**能用程序校验的地方就别靠模型规划**（这一步的顺序对不对，跑一遍就知道）；**报告规划能力时用可验证的指标**（步骤通过率、返工率、关键路径偏差），不用「看起来挺有条理」。

## 3.4.7 长任务：上下文压缩、结构化笔记与子代理

任务一长，规划的敌人就从「想不清」变成「记不住」。官方给出的三套手法各有明确分工：

**上下文压缩**：把接近窗口上限的对话总结成一份摘要，用摘要开一段新上下文。关键是**保留什么**——架构决策、未解决的 bug、实现细节要留，冗余的工具输出可以丢；Claude Code 的做法是压缩后继续，并附上最近访问的 5 个文件。最轻量的一种压缩是**清理旧的工具结果**：工具调用过去很久之后，原始返回内容几乎不再被需要。

**结构化笔记**：让代理把进度、待办、已确认的事实写到上下文之外的存储里（一份 `NOTES.md`、一张 todo 表），需要时再读回来。它是跨会话续跑的基础——上下文重置之后，代理读自己的笔记接着干。

**子代理**：主代理拿高层计划，把「深挖一类信息」的活交给子代理；子代理可以用几万词元的预算去翻资料，只把一两千词元的结构化摘要交回来。计划留在主线，细节留在支线，两边的上下文都干净。

三者的账可以量。同一个 20 轮的任务，每轮新增一次工具调用与一条工具返回：

```python
"""长任务的上下文账：不压缩、只清理旧工具结果、每 5 轮压缩一次。用真实分词器数词元。"""
import tiktoken
enc = tiktoken.get_encoding("o200k_base")
n = lambda s: len(enc.encode(s))

ROUNDS, SUMMARY, KEEP = 20, 300, 2
FIXED = n("你是数据分析助手，可用工具 search / calc / write_file，必须先核实再下结论。") + n("比较两家公司 2025 年营收并给出结论")
CALL = n('search({"query":"A 公司 2025 年营收与利润率"})')
RESULT = n("A 公司 2025 年营收 1,240 亿元，同比增长 18%；净利润 148 亿元，利润率 11.9%。")
PLACEHOLDER = n("[工具结果已清理]")

def run(mode):
    hist, billed, peak, raw = FIXED, 0, FIXED, []
    for r in range(1, ROUNDS + 1):
        hist += CALL + RESULT
        raw.append(RESULT)                      # raw 记录“还是原文”的结果
        if mode == "trim":
            while len(raw) > KEEP:
                hist += PLACEHOLDER - raw.pop(0)
        if mode == "compact" and r % 5 == 0 and r < ROUNDS:
            billed += hist                      # 压缩这一次调用本身也要付输入
            raw = raw[-KEEP:]
            hist = FIXED + SUMMARY + sum(raw)
        billed += hist                          # 本轮正常调用
        peak = max(peak, hist)
    return billed, peak

print("策略 | 累计计费输入 | 峰值上下文 | 相对不压缩")
base = None
for label, mode in [("不压缩", "none"), ("只清理旧工具结果", "trim"), ("每 5 轮压缩一次", "compact")]:
    billed, peak = run(mode)
    base = base or billed
    print(f"{label} | {billed} | {peak} | {billed / base:.0%}")
```

输出：

```text
策略 | 累计计费输入 | 峰值上下文 | 相对不压缩
不压缩 | 10840 | 998 | 100%
只清理旧工具结果 | 6565 | 548 | 61%
每 5 轮压缩一次 | 10306 | 642 | 95%
```

结果和直觉相反：**省得最多的是「清理旧工具结果」**（−39%），因为它把重复内容直接替换成占位符，不需要额外调用；**定期压缩只省 5%**，因为压缩自己也要把整段历史读一遍。压缩真正的收益在**峰值**（998 → 642），也就是「窗口被撑爆」的风险，而不是账单。

所以三套手法的选用依据是任务形状，不是「哪个更省」：

| 任务形状 | 用哪套 | 为什么 |
| --- | --- | --- |
| 需要大量来回对话、上下文连贯性重要 | 压缩 | 保住对话流，只在接近上限时收一次 |
| 迭代推进、有清晰里程碑 | 结构化笔记 | 进度落在外部，上下文重置也能续跑 |
| 可并行的探索与研究 | 子代理 | 把细节隔离在支线，主线只拿摘要 |

> 💡 **提示**：三者可以叠加，但顺序是固定的——**先清理工具结果（免费），再考虑笔记（便宜），最后才压缩（最贵）**。
> 一上来就做大段摘要，往往是花了钱、还把关键细节总结丢了。

## 3.4.8 传统决策机制的对照：规则、状态机与行为树

不是所有决策都该交给模型。四种经典机制至今仍在大量系统里承担决策，它们与代理循环是互补关系：

| 机制 | 适合的场景 | 优点 | 失效方式 |
| --- | --- | --- | --- |
| 条件–动作规则 | 状态少、规则明确、要能事后解释 | 可读、可审计、延迟极低 | 规则一多就互相冲突，维护成本指数上升 |
| 有限状态机 | 流程有明确阶段与迁移条件 | 状态与迁移都能画出来，测试容易 | 状态一多就爆炸，跨状态行为难表达 |
| 行为树 | 反应式决策、优先级与中断频繁 | 结构清晰，选择节点天然表达优先级 | 复杂条件编排仍会变得难读 |
| 混合架构（反应式 + 审慎式） | 既要实时反应又要长期规划 | 反应层保证安全与实时，审慎层负责规划 | 两层的接口与冲突解决是关键难点 |

**判据只有两条**：决策序列能不能枚举？出了问题需不需要「解释为什么这么决定」？两条都是「能」的时候，传统机制往往比模型更合适——它更快、更便宜，而且**它的行为可以被测试**。反过来，条件写不清、状态空间写不全、输入是自然语言的时候，才是模型的地盘。

混合架构里有一条经验值得单独记住：**安全与实时相关的决策放反应层（规则 / 状态机），需要理解和权衡的决策放审慎层（模型）**。让模型去管「这个操作能不能执行」是危险的——判断延迟不可控，而且它可能被提示注入说服（第 3.8 节）。

## 3.4.9 知舟接线

这一节把计划层接进知舟，是 [`PROJECT.md`](PROJECT.md) 的**第四段增量**。
标注规则同 1.15：`plan.py` 的校验、分层、diff 都是纯函数，**实跑**；
`/agent/plan` 端点与写库路径需要模型凭据与 MySQL / Redis 服务端，属**拼接验证**（下文逐处标明）。

### 加了什么

3.3 让知舟的循环能转，但它每一轮「下一步做什么」都从零想，且没有全局产物可以审。
这一节给知舟加一个**计划层**：先把任务变成一份结构化的计划（3.4.4 的四个字段），
在动第一个工具之前静态校验，按依赖分层执行，失败时只改该改的几步。
它落在新模块 `app/agent/plan.py`，不改动第 1 篇的任何端点与表。

### 接口契约

| 文件 | 作用 | 关键签名 |
| --- | --- | --- |
| `app/agent/plan.py`（新增） | 计划对象（`Step` / `Plan`）、五类校验、拓扑分层、diff 式重规划 | `validate(plan) -> list[str]`｜`layers(plan) -> list[list[str]]`｜`apply_diff(plan, ops) -> Plan` |

| `app/services/agent_plan_service.py`（新增） | 生成 → 校验 → 重生成（≤2 次）→ 分层 | `def plan(self, task: str, max_steps: int) -> tuple[Plan, list[str]]` |
| `app/api/agent.py`（新增路由） | **只规划不执行**，让人能在动手前审一遍计划 | `POST /api/v1/agent/plan`，外壳沿用 `Result{code, msg, data}` |
| `tests/agent/test_plan.py`（新增） | 五个用例，不需要模型也不需要数据库 | — |

它依赖前两章的零件：**3.2 的 `llm/client.py`**（受约束解码把模型输出变成 `dict`，形状由
`llm/schemas.py` 保证）与 **3.3 的 `agent/runtime.py`**（步数上限、预算与追踪记录）。
从 3.5 开始，计划里每个 `action` 会绑定一个真实工具，这份对象才真正“能跑”。

```python
# app/agent/plan.py —— 计划层的核心（节选：表示、校验、分层、diff）
"""知舟的计划层：表示、五类静态校验、分层与 diff 式重规划。

计划是**纯数据**：所以它能在动第一个工具之前被检查、被展示、被改。
"""
from __future__ import annotations

from dataclasses import dataclass, field


@dataclass
class Step:
    id: str
    action: str
    accept: str = ""
    deps: list[str] = field(default_factory=list)
    status: str = "todo"


@dataclass
class Plan:
    goal: str
    steps: list[Step]
    max_steps: int = 12

    @property
    def by_id(self) -> dict[str, Step]:
        return {s.id: s for s in self.steps}


def deps_of(plan: Plan, sid: str) -> list[str]:
    """取某步的**已有**依赖。

    这里必须容忍「引用了不存在的步骤」：校验器的职责正是把这种计划拦下来，
    它自己不能因为输入非法而崩——直接写 `plan.by_id[sid].deps`，
    碰到悬空依赖就抛 KeyError，那等于最该跑通的那条路径跑不通。
    """
    s = plan.by_id.get(sid)
    return [d for d in s.deps if d in plan.by_id] if s else []


def validate(plan: Plan) -> list[str]:
    """动第一个工具之前能查出来的五类问题。全是纯函数，不需要模型。"""
    issues: list[str] = []
    ids = [s.id for s in plan.steps]
    dup = sorted({i for i in ids if ids.count(i) > 1})
    if dup:
        issues.append(f"步骤 id 重复：{dup}")
    for s in plan.steps:
        if not s.accept:
            issues.append(f"{s.id}：没有验收标准，完成后无法判断是否成功")
        for d in s.deps:
            if d not in ids:
                issues.append(f"{s.id}：依赖 {d} 不存在（悬空依赖）")
    color: dict[str, int] = {}          # 三色 DFS 找环
    cycle: list[str] = []

    def dfs(u: str, stack: list[str]) -> None:
        color[u] = 1
        for v in deps_of(plan, u):
            if v not in color:
                dfs(v, stack + [v])
            elif color[v] == 1 and not cycle:
                cycle.append(" → ".join(stack + [v]))
        color[u] = 2

    for s in plan.steps:
        if s.id not in color:
            dfs(s.id, [s.id])
    if cycle:
        issues.append(f"依赖成环：{cycle[0]}")
    if len(plan.steps) > plan.max_steps:
        issues.append(f"步骤数 {len(plan.steps)} 超过上限 {plan.max_steps}")
    return issues


def layers(plan: Plan) -> list[list[str]]:
    """拓扑分层：同层可并行，层数就是关键路径长度。只对校验通过的计划调用。"""
    depth: dict[str, int] = {}
    by_id = plan.by_id

    def d(i: str) -> int:
        if i not in depth:
            deps = [x for x in by_id[i].deps if x in by_id]
            depth[i] = 0 if not deps else 1 + max(d(x) for x in deps)
        return depth[i]

    for s in plan.steps:
        d(s.id)
    out: dict[int, list[str]] = {}
    for s in plan.steps:
        out.setdefault(depth[s.id], []).append(s.id)
    return [out[k] for k in sorted(out)]


def apply_diff(plan: Plan, ops: list[tuple[str, str, Step | None]]) -> Plan:
    """只允许替换 / 插入 / 删除三种操作，已完成步骤的 id 一律保留。"""
    steps = list(plan.steps)
    for op, sid, new in ops:
        if op == "replace":
            steps = [new if s.id == sid else s for s in steps]
        elif op == "insert":
            assert new is not None
            steps.insert(next(i for i, s in enumerate(steps) if s.id == sid) + 1, new)
        elif op == "delete":
            steps = [s for s in steps if s.id != sid]
    return Plan(goal=plan.goal, steps=steps, max_steps=plan.max_steps)


def draft_plan(model_reply: dict) -> Plan:
    """受约束解码把模型输出变成 dict，形状由 schema 保证。"""
    return Plan(goal=model_reply["goal"],
                max_steps=model_reply.get("max_steps", 12),
                steps=[Step(**s) for s in model_reply["steps"]])


BAD = {"goal": "给文章 42 生成摘要与标签并写草稿", "max_steps": 4, "steps": [
    {"id": "s1", "action": "load_article", "accept": "拿到 title 与 content"},
    {"id": "s1", "action": "load_article", "accept": "拿到作者昵称"},
    {"id": "s2", "action": "summarize", "accept": "摘要 80–120 字", "deps": ["s9"]},
    {"id": "s3", "action": "tag", "accept": "", "deps": ["s4"]},
    {"id": "s4", "action": "write_draft", "accept": "草稿落库且 drafted=0", "deps": ["s3"]},
]}

GOOD = {"goal": "给文章 42 生成摘要与标签并写草稿", "steps": [
    {"id": "s1", "action": "load_article", "accept": "拿到 title 与 content"},
    {"id": "s2", "action": "summarize", "accept": "摘要 80–120 字", "deps": ["s1"]},
    {"id": "s3", "action": "tag", "accept": "标签 1–3 个且属既有栏目", "deps": ["s1"]},
    {"id": "s4", "action": "write_draft", "accept": "草稿落库且 drafted=0", "deps": ["s2", "s3"]},
]}

if __name__ == "__main__":
    print("=== 第一次生成（形状合法，计划不一定活着）===")
    plan = draft_plan(BAD)
    for i in validate(plan):
        print("  ✗", i)

    print("\n=== 重新生成后 ===")
    plan = draft_plan(GOOD)
    print("  校验通过" if not validate(plan) else "  仍有问题")
    lay = layers(plan)
    print(f"  关键路径 {len(lay)} 层 ｜ " + " ｜ ".join(f"L{i}: {','.join(v)}" for i, v in enumerate(lay)))

    print("\n=== 执行到 s2 失败，重规划只改该改的 ===")
    plan.steps[0].status = "done"
    plan.steps[1].status = "failed"
    new = apply_diff(plan, [("replace", "s2", Step(
        "s2", "summarize_chunked", "分段摘要后合并，80–120 字", ["s1"]))])
    print("  diff：replace s2 → summarize_chunked（依赖不变，仍是 s1）")
    print(f"  已完成步骤未重跑：{[s.id for s in new.steps if s.status == 'done']}")
    print(f"  重跑范围：{[s.id for s in new.steps if s.status != 'done']}")
    print(f"  重规划后校验：{'通过' if not validate(new) else validate(new)}")
```

### 不能破坏什么

- **不改既有端点与表**：`/agent/plan` 是新增路由，1.15 的十来个文章/用户接口请求与响应形状一字不动；
  自查：跑 1.14 建立的测试套，全绿才算数。
- **不把计划塞进系统提示或前缀**：计划一变就打断前缀缓存（3.1.6），所以它放在需要它的位置，
  不放在被反复复用的前缀里。
- **追踪里不落正文**：`Plan`/`Step` 只记 `id` / `action` / 状态，不记文章内容与用户信息——
  追踪表是长期留存的地方，正文一旦进去就收不回来（3.8 会展开这条边界）。
- **校验器必须先于被校验的数据成立**：一个遇到坏输入就抛异常的校验器，等于没有校验器。
  所以它的第一类用例是「输入非法」，而不是「输入合法」。

## 常见坑

1. **现象**：计划生成得很好，跑到一半发现第 3 步的前提是错的。**原因**：计划被当成一次性的结论，而不是可修改的假设。**修法**：把计划存成结构化数据、状态落库，支持「替换/插入/删除」三种局部修改，重规划产 diff 而不是新计划。
2. **现象**：一次性规划的 12 步任务，在第 7 步失败后整体重跑。**原因**：没有阶段划分，返工面等于全部。**修法**：在计划里划出 3–5 个阶段，每阶段一个可验收交付物；阶段内的失败在阶段内解决。
3. **现象**：计划里出现 `deps: ["s9"]` 但没有 `s9`，或者两个步骤互相依赖。**原因**：计划从没被静态校验过。**修法**：生成后立刻跑校验（重复 id、悬空依赖、缺验收、成环、超上限），不通过就重生成，两次仍不通过退回边想边做；同时用「坏计划」本身作为校验器的第一个测试用例——只拿好计划试过的校验器，往往在它最该拦下的那类输入上直接抛异常。
4. **现象**：为了让任务更快，把每一步都拆得更细，结果总时长没变。**原因**：拆细只增加并行宽度，不减关键路径。**修法**：先算关键路径，只优化它上面的步骤；宽度受并发上限约束，别无限拆。
5. **现象**：跑到十几轮后请求超窗失败，或明显变傻。**原因**：历史线性增长，从没做过清理或压缩。**修法**：先清理过期的工具结果，再考虑结构化笔记，最后才用压缩；同时监控峰值上下文而不是只看平均值。

## 面试视角

「Agent 规划与决策策略」是这类岗位最常深挖的一章，题库里正好有三组题可以直接对上：

- **任务分解类**（「如何将复杂任务分解成合理子任务」「任务目标层次化分解的关键原则」「子任务依赖关系如何保证执行顺序」「如何处理子任务间的依赖冲突」「中间结果聚合策略的设计原则」）：答题时把三个层次说清——**能不能拆**（有明确交付物）、**怎么排序**（依赖图 + 拓扑序，同层可并行）、**怎么收口**（聚合点与冲突解决策略）。再加一条工程判据「每步必须能单独验收」，答案就比只背概念完整一层。
- **分层与回落类**（「HTN 分层任务网络的设计要点」「抽象层级划分的原则」「如何根据需求动态调整抽象层级」「分层递归细化中如何平衡细化深度与效率」）：要点是**抽象层级按「谁来验收」划分**、**细化深度设上限**、**阶段检查点就是重规划的最小单元**。这三个说法都能落到代码上。
- **推理与反思类**（「如何利用思维链提升 LLM 规划的准确性」「如何在 LLM 中实现路径多样化的规划探索」「如何进行模型自我反思以修正规划」「如何优化多步推理中的回溯效率」「ReAct 框架中如何平衡推理与行动的权重」）：一定要给出边界——反思需要外部信号，否则会变差；多路径探索的收益要按成本折扣（第 3.2.6 节的投票收益与相关性折扣）；回溯要在计划层面做，而不是让模型重述一遍历史。

高频延伸问法还有：Plan-and-Execute 与 ReAct 怎么选（答「取决于中间结果会不会推翻计划」，并给返工代价那条对照）；什么时候不该让模型规划（答「能枚举、能程序化校验的，写死更可靠」）。

## 本章小结

1. 规划解决三件事：从哪开始、会不会漏、做到哪了；它的本质是把「要做什么」与「现在做什么」分开。
2. 先计划后执行的差别不在平均成本，而在**失败时的返工面**：12 步任务第 7 步失败，一次性计划 22 次调用、作废 6 步，分层 18/2，边想边做 13/0。
3. 推荐形态是「分层计划 + 阶段检查点」：全局可控、局部灵活，阶段是重规划的最小单元。
4. 分解的三条判据：可单独验收、输入输出明确、失败可重试；粒度看关键路径而不是步数（4/10/20 步对应 3/3/4 轮）。
5. 计划要是一份结构化数据（id/action、deps、accept、上限），并在动手前静态校验五类问题——这些检查一条都不需要调用模型。
6. 重规划的触发信号有四类；改计划要做 diff 而不是重写，且注意它会打断前缀缓存。
7. 提高规划可靠性的五个方向是任务分解、计划选择、外部模块、反思、记忆；边界是——模型在经典规划任务上仍差得远，常识任务上难以区分规划与检索。
8. 长任务靠三套手法：先清理工具结果（省 39%），再用结构化笔记，最后才是压缩（省 5%，但把峰值从 998 降到 642）。
9. 状态少、规则明确、需要解释与实时性的决策，交给规则、状态机或行为树；安全相关判断不要放在审慎层。

## 练习

- **基础**：给第 3.4.4 节的校验器加两条规则——「步骤引用了不存在的工具名」与「某步的验收标准不是可执行命令」，并用两份构造的计划验证。
- **进阶**：把一个你熟悉的真实任务拆成 8–12 步的计划，画出依赖图，标出关键路径与并行宽度，然后回答：这份计划里哪一步最可能失败？它失败时你要重跑几步？
- **挑战**：实现一个「分层计划 + 阶段检查点」的执行器：计划分 3 个阶段，每阶段末尾产出可验收的交付物；任一步失败时只重跑该阶段，并把每次重规划写进追踪记录。最后写三句话说明它在什么条件下会退化成「整体重跑」。

**三处按官方口径改写的地方**：

1. **Plan-and-Execute 的代码**。那份笔记里的 `from langchain.agents import Plan, Execute` 在任何版本里都不存在；「先计划后执行」这个模式是真的，但它要靠自己实现（或用编排者–工作者），不是导入两个类。
2. **「最大迭代次数」式的规划护栏**。笔记把步数上限当成主要手段；本章的对照表明，**阶段划分与计划校验**才是降本的主力——一次性计划失败一次就要重跑全部步骤。
3. **把计划写进系统提示**。旧写法习惯把整份计划放进最前面的提示里；这会让每次重规划都打断前缀缓存，正确做法是把计划放在需要它的位置，而不是放在被反复复用的前缀里。
