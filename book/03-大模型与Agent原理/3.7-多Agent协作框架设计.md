# 3.7 多 Agent 协作框架设计

> **本章导读**：上一章的代理已经能记住事，但它仍然只有一个上下文窗口。
> 一个窗口要同时装三份材料就会开始顾此失彼，要把三件互不依赖的事串着做完就会很慢。
> 多 Agent 就是把「一个窗口做强」换成「几个窗口分工」——而分工一旦发生，
> **新的失败方式就出现了**：信息在交接处丢失、两个人查同一件事、三个人都没查某一件事。
>
> 一句话贯穿全章：**子代理之间不共享上下文，交接单是唯一的通道**。
> 你在单子里没写的，它就真的不知道——不是「它应该能猜到」，而是「它连材料都没有」。
> 学完本章，你能判定一件事该不该拆、能写出四件齐全的交接单、能给每份分工切出预算、
> 能认出协作失效的四种样子，并能说清多 Agent 到底买到了什么（不是省钱，是并行度）。

## 3.7.1 什么时候需要多个代理：单代理的四种受限表现

先把最容易走偏的一句话挡在门口：**多 Agent 不是「更高级的 Agent」**。
它是用一个上下文窗口换一组上下文窗口，而这个交换有价格。
判断该不该换，看的是**单代理在这件事上具体受限在哪**——四种受限，各有各的处方。

| 受限表现 | 你看到的样子 | 真实原因 | 处方 |
| --- | --- | --- | --- |
| **装不下** | 三份材料一起塞进去，答案开始丢三落四 | 上下文太长，注意力被稀释（上下文腐烂） | 分窗口：每份材料进一个窗口 |
| **串不动** | 三件互不依赖的事，一件一件等 | 一个循环是串行的，动作必须一环等一环 | 并行：几个窗口同时开 |
| **两副面孔** | 同一个提示里既要「大胆起草」又要「严格挑错」，两件事都做不好 | 两个目标在同一个上下文里互相污染 | 分角色：起草一个窗口、审校另一个 |
| **一处跑歪全歪** | 循环在中途钻了牛角尖，整件事都跟着歪 | 单点：没有第二条独立的观察路径 | 冗余：两个角色各自看一遍 |

四种受限里，只有前两种能靠「多开几个窗口」直接解决；
后两种解决的是**质量**问题——多出来的那个窗口是给「另一种视角」用的，
它的产出可能和第一个窗口差不多，而它值钱的地方恰恰在于**它不是同一个窗口**。

### 可切性：拆之前必须回答的一个问题

拆分的判据不是「任务大不大」，而是**子任务之间要不要对方的中间结果**。

```text
互不依赖（能拆）        三个方向各查一点，最后汇成一段话
                        每份结论只用「目标」就能开跑
依赖中间结果（不要拆）  改一段代码：先跑测试 → 看报错 → 再改
                        第二个人必须拿到第一个人的输出才能动手
```

第二种任务拆给子代理的后果很具体：子代理 A 在等 B 的结论，B 在等 C 的，
而它们在并行地等——**你付了多份的钱，买到的是一串互相等待的串行**。
官方那篇多 Agent 系统的文章把这条写得最直白：这类任务用单代理，不要拆。

**官方给的两个数字**（Anthropic 的多 Agent 研究系统，见延伸阅读）：
以 Claude Opus 4 为主管的「主管 + 若干 Sonnet 4 子代理」在其内部研究评测上，
比单代理的 Claude Opus 4 高出 **90.2%**；而成本的量级是：
代理（agent）本身约是普通对话的 **4 倍**词元，多代理系统约是 **15 倍**。
两个数字必须一起读——**质量收益是真的，价格也是真的**，第 3.7.6 节会把它变成你能自己量的账。

## 3.7.2 编排者–工作者：主管规划、子代理并行、主管汇总

本章实现的结构是**编排者–工作者**（orchestrator–workers）：一个主管 + 若干子代理。
它有三个环节，分开看是因为它们各自会坏，而且坏法完全不同：

```text
规划  把目标拆成几份交接单       坏的样子：单子太笼统 → 子代理重复劳动或漏掉整块
执行  每个子代理在自己的窗口里跑到收敛   坏的样子：某个子代理失控，把总预算吃光
汇聚  合并、去重、报缺口          坏的样子：看起来汇总了，其实三份结论是同一件事
```

这三件事在代码里必须**分开写**，因为它们的验证方式不同：
规划是**纯数据**（能被校验、能在花钱之前被拒），执行是**有副作用的并行**（不能重入），
汇聚是**只读的算术**（去重、算缺口都不需要模型）。

主管是唯一能看到全部子代理结论的角色，这一点决定了预算的切法——先看代码：

```python
# app/agent/orchestrator.py —— 交接单的四件与被拦下的三种坏单（节选）
REQUIRED_FIELDS = ("objective", "deliverable", "tools", "boundaries")

# 官方给的三条档位（Anthropic 多 Agent 研究系统）：把「该花多少力气」写进提示，而不是让模型自己判。
EFFORT_LADDER: tuple[tuple[str, int, int], ...] = (
    ("simple", 1, 3),        # 单点事实：1 个代理，3–10 次工具调用
    ("compare", 3, 10),      # 直接对比：2–4 个子代理，每个 10–15 次
    ("complex", 6, 15),      # 复杂调研：>10 个子代理，职责必须划清
)


class HandoffError(ValueError):
    """交接单不合规：宁可在这里当场报错，也不要把它发给子代理。"""
```

一次编排的骨架只有四步，但每一步都有「为什么必须在这一步」的理由：

```python
# app/agent/orchestrator.py —— 切预算 → 并行执行 → 汇聚（节选）
    now = clock or time.monotonic
    started = now()
    seen: set[str] = set()
    for h in handoffs:
        h.validate()
        if h.fingerprint() in seen:
            raise HandoffError(f"交接单重复：{h.role} 的目标/交付/工具与前面某一份相同——"
                               f"那就是同一件事做两遍，你付两份钱买一份结论")
        seen.add(h.fingerprint())

    lead_budget, sub_budgets = split_budget(handoffs, total=total_tokens)
    out = Orchestration(goal=goal, handoffs=list(handoffs))
    with ThreadPoolExecutor(max_workers=min(max_workers, len(handoffs))) as pool:
        futures = [pool.submit(run_subagent, h, config=config, registry_factory=registry_factory,
                               system=system, budget=b, chat_fn=chat_fn,
                               on_call=on_call_for(h.role) if on_call_for else None)
                   for h, b in zip(handoffs, sub_budgets)]
        out.results = [f.result() for f in futures]
```

四步的顺序都是硬约束：**校验与去重先于切预算**（单子不合格就不该开始花钱）、
**切预算先于起线程**（每个子代理拿到的是自己的硬上限，不是大家抢的一个池子）、
**收结果先于汇总**（`f.result()` 会等全部结束，所以汇总看到的是一份完整的账）。

### 并行的是上下文窗口，不是工具调用

这条区分很容易被略过，但它是本章与第 3.5 节的分界：

- **3.5.8 的并行**：一次模型响应里回了多个工具调用 → 循环把它们排好队依次执行，
  **模型调用还是 1 次**。它省的是往返次数。
- **本章的并行**：几个独立的**上下文窗口**同时在探索，各自有各自的系统提示、工具子集与预算。
  它省的是**串行阶段**——关键路径只等于「最长的那个子代理」，不是「全部之和」。

两种并行叠加：一个子代理内部可以有一次响应多个工具调用，
而子代理之间是线程池级别的并行。它们互不干扰，因为前者在循环里，后者在循环之外。

## 3.7.3 三种结构：层级、黑板、对等

编排者–工作者只是三种常见结构里的一种。选错结构的代价，比选错提示的代价大得多。

| 结构 | 谁在决定下一步 | 适合的任务形状 | 主要代价 |
| --- | --- | --- | --- |
| **层级**（编排者–工作者） | 主管 | 目标清晰、能切成几块独立方向（广度优先） | 主管是单点；它的规划质量决定整次的天花板 |
| **黑板** | 谁有进展谁写入共享状态 | 探索型、分工在开跑时说不清 | 并发写共享状态要处理冲突（版本/锁），状态会长大 |
| **对等**（接力） | 上一棒指定的下一棒 | 流水线式：起草 → 审校 → 定稿 | 每一棒都要重新装配上下文，容易在交接处丢信息 |

三者的区别可以用一句话记住：**层级是「谁说话算数」清楚，黑板是「谁先发现谁写」，
对等是「谁交给谁」清楚**。它们不是互斥的——真实的系统常常是层级的每一格里再放一条对等链
（本章的路径五就是：主管派三份单子，而「写作者」这一份的产出会被「审校者」接着看）。

**本章为什么实现层级**：它是三者里唯一能在**没有额外基础设施**的情况下把契约做硬的——
共享状态（黑板）需要存储与并发控制，接力（对等）需要给每一棒定义输入输出。
第 4 篇会用 LangGraph 的 `StateGraph` 把同一件事重写一遍，那一份的核心正是共享状态；
到那时把两份实现摆在一起看，**层级替你做了什么、藏了什么**会非常清楚。

## 3.7.4 交接契约：四件，少一件它就开始猜

交接单（handoff）是子代理拿到的**全部信息**。官方那篇的说法是每份子任务要带上
四样：目标、输出格式、可用工具与来源、明确的边界。本章把它写成四个字段：

```python
# app/agent/orchestrator.py —— 四件缺失各自的报错（节选）
    def validate(self) -> None:
        for name in REQUIRED_FIELDS:
            if not str(getattr(self, name)).strip():
                raise HandoffError(f"交接单缺了「{name}」：子代理会自己猜，而它猜的方向不由你决定")
        if not self.tools:
            raise HandoffError(f"交接单的「tools」是空的：子代理只能干看着（角色 {self.role}）")
        if self.allow_write and not self.boundaries.startswith("写"):
            # 提权必须**写在交接单里**，不能靠调用方记得：否则一次重构就会把写权限漏下去。
            raise HandoffError(f"角色 {self.role} 拿到了写权限，但 boundaries 没有说明写什么")
```

四件里最容易被省掉的是 `boundaries`，而它是最能省事的一件：
没有它，两个子代理会去查同一件事——**实测里最常见的一种浪费**，
而你付了两份钱买到一份结论。所以校验不是「友好提示」，它是**在花钱之前拦下**：

```text
$ python demo.py --only 5
  提权没写在 boundary 里 → 角色 写作者 拿到了写权限，但 boundaries 没有说明写什么
```

「提权写在单子上」这一条的工程含义值得单独说：写权限**不是**调用方传给子代理的一个参数，
它是单子上的一行字。参数会被忘、会被重构掉，而单子会被 `validate()` 检查。
这与第 3.5 节「写操作必须停在人工确认」是同一条纪律的两个位置：
**危险的东西要写在会被检查的地方。**

### 交接单是数据，不是提示片段

`@dataclass(frozen=True)` 这一行决定了后面所有能力：因为它是数据，所以它能被
`validate()` 校验、能被单测覆盖、能被日志化、能被去重。指纹就是去重用的：

```python
# app/agent/orchestrator.py —— 交接单的指纹：发现「两份单子其实是同一件事」（节选）
    def fingerprint(self) -> str:
        """交接单的指纹：用来发现「两份交接单其实是同一件事」。"""
        payload = f"{self.objective}|{self.deliverable}|{'/'.join(sorted(self.tools))}|{self.boundaries}"
        return hashlib.sha256(payload.encode("utf-8")).hexdigest()[:12]
```

注意指纹只看目标/交付/工具/边界——**角色名不参与**。把 A 的单子改个角色名叫 B，
它们仍然是同一件事做两遍。反过来，同一位专家被派去干两件真正不同的事，指纹不同，允许放行。

### 子代理只看到自己那一份工具

`tools` 进到执行层会变成什么，是本章与第 3.5 节最容易冲突的地方——
3.5 说「让代理先看到全部工具再决定用哪个」，本章说「只给它那一份」：

```python
# app/agent/tools/zhizhou.py —— 按角色构造注册表（节选）
def build_for(user_id: int, store: dict | None = None, names: Sequence[str] | None = None
              ) -> Registry:
    """按**角色**构造注册表：子代理只看得到自己那一份工具。

    这与 3.5 那条「先看全部工具，再决定用哪个」正好相反，而且不矛盾：
    那条针对的是**一个**要拿主意的代理；这里是「职责已经被交接单划定了」的子代理，
    它多看到的每个工具都是一个新的走错路的机会（而它的上下文窗口本来就很窄）。
    """
```

两句话不矛盾的判据是**职责是否已经被划定**。单代理没有外部约束，
所以它需要看到全部选项；子代理的职责写在单子上，所以多给它的每个工具都是**新的走错路的机会**。
顺带一个副作用：工具子集的 schema 不再跟着每一次请求走——第 3.7.6 节的实测里，
这一项让多代理的固定开销反而比单代理更低。

### 一句坏交接单长什么样（实测）

这一条是**跑起来才知道**的，所以它值得被完整记下来。第一次真机跑路径五，
三份交接单里有两份是坏的，而且坏法不同：

```text
$ python demo.py --only 5      # 修交接单之前
  角色    状态      步   调用     词元  交付
  检索者   ok        2    2    2500  - 滑动过期：每次换新令牌时把刷新令牌也一起换掉…
  写作者   timeout   3    4    2490  很抱歉，当前无法完成写作任务。原因是我尚未通过工具检索到任何具体的写作方法或素材
  审校者   ok        1    1     548  我需要先知道要审校哪篇文章。请提供文章ID或标题，我来查找并审校。
  词元合计 5538｜被打折 ['写作者']｜草稿：（未写入）
```

两处错，都是**单子的问题，不是模型的问题**：

1. **写作者的单子缺材料，也缺取材料的工具。** 原文写的是「按检索到的做法写一段草稿正文」——
   而那三种做法在**检索者的上下文里**，不在写作者的上下文里。
   子代理之间只靠交接单通信，所以「检索到的」这四个字对着它就是一个空指针。
   它只有 `create_draft` 一个工具，于是它只能在预算耗尽前说实话：我没有材料。
   **处方**：单子里要么带上材料，要么带上去取材料的工具（这里是加 `read_article`，
   并把目标写成「读 42 号文章的正文，据此写…」）。
2. **审校者的单子指代不清。** 「这篇文章」在主管的脑子里，不在单子上。
   它照实地回来问你要文章 id——这不算失败，算**信息没到**。
   **处方**：把 id、标题、版本号这类**指代物**写死在单子里，不要写「这篇文章」「刚才那篇」。

改完之后同一个路径跑通了，而且第三份产出带回了一个只有「另一个视角」才看得见的东西：

```text
$ python demo.py --only 5      # 修交接单之后
  交接单：检索者（2 个工具）、写作者（2 个工具，已提权写）、审校者（2 个工具）
  角色    状态      步   调用     词元  交付
  检索者   ok        2    2    2488  滑动过期：每次换新令牌时把刷新令牌也一起换掉，旧的那枚立刻作废。
  写作者   ok        3    3    5065  已为 42 号文章写草稿正文，未发布。
  审校者   ok        3    3    4192  文章 42 号｜**标签**：安全、后端、JWT、部署｜**缺口**：结尾被截断
  词元合计 11745（主管 0 ＋ 子代理 11745）｜耗时 21.3s
  缺口 无｜被打折 无｜重复 无｜主管那一步 没失败
  草稿：已写入，状态 draft
  发布：False（子代理没有审批通道，工具子集里也没有 publish_article）
```

三件值得停下来看的：

- **审校者真的抓到了一个缺陷**：它说「缺口：结尾被截断」。这不是客套，
  而是同一个任务里**另一个上下文窗口**看到的、写作者自己看不见的问题——
  这正是「两副面孔」那种受限的处方生效的样子，也是多 Agent 唯一无法用省钱解释的价值。
- **草稿写进去了，但没发布。** 写作者被提权写了草稿，而它**看不到** `publish_article`：
  子代理的工具子集里没有它，而且子代理这条路径**没有人工确认回调**。
  于是「并行三个写操作、旁边没人确认」这件事在结构上不可能发生——它不需要靠自觉。
- **主管那一步没调模型**（`主管 0`），所以 11,745 词元全是子代理花的。
  真机的 `--synth` 模式会给主管一次调用，第 3.7.6 节把两种都量了。

## 3.7.5 按任务复杂度配资源：规则决定，模型不决定

「该开几个子代理」如果交给模型判断，你会得到两个后果：**同一个任务两次跑出不同的规模**，
以及**每次都要多花一次调用来问它**。所以这一层用规则：

```text
$ python experiments/multi_agent_cost.py
档位表（官方经验值，复杂度的名字 → 子代理数、每个的工具调用上限）：
(('simple', 1, 3), ('compare', 3, 10), ('complex', 6, 15))
```

`ladder_for(complexity)` 只接受三个名字，别的输入当场报错——**名字是枚举，不是自由文本**。
官方给这三档时的原话大意是：**投入必须能被扩缩**（简单查询 1 个代理 3–10 次调用就够，
复杂调研要 10 个以上子代理且职责必须划清）。把这句话变成代码，最关键的一步是
**让「力气」成为调用方写下来的一个枚举值**：写 `complex` 的人要对得起这个档位的预算，
而不是让模型自己猜自己该多努力。

### 预算按份切，不抢一个池子

```python
# app/agent/orchestrator.py —— 总预算切成「主管一份 + 每份交接单一门」（节选）
    if not handoffs:
        raise HandoffError("一份交接单都没有：编排退化成了一次普通调用（那就不需要编排器）")
    lead = Budget(max_steps=4, max_tokens=max(int(total * lead_share), 500))
    rest = total - lead.max_tokens
    if rest < len(handoffs) * 500:
        raise HandoffError(f"预算不够切：{total} 词元要分给 1 个主管 + {len(handoffs)} 个子代理")
    each = rest // len(handoffs)
    return lead, [Budget(max_steps=h.max_steps, max_tokens=min(h.max_tokens, each))
                  for h in handoffs]
```

三个决定，每个都有理由：

1. **每份是硬上限**。抢池子的后果很具体：先跑完的那个把预算吃光，
   后面的子代理在「预算耗尽」里收口——而**它的收口结论会被当成「这个方向没东西」**。
   一次资源调度错误伪装成了一次调研结论，这是最难发现的一类错。
2. **主管单独留一份**（默认 25%）。它是唯一能看到全部子代理结论的角色；
   把它的预算分光，等于让汇总在最有信息量的一步上没预算可用。
3. **每份有一个下限**（500 词元）。切得太碎会让子代理在**读到东西之前**就收口——
   那不是「它没找到」，而是假阴性。所以预算不够切时宁可报错，不偷偷把某一份切到 0。

## 3.7.6 成本边界：多 Agent 买到的到底是什么

这一节全部是量出来的账，分两张表：**离线的算术**与**真机的实测**。
离线的意义是它能被复现（不需要密钥），真机的意义是它有服务商的真实开销。

### 离线：两种组织方式在同一个任务上的算术

```text
$ python experiments/multi_agent_cost.py
任务：知舟上那篇讲刷新令牌的文章讲了哪几种做法？它的标签有哪些？站内一共多少篇文章？

配置              | 模型调用 | 串行阶段 | 请求体词元 | 其中消息体 | 其中 schema | 峰值 | 覆盖
-------------------------------------------------------------------
单代理             |        4 |        4 |       7351 |       4735 |        2616 | 2228 | 5/5
多代理·拼接汇总        |        6 |        2 |       2874 |       1962 |         912 | 1822 | 5/5
多代理·主管汇总（40）    |        7 |        2 |       3085 |       2172 |         913 | 1822 | 5/5
多代理·主管汇总（300）   |        7 |        2 |       3877 |       2964 |         913 | 1822 | 5/5
多代理·主管汇总（900）   |        7 |        2 |       5677 |       4764 |         913 | 2803 | 5/5
```

四句读数（都是表里的数）：

1. **总量** 7,351 → 2,874（-61%）。单代理每多一轮，前面的工具结果就要**重发一次**；
   多代理把它们分进三个上下文，各自只发一次。
2. **每次请求的固定开销** 2,616 → 912。多代理的调用次数更多（4 → 6），这一项却更小——
   因为子代理只带自己那 1–2 个工具的 schema，而单代理每一次都背着全部 6 个。
   **工具子集既是权限边界，也是每一轮的成本。**
3. **峰值** 2,228 → 1,822。注意它不是「有几份材料」决定的，而是**最大的一份**决定的：
   那篇正文必须被完整读进某个上下文，切分降不下它。
4. **串行阶段** 4 → 2。子代理互不等待，关键路径是「最长的那一个子代理」；
   官方那个「复杂调研省下 90% 时间」说的就是这一列。

第五句留给交接单的长度——**这是「压缩率」这个旋钮的账**：

```text
5. 交接单交回多长，主管那一次就多贵：
   多代理·主管汇总（40）   汇总那一次   211 词元 ｜ 总计   3085 词元（比单代理 -58%）
   多代理·主管汇总（300）  汇总那一次  1003 词元 ｜ 总计   3877 词元（比单代理 -47%）
   多代理·主管汇总（900）  汇总那一次  2803 词元 ｜ 总计   5677 词元（比单代理 -23%）
```

结论比数字重要：**汇总那一次的体量 = 固定部分 + Σ（各份结论）**。
子代理交回得越长，主管那一次越贵——而单代理的账里根本没有这一栏。
这就是官方反复强调「子代理要**先压缩、再交回**」的原因：
省下的重发费，会从这一栏流回去。900 词元那一行已经接近单代理，
而且**峰值反转了**（2,803 > 2,228，峰值出现在主管汇总那一次）。

### 真机：同一任务，两种组织

同一句任务、同一个端点（OpenAI 兼容方言），单代理与多代理各跑：

| 配置 | 模型调用 | 词元 | 墙钟 | 关键词覆盖 |
| --- | ---: | ---: | ---: | :---: |
| 单代理（一个循环做完三件事） | 3 | 4,913 | 4.6s | 5/5 |
| 多代理（并发 3，主管再调一次汇总） | 3 + 1 | 4,590（主管 287） | 3.7s | 5/5 |
| 多代理（**并发 1**，同样三份单子） | 3 + 1 | 4,516 | **19.2s** | 2/5 |

三个读数，一个反直觉：

- **词元几乎打平**（4,590 对 4,913，多代理略低 7%）。与离线表 -61% 的差距不是矛盾，
  而是**模型自己选的路**：真机里它把「读正文」安排在了最后一步（前两轮只搜和数），
  于是累积重发的量本来就小；离线剧本里三件事是均匀分布的，重发量被放大了。
  **两行数字都对，但它们量的不是同一件事**——离线量的是装配的算术，真机量的是模型的选择。
- **并行度是真的**：并发上限从 1 改成 3，墙钟 19.2s → 3.7s。
  三份单子本来就互不依赖，`max_workers=1` 等于把并行买来的东西又还回去了。
- **墙钟要多次量**：同一配置的另外几次是 25.9s 与 38.7s——
  那几次撞上了服务商的排队与限流。**单次墙钟不能当结论，只能当区间**。

### 并行度不是免费的：那两次限流

真机跑的时候撞到过两次限流，两次的位置不同，而它们都指向同一件事：

1. 一次是**并发 3 打过去**，`标签` 子代理整条挂掉（服务商回 429），
   编排把它记成 `failed` 并放进了缺口清单；主管的汇总照旧交出了另外两份结论，
   并在答案里写明「子代理未提供该文章的标签信息」——**一个子代理的失败没有变成整次失败**。
2. 一次是**主管汇总那一步**被限流。修之前这里直接把异常抛给了调用方：
   三个子代理的钱都花了，调用方却什么都拿不到。修法是把主管那一步也隔离起来，
   降级退到拼接汇总，并把原因记在账上：

```python
# app/agent/orchestrator.py —— 主管那一步也要有隔离（节选）
        # 子代理有隔离，**主管那一步也要有**。它是最后一步：它炸了，前面几份子代理的钱
        # 就白花了，而调用方拿不到任何东西——实测里那一炸是服务商限流（429）。
        # 降级办法是现成的：退回拼接汇总，并把失败原因记在账上（不假装成功）。
        try:
            out.answer = synthesize(goal, out.results)
        except Exception as exc:                          # noqa: BLE001
            out.lead_error = f"{type(exc).__name__}: {exc}"
            out.answer = (f"（汇总那一步失败了：{out.lead_error}）\n\n"
                          + default_synthesis(goal, out.results))
```

由此得到一条部署层面的结论：**并发上限要按服务商的限额设**。
`max_workers` 不是「越大越好」的参数，它是你的账户额度与对方限流的函数；
而**子代理与主管两侧都要有降级路径**，否则一次限流就能把一次已经花了钱的编排清零。

### 那一次记账错：失败的行不能写 0 次调用

同一批真机跑还暴露了一个纯记账问题：`标签` 子代理失败那一行是
**`failed｜0 次调用｜396 词元`**——同一行的两个数互相矛盾。

原因是模型调用数记在循环的**局部变量**里，异常一抛，那个变量随栈一起消失，
于是失败路径只能硬写 0。修法是把调用数记在预算上（它本来就是这一份的账本）：

```python
# app/agent/runtime.py —— 调用数记在预算上（节选）
    def count_call(self) -> None:
        """记一次模型调用。**它记在预算上，而不是调用方的一个局部变量里**：

        子代理抛异常时，那个局部变量随栈一起消失，而「它花掉的几次调用」必须留下——
        否则一次失败在账上变成 0 次调用（3.7 实测里真的出现过：状态 failed、0 次调用、
        396 词元，两个数字互相矛盾）。预算本来就是这一份的账本，调用数也该记在这里。
        """
        self.calls += 1
```

这类错值得单独记一笔：**它不影响任何功能，只让账目失真**。
而账目是「这次编排值不值」唯一的依据——失真一次，后面所有关于成本的判断都建在沙上。

## 3.7.7 协作失效的四种样子与各自的处方

把上面所有实测归拢，协作失效只有四种样子。它们的共同点是**都不会报错**：

| 失效样子 | 在账上长什么样 | 处方 |
| --- | --- | --- |
| **重复劳动** | `duplicates()` 非空：两角色的产出指纹相同 | 改交接单（加边界/去掉重叠），不是加人 |
| **缝隙** | `gaps()` 非空：`empty`（没找到）或 `failed`（跑挂了） | 补一份新单子；`failed` 还要查那个子代理为什么炸 |
| **打折** | `degraded()` 非空：`timeout`——交了东西但可能不完整 | 重新分预算或减少它的职责；**不要当缺口重跑**（白花钱） |
| **指代不清** | 子代理回来问你要 id / 说没有材料 | 把指代物与材料写进单子 |

第三种（打折）最容易被处理错，所以代码里它是**单独一档**：

```python
# app/agent/orchestrator.py —— 三种收尾要分开（节选）
    def gaps(self) -> list[str]:
        """**没有交回可用东西的角色**：它不是失败，而是「这一块还没人看」。两种处置完全不同：
        缺口要补一份新的交接单，失败要查那个子代理为什么炸。"""
        return [r.role for r in self.results if r.status in ("empty", "failed")]

    def degraded(self) -> list[str]:
        """被预算/步数提前收口的角色：**它交了东西，但那东西可能不完整**。

        把它归进「缺口」会让人重跑一遍白花一份钱；把它当成正常结论，
        汇总里就混进了一段「我只看到一半但我不知道」。所以它单独一档。"""
        return [r.role for r in self.results if r.status == "timeout"]
```

四个状态（`ok` / `empty` / `failed` / `timeout`）对应四种处置，而它们的区别**全在处置上**：

- `ok`：直接用。
- `empty`：**它的方向还没有人看**——补一份单子，或者承认这个方向没有。
- `failed`：**它炸了**——先查原因（限流？工具报错？），再决定要不要重跑。
- `timeout`：**它交了半成品**——要么给它更多预算，要么把它的职责切小；
  把它当结论用会在汇总里混进一段「我只看到一半」，把它当缺口会在重跑里白花钱。

最后一种失效不在这个表里，因为它不属于「某个子代理」：**该拆的没拆、不该拆的拆了**。
判据在第 3.7.1 节——子任务之间要不要对方的中间结果。要，就别拆。

## 3.7.8 评测：结果与过程分开判

多 Agent 的评测比单代理复杂，因为**同一份投入可能产出很少**，也可能**产出很多但都是重复的**。
所以指标要分两组，而且**两组都要看**：

| 组 | 指标 | 怎么看 |
| --- | --- | --- |
| **结果** | 覆盖率（事实关键词命中数）、是否交付（草稿写入了吗）、是否越界（该被拦的拦住了吗） | 与单代理**同一任务、同一口径**对照 |
| **过程** | 串行阶段、重复、缺口、打折、每角色词元、调用次数 | 不看这些，就无法解释结果为什么好或坏 |

过程指标的价值在一次对比里最明显：覆盖 `5/5` 的那一次与覆盖 `2/5` 的那一次，
**用的工具、看到的材料一模一样**——差别只是模型的采样与汇总的措辞。
所以有一条纪律必须写下来：**单次成功不能当通过**（第 3.5 节的实测已经独立得出过同一个结论）。
样本小的时候，先跑 5–10 次看分布，再谈优化；`tests/agent/eval_cases.jsonl` 与
回归脚本是第 3.9 节的事，但**「多跑几次」这个习惯要在本章就建立**。

质量维度上还要补一句：**多 Agent 的评测需要第三方视角**。
路径五里审校者说出的「缺口：结尾被截断」，是写作者自己的上下文里看不见的东西。
这两个角色跑的是同一个模型、同一套工具——**差别只在上下文**。
所以评「多 Agent 值不值」时，看的不是「它有没有给出更好的答案」，
而是「**另一个窗口有没有看出第一个窗口看不出的问题**」。

## 3.7.9 协议边界：A2A 管「谁来做」，MCP 管「能做什么」

本章的交接单是**本地**的：同一进程、同一套工具、由你的代码直接构造与校验。
一旦子代理变成别的团队、别的厂商、别的机器上的系统，就要用协议。这里有两个必须分清的名字：

| 协议 | 管什么 | 核心概念 | 在本章里的对应物 |
| --- | --- | --- | --- |
| **MCP**（模型上下文协议） | 代理**能做什么**：把工具与数据接进来 | 工具、资源、提示 | `app/agent/tools/registry.py`（能力接入） |
| **A2A**（Agent2Agent） | **谁来做**：把任务交给另一个代理 | Agent Card、Task、Message/Part、Artifact | `Handoff` ＋ `Orchestration`（任务交接） |

A2A 官方规范（v1.0.0，见延伸阅读）里那条**不透明执行**（opaque execution）原则，
几乎就是本章那句话的协议版：代理之间**按声明出来的能力与交换的信息**协作，
**不需要访问对方的内部状态、记忆或工具实现**。
这一句解释了为什么交接单必须自带材料：对方的上下文你既看不见也不该依赖。

规范里的另外三件事也很值得对照：

- **Agent Card**：一个 JSON 文档，声明身份、能力、技能、服务端点与认证要求
  ——对应本章「对方能接什么活」这一层（本章用枚举的档位代替）。
- **Task 是有生命周期的**：任务有自己的 id 与状态机，支持流式更新与长时任务；
  ——对应本章的四种 `status`（`ok` / `empty` / `failed` / `timeout`），
  只是本地版把状态留在内存里，协议版把它变成可查询的资源。
- **异步优先**：跨系统协作默认是长时任务，所以要能推、能查、能取消；
  ——本章的线程池是同步等待的最小形态，第 8 篇会把这一层换成真正的任务与队列。

**一句话划界**：MCP 是**纵向**的（代理接到能力），A2A 是**横向**的（代理接到任务）。
本章的 `Handoff` 与 `registry` 正好是这两条轴上的最小本地实现——它们各自长什么样、
边界在哪里，对照完协议会清楚得多。

### 加了什么

**端点**：本章**不新增端点**——多 Agent 是一次编排过程，不是一个新资源。

### 怎么验

**离线可验的部分**（不需要密钥，也不需要数据库）：

```text
$ python demo.py --offline               # 含路径五：交接单校验 + 并行 + 草稿写入且未发布
$ python demo.py --only 5                # 真机版；上面贴的就是它的输出
$ python experiments/multi_agent_cost.py # 本章 3.7.6 的两张表（离线那一张）
$ python -m pytest tests/agent/test_orchestrator.py -q    # 18 条：交接单 / 预算 / 执行 / 汇聚
$ python tools/check_runnable.py         # 正文代码块 ↔ 可运行树，全树 150 条测试（不需 pytest）
```

四条断言值得单独列出来，因为它们对应本章的四条纪律：

```text
1. 交接单缺件 → HandoffError（在花钱之前，不是发给子代理之后）
2. 提权没写在 boundaries 里 → HandoffError（权限是单子上的一行字）
3. 一份子代理 failed，其余照旧交付，缺口清单里有它
4. 草稿写入 store 且 status == "draft"；publish 未被调用（子代理没有审批通道）
```

**真机跑通的部分**（需要凭据）：`demo.py --only 5` 的三个角色全部 `ok`，
草稿写入、未发布；`experiments/multi_agent_cost.py --real` 给出同一任务上
单代理与多代理的对照（3.7.6 的真机表）。**服务商限流是这条路径最常见的失败**，
所以两侧的降级路径都要按「会发生」来设计，不能按「不应该发生」来写。

### 不能破坏什么

- **不改前六段的分工**：`loop.py`、`policy.py`、`memory.py`、`registry.py` 的对外形状不变；
  本章只在预算上加了一个计数方法（`count_call`），**没有改任何既有函数签名**。
- **子代理默认只读**：默认 `allow_write=False`；提权必须写进 `boundaries`
  且由主管显式开启。任何「顺手把写权限传下去」的改动都算破坏。
- **子代理不共享上下文**：不要为了「省一次调用」让两个角色共用一份消息列表——
  那会把并行退化成串行，并且让交接契约失效（它依赖「对方只看得到单子」这个前提）。
- **主管那一步必须能被降级**：`synthesize` 抛异常时退回拼接汇总并记 `lead_error`，
  **不允许**让异常把整次编排的产出清零。
- **失败的行不许写 0 次调用**：调用数从 `budget.calls` 读；任何硬写常量都会让成本账失真。
- **并发上限是参数不是常量**：`max_workers` 要能按服务商限额下调（实测里 3 就打到了限流）。
- **测试必须真的被跑到**：`tools/check_runnable.py` 的测试清单**从盘上长出来**——
  这里刚修过一个真事故：清单写死时，`test_orchestrator.py` 的 18 条**一条都没跑**，
  而输出里只有一个看不出问题的「71 条」。

## 常见坑

1. **把「多 Agent」当成默认选择**。它买的是并行度与第二视角，代价是多份上下文与交接成本。
   单代理能做完的事拆开做，你会得到更贵、更慢、且更难查的一版。
2. **拆了不可拆的任务**。依赖中间结果的任务（改代码、逐步排查）拆开之后，
   子代理在并行地互相等待——付了多份钱买到一串串行。
3. **交接单缺件**。目标/交付/工具/边界少一件，子代理就开始猜；四件缺一都要在
   `validate()` 处当场报错，而不是寄希望于模型的常识。
4. **单子写着「按检索到的做法写」**。「检索到的」在其他子代理的上下文里——
   子代理不共享上下文，这句对它是空指针。**要么给材料，要么给取材料的工具。**
5. **指代不清**。「这篇文章」「刚才那篇」在主管脑子里；id、标题、版本号要写死在单子上。
6. **预算抢池子**。先跑完的把额度吃光，后面的在「预算耗尽」里收口，
   而它的收口结论会被当成调研结论——**资源调度错误伪装成事实结论**。
7. **不切主管那一份**。主管是唯一看得见全部结论的角色，把它饿死，
   汇总就变成「谁先交谁说了算」。
8. **把 `timeout` 当成 `empty`**。前者交了半成品（也许只缺一段），后者什么都没交；
   处置完全不同，混在一起要么白重跑，要么把半成品当结论。
9. **只保护子代理不保护主管**。实测里主管那一步的限流会把整次编排的产出清零——
   它是最后一步，前面的钱都花了。
10. **失败的行记 0 次调用**。它不影响功能，但会让「这次编排值不值」的判断全建在错账上。
11. **子代理拿全套工具**。多给它的每个工具都是新的走错路的机会，而且每一次请求都要多背 schema。
12. **`max_workers` 拉满**。并发上限是服务商限额的函数，不是越大越好；
    实测里 3 就已经撞上限流，而限流会伪装成「某个子代理 failed」。
13. **单次跑当验收**。同一配置两次跑出 5/5 与 2/5 的覆盖率——先看分布，再谈优化。

## 面试视角

- **问「什么时候用多 Agent」**：先给**可切性判据**（子任务要不要对方的中间结果），
  再给四种受限（装不下 / 串不动 / 两副面孔 / 一处跑歪全歪），
  最后给出你的成本口径（官方那两个数：约 4× 与约 15× 对话词元）。这三层答完，基本可以停。
- **问「怎么保证子代理不跑偏」**：从**交接契约**答——四件（目标/交付/工具/边界）、
  写成数据而不是提示片段、在花钱之前校验、提权写在单子上。
  再补一句「工具子集按角色裁剪」，这是最容易被忽略、又最有效的一条。
- **问「多 Agent 比单 Agent 强在哪」**：**别说更省**。省不省取决于组织方式与压缩率，
  真机同一任务上可能只差 7%；它真正买到的是**并行度**（关键路径从「全部之和」变成「最长的一个」）
  与**第二视角**（审校者看出写作者看不见的截断）。
- **问「子代理挂了怎么办」**：分四种状态答（`ok`/`empty`/`failed`/`timeout`），
  每种给处置；再强调两侧都要有降级路径（子代理与主管），并说出你自己撞到的那个限流。
- **问「A2A 和 MCP 有什么区别」**：一句话——MCP 管「能做什么」（纵向接能力），
  A2A 管「谁来做」（横向派任务）；A2A 的**不透明执行**原则正好解释了
  「为什么交接单必须自带材料」（对方的状态你看不见也不该依赖）。

## 本章小结

1. 多 Agent 不是升级版单 Agent，它的核心矛盾是：**子代理之间不共享上下文，交接单是唯一通道**。
2. 该不该拆的判据是**可切性**：子任务要不要对方的中间结果。要，就别拆。
3. 编排者–工作者有三个环节（规划/执行/汇聚），它们各自会坏，所以要分开写、分开验。
4. 并行的是**上下文窗口**，不是工具调用；后者在 3.5 已经处理过了。
5. 交接单四件：目标、交付格式、可用工具、边界。缺一件它就开始猜。
6. 交接单是**数据**——所以能校验、能去重（指纹）、能测试、能在花钱之前拦下坏单子。
7. 提权写在单子上（`boundaries` 以「写」开头），不写在调用方的参数里。
8. 预算**按份切硬上限**：主管单独留 25%，每份有 500 词元下限；不够切就报错，不偷偷切到 0。
9. 协作失效四种样子：重复、缝隙、打折、指代不清；四种状态（`ok`/`empty`/`failed`/`timeout`）
   各有各的处置。
10. 多 Agent 买到的是**并行度**与**第二视角**，不一定是省钱——
    压缩率（子代理交回多长）是决定总成本的那个旋钮。
11. 评测要**结果与过程**分开看，而且**单次成功不能当通过**。
12. MCP 是纵向的（接能力），A2A 是横向的（派任务）；本章的 `Handoff` 是后者的最小本地版。

## 练习

- **基础**：给路径五加第四个角色「事实核查者」（只读，工具 `read_article`），
  目标是「逐条核对写作者草稿里的三个说法是否都在正文里能找到」，
  并让它的交付格式固定为「说法 → 在/不在（位置）」。
  然后回答：为什么它的 `boundaries` 里必须写「不得改写草稿」？
- **进阶**：把路径五的 `max_workers` 从 3 改成 1 再改成 3，各跑两次，
  记录墙钟与关键词覆盖；再用 `--synth` 打开主管汇总跑两次。
  画出「并发度 → 墙钟」与「汇总是否调模型 → 词元」两条线，
  并解释为什么这两条线的形状完全不同。
- **挑战**：给编排器加一个**重试策略**：当某一份 `failed` 且失败原因是限流（429）时，
  把它单独重跑一次（不重跑其它份），并把重试次数记进账；
  要求「重试后仍失败的份」与「第一次就失败的份」在报告里可区分。
  然后用限流真实复现一次，证明：**重试不能改变结论，只能改变代价**——
  什么情况下应该重试，什么情况下应该直接报缺口？
