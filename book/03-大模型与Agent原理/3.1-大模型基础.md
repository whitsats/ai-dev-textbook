# 3.1 大模型基础：从 Transformer 到 Token

> **本章导读**：前三篇你学的是「怎么把系统写对」和「怎么用 AI 写系统」。从这一章开始
> 换一个方向：**你要调用的那个东西，内部是怎么运作的**。
>
> 很多应用开发者觉得原理「用不上」——模型是个 HTTP 接口，调它就行。这个判断在三个
> 地方会立刻失效：
>
> 1. **它在按量计费。** 你写进去的每一个字、模型吐出来的每一个字都要付钱，
>    而「一个汉字要几个词元」这件事**不是常数**——它取决于你用的模型换了哪代分词器。
>    实测：同一句话，旧分词器下中文比英文贵 2.41 倍，新分词器下是 0.94 倍。
> 2. **它没有记忆。** 「上下文窗口」听起来像内存条，实际是**这一次请求的工作台**。
>    你上一轮说的话之所以还在，是因为**你把它们又发了一遍**，并为它们付了第二次钱。
> 3. **它一次只做一件事。** 模型不会「先规划再写」，它只会**预测下一个词元**——
>    所有看起来像规划的行为，都是这个动作在长序列上的副产品。
>
> 本章不讲数学推导，也不讲怎么训练模型。它只回答一个问题：
> **哪些内部事实，会改变你写代码的方式**。九个事实，九条工程结论。
>
> 读完后你应该能对下面这些问题给出确定答案：为什么注意力要除以 `√d_k`？
> 为什么「中文更贵」这句话在 2026 年已经过期？为什么把文档全塞进上下文反而更差？
> 为什么官方开始劝你别再传 `temperature`？以及，为什么「涌现能力」可能根本不存在。

## 3.1.1 自回归：模型每次只做一件事

大语言模型（Large Language Model, LLM）的原始训练目标只有一句话：
**给定前面的词元，预测下一个词元**。就这么简单，也仅此而已。

生成一句话的过程是：预测第 1 个词元 → 把它接在输入后面 → 再预测下一个 → 直到输出结束标记。
这个循环叫**自回归**（autoregressive）。它带来三个后果，每一条都会落到你的代码里。

**后果一：它不可回退。** 第 7 个词元一旦采样出来，就进入第 8 个词元的输入。
模型没有「撤销上一个词」的机制——所谓「重新生成」，是**从头再采样一遍**，
不是修订。所以：让模型「把刚才那句话改一个字」时，你得到的是重写，不是编辑。

**后果二：错误会级联。** 因为每一步都基于前一步的输出，一个跑偏的开头会被后续步骤
当成事实继续推理。这就是为什么长链推理会「越错越自信」，也是为什么工程上更可靠的做法是
**让它分步输出并逐步校验**，而不是一次要一个长结论。第 3.4、3.5 节讲的两套机制——
规划与工具调用——本质上都是在给这个循环加外部校验点。

**后果三：成本与长度同向增长。** 你按输入与输出的词元数付费，而每一轮的**历史都会重发一次**。
一个 10 轮的对话，第 10 轮要重新读前 9 轮的全部内容——所以多轮对话的成本不是线性的，
是**随轮数加速累积**的。第 3.1.6 节的「前缀缓存」就是专门对付这一条的。

还有一个容易被忽略的性质：**输出是采样的结果，不是确定性计算结果**。同一个提示
跑两次得到不同答案是正常现象，官方文档也把它写成前提——所以它建议把生产应用
**固定到具体的模型快照**，并建立评测来观察行为变化。这条建议背后是一个很实用的推论：
任何依赖「模型每次都给同样答案」的设计都是脆弱的，正确做法是把不确定性放进测试里，
而不是假设它不存在（第 3.9 节讲怎么测）。

## 3.1.2 注意力：Transformer 取代 RNN 的那一步

2017 年的那篇论文提出了 Transformer，它的主张是**完全用注意力机制**做序列建模，
把循环（RNN）与卷积整个去掉。论文给的两条理由是：质量更好，而且**更可并行**——
翻译任务上它用 8 块 GPU 训练 3.5 天就拿到了当时最好的成绩。

「更可并行」是理解这个架构为什么统治了今天的钥匙。RNN 必须一个词一个词地算，
第 100 个词要等前 99 个算完；注意力把整段序列**一次摊开**算，位置之间没有先后依赖。
训练能并行，模型才能做大——这条因果链比任何架构细节都重要。

### 自注意力在算什么

三个角色，都是同一个输入序列乘上三组**可训练**的矩阵得到的：

| 记号 | 名称 | 直觉 |
| --- | --- | --- |
| Q | 查询（Query） | 「我在找一个什么样的位置」 |
| K | 键（Key） | 「我这里有什么，可供别人匹配」 |
| V | 值（Value） | 「如果被选中，我交出什么内容」 |

计算分四步：**①** `Q` 与所有 `K` 做点积得到相似度分数；**②** 分数除以 `√d_k`；
**③** 用 softmax 归一化成权重（和为 1）；**④** 用权重对 `V` 加权求和得到输出。
第 ① 步和第 ④ 步就是「注意力」的字面含义：**按相关性加权**。

顺序、因果这些概念在这里完全不存在——注意力本身只管相关性。这是 3.1.3 要补的位置编码
与掩码存在的原因，也是 Transformer 最容易被误解的一点。

### 为什么必须除以 √d_k

这是本章唯一一个「公式必须懂」的地方，因为它直接决定模型能不能学到东西。
`Q` 与 `K` 做点积时，**向量的维度 d_k 越大，点积的数值范围越大**——
这不是模型学出来的，是数学必然。而 softmax 对输入尺度极度敏感：数值一散开，
它就会把几乎全部权重压到一个位置上。

下面这段代码把这件事测出来（`numpy`，无随机性以外的假设）：

```python
import numpy as np
rng = np.random.default_rng(7)

def softmax(x):
    e = np.exp(x - x.max(axis=-1, keepdims=True))
    return e / e.sum(axis=-1, keepdims=True)

for d in (8, 64, 512):
    q, k = rng.normal(size=(64, d)), rng.normal(size=(64, d))
    raw, scaled = q @ k.T, (q @ k.T) / np.sqrt(d)
    a_raw, a_sc = softmax(raw), softmax(scaled)
    # exp(信息熵) 是「有效参与的位置数」：越接近 1 说明注意力越垮塌到单个位置
    eff = lambda a: float(np.exp(-(a * np.log(a + 1e-12)).sum(axis=-1)).mean())
    print(f"d_k={d:>4} 未缩放 max={a_raw.max(axis=-1).mean():.3f} "
          f"有效位置={eff(a_raw):>5.2f} ｜ 缩放后 max={a_sc.max(axis=-1).mean():.3f} "
          f"有效位置={eff(a_sc):>5.2f}")
```

实跑输出：

```text
d_k=   8 未缩放 max=0.361 有效位置=12.67 ｜ 缩放后 max=0.088 有效位置=44.43
d_k=  64 未缩放 max=0.826 有效位置= 1.90 ｜ 缩放后 max=0.106 有效位置=41.53
d_k= 512 未缩放 max=0.958 有效位置= 1.15 ｜ 缩放后 max=0.111 有效位置=39.53
```

这张表就是「为什么要缩放」的全部答案。维度 512 时，不缩放的注意力**平均只关注 1.15 个位置**，
权重最大 0.958：softmax 已经把其他 63 个位置压成了 0。而 `d_k=64` 时就已经塌到 1.9 个位置了。
除以 `√d_k` 之后，有效位置回到 39–44 之间——模型才**有得选**。
用更直白的话说：**不缩放的话，注意力在训练刚开始时就退化成「只看一个位置」**，
梯度几乎传不到别处，模型学不会「综合考虑上下文」。

同一组随机数据下，分数的分布范围也说明了这件事：未缩放时是 `-111.7 ~ 81.5`，
缩放后是 `-4.9 ~ 3.6`。softmax 在这么大的区间上只会输出 0 与 1。

### 多头：用不同的子空间看同一段话

一个注意力头只能给出一组权重。**多头注意力**把 Q/K/V 拆成若干份并行计算，
每份用独立的投影矩阵，最后拼接回来。它的价值是**多样性**：有的头学出「关注相邻词」，
有的学出「关注主语」，有的学出「关注标点结构」——它们在同一层里同时工作。
这也解释了一件事：你不能通过「看某一层的注意力图」来断言模型的推理依据，
因为依据分散在多个头、多层里。

### 代价：长度是平方的

每个位置都要和**所有**位置算相似度，所以自注意力的计算量随序列长度**平方**增长：
长度翻倍，注意力开销变成 4 倍。这条事实解释了你后面会反复遇到的现象：
长上下文的**价格与延迟**不是线性上升的；也解释了为什么整个行业都在研究
「怎么少算一点注意力」（稀疏注意力、分页注意力、各种近似方法）。
第 3.1.6 节的 KV 缓存是另一个方向的优化：它不去减少计算，而是**避免重复计算**。

## 3.1.3 只留解码器：位置、掩码与前馈

Transformer 原版是**编码器-解码器**结构：编码器读入完整输入（没有掩码，任意位置可见），
解码器一边看自己已生成的部分一边参考编码器输出。但自回归生成只需要后者——
今天的对话模型绝大多数**只保留了解码器**。这个取舍带来四件必须知道的事。

**位置编码。** 注意力本身不含顺序信息：把输入打乱，权重矩阵的运算结果只是行序换了，
「谁在前」这个信息消失了。所以必须在输入里**注入位置**。原论文用正弦余弦函数
（不同频率的波），现代开源模型则多用旋转位置编码（RoPE），
做法是把位置信息编进向量的旋转里，好处是相对位置的表达更自然。
对你的实际影响只有一条：**上下文里的顺序是有含义的**，同样的内容换个位置放，
效果会变——这就是为什么「把重要信息放末尾」这类提示技巧不是玄学。

**因果掩码。** 生成第 n 个词时，模型不能看到第 n+1 个词——否则训练时它就等于
「抄答案」。做法是在注意力分数上把未来位置置为负无穷，softmax 之后它们的权重就是 0。
这一机制叫因果掩码（causal mask）。它同时保证了训练与推理的一致性：
训练时一次算完整个序列，每个位置看到的上下文宽度与推理时逐词生成完全相同。

**残差连接与层归一化。** 每个子层外面套一条「把输入直接加到输出上」的旁路（残差），
再配一层归一化。两者一起解决的是**深层网络的训练稳定性**：没有残差，
梯度要穿过几十层注意力，梯度消失（或爆炸）几乎必然发生。

**前馈层。** 每个位置还会过一遍两层全连接网络（中间夹一个激活函数）。
注意力负责「在位置之间搬运信息」，前馈层负责「对每个位置各自做非线性变换」。
两者交替堆叠，就是一层 Transformer。

| 零件 | 解决的问题 | 不做会怎样 |
| --- | --- | --- |
| 位置编码 | 注意力没有顺序概念 | 词序被打乱，语义全丢 |
| 因果掩码 | 生成时不能看到未来 | 训练就等于抄答案，推理时行为不一致 |
| 残差连接 | 深层网络的梯度传递 | 层数一深就训不动 |
| 层归一化 | 各层数值尺度漂移 | 训练不稳定、对学习率极度敏感 |
| 前馈层 | 位置级的非线性变换 | 表达力退化为加权平均 |

这四件里，只有**位置编码**和**掩码**会直接影响你写提示的方式；
另外两件是训练侧的事，知道它们在那就够了。

## 3.1.4 训练三阶段：预训练、指令微调与偏好对齐

一个能对话的模型不是一次训练出来的，而是三段工序的产物。**分清这三段，
你就能分清「模型的哪些毛病是甩不掉的、哪些是当前一代的取舍」。**

| 阶段 | 数据形态 | 它在改什么 | 你的体感 |
| --- | --- | --- | --- |
| 预训练 | 海量无标注文本 | 学会语言规律与世界知识 | 知识有截止日期；会「续写」而不是「回答」 |
| 指令微调（SFT） | 人工写的示范问答 | 学会按指令作答的**格式与风格** | 它开始「回答」而不是「续写」 |
| 偏好对齐（RLHF / DPO） | 对多个回答的人工排序 | 学会人类**更偏好**哪种回答 | 更有用、更少有害输出，但会出现回避与套话 |

第三段的效果有多强，有一组被反复引用的对照：在人类评估里，
**13 亿参数的 InstructGPT 的输出比 1750 亿参数的 GPT-3 更受人偏好**——
参数量差 100 倍。同时它的真实性更好、有害输出更少，而在公开 NLP 数据集上
**性能回退很小**。

这组数字值得停一下。它说明两件事：

- **「能力」与「可用性」是两个维度。** 大模型可能更懂，但不一定更听话；
  对齐做的事是让模型**用它的能力去满足你的意图**。
- **对齐是有代价的，只是这个代价量级不靠直觉。** 业内把它叫做「对齐税」——
  为了让模型更安全更听话而牺牲的那部分原始能力。上面对照里它很小，
  但这并不是永远如此，也不是所有能力都只是「很小回退」。

对你的工程结论：**不要用「模型更大」来解释「回答不满意」**。
同样一个模型，指令写得清楚与不清楚的差距，经常大于换一个更贵的模型。
第 3.2 节的提示工程、第 3.5 节的工具调用，都是在拿这一段的结论做基础。

## 3.1.5 词元：分词器决定的成本与边界

现在进入最直接影响你账单的一节。

模型不读字符，它读**词元（Token）**：一串整数 id，每个 id 对应一段字节。
把文本切成词元序列的组件叫**分词器**（tokenizer），主流实现是 BPE 及其变体——
从字节开始，反复把最常一起出现的片段合并成一个新的词元。合并的规则是**训出来的**，
所以不同模型、不同代的分词器切同一段文本，结果可以差很多。

这件事的工程含义是：**你不能用「字数」估算成本与长度，只能用「词元数」；
而词元数没有通用换算比。** 下面用官方开源编码器实测一组样例：

```python
import tiktoken

samples = {
    "英语句子": "The quick brown fox jumps over the lazy dog.",
    "中文句子": "快速的棕色狐狸跳过了那只懒狗。",
    "中英同义（中）": "上下文窗口不是记忆，它是这一次推理的工作台。",
    "中英同义（英）": "The context window is not memory; it is the workbench for this one inference.",
    "Java 代码": 'public class A { public static void main(String[] a) { System.out.println("hi"); } }',
    "JSON": '{"model": "claude-opus-5", "max_tokens": 1024, "messages": [{"role": "user", "content": "hi"}]}',
    "日文": "お誕生日おめでとう",
}
for name, s in samples.items():
    counts = {e: len(tiktoken.get_encoding(e).encode(s)) for e in
              ("r50k_base", "cl100k_base", "o200k_base")}
    print(f"{name:<14}字符 {len(s):>3} ｜ " + " ｜ ".join(f"{e} {n:>3}" for e, n in counts.items()))
```

实跑输出（三列分别是 2020 年、2023 年、2024 年三代编码器）：

```text
英语句子        字符  44 ｜ r50k_base  10 ｜ cl100k_base  10 ｜ o200k_base  10
中文句子        字符  15 ｜ r50k_base  33 ｜ cl100k_base  27 ｜ o200k_base  15
中英同义（中）    字符  22 ｜ r50k_base  41 ｜ cl100k_base  25 ｜ o200k_base  16
中英同义（英）    字符  77 ｜ r50k_base  17 ｜ cl100k_base  17 ｜ o200k_base  17
Java 代码      字符  84 ｜ r50k_base  24 ｜ cl100k_base  21 ｜ o200k_base  21
JSON          字符  95 ｜ r50k_base  39 ｜ cl100k_base  35 ｜ o200k_base  35
日文            字符   9 ｜ r50k_base  14 ｜ cl100k_base   9 ｜ o200k_base   8
```

### 三条结论，每一条都反直觉

**一、英文的字符/词元比非常稳定：约 4.5–4.8 字符/词元**（上表英语句 44 ÷ 10 = 4.4；
换一段 157 字符的英文是 33 个词元 = 4.76）。这个数字十年没变，可以直接当经验值用。

**二、「中文更贵」在 2026 年已经过期。** 同样意思的一句话：
`r50k_base` 下中文 41 个词元 vs 英文 17 个（**2.41 倍**），`cl100k_base` 降到 1.47 倍，
而 `o200k_base` 下是 **0.94 倍——中文反而略便宜**。同样是 22 个汉字的短句，
词元数从 41 掉到 16，**降了 61%**。这不是措辞问题，是分词器的训练语料变了。
所以凡是「中文比英文贵两倍」之类的说法，先问一句：**哪一代分词器、哪个模型？**
而且这件事会**往回走**：官方文档明确写过，较新的一代模型换了新分词器，
**同样的文本会产生大约多 30% 的词元**。换模型时长度与预算必须重新测，不能沿用旧结论。

**三、一个词元可以不是合法的 UTF-8 边界。** 词元是字节片段，不保证落在字符边界上。
实测表情符号 `🎉🎉` 会被切成两个词元：`b'\xf0\x9f\x8e'` 与 `b'\x89'`——
一个完整的四字节 emoji 被从中间劈开，两个片段单独解码都是非法 UTF-8。
所以按字符做截断会切坏内容；**按词元截断则会切坏字节**——
这正是官方提醒「单个词元解码可能是有损的」的原因，也是为什么长文本处理要
在**语义边界**（段落、句子）上切，而不是在字符或词元计数上切（第 5.2 节展开）。

### 怎么数，以及为什么工具定义特别贵

不要用字数估算，**用官方接口数**。Anthropic 提供了 `count_tokens` 接口，
输入与生成请求相同（含系统提示、工具定义、图片、文档），返回输入词元数。
三个细节要记住：它是**估算值**，与实际计费可能略有出入；它支持工具定义但不支持
服务端工具与 URL 形式的图片；**系统为优化自动添加的词元不计费**。

工具定义的开销常被低估。实测一个字段齐全的单工具 JSON Schema 是 **59 个词元**，
而一句用户提问（`What is the status of order 42?`）只有 9 个——**工具定义是提问的 6.6 倍**。
一个挂了 20 个工具的应用，每一轮都在为此付费，哪怕这一轮一个工具都没用上。
这就是第 3.5 节要讲「工具怎么设计」和第 6.4 节要算「成本怎么控」的起点。

## 3.1.6 上下文窗口：工作台，不是记忆

**上下文窗口（Context Window）**的官方定义是：模型生成回答时**能参考的全部文本**，
包括它自己生成的那部分。官方把它比作模型的**工作记忆**，并特意区分了它与训练语料——
后者是模型「知道」的东西，前者是它「此刻看得到」的东西。

窗口里到底装了什么？清单比多数人以为的长：

- 系统提示（system）
- `messages` 里的每一条消息，**包括工具返回结果、图片、文档**
- 你的**工具定义**
- 模型这一轮生成的输出，**包括思考词元**（thinking tokens）

后两项是最容易被漏算的：工具定义每轮都在；开了思考模式的模型，
思考部分也按输出计费并占用窗口。当前主力模型的窗口在 **20 万到 100 万词元**之间，
其中大窗口模型的单次输出上限是 12.8 万词元——**输入与输出共用同一个窗口**，
所以要给回答留出空间，而不是把窗口塞满。

### 「塞满就好」是错的：上下文腐烂

官方文档里有一句非常关键的话：**上下文不是越多越好；词元数增长时，准确率与召回会下降**，
这个现象叫**上下文腐烂**（Context Rot）。原因是多层的，本章已经能讲清其中两层：
注意力在长序列上会被稀释（3.1.2 的权重分布），以及位置带来的远近偏好（3.1.3）。
更完整的机制在 3.6 与 5.4 两节展开。

工程结论只有一句：**上下文是预算，不是仓库**。你往里放什么，是设计决策，
需要像对待数据库查询一样对待它——放少了模型不知道，放多了它抓不住重点。

### KV 缓存与前缀缓存：两条不同的省钱路径

模型生成每个词元时，都要用到前面所有词元的中间结果（注意力里的 K 与 V）。
把它们缓存起来避免重复计算，就叫 **KV 缓存**（KV Cache）。它有两个重要性质：
**内存占用随对话增长而增长**，而且大小是动态的；管理不当会造成碎片与重复，
直接限制服务器能同时处理多少请求。这正是「分页注意力」（PagedAttention）那套工作的出发点——
用类似操作系统虚拟内存分页的办法管理 KV 缓存，把浪费压到接近零，并支持请求间共享，
在同等延迟下把吞吐提高了 2–4 倍。

对你的产品来说，更直接的是**前缀缓存**（Prompt Caching）：把提示的**前缀**
（按 `工具 → 系统提示 → 消息` 的顺序）缓存在服务端，下次命中就不必重新处理。
官方给出的经济账很具体：默认缓存 5 分钟、命中读取约为**基础输入价的 0.1 倍**，
写入约 1.25 倍，可付费延长到 1 小时。三个容易踩的点：

- **缓存的是前缀，不是内容**。把变动的东西（时间戳、用户输入）放在前面，
  后面的稳定内容就永远命不中——顺序决定能不能省钱。
- **缓存的生命周期从请求开始算**，流式输出的耗时也算在里面。
- **命中的词元照样占上下文窗口**。缓存改变的是你付多少钱，不是它占不占地方。

### 超了会怎样

输入本身就超过窗口，接口直接返回 `400`（提示过长）；而在较新的一代模型上，
「输入 + `max_tokens` 超过窗口」的请求会被**接受**，跑到窗口尽头时以
`stop_reason: model_context_window_exceeded` 这类结束原因停下——也就是说，
**超限不一定报错，可能只是被截断**。这类「静默降级」必须在代码里显式处理
（第 6.2 节的错误处理会展开）。另外，部分模型会把剩余预算注入上下文，
让你能在系统提示里要求它「留出足够的空间收尾」。

## 3.1.7 采样与不确定性：为什么同一个提示两次不一样

生成下一个词元时，模型输出的是**整个词表的概率分布**，最终选哪个由采样参数决定。
历史上最常见的两个是 `temperature`（把分布变平或变尖）与 `top_p`（只从累积概率
最高的那部分里采）。它们的存在意味着：**「同一个提示给两个答案」不是 bug，
而是接口的默认行为**。

这个默认行为正在被收回去。官方文档现在明确写着：**较新的一代模型不再支持
`temperature`、`top_p`、`top_k` 采样参数——传非默认值会直接返回 400**，
官方建议改用提示来引导行为。同一份文档还规定了另一条约束：
**开启思考时 `temperature` 必须为 1（或省略）**。

| 你以为 | 实际情况 | 你该怎么做 |
| --- | --- | --- |
| `temperature=0` 就是确定性输出 | 官方只承诺「更集中」，不承诺逐字复现；且新模型已不收这个参数 | 把非确定性当常态：写评测、给重试、要结构化输出 |
| 换个更高温度的模型「更有创意」 | 采样参数正在被移除，风格差异更多来自模型本身与提示 | 用提示与示例表达风格，不靠调参 |
| 同一个输入必然同一个输出 | 官方明确把非确定性写进文档，并建议固定模型快照 | 生产环境钉住快照版本，变更走评测 |

结论不是「没法控制」，而是**控制点换了位置**：从「调参数」换到
「写清提示 + 固定版本 + 建立评测」。第 3.2 与 3.9 两节就是这两件事的展开。

## 3.1.8 规模：Scaling Law 与「涌现」之争

最后一个事实，也是最容易被讲成神话的一个。

**规模确实遵循规律。** 早期工作发现，模型的损失随参数量、数据量、算力呈**幂律**下降，
可以外推与预测。而 Chinchilla 那条结论改写了「怎么花预算」：在固定算力下，
**参数量与训练词元数应当等比例增长**——模型翻一倍，数据也该翻一倍，
而不是一味把模型做大、数据不增。论文用同一份算力训练出的 700 亿参数模型，
在大量下游任务上**稳定超过** 2800 亿参数的 Gopher、1750 亿的 GPT-3 与
5300 亿的 Megatron-Turing NLG。这是「数据不足的大模型并不划算」的直接证据。

**「涌现能力」则没有那么稳。** 一说认为存在**涌现能力**：某些能力在小模型上完全不存在，
模型一大就突然出现，且无法由小模型的表现外推出。另一说给了替代解释：
那种「突然出现」很可能来自**评测指标的选择**——非线性或不连续的指标
（比如答对率、精确匹配）会把平滑的进步画成断崖；换成线性或连续的指标，
能力随规模的进步是**平滑可预测**的。论文做了三组验证，包括在视觉任务上
**用指标选择人为制造出「从未见过的涌现」**。

这一节的工程价值在于：**它教你怎么读能力声明**。

- 看到「某模型出现了新能力」，先问**用的什么指标**。指标能把连续进步打扮成突变。
- 看到「小模型做不到」先别下结论说「能力不够」——可能是提示方式不匹配，
  也可能是你的评测太粗糙（这正是第 3.9 节要建评测的原因）。
- 看到「模型越大越好」，回到 Chinchilla：**在给定预算下，数据与参数要配比**，
  「大」本身不是收益来源。

## 3.1.9 把这九个事实变成九个判断

本章的事实都可以直接折算成工程决策。这张表是本章的收口，也是后面各章的入口。

| 事实 | 你写代码时的判断 |
| --- | --- |
| 自回归、一次一个词元 | 长输出会慢且贵；长任务要拆步、逐步校验，别指望一次给完 |
| 不可回退 | 「改一个字」是重写；需要局部修改就重新给上下文再说一遍 |
| 输出是采样的 | 生产固定模型快照 + 建评测；不要让业务逻辑依赖逐字复现 |
| 注意力是平方复杂度 | 长上下文的价格与延迟不是线性的，长度预算是硬约束 |
| 位置编码有实际影响 | 重要指令与资料的**位置**要设计，不要只是「塞进去」 |
| 训练分三段 | 「不顺从」用提示与结构解决，不是靠换更大的模型 |
| 词元由分词器决定 | 用官方接口数，不用字数估；换模型要重新测长度与成本 |
| 上下文窗口是工作台 | 窗口是预算：清理、压缩、按需加载；不要把它当数据库或记忆 |
| 前缀缓存按前缀命中 | 稳定内容放前面、变动内容放后面，顺序即省钱 |

下一章（3.2）把注意力从「模型内部」转到「你说什么」；3.3–3.6 讲智能体的四个部件；
3.7–3.9 讲多智能体、安全与评测。而第 5 篇的 RAG 与第 6 篇的成本工程，
本质上都是本章这几条约束在系统层面的应对方案。

## 常见坑

1. **用字数估成本。** 中文在旧分词器下 1 个字能顶到近 2 个词元，新分词器下不到 1 个。
   估错了不会报错，只会让预算一路超。
2. **把「中文比英文贵」当成常识写进设计。** 它取决于模型代次；同一句话在三代编码器下
   的比值是 2.41 / 1.47 / 0.94。
3. **按字符或词元截断长文本。** 词元不保证是合法 UTF-8 边界（`🎉🎉` 会被劈成两个词元），
   按计数截断会切出坏字符。在段落或句子边界切。
4. **把窗口大小当记忆容量。** 官方文档写得很直接：词元越多，准确率与召回会下降。
   塞满窗口换来的往往不是「更懂」，而是「更糊涂」。
5. **把易变内容放在提示开头。** 前缀缓存按前缀命中，时间戳、随机 ID、
   当次用户输入一旦放在前面，后面再稳定的内容也命不中，白付全价。
6. **忘记工具定义与思考词元都占窗口、都要计费。** 一个工具定义就可能是
   一句用户提问的 6.6 倍；开了思考模式，思考部分按输出计费。
7. **依赖 `temperature=0` 保证可复现。** 官方只承诺概率更集中，不承诺逐字复现；
   较新模型已不接受该参数。要可复现，就固定模型快照并建立评测。

## 本章小结

- 模型只做一件事：预测下一个词元。由此推出不可回退、错误级联、成本随长度增长，
  以及输出是采样的、不是确定性计算的。
- Transformer 用注意力取代循环，换来可并行——这才是它统治今天的根本原因。
  注意力四步：点积、除以 `√d_k`、softmax、加权求和。
- `1/√d_k` 防的是 softmax 垮塌：实测 d_k=512 时不缩放平均只关注 1.15 个位置，
  缩放后回到 39 个以上。
- 因果掩码保证「看不见未来」，位置编码补上顺序，残差与归一化让深层可训练，
  前馈层提供位置级的非线性。
- 训练分三段：预训练给知识，指令微调给格式，偏好对齐给偏好。13 亿参数的
  对齐模型在人类偏好上胜过 1750 亿参数的原始模型。
- 词元由分词器决定：英文约 4.5–4.8 字符/词元且稳定；中文从 0.54 涨到 1.38 字符/词元；
  较新模型换分词器后同样文本约多 30% 词元。词元可以不是合法 UTF-8 边界。
- 上下文窗口是工作台：工具定义、思考词元都计入；词元越多，准确率与召回下降（上下文腐烂）。
- KV 缓存省的是重复计算，前缀缓存省的是钱；两者都不能让词元不占窗口。
- 采样参数正在被新模型移除；不确定性是官方承认的设计前提，对策是固定快照 + 评测。
- 规模遵循幂律，但「涌现」可能是指标造成的假象——读能力声明先看指标。

## 练习

1. **测你自己的文本。** 用 3.1.5 的脚本量你项目里真实的提示词（含系统提示与工具定义），
   分别用 `cl100k_base` 与 `o200k_base` 数一遍，算出两代之间的差幅。
   然后回答：如果换到新代分词器的模型，你当前的输入长度上限要打几折？
2. **复现缩放实验。** 把 3.1.2 的代码改成固定 `d_k=512`、只用一行（`n=1`）的 Q/K，
   比较缩放前后「有效位置」的变化，并解释为什么单行时这个指标会趋近 1。
3. **设计一个省钱的前缀。** 给你一个「客服问答」应用的提示结构（系统提示、
   产品手册全文、历史对话、用户当前问题），指出哪些内容应该放前面以命中前缀缓存，
   哪些会导致缓存永远失效，并写出改进后的顺序。
4. **做一次指标实验。** 找 5 个同类任务（例如从一段文本里抽字段），
   用两种指标评价：一种连续（字段字符相似度），一种离散（完全正确 / 不正确）。
   把你的结果画出来，说明离散指标为什么会显得「要么不会、要么全会」——
   这就是「涌现」争论的核心机制。
