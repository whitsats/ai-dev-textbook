## 3.3.1 从一次回答到一个循环

你问一个对话模型「帮我规划周末去京都的旅行，预算 5000 元」，它会给你一份像样的清单：清水寺、金阁寺、附近的酒店区域、大概的机票区间。然后你去携程查机票、去订房网站比价、把每天行程排进日历——**清单是模型给的，活是你干的**。

同样的请求交给一个代理循环，过程是这样的：先查往返机票的实时价格，再比三家酒店并筛掉超预算的，按景点开放时间排出每天的顺序，把各项加起来核一遍总数，最后交付一份包含航班号、酒店名与每日时间表的计划。**清单和活都是它干的。**

这个差别不是「谁更聪明」，而是**有没有回路**。一次调用是「文本进、文本出」：模型看不到自己的建议在真实世界里会发生什么，也没有机会根据结果调整。代理循环把动作的结果重新放回模型的输入里，于是下一步可以基于事实，而不是基于假设。

把这份能力拆开，是三条：

| 能力 | 说的是什么 | 缺了它会怎样 |
| --- | --- | --- |
| 自主感知 | 能理解当前任务与环境状态 | 只能回答被问到的那一句，接不上上一轮的结果 |
| 自主决策 | 能定计划并按情况调整 | 只会照着一张写死的流程图走 |
| 自主执行 | 能调用工具真的把事做完 | 停在「建议」这一步，剩下交给用户 |

一句话概括它的构成：**大语言模型（大脑）＋ 工具（手脚）＋ 记忆（经验）＋ 规划（智慧）**。第 3.3.4 节展开这四个部件。

> 💡 **提示**：判断一个系统是不是 Agent，不要数它调了几个工具，而要问一句：**「下一步做什么」是谁决定的？**
> 由你的代码决定，那是工作流；由模型决定，那才是 Agent。这一条是本章余下部分的主线。

## 3.3.2 分界线：工作流还是 Agent

「Agent」这个词被用得很松：有人指「长时间自主运行、自己找活的系统」，有人指「按固定流程走几遍 LLM 的实现」。厂商的官方文档把这两类合称**代理式系统**，但在架构上给了一条明确的分界线：

> **工作流**是「大语言模型与工具由预定义的代码路径编排」的系统；
> **Agent**是「大语言模型动态决定自己的流程与工具调用、并始终掌握如何完成任务」的系统。

按这条线，把上一个例子改造成工作流是这样的：先调一次模型抽出行程要素，再调一次查机票，再调一次排日程，最后调一次生成文案——四次调用，谁先谁后由你的代码固定。同一个任务，两种形态都能交付东西；区别在于**路径是谁定的**。

官方给的选型建议是「先找最简方案，只在需要时才增加复杂度」：很多应用的答案就是**一次调用加上检索与示例**，连工作流都不必写。代理式系统是用**延迟与成本**换任务表现的，这笔交易得先算清楚。

三个问题问下来，选型基本就定了：

| 自测问题 | 答「是」的含义 |
| --- | --- |
| 步骤能不能事先枚举出来？ | 能枚举就写工作流：可预测、可测试、可回归 |
| 步数能不能估出来？ | 估得出（比如固定 3–5 步）就用工作流，别为不确定性付费 |
| 环境能不能给出可信的反馈？ | 能（编译通过、测试通过、接口返回）才值得让模型自己决策：它有了判断进展的锚 |

反过来，**必须**用 Agent 的场合有很集中的特征：任务是开放式的、步骤数根本无法预测、路径不可能写死，而且你有基本把握它的决策是可信的。官方点名的两个域是客服与编码——它们恰好都满足「有明确成功标准、能形成反馈回路、能被人监督」这三条。编码尤其典型：代码正确性可以由测试自动验证，于是循环里的每一步都有一个不依赖模型自己的真值。

> ⚠️ **注意**：自主性越强，**成本越高、错误越容易累积**。这不是保守，是算术：单步 95% 的可靠性走 10 步只剩约 60%（推导见第 3.2.9 节）。
> 所以官方对代理系统的要求是两条：在沙箱环境里充分测试，配上护栏（第 3.3.6 节）。

## 3.3.3 代理循环的四步与四种终止条件

一个代理循环，每一轮只做四件事：

1. **模型决策**：把「任务 + 已有历史 + 工具清单」交给模型，模型产出下一步——要么调用某个工具，要么给出最终答案。
2. **运行时执行**：你的代码校验这个决定（工具存在吗？参数合法吗？权限允许吗？），然后真的去执行。
3. **结果回填**：把工具返回的内容作为一条新消息追加进历史。
4. **再问一次**：带着变长的历史回到第 1 步。

这个形状来自 ReAct（Reasoning + Acting）：让模型**把推理过程与行动交替生成**，而不是先想完再做。论文给出的证据很具体：在 HotpotQA 与 Fever 上，通过与一个简单的 Wikipedia API 交互，ReAct **克服了思维链里常见的幻觉与错误传播**；在两个交互式决策基准上（ALFWorld 与 WebShop），它比模仿学习与强化学习方法分别高出 **34 与 10 个绝对成功率百分点**，而提示里只放了一两个示例。论文还强调了一条副产品：带推理痕迹的轨迹**比只有动作的轨迹更好读**，人能看懂它为什么那么做。

有一条要认清的变化：ReAct 是 2022 年的提示写法，行动靠约定文本格式（`Action: Search("...")`）再事后解析。今天模型把行动产出成结构化的工具调用（见第 3.5 节），轨迹更规整、解析失败更少，但**循环的形状没变**——真正稳定的那部分不是文本格式，是「决策 → 执行 → 回填」这个回路。

### 谁负责让循环停下来

模型只承诺一件事：「我说完了」。它不承诺**一定**会说。所以终止条件是运行时的责任，至少有四类：

| 终止条件 | 触发时机 | 触发时用户拿到什么 |
| --- | --- | --- |
| 模型给出最终答案 | 正常结束 | 答案 |
| 步数上限 | 步数用完 | **没有答案**，除非运行时补救 |
| 时长上限 | 超过墙钟时间（工具慢、外部接口挂住） | **没有答案**，除非运行时补救 |
| 成本预算 | 词元或金额超过上限 | **没有答案**，除非运行时补救 |
| 卡死检测 | 连续若干步没有进展 | **没有答案**，除非运行时补救 |
| 人工中断 | 用户或值班同学叫停 | 取决于实现 |

后五种都会让用户面对一个「跑了半天、什么都没给」的界面，所以工程上要配一步**强制收口**：不再要求模型继续探索，而是给它一句明确指令——用已有信息给出当前最好的答案，并说明还缺什么。代价是额外一次模型调用，换来的是「有交代」而不是「失败」。

同一批「模型」在不同运行时策略下的表现差别有多大，可以直接量：

```python
def run(policy, max_steps=8, budget=99, repeat_limit=3, wrap_up=True):
    """一轮 = 一次模型调用 + 一次工具执行。返回 (步数, 模型调用次数, 终止原因, 有答案)。"""
    trace, seen, calls = [], [], 0
    def stop(reason, answered):
        nonlocal calls
        if answered:
            return len(trace), calls, reason, True
        if wrap_up:                     # 强制收口：再要一次「基于已有信息的最佳答案」
            calls += 1
        return len(trace), calls, reason + "（收口）", wrap_up
    for n in range(1, max_steps + 1):
        if n > budget:
            return stop("预算用完", False)
        d = policy(n)
        calls += 1
        trace.append(d)
        if d.get("final"):              # 终止条件一：模型给答案
            return stop("模型给出最终答案", True)
        seen.append((d["action"], d["arg"]))
        if repeat_limit and len(seen) >= repeat_limit and len(set(seen[-repeat_limit:])) == 1:
            return stop("卡死检测：连续 3 次相同动作", False)   # 终止条件二：卡死
    return stop("步数上限", False)        # 终止条件三：硬上限

def scripted(*decisions):               # 把「模型」换成一个背好的剧本
    return lambda n: decisions[min(n - 1, len(decisions) - 1)]

models = {
    "会收敛的模型": scripted({"action": "search", "arg": "AI 市场规模"},
                             {"action": "calc", "arg": "2440 * 0.3"},
                             {"final": True}),
    "重复同一动作": scripted({"action": "search", "arg": "更详细"}),
    "换着说法没进展": scripted(*[{"action": "search", "arg": f"AI 市场规模 第{n}次"} for n in range(1, 12)]),
}
print("模型 | 运行时策略 | 步数 | 模型调用 | 终止原因 | 有答案")
for name, pol in models.items():
    for label, kw in [("只设硬上限 8 步", dict(repeat_limit=None, budget=99)),
                      ("加卡死检测", dict()),
                      ("再加预算 4 步", dict(budget=4))]:
        steps, calls, why, ok = run(pol, **kw)
        print(f"{name} | {label} | {steps} | {calls} | {why} | {ok}")
```

输出：

```text
模型 | 运行时策略 | 步数 | 模型调用 | 终止原因 | 有答案
会收敛的模型 | 只设硬上限 8 步 | 3 | 3 | 模型给出最终答案 | True
会收敛的模型 | 加卡死检测 | 3 | 3 | 模型给出最终答案 | True
会收敛的模型 | 再加预算 4 步 | 3 | 3 | 模型给出最终答案 | True
重复同一动作 | 只设硬上限 8 步 | 8 | 9 | 步数上限（收口） | True
重复同一动作 | 加卡死检测 | 3 | 4 | 卡死检测：连续 3 次相同动作（收口） | True
重复同一动作 | 再加预算 4 步 | 3 | 4 | 卡死检测：连续 3 次相同动作（收口） | True
换着说法没进展 | 只设硬上限 8 步 | 8 | 9 | 步数上限（收口） | True
换着说法没进展 | 加卡死检测 | 8 | 9 | 步数上限（收口） | True
换着说法没进展 | 再加预算 4 步 | 4 | 5 | 预算用完（收口） | True
```

三个可以直接用的结论：

- **同一个卡死的模型，只设硬上限时跑了 8 步、第 9 次调用才收口；加上卡死检测后第 3 步就停，模型调用从 9 次降到 4 次。**卡死检测不是锦上添花，它省的是真金白银。
- **「换着说法没进展」这一行，卡死检测完全拦不住**：动作参数每次都不同，`(action, arg)` 从没重复过，于是照样跑满 8 步。这是第 3.3.7 节要处理的问题。
- **每一行都要额外付出一次收口调用**才拿到答案。这笔账要算进预算：把上限设成「最后一步必须留给收口」，而不是「跑完上限再看」。

> 💡 **提示**：三个数字一起看——**步数、模型调用次数、工具调用次数**。它们不相等：一轮里可能有多个工具调用（并行），而收口是不带工具调用的一次模型调用。
> 日志里只记「跑了 5 步」，等于把成本和错误都藏起来了。

## 3.3.4 能力四要素：模型、规划、工具、记忆

把 Agent 拆成部件，最常见的切法是四个。它们各自要解决一个不同的问题：

| 部件 | 在循环里的角色 | 典型失效 | 判据 | 详见 |
| --- | --- | --- | --- | --- |
| 大语言模型 | 控制器：每一轮读上下文、产出下一个决策 | 决策与事实不符（幻觉）、格式不可解析 | 决策格式的解析失败率 | 第 3.1、3.2 节 |
| 规划 | 把任务拆成步骤、安排先后与依赖 | 计划一开始就错，后面越走越偏 | 中途重规划的次数与时机 | 第 3.4 节 |
| 工具 | 唯一能读写外部世界的通道 | 选错工具、参数不合、返回超长 | 工具选择准确率、失败重试率 | 第 3.5 节 |
| 记忆 | 短期在上下文窗口，长期在外部存储 | 上下文腐烂、历史越滚越贵 | 每轮输入词元的增长曲线 | 第 3.6 节 |

三条容易误解的地方，先说清楚：

**模型不是「思考者」，是控制器。** 它每一轮只做一件事：读一遍上下文，产出下一段。它看不到工具内部的真实状态——数据库里到底有几行、接口返回的 JSON 有几个字段——它只能看到运行时回填给它的那段文本。所以「模型判断错了」的很大一部分其实要归到「回填的文本没把关键信息带上」。「大脑」这个比喻在工程上只对一半：它不会自己长出手脚，手脚是你接上去的。

**规划不等于把步骤一次列全。** 有静态计划（先列清单再照做）与边做边定（每一步再决定下一步）两档，选择依据是「你事先能不能知道需要哪几步」。这一档差别很大，展开在第 3.4 节。

**记忆是两层，不在一个地方。** 短期记忆就是上下文窗口里的历史——它随轮数增长、按词元付费、会腐烂；长期记忆要落到外部存储，靠检索按需取回。Anthropic 的记忆工具给出的形态值得记：模型看到的是一批记忆文件，读写**由你的应用在客户端执行**，路径限定在固定的记忆目录下（要防路径遍历），存储位置与租户隔离由你控制。更常见的做法是「即时检索」——不把全部相关材料预先塞进提示，而是让模型需要时再去取。

### 两套切法，回答的不是同一个问题

上面这套四要素是「能力从哪来」的切法。工程与面试里还有另外两套，把它们摆在一起，就不容易打架了：

| 出处 | 切法 | 强调什么 |
| --- | --- | --- |
| 厂商官方（Anthropic《Building effective agents》） | **增强型大语言模型**：模型 + 检索 + 工具 + 记忆，作为代理式系统的基础构件 | 构件可组合，复杂度按需叠加 |
| 官方运行时（OpenAI Agents SDK） | **Agent = 模型 + 指令 + 工具**，另有护栏、交接、会话等原语 | 运行时该提供哪些积木 |
| 控制论视角（面试题里问得最多） | **感知 → 决策 → 行动**，循环往复 | 时间上发生了什么、如何保证实时与不阻塞 |

三套切法的关系：四要素说**能力从哪来**（模型、规划、工具、记忆），三段式说**时间上发生了什么**（把上下文组装与工具返回看作感知，把模型的一次输出看作决策，把工具执行看作行动）。所以「感知层 / 认知层 / 执行层 / 记忆层」四层架构里的每一层，都能在四要素里找到归属——认知层是模型与规划，执行层是工具集，记忆层就是记忆。

> ⚠️ **注意**：不要用 `temperature=0` 来「让推理更稳定」。较新一代模型已不接受该参数的非默认值（传了返回 400，见第 3.1.7 节）。
> 循环里稳定的正确来源是固定的模型快照、受约束的结构化决策，加上一套回归评测。

## 3.3.5 六种编排：五种工作流加一个 Agent

官方把常见形态归纳成五种工作流加一个自主 Agent。这六种不是要你选一个，而是**从最简到最复杂的阶梯**——先试简单的，只有在它能证明不够的时候才往上走：

| 形态 | 一句话定义 | 适用判据 | 失效迹象 |
| --- | --- | --- | --- |
| 提示链（Prompt Chaining） | 任务切成固定几步，前一步的输出喂给后一步，中间可加程序化校验 | 任务能干净地拆成固定子任务；愿意用延迟换准确率 | 中间产物格式不稳，校验一直拦 |
| 路由（Routing） | 先分类输入，再交给专门的处理链或专门的模型 | 类别明确、分类准确；不同类别的处理方式差异大 | 分类错了，后面全错 |
| 并行化（Parallelization） | 分节：独立子任务同时跑后汇总；投票：同一任务跑多次取多数 | 子任务互相独立；或需要多视角提高置信度 | 汇总逻辑成了新的瓶颈 |
| 编排者–工作者（Orchestrator–Workers） | 一个中心模型动态拆任务、分给工作者、汇总结果 | 子任务无法预先确定（改几个文件取决于任务本身） | 中心模型成了单点，拆解质量决定上限 |
| 评估者–优化者（Evaluator–Optimizer） | 一个模型生成、另一个给评价，循环改进 | 评价标准清晰，且「有人把意见说清时输出确实能变好」 | 评估者与生成者同源，只会互相附和 |
| 自主 Agent | 模型自己决定流程与工具调用，直到任务完成 | 开放问题、步数不可预测、路径写不死、环境能给真值 | 成本失控、错误累积、卡死（第 3.3.7 节） |

**什么时候不该做 Agent**，是一份比上面更有用的清单：

- 路径能枚举 → 写工作流。可测试、可回归，比「让模型决定」便宜一个数量级。
- 只需要把输入变成输出、不需要访问外部世界 → 单次调用加检索与示例通常就够。
- 没有可信的成败信号 → 循环里的每一步都在猜，模型无法判断自己是否在靠近目标。
- 失败不可逆、又没人看着 → 先把人类在环补上（第 3.3.6 节），再谈自主。

### 循环的账单：按「轮数 × 累计历史」付费

循环贵在哪里，用一个具体任务量一遍就够了。固定部分是系统提示 59 词元 + 3 个工具定义 99 词元 + 任务 22 词元 = **180 词元**；模型每一轮都会**把完整历史重新发一遍**：

| 轮次 | 该轮新增 | 该轮输入（＝累计历史） | 累计计费输入 |
| ---: | ---: | ---: | ---: |
| 1 | 31 | 211 | 211 |
| 2 | 33 | 244 | 455 |
| 3 | 33 | 277 | 732 |
| 4 | 20 | 297 | 1,029 |
| 5 | 22 | 319 | 1,348 |
| 6 | 46 | 365 | 1,713 |
| 7 | 16 | 381 | 2,094 |

七轮下来，计费输入合计 **2,094 词元**，而固定部分被重复发送 7 次、单独占 **1,260 词元（60%）**。同样这点内容写成三步固定工作流，是 **615 词元**——只有循环的 **29%**。这就是工作流的性价比来源：它不是更快，是**更少次地重复发送同一段前缀**。

省钱手段有顺序，别跳步：

1. **先减轮数**：卡死检测与预算上限（第 3.3.3 节）是回报最高的两项。
2. **再减固定部分**：工具定义是固定开销的大头（这里 3 个工具 99 词元，而任务本身只有 22 词元）。挂 20 个工具的应用，每一轮都在为用不到的定义付钱（第 3.1.5 节量过同一现象）。
3. **最后才谈缓存**：前缀缓存能把重复前缀的读取价格降到约十分之一（第 3.1.6 节），但它有门槛——**最小可缓存长度按模型是 1,024 到 4,096 词元，比它短的提示不会缓存，而且不报错**。上面这个例子固定部分只有 180 词元，标了缓存标记也不会命中，`usage` 里的缓存字段会是 0。看不到报错就当没事发生，是这类优化最常见的翻车方式。

## 3.3.6 护栏与人类在环

自主性带来的风险不是「模型会不会乱说话」，而是**它真的会去执行动作**。护栏（Guardrail）就是在动作发生前后加的那几道门：

| 位置 | 拦什么 | 具体做法 | 拦不住什么 |
| --- | --- | --- | --- |
| 输入侧 | 注入、越权请求、超范围问题 | 分类或规则先判一遍，命中就走预设回复 | 伪装成正常请求的越权 |
| 输出侧 | 不合规内容、不该外发的数据 | 写库/发信之前做一次校验 | 模型自己都没想到的敏感聚合 |
| 动作侧 | 危险操作、越界路径 | 沙箱、只读默认、白名单、路径校验 | 白名单内部的误用 |
| 资源侧 | 成本失控、被刷 | 步数/词元/金额预算、限流 | 预算内的浪费 |

两条来自官方运行时的实现细节值得照抄：

- **输入与输出校验可以和主流程并行跑，并且快速失败。** 把「判一遍」当成循环后面的一道串行关卡，会让每次请求都多等一整段延迟；并行做，命中问题时立刻中止。
- **护栏要在模型之前或写库之前，不能只在最后。** 输出校验写在解析之后、写库之前才有意义；写在解析成功之后但数据已经落库，等于没拦。

**人类在环**（Human in the Loop）是护栏的人肉版本，三个位置各有用途：执行**前**的审批（敏感动作，例如退款、删数据、发邮件）、执行**中**的检查点（长任务每完成一个阶段汇报一次，人能叫停）、阻塞时的**求助**（缺信息、缺权限时主动停下来问，而不是猜）。官方对代理系统的两条要求——沙箱环境充分测试、配好护栏——说的都是同一件事：**让不可逆的动作尽可能地少、尽可能地晚**。

## 3.3.7 五个已知难点：一张地图

循环能跑起来之后，坑的位置相当固定。这一节先把五个难点列清楚，各自给一条能立刻用上的判据，细节留给后面的章：

| 难点 | 现象 | 归因 | 先用的判据 | 详见 |
| --- | --- | --- | --- | --- |
| 卡死与无进展 | 反复调同一个工具，或换着说法查同一件事 | 模型没有「进展」这个概念，它只看当前上下文 | 连续相同动作 / 相同观察 / 无新事实（见下） | 本章 3.3.3、第 3.9 节 |
| 工具选择错误 | 该查库的去搜网页，参数填错 | 工具描述含糊、职责重叠 | 工具名与描述能不能让新人一次选对 | 第 3.5 节 |
| 上下文溢出 | 跑到十几轮后请求 400，或明显变傻 | 历史线性增长，窗口是预算不是仓库 | 每轮输入词元的增长曲线 | 第 3.6 节 |
| 错误处理 | 一个工具报错，整个循环崩掉或假装成功 | 把工具异常当成程序异常 | 工具失败后循环是否继续、有没有降级 | 第 3.5、3.8 节 |
| 成本失控 | 一个无关请求烧掉几十万词元 | 轮数乘以累计历史（第 3.3.5 节） | 单次任务的词元分布，而不是平均值 | 第 6 篇 |

卡死这一条值得单独立判据，因为**检测口径不同，能拦住的形态完全不同**。下面这组对照把两种常见卡死形态、四种检测口径摆在一起：

```python
TOOLS = {"search": lambda q: {"AI 市场规模": "2025 年全球 AI 市场约 2,440 亿美元",
                              "更详细": "无更多信息"}.get(q, "无结果")}

def run(policy, max_steps=8, same_action=None, same_obs=None, no_progress=True):
    seen_a, seen_o, info = [], [], set()
    for n in range(1, max_steps + 1):
        d = policy(n)
        a, obs = (d["action"], d["arg"]), TOOLS[d["action"]](d["arg"])
        seen_a.append(a); seen_o.append(obs)
        if same_action and len(seen_a) >= same_action and len(set(seen_a[-same_action:])) == 1:
            return n, f"同动作 × {same_action}"
        if same_obs and len(seen_o) >= same_obs and len(set(seen_o[-same_obs:])) == 1:
            return n, f"同观察 × {same_obs}"
        if no_progress and obs in info and n >= 3:   # 观察过的东西又出现一次
            return n, "无新事实"
        info.add(obs)
    return max_steps, "硬上限"

cases = {
    "换个说法、参数相同": lambda n: {"action": "search", "arg": "AI 市场规模"},
    "换了参数、结果相同": lambda n: {"action": "search", "arg": f"AI 市场规模 第{n}次"},
}
print("形态 → 检测口径 → 停在第几步")
for label, pol in cases.items():
    for det, kw in [("只数相同动作 × 3", {"same_action": 3}),
                    ("数相同动作 × 2", {"same_action": 2}),
                    ("数相同观察 × 2", {"same_obs": 2}),
                    ("数无新事实", {}),
                    ("什么都不检测", {"no_progress": False})]:
        n, why = run(pol, **kw)
        print(f"  {label} | {det} | 第 {n} 步（{why}）")
```

输出：

```text
形态 → 检测口径 → 停在第几步
  换个说法、参数相同 | 只数相同动作 × 3 | 第 3 步（同动作 × 3）
  换个说法、参数相同 | 数相同动作 × 2 | 第 2 步（同动作 × 2）
  换个说法、参数相同 | 数相同观察 × 2 | 第 2 步（同观察 × 2）
  换个说法、参数相同 | 数无新事实 | 第 3 步（无新事实）
  换个说法、参数相同 | 什么都不检测 | 第 8 步（硬上限）
  换了参数、结果相同 | 只数相同动作 × 3 | 第 3 步（无新事实）
  换了参数、结果相同 | 数相同动作 × 2 | 第 3 步（无新事实）
  换了参数、结果相同 | 数相同观察 × 2 | 第 2 步（同观察 × 2）
  换了参数、结果相同 | 数无新事实 | 第 3 步（无新事实）
  换了参数、结果相同 | 什么都不检测 | 第 8 步（硬上限）
```

读法是看括号里的口径：**在「换了参数、结果相同」这一行，真正拦住它的是「无新事实」，不是任何一栏数动作的写法**（参数每次都不同，动作从上到下都没重复过）。而「数相同观察」在两种形态下都在第 2 步就停，看起来最灵——它的代价是会误杀合法场景：轮询一个有状态的任务时，重复拿到「进行中」是正常的。

所以工程上的做法不是挑一个最灵的，而是**三个都装、阈值不同，再加上硬上限**：相同观察 × 5 报警、相同动作 × 3 直接停、硬上限兜底。别指望某一个公式能覆盖所有形态。

## 3.3.8 最小 Agent：一百行以内

框架把循环、工具注册、追踪记录、成本统计都包好了（第 3.4、3.5 节会讲 LangChain / LangGraph 的写法）。在用它之前，先手写一遍最小版本——不是为了造轮子，而是为了知道框架里的每个原语替换掉了哪几行代码。下面这个实现零依赖，模型用一个背好剧本的函数代替，其余部分与真实运行时的结构完全一致：

```python
"""最小 Agent：零依赖。把 policy 换成真实的模型调用即可。"""

TOOLS = {
    "search": lambda q: {"AI 市场规模": "2025 年全球 AI 市场约 2,440 亿美元",
                         "更详细": "无更多信息"}.get(q, "无结果"),
    "calc": lambda e: str(eval(e, {"__builtins__": {}})),
}

def run_agent(policy, task, max_steps=8, repeat_limit=3, budget=8):
    trace, seen, calls = [], [], 0
    def stop(reason, answered):
        nonlocal calls
        if answered:
            return trace, f"{reason}（共 {calls} 次模型调用）"
        calls += 1                                  # 强制收口：多要一次「最佳答案」
        return trace, f"{reason} → 触发强制收口（共 {calls} 次模型调用）"

    for n in range(1, max_steps + 1):
        if n > budget:
            return stop(f"预算用完（{budget} 步）", False)
        d = policy(task, trace)                     # 这一行就是一次模型调用
        calls += 1
        trace.append({"n": n, "thought": d["thought"], "action": d.get("action"),
                      "arg": d.get("arg"), "observation": None, "final": bool(d.get("final"))})
        if d.get("final"):
            return stop("模型给出最终答案", True)
        seen.append((d["action"], d.get("arg")))
        trace[-1]["observation"] = TOOLS[d["action"]](d["arg"])   # 执行动作 + 回填结果
        if repeat_limit and len(seen) >= repeat_limit and len(set(seen[-repeat_limit:])) == 1:
            return stop(f"连续 {repeat_limit} 次相同动作（第 {n} 步）", False)
    return stop(f"达到步数上限 {max_steps}", False)

def scripted(script):                               # 把「模型」换成一个背好的剧本
    return lambda task, trace: script[min(len(trace), len(script) - 1)]

good = scripted([
    {"thought": "先查市场规模", "action": "search", "arg": "AI 市场规模"},
    {"thought": "算 30% 是多少", "action": "calc", "arg": "2440 * 0.3"},
    {"thought": "信息够了，给结论", "final": True},
])
stuck = scripted([
    {"thought": "再搜一次更详细的", "action": "search", "arg": "更详细"},
])

for name, policy, kw in [("正常收敛", good, {}),
                         ("重复同一动作", stuck, {}),
                         ("重复同一动作 + 预算 2 步", stuck, {"budget": 2})]:
    trace, why = run_agent(policy, "比较 AI 市场规模与 30% 份额", **kw)
    print(f"\n=== {name} ===")
    print(f"终止：{why}｜步数 {len(trace)}｜工具调用 {sum(1 for t in trace if t['action'])} 次")
    for t in trace:
        tail = "→ 最终答案" if t["final"] else f"→ {t['action']}({t['arg']}) → {t['observation']}"
        print(f"  [{t['n']}] {t['thought']} {tail}")
```

输出：

```text
=== 正常收敛 ===
终止：模型给出最终答案（共 3 次模型调用）｜步数 3｜工具调用 2 次
  [1] 先查市场规模 → search(AI 市场规模) → 2025 年全球 AI 市场约 2,440 亿美元
  [2] 算 30% 是多少 → calc(2440 * 0.3) → 732.0
  [3] 信息够了，给结论 → 最终答案

=== 重复同一动作 ===
终止：连续 3 次相同动作（第 3 步） → 触发强制收口（共 4 次模型调用）｜步数 3｜工具调用 3 次
  [1] 再搜一次更详细的 → search(更详细) → 无更多信息
  [2] 再搜一次更详细的 → search(更详细) → 无更多信息
  [3] 再搜一次更详细的 → search(更详细) → 无更多信息

=== 重复同一动作 + 预算 2 步 ===
终止：预算用完（2 步） → 触发强制收口（共 3 次模型调用）｜步数 2｜工具调用 2 次
  [1] 再搜一次更详细的 → search(更详细) → 无更多信息
  [2] 再搜一次更详细的 → search(更详细) → 无更多信息
```

这段代码里的每个部分，在框架里都有对应的原语：

| 最小实现里的东西 | 框架里的对应 | 它真正替你解决的问题 |
| --- | --- | --- |
| `TOOLS` 字典 | 工具注册与 schema 生成 | 把函数签名变成模型能读的参数说明、校验入参 |
| `policy(task, trace)` | 一次模型调用 | 上下文组装、重试、错误映射 |
| `trace` 列表 | 追踪记录 | 可回放、可评测、可挂到可观测性平台 |
| `repeat_limit` / `budget` | 运行时上限与护栏 | 在框架里通常叫最大轮数与预算，别用默认值 |
| `stop()` 里的收口调用 | 提前停止策略 | 让「没做完」也有交付 |
| 无 | 交接 / 子代理 | 把子任务交给另一个 Agent，第 3.7 节 |
| 无 | 会话与长期记忆 | 跨任务保留状态，第 3.6 节 |

从这段最小实现走到生产，要补的是六件事：**决策用受约束解码**（第 3.2.4 节）、**每个工具都要有超时、重试与幂等**（第 3.5 节）、**追踪记录落盘并能回放**（第 3.9 节）、**预算按任务而不是按天**、**危险动作先过审批**（第 3.3.6 节）、**有一套跑得很快的评测集**（第 3.9 节）。这六件里没有一件是「换个更强的模型」能替代的。

## 3.3.9 三种视角与三条常见误解

同一套东西，从三个角度看会得到三组不同的工程问题。切换视角的用处是：你现在卡在哪一类问题上，就用对应的那一套问句去查。

| 视角 | 你会问的问题 | 主要产出 |
| --- | --- | --- |
| 把它当员工 | 它的职责边界在哪？输入什么、交付什么？错了怎么兜？ | 任务规格、输入输出契约、失败处理 |
| 把它当循环系统 | 一轮多长？跑几轮停？中途怎么调？ | 终止条件、预算、追踪记录与看板 |
| 把它当大脑加工具箱 | 要给它加什么能力？工具描述够清楚吗？ | 工具集设计、工具描述、执行效率 |

三条最常见的误解，都值得在面试里主动澄清：

> 🔥 **常见坑**：**「Agent 会从经验里学习」**。在一次运行里，模型权重一点没变。它看起来「学会了」的东西，其实是你写进记忆或规则文件、下次再检索回上下文里的内容。
> 这会直接影响设计：期待它自己变好，就会漏掉「把该记的记下来」这一步。

> 🔥 **常见坑**：**「步数越多越准」**。多步把单步错误相乘，同时每一步都在为累计历史付费（第 3.3.5 节）。步数上限不是安全垫，它是产品参数。

> 🔥 **常见坑**：**「模型会自己停下来」**。它只是**可能**会说完了；终止是运行时的责任。上限触发时的强制收口，决定了用户看到的是答案还是空白。

# app/agent/runtime.py（预算 / 追踪 / 终止判定）与 app/agent/loop.py（循环）——两文件节选合并
"""知舟的 Agent 运行时：预算、追踪、终止判定。

终止永远由运行时负责，不由模型负责——模型只提「下一步做什么」。
"""
from __future__ import annotations

import time
from collections.abc import Callable
from dataclasses import dataclass, field


@dataclass
class Budget:
    """一次任务的三类上限。时钟可注入，否则「超时」这条永远测不了。"""
    max_steps: int = 8
    max_tokens: int = 1200
    max_seconds: float = 30.0
    clock: Callable[[], float] = time.monotonic
    started: float = field(init=False, default=0.0)
    steps: int = 0
    tokens: int = 0

    def __post_init__(self) -> None:
        self.started = self.clock()

    def charge(self, tokens: int) -> None:
        self.tokens += tokens

    def begin_step(self) -> None:
        self.steps += 1

    def exhausted(self) -> str | None:
        if self.steps >= self.max_steps:
            return "步数上限"
        if self.tokens >= self.max_tokens:
            return "预算耗尽"
        return "墙钟超时" if self.clock() - self.started >= self.max_seconds else None


@dataclass
class TraceEntry:
    n: int
    thought: str
    action: str | None = None
    arg: str | None = None
    observation: str | None = None
    tokens: int = 0
    final: bool = False


@dataclass
class Trace:
    """每一步都记。两种卡死口径都留痕：动作序列 ＋ 观察集合。"""
    task: str
    entries: list[TraceEntry] = field(default_factory=list)
    calls_seen: list[tuple[str, str]] = field(default_factory=list)
    facts_seen: set[str] = field(default_factory=set)
    repeat_limit: int = 3

    def add(self, e: TraceEntry) -> None:
        self.entries.append(e)

    def stalled_by_action(self, action: str, arg: str) -> bool:
        """口径一：连续 N 次完全相同的动作（参数也一样）。"""
        self.calls_seen.append((action, arg))
        if len(self.calls_seen) < self.repeat_limit:
            return False
        return len(set(self.calls_seen[-self.repeat_limit:])) == 1

    def stalled_by_fact(self, observation: str) -> bool:
        """口径二：没有新事实。参数每次都不同、结果却一样时只有它拦得住。"""
        if observation in self.facts_seen:
            return True
        self.facts_seen.add(observation)
        return False


@dataclass
class LoopResult:
    answer: str | None
    steps: int
    calls: int
    tokens: int
    reason: str
    trace: Trace


def run_agent(task: str, policy, tools: dict, budget: Budget) -> LoopResult:
    """决策 → 执行 → 回填 → 再问。终止永远是运行时的责任。"""
    trace = Trace(task)

    def wrap_up(reason: str) -> LoopResult:
        """强制收口：不再探索，只要一个「基于已有信息的最佳答案」。"""
        budget.count_call()
        d = policy(task, trace, wrap_up=True)
        budget.charge(d.get("tokens", 0))
        return LoopResult(d.get("final_text"), budget.steps, budget.calls,
                          budget.tokens, f"{reason} → 收口", trace)

    while True:
        why = budget.exhausted()
        if why:
            return wrap_up(why)
        d = policy(task, trace)
        # 只有「真的问了一次模型」才计一次调用：一次响应里的第 2、3 个工具调用
        # 是排队执行，不再问模型，所以它花了步数但不该被记成模型调用（3.5.8）。
        if d.get("model_call", True):
            budget.count_call()
        budget.charge(d.get("tokens", 0))
        budget.begin_step()
        if d.get("final"):
            trace.add(TraceEntry(budget.steps, d["thought"], tokens=d["tokens"], final=True))
            return LoopResult(d["thought"], budget.steps, budget.calls, budget.tokens,
                              "模型给出最终答案", trace)
        action, arg = d["action"], d["arg"]
        if action not in tools:                  # 决策校验先于执行
            return wrap_up(f"工具 {action} 不存在")
        try:
            obs = tools[action](arg)
        except Exception as exc:                 # 工具异常不能拖垮循环
            obs = f"[工具失败] {type(exc).__name__}: {exc}"
        trace.add(TraceEntry(budget.steps, d["thought"], action, arg, obs, d["tokens"]))
        if trace.stalled_by_action(action, arg):
            return wrap_up(f"卡死：连续 {trace.repeat_limit} 次相同动作")
        if trace.stalled_by_fact(obs):
            return wrap_up("无新事实")

### 不能破坏什么

- **不动既有端点与表**：`agent_session` / `agent_message` 是新表，`user` / `article` / `comment` /
  `favorite` 一字不改；新路由前缀 `/api/v1/agent`，与文章、用户两套路由不交叉。
- **不把会话历史塞进既有表**：那些表有它们自己的更新入口与缓存，混进 Agent 历史会让两边都难维护。
- **追踪与记忆分开**：追踪（`trace`）里只留摘要指纹与观察的头 120 字符，正文不落追踪；
  会话表则相反，**正文必须落库**，否则第二次会话装配出来的上下文只是一串哈希。
  这个界线在 3.6 被写清过一次：3.5 的 `agent_message` 只存 `content_digest`（当时为了脱敏），
  结果记忆是假的——迁移补上 `content` 与 `tool_call_id`，同时把「能删、有保留期、能按用户清空」
  作为它的条件（第 3.6、3.8 节）。
- **两个工具都是只读的**：`search_article` / `read_article` 不会改变任何东西，
  所以这一节的循环即使失控也不会造成写侧副作用。写工具从 3.5 开始引入，并且一律带幂等键与人工确认。
- **上限不能照用默认值**：`max_steps` / `max_tokens` / `max_seconds` 三个都要按任务设；
  少设一个，就有一类「跑到底却没有答案」的路径没被覆盖。
- 自查：`python -m pytest tests/ -q` 全绿；`git grep -n "@router" app/api/` 确认既有路由未动。

## 常见坑

1. **现象**：任务跑了 30 秒返回「处理失败」。**原因**：只设了步数上限，没有收口调用，模型走到上限时手里只有一堆观察结果。**修法**：把上限的最后一步留给强制收口，指令写明「用已有信息给出最佳答案，并列出还缺什么」。
2. **现象**：日志显示 5 步，账单显示 11 次模型调用。**原因**：并行工具调用与检索压缩都会额外产生调用，只记「步数」掩盖了真实次数。**修法**：追踪记录里同时记步数、模型调用次数、工具调用次数与输入/输出词元。
3. **现象**：卡死检测从不触发，任务跑到超时。**原因**：只比较动作参数，模型换一种说法就绕过去了。**修法**：三个口径一起装——相同动作、相同观察、无新事实——再加硬上限。
4. **现象**：同一轮里工具调用一次比一次慢，最后超时。**原因**：把同步阻塞的工具（大文件解析、外部 API）直接塞进循环，没有超时。**修法**：每个工具独立设超时与重试上限，超时就返回一个明确的失败观察，让模型自己换路。
5. **现象**：上下文窗口被快速填满，模型开始答非所问。**原因**：工具返回的原始内容（整页 HTML、整个目录树）被逐字回填。**修法**：工具返回前先裁剪与摘要，只回填决策需要的那几个字段。

## 面试视角

「单代理循环」是 Agent 方向最基础的考点，题库里这一组的两道题正好是本章的两半：

- **「单代理循环的核心组成部分有哪些？」** 高分的答法不是背「感知、决策、行动」三个词，而是补上「它们之间靠什么连起来」：感知阶段收集环境信息、决策阶段依据状态定策略、行动阶段执行并影响环境，**循环的连续性与同步机制**（谁负责串起来、并行的动作怎么收敛）才是真正的工程内容。把「大语言模型 + 规划 + 工具 + 记忆」四个部件与这三段对应起来讲，答案会完整一层。
- **「单代理循环架构面临的主要设计难点？」** 问的是「感知信息的及时性与准确性、决策的计算复杂度、动作的时序控制」，以及稳定性、鲁棒性、扩展性，还有阻塞与延迟。答题时把「难点」和「手段」配对着说最有说服力：感知延迟 → 用最小必要上下文；决策复杂度 → 用受约束解码缩小输出空间、用路由把难问题分出去；动作时序 → 幂等 + 超时 + 重试；阻塞 → 异步与并行工具调用。

其它高频延伸问法：Agent 与工作流的区别（第 3.3.2 节，一定要答「下一步谁决定」而不是「谁调的工具多」）；Agent 为什么需要终止条件（第 3.3.3 节，答四种上限加收口）；多 Agent 什么时候必要（第 3.7 节，先答「多数场景单 Agent 够用」）。

## 本章小结

1. 判断一个系统是不是 Agent，看「下一步做什么」由谁决定：代码决定是工作流，模型决定才是 Agent。
2. 代理循环每轮四步：模型决策、运行时执行、结果回填、带着变长的历史再问一次。
3. ReAct 的价值是把推理与行动交替生成——论文的实测是 ALFWorld 与 WebShop 上分别高 34 与 10 个百分点，并且克服了纯思维链的幻觉与错误传播。
4. 终止条件是运行时的责任，至少四类：模型给答案、步数、时长、预算；卡死检测是第五类，效果最直接（同一模型从 9 次调用降到 4 次）。
5. 能力四要素是「能力从哪来」，感知–决策–行动是「时间上发生了什么」，两套切法不冲突。
6. 六种编排是从简到繁的阶梯，能写死路径就不要交给模型；循环的成本 = 轮数 × 累计历史，固定前缀常占大头（示例中 7 轮占 60%）。
7. 护栏要放在动作之前或写库之前，输入与输出校验可以并行、快速失败；人类在环的三个位置各有用途。
8. 一百行能写出可用的最小 Agent；从它到生产要补的是受约束解码、工具的超时重试幂等、追踪记录、按任务的预算、审批与评测集。

## 练习

- **基础**：把第 3.3.3 节的 `run()` 改成「模型调用次数上限」而不是「步数上限」，解释两者在什么时候会分叉（提示：一轮里可能有多个工具调用）。
- **进阶**：给第 3.3.8 节的最小 Agent 加一个 `observe_same` 口径的卡死检测，并构造一个能绕过「相同动作」但被它拦住的剧本来验证。
- **挑战**：用真实模型 API 替换 `policy`，接上两个真实工具（例如本地文件读取与一个 HTTP 接口），要求：每轮决策用受约束解码、工具全部带超时与重试、追踪记录落盘，并写一份三句话的说明——这一版为什么还不该上线。
